## 08:40, до открытия кабинета

Администратор учебного кабинета приходит за двадцать минут до первой пары. На двенадцати машинах нужно проверить свободное место, состояние службы удалённого доступа и наличие свежего файла с расписанием. Вручную это четыре команды на машину и почти час работы, если ничего не отвлекает. В понедельник отвлекает всё: одна машина не отвечает, на другой закончилось место, третью вчера переустановили.

В прошлом семестре проверку пропустили, и на машине с базой учебного проекта закончился диск. База остановилась в середине занятия, восстановление заняло остаток дня. Причина была не в поломке железа, а в том, что ручная проверка зависит от внимания человека и не оставляет следа.

**Сценарий администрирования это текстовый файл с последовательностью команд, который выполняет одну повторяемую работу и сообщает результат.** Он не заменяет администратора, а снимает с него монотонность: одинаковые команды выполняются одинаково, проверка не забывается, а вывод сохраняется в журнал.

Сценарий ценен не длиной, а повторяемостью. Один раз написанная проверка запускается каждое утро, её можно передать коллеге, положить в систему контроля версий и сравнить результат вчера и сегодня. Поэтому главный вопрос при написании не «какие команды я знаю», а «что должно быть на выходе и как понять, что работа не удалась».

## Из чего состоит сценарий

У сценария оболочки три обязательные части: оболочка, которая его исполняет, команды и способ запуска. Первая строка задаёт интерпретатор.

```bash
#!/usr/bin/env bash
```

Запись `#!/usr/bin/env bash` означает: найти программу `bash` в пути поиска и передать ей этот файл. Прямой путь `#!/bin/bash` тоже работает, но привязан к расположению программы. `env` удобнее для переносимых сценариев, хотя в учебной Ubuntu оба варианта дадут одинаковый результат.

Файл должен быть исполняемым. Права `rw-r--r--` позволяют читать сценарий, но не запускать его. Команда `chmod +x check-lab.sh` добавляет бит выполнения, после чего сценарий запускается как обычная программа.

```bash
cd ~/os-lab
mkdir -p bin logs
printf '%s\n' '#!/usr/bin/env bash' 'echo "стенд проверен"' > bin/hello.sh
chmod +x bin/hello.sh
./bin/hello.sh
```

Запись `./bin/hello.sh` запускает файл по относительному пути. Если написать просто `hello.sh`, оболочка станет искать программу в каталогах из переменной `PATH`, не найдёт её и вернёт ошибку `command not found`. Точка в начале пути означает текущий каталог, и это осознанное решение: не каждый файл из текущей папки должен запускаться по имени.

Сценарий читается сверху вниз, как рецепт. Оболочка разбирает строку, подставляет переменные, делит результат на слова и только потом запускает команду. Почти все ошибки новичка происходят на этапе подстановки и разбиения на слова, а не в самих командах.

## Переменные, кавычки и подстановки

Переменная хранит строку или число и задаётся без пробелов вокруг знака равенства.

```bash
name="учебный стенд"
count=12
echo "Проверяю $name, машин: $count"
echo 'Проверяю $name, машин: $count'
```

Первый `echo` подставляет значения, второй печатает текст буквально. Двойные кавычки разрешают подстановку переменных и команд, одинарные запрещают. Это различие важнее, чем кажется: путь с пробелом внутри ломает команду, если его не обернуть в двойные кавычки.

```bash
dir="$HOME/os-lab/учебные материалы"
mkdir -p "$dir"
```

Без кавычек оболочка разбила бы строку на два аргумента и создала два каталога с неверными именами. С кавычками создаётся один каталог. Правило простое: подставляйте переменную в кавычках, пока не доказано, что разбиение на слова нужно.

Результат команды подставляется через `$(...)`. Так в сценарий попадает дата, имя машины или число файлов.

```bash
today=$(date +%F)
report="$HOME/os-lab/logs/report-$today.log"
printf 'Отчёт за %s: %s\n' "$today" "$report"
```

`date +%F` печатает дату в формате `2026-11-03`, а `printf` подставляет её в шаблон. `printf` предпочтительнее `echo` для отчётов: он одинаково обрабатывает пробелы, проценты и переводы строк.

У сценария есть аргументы. `$0` это имя самого сценария, `$1` первый аргумент, `$#` их число, `$@` весь список. Проверка числа аргументов защищает от запуска без параметров.

```bash
if [ "$#" -ne 1 ]; then
  echo "Использование: $0 каталог" >&2
  exit 2
fi
target="$1"
```

Запись `>&2` направляет сообщение в поток ошибок, а не в обычный вывод. Это позволяет отделить диагностику от данных: отчёт можно перенаправить в файл, а ошибка всё равно останется на экране.

> [!PITFALL] Пробел вокруг знака равенства
> Строка `name = "стенд"` запускает команду `name` с аргументами `=` и `стенд`, а не создаёт переменную. Оболочка сообщит `command not found`. Присваивание всегда пишется слитно: `name="стенд"`.

## Условия, циклы и функции

У каждой команды есть код возврата: `0` означает успех, ненулевое число означает ошибку. Оболочка хранит код последней команды в `$?`, но проверять его вручную почти не нужно: для этого есть `if`, `&&` и `||`.

```bash
if [ -d "$HOME/os-lab/logs" ]; then
  echo "каталог журналов есть"
else
  echo "каталог журналов отсутствует"
fi
```

Квадратные скобки это команда `test`, поэтому пробелы внутри обязательны. `-d` проверяет каталог, `-f` обычный файл, `-e` существование, `-z` пустую строку, `-n` непустую. Для чисел используются `-eq`, `-ne`, `-lt`, `-gt`, для строк `=` и `!=`. В bash есть улучшенные двойные скобки `[[ ... ]]`, где не нужно заключать переменные в кавычки, но в переносимых сценариях чаще пишут `[ ... ]` с кавычками.

Проверка условий через `&&` и `||` читается как «сделай это, и если успешно, сделай то».

```bash
mkdir -p "$HOME/os-lab/logs" && echo "каталог готов"
command -v ssh >/dev/null || echo "клиент ssh не установлен" >&2
```

Первая строка выполняет вторую команду только при успехе. Вторая печатает предупреждение, если `ssh` не найден. `command -v` ищет программу в `PATH` и возвращает успех, если она есть.

Ветвление по нескольким вариантам удобно оформлять через `case`. Он читается лучше длинной цепочки `elif`.

```bash
case "${1:-status}" in
  status) echo "проверка состояния" ;;
  start)  echo "запуск проверки" ;;
  stop)   echo "остановка" ;;
  *)      echo "неизвестная команда: $1" >&2; exit 2 ;;
esac
```

Запись `${1:-status}` подставляет значение по умолчанию, если аргумент не передан. Это дешёвый способ сделать сценарий удобным: без аргумента он показывает состояние, с аргументом выполняет действие.

Цикл `for` перебирает список значений или файлы по маске.

```bash
for machine in ubuntu-lab win-lab; do
  echo "проверяю $machine"
done

for file in "$HOME"/os-lab/logs/*.log; do
  [ -e "$file" ] || continue
  printf '%s: %s строк\n' "$file" "$(wc -l < "$file")"
done
```

Проверка `[ -e "$file" ] || continue` нужна на случай, когда маска не совпала ни с одним файлом: bash подставит саму строку с звёздочкой, и без проверки цикл попытается обработать несуществующий файл.

Цикл `while read` читает файл построчно и не теряет пробелы, если указать `IFS=` и `-r`.

```bash
while IFS= read -r line; do
  case "$line" in
    *ERROR*) echo "ошибка: $line" ;;
  esac
done < "$HOME/os-lab/logs/check.log"
```

`IFS=` отключает обрезку пробелов по краям, `-r` запрещает трактовать обратную косую черту как спецсимвол. Без них строки журнала могут измениться до неузнаваемости.

Функция выносит повторяющийся блок и даёт ему имя. Внутри функции полезно объявлять переменные локальными, иначе они останутся в сценарии после вызова.

```bash
log() {
  local level="$1"
  shift
  printf '%s %-5s %s\n' "$(date '+%F %T')" "$level" "$*" | tee -a "$LOG"
}
```

`shift` сдвигает аргументы влево, поэтому после него `$*` содержит только текст сообщения. `tee -a` одновременно печатает строку и дописывает её в файл журнала. Такой функции достаточно, чтобы все сообщения сценария выглядели одинаково.

Соберём рабочий сценарий проверки стенда. Он проверяет свободное место и службу `ssh`, пишет журнал и возвращает ненулевой код, если нашёл проблему.

```bash
#!/usr/bin/env bash
set -euo pipefail

LOG_DIR="$HOME/os-lab/logs"
REPORT="$LOG_DIR/check-$(date +%F).log"
WARN_PERCENT=80
LOG="$REPORT"

mkdir -p "$LOG_DIR"
: > "$REPORT"

log() {
  local level="$1"
  shift
  printf '%s %-5s %s\n' "$(date '+%F %T')" "$level" "$*" | tee -a "$LOG"
}

check_disk() {
  local path="$1"
  local used
  used=$(df --output=pcent "$path" | tail -n 1 | tr -dc '0-9')
  if [ "$used" -ge "$WARN_PERCENT" ]; then
    log "WARN" "$path занят на ${used}%"
    return 1
  fi
  log "OK" "$path занят на ${used}%"
  return 0
}

main() {
  local failed=0
  check_disk "$HOME" || failed=$((failed + 1))
  if systemctl is-active --quiet ssh; then
    log "OK" "служба ssh работает"
  else
    log "FAIL" "служба ssh не работает"
    failed=$((failed + 1))
  fi
  if [ "$failed" -gt 0 ]; then
    log "TOTAL" "проблем: $failed"
    exit 1
  fi
  log "TOTAL" "проверки пройдены"
}

main "$@"
```

Разберём ключевые строки. `set -euo pipefail` включает три защиты: выход при ошибке, ошибку при обращении к необъявленной переменной и ошибку в конвейере, если упала любая его часть. `: > "$REPORT"` очищает файл перед новым запуском, чтобы отчёт не смешивался со вчерашним. `df --output=pcent` печатает только процент, `tail -n 1` берёт строку с числом, `tr -dc '0-9'` оставляет цифры. `return 1` сообщает вызывающей стороне о проблеме, а `failed=$((failed + 1))` считает такие случаи.

Запуск сценария вручную выглядит так:

```text
2026-11-03 08:41:12 OK    /home/student занят на 38%
2026-11-03 08:41:12 OK    служба ssh работает
2026-11-03 08:41:12 TOTAL проверки пройдены
```

Код возврата после такого запуска равен нулю. Если служба остановлена, в журнале появится строка `FAIL`, итог `проблем: 1`, а код возврата станет равен единице. Именно код возврата читает планировщик и система мониторинга, а не текст на экране.

## Пакетный файл Windows

В Windows исторический аналог сценария оболочки это пакетный файл с расширением `.bat` или `.cmd`. Его исполняет `cmd.exe`, а не PowerShell. Пакетный файл короче и работает без настройки политики выполнения, но его язык беднее: строки, а не объекты, слабая обработка ошибок и запутанная работа с переменными внутри циклов.

Простейший пакетный файл начинается с отключения эха команд и включает локальную область переменных.

```bat
@echo off
setlocal
set "LOG=%USERPROFILE%\os-lab\logs\check.log"
if not exist "%USERPROFILE%\os-lab\logs" mkdir "%USERPROFILE%\os-lab\logs"
echo %DATE% %TIME% старт проверки>>"%LOG%"
if exist "%USERPROFILE%\os-lab\data\report.csv" (
  echo файл найден>>"%LOG%"
) else (
  echo файл не найден>>"%LOG%"
  exit /b 1
)
```

`@echo off` убирает печать каждой команды, `setlocal` ограничивает переменные файлом. Запись `set "LOG=..."` с кавычками вокруг всего присваивания защищает от пробела в конце строки. Обращение к переменной идёт через `%LOG%`. Условие `if exist` проверяет файл или каталог, `exit /b 1` возвращает код ошибки, не закрывая окно.

Цикл по файлам записывается через `for`, а разбор строк через `for /f`. В файле, в отличие от командной строки, переменная цикла требует двойного процента.

```bat
for %%f in ("%USERPROFILE%\os-lab\logs\*.log") do (
  echo обрабатываю %%~nxf
)
for /f "tokens=1,2 delims= " %%a in (list.txt) do (
  echo %%a %%b
)
```

`%%~nxf` оставляет имя и расширение без пути. `for /f` читает файл построчно, `tokens` выбирает поля, `delims` задаёт разделители. Внутри блока переменные, изменённые в цикле, видны только при отложенном раскрытии: `setlocal enabledelayedexpansion` и запись `!var!` вместо `%var%`. Без этого все итерации увидят старое значение.

Сравнение трёх языков удобно держать перед глазами.

| Задача | bash | cmd.exe | PowerShell |
|---|---|---|---|
| Переменная | `name="стенд"` | `set "name=стенд"` | `$name = 'стенд'` |
| Обращение | `$name` | `%name%` | `$name` |
| Условие | `if [ -f "$file" ]` | `if exist "%file%"` | `if (Test-Path $file)` |
| Цикл по файлам | `for f in *.log` | `for %%f in (*.log) do` | `foreach ($f in Get-ChildItem *.log)` |
| Код возврата | `$?`, `exit 1` | `%ERRORLEVEL%`, `exit /b 1` | `$LASTEXITCODE`, `exit 1` |
| Справка | `man`, `--help` | `/?` | `Get-Help` |

У пакетных файлов две типичные ловушки. Первая это кодировка: `cmd.exe` в русской Windows читает файл в кодовой странице 866, а сохранённый в UTF-8 текст может превратиться в мусор. Вторая это перенос строки: файл, сохранённый в Linux с одним переводом строки, может выполниться частично. Перед переносом пакетного файла между системами проверяют кодировку и конец строки.

Для новой работы в Windows чаще выбирают PowerShell: он работает с объектами, понимает Unicode и даёт нормальные сообщения об ошибках. Пакетный файл остаётся там, где нужна совместимость со старыми системами или совсем короткая команда.

::/gate

::gate Почему сценарий, который отлично работает в терминале, может упасть при запуске по расписанию?

## Запуск по расписанию

Ручной запуск требует человека. Планировщик запускает сценарий по времени, и тогда проверка не зависит от того, кто открыл кабинет.

В Linux расписанием заведует служба `cron`, а задачи пользователя хранятся в его таблице `crontab`. Команда `crontab -e` открывает таблицу в редакторе, `crontab -l` печатает её содержимое. Формат строки состоит из пяти полей времени и команды.

```cron
# минута час день_месяца месяц день_недели команда
*/15 * * * *  "$HOME/os-lab/bin/check-lab.sh" >> "$HOME/os-lab/logs/cron.log" 2>&1
0 8 * * 1-5   "$HOME/os-lab/bin/morning-report.sh"
30 23 * * 0   "$HOME/os-lab/bin/weekly-clean.sh"
@reboot       "$HOME/os-lab/bin/start-heartbeat.sh"
```

`*/15` означает каждые пятнадцать минут, `0 8 * * 1-5` означает в 08:00 с понедельника по пятницу, `30 23 * * 0` означает в 23:30 по воскресеньям. `@reboot` выполняет команду после загрузки. Символ `%` в crontab означает перевод строки, поэтому внутри команды его экранируют как `\%`; это частая причина странного поведения задач с датой.

У cron своё окружение. Он запускает команду через `/bin/sh` с минимальным набором переменных, обычно `PATH=/usr/bin:/bin`, и домашним каталогом пользователя. Ваш `PATH`, добавленный в `~/.bashrc`, не подхватывается, потому что `~/.bashrc` читают интерактивные оболочки, а не cron. Поэтому в сценарии для расписания либо указывают полные пути к программам, либо задают `PATH` явно.

```bash
PATH="$HOME/.local/bin:/usr/local/bin:/usr/bin:/bin"
export PATH
```

Второе отличие это отсутствие терминала. Команда, которая спрашивает подтверждение, в cron зависнет навсегда. Все интерактивные запросы из сценария для расписания убирают, а вывод и ошибки направляют в файл.

Проверить задание можно, не дожидаясь срока. `crontab -l` показывает, что запись принята. Журнал cron в Ubuntu смотрят через `journalctl -u cron` или `grep CRON /var/log/syslog`. Если сценарий не запустился, сначала проверяют права на файл, затем путь и только потом синтаксис.

В Windows расписанием управляет Планировщик заданий. Его настройки доступны через графический интерфейс, а для сценариев и учебных работ удобнее командная строка.

```bat
schtasks /Create /TN "OSLab Check" /SC DAILY /ST 08:00 ^
  /TR "powershell.exe -NoProfile -File %USERPROFILE%\os-lab\bin\check-lab.ps1"
schtasks /Query /TN "OSLab Check" /V /FO LIST
schtasks /Run /TN "OSLab Check"
```

Ключ `/SC DAILY` задаёт ежедневный запуск, `/ST` время, `/TR` команду. `schtasks /Query` показывает состояние, время последнего запуска и код результата. `/Run` запускает задание немедленно, что удобно для проверки. Удаление выполняется ключом `/Delete`, но перед ним стоит сохранить описание задания: восстановить его из памяти сложнее, чем посмотреть.

Современный способ в PowerShell использует командлеты и объекты, а не строки.

```powershell
$action = New-ScheduledTaskAction -Execute 'powershell.exe' `
  -Argument "-NoProfile -File `"$env:USERPROFILE\os-lab\bin\check-lab.ps1`""
$trigger = New-ScheduledTaskTrigger -Daily -At 8:00
Register-ScheduledTask -TaskName 'OSLab Check' -Action $action -Trigger $trigger
Get-ScheduledTaskInfo -TaskName 'OSLab Check'
```

`New-ScheduledTaskAction` описывает, что запускать, `New-ScheduledTaskTrigger` когда, `Register-ScheduledTask` регистрирует задание. Обратные кавычки в конце строки продолжают команду на следующей строке, а вложенные кавычки вокруг пути нужны, потому что путь может содержать пробелы.

| Задача | Linux | Windows |
|---|---|---|
| Посмотреть задания | `crontab -l` | `schtasks /Query /FO LIST` |
| Создать ежедневное | строка в `crontab -e` | `schtasks /Create /SC DAILY` |
| Запустить сейчас | выполнить файл вручную | `schtasks /Run` |
| Проверить результат | `journalctl`, файл журнала | код результата, история задания |
| Убрать задание | удалить строку | `schtasks /Delete` |

::/gate

::gate Что чаще всего ломает сценарий, который уже принят в расписание и выглядит правильным?

## Типичные ошибки и цена автоматизации

Первая ошибка касается переносов строк. Файл, созданный в Windows и перенесённый в Linux, хранит в конце строк символ возврата каретки. Оболочка читает первую строку как `#!/usr/bin/env bash\r` и не находит интерпретатор с таким именем. Симптом выглядит странно: `bad interpreter: No such file or directory`, хотя `bash` установлен. Лечится удалением символа `\r` из файла, например командой `sed -i 's/\r$//' script.sh`.

Вторая ошибка это отсутствие кавычек вокруг переменной. Пока путь простой, сценарий работает. Как только в имени появляется пробел или кириллица с нестандартной локалью, команда разваливается на части. Проверять нужно на пути с пробелом, а не на идеальном примере.

Третья ошибка связана с `set -e` и командами, которые возвращают ненулевой код не из-за сбоя. `grep` возвращает единицу, когда совпадений нет. В сценарии с `set -e` строка `grep -q ERROR "$LOG"` завершит работу, хотя отсутствие ошибок это нормальный результат. Правильно писать `if grep -q ERROR "$LOG"; then ...` или добавлять `|| true`, если код не важен.

Четвёртая ошибка это удаление по пустой переменной. Строка `rm -rf "$DIR"/*` при пустом `DIR` может стать `rm -rf /*`. Защита ставится до удаления: `: "${DIR:?переменная не задана}"`. Конструкция `${DIR:?}` завершает сценарий, если переменная пуста или не объявлена.

Пятая ошибка это права. Сценарий, доступный на запись всем, может изменить любой пользователь, а задание cron унаследует эти права. Файл сценария должен принадлежать администратору и не быть доступным на запись группе и остальным: `chmod 755` для исполняемого файла и `chmod 700` для каталога с секретами.

Шестая ошибка это отсутствие журнала. Сценарий, который молча завершился, невозможно отличить от сценария, который не запускался. Поэтому каждая ветка работы пишет строку с временем, результатом и причиной. Журнал должен быть понятен человеку, который откроет его через месяц.

> [!KEY] Сценарий проверяют на пустом каталоге, на несуществующем файле и на остановленной службе
> Успешный запуск доказывает только то, что успешный путь работает. Ошибки находятся там, где данных нет, служба выключена, а файл занят другим процессом.

Автоматизация имеет цену. Сценарий нужно написать, проверить, положить в систему контроля версий и поддерживать при изменении среды. Если работа выполняется один раз, дешевле сделать её руками. Если работа повторяется каждую неделю и занимает больше десяти минут, сценарий окупается уже на третьем запуске.

Есть и организационная цена. Сценарий, который запускается по расписанию, должен быть идемпотентным: повторный запуск не создаёт второй каталог, не дописывает строку дважды и не ломает уже настроенное состояние. Для этого используют `mkdir -p`, проверку `grep -q` перед добавлением строки и явные условия вместо бездумного повторения команд.

Наконец, сценарий не должен хранить пароли в открытом виде. Пароль в тексте файла виден всем, у кого есть доступ на чтение, и остаётся в истории правок. Для учебного стенда допустим ввод пароля при запуске, а для рабочей системы нужны отдельные механизмы хранения секретов, которые выходят за рамки этой лекции.

## Итоги

- Сценарий это исполняемый текстовый файл с интерпретатором в первой строке и командами, которые выполняются сверху вниз.
- Переменные подставляются в двойных кавычках, а результат команды берётся через `$(...)`; без кавычек путь с пробелом ломает команду.
- Код возврата `0` означает успех, ненулевое значение ошибку; `if`, `&&` и `||` строят ветвление по этому коду.
- `for` перебирает список, `while read` читает файл построчно, функция выносит повторяющийся блок и делает журнал единообразным.
- `cron` и Планировщик заданий запускают сценарий по времени, но дают минимальное окружение и не показывают диалогов.
- Сценарий для расписания проверяют на пустых данных, отсутствующих файлах и остановленных службах, а результат пишут в журнал.
