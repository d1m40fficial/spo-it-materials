## Пятница, 17:40

В учебной машине `ubuntu-lab` заканчивается место. За семестр в домашнем каталоге накопились отчёты и архивы, а сегодня система отвечает отказом на попытку установить программу:

```text
$ sudo apt install htop
...
E: You don't have enough free space in /var/cache/apt/archives.
```

Команда `df -h` показывает причину:

```text
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1        24G   24G     0 100% /
```

Диск заполнен полностью. Через несколько проверок выясняется, что место заняли не отчёты, а старые ядра, журналы и кеш пакетов. Удаление пары файлов освобождает 200 МБ, установка проходит, и через день история повторяется.

**Пакеты и диски это два разных слоя, и путать их причины нельзя.** Пакетный менеджер отвечает за состав программ, версии и зависимости. Файловая система отвечает за место, разделы и сохранность данных. Ошибка «нет места» приходит из второго слоя, хотя сообщение появляется в команде первого. Пока эти слои не разделены в голове, любое лечение будет временным.

Дальше разберём три вопроса. Как программа попадает в систему вместе со своими зависимостями. Как диск превращается в каталог, в который можно писать. И как проверить файловую систему, не разрушив её.

## Пакет это запись, а не папка с файлами

Программа в Linux почти никогда не устанавливается копированием каталога. Она приходит пакетом формата `.deb`, внутри которого лежат три части: метаданные с именем, версией и зависимостями, сценарии установки и удаления, а также сами файлы. Метаданные важнее файлов: именно по ним система понимает, что установлено, чего не хватает и что можно удалить.

Низкоуровневая работа с пакетами лежит на `dpkg`. Он умеет распаковать пакет, зарегистрировать его в базе и вызвать сценарии. Но `dpkg` не умеет скачивать пакеты из интернета и не решает зависимости. Если установить пакет командой `sudo dpkg -i file.deb`, а нужной библиотеки нет, установка завершится ошибкой с перечнем неудовлетворённых зависимостей.

Верхний уровень это `apt`. Он читает списки пакетов из репозиториев, строит план установки, скачивает недостающие пакеты, проверяет подписи и передаёт работу `dpkg`. Для обычной установки программ почти всегда нужен `apt`; `dpkg` остаётся для просмотра базы и для редких локальных файлов.

| Задача | Команда `apt` | Команда `dpkg` |
|---|---|---|
| Обновить списки пакетов | `apt update` | не умеет |
| Установить пакет с зависимостями | `apt install имя` | `dpkg -i файл.deb` без зависимостей |
| Удалить программу | `apt remove имя` | `dpkg -r имя` |
| Удалить вместе с настройками | `apt purge имя` | `dpkg -P имя` |
| Показать установленные пакеты | `apt list --installed` | `dpkg -l` |
| Показать файлы пакета | `apt-file list имя` | `dpkg -L имя` |
| Найти пакет по файлу | `apt-file search путь` | `dpkg -S путь` |

Команды `apt-file` работают после установки одноимённого пакета. Без него файлы установленного пакета показывает `dpkg -L`, а владельца файла `dpkg -S`. Для учебной работы этого достаточно: `apt-file` нужен, когда пакет ещё не установлен и нужно понять, в каком пакете лежит программа.

Посмотрим на живом примере. Сначала обновляются списки, затем ищется пакет, затем он устанавливается.


`apt-cache policy` показывает установленную версию, версию-кандидата и репозиторий, откуда она взята. `apt install` ставит не только `ncdu`, но и `libncursesw6`, потому что программа зависит от библиотеки. Пользователь не выбирал библиотеку: зависимость разрешил пакетный менеджер.

Проверить результат можно тремя командами. `dpkg -l ncdu` показывает строку состояния, `dpkg -L ncdu` перечисляет файлы пакета, `dpkg -S /usr/bin/ncdu` находит владельца файла.


Буквы `ii` в первой колонке означают: пакет нужно установить, и он уже установлен. Встречаются `rc`: пакет удалён, но его файлы настроек остались. Если после `apt remove` программа исчезла, а настройки в `/etc` остались, это нормальное поведение. `apt purge` удаляет и настройки, поэтому его применяют, когда нужно начать с чистого листа.

Разница между `apt upgrade` и `apt full-upgrade` тоньше, чем кажется. Обычный `upgrade` обновляет пакеты, но не удаляет установленные ради разрешения конфликтов. `full-upgrade` может удалить пакет, если новая версия системы с ним несовместима. В учебной машине безопаснее `upgrade`; `full-upgrade` применяют осознанно, прочитав список удаляемых пакетов.

`apt autoremove` удаляет зависимости, которые больше не нужны ни одному пакету. После удаления `ncdu` библиотека `libncursesw6`, скорее всего, останется нужна другим программам, а какой-нибудь узкий модуль уйдёт. Перед запуском полезно посмотреть список: команда печатает, что именно будет удалено, и ждёт подтверждения.

## Репозиторий, компоненты и доверие

`apt` не знает о программах сам по себе. Он читает списки из репозиториев, адреса которых записаны в `/etc/apt/sources.list` и в файлах каталога `/etc/apt/sources.list.d/`. Одна строка описывает репозиторий и его компоненты.

```text
deb http://archive.ubuntu.com/ubuntu jammy main restricted
deb http://archive.ubuntu.com/ubuntu jammy-updates main restricted
deb http://security.ubuntu.com/ubuntu jammy-security main restricted
```

Первое слово `deb` означает бинарный репозиторий, второе это адрес, третье кодовое имя выпуска, дальше перечислены компоненты. Для Ubuntu 22.04 кодовое имя `jammy`. Компонент задаёт правила распространения и поддержки.

| Компонент | Что содержит | Кто поддерживает |
|---|---|---|
| main | свободное ПО с полной поддержкой Canonical | Canonical |
| restricted | драйверы и прошивки с закрытым кодом | Canonical |
| universe | свободное ПО сообщества | сообщество |
| multiverse | ПО с ограничениями распространения | сообщество |

Если нужной программы нет в `main`, она часто лежит в `universe`. Именно оттуда пришёл `ncdu`. Включение компонента не требует переустановки системы: достаточно добавить слово в строку репозитория и выполнить `apt update`.

Вторая часть доверия это подпись. Каждый репозиторий подписан ключом, а `apt` проверяет подпись перед использованием списка. Если ключ неизвестен, появляется ошибка `NO_PUBKEY` или `The following signatures couldn't be verified`. Нельзя лечить её добавлением случайного ключа из интернета: сначала выясняют, кто владеет репозиторием и каким ключом он подписан.

Старый способ `apt-key add` считается устаревшим. Ключи хранят отдельными файлами в `/etc/apt/trusted.gpg.d/` или в каталоге ключей конкретного репозитория. Для учебной работы достаточно знать, что подпись проверяется, а не отключается флагом `--allow-unauthenticated` ради удобства.

Отдельно стоит `snap`. Это другой формат упаковки: программа приходит вместе с зависимостями в изолированном образе и обновляется автоматически. `snap list` показывает установленные образы, `snap install имя` ставит новый. `snap` и `apt` не заменяют друг друга: часть программ удобнее в одном формате, часть в другом. Смешивать их без причины не стоит, потому что у каждого свои каналы обновления и своё место на диске.

Опасная привычка это подключение репозитория другой версии Ubuntu. Пакеты `jammy` рассчитаны на библиотеки `jammy`. Если добавить репозиторий `focal` или `noble`, `apt` попытается поставить программу с зависимостями от другой версии системы. Иногда это срабатывает, чаще приводит к конфликту версий и поломке обновлений. Правило простое: репозиторий должен соответствовать выпуску системы, а сторонний репозиторий добавляют только с ключом и пониманием, кто его поддерживает.

Кеш пакетов лежит в `/var/cache/apt/archives`. Скачанные `.deb` остаются там после установки, поэтому кеш может занимать сотни мегабайт. `apt clean` очищает его полностью, `apt autoclean` удаляет только устаревшие файлы. Это первое место, куда смотрят при нехватке места, но не единственное.

## Диск: разделы, файловая система, точка монтирования

Физический диск это набор блоков. Прежде чем файл получит имя, диск проходит три преобразования.

1. **Таблица разделов** делит диск на области. Она хранится в начале диска и описывает, где начинается и заканчивается каждый раздел.
2. **Файловая система** внутри раздела описывает, какие блоки заняты, где лежат имена и атрибуты файлов.
3. **Точка монтирования** присоединяет файловую систему к общему дереву каталогов.

Пока раздел не отформатирован, в нём нет файловой системы, и смонтировать его некуда. Пока файловая система не смонтирована, её файлы не видны в дереве, хотя данные на диске уже записаны. Это не ошибка, а нормальное состояние: система видит раздел как устройство, но не как каталог.

Таблиц разделов две. MBR появилась в 1980-х и ограничена четырьмя первичными разделами и адресацией до 2 ТБ. GPT пришла ей на смену: до 128 разделов по умолчанию, 64-битная адресация, резервная копия таблицы в конце диска и контрольные суммы. Современные системы устанавливаются на GPT, а MBR остаётся для старых машин и небольших носителей.

| Признак | MBR | GPT |
|---|---|---|
| Максимум разделов | 4 первичных, дальше логические | 128 по умолчанию |
| Максимальный диск | около 2 ТБ | практически не ограничен |
| Защита таблицы | нет | CRC и резервная копия |
| Загрузка | BIOS | BIOS или UEFI |
| Типичное применение | старые системы, флешки | современные диски и виртуальные машины |

Посмотреть текущую картину можно командами `lsblk -f`, `sudo fdisk -l` и `sudo blkid`. `lsblk` показывает дерево устройств и файловые системы, `fdisk` таблицу разделов, `blkid` идентификаторы и метки.

```text
$ lsblk -f
NAME   FSTYPE FSVER LABEL UUID                                 FSAVAIL FSUSE% MOUNTPOINTS
sda
├─sda1 ext4   1.0         a1b2c3d4-1111-4a2b-9c3d-000000000001   18.2G    20% /
├─sda2
└─sda3
sdb
```

Виртуальные диски в этой машине называются `sda`, `sdb` и так далее. Буква не закреплена навсегда: при изменении порядка подключения диск может получить другое имя. Поэтому в постоянных настройках монтирования используют UUID, а не `/dev/sdb1`.

Форматирование создаёт файловую систему и уничтожает прежнее содержимое раздела. Команда `mkfs.ext4` пишет суперблок, таблицы inode, журнал и служебные области. После неё на разделе появляется пустая файловая система с меткой, которую можно задать флагом `-L`.

Монтирование связывает файловую систему с каталогом. Команда `mount /dev/sdb1 /srv/data` делает содержимое раздела видимым в `/srv/data`. Обратная операция `umount /srv/data` отключает его. Пока раздел смонтирован, файлы можно читать и писать; после отключения каталог снова показывает содержимое корневой файловой системы, а данные остаются на разделе.

## Новый диск за шесть команд

Вернёмся к ситуации с нехваткой места. Вместо удаления файлов добавим второй виртуальный диск. В настройках машины, в разделе «Носители», создаётся новый диск VDI на 10 ГБ и подключается к контроллеру SATA. После загрузки системы появляется устройство `sdb`.

```text
$ lsblk
NAME   MAJ:MIN RM  SIZE RO TYPE MOUNTPOINTS
sda      8:0    0   25G  0 disk
└─sda1   8:1    0   24G  0 part /
sdb      8:16   0   10G  0 disk
```

Диск `sdb` существует, но разделов на нём нет. Создадим таблицу GPT и один раздел на весь объём. Утилита `parted` умеет работать в неинтерактивном режиме, поэтому команды можно записать в сценарий.

```text
$ sudo parted /dev/sdb --script mklabel gpt
$ sudo parted /dev/sdb --script mkpart data ext4 1MiB 100%
$ sudo partprobe /dev/sdb
$ lsblk /dev/sdb
NAME   MAJ:MIN RM SIZE RO TYPE MOUNTPOINTS
sdb      8:16   0  10G  0 disk
└─sdb1   8:17   0  10G  0 part
```

Разберём параметры. `mklabel gpt` создаёт новую таблицу разделов и стирает старую. `mkpart data ext4 1MiB 100%` создаёт раздел с именем `data` от отметки 1 МиБ до конца диска. Отступ в 1 МиБ нужен для выравнивания: блоки диска и страницы памяти удобнее, когда границы совпадают. `partprobe` просит ядро перечитать таблицу, чтобы новый раздел появился без перезагрузки.

Теперь создадим файловую систему и точку монтирования.

```text
$ sudo mkfs.ext4 -L data /dev/sdb1
mke2fs 1.46.5 (30-Dec-2021)
Creating filesystem with 2617344 4k blocks and 655360 inodes
Filesystem UUID: 6f1c2a9e-7b3d-4c8a-9e10-2d4f6a8b0c11
Superblock backups stored on blocks:
        32768, 98304, 163840, 229376, 294912, ...
Allocating group tables: done
Writing inode tables: done
Creating journal (16384 blocks): done
Writing superblocks and filesystem accounting information: done

$ sudo mkdir -p /srv/data
$ sudo mount /dev/sdb1 /srv/data
$ df -h /srv/data
Filesystem      Size  Used Avail Use% Mounted on
/dev/sdb1       9.8G   24K  9.3G   1% /srv/data

$ findmnt /srv/data
TARGET    SOURCE    FSTYPE OPTIONS
/srv/data /dev/sdb1 ext4   rw,relatime
```

Обратите внимание на разницу между 10 ГБ и 9,8 ГБ. Файловая система занимает место под служебные структуры, а 5 процентов блоков зарезервированы для root. Резерв нужен, чтобы службы могли писать в журналы даже при заполнении диска пользователем. Для раздела с данными резерв часто уменьшают командой `sudo tune2fs -m 1 /dev/sdb1`, но делают это осознанно.

Права на точку монтирования задаются как на обычный каталог. Если писать в `/srv/data` должен пользователь `student`, ему нужен владелец каталога.

```bash
sudo chown student:student /srv/data
```

После этого можно создать файл, размонтировать раздел и смонтировать снова. Файл останется на месте: он лежит на `sdb1`, а каталог `/srv/data` служит только точкой входа.

::gate Почему проверять файловую систему на смонтированном разделе опасно?

## fstab: как сделать монтирование постоянным

Команда `mount` действует до перезагрузки. Чтобы раздел подключался автоматически, его описывают в `/etc/fstab`. Файл состоит из строк с шестью полями.

| Поле | Что означает | Пример |
|---|---|---|
| Устройство | UUID, метка или путь | `UUID=6f1c...` |
| Точка монтирования | каталог в дереве | `/srv/data` |
| Тип файловой системы | ext4, xfs, ntfs | `ext4` |
| Опции | режим и поведение | `defaults,nofail` |
| Дамп | нужен ли `dump` | `0` |
| Проверка | порядок `fsck` при загрузке | `2` |

UUID раздела берут из `sudo blkid /dev/sdb1` или из `lsblk -f`. Пример строки:

```text
UUID=6f1c2a9e-7b3d-4c8a-9e10-2d4f6a8b0c11 /srv/data ext4 defaults,nofail 0 2
```

Опция `nofail` разрешает загрузке продолжиться, если диск не найден. Без неё отсутствующий раздел приведёт систему в аварийный режим, и для восстановления понадобится консоль. Для учебного виртуального диска `nofail` полезна: если диск случайно отключили, система всё равно загрузится.

Проверка перед перезагрузкой обязательна. Команда `sudo mount -a` монтирует всё, что описано в `fstab`, и печатает ошибки. `findmnt --verify` проверяет синтаксис и предупреждает о неизвестных опциях. Если обе команды проходят без ошибок, риск неудачной загрузки минимален.

Порядок проверки такой:

1. Записать строку в `/etc/fstab` с UUID.
2. Выполнить `sudo systemctl daemon-reload`, чтобы systemd перечитал настройки.
3. Выполнить `sudo mount -a`.
4. Проверить `findmnt /srv/data` и `df -h /srv/data`.
5. Перезагрузиться и повторить проверку.

Если после правки система загрузилась в аварийный режим, нужно войти в консоль, смонтировать корень в режиме чтения и письма и исправить строку. Именно поэтому `fstab` правят с открытым вторым терминалом или снимком машины.

Размонтировать занятый раздел не получится: система сообщит `target is busy`. Команда `lsof +D /srv/data` показывает процессы, которые держат файлы, `fuser -vm /srv/data` показывает их с идентификаторами. После закрытия программ `umount` проходит. Принудительное `umount -l` откладывает отключение и не решает причину.

## Файловые системы и цена журнала

Файловая система решает две задачи: хранит данные и хранит метаданные. Метаданные это имена, права, размеры, время изменения и указатели на блоки. Если питание пропало в момент записи, метаданные могут остаться в несогласованном состоянии: файл есть в каталоге, но его блоки помечены свободными.

Журналирование уменьшает этот риск. Перед изменением метаданных система пишет намерение в журнал, затем выполняет изменение, затем помечает запись завершённой. После сбоя журнал проигрывается, и метаданные возвращаются к согласованному состоянию. Журнал не спасает сами данные: он защищает структуру, а не содержимое файла. Резервная копия всё равно нужна.

| Файловая система | Журнал | Максимальный файл | Максимальный раздел | Где применяется |
|---|---|---|---|---|
| ext4 | есть | 16 ТБ | 1 ЭиБ | Linux по умолчанию |
| XFS | есть | 8 ЭиБ | 8 ЭиБ | серверы, большие файлы |
| Btrfs | есть, копирование при записи | 16 ЭиБ | 16 ЭиБ | снимки, подтома |
| NTFS | есть | 16 ЭиБ теоретически | 256 ТБ практически | Windows |
| exFAT | нет | 16 ЭиБ | 128 ПиБ | флешки, внешние диски |
| FAT32 | нет | 4 ГБ | 2 ТБ | загрузка, прошивки |

ext4 остаётся рабочей лошадкой Ubuntu. Она умеет расти на лету, проверяться после сбоя и работать с отдельным журналом. Количество inode фиксируется при создании файловой системы, поэтому раздел с миллионом мелких файлов может исчерпать inode раньше, чем место. Проверяется это командой `df -i`: если `IUse%` близок к 100, свободное место есть, а новые файлы не создаются.

XFS хороша для больших файлов и параллельной записи, но не умеет уменьшаться. Btrfs предлагает снимки и контрольные суммы блоков, однако требует понимания подтомов и дефрагментации. NTFS нужна Windows: она хранит права доступа и журнал транзакций. exFAT удобна для переносных носителей, потому что работает и в Windows, и в Linux, и не имеет ограничения 4 ГБ на файл. FAT32 остаётся там, где её понимает прошивка: загрузчики, камеры, простые устройства.

Цена журнала это дополнительная запись. На медленном диске журнал заметен, на SSD почти нет. Опция `data=ordered`, принятая в ext4 по умолчанию, гарантирует, что данные попадут на диск раньше метаданных, но не даёт полной защиты от потери последних секунд записи. Для баз данных и виртуальных машин важнее правильное завершение работы и резервные копии, чем надежда на журнал.

## Проверка и починка

Проверка файловой системы выполняется утилитой `fsck`, которая для ext4 вызывает `e2fsck`. Главное правило: проверять только отмонтированный раздел или раздел, смонтированный только для чтения. Работающая файловая система меняет метаданные во время проверки, и утилита может принять согласованные данные за ошибку.

```text
$ sudo umount /srv/data
$ sudo fsck -f /dev/sdb1
fsck from util-linux 2.37.2
e2fsck 1.46.5 (30-Dec-2021)
Pass 1: Checking inodes, blocks, and sizes
Pass 2: Checking directory structure
Pass 3: Checking directory connectivity
Pass 4: Checking reference counts
Pass 5: Checking group summary information
data: 11/655360 files (0.0% non-contiguous), 88911/2617344 blocks

$ sudo mount /dev/sdb1 /srv/data
```

Флаг `-f` заставляет проверить даже чистую файловую систему. Без него `fsck` может ответить, что проверка не нужна. Флаг `-n` выполняет пробный проход и ничего не меняет: он полезен, когда непонятно, стоит ли запускать починку.

Коды возврата `e2fsck` помогают понять результат. `0` означает отсутствие ошибок, `1` означает, что ошибки найдены и исправлены, `2` требует перезагрузки, `4` означает, что ошибки остались неисправленными. В последнем случае автоматическая починка не справилась, и нужно разбираться с журналом и резервными копиями.

Если раздел корневой и отмонтировать его нельзя, загружаются с установочного носителя или в режиме восстановления. В учебной машине проще сделать снимок и проверить дополнительный диск: так ошибка не заблокирует систему.

Признаки проблем с диском видны в журнале ядра. `dmesg -T | grep -i -E 'error|fail|i/o'` показывает ошибки ввода-вывода с метками времени, `journalctl -k -p err` показывает только ошибки ядра. Сообщения `I/O error`, `UNC` или `medium error` говорят о проблеме носителя, а не файловой системы. В виртуальной машине такие ошибки чаще возникают из-за нехватки места на хосте или повреждённого файла диска.

## Типичные ошибки

| Ошибка | Симптом | Как исправить |
|---|---|---|
| `apt install` без `apt update` | пакет не найден или версия старая | выполнить `apt update` |
| `apt remove` вместо `apt purge` | настройки остаются | удалить пакет с `purge` |
| Форматирование `sda` вместо `sdb` | уничтожен корневой раздел | остановиться и восстановить из снимка |
| Запись в `fstab` по `/dev/sdb1` | после перезагрузки раздел не найден | заменить на UUID |
| `fsck` на смонтированном разделе | предупреждение или повреждение | отмонтировать раздел |
| Журнал и кеш занимают весь корень | `df -h` показывает 100% | очистить `apt clean`, старые ядра, журналы |
| Закончились inode | `df -i` показывает 100% | удалить мелкие файлы, пересоздать раздел |
| MBR на диске больше 2 ТБ | видна только часть объёма | перейти на GPT |

Отдельно про старые ядра. Ubuntu хранит несколько версий ядра, чтобы можно было загрузиться после неудачного обновления. Со временем `/boot` заполняется, и `apt upgrade` начинает падать с ошибкой нехватки места. Список установленных ядер показывает `dpkg -l 'linux-image-*'`, удаляют только старые версии, оставляя текущую и одну предыдущую. Автоматически это делает `apt autoremove`, если пакеты помечены как автоматически установленные.

## Итоги

- Пакет это запись с метаданными, зависимостями и файлами; `apt` разрешает зависимости, `dpkg` регистрирует пакет в системе.
- Репозиторий должен соответствовать выпуску системы, а его подпись проверяется, а не отключается.
- Диск становится пригодным для файлов после трёх шагов: таблица разделов, файловая система, точка монтирования.
- Постоянное монтирование описывается в `fstab` по UUID, а перед перезагрузкой проверяется `mount -a`.
- Журнал защищает метаданные, но не заменяет резервную копию.
- `fsck` запускают только на отмонтированном разделе, иначе проверка сама создаёт ошибки.

::quiz
Q: Что делает команда `apt update`?
+ Обновляет списки пакетов из репозиториев
- Устанавливает все доступные обновления
- Удаляет кеш скачанных пакетов
- Пересоздаёт файловую систему
! `apt update` обновляет только индексы, установка выполняется командой `apt upgrade`.

Q: Чем `apt remove` отличается от `apt purge`?
+ `purge` удаляет и файлы настроек пакета
- `remove` удаляет зависимости, а `purge` нет
- `purge` удаляет только кеш
- Разницы нет
! `remove` оставляет настройки, `purge` удаляет их вместе с пакетом.

Q: Что такое зависимость пакета?
+ Другой пакет или библиотека, без которой программа не работает
- Файл журнала пакетного менеджера
- Копия пакета в кеше
- Список репозиториев системы
! Пакетный менеджер устанавливает зависимости автоматически.

Q: Какая команда показывает файлы, установленные пакетом `ncdu`?
+ `dpkg -L ncdu`
- `dpkg -l ncdu`
- `apt update ncdu`
- `apt-cache policy ncdu`
! `dpkg -L` перечисляет файлы пакета, `dpkg -l` показывает строку состояния.

Q: Сколько первичных разделов допускает таблица MBR?
+ Четыре
- Восемь
- Шестнадцать
- Сто двадцать восемь
! Четыре первичных раздела, остальные можно создать как логические.

Q: Какой максимальный размер диска практически поддерживает MBR?
+ Около 2 ТБ
- Около 16 ТБ
- Около 256 ТБ
- Не ограничен
! Для больших дисков используют GPT.

Q: Что происходит при выполнении `mkfs.ext4 /dev/sdb1`?
+ Создаётся новая файловая система, прежние данные раздела теряются
- Раздел монтируется в корень
- Создаётся таблица разделов
- Данные копируются в резервную копию
! Форматирование пишет новые служебные структуры поверх старых.

Q: Что такое точка монтирования?
+ Каталог, в который подключается файловая система
- Имя раздела в таблице GPT
- Адрес репозитория пакетов
- Файл журнала файловой системы
! Через точку монтирования содержимое раздела попадает в общее дерево.

Q: Почему в `fstab` указывают UUID, а не `/dev/sdb1`?
+ Имя устройства может измениться при другом порядке подключения
- UUID занимает меньше места в файле
- С UUID не нужна файловая система
- UUID ускоряет запись на диск
! UUID привязан к файловой системе и не зависит от порядка устройств.

Q: Когда можно безопасно запускать `fsck` для раздела ext4?
+ Когда раздел отмонтирован
- В любой момент, пока система работает
- Только во время установки пакетов
- Только при заполненном диске
! Проверка работающей файловой системы может повредить метаданные.

Q: Какие утверждения о журналировании верны?
+ Журнал помогает восстановить согласованность метаданных после сбоя
+ Журнал не заменяет резервную копию данных
+ Журнал есть у ext4, XFS и NTFS
- Журнал гарантирует сохранность всех файлов при отключении питания
! Журнал защищает структуру, но последние данные могут быть потеряны.

Q: Какие команды помогают найти причину заполнения диска?
+ `df -h`
+ `df -i`
+ `du -sh *`
- `mkfs.ext4`
- `parted mklabel`
! `df` показывает место и inode, `du` находит крупные каталоги.

Q: Какие файловые системы не имеют журнала?
+ FAT32
+ exFAT
- ext4
- NTFS
! FAT32 и exFAT проще, но после сбоя требуют полной проверки.

Q: Какая команда монтирует всё, что описано в `/etc/fstab`?
= mount -a
= sudo mount -a
! `mount -a` читает `fstab` и подключает описанные разделы.

Q: Как называется утилита проверки и починки файловых систем Linux?
= fsck
= e2fsck
! `fsck` выбирает проверку по типу файловой системы, для ext4 работает `e2fsck`.
