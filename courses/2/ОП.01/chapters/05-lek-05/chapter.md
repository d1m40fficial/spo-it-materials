## Два кладовщика и одна накладная

В учебной ИС склада два процесса одновременно принимают товар. Каждый читает остаток, прибавляет своё количество и записывает результат. Остаток был 100. Первый процесс прочитал 100 и собирается записать 110. Второй тоже прочитал 100 и записывает 120. В итоге на складе 120 единиц вместо 130, а десять единиц исчезли из учёта.

Ошибка не в арифметике и не в базе данных. Ошибка в том, что операция «прочитать, изменить, записать» состоит из трёх шагов, и между ними может вклиниться другой процесс. Такая ситуация называется **гонкой данных**: результат зависит от того, кто успел первым, а не от логики программы.

**Синхронизация это набор правил, которые не дают нескольким потокам одновременно менять общий ресурс и приводят их действия к предсказуемому порядку.** Без неё программа может работать правильно тысячу раз и выдать неверный результат на тысячу первый.

## Гонка данных: три инструкции вместо одной

Процессор не умеет прибавить единицу к переменной в памяти одной командой. Обычно это три действия: загрузить значение в регистр, прибавить, записать обратно. Между загрузкой и записью может произойти прерывание, и планировщик передаст процессор другому потоку.

Последовательность для двух потоков выглядит так:

| Шаг | Поток A | Поток B | Значение в памяти |
|---|---|---|---|
| 1 | читает 100 | | 100 |
| 2 | | читает 100 | 100 |
| 3 | прибавляет 10 | | 100 |
| 4 | | прибавляет 20 | 100 |
| 5 | пишет 110 | | 110 |
| 6 | | пишет 120 | 120 |

Оба потока выполнили свою операцию, но одно обновление потерялось. Это называется потерянным обновлением. Тот же эффект возникает при работе с файлом, счётчиком в базе и элементом массива.

Воспроизвести гонку можно в `ubuntu-lab` на файле. Два одинаковых цикла запускаются одновременно и каждый двести раз делает «прочитать, прибавить, записать».

```bash
printf '0\n' > counter
for i in $(seq 1 200); do
  n=$(cat counter)
  echo $((n + 1)) > counter
done
```

Если запустить этот цикл в двух терминалах одновременно, в файле почти всегда окажется меньше 400. Точное число зависит от планировщика, поэтому повторные запуски дают разные результаты. Нестабильность и есть признак гонки.

Не всякая общая переменная опасна. Если несколько потоков только читают значение и никто не пишет, гонки нет. Опасны изменения, а также чтение во время записи, когда поток может увидеть половину обновлённой структуры.

> [!INTUITION] Гонка возникает не потому, что потоков много, а потому, что между чтением и записью есть окно, в которое может войти другой поток.

## Критическая секция и её требования

Участок кода, который обращается к общему ресурсу и не должен выполняться параллельно, называется **критической секцией**. Задача синхронизации сводится к тому, чтобы в критической секции в каждый момент находился только один поток.

Корректное решение должно удовлетворять трём условиям:

- **Взаимное исключение.** Два потока не находятся в критической секции одновременно.
- **Прогресс.** Если секция свободна и есть желающие, один из них войдёт в неё за конечное время.
- **Ограниченное ожидание.** Поток, который хочет войти, не может ждать бесконечно, пока другие обходят его.

Первое условие очевидно, два других часто забывают. Решение, которое даёт только взаимное исключение, но позволяет одному потоку вечно обгонять другого, формально защищает данные, но несправедливо и на практике приводит к зависанию.

Критическая секция должна быть короткой. Пока поток держит блокировку, остальные ждут, поэтому длинные вычисления и операции ввода-вывода внутри секции снижают параллелизм. Правило простое: под блокировкой меняют данные, а тяжёлую работу выносят наружу.

## Мьютекс

Самый распространённый примитив это **мьютекс**, от слов mutual exclusion. У него два состояния: свободен и захвачен. Поток вызывает `lock`, получает ресурс или ждёт, пока владелец не вызовет `unlock`. Владельцем может быть только тот поток, который захватил мьютекс.

В Python мьютекс представлен классом `threading.Lock`. Запись `with lock:` захватывает его на время блока и гарантированно освобождает при выходе, даже если внутри произошло исключение.

```python
import threading

lock = threading.Lock()
balance = 100

def deposit(amount):
    global balance
    with lock:
        current = balance
        balance = current + amount
```

Если убрать `with lock`, вернётся гонка из первого раздела. С блокировкой второй поток ждёт, пока первый закончит чтение и запись, и видит уже обновлённое значение.

У мьютекса есть важное свойство: он не рекурсивный по умолчанию. Если поток захватил мьютекс и попытается захватить его снова, он заблокируется сам себя. В Python для такого случая есть `threading.RLock`, который считает глубину захвата, но злоупотреблять им не стоит: рекурсивная блокировка часто скрывает ошибку в структуре кода.

Захват с ожиданием не всегда удобен. Функция `acquire(blocking=False)` или `try_lock` позволяет попробовать захватить ресурс и, если он занят, заняться другой работой. Это полезно в обработчиках событий, где нельзя надолго блокироваться.

В ядре Linux мьютекс построен на механизме `futex`. В простом случае захват происходит в пользовательском пространстве атомарной инструкцией, а в ядро поток уходит только тогда, когда нужно уснуть. Поэтому неконфликтный захват дешёвый, а ожидание дороже, но не сжигает процессор.

## Семафор

**Семафор** это счётчик с двумя операциями: уменьшить и увеличить. Уменьшение называется `wait` или `acquire`, увеличение `signal` или `release`. Если счётчик больше нуля, операция уменьшения проходит сразу. Если равен нулю, поток ждёт, пока другой поток не увеличит счётчик.

Семафор со значением 1 ведёт себя как мьютекс, но между ними есть разница. Мьютекс принадлежит потоку, который его захватил, и освободить его может только владелец. Семафор не имеет владельца: один поток может уменьшить счётчик, а другой увеличить. Это позволяет использовать семафор для сигналов и ограничения числа одновременных операций.

Классический пример это ограниченный буфер, куда производитель кладёт элементы, а потребитель забирает. Нужны три примитива: семафор свободных мест, семафор заполненных мест и мьютекс для самого буфера.

```text
empty = Semaphore(N)
full  = Semaphore(0)
mutex = Mutex()

производитель:
    empty.wait()
    mutex.lock()
    положить элемент
    mutex.unlock()
    full.signal()

потребитель:
    full.wait()
    mutex.lock()
    взять элемент
    mutex.unlock()
    empty.signal()
```

Порядок операций важен. Производитель сначала ждёт свободное место, потом захватывает мьютекс и только затем меняет буфер. Если поменять местами ожидание и захват, можно получить тупик: производитель держит мьютекс и ждёт место, а потребитель не может войти в буфер, чтобы место освободить.

Семафор со значением N ограничивает параллелизм. Если нужно не больше трёх одновременных обращений к внешнему сервису, ставят семафор с начальным значением 3. Четвёртый поток подождёт, пока один из трёх не закончит.

| Свойство | Мьютекс | Семафор |
|---|---|---|
| Значение | занят или свободен | целое число |
| Владелец | есть | нет |
| Кто освобождает | только владелец | любой поток |
| Основное назначение | взаимное исключение | ограничение и сигнал |
| Рекурсивность | обычно нет | не применима |

## Спинлок и другие примитивы

В ядре и в высокопроизводительном коде встречается **спинлок**. Поток не засыпает, а повторяет попытку захвата в цикле, пока ресурс не освободится. Это выгодно, если критическая секция очень короткая и переключение контекста дороже ожидания. На одном процессоре спинлок бессмысленен: пока поток крутится, владелец не выполнится.

Спинлоки требуют осторожности. Долгое удержание сжигает процессор, а захват спинлока с отключёнными прерываниями может привести к зависанию, если обработчик прерывания попытается взять тот же замок. Поэтому в прикладном коде их почти не используют.

Для данных, которые чаще читают, чем пишут, применяют **блокировку чтения и записи**. Много читателей могут работать одновременно, а писатель получает монопольный доступ. Это ускоряет чтение, но усложняет справедливость: поток читателей может не пустить писателя надолго.

**Условная переменная** позволяет потоку ждать не захвата, а изменения состояния. Поток захватывает мьютекс, проверяет условие и, если оно ложно, засыпает на условной переменной. Другой поток меняет данные и будит ждущих. Проверку условия делают в цикле, потому что пробуждение может быть ложным.

**Атомарные операции** решают задачу без блокировки. Инструкция сравнения с обменом проверяет, что значение не изменилось, и только тогда записывает новое. На этом строятся счётчики и очереди без замков. Они быстрее при низкой конкуренции, но сложны в написании и требуют понимания порядка доступа к памяти. В прикладной задаче почти всегда достаточно мьютекса.

## Синхронизация в базах данных

Информационная система редко обходится блокировками внутри одного процесса. Несколько приложений и пользователей меняют одни и те же строки, поэтому СУБД строит собственную синхронизацию.

Транзакция захватывает блокировку строки на время изменения и держит её до commit или rollback. Другая транзакция, которая хочет изменить ту же строку, ждёт. Если ожидание слишком долгое, СУБД прерывает его по тайм-ауту. В MySQL параметр `innodb_lock_wait_timeout` по умолчанию равен 50 секундам, в PostgreSQL `lock_timeout` по умолчанию отключён и ждёт до отмены.

Порядок обновления строк снова решает дело. Две транзакции, которые переводят деньги между счетами в разном порядке, могут заблокировать друг друга. Если обе сначала блокируют счёт с меньшим номером, а потом с большим, цикл не возникает.

Есть два подхода к защите от потерянных обновлений. Пессимистический заранее блокирует строку и заставляет остальных ждать. Оптимистический не блокирует, а добавляет к строке номер версии и при записи проверяет, что версия не изменилась. Если изменилась, приложение повторяет операцию. Оптимистический подход лучше работает при редких конфликтах, пессимистический при частых.

Транзакции стоит делать короткими. Чем дольше транзакция держит строки, тем больше очередь ожидающих и тем выше шанс тупика. Долгие вычисления и обращения к внешним сервисам внутри транзакции увеличивают это время.

## Как выбрать примитив

Выбор зависит от задачи, а не от привычки.

| Задача | Примитив | Почему |
|---|---|---|
| Защитить общий счётчик или структуру | мьютекс | нужен исключительный доступ |
| Ограничить число одновременных обращений | семафор со значением N | считает свободные места |
| Передать сигнал о готовности данных | семафор или условная переменная | поток ждёт события, а не замка |
| Защитить данные, которые часто читают | блокировка чтения и записи | читатели не мешают друг другу |
| Очень короткая секция в ядре | спинлок | переключение дороже ожидания |
| Один счётчик без сложной логики | атомарная операция | не нужен замок |

Если сомневаетесь, начинайте с мьютекса и короткой критической секции. Усложнять стоит только тогда, когда измерение показало проблему.

## Тупик и четыре условия

**Взаимная блокировка**, или тупик, возникает, когда два или больше потока ждут ресурсы, которые держат друг друга, и ни один не может продолжить работу. Внешне система жива, процессор свободен, но конкретные потоки стоят навсегда.

Тупик возможен только при одновременном выполнении четырёх условий, которые называют условиями Коффмана:

- **Взаимное исключение.** Ресурс нельзя использовать совместно.
- **Удержание и ожидание.** Поток держит один ресурс и ждёт другой.
- **Отсутствие отъёма.** Ресурс нельзя забрать силой, только освободить добровольно.
- **Циклическое ожидание.** Существует цепочка потоков, где каждый ждёт ресурс следующего.

Убрать хотя бы одно условие значит исключить тупик. На практике чаще всего работают с последним.

Пример с двумя блокировками. Поток T1 захватывает A, поток T2 захватывает B. Затем T1 пытается захватить B, а T2 пытается захватить A. Оба блокируются, и каждый ждёт освобождения от другого.

| Время | T1 | T2 | Кто чего ждёт |
|---|---|---|---|
| 0 | захватил A | | T1 держит A |
| 1 | | захватил B | T2 держит B |
| 2 | ждёт B | | T1 ждёт T2 |
| 3 | | ждёт A | T2 ждёт T1 |

Граф ожидания содержит цикл T1, T2, T1. Пока цикл есть, тупик не разрешится сам.

## Порядок захвата

Самое надёжное профилактическое средство это **единый порядок захвата**. Если все потоки захватывают блокировки в одном и том же порядке, цикл невозможен. В примере выше достаточно договориться, что A всегда захватывается раньше B. Тогда T2 не сможет держать B и ждать A: он сначала возьмёт A и будет ждать, пока T1 освободит её.

Порядок задают по понятному признаку: по имени ресурса, по числовому идентификатору, по адресу объекта. Главное, чтобы правило было одно для всей программы и не менялось в разных функциях. Если одна функция захватывает A и B, а другая B и A, тупик рано или поздно появится.

В базе данных тот же принцип применяют к таблицам и строкам. Две транзакции, которые обновляют счета в разном порядке, могут заблокировать друг друга. Если обе обновляют счета по возрастанию номера, цикл не возникает.

Другие способы профилактики:

- захватить все нужные ресурсы сразу, до начала работы, и не ждать ничего внутри;
- использовать `try_lock` с тайм-аутом и при неудаче отпустить уже захваченное и повторить;
- свести число блокировок к одной грубой блокировке, если производительность позволяет;
- применять иерархию блокировок, где уровень можно захватывать только после более высокого.

Тайм-аут не устраняет тупик, а делает его обратимым: поток отпускает ресурсы и пробует снова. Это лучше вечного ожидания, но может снизить производительность при высокой конкуренции.

## Обнаружение и восстановление

Если профилактика не сработала, систему нужно спасать. Операционная система или СУБД может построить граф ожидания и найти в нём цикл. Обнаружение стоит вычислений, поэтому его запускают не постоянно, а по тайм-ауту или по подозрению.

В MySQL и InnoDB есть встроенный детектор тупиков. Когда транзакция ждёт блокировку дольше порога, СУБД ищет цикл и откатывает одну из транзакций с ошибкой 1213. В сообщении `SHOW ENGINE INNODB STATUS` появляется раздел `LATEST DETECTED DEADLOCK` с запросами и удерживаемыми блокировками. PostgreSQL использует параметр `deadlock_timeout`, по умолчанию около одной секунды, и также завершает одну из транзакций.

Восстановление почти всегда означает жертву. Откатывают транзакцию, завершают поток или снимают блокировку. Выбирают того, кому дешевле повторить работу, а не того, кто «виноват». После отката клиент повторяет операцию, и система продолжает работу.

В обычной ОС универсального детектора тупиков нет. Ядро видит зависшие потоки, но не всегда знает, какой ресурс они делят. Поэтому диагностикой занимаются разработчик и администратор: смотрят стеки, блокировки и журналы.

## Голодание и livelock

Тупик не единственная неприятность. **Голодание** это ситуация, когда поток готов работать, но никогда не получает ресурс, потому что его постоянно обходят другие. Пример: поток с низким приоритетом ждёт мьютекс, а поток с высоким захватывает его снова и снова. Решение: справедливая очередь или старение приоритета.

**Livelock** внешне похож на работу: потоки не спят, меняют состояние, пытаются договориться, но прогресса нет. Аналогия: два человека в узком коридоре шагают в одну сторону, затем одновременно в другую и не могут разойтись. В программе так бывает, когда два потока при конфликте отпускают блокировку и сразу пытаются снова. Лечится случайной задержкой или разным порядком повторов.

Отличать эти состояния важно при диагностике. При тупике потоки спят и процессор свободен. При livelock процессор загружен, но полезной работы нет. При голодании один поток работает, а другой бесконечно ждёт.

## Наблюдение на стенде

В `ubuntu-lab` блокировки видны не всегда, но кое-что проверить можно. Команда `lslocks` показывает блокировки файлов, `cat /proc/locks` даёт их в необработанном виде, `ps -eLf` показывает потоки и их состояние.

Если программа зависла, полезно посмотреть, чего она ждёт. `cat /proc/PID/status` содержит счётчики добровольных и принудительных переключений, а `cat /proc/PID/wchan` показывает функцию ожидания. Для Python есть встроенный модуль `faulthandler`: вызов `faulthandler.dump_traceback_later(10, repeat=True)` печатает стеки всех потоков через десять секунд, и по ним видно, кто держит блокировку.

Трассировка `strace -f -e trace=futex` показывает обращения к `futex`, на котором построены мьютексы и условные переменные. Если поток стоит в `futex`, он ждёт освобождения примитива. Смотреть на это долго не стоит: трассировка замедляет программу.

В Windows монитор ресурсов умеет показывать цепочку ожидания. Вкладка «ЦП» с колонкой «Анализ ожидания» строит граф, по которому видно, какой процесс ждёт другой. Это полезно, когда приложение зависло и непонятно, кто виноват.

| Что проверить | Ubuntu | Windows 10 |
|---|---|---|
| Блокировки файлов | `lslocks`, `/proc/locks` | монитор ресурсов, `handle` |
| Потоки и состояние | `ps -eLf` | вкладка «Подробности» |
| Ожидание | `/proc/PID/wchan`, `strace -f` | анализ ожидания |
| Стеки потоков | `faulthandler`, отладчик | отладчик, дамп процесса |
| Тупики в СУБД | журнал СУБД, `SHOW ENGINE` | журнал СУБД |

## Типичные ошибки

**«Поставлю блокировку на всякий случай».** Лишняя блокировка снижает параллелизм и увеличивает риск тупика. Защищать нужно только общие изменяемые данные.

**«Мьютекс и семафор это одно и то же».** Мьютекс имеет владельца и даёт исключительный доступ. Семафор считает ресурсы и может использоваться для сигналов между потоками.

**«Достаточно одного теста, гонки нет».** Гонка проявляется редко и зависит от момента переключения. Отсутствие ошибки в одном запуске ничего не доказывает.

**«Порядок захвата не важен, если блокировки короткие».** Тупик не зависит от длительности. Достаточно неудачного совпадения, чтобы потоки встали навсегда.

**«`kill -9` решит проблему тупика».** Он завершит процесс, но не устранит причину. После перезапуска тупик повторится, если порядок захвата не изменён.

**«GIL в Python заменяет блокировки».** Глобальная блокировка интерпретатора не защищает составные операции с файлами, базой и внешними ресурсами.

## Итоги

- Гонка данных возникает, когда несколько потоков меняют общий ресурс без согласования, и приводит к потерянным обновлениям.
- Критическая секция требует взаимного исключения, прогресса и ограниченного ожидания.
- Мьютекс даёт исключительный доступ с владельцем, семафор считает ресурсы и служит для сигналов.
- Тупик возможен при mutual exclusion, удержании с ожиданием, отсутствии отъёма и цикле ожидания.
- Единый порядок захвата блокировок это самый практичный способ профилактики тупика.
- Обнаружение строит граф ожидания, восстановление откатывает одну из сторон, а голодание и livelock требуют отдельных мер.

- Одновременная работа двух процессоров над разными файлами

- Часть операционной системы, работающая с диском
- Раздел жёсткого диска

- Взаимное исключение
- Прогресс
- Ограниченное ожидание
! Бесконечное ожидание нарушает требование ограниченного ожидания.

- Высокий приоритет процесса

+ Вводят единый порядок захвата блокировок
- Увеличивают число блокировок
- Отключают планировщик
- Запускают все потоки с одним приоритетом
! Единый порядок исключает цикл ожидания.

Q: Чем livelock отличается от тупика?
+ Потоки активны и меняют состояние, но прогресса нет
- Потоки спят и не потребляют процессор
- Система перезагружается
- Один поток монопольно занял процессор
! При livelock работа имитируется, но результат не достигается.

+ Мьютекс для доступа к буферу
- Спинлок для каждого элемента
- Второй мьютекс для потребителя
! Семафоры считают места, мьютекс защищает сам буфер.

+ Взаимное исключение
+ Удержание и ожидание
+ Отсутствие отъёма ресурса
- Наличие более двух процессоров
- Высокая загрузка процессора

+ Семафор хранит целое значение
+ Уменьшение счётчика может заблокировать поток

- Семафор всегда имеет владельца
- Семафор нельзя использовать для сигналов
