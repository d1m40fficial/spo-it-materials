## Цель работы

Научиться проверять сеть по слоям и отличать причину сбоя от его симптома. В работе фиксируются адрес и маршрут гостевой Linux, проверяется доступность шлюза и внешнего узла, сравнивается разрешение имён, проверяется порт SSH и моделируется отказ службы. Результат работы это заполненная карта диагностики: таблица, по которой другой человек сможет повторить проверку и прийти к тому же выводу.

Отдельное внимание уделяется пробросу порта. Хост обращается к гостю через `127.0.0.1:2222`, хотя у гостя адрес `10.0.2.15`. Это разные адреса и разные стороны NAT. Проверка покажет, где заканчивается сеть и начинается служба.

## Оборудование и программное обеспечение

- Хост с Windows 10 и VirtualBox, машина запущена.
- Права пользователя `student` и пароль `1111` для `sudo`.

## Краткие теоретические сведения

Сетевой стек проверяется снизу вверх. Интерфейс должен быть включён и иметь адрес. Адрес должен попадать в локальную сеть с правильной маской. Маршрут по умолчанию должен указывать на доступный шлюз. DNS должен разрешать имя в адрес. Порт должен слушать службу, а служба должна отвечать. Каждый слой проверяется отдельной командой, и результат записывается.

`ip -br a` показывает интерфейсы и адреса, `ip route` таблицу маршрутов, `ip route get` выбранный путь. `ping` проверяет ICMP-доступность узла. `traceroute` показывает путь до узла. `getent`, `resolvectl` и `dig` проверяют имена. `ss` показывает сокеты и состояния, `Test-NetConnection` проверяет TCP-соединение из Windows.

Порт это число от 0 до 65535. Вместе с адресом и протоколом он образует сокет. Состояние `LISTEN` означает, что служба ждёт соединения, `ESTAB` означает установленное соединение, `TIME-WAIT` остаётся после закрытия. Если порт не слушается, соединение получает отказ. Если порт фильтруется, соединение зависает до тайм-аута.

В режиме NAT гость находится в сети `10.0.2.0/24`. Его адрес `10.0.2.15`, шлюз `10.0.2.2`, DNS `10.0.2.3`. Хост не может подключиться к гостю по этому адресу. Для SSH настроен проброс: хост слушает `127.0.0.1:2222` и передаёт соединение на `10.0.2.15:22`. Проверка порта на хосте и проверка службы в госте это две разные операции.

Проверка порта не говорит, почему служба не отвечает. `Test-NetConnection` устанавливает TCP-соединение и сразу закрывает его. Если соединение установилось, значит, порт слушается и сеть работает. Дальше проверяют приложение: принимает ли оно запрос, не зависло ли, не требует ли аутентификации. Отсутствие соединения делится на отказ и тайм-аут, и это деление задаёт направление поиска.

Разрешение имён тоже имеет порядок. Система сначала смотрит `/etc/hosts`, затем обращается к DNS, а результат кеширует. Кеш ускоряет работу, но скрывает изменения: имя может указывать на старый адрес ещё несколько минут. При диагностике полезно проверить `getent`, затем `resolvectl`, затем `dig`: если все три дают один ответ, проблема не в имени.

## Ход работы

### Шаг 1. Зафиксируйте адрес и маршрут

Работайте в окне виртуальной машины, а не через SSH: на шаге 5 служба SSH будет остановлена, и удалённое соединение оборвётся.

В госте выполните команды.

```bash
ip -br a
ip addr show enp0s3
ip route
ip route get 8.8.8.8
cat /proc/sys/net/ipv4/ip_local_port_range
```

Первая команда показывает интерфейсы и адреса, вторая подробности адаптера, третья таблицу маршрутов, четвёртая выбранный путь к внешнему адресу, пятая диапазон временных портов. Заполните таблицу.

| Параметр | Команда | Значение |
|---|---|---|
| Интерфейс | `ip -br a` |  |
| Адрес и маска | `ip -br a` |  |
| Состояние интерфейса | `ip addr show enp0s3` |  |
| Маршрут по умолчанию | `ip route` |  |
| Шлюз | `ip route` |  |
| Источник для 8.8.8.8 | `ip route get 8.8.8.8` |  |
| Диапазон временных портов | `cat /proc/sys/net/ipv4/ip_local_port_range` |  |

На хосте откройте PowerShell и выполните свои команды.

```powershell
ipconfig /all
route print
Get-NetIPConfiguration
```

Сравните адрес хоста и адрес гостя. Они находятся в разных сетях, и это нормально: NAT скрывает гостя за адресом хоста. Запишите адрес хоста, его шлюз и адрес гостя в отдельную таблицу. Объясните одним предложением, почему хост не может обратиться к гостю по адресу `10.0.2.15`.

Обратите внимание на маску. Если у гостя `/24`, то адреса `10.0.2.1` и `10.0.2.254` находятся с ним в одной сети, а `10.0.3.15` уже в другой и пойдёт через шлюз. Неверная маска ломает связь с соседями, хотя адрес выглядит правильным. Поэтому в таблицу записывают не только адрес, но и длину маски.

### Шаг 2. Проверьте шлюз и внешний узел

Установите утилиты диагностики, если их нет.

```bash
sudo apt update
sudo apt install -y traceroute dnsutils netcat-openbsd
```

Проверьте шлюз, внешний адрес и путь.

```bash
ping -c 4 10.0.2.2
ping -c 4 8.8.8.8
traceroute 8.8.8.8
```

Первый `ping` проверяет шлюз NAT, второй внешний адрес, третий показывает путь. Запишите потери, среднее время и число прыжков.

| Проверка | Команда | Потери | Среднее время | Вывод |
|---|---|---|---|---|
| Шлюз | `ping -c 4 10.0.2.2` |  |  |  |
| Внешний узел | `ping -c 4 8.8.8.8` |  |  |  |
| Путь | `traceroute 8.8.8.8` |  |  |  |

Первый прыжок `traceroute` должен совпасть с адресом шлюза. Звёздочки на следующих прыжках не означают аварию: промежуточные узлы часто не отвечают на служебные пакеты. Если внешний `ping` не проходит, проверьте, открывается ли сайт в браузере. Возможна блокировка ICMP при работающем TCP.

Время ответа измеряется в миллисекундах. В локальной сети оно обычно меньше одной миллисекунды, до внешнего узла зависит от провайдера. Резкий рост времени и потери на одном из прыжков указывают на перегруженный участок. Потери на последнем прыжке при нормальном времени чаще означают ограничение на стороне сервера, а не проблему канала.

### Шаг 3. Проверьте разрешение имён

Сравните три способа разрешения имени.

```bash
getent hosts ubuntu.com
resolvectl query ubuntu.com
dig +short ubuntu.com
```

`getent` использует те же источники, что и программы. `resolvectl` обращается к локальному resolver. `dig` показывает ответ DNS-сервера. Запишите адреса и время ответа.

| Способ | Команда | Результат | Время |
|---|---|---|---|
| Системный | `getent hosts ubuntu.com` |  |  |
| Resolver | `resolvectl query ubuntu.com` |  |  |
| DNS-запрос | `dig +short ubuntu.com` |  |  |

На хосте выполните `Resolve-DnsName ubuntu.com` и сравните адреса. Они могут отличаться: крупные сайты возвращают разные адреса в зависимости от региона и балансировки. Совпадение не обязательно, важна способность получить ответ.

Если `getent` возвращает адрес, а `dig` нет, проблема в локальном resolver или в его кеше, а не в отсутствии сети. Если оба не возвращают адрес, проверьте `resolvectl status` и доступность DNS-сервера. Если адрес возвращается, но браузер сайт не открывает, ищите прокси, сертификат или сам сайт, а не DNS.

Проверьте, что имя разрешается и без DNS, если добавить его в `/etc/hosts`. Не меняйте файл постоянно: достаточно понять порядок источников. Запишите, какой источник система проверяет первым.

### Шаг 4. Проверьте порт SSH

В госте посмотрите слушающие сокеты.

```bash
sudo ss -tulpn
sudo ss -tlnp | grep :22
```

Найдите строку с портом 22. Запишите адрес привязки, состояние и имя процесса. Если адрес `0.0.0.0` или `[::]`, служба принимает соединения на всех интерфейсах. Если `127.0.0.1`, снаружи порт недоступен.

На хосте проверьте проброс.

```powershell
Test-NetConnection 127.0.0.1 -Port 2222
Test-NetConnection 127.0.0.1 -Port 2223
```

Первая команда должна показать `TcpTestSucceeded : True`, вторая `False`. Порт 2223 не проброшен, поэтому соединение получает отказ. Запишите оба результата и объясните разницу.

| Проверка | Где | Команда | Результат |
|---|---|---|---|
| Слушает ли SSH | гость | `sudo ss -tlnp` |  |
| Порт 2222 | хост | `Test-NetConnection` |  |
| Порт 2223 | хост | `Test-NetConnection` |  |

Если порт 2222 не отвечает, проверьте три вещи: правило проброса в настройках машины, состояние службы `ssh` и адрес привязки. Не начинайте с переустановки SSH: причина чаще в одной из этих трёх настроек.

### Шаг 5. Смоделируйте отказ службы

Остановите SSH в госте и проверьте, что изменилось.

```bash
sudo systemctl stop ssh
sudo systemctl status ssh --no-pager
sudo ss -tlnp | grep :22
```

Служба должна быть неактивна, а порт 22 не должен слушаться. На хосте повторите проверку порта 2222 и попробуйте подключиться.

```powershell
Test-NetConnection 127.0.0.1 -Port 2222
ssh -p 2222 student@127.0.0.1
```

`Test-NetConnection` покажет `False`, а `ssh` сообщит `Connection refused`. Запишите сообщение и объясните, почему отказ отличается от тайм-аута. Затем верните службу.

```bash
sudo systemctl start ssh
sudo systemctl status ssh --no-pager
```

Снова проверьте порт с хоста. Он должен вернуться в состояние `True`. Заполните таблицу наблюдений.

| Состояние службы | Порт в госте | Результат на хосте | Сообщение |
|---|---|---|---|
| Работает |  |  |  |
| Остановлена |  |  |  |
| Работает после возврата |  |  |  |

### Шаг 6. Проверьте проброс на другом порту

Не выключая машину, откройте «Устройства», «Сеть», «Настройки сети», «Проброс портов». Измените порт хоста с 2222 на 2223, сохраните правило и проверьте оба порта с хоста.

```powershell
Test-NetConnection 127.0.0.1 -Port 2223
Test-NetConnection 127.0.0.1 -Port 2222
```

Новый порт должен работать, старый перестать. Подключитесь по SSH через 2223, выполните `who` и выйдите. Затем верните правило 2222 и проверьте, что доступ восстановился.

| Правило | Порт 2222 | Порт 2223 | Вход по SSH |
|---|---|---|---|
| Исходное |  |  |  |
| Изменённое |  |  |  |
| Возвращённое |  |  |  |

Объясните, почему смена порта на хосте не требует изменений в госте. Служба SSH продолжает слушать порт 22, меняется только внешняя точка входа.

### Шаг 7. Соберите карту диагностики

Заполните таблицу по результатам работы. В столбце «Признак» укажите, что видно при сбое, в столбце «Вывод» отметьте, какой слой проверен.

| Слой | Команда | Норма | Признак сбоя | Вывод |
|---|---|---|---|---|
| Интерфейс | `ip -br a` | UP и адрес | DOWN или 169.254 |  |
| Маршрут | `ip route get 8.8.8.8` | via 10.0.2.2 | unreachable |  |
| Шлюз | `ping -c 4 10.0.2.2` | 0% потерь | 100% потерь |  |
| Имя | `getent hosts ubuntu.com` | адрес | нет ответа |  |
| Порт в госте | `sudo ss -tlnp` | LISTEN на 0.0.0.0:22 | порт не слушается |  |
| Порт на хосте | `Test-NetConnection` | True | False |  |
| Служба | `systemctl status ssh` | active (running) | inactive (dead) |  |

Разберите два случая в двух-трёх предложениях каждый. Первый: гость открывает сайты, хост не подключается к порту 2222. Второй: гость пингует `8.8.8.8`, но не разрешает имена. Для каждого случая укажите проверяемый слой и следующую команду.

Добавьте третий случай: порт 2222 отвечает `True`, SSH показывает приглашение, но вход с паролем `student` не происходит. Сеть и порт здесь исправны, поэтому проверяют аутентификацию: имя пользователя, пароль, права и журнал `journalctl -u ssh`. Этот случай показывает границу диагностики: команды сети доводят до службы, а дальше начинается её собственная конфигурация.

## Требования к отчёту

Отчёт содержит:

- цель работы и схему адресов: гость, шлюз, DNS, проброс;
- таблицу адреса и маршрута гостя и хоста;
- результаты `ping` для шлюза и внешнего узла с потерями и временем;
- результат `traceroute` с числом прыжков;
- сравнение трёх способов разрешения имени;
- состояние порта 22 в госте и результаты проверки портов 2222 и 2223 на хосте;
- таблицу наблюдений при остановке и возврате службы;
- результаты смены порта проброса;
- заполненную карту диагностики и разбор двух случаев.

Снимки экрана приводятся для `ip route`, `ss -tlnp`, `Test-NetConnection` и `systemctl status ssh`. На снимке должны быть видны команда и результат.

## Что сдать

- отчёт с таблицами адресов, маршрутов и портов;

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

- **5**: адрес и маршрут зафиксированы, шлюз и внешний узел проверены, имена разрешены тремя способами, порт найден в госте и проверен с хоста, отказ службы смоделирован и объяснён, проброс изменён и возвращён, карта диагностики заполнена, оба случая разобраны.
- **4**: работа выполнена, но одна-две проверки не записаны, различие отказа и тайм-аута объяснено кратко или карта заполнена частично.
- **3**: адрес и порт проверены, но моделирование отказа не выполнено, смена проброса не проверена, разбор случаев отсутствует.
- **2**: работа не выполнена или проверки не отражают состояние стенда.
- **1**: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
