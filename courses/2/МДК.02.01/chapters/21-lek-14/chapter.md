## Все тесты зелёные

Проект проходит сто тестов. В рабочей системе сотрудник открывает чужую заявку: запрос не фильтрует по владельцу. Тест был, но проверял только пустой список.

**Тестирование** сравнивает ожидаемое поведение с фактическим. Тест без проверки важного условия создаёт ложное спокойствие.

Главная мысль занятия: **тест проверяет утверждение, а не строки кода**. Сначала формулируют ожидание, потом пишут проверку.

## Уровни тестирования

::figure test-levels | Пирамида уровней: много модульных тестов, меньше интеграционных, ещё меньше приёмочных. Внизу быстрые и дешёвые проверки, вверху медленные.

**Модульный тест** проверяет функцию или класс отдельно. Он быстрый и точно указывает место ошибки.

**Интеграционный тест** проверяет связь модулей: приложение и база, два сервиса, запрос и ответ.

**Приёмочный тест** проверяет сценарий целиком с точки зрения пользователя.

Пирамида означает пропорцию: основа даёт быструю обратную связь, вершина подтверждает цель.

## Тест-дизайн

**Класс эквивалентности** это набор значений, для которых поведение одинаково.

Для поля «тема заявки»:

- пустая строка;
- обычная строка;
- строка из одних пробелов;
- строка длиннее предела.

Достаточно одного представителя класса. Проверять сто обычных строк бессмысленно.

**Граничные значения** проверяют края диапазона. Если длина от 1 до 80, проверяют 0, 1, 80 и 81.

Комбинации условий быстро растут. Поэтому выбирают пары, которые чаще ломаются: пусто, максимум, неверный тип, нет прав.

## Структура тест-кейса

Хороший тест-кейс содержит:

1. название с ожидаемым результатом;
2. предусловие;
3. шаги;
4. ожидаемый результат;
5. фактический результат при прогоне.

Пример:

```text
Название: закрытие заявки без прав возвращает ошибку
Дано: пользователь с ролью сотрудник
Когда: вызывает закрытие чужой заявки
Тогда: ответ 403, статус заявки не меняется
```

## Покрытие

**Покрытие** показывает, какая часть кода или требований проверена.

- покрытие строк: выполнялась ли строка;
- покрытие ветвей: проверены ли обе стороны условия;
- покрытие требований: есть ли тест на каждый критерий приёмки.

Сто процентов покрытия не гарантируют правильность. Можно выполнить строку и не проверить результат.

## Что тестировать в первую очередь

- права доступа;
- пустые и максимальные значения;
- ошибки внешних служб;
- повторные действия;
- переходы статусов;
- сохранение данных.

Эти места чаще всего приводят к потере данных или доступу к чужим данным.

## Где тестирование ломается

**Тест без утверждения.** Код выполняется, но результат не сравнивается.

**Только счастливый путь.** Проверяют успешный сценарий, ошибки остаются.

**Тест зависит от порядка.** Второй тест падает после первого.

**Медленные тесты на всё.** Прогон занимает час, его перестают запускать.

**Погоня за покрытием.** Пишут тесты ради процента, а не ради проверки.

**Нет теста на дефект.** Ошибку исправили, но не закрепили проверкой.

> [!PITFALL] Тест, который никогда не падал, возможно, ничего не проверяет. Убедитесь, что при поломке он действительно краснеет.

## Итоги

- Уровни тестов различаются скоростью и областью проверки.
- Классы эквивалентности сокращают число случаев.
- Границы проверяют отдельно.
- Тест-кейс содержит ожидаемый результат.
- Покрытие полезно, но не доказывает правильность.

::quiz
Q: Что сравнивает тест?
+ Ожидаемое поведение с фактическим
- Скорость сервера с тарифом
- Код с документацией
- Число строк с нормой
! Проверка поведения.

Q: Что проверяет модульный тест?
+ Отдельную функцию или класс
- Всю систему целиком
- Только интерфейс
- Только базу
! Малая область.

Q: Что проверяет приёмочный тест?
+ Сценарий целиком
- Одну строку
- Синтаксис
- Стиль кода
! Цель пользователя.

Q: Что такое класс эквивалентности?
+ Значения с одинаковым поведением
- Все возможные значения
- Только границы
- Случайные значения
! Один представитель.

Q: Какие значения проверяют на границе диапазона 1..80?
+ 0, 1, 80, 81
- 40, 41, 42
- 1, 2, 3
- 100, 200
! Края диапазона.

Q: Что содержит тест-кейс?
+ Ожидаемый результат
- Только шаги
- Только название
- Только код
! Проверка результата.

Q: Что показывает покрытие ветвей?
+ Проверены ли обе стороны условия
- Сколько файлов в проекте
- Сколько тестов написано
- Сколько авторов
! Ветви условий.

Q: Почему 100 процентов покрытия не гарантируют правильность?
+ Строка выполнена, но результат не проверен
- Покрытие всегда врёт
- Тесты слишком быстрые
- Код слишком короткий
! Нужны утверждения.

Q: Что тестируют в первую очередь?
+ Права доступа и потерю данных
- Цвет кнопок
- Название проекта
- Скорость набора
! Риски.

Q: Какие уровни тестирования существуют?
+ Модульные
+ Интеграционные
+ Приёмочные
+ Системные
- Стилевые
- Цветовые
! Остальное не уровни.

Q: Какие ошибки тестирования типичны?
+ Тест без утверждения
+ Только счастливый путь
+ Тест зависит от порядка
+ Нет теста на дефект
- Проверка границ
- Проверка прав
! Остальное хорошо.

Q: Что проверяют в первую очередь?
+ Пустые значения
+ Максимальные значения
+ Ошибки внешних служб
+ Повторные действия
- Цвет фона
- Логотип
! Остальное не риск.

Q: Как называют набор значений с одинаковым поведением?
= класс эквивалентности
= equivalence class
! Один представитель.

Q: Какие значения проверяют на границе?
= граничные
= границы
! Края диапазона.

Q: Что сравнивает тест с ожиданием?
= результат
= фактический результат
! Проверка.
