## «Запустите как-нибудь»

Новый разработчик открывает проект. В README одна строка: «Запустите как-нибудь». В коде нет описания API, а решение «почему выбрали SQLite» помнит только ушедший сотрудник. Первый день уходит на чтение конфигурации, второй на догадки о версии Python, третий на выяснение, что база должна быть создана вручную.

Проект работает. Знание о том, как его запустить, существует. Но оно хранится в голове автора и в переписке, а не в документе.

**Документация** это ответы на вопросы, которые возникают у читателя. Документ нужен не для отчёта, а для конкретного вопроса: как установить, как вызвать, что изменилось, почему так решили.

Главная мысль занятия: **документ выбирают по читателю и вопросу**. Один файл на все случаи быстро устаревает, потому что пытается быть учебником, справочником и дневником одновременно.

Документация кажется вторичной по сравнению с кодом. Это ошибка. Для нового человека документ является интерфейсом к проекту. Если интерфейс врёт, код не помогает: его ещё нужно найти и понять.

Второй читатель документа это сам автор через полгода. Он забудет, почему выбрал формат, где лежит конфигурация и что означает странная проверка. Запись решения экономит не только чужое время, но и своё.

У документации есть цена. Её пишут, проверяют, обновляют и хранят. Если писать всё подряд, время уходит на текст, который никто не читает. Поэтому важнее не объём, а попадание в вопрос.

## Документация как ответ на вопрос

У любого документа есть три параметра: читатель, вопрос и момент чтения. Читатель может быть новым разработчиком, интегратором, пользователем, администратором или будущим членом команды. Вопрос может быть «как начать», «как сделать», «что означает параметр», «почему так устроено». Момент может быть первым запуском, работой, разбором инцидента или приёмкой.

Смена любого параметра меняет документ. Новый разработчик спрашивает «с чего начать». Интегратор спрашивает «какой код вернётся при ошибке». Пользователь спрашивает «как закрыть заявку». Команда через год спрашивает «почему отказались от серверной базы».

Стандарт ISO/IEC/IEEE 26514:2022 описывает проектирование и разработку информации для пользователей: как определять аудиторию, задачи и структуру документа [ISO/IEC/IEEE 26514:2022](https://www.iso.org/standard/77451.html). Он не задаёт шаблон README, но задаёт рамку: документ начинается с аудитории и задачи, а не с желания автора что-то рассказать.

### Документ как артефакт

В процессе разработки документ является таким же артефактом, как тест или сборка. У него есть владелец, версия и критерий готовности.

Владелец не обязательно автор. README обычно поддерживает тот, кто отвечает за сборку. Описание API поддерживает владелец сервиса. Руководство пользователя поддерживает продуктовая команда или поддержка. Если владельца нет, документ живёт до первого изменения.

Критерий готовности формулируют через читателя. README готов, когда человек с чистого компьютера проходит установку по тексту и получает работающее приложение. Описание API готово, когда интегратор может собрать запрос по примеру и понять ошибку по коду ответа.

Версия важна не меньше. Документ без версии нельзя сопоставить с продуктом. Через полгода никто не знает, относится ли инструкция к текущей сборке или к прошлогодней.

### Документация рядом с кодом

Документ удобно хранить там же, где код. Тогда он проходит то же ревью, попадает в ту же историю и обновляется тем же коммитом. Этот подход называют docs-as-code.

У него есть цена: документацию нужно собирать и проверять как код. Ссылки ломаются, разметка ошибается, примеры устаревают. Зато исчезает разрыв между версией продукта и версией текста.

Противоположный подход, отдельный сайт документации, удобен для больших продуктов с редакторами и переводом. Для учебного проекта он чаще вредит: сайт живёт отдельно, обновляется редко и быстро расходится с репозиторием.

Практическое правило: **документ лежит рядом с тем, что описывает**. README в корне, описание API рядом с сервисом, ADR в папке решений, changelog в корне.

### Сколько стоит документация

Документация расходует время трижды: на написание, на проверку и на поддержку. Если не считать эти затраты, документ появляется один раз и остаётся в том виде, в каком был написан.

Полезно оценивать не объём, а число отвеченных вопросов. README, который снимает десять вопросов новичка, полезнее тридцати страниц архитектурных рассуждений, которые никто не открывает.

Правило повторного вопроса помогает выбрать, что документировать. Если один и тот же вопрос задали дважды, ответ стоит записать. Если вопрос задают в третий раз, документ нужно поставить туда, где вопрос возникает: в README, в шаблон задачи или в сообщение об ошибке.

Документация имеет обратную сторону: её нужно поддерживать. Поэтому лучше меньше документов, но с владельцем и датой проверки, чем много файлов без ответственного. «Документационный долг» это не метафора: устаревший текст требует времени на опровержение и портит доверие к остальным документам.

### Почему документация устаревает

Документация устаревает по трём причинам. Первая: код изменился, а текст остался. Вторая: текст был неверным с самого начала, но его никто не проверял. Третья: изменился читатель, а документ продолжают писать для прежней аудитории.

Первая причина самая частая. Её лечат не героическими усилиями, а процессом: изменение поведения и изменение документа идут в одном коммите или в одной задаче. Проверка на ревью спрашивает не «обновил ли ты документацию», а «какой документ теперь врёт».

Вторая причина опаснее. Неверный текст выглядит убедительно. По нему действуют уверенно и получают ошибку. Устаревшая документация хуже отсутствующей: отсутствие заставляет искать, а ложный текст заставляет ошибаться.

Третья причина заметна в учебных проектах. README пишут для преподавателя, а пользуется им следующая группа. Формулировки «сдайте отчёт» остаются, хотя читателю нужно «запустите тесты».

## Четыре вида по цели

Полезную рамку предложил Даниэле Прокида в проекте Diátaxis. Он делит документацию по двум осям: изучение против работы и практика против теории. Получаются четыре вида: учебный материал, руководство по задаче, справочник и объяснение [Diátaxis](https://diataxis.fr/).

| Вид | Вопрос читателя | Форма | Пример в проекте |
|---|---|---|---|
| учебный материал | как сделать первый шаг | последовательные уроки | быстрый старт в README |
| руководство | как решить задачу | шаги для конкретной цели | «Как закрыть заявку» |
| справочник | что означает параметр | точное описание без сюжета | описание API |
| объяснение | почему так устроено | контекст и компромиссы | ADR, схема архитектуры |

Рамка полезна тем, что запрещает смешивать жанры. Учебник с длинным объяснением архитектуры перестаёт быть учебником. Справочник с историями о том, как автор пришёл к решению, перестаёт быть справочником.

В проекте виды часто совмещены. README содержит и учебный материал, и короткий справочник команд. Это нормально, если части разделены заголовками и читатель понимает, где он находится.

Опасность совмещения в том, что один жанр вытесняет другой. Автор увлекается объяснением, и новый человек не находит команду запуска. Или наоборот: остаётся список команд без объяснения, почему они такие.

## README и первый запуск

README это первый документ, который читают в репозитории. Его задача узкая: довести человека до работающего приложения и объяснить, где искать дальше.

Хороший README отвечает на вопросы по порядку:

1. Что это за проект и какую задачу решает.
2. Какие требования к окружению.
3. Как установить зависимости.
4. Как создать и заполнить базу.
5. Как запустить приложение.
6. Как проверить, что всё работает.
7. Где лежат основные папки.
8. Какие известные ограничения.

Порядок не случаен. Человек читает сверху вниз и на каждом шаге должен получить результат. Если установка начинается с описания архитектуры, читатель уходит раньше, чем дойдёт до команды.

### Проверка с чистого листа

Главный критерий README это воспроизводимость на чистом окружении. Автор проверяет текст на своей машине, где уже установлены зависимости, создана база и настроены переменные. У нового человека этого нет.

Проверка выглядит так: новая папка, новая виртуальная среда, чистый клон репозитория. Все команды берутся из README и выполняются буквально. Каждая ошибка означает, что документ чего-то не сказал.

Проверку полезно делать перед каждым выпуском. Это дешевле, чем помогать новому человеку в чате. В команде из двух человек роль нового человека может выполнять коллега, который ещё не запускал проект.

### Команды должны работать

Команда в README это обещание. Если написано `pip install -r requirements.txt`, файл обязан существовать. Если написано `python app.py`, файл обязан запускаться из указанной папки.

Типичные ошибки:

- команда требует пакета, которого нет в списке зависимостей;
- путь указан от другой папки;
- версия Python не совпадает;
- база не создана, а приложение ожидает таблицы;
- переменная окружения не описана;
- пример содержит пароль, который нельзя публиковать.

Каждая ошибка ломает первый запуск. Человек не обязан быть внимательнее автора.

### Что писать про окружение

Требования к окружению описывают явно: версия Python, менеджер пакетов, база данных, необходимые системные библиотеки. Если проект использует SQLite, это стоит сказать: отдельный сервер не нужен. Если нужен MySQL, указывают версию и способ запуска.

Хорошая практика дать две команды: установка и проверка. Проверка может быть тестом или коротким скриптом, который печатает версию и подключается к базе.

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
python -m pytest -q
```

Для Linux и macOS активация выглядит иначе. Если проект учебный и кроссплатформенный, в README приводят оба варианта. Если только Windows, это тоже пишут явно, чтобы не тратить время на догадки.

### Раздел «если что-то пошло не так»

Первый запуск редко проходит идеально. Хороший README содержит короткий раздел с типичными сбоями: симптом, причина, действие.

| Симптом | Частая причина | Что сделать |
|---|---|---|
| порт занят | запущен другой экземпляр | остановить процесс или сменить порт |
| модуль не найден | не активирована среда | активировать окружение и установить зависимости |
| таблица не существует | не выполнена миграция | создать базу и применить схему |
| неверная кодировка | файл сохранён в другой кодировке | сохранить в UTF-8 |
| отказ доступа к базе | не задан путь или пароль | проверить переменные окружения |

Раздел не должен превращаться в форум. Пять-семь самых частых случаев достаточно. Остальное ищут в журнале и в трекере.

Полезно указать, куда писать при проблеме: issue в репозитории, чат команды или почта. Это экономит время и не оставляет человека одного с ошибкой.

### README и документация кода

README не заменяет комментарии и docstring. Он объясняет, как пользоваться проектом снаружи. Docstring объясняет, что делает функция и какие у неё аргументы.

В Python договорённости о docstring описаны в PEP 257 [PEP 257](https://peps.python.org/pep-0257/). Короткая строка после определения функции, затем пустая строка и подробности. Стиль не так важен, как наличие и актуальность.

```python
def close_request(request_id: int, user: User) -> None:
    """Закрыть заявку от имени пользователя.

    Проверяет право: менеджер или владелец заявки.
    """
```

Docstring нужен тому, кто вызывает функцию из кода. README нужен тому, кто запускает проект. Руководство нужно тому, кто пользуется интерфейсом. Это три разных читателя.

::figure docs-diataxis | Нажмите на цель чтения: схема покажет вид документа, его вопрос и типичную ошибку. Карточки соответствуют четырём видам по цели.

Схема помогает выбрать жанр до того, как начат текст. Если цель не формулируется, документ лучше не писать: он превратится в смесь.

## API как контракт

Описание API это не рассказ о функциях, а контракт обмена. Интегратору нужно знать, какой запрос отправить, что придёт в ответ, какие ошибки возможны и что они означают.

Минимальный набор для каждой конечной точки:

- метод и путь;
- параметры пути, запроса и заголовков;
- формат тела;
- успешный ответ с примером;
- коды ошибок и условия их возникновения;
- ограничения: размер, частота, права.

Пример:

```text
GET /api/requests?status=open&limit=20
200: {"items": [{"id": 1, "subject": "Лампа", "status": "open"}], "next": null}
401: нет или истёк токен
403: нет прав на список
422: недопустимый статус
```

Пример важнее описания. По схеме `{"items": [...], "next": null}` интегратор понимает, что список постраничный, а пустая страница возвращает пустой массив, а не ошибку. Без примера он будет угадывать.

### Формальное описание

Для HTTP API используют OpenAPI Specification. Спецификация 3.1.1 описывает структуру документа: пути, операции, схемы данных, ответы и безопасность [OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html).

Формальное описание даёт три выгоды. Его можно проверить на соответствие коду. По нему генерируют клиентов и документацию. Оно служит основой для тестов контракта.

Цена тоже есть. Спецификация требует дисциплины: при изменении ответа нужно обновить схему, иначе она начнёт врать. Если спецификацию пишут отдельно от кода, она устаревает так же, как обычный текст.

Разумный компромисс для учебного проекта: спецификация как источник истины для контракта, примеры в ней, а серверная проверка соответствия хотя бы для главных ответов.

### Ошибки как часть контракта

Ошибки описывают так же подробно, как успешные ответы. Интегратор должен знать, что делать при 401, 403, 404, 409 и 422.

| Код | Когда | Что делать клиенту |
|---|---|---|
| 400 | тело не разбирается | исправить запрос |
| 401 | нет токена | обновить токен |
| 403 | нет прав | не повторять |
| 404 | объект не найден | показать пустое состояние |
| 409 | конфликт версий | перечитать и повторить |
| 422 | данные не прошли проверку | показать поля с ошибкой |
| 500 | сбой сервера | повторить с задержкой |

Различие между 400 и 422 важно. 400 означает, что запрос не удалось разобрать. 422 означает, что запрос разобран, но данные неверны. Клиент обрабатывает их по-разному.

Формат ошибки тоже часть контракта. Полезно возвращать стабильную структуру: код, сообщение для человека и список полей с ошибками. Тогда клиент показывает сообщение, не разбирая текст, а проверка форм подсвечивает конкретное поле.

### Аутентификация, идемпотентность, пагинация

Три вещи в API ломают интеграцию чаще всего, и все три должны быть в описании.

**Аутентификация.** Где передаётся токен, какой заголовок, что означает истечение срока. Различие 401 и 403 описано выше: 401 говорит «представься», 403 говорит «тебе нельзя».

**Идемпотентность.** Повторная отправка запроса не должна создавать вторую заявку, если клиент повторил запрос после таймаута. Для этого используют ключ идемпотентности в заголовке. В описании указывают, сколько времени ключ хранится и что вернётся при повторе.

**Пагинация.** Клиент должен знать, как получить следующую страницу и когда остановиться. Курсор надёжнее номера страницы при изменении данных: новая запись не сдвигает выдачу. В ответе полезно поле `next`, как в примере выше.

Если этих деталей нет, интегратор придумает свои. Его решение может оказаться несовместимым с сервером, и виноватым будет описание.

### Версии и совместимость

API меняется. Новое поле в ответе обычно безопасно, удаление поля ломает клиента. Изменение типа с числа на строку ломает почти всегда.

Поэтому контракт версионируют. Версия может быть в пути (`/api/v2/requests`), в заголовке или в самом сервисе. Способ выбирают один и придерживаются его.

Документация обязана указывать, что изменилось между версиями. Без этого интегратор узнаёт о несовместимом изменении из падения в работе.

### Сгенерированное и рукописное

Документацию можно генерировать из кода и схем. Генерация хороша для справочника: список параметров и типов всегда совпадает с реализацией. Рукописный текст лучше для объяснения: зачем нужна конечная точка и как выбрать между двумя похожими.

Практика проста: справочную часть генерируют, объяснения пишут руками и держат рядом. Попытка сгенерировать смысл даёт текст без смысла.

## Руководство пользователя

Руководство нужно человеку, который выполняет работу, а не изучает систему. Его единица это задача, а не экран. «Как закрыть заявку» полезнее, чем «Описание формы закрытия».

Для каждого сценария достаточно пяти частей: что нужно до начала, шаги, ожидаемый результат, что делать при ошибке и куда обратиться. Шаги пишут глаголами: «нажмите», «выберите», «введите». Термины берут из интерфейса, иначе пользователь ищет кнопку, которой нет.

| Сценарий | Предусловие | Результат |
|---|---|---|
| создать заявку | пользователь вошёл в систему | заявка в статусе открыта |
| найти заявку | есть хотя бы одна заявка | список с фильтром |
| закрыть заявку | роль позволяет закрытие | статус закрыта, запись в истории |

Скриншоты помогают, но устаревают быстрее текста. Если интерфейс меняется часто, лучше описывать смысл шага и подписывать элементы, чем показывать устаревшую копию экрана. Снимок уместен там, где положение элемента трудно описать словами.

Ошибки описывают с точки зрения пользователя. Не «ошибка 422», а «поле темы слишком длинное, сократите до 80 символов». Технический код можно указать рядом, но не вместо объяснения.

Руководство не должно превращаться в учебник. Пользователю не нужна история решения, ему нужен результат. Если хочется объяснить, почему система устроена именно так, для этого есть отдельный вид документа.

## ADR: почему так решили

**ADR**, architecture decision record, фиксирует архитектурное решение: контекст, варианты, выбор и последствия. Формат предложил Майкл Нигард в 2011 году [Nygard, 2011](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions).

Структура короткая:

- заголовок и дата;
- статус: предложено, принято, заменено;
- контекст: какие силы действуют;
- решение: что выбрали;
- последствия: что станет проще, что сложнее.

Пример:

```text
ADR 3. Хранение данных в SQLite
Статус: принято, 2026-02-10
Контекст: учебный продукт, один сервер, до 40 пользователей,
нет администратора базы, установка должна быть простой.
Решение: SQLite в файле рядом с приложением.
Последствия: простая установка и резервная копия файлом;
ограниченная параллельная запись; переход на серверную
базу потребует миграции.
```

ADR объясняет не «что», а «почему». Код показывает, что выбрали. ADR показывает, какие варианты рассматривали и чем заплатили.

### Когда писать ADR

ADR пишут, когда решение трудно отменить или когда его будут пересматривать. Выбор базы, способ аутентификации, формат обмена, схема развёртывания подходят. Выбор имени переменной не подходит.

Признак: если через год новый человек спросит «почему так», ответ должен быть в репозитории, а не в чьей-то памяти.

ADR не переписывают задним числом. Если решение изменилось, пишут новый документ со статусом «заменяет ADR 3». Старый остаётся историей. Иначе теряется причина, по которой прошлое решение казалось разумным.

Полезен индекс: список ADR с номерами, заголовками и статусами. Он занимает десять строк и позволяет найти нужное решение без поиска по файлам.

### ADR, RFC и журнал решений

Три формата легко перепутать.

**RFC** это предложение для обсуждения. Он описывает варианты и собирает замечания до решения. RFC может закончиться ничем.

**ADR** это запись о принятом решении. Он короткий, фиксирует контекст и последствия, не пересказывает обсуждение.

**Журнал решений** это список ADR или коротких записей: дата, вопрос, выбор. Он нужен для навигации, а не для чтения подряд.

В учебной команде достаточно ADR и журнала. RFC полезен, если решение затрагивает несколько команд и требует согласования. Для выбора библиотеки в проекте из трёх человек хватит одной страницы ADR.

### Последствия важнее решения

Раздел последствий часто пишут формально: «плюсы и минусы». Польза появляется, когда последствия конкретны.

Плохо: «SQLite может не подойти при росте нагрузки».

Хорошо: «одновременная запись блокируется; при 40 пользователях это допустимо, при 400 понадобится серверная база; резервная копия делается копированием файла и требует остановки записи».

Конкретность позволяет принять решение позже, когда условия изменятся. Она же показывает, что автор понимал цену выбора.

## Changelog: что изменилось

**Changelog** перечисляет изменения по версиям так, чтобы читатель понял, что затронет его при обновлении. Формат Keep a Changelog задаёт простые правила: версия, дата, категории, понятные формулировки [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/).

Категории:

- добавлено;
- изменено;
- исправлено;
- удалено;
- безопасность.

Запись пишут для пользователя, а не для автора коммита. «Исправлен баг в обработчике» ничего не говорит. «Заявка с кавычкой в теме больше не теряется» говорит.

### Changelog не равен git log

История коммитов описывает, как менялся код. Changelog описывает, что изменилось для пользователя. Это разные аудитории и разный уровень детализации.

В git log может быть двадцать коммитов про рефакторинг, которые не меняют поведение. В changelog они не попадают. В git log может быть один коммит с несовместимым изменением, который в changelog занимает отдельный раздел.

Автоматическая генерация из коммитов экономит время, но требует дисциплины сообщений. Если сообщения написаны для себя, changelog получится нечитаемым.

### Breaking changes

Изменение, которое ломает совместимость, указывают отдельно и объясняют, что делать. Недостаточно написать «удалён параметр `status`». Нужно сказать, чем его заменить и как мигрировать.

Для версий используют семантическое версионирование: major меняется при несовместимом изменении, minor при добавлении совместимой функции, patch при исправлении. Связь между версией и changelog делает обновление предсказуемым.

::figure changelog-anatomy | Разметка записи changelog: версия и дата, категории, формулировка для пользователя, отдельный блок несовместимых изменений и ссылка на сравнение версий.

Схема показывает, что запись читается как ответ на вопрос «что мне делать при обновлении». Если ответа нет, запись неполная.

## Реальные случаи

Документация редко выглядит причиной аварии. Но три случая показывают, что её отсутствие или неточность меняют последствия.

### Equifax, 2017

В 2017 году злоумышленники получили данные около 147,9 миллиона потребителей из системы кредитного бюро Equifax. Уязвимость в Apache Struts была известна, исправление вышло в марте 2017 года, а атака продолжалась с мая по июль.

Отчёт комитета Палаты представителей США по надзору и правительственной реформе, опубликованный в декабре 2018 года, разбирает не только пропущенное обновление, но и управление: неполную инвентаризацию систем, отсутствие единой картины того, где работает уязвимое программное обеспечение, и слабый контроль обновлений [U.S. House, 2018](https://oversight.house.gov/wp-content/uploads/2018/12/Equifax-Report.pdf).

Инвентаризация это документ. Если в организации нет списка систем, версий и владельцев, вопрос «где у нас Struts» решается обходом серверов. Пока обход идёт, уязвимость остаётся открытой.

Отчёт отдельно отмечает разрыв между знанием и действием. Исправление было доступно за два месяца до атаки, но организация не смогла быстро определить, где именно используется уязвимая версия, и не провела проверку полноты обновления.

Урок: **документация инфраструктуры является частью безопасности**. Список компонентов, версий и ответственных нужен не для отчёта, а для реакции на уязвимость.

### left-pad, 2016

В марте 2016 года автор небольшого пакета `left-pad` удалил его из реестра npm вместе с 272 другими своими пакетами. Пакет напрямую или через зависимости использовали многие проекты. В течение нескольких минут после удаления посыпались сотни отказов в минуту, потому что сборочные цепочки не могли получить зависимость.

Компания npm описала события в блоге: потребовалось около 2,5 часа, чтобы восстановить работоспособность, а одну из версий пришлось публиковать заново из резервной копии, потому что часть проектов требовала конкретную версию `0.0.3` [npm, 2016](https://blog.npmjs.org/post/141577284765/kik-left-pad-and-npm).

Причина масштаба не в сложности пакета, а в контракте зависимостей. Проекты не знали полный список своих зависимостей и не имели плана на исчезновение пакета. Когда он пропал, не осталось документа, по которому можно быстро понять, что именно сломалось.

Урок: **зависимости тоже документируют**. Файл блокировки версий, список критичных библиотек и запись о причине выбора снижают панику при исчезновении или смене зависимости.

### Log4Shell, 2021

В декабре 2021 года обнаружили уязвимость CVE-2021-44228 в библиотеке Log4j, которую используют миллионы приложений на Java. Агентство по кибербезопасности США CISA выпустило совместное предупреждение с перечнем уязвимых версий и мер [CISA, 2021](https://www.cisa.gov/news-events/cybersecurity-advisories/aa21-356a).

В предупреждении указан диапазон: версии с 2.0-beta9 по 2.12.1 и с 2.13.0 по 2.15.0. Этого недостаточно, чтобы найти уязвимость в своей системе. Нужно знать, какие приложения используют Log4j и какие версии в них входят.

Быстрее отвечали те, у кого была инвентаризация зависимостей. Без неё библиотеку искали по исходникам, контейнерам и спискам установленного программного обеспечения.

Для такой инвентаризации используют перечень компонентов сборки, часто называемый SBOM. Это машиночитаемый список библиотек и версий, который собирается вместе с продуктом. Без него вопрос об уязвимой зависимости решается вручную, а ручной обход не масштабируется.

Урок: **точность документации измеряется скоростью ответа на вопрос**. Если на вопрос «используем ли мы уязвимую версию» нельзя ответить за час, документация не выполняет свою работу.

| Случай | Чего не хватило | Что помогает |
|---|---|---|
| Equifax | инвентаризации систем и версий | реестр компонентов и владельцев |
| left-pad | фиксации зависимостей | файл блокировки и список критичных пакетов |
| Log4Shell | карты зависимостей | автоматический список версий |

Общее у трёх случаев одно: документ нужен не для проверки, а для действия под давлением.

## Документация учебного продукта

Учебный проект не требует многотомного руководства. Ему нужен минимальный комплект, который отвечает на вопросы читателей.

**README.** Назначение, требования, установка, запуск, проверка, структура, ограничения. Одна страница.

**Описание API.** Пять-семь конечных точек с примерами, ошибками и правами. Одна страница или файл OpenAPI.

**Руководство пользователя.** Три-пять сценариев: создать заявку, найти, закрыть, сменить статус, выйти. Без описания каждой кнопки.

**ADR.** Два-три решения: база, аутентификация, формат обмена. По одной странице.

**Changelog.** Одна запись на версию, категории и понятные формулировки.

Этого достаточно, чтобы новый человек запустил проект, интегратор собрал запрос, пользователь выполнил задачу, а команда поняла решения.

Комплект проверяют по вопросам, а не по числу страниц. Может ли человек, не видевший проект, запустить его за один вечер? Может ли интегратор собрать запрос без переписки с автором? Понимает ли пользователь, что делать при ошибке? Находит ли команда причину решения через год? Если на все четыре вопроса есть ответ, документация работает.

### Как поддерживать свежесть

Свежесть обеспечивают три привычки.

Первая: документ меняют в том же коммите, что и поведение. Ревью проверяет, не остался ли текст неверным.

Вторая: у каждого документа есть владелец и дата последней проверки. Дата не гарантирует правду, но показывает, когда текст читали.

Третья: команды и примеры проверяют автоматически, где возможно. README можно прогнать в чистом контейнере, примеры API отправить в тест контракта, ссылки проверить сборкой.

### Ревью документации

Документ проверяют так же, как код. Ревью смотрит на четыре вещи: читателя, полноту, точность и свежесть.

Читатель проверяется вопросом «кто это откроет и что он уже знает». Если текст предполагает знание, которого у читателя нет, начало нужно переписать.

Полнота проверяется прохождением сценария. Человек берёт документ и выполняет шаги, не заглядывая в код. Каждый пропуск становится задачей.

Точность проверяется запуском команд и сверкой примеров с текущей версией. Ссылки проверяет сборка, команды проверяет человек или скрипт.

Свежесть проверяется датой и диффом. Если поведение изменилось, а документ нет, ревью должно это заметить. Автоматическая проверка не понимает смысл, поэтому последнее слово остаётся за человеком.

### Что писать не нужно

Не нужно пересказывать код. Комментарий, который повторяет строку, бесполезен. Не нужно описывать очевидные кнопки. Не нужно хранить пароли и токены. Не нужно писать документ «для отчёта», если у него нет читателя.

Документация это инструмент, а не доказательство трудолюбия. Лучше короткий README, который работает, чем тридцать страниц, которые никто не открывает.

### Один источник истины

Копия документа устаревает быстрее оригинала. Если пример запроса продублирован в README, в руководстве и в описании API, при изменении формата обновят один из трёх. Остальные начнут врать.

Правило простое: у факта есть одно место, остальные ссылаются на него. Список полей живёт в спецификации, README даёт ссылку. Команда запуска живёт в README, руководство ссылается на раздел.

Ссылки тоже требуют дисциплины. Якорь меняется вместе с заголовком, и ссылка ломается. Проверка ссылок в сборке ловит это раньше читателя.

## Итоги

- Документ выбирают по читателю, вопросу и моменту чтения.
- Четыре вида документа различаются целью: научить, помочь, описать, объяснить.
- README доводит до первого запуска и проверяется на чистом окружении.
- API описывают как контракт с примерами и ошибками.
- ADR сохраняет контекст и последствия решения.
- Changelog говорит пользователю, что изменилось, а не пересказывает коммиты.
- Документация зависимостей и систем нужна для реакции на инцидент.
- Свежесть поддерживается процессом, а не разовой акцией.
