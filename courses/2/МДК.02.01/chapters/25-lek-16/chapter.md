## «Запустите как-нибудь»

Новый разработчик открывает проект. В README одна строка: «Запустите как-нибудь». В коде нет описания API, а решение «почему выбрали SQLite» помнит только ушедший сотрудник.

**Документация** это ответы на вопросы, которые возникают у читателя. Документ нужен не для отчёта, а для конкретного вопроса.

Главная мысль занятия: **документ выбирают по читателю и вопросу**. Один файл на все случаи быстро устаревает.

## Виды документов

::figure docs-map | Карта документации: README для разработчика, API для интегратора, руководство для пользователя, ADR для команды, changelog для всех.

| Документ | Читатель | Вопрос |
|---|---|---|
| README | новый разработчик | как установить и запустить |
| API | интегратор | какой запрос и какой ответ |
| руководство | пользователь | как выполнить задачу |
| ADR | команда | почему так решили |
| changelog | все | что изменилось в версии |

Документ может быть коротким. Главное, чтобы он отвечал на вопрос и был актуален.

## README

README содержит:

1. назначение проекта;
2. требования к окружению;
3. установку;
4. запуск;
5. проверку работы;
6. структуру папок;
7. известные ограничения.

Команды должны быть скопированы и проверены. Если написано `pip install -r requirements.txt`, файл обязан существовать.

README не пересказывает весь код. Он доводит до первого успешного запуска.

## API

Описание API включает:

- адрес и метод;
- параметры;
- формат тела;
- успешный ответ;
- коды ошибок;
- пример запроса и ответа.

Пример:

```text
GET /api/requests?status=open
200: [{"id": 1, "subject": "Лампа", "status": "open"}]
401: нет токена
403: нет прав
```

Описание без примеров заставляет интегратора угадывать.

## Руководство пользователя

Руководство пишут по сценариям, а не по кнопкам. «Как создать заявку» лучше, чем «Описание формы».

Для каждого сценария:

- что нужно до начала;
- шаги;
- ожидаемый результат;
- что делать при ошибке.

Скриншоты помогают, но не заменяют текст. Они устаревают быстрее.

## ADR

**ADR** фиксирует архитектурное решение: контекст, варианты, выбранный вариант, последствия.

Пример:

> Контекст: нужна база без отдельного сервера. Решение: SQLite. Последствия: простая установка, ограничение на одновременную запись.

Через год ADR объясняет, почему решение было разумным в тех условиях.

## Changelog

**Changelog** перечисляет изменения по версиям. Читатель понимает, что сломается при обновлении.

Категории:

- добавлено;
- изменено;
- исправлено;
- удалено;
- безопасность.

Changelog не равен списку коммитов. В него попадают изменения, важные пользователю.

## Где документация ломается

**Документ ради отчёта.** Написан один раз и не обновляется.

**Команды не проверены.** Установка не работает с чистого листа.

**Нет читателя.** Непонятно, кому адресован текст.

**Скриншоты вместо текста.** Интерфейс изменился, инструкция устарела.

**Нет примеров API.** Интегратор угадывает формат.

**Решение без контекста.** Через год непонятно, почему так сделали.

> [!PITFALL] Устаревшая документация хуже отсутствующей: по ней действуют уверенно и получают ошибку.

## Итоги

- Документ выбирают по читателю и вопросу.
- README доводит до первого запуска.
- API описывают с примерами и ошибками.
- Руководство строят по сценариям.
- ADR и changelog сохраняют решения и изменения.

::quiz
Q: Зачем нужна документация?
+ Отвечать на вопросы читателя
- Увеличивать объём проекта
- Заменять тесты
- Хранить пароли
! Польза для читателя.

Q: Для кого README?
+ Для нового разработчика
- Для пользователя
- Для бухгалтера
- Для провайдера
! Первый запуск.

Q: Что описывает API?
+ Запросы, ответы и ошибки
- Установку проекта
- Правила бизнеса
- Дизайн экрана
! Контракт интеграции.

Q: Что содержит ADR?
+ Контекст, варианты, решение и последствия
- Список коммитов
- Скриншоты
- Прайс
! Архитектурное решение.

Q: Что содержит changelog?
+ Изменения, важные пользователю
- Все коммиты подряд
- Пароли
- Список сотрудников
! История версий.

Q: Как строят руководство пользователя?
+ По сценариям
- По кнопкам
- По файлам
- По авторам
! Задачи пользователя.

Q: Почему команды в README нужно проверять?
+ Они могут не работать с чистого листа
- Они слишком длинные
- Они на английском
- Их нельзя копировать
! Проверка установки.

Q: Чем changelog отличается от git log?
+ Changelog говорит о важном для пользователя
- Он длиннее
- Он хранит код
- Он автоматический
! Разная аудитория.

Q: Почему устаревшая документация опасна?
+ По ней действуют и получают ошибку
- Она занимает место
- Она слишком короткая
- Она не переведена
! Ложная уверенность.

Q: Какие документы полезны в проекте?
+ README
+ API
+ Руководство
+ ADR
+ Changelog
- Прайс оборудования
- Личные заметки
! Остальное не документация продукта.

Q: Что входит в README?
+ Назначение
+ Установка
+ Запуск
+ Проверка
- Пароль администратора
- Список клиентов
! Остальное лишнее.

Q: Какие ошибки документации типичны?
+ Документ ради отчёта
+ Команды не проверены
+ Нет читателя
+ Скриншоты вместо текста
- Примеры API
- Проверенный запуск
! Остальное хорошо.

Q: Как называют документ с архитектурным решением?
= ADR
= architecture decision record
! Решение и контекст.

Q: Что перечисляет изменения по версиям?
= changelog
= журнал изменений
! История версий.

Q: Для кого пишут руководство пользователя?
= пользователь
= для пользователя
! Сценарии задач.
