## «У меня собирается»

Разработчик передаёт проект архивом. На другом компьютере не хватает библиотеки, версия Python другая, а файл базы лежит в личной папке. Сборка существует только на машине автора.

**Релиз** это версия продукта, которую можно передать и установить по инструкции. Он включает артефакт, номер версии и список изменений.

Главная мысль занятия: **релиз должен собираться повторяемо**. Если результат зависит от настроек автора, это не релиз.

Слово «собирается» опасно своей простотой. Оно скрывает вопрос: где именно собирается, из каких файлов, с какими версиями инструментов и что попадает в результат. На ноутбуке автора ответ обычно такой: из рабочей папки, с глобально установленными библиотеками, с несохранёнными правками и с файлом настроек, о котором знает только автор. На сервере или на компьютере преподавателя эти условия не выполняются.

Разрыв обнаруживается в самый неудобный момент. Перед защитой проекта выясняется, что установка занимает сорок минут, половина шагов описана в переписке, а собранный архив содержит пароль от базы. Код при этом работал. Не работал процесс выпуска.

Дальше разберём, из чего состоит релиз, почему номер версии является обещанием, зачем нужен changelog и как проверять артефакт до того, как его получит пользователь.

## Релиз это не папка с файлами

Полезно развести четыре близких понятия.

| Понятие | Что это | Проверка |
|---|---|---|
| сборка | процесс получения результата из исходников | команда завершилась без ошибок |
| артефакт | файл или набор файлов, готовый к установке | контрольная сумма совпадает |
| релиз | артефакт плюс версия, changelog и инструкция | установка прошла на чистой среде |
| развёртывание | перенос релиза в рабочую среду | система отвечает пользователям |

Сборка может пройти успешно, а релиза не быть. Например, если артефакт собран, но не имеет номера версии и никто не проверил установку. Развёртывание тоже не равно релизу: один и тот же артефакт можно поставить на тестовый стенд, на компьютер колледжа и на рабочий сервер.

У релиза есть адресат. Пользователь получает не репозиторий и не инструкцию для автора, а готовый продукт с понятным номером и описанием изменений. Поэтому релиз отвечает на четыре вопроса:

- что именно установлено;
- какие изменения вошли в эту версию;
- как проверить, что установка прошла правильно;
- как вернуться к предыдущей версии.

Стандарт ISO/IEC/IEEE 12207:2026 относит выпуск и передачу к процессам жизненного цикла, у которых есть вход, результат и проверка [ISO/IEC/IEEE 12207:2026](https://www.iso.org/standard/90219.html). Это подтверждает простую мысль: релиз является инженерной работой, а не побочным действием разработки.

Если ответа нет хотя бы на один вопрос, передача превращается в пересылку файлов.

Есть ещё один слой, который часто пропускают: **идентичность артефакта**. Два файла с одинаковым именем могут содержать разное содержимое. Если через месяц пользователь сообщает об ошибке, команда должна точно знать, какой файл у него стоит. Номер версии помогает, но только вместе с контрольной суммой и записью о том, из какого коммита собран артефакт.

В учебном проекте достаточно простого правила: каждый переданный файл имеет версию, контрольную сумму и ссылку на инструкцию. Этого мало для крупной системы, но уже достаточно, чтобы не спорить, «та ли это сборка».

## Воспроизводимая сборка

Сборка воспроизводима, когда из одного и того же исходного состояния получается один и тот же результат. Практически это означает четыре условия:

- зависимости зафиксированы;
- команда сборки записана;
- артефакт получается из чистого репозитория;
- результат не зависит от локальных файлов и настроек.

Слово «фиксированы» не означает «навсегда заморожены». Оно означает, что версия зависимости известна и записана. Разница видна в двух строках:

```text
requests>=2.0
requests==2.31.0
```

Первая строка разрешает установить любую версию начиная с 2.0. Сегодня это может быть 2.31, через год 2.40, а вместе с ней придёт изменение поведения. Вторая строка фиксирует конкретную версию. Для библиотеки, которую используют другие, диапазон иногда полезен. Для сборки релиза нужна точность.

В Python версии обычно фиксируют в `requirements.txt` или в lock-файле. В .NET используют файл проекта и `dotnet publish`. В JavaScript применяют lock-файл пакетного менеджера. Названия разные, смысл один: сборка не должна заново выбирать версии зависимостей.

Команда сборки тоже является частью релиза. Если она живёт в голове автора, её нельзя повторить. Хорошая команда короткая и проверяемая:

```text
python -m venv .venv
pip install -r requirements.txt
pytest
python -m build
```

Для .NET аналог выглядит так:

```text
dotnet restore
dotnet test
dotnet publish -c Release -o publish
```

Это не требование к конкретному инструменту. Это требование к форме: шаги записаны, выполняются по порядку и не требуют ручных действий, которых нет в тексте.

### Откуда берётся невоспроизводимость

Результат сборки меняется по нескольким причинам.

**Время.** В артефакт попадает дата сборки или номер сборки, и два запуска дают разные файлы. Это не всегда ошибка, но такие поля нужно отделять от содержательного результата.

**Путь.** Абсолютный путь к папке проекта может попасть в скомпилированный файл или в журнал. На другом компьютере путь другой.

**Порядок файлов.** Обход каталога может возвращать файлы в разном порядке. Если порядок влияет на упаковку, результат меняется.

**Сеть.** Сборка скачивает зависимость с сервера, и сервер отдаёт другую версию или недоступен.

**Локальный кеш.** На машине автора лежит старая библиотека, и сборка незаметно использует её вместо объявленной.

**Несохранённые файлы.** В рабочей папке есть файл, которого нет в репозитории. Сборка из репозитория его не найдёт.

**Секреты и настройки.** Пароль или адрес сервера подставляются из локального файла, поэтому результат зависит от машины.

Проверка проста: взять чистый клон репозитория на другой машине или в контейнере, выполнить записанные команды и сравнить результат. Если сборка требует файла с рабочего стола, она не воспроизводима.

### Герметичная сборка

В книге Google о надёжности сайтов описано понятие **герметичной сборки**: сборка не зависит от того, что установлено на машине сборщика, и использует известные версии инструментов и библиотек [Google SRE, Release Engineering](https://sre.google/sre-book/release-engineering/). Это более строгий вариант воспроизводимости, но идея доступна и в учебном проекте.

Практический минимум:

- сборка запускается из чистого каталога;
- зависимости ставятся по зафиксированному списку;
- версия языка и сборщика записана в README;
- в артефакт не попадают файлы, которых нет в репозитории;
- результат сборки имеет контрольную сумму.

Google в той же главе подчёркивает: релизный процесс должен быть повторяемым, а не «уникальным снегом». Уникальная сборка не проверяется повторно и не восстанавливается через месяц.

### Компромисс точности и свежести

Фиксация версий создаёт работу. Обновление библиотеки требует проверки, а иногда и правок кода. Чем точнее зафиксированы зависимости, тем стабильнее сборка и тем чаще команда должна сознательно обновляться.

Обратная крайность тоже плоха. Проект с зависимостями «примерно такими» однажды перестаёт собираться, потому что внешняя библиотека выпустила несовместимую версию. Ошибка возникает не в момент обновления, а в момент следующей установки.

Разумная стратегия для учебного проекта: точные версии в релизе, отдельная задача на обновление зависимостей, проверка обновления тестами. Обновление становится событием с датой и результатом, а не побочным эффектом установки.

::figure release-pipeline | Конвейер релиза: коммит, тесты, сборка, версия, changelog и установка. Внизу правила semver.

Конвейер на схеме выглядит линейным, но внутри каждого шага есть проверка. Коммит проверяют на состав изменений, тесты на прохождение, сборку на соответствие версии, changelog на понятность, установку на чистую среду. Если шаг не даёт проверяемого результата, он превращается в формальность.

Автоматизация не обязательна на первом шаге. Важна повторяемость команд. Ручной конвейер, записанный в README и выполненный дважды разными людьми, полезнее автоматического, который никто не понимает.

## Semver: три числа и обязательства

**Semantic Versioning**, или semver, задаёт формат `MAJOR.MINOR.PATCH` и правила изменения каждого числа [semver.org](https://semver.org/). Спецификация говорит не о красоте номера, а о том, что пользователь может предположить по номеру.

| Часть | Когда меняется | Что обещает |
|---|---|---|
| MAJOR | несовместимое изменение публичного интерфейса | обновление может потребовать правок |
| MINOR | новая возможность без поломки | старый код продолжает работать |
| PATCH | исправление без изменения интерфейса | поведение исправлено, совместимость сохранена |

Пример: `1.4.2` означает: первая major-версия, четвёртая minor-версия, второе исправление. После несовместимого изменения номер становится `2.0.0`, а не `1.5.0`. После новой возможности без поломки `1.5.0`. После исправления `1.4.3`.

Спецификация требует объявить публичный интерфейс. Для библиотеки это набор функций и форматов, на которые могут опираться другие. Для приложения публичный интерфейс может быть API, формат файла, схема базы или даже набор экранных сценариев, если на них опираются пользователи.

### Правила, которые чаще всего нарушают

**Изменение уже выпущенной версии.** Semver прямо говорит: содержимое выпущенной версии менять нельзя, любое изменение выпускается под новым номером. Если артефакт `1.4.2` пересобрали и заменили, пользователи с той же версией получили разное поведение. Сравнение версий перестаёт работать.

**Несовместимое изменение в patch.** Разработчик переименовал поле в ответе API и выпустил `1.4.3`, потому что «изменилась одна строка». Формально номер говорит «ничего не сломалось», фактически сломался клиент. Пользователь не может защититься, кроме как вручную проверять каждый выпуск.

**Новая возможность в patch.** Тоже нарушение, хотя менее опасное. Номер перестаёт сообщать, что в версии появилось что-то новое.

**Отсутствие объявленного интерфейса.** Если публичный интерфейс не определён, команда спорит, считается ли изменение ломающим. Спор решается мнением, а не документом.

**Major-версия без причины.** Номер `2.0.0` после косметической правки обесценивает сигнал. Пользователи перестают верить, что major означает несовместимость.

### Ноль как особая зона

Версия `0.y.z` означает начальную разработку. Публичный интерфейс не считается стабильным, и изменения могут быть любыми. Это полезная зона для учебного проекта: продукт ещё не передан, интерфейс меняется, обещать совместимость рано.

Версия `1.0.0` означает, что интерфейс объявлен и дальше действуют правила совместимости. Для учебного продукта `1.0.0` удобно ставить к защите проекта: с этого момента изменения должны сопровождаться версией и changelog.

### Pre-release и метаданные

К номеру можно добавить предварительную метку: `1.4.0-beta.1`. Такая версия имеет меньший приоритет, чем `1.4.0`, и означает нестабильность. Метаданные сборки добавляют через плюс: `1.4.0+20261126`. Они не влияют на сравнение версий.

Эти поля полезны, но требуют дисциплины. Если `beta` стоит на версии, которую уже используют как рабочую, метка теряет смысл.

### Где semver не работает

Semver опирается на существование публичного интерфейса и на возможность его сравнивать. В приложении, которое не предоставляет API, граница размыта. В проекте, где версия означает дату (`2026.11`), semver не подходит. В библиотеке, которая ещё не имеет пользователей, строгие правила могут замедлять работу.

Это не отменяет главного: номер версии должен что-то сообщать. Если команда выбрала календарную версию, она обязана объяснить, что означает смена месяца. Если выбрала semver, она обязана соблюдать правила.

Есть и организационная цена. Каждый несовместимый выпуск требует миграции у пользователей. Поэтому крупные библиотеки долго живут на одной major-версии, а новую готовят с руководством по переходу. Semver не запрещает ломать совместимость. Он требует делать это явно.

::figure version-decider | Нажимайте тип изменения: схема показывает, как меняется версия `1.4.2` и в какую категорию changelog попадает запись.

Интерактивная схема полезна как тренажёр: одно и то же изменение можно описать по-разному, и номер версии показывает, какое обещание дано пользователю.

### Проверка совместимости

Номер версии не заменяет проверку. Даже аккуратная команда может ошибиться. Поэтому перед major-выпуском полезно:

- зафиксировать публичный интерфейс в документе;
- прогнать сценарии старого клиента против новой версии;
- проверить миграцию данных;
- описать удаление и замену функций;
- дать пользователю хотя бы одну minor-версию с предупреждением об устаревании.

Semver рекомендует объявлять устаревание в minor-версии, а удалять в major. Это даёт пользователю время. Если функцию удаляют сразу, без промежуточного выпуска, формально номер может быть верным, а процесс миграции всё равно сломан.

## Changelog: текст для человека

**Changelog** это упорядоченный список заметных изменений по версиям. Соглашение Keep a Changelog задаёт простые принципы: changelog пишут для людей, в нём есть запись для каждой версии, изменения сгруппированы по типам, последняя версия идёт первой, дата указана, а формат версии объяснён [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

Стандартные категории:

- **Added**: новая возможность;
- **Changed**: изменение существующего поведения;
- **Deprecated**: функция скоро будет удалена;
- **Removed**: функция удалена;
- **Fixed**: исправление;
- **Security**: закрыта уязвимость.

Категории нужны не для красоты. Они отвечают на разные вопросы пользователя. «Добавлено» говорит, что можно делать нового. «Изменено» предупреждает, что привычный сценарий может работать иначе. «Удалено» требует проверить зависимости. «Безопасность» требует обновиться быстрее обычного.

### Changelog не равен журналу коммитов

Соблазн автоматизации понятен: взять `git log` и превратить в список. Проблема в том, что коммит описывает шаг работы автора, а changelog описывает заметное изменение для пользователя. В журнале будут «поправил отступ», «переименовал переменную», «слил ветку». Пользователь не поймёт, что ему делать.

Keep a Changelog прямо называет журнал коммитов плохой заменой: в нём много шума, а цель записи другая. Хорошая запись отвечает на вопрос «что изменится для меня».

| Плохо | Почему | Лучше |
|---|---|---|
| Рефакторинг модуля | пользователь не видит результата | Заявку можно закрыть с комментарием |
| Обновил библиотеку | непонятно, что это даёт | Исправлено падение при пустом списке |
| Правки по ревью | нет смысла для читателя | Добавлена проверка прав при экспорте |
| Удалил старый код | не сказано, что перестало работать | Удалён экспорт в формате CSV |

Автоматизация полезна как черновик. Инструмент собирает изменения, автор редактирует формулировки и убирает внутренние детали. Полностью автоматический changelog без редактора почти всегда превращается в шум.

### Раздел Unreleased

Соглашение рекомендует держать вверху раздел `Unreleased`, где накапливаются будущие изменения. Перед выпуском записи переносят в раздел с номером и датой. Это уменьшает работу в день релиза и не даёт забыть важное изменение.

Дата пишется в формате `2026-11-26`. Такой формат не путает день и месяц и соответствует ISO 8601. Для учебного проекта это мелочь, которая экономит споры.

### Отозванные версии

Если версия выпущена с серьёзной ошибкой, её помечают как отозванную. Keep a Changelog предлагает метку `[YANKED]`. Она нужна, чтобы пользователь, который ищет информацию о версии, увидел предупреждение, а не пустоту.

Отзыв версии не означает, что её можно переписать. Артефакт остаётся в истории, но получает явную пометку и, если возможно, блокировку установки. Следующая исправленная версия выходит с новым номером.

### Changelog как инструмент поддержки

Changelog экономит время поддержки. Вместо вопроса «что изменилось в новой версии» пользователь читает список. Вместо спора «почему перестало работать» команда смотрит, в какой версии появилось изменение.

Для этого записи должны быть полными. Если в changelog указана только половина изменений, пользователь перестаёт ему доверять. Неполный changelog опаснее отсутствующего: он создаёт ложное чувство, что других изменений нет.

## Артефакт и происхождение

**Артефакт** это файл, который передают для установки: архив, пакет, исполняемый файл, образ контейнера. Артефакт содержит собранный код, файлы конфигурации без секретов, инструкцию и номер версии.

В артефакт не попадают:

- пароли, ключи и токены;
- личные данные пользователей;
- журналы разработки и временные файлы;
- локальные кеши и виртуальные окружения;
- файлы, которых нет в репозитории.

Последний пункт важнее, чем кажется. Если артефакт собран из рабочей папки, в него может попасть старая база, тестовый файл или заметка автора. Проверка состава артефакта должна быть отдельным шагом.

### Контрольная сумма

**Контрольная сумма** это короткий отпечаток файла. Если файл изменился хотя бы на байт, отпечаток меняется. Пользователь скачивает артефакт, вычисляет сумму и сравнивает с опубликованной.

Это защита от случайной подмены и от частичной загрузки. Она не защищает от злоумышленника, который поменял и файл, и опубликованную сумму. Для более сильной гарантии нужна подпись и происхождение.

### Происхождение и SBOM

**Происхождение** (provenance) описывает, где и как собран артефакт: из какого репозитория, коммита, сборочной системы и шагов. Спецификация SLSA описывает уровни гарантий и рекомендует передавать provenance вместе с артефактом [SLSA](https://slsa.dev/). GitHub Actions умеет создавать подписанные attestations для сборок, а также прикладывать список зависимостей [GitHub Actions, artifacts](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts).

**SBOM** (software bill of materials) это перечень компонентов и версий, из которых состоит продукт. Он нужен, когда нужно быстро ответить на вопрос: «есть ли у нас уязвимая библиотека». Без SBOM ответ ищут вручную по всем проектам.

Для учебного проекта достаточно трёх вещей: файл `requirements.txt` с точными версиями, контрольная сумма артефакта и запись в README о том, из какого коммита собрана версия. Это ещё не SLSA, но уже проверяемая цепочка.

### Воспроизводимость как защита от подмены

Проект Reproducible Builds описывает практику, при которой независимый сборщик может повторить сборку и получить тот же результат [Reproducible Builds](https://reproducible-builds.org/). Если результат совпадает, появляется уверенность, что в артефакт не добавлено ничего лишнего.

Это особенно важно для открытого кода, который распространяют архивами. Пользователь доверяет не только репозиторию, но и файлу, который скачал. Если архив собирается не из того же исходника, который виден в репозитории, доверие не подкреплено доказательством.

::figure artifact-anatomy | Что входит в артефакт и что в него попадать не должно. Слева состав релиза, справа типичные лишние файлы, которые превращают передачу в утечку или сюрприз.

Схема подчёркивает простую мысль: артефакт это не «всё, что лежало в папке», а выбранный и проверенный набор.

### Подпись и ключи

Подпись артефакта подтверждает, что его выпустил владелец ключа. Она полезна, но добавляет задачу: ключ нужно хранить, защищать и менять при компрометации. В учебном проекте подпись можно заменить контрольной суммой и записью о сборке. В продукте с внешними пользователями одной контрольной суммы недостаточно.

Не стоит начинать с самой сложной схемы. Сначала команда должна научиться собирать из чистого репозитория и проверять установку. Подпись без воспроизводимой сборки подтверждает только то, что файл подписан, а не то, что он собран из проверенного кода.

::/gate

## Три релиза, которые объясняют правила

Правила про версии и артефакты звучат абстрактно, пока не видно, что происходит при их нарушении. Ниже три случая с официальными отчётами и документами.

### XZ Utils, 2024

В марте 2024 года исследователь Андрес Фройнд обнаружил бэкдор в библиотеке сжатия xz, точнее в liblzma. Атака была направлена на серверы SSH в Linux. Фройнд заметил необычную задержку при входе по SSH и начал разбираться. Оказалось, что вредоносный код присутствовал не только в репозитории, но и в распространяемых архивах версий 5.6.0 и 5.6.1 [Freund, oss-security, 2024](https://www.openwall.com/lists/oss-security/2024/03/29/4).

Ключевая деталь для темы релиза: часть кода находилась только в tar-архивах. Файл `m4/build-to-host.m4` в архиве отличался от версии в git и запускал обфусцированный скрипт при сборке. То есть артефакт не соответствовал исходному коду, который видели проверяющие.

Атака имела условия срабатывания: архитектура x86-64, Linux, glibc, сборка в пакете Debian или RPM. Вредоносный код пытался влиять на проверку подписи в SSH. К счастью, затронутые версии ещё не успели широко попасть в стабильные дистрибутивы. Red Hat присвоил уязвимости номер CVE-2024-3094.

Процессные причины:

- архив релиза собирался не из того же дерева, которое проверяли в репозитории;
- сборочные скрипты в архиве не были частью обычного обзора;
- доверие к сопровождающему заменило проверку происхождения;
- у пользователей не было простого способа сравнить архив с исходником.

Урок: **артефакт это отдельный объект доверия**. Проверять только репозиторий недостаточно. Нужно знать, из какого исходника собран архив, и уметь это доказать. Воспроизводимая сборка и provenance перестают быть академической темой, когда цена подмены измеряется доступом к серверам.

### Windows 10, версия 1809, 2018

В октябре 2018 года Microsoft начала распространять обновление Windows 10 October 2018 Update, версия 1809. Через несколько дней появились сообщения о пропаже файлов. Microsoft приостановила распространение, убрала образы со всех каналов и начала расследование [Microsoft, 2018](https://blogs.windows.com/windowsexperience/2018/10/09/updated-version-of-windows-10-october-2018-update-released-to-windows-insiders/).

Причина оказалась связана с перенаправлением известных папок (Known Folder Redirection). Если пользователь перенёс папки «Документы», «Изображения» или «Рабочий стол» в другое место, но старые файлы остались в исходной папке, обновление могло удалить исходную папку вместе с содержимым. В обновлении был код, который убирал пустые дубликаты папок. Сочетание этого кода с другой последовательностью сборки обновления привело к удалению старых папок.

Microsoft оценила долю пострадавших установок как одну сотую процента. Но компания признала: любая потеря данных серьезна. Обновление было остановлено, исправлено и позже выпущено снова.

Процессные причины:

- проверка не покрыла редкую, но допустимую конфигурацию пользователя;
- изменение, удаляющее папки, не было защищено достаточной проверкой;
- обновление сначала стало доступно вручную, что ограничило масштаб, но не отменило риск;
- откат клиентской системы сложен, поэтому цена ошибки выше, чем у серверного релиза.

Урок: **релиз проверяют на пути миграции, а не только на чистой установке**. Чистая система без старых папок проходит проверку. Пользовательская система с историей и нестандартными настройками ломается. Поэтапное распространение уменьшает масштаб, но не заменяет проверку данных.

### npm и left-pad, 2016

22 марта 2016 года автор пакета `left-pad` удалил из реестра npm свой пакет и ещё 272 пакета. `left-pad` был маленькой функцией выравнивания строки, но от него зависели тысячи проектов, в том числе через цепочки зависимостей. Сборки начали падать сотнями в минуту. npm восстановил версию `0.0.3` из резервной копии, и сбой длился около 2,5 часов [npm, 2016](https://blog.npmjs.org/post/141577284765/kik-left-pad-and-npm).

Формально это не ошибка сборки. Это событие в экосистеме зависимостей. Но для релиза вывод тот же: если артефакт зависит от внешнего пакета, который может исчезнуть, воспроизводимость не гарантирована.

Процессные причины:

- версия пакета не была иммутабельной: её можно было удалить;
- проекты полагались на диапазон версий и не фиксировали зависимость;
- у многих не было локального кеша или зеркала;
- цепочка зависимостей была длиннее, чем думали авторы.

Урок: **версия это контракт не только с пользователем, но и с экосистемой**. Если выпущенная версия может исчезнуть или измениться, на неё нельзя опираться. Фиксация зависимостей, lock-файлы, локальное зеркало и проверка цепочки поставок уменьшают риск.

| Случай | Что сломалось | Какой артефакт помог бы | Вывод |
|---|---|---|---|
| XZ Utils | архив не соответствовал исходнику | воспроизводимая сборка, provenance | проверяй происхождение |
| Windows 1809 | обновление удалило данные | проверка миграции, поэтапный выпуск | проверяй путь пользователя |
| npm left-pad | зависимость исчезла из реестра | lock-файл, зеркало, фиксация | фиксируй и храни зависимости |

Общее у трёх случаев одно: релиз рассматривали как техническую операцию, а не как обязательство перед пользователем. В одном случае обязательством была целостность артефакта, в другом сохранность данных, в третьем доступность зависимости. Формально разные сбои, процессный вывод общий.

## Конвейер релиза в учебном проекте

Учебный проект не требует промышленной инфраструктуры. Ему нужен конвейер, который можно повторить и объяснить.

| Шаг | Действие | Результат | Проверка |
|---|---|---|---|
| 1 | зафиксировать изменения | коммит и тег | история совпадает с релизом |
| 2 | прогнать тесты | отчёт о тестах | все обязательные тесты зелёные |
| 3 | собрать артефакт | архив или пакет | сборка из чистого клона |
| 4 | присвоить версию | номер по semver | номер соответствует изменениям |
| 5 | заполнить changelog | раздел версии | записи понятны пользователю |
| 6 | проверить состав | список файлов | нет секретов и лишних файлов |
| 7 | вычислить сумму | файл с хешем | сумма воспроизводится |
| 8 | установить на чистую среду | работающий продукт | главный сценарий проходит |
| 9 | сохранить предыдущий релиз | архив прошлой версии | откат возможен |

Девять шагов не означают девять инструментов. В небольшом проекте часть шагов выполняется вручную, но каждый имеет результат.

### Автоматизация по частям

Автоматизировать всё сразу не нужно. Порядок полезности обычно такой:

1. тесты, потому что они дают быструю обратную связь;
2. сборка, потому что она должна быть повторяемой;
3. проверка состава артефакта, потому что она предотвращает утечки;
4. публикация и установка, потому что они чаще всего делаются вручную.

Если команда автоматизирует публикацию раньше тестов, она ускоряет выпуск ошибок. Если автоматизирует сборку, но не проверяет состав, она быстрее получает архив с паролем.

В GitHub Actions шаги описываются в workflow, а результат сборки можно сохранить как artifact. Для релиза полезны environments с правилами защиты: обязательное одобрение, ограничение ветки, история развёртываний [GitHub Actions, deployments](https://docs.github.com/en/actions/deployment/about-deployments/deploying-with-github-actions). Это не обязательный инструмент, а пример того, как процесс выражается в конфигурации.

### Тег и версия

Тег в Git и номер версии должны совпадать. Если тег `v1.4.2` указывает на коммит, из которого собран артефакт `1.4.2`, связь проверяема. Если тег поставили после сборки на другой коммит, связь потеряна.

Правило простое: сначала определяется коммит, затем сборка, затем тег, затем артефакт. Не наоборот. Иначе возникает ситуация, когда артефакт существует, а исходник, из которого он получен, неизвестен.

### Хранение релизов

Предыдущий релиз нужно хранить. Не только исходники, но и артефакт, changelog и инструкцию. Если новая версия ломает работу, пользователь должен получить старую без пересборки.

Хранение релизов отвечает на вопрос «что было установлено вчера». В учебном проекте достаточно папки `releases` с архивами и файлами контрольных сумм. В продукте используют репозиторий пакетов или хранилище артефактов.

## Проверка установки на чистой среде

Установку проверяют на среде, где нет следов разработки. Это может быть новая виртуальная машина, контейнер, другой компьютер или новый пользователь системы.

Порядок:

1. взять артефакт из хранилища;
2. сверить контрольную сумму;
3. выполнить инструкцию без подсказок автора;
4. запустить продукт;
5. пройти главный сценарий;
6. проверить, что версия отображается;
7. проверить журналы на ошибки;
8. попробовать удалить или обновить продукт.

Если для установки нужны файлы с рабочего стола автора, релиз не готов. Если инструкция требует команды, которой нет в тексте, релиз не готов. Если после установки версия не отображается, пользователь не сможет сообщить, что у него стоит.

### Что проверять в главном сценарии

Главный сценарий это путь, ради которого продукт существует. Для системы заявок: войти, создать заявку, увидеть её в списке, закрыть. Для учебного проекта достаточно одного сквозного сценария, который проходит от начала до конца.

Проверка установки не заменяет полный прогон тестов. Она отвечает на другой вопрос: работает ли собранный артефакт в среде, похожей на пользовательскую. Тесты могут проходить в репозитории и падать после упаковки, потому что в артефакт не попал файл конфигурации.

### Чистая среда и данные

Чистая среда не означает пустая база. Наоборот, полезно проверить два случая: установка с пустой базой и установка с копией данных предыдущей версии. Второй случай показывает, переживёт ли обновление существующие записи.

Если продукт обновляется поверх старой версии, проверяют миграцию. Если продукт ставится с нуля, проверяют начальные данные и создание администратора. Это разные сценарии, и оба должны быть в инструкции.

### Откат релиза

Для релиза откат означает возврат предыдущего артефакта и, если нужно, предыдущей схемы данных. Он должен быть подготовлен до выпуска.

Минимальные условия:

- предыдущий артефакт сохранён;
- предыдущая версия схемы известна;
- есть резервная копия данных;
- инструкция отката проверена;
- ответственный знает, когда откат применяется.

Откат не всегда возможен. Если новая версия уже изменила данные в несовместимом формате, простой возврат файла не поможет. Поэтому совместимость схемы и обратимость миграции обсуждают до релиза, а не во время сбоя.

## Чек-лист релиза

Перед передачей версии ответьте на вопросы.

1. Сборка выполнена из чистого клона репозитория?
2. Все зависимости зафиксированы?
3. Команда сборки записана в README?
4. Тесты проходят, отчёт сохранён?
5. Номер версии соответствует изменениям?
6. Changelog описывает изменения для пользователя?
7. В артефакте нет секретов и личных данных?
8. Контрольная сумма вычислена и опубликована?
9. Установка проверена на чистой среде?
10. Главный сценарий пройден?
11. Версия видна в продукте?
12. Предыдущий релиз сохранён и откат описан?

Чек-лист не гарантирует отсутствие ошибок. Он не даёт забыть шаг, который потом дорого исправлять.

## Итоги

- Релиз это артефакт, версия, changelog и проверенная установка, а не папка с файлами.
- Воспроизводимая сборка получается из чистого репозитория по записанной команде.
- Semver связывает номер версии с типом изменения и обещанием совместимости.
- Changelog пишут для пользователя, а не пересказывают коммиты.
- Артефакт содержит нужное и не содержит секретов, журналов и личных данных.
- Происхождение и контрольная сумма позволяют проверить, откуда взялся файл.
- Реальные сбои показывают цену подмены артефакта, непроверенной миграции и исчезнувшей зависимости.
- Установку проверяют на чистой среде, а предыдущий релиз хранят для отката.

Q: Что делает сборку воспроизводимой?
+ Чистый репозиторий, фиксированные зависимости и записанная команда
- Сборка на машине автора с локальным кешем
- Ручное копирование файлов из рабочей папки
- Отсутствие тестов и инструкции
! Повторяемость важнее удобства автора.

Q: Когда по semver меняется MAJOR?
+ При несовместимом изменении публичного интерфейса
- При любом исправлении
- При добавлении возможности без поломки
- При смене даты выпуска
! Major сообщает о возможной поломке.

Q: Что semver говорит о содержимом выпущенной версии?
+ Его нельзя менять, изменения выходят под новым номером
- Его можно пересобрать и заменить
- Его можно дополнить новой функцией
- Его можно удалить из реестра
! Иначе номер перестаёт быть обещанием.

Q: Для кого пишут changelog?
+ Для пользователей и сопровождения
- Для компилятора
- Для базы данных
- Для отдела кадров
! Запись объясняет заметное изменение.

Q: Что обязательно входит в артефакт?
+ Собранный код, конфигурация без секретов и инструкция
- Пароли и ключи
- Личные файлы автора
- Журналы разработки
! Артефакт должен быть безопасным и понятным.

Q: Что показал случай XZ Utils?
+ Архив релиза мог отличаться от проверенного исходника
- Язык Python перестал поддерживаться
- Все дистрибутивы обновились автоматически
- Бэкдор был только в документации
! Проверять нужно происхождение артефакта.

Q: Почему обновление Windows 1809 удаляло файлы?
+ Сочетание перенаправления папок и кода очистки дубликатов
- Пользователи удалили файлы сами
- В системе не было антивируса
- Обновление не проверяло лицензию
! Редкая конфигурация не была покрыта проверкой.

Q: Чему учит случай left-pad?
+ Выпущенная версия зависимости должна быть неизменной и доступной
- Маленькие пакеты не нужны
- Реестр пакетов всегда надёжен
- Lock-файлы замедляют сборку
! Исчезновение зависимости ломает сборки.

Q: Что описывает provenance артефакта?
+ Где и как он был собран
- Сколько стоит лицензия
- Кто пользовался продуктом
- Какие тесты не запускались
! Происхождение связывает файл с исходником.

Q: Какие практики поддерживают воспроизводимость?
+ Фиксация версий зависимостей
+ Сборка из чистого клона
+ Запись версии инструментов
+ Проверка контрольной суммы
- Использование локального кеша без объявления
- Правка артефакта после сборки
! Остальное делает результат зависимым от машины.

Q: Что не должно попадать в артефакт?

+ Личные данные
+ Журналы разработки
+ Временные файлы
- Инструкция по установке
- Номер версии
! Остальное нужно релизу.
