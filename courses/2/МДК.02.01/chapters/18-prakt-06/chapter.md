## Что требуется

Смоделировать параллельную работу двух разработчиков и слить изменения.

Работа состоит из четырёх частей:

1. подготовка репозитория и файла;
2. две ветки с пересекающимися изменениями;
3. конфликт и его разрешение;
4. проверка истории и сравнение merge с rebase.

Результаты переносятся в `report_template.docx`.

## Ход работы

### Шаг 1. Подготовьте репозиторий

Создайте папку проекта и файл `app.py` с функцией, которая возвращает подпись статуса:

```python
def status_label(status):
    return "Новая"
```

Сделайте первый коммит в ветке `main`.

### Шаг 2. Создайте две ветки

От `main` создайте ветки `feature/status-a` и `feature/status-b`.

В первой измените подпись для статуса `new` на «Новая заявка». Во второй измените ту же строку на «Открыта». В каждой ветке сделайте коммит.

### Шаг 3. Слейте первую ветку

Переключитесь на `main` и выполните:

```bash
git merge feature/status-a
```

Убедитесь, что слияние прошло без конфликта.

### Шаг 4. Слейте вторую ветку

```bash
git merge feature/status-b
```

Git сообщит о конфликте. Откройте `app.py` и найдите маркеры.

### Шаг 5. Разрешите конфликт

Прочитайте оба варианта. Выберите формулировку, которая соответствует словарю проекта, или соедините их.

Удалите маркеры, сохраните файл и завершите слияние:

```bash
git add app.py
git commit
```

### Шаг 6. Проверьте результат

```bash
git log --oneline --graph
python -c "import app; print(app.status_label('new'))"
```

Запишите историю и вывод функции. Если в проекте есть тесты, запустите их.

### Шаг 7. Сравните с rebase

Создайте отдельную ветку от состояния до слияния, например `feature/status-c`, и выполните rebase на `main`.

Сравните историю до и после. Объясните, почему опубликованную ветку переписывать нельзя.

### Шаг 8. Соберите отчёт

Заполните таблицы, вставьте вывод команд и ответьте на вопросы.

## Критерии оценки

| Балл | Что оценивается |
|---:|---|
| 1 | Работа сделана с ИИ или скопирована без возможности объяснить и исправить |
| 2 | Ветки не созданы или конфликт не разрешён |
| 3 | Слияние выполнено, но проверка или сравнение неполные |
| 4 | Все части выполнены, отчёт заполнен, есть мелкие недочёты |
| 5 | История читается, конфликт объяснён, merge и rebase сравнены по делу |

## Что сдаётся

- `report.docx` с таблицами, выводом `git log` и результатом запуска.
- Скриншот конфликта до и после разрешения.

> [!PITFALL] Удалить чужие строки при конфликте проще всего, но так теряется изменение второй ветки. Сначала разберитесь, зачем оно было нужно.
