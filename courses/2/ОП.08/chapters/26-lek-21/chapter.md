## Вопрос внутри вопроса

Менеджер книжного магазина «Страница» просит список книг, которые дороже средней цены по каталогу. В каталоге 4800 позиций, средняя цена меняется после каждой поставки. Можно поступить в два шага: сначала выполнить `SELECT AVG(price) FROM books`, записать число, а потом подставить его во второй запрос. Способ работает, пока каталог не изменился между двумя запросами. Если в этот момент кто-то добавил книгу, второй запрос посчитает по старой средней, и отчёт разойдётся с базой.

Второй способ надёжнее: попросить базу саму вычислить среднюю в момент выполнения. Для этого второй запрос помещают внутрь первого.

```sql
SELECT title, price
FROM books
WHERE price > (SELECT AVG(price) FROM books)
ORDER BY price DESC;
```

**Подзапрос это SELECT внутри другого запроса.** Он всегда стоит в скобках, выполняется в контексте внешнего запроса и возвращает набор строк и столбцов. Внешний запрос решает, что именно взять из этого набора: одно значение, список значений, признак существования строки или целую таблицу.

| Место подзапроса | Что возвращает | Типичная задача |
|---|---|---|
| WHERE со сравнением | одно значение | цена выше средней |
| WHERE с IN | один столбец, много строк | книги выбранных категорий |
| WHERE с EXISTS | признак, есть строка или нет | клиенты без заказов |
| FROM | таблицу | итоги по площадкам, затем среднее |
| SELECT | одно значение для каждой строки | сумма заказа в строке заказа |
| HAVING | одно значение | категория с максимальной выручкой |

Подзапрос не является отдельной таблицей в базе. Он не сохраняется между выполнениями и не имеет имени, если это имя не задано явно в `FROM`. Поэтому его результат нельзя открыть после завершения запроса. Это важно для понимания: подзапрос это часть вычисления, а не объект схемы.

Результат первого запроса на учебном фрагменте: средняя цена 903,75, выше неё десять книг. Верхние строки выглядят так.

| title | price |
|---|---|
| Искусство видеть | 1500 |
| Базы данных с нуля | 1400 |
| Python для начинающих | 1350 |
| История России в датах | 1300 |
| Основы алгоритмов | 1250 |

Число 903,75 получено как `AVG(price)` по 24 книгам фрагмента. В полном каталоге средняя другая, но форма запроса не меняется. Подзапрос каждый раз считает её заново по текущим данным.

## Скалярный подзапрос: одно значение

Скалярный подзапрос возвращает ровно одну строку и один столбец. Его можно сравнивать с числом, текстом или датой через `=`, `>`, `<`, `>=`, `<=`, `<>`. Он также подходит для `SELECT` и для `HAVING`.

```sql
SELECT title, price
FROM books
WHERE price = (SELECT MAX(price) FROM books);
```

| title | price |
|---|---|
| Искусство видеть | 1500 |

Запрос читается так: найти книгу, цена которой равна максимальной цене каталога. Подзапрос `MAX(price)` всегда возвращает одно число, даже если в каталоге нет ни одной строки. Тогда `MAX` вернёт `NULL`, и сравнение `price = NULL` не найдёт ничего. Это не ошибка синтаксиса, а следствие трёхзначной логики SQL.

Скалярный подзапрос удобен, когда нужно подставить результат агрегата в условие строки. Например, найти книги дороже средней именно в своей категории.

```sql
SELECT b.title, b.price, b.category_id
FROM books b
WHERE b.price > (
  SELECT AVG(b2.price)
  FROM books b2
  WHERE b2.category_id = b.category_id
)
ORDER BY b.category_id, b.price;
```

Здесь внутренний запрос ссылается на `b.category_id` из внешнего. Такой подзапрос называют коррелированным: он выполняется не один раз, а для каждой строки внешнего запроса, потому что его условие зависит от этой строки. Результат на фрагменте: книги, которые дороже среднего по своей категории, а не по всему каталогу.

Главное требование к скалярному подзапросу: он обязан возвращать не больше одной строки. Если строк две, разные СУБД ведут себя по-разному. PostgreSQL и MySQL сообщают об ошибке. SQLite молча берёт первую строку и продолжает работу.

```sql
-- В категории 10 две книги, подзапрос вернёт две строки
SELECT title, price
FROM books
WHERE price = (SELECT price FROM books WHERE category_id = 10);
```

| title | price |
|---|---|
| Python для начинающих | 1350 |

SQLite не сообщил об ошибке и выбрал первую строку. Запрос выглядит рабочим, но ответ неверен: вторая книга с ценой 1190 не попала в результат, хотя условие формально выполнено. Поэтому в скалярном подзапросе всегда добавляют `MAX`, `MIN`, `LIMIT 1` или такое условие, которое гарантирует единственность. Полагаться на «повезёт» в запросе нельзя.

Ещё одна ловушка связана с `NULL`. Сравнение `price = (SELECT ...)` не найдёт строку, если подзапрос вернул `NULL`. Для проверки на отсутствие значения нужен `IS NULL`, а не `= NULL`. Если подзапрос может вернуть пустой результат, лучше использовать `NOT EXISTS` или `COALESCE`.

## Список значений: IN и NOT IN

Оператор `IN` принимает подзапрос, который возвращает один столбец и любое число строк. Это самый частый вид подзапроса в фильтре.

```sql
SELECT title, price
FROM books
WHERE category_id IN (
  SELECT id
  FROM categories
  WHERE name IN ('Компьютеры', 'Бизнес')
)
ORDER BY price DESC;
```

| title | price |
|---|---|
| Python для начинающих | 1350 |
| SQL за 30 дней | 1190 |
| Управление проектами | 1100 |
| Продажи без давления | 820 |

Внутренний запрос вернул два идентификатора категорий, внешний отобрал книги с этими идентификаторами. Тот же результат можно получить через `JOIN`, но `IN` яснее показывает намерение: нужны строки, у которых ключ входит в список.

Обратный оператор `NOT IN` звучит так же просто, но содержит известную ловушку. Если в списке есть `NULL`, результат `NOT IN` почти всегда пуст. Проверим на учебном примере. Пусть есть временная таблица «чёрный список» клиентов, куда при импорте попало пустое значение.

```sql
CREATE TEMP TABLE blacklist (customer_id INTEGER);
INSERT INTO blacklist VALUES (1), (NULL);

SELECT COUNT(*) FROM customers
WHERE id NOT IN (SELECT customer_id FROM blacklist);
```

Результат: `0`. Хотя в базе 12 клиентов, и только один из них входит в список явно. Причина в трёхзначной логике. Условие `id NOT IN (1, NULL)` раскрывается как `id <> 1 AND id <> NULL`. Второе сравнение даёт не истину и не ложь, а «неизвестно». Всё условие становится неизвестным, и строка не проходит фильтр. Один `NULL` в подзапросе обнуляет весь результат.

Безопасная замена выглядит так.

```sql
SELECT COUNT(*) FROM customers c
WHERE NOT EXISTS (
  SELECT 1
  FROM blacklist b
  WHERE b.customer_id = c.id
);
```

Результат: `11`. `NOT EXISTS` проверяет наличие строки и не зависит от `NULL`. Правило простое: `NOT IN` используют только тогда, когда столбец подзапроса объявлен `NOT NULL` и в нём действительно нет пустых значений. Во всех остальных случаях берут `NOT EXISTS` или `LEFT JOIN` с проверкой на `NULL`.

## EXISTS и коррелированные подзапросы

`EXISTS` возвращает не значение, а ответ на вопрос «есть ли хотя бы одна строка». Внутри него обычно пишут `SELECT 1`, потому что содержимое списка столбцов не важно. База прекращает поиск, как только нашла первую подходящую строку, и не читает остальные.

Задача: найти клиентов, которые ещё не сделали ни одного заказа.

```sql
SELECT c.name, c.city
FROM customers c
WHERE NOT EXISTS (
  SELECT 1
  FROM orders o
  WHERE o.customer_id = c.id
);
```

| name | city |
|---|---|
| Никитин Павел | Калуга |
| ООО «Книжный клуб» | Тверь |

Внутренний запрос ссылается на `c.id`, поэтому он коррелирован. Для каждого клиента база ищет хотя бы один заказ с его идентификатором. Если заказ найден, `EXISTS` даёт истину, и `NOT EXISTS` исключает клиента. Если заказов нет, клиент остаётся в результате.

Сравним с `IN`:

```sql
SELECT name, city
FROM customers
WHERE id NOT IN (SELECT customer_id FROM orders);
```

На этой базе оба запроса дают одинаковый результат, потому что `orders.customer_id` объявлен `NOT NULL`. Но стоит появиться `NULL`, и `NOT IN` начнёт возвращать пустой список, а `NOT EXISTS` продолжит работать правильно. Кроме того, `EXISTS` умеет останавливаться на первой найденной строке, а `IN` в некоторых планах строит полный список значений. На больших таблицах это заметно.

Есть и содержательная разница. `IN` сравнивает значение со списком. `EXISTS` проверяет факт наличия строки, удовлетворяющей условию. Если условие сложное и включает несколько столбцов или дополнительную фильтрацию, `EXISTS` выражает его естественнее.

```sql
SELECT b.title
FROM books b
WHERE EXISTS (
  SELECT 1
  FROM book_authors ba
  JOIN authors a ON a.id = ba.author_id
  WHERE ba.book_id = b.id
    AND a.last_name = 'Волков'
);
```

| title |
|---|
| Математика для всех |
| Основы алгоритмов |
| Python для начинающих |
| SQL за 30 дней |

Здесь внутренний запрос соединяет таблицу связи `book_authors` с авторами и проверяет, есть ли у книги автор с фамилией Волков. Внешний запрос выводит только название. Тот же результат дал бы `JOIN` с `DISTINCT`, но `EXISTS` не размножает строки, если у книги два автора с подходящей фамилией. Это важное свойство: проверка существования не создаёт дублей.

Коррелированный подзапрос может быть и в `SELECT`. Тогда он вычисляется для каждой строки внешнего запроса и возвращает одно значение. Например, число заказов клиента.

```sql
SELECT c.name,
       (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.id) AS orders_count
FROM customers c
ORDER BY orders_count DESC, c.name;
```

На фрагменте десять клиентов имеют по два заказа, двое не имеют ни одного. Такой запрос удобен для отчёта, но у него есть цена: подзапрос выполняется для каждой строки. При 12 клиентах это незаметно, при 120 тысячах клиентов без индекса на `orders.customer_id` каждая проверка превратится в полный просмотр таблицы заказов. Индекс по внешнему ключу здесь не роскошь, а необходимость.

## Подзапрос как таблица: FROM

Подзапрос можно поставить в `FROM` и обращаться к его результату как к обычной таблице. Такой результат называют производной таблицей. У неё обязательно должно быть имя, иначе внешний запрос не сможет сослаться на столбцы.

Задача: посчитать выручку по каждой площадке, а затем найти площадки, чья выручка выше средней по четырём площадкам. Сначала нужны итоги по площадкам, потом среднее от этих итогов. Одним `GROUP BY` не обойтись: агрегат от агрегата SQL не разрешает.

```sql
SELECT s.name, t.revenue
FROM stores s
JOIN (
  SELECT o.store_id,
         SUM(i.quantity * i.unit_price) AS revenue
  FROM orders o
  JOIN order_items i ON i.order_id = o.id
  WHERE o.status <> 'отменён'
  GROUP BY o.store_id
) t ON t.store_id = s.id
WHERE t.revenue > (
  SELECT AVG(revenue)
  FROM (
    SELECT SUM(i.quantity * i.unit_price) AS revenue
    FROM orders o
    JOIN order_items i ON i.order_id = o.id
    WHERE o.status <> 'отменён'
    GROUP BY o.store_id
  )
)
ORDER BY t.revenue DESC;
```

| name | revenue |
|---|---|
| Страница на Арбате | 27680 |
| Страница в Туле | 18090 |

Средняя выручка по площадкам равна 17090. Московская и тульская площадки выше неё, тверская и калужская ниже. Внутренний запрос в `FROM` сначала сворачивает строки заказов в четыре итога. Внешний запрос соединяет эти итоги с названиями площадок и сравнивает с ещё одним подзапросом, который считает среднее по тем же четырём итогам.

Производная таблица полезна, когда нужно сначала изменить уровень детализации. В исходных данных строка это позиция заказа. В отчёте строка это площадка. Подзапрос выполняет переход между уровнями, а внешний запрос работает уже с площадками.

Имя производной таблицы задают через `AS`. В SQLite `AS` для таблицы можно опустить, но лучше писать явно: это защищает от путаницы, когда в запросе несколько подзапросов. Столбцы внутри производной таблицы тоже можно переименовать: `AS t(store_id, revenue)`. Тогда внешний запрос не зависит от внутренних псевдонимов.

Вложенность не ограничена двумя уровнями. Но каждый следующий уровень усложняет чтение. Если запрос становится трёхэтажным, часто лучше вынести первый этап в представление или в общее табличное выражение `WITH`. Представления разберём на следующем занятии, а `WITH` по смыслу похож на производную таблицу, только с именем в начале запроса.

## Подзапрос в SELECT

В списке столбцов скалярный подзапрос вычисляет одно значение для каждой строки результата. Это удобно, когда нужно добавить в отчёт показатель, которого нет в исходной таблице.

Например, вывести каждый заказ с его суммой.

```sql
SELECT o.id,
       o.order_date,
       (SELECT SUM(i.quantity * i.unit_price)
        FROM order_items i
        WHERE i.order_id = o.id) AS total
FROM orders o
ORDER BY o.id;
```

| id | order_date | total |
|---|---|---|
| 1 | 2026-09-02 | 3330 |
| 2 | 2026-09-03 | 2390 |
| 3 | 2026-09-04 | 3310 |
| 8 | 2026-09-10 | 7530 |
| 19 | 2026-09-23 | 5690 |

Сумма заказа 8 равна 7530: три позиции, одна из них три экземпляра по 1250. Подзапрос в `SELECT` каждый раз обращается к `order_items` с условием по текущему `o.id`. Если у заказа нет ни одной позиции, `SUM` вернёт `NULL`, а не ноль. В отчёте пустая сумма выглядит как пропуск, поэтому пишут `COALESCE((SELECT ...), 0)`.

Подзапрос в `SELECT` не заменяет `JOIN`, если нужны столбцы из второй таблицы. Он возвращает только одно значение. Если попытаться вернуть название книги или несколько столбцов, SQLite возьмёт первое значение первой строки и не предупредит. Это та же ловушка скалярного подзапроса, что и в `WHERE`.

Цена такого приёма зависит от числа строк внешнего запроса. Для 20 заказов разница незаметна. Для отчёта по миллиону заказов подзапрос в `SELECT` может выполниться миллион раз. Иногда планировщик переписывает его в соединение, но рассчитывать на это без проверки плана нельзя. Если показатель нужен для каждой строки большой таблицы, соединение с заранее сгруппированным подзапросом обычно предсказуемее.

## Подзапрос в HAVING

`HAVING` фильтрует уже посчитанные группы. Скалярный подзапрос здесь позволяет сравнить итог группы с другим итогом, вычисленным по тем же данным. Задача: найти категорию с самой большой выручкой.

```sql
SELECT c.name,
       SUM(i.quantity * i.unit_price) AS total
FROM categories c
JOIN books b ON b.category_id = c.id
JOIN order_items i ON i.book_id = b.id
JOIN orders o ON o.id = i.order_id
WHERE o.status <> 'отменён'
GROUP BY c.id, c.name
HAVING total = (
  SELECT MAX(total)
  FROM (
    SELECT SUM(i2.quantity * i2.unit_price) AS total
    FROM books b2
    JOIN order_items i2 ON i2.book_id = b2.id
    JOIN orders o2 ON o2.id = i2.order_id
    WHERE o2.status <> 'отменён'
    GROUP BY b2.category_id
  )
);
```

| name | total |
|---|---|
| Художественная литература | 15500 |

Внутренний подзапрос в `FROM` считает выручку каждой категории. Внешний `MAX(total)` выбирает наибольшую из двенадцати сумм. Основной запрос группирует те же строки по категориям и оставляет группу, чья сумма совпала с максимумом.

Почему не написать `ORDER BY total DESC LIMIT 1`? Для одного победителя результат тот же, но у двух способов разная семантика при равенстве. `LIMIT 1` вернёт одну произвольную строку из нескольких с одинаковым максимумом. `HAVING` вернёт все категории, которые делят первое место. Если отчёт должен показать всех лидеров, `HAVING` честнее. Если нужна ровно одна строка для карточки, `LIMIT 1` проще, но в нём стоит добавить второй столбец сортировки, чтобы выбор был предсказуемым.

Подзапрос в `HAVING` не видит псевдоним `total` внутри себя. В основном запросе SQLite разрешает ссылаться на псевдоним агрегата, но переносимость этого приёма ограничена: в других СУБД может потребоваться повторить выражение `SUM(...)`. Если запрос должен работать не только в SQLite, выражение дублируют или оборачивают весь расчёт в производную таблицу.

## Как читать подзапрос

Подзапрос удобнее читать изнутри наружу. Сначала выясняют, что возвращает внутренний `SELECT`: одно число, список идентификаторов, признак существования или таблицу с несколькими столбцами. Потом смотрят, как внешний запрос использует этот результат. Такой порядок снимает половину ошибок: если внутренний запрос возвращает таблицу, а внешний ждёт одно число, запрос либо упадёт, либо молча возьмёт первую строку.

Форматирование тоже помогает. Внутренний запрос сдвигают на два пробела, `SELECT`, `FROM` и `WHERE` каждого уровня ставят на отдельные строки, а псевдонимы дают осмысленные: `b` для книг, `o` для заказов, `i` для позиций. Когда в запросе три таблицы и два подзапроса, короткие имена `a`, `b`, `c` быстро перестают что-либо значить.

Полезно проверять каждый уровень отдельно. Скопируйте внутренний запрос, выполните его без внешнего и посмотрите на результат: сколько строк, какие столбцы, есть ли `NULL`. Если внутренний запрос возвращает 4800 строк вместо одного числа, ошибка найдена до того, как попала в отчёт.

## Подзапрос или JOIN

Оба инструмента решают похожие задачи, и выбор не всегда очевиден. Начнём с различия в результате. Соединение добавляет столбцы из второй таблицы и размножает строки, если одной строке первой таблицы соответствует несколько строк второй. Подзапрос в `WHERE` или `SELECT` может сохранить одну строку на клиента.

Проверим на клиентах и заказах.

```sql
SELECT c.name, o.id AS order_id
FROM customers c
JOIN orders o ON o.customer_id = c.id
ORDER BY c.name;
```

Этот запрос вернёт 20 строк, потому что у десяти клиентов по два заказа. Если нужен список клиентов, которые хотя бы раз заказывали, соединение даст дубли. Придётся добавить `DISTINCT`, а это лишняя работа и риск ошибиться при добавлении столбцов.

```sql
SELECT name
FROM customers
WHERE id IN (SELECT customer_id FROM orders);
```

Результат: десять клиентов, каждая строка один раз. Подзапрос здесь точнее выражает вопрос «кто делал заказ», а не «какие заказы были».

| Ситуация | Лучше |
|---|---|
| нужны столбцы обеих таблиц | JOIN |
| нужен только признак или фильтр по второй таблице | подзапрос |
| одна строка на объект, а во второй таблице много связанных строк | подзапрос или GROUP BY |
| нужна сумма по каждой строке | подзапрос в SELECT или соединение с агрегатом |
| важна читаемость сложного условия | EXISTS |
| нужны все строки первой таблицы без пары | LEFT JOIN или NOT EXISTS |

Про производительность нельзя дать один совет на все случаи. Современные планировщики часто превращают `IN` в соединение, а `EXISTS` в полу соединение. На маленьких таблицах разница незаметна. На больших решает наличие индекса и форма условия. Правильный путь такой: написать запрос понятно, посмотреть план через `EXPLAIN QUERY PLAN`, добавить индекс под условие соединения и сравнить время. Об этом подробно на занятии про индексы.

Есть ещё один критерий: семантика. `LEFT JOIN` с условием `WHERE o.id IS NULL` и `NOT EXISTS` дают одинаковый результат, но `LEFT JOIN` может создать дубли, если условие соединения не уникально. `NOT EXISTS` такой ошибки не допускает. Когда вопрос звучит «есть ли», выбирают `EXISTS`. Когда «покажи данные из обеих таблиц», выбирают `JOIN`.

Читаемость тоже часть правильного выбора. Запрос живёт в отчёте и в коде приложения, его будут править через полгода. Подзапрос, который прямо отвечает на вопрос «клиенты без заказов», понятнее соединения с проверкой на `NULL`, даже если план выполнения у них одинаковый. И наоборот, соединение трёх таблиц с явными условиями `ON` понятнее трёх вложенных подзапросов в `SELECT`. Выбирают тот вариант, который быстрее объяснить коллеге, а затем проверяют план и время.

::/gate

## Типичные ошибки

**Скалярный подзапрос возвращает несколько строк.** В SQLite ошибки нет, база берёт первую строку. Результат выглядит правдоподобно и молча теряет часть данных. Лечение: агрегат, `LIMIT 1` или условие, гарантирующее единственность.

**NOT IN с NULL.** Один пустой идентификатор в подзапросе делает результат пустым. Лечение: `NOT EXISTS` или `NOT NULL` в подзапросе.

**Забытая корреляция.** Если во внутреннем запросе написать `WHERE customer_id = customer_id`, оба имени относятся к внутренней таблице, и условие всегда истинно. Подзапрос вернёт все заказы, а не заказы клиента. Лечение: псевдонимы и явное указание внешней таблицы.

**Агрегат в WHERE.** `WHERE price > AVG(price)` вызывает ошибку `misuse of aggregate function AVG()`. Агрегат нельзя использовать в `WHERE`, потому что `WHERE` фильтрует строки до группировки. Нужен подзапрос или `HAVING`.

**Подзапрос в IN возвращает два столбца.** Ошибка `sub-select returns 2 columns - expected 1`. Внутри `IN` должен быть ровно один столбец.

**Отсутствие псевдонима производной таблицы.** Запрос с подзапросом в `FROM` без имени не сможет обратиться к его столбцам. В SQLite имя иногда подставляется автоматически, но в других СУБД запрос не выполнится.

**Ожидание кэширования.** Подзапрос не сохраняет результат между запусками. Если данные изменились, изменится и ответ. Это правильно, но нельзя использовать подзапрос как замену временной таблице при тяжёлом расчёте.

**Слишком глубокая вложенность.** Три и четыре уровня вложенности читаются хуже, чем два запроса с `WITH` или представлением. Если подзапрос повторяется в отчёте несколько раз, его стоит вынести.

**Пустой результат вместо нуля.** Подзапрос с `SUM` по отсутствующим строкам возвращает `NULL`. В отчёте это выглядит как пропущенная сумма, а не как ноль. Если бизнес-смысл требует нуля, применяют `COALESCE`. Если смысл в том, что данных нет, `NULL` оставляют и объясняют в отчёте.

**Одинаковые подзапросы в одном запросе.** Когда один и тот же расчёт повторяется в `SELECT`, `WHERE` и `HAVING`, база может выполнить его несколько раз. Производная таблица или `WITH` позволяют посчитать один раз и сослаться на результат. Это не только короче, но и честнее: все части отчёта используют одно и то же число.

## Итоги

- Подзапрос это SELECT в скобках внутри другого запроса; он не хранится в базе.
- Скалярный подзапрос возвращает одно значение, но SQLite молча берёт первую строку, если строк несколько.
- `IN` удобен для списка значений, а `NOT IN` опасен при `NULL`; надёжная замена это `NOT EXISTS`.
- `EXISTS` проверяет наличие строки, не размножает результат и хорошо работает с коррелированными условиями.
- Подзапрос в `FROM` задаёт новый уровень детализации и позволяет считать агрегат от агрегата.
- Подзапрос в `SELECT` добавляет показатель к каждой строке, но выполняется для каждой строки.
- Выбор между подзапросом и `JOIN` определяется тем, нужны ли столбцы второй таблицы и должна ли сохраняться одна строка на объект.

::quiz
Q: Что такое подзапрос?
+ Запрос SELECT внутри другого запроса
- Копия таблицы, сохранённая в базе
- Индекс, построенный по результату запроса
- Команда изменения структуры таблицы
! Подзапрос выполняется в составе внешнего запроса и не хранится как объект схемы.

Q: Какой результат возвращает скалярный подзапрос?
+ Одну строку и один столбец
- Любое число строк и столбцов
- Только признак существования строки
- Только список идентификаторов
! Скалярный подзапрос используется там, где нужно одно значение.

Q: Что вернёт `SELECT AVG(price) FROM books`, если таблица пуста?
+ NULL
- 0
- Ошибку
- Пустую строку
! Агрегат по пустому набору строк возвращает NULL.

Q: Чем опасен `NOT IN` с подзапросом, где есть NULL?
+ Результат становится пустым из-за неизвестного сравнения
- Запрос выполняется медленнее, но результат верный
- SQLite заменяет NULL на ноль
- Подзапрос возвращает две строки
! Сравнение с NULL даёт «неизвестно», и условие не проходит.

Q: Какая замена `NOT IN` безопасна при возможных NULL?
+ NOT EXISTS
- IN
- EXISTS
- LEFT JOIN без условия
! NOT EXISTS проверяет наличие строки и не зависит от NULL.

Q: Что делает EXISTS?
+ Проверяет, есть ли хотя бы одна подходящая строка
- Возвращает сумму значений
- Считает число строк
- Удаляет повторяющиеся строки
! EXISTS отвечает на вопрос о наличии строки и останавливается на первой.

Q: Где подзапрос может стоять в запросе?
+ В WHERE
+ В FROM
+ В SELECT
- В имени таблицы после CREATE TABLE
! Подзапрос допустим в WHERE, FROM, SELECT, HAVING и в ряде других мест, но не в имени создаваемой таблицы.

Q: Зачем производной таблице в FROM нужно имя?
+ Чтобы внешний запрос мог ссылаться на её столбцы
- Чтобы база сохранила её после запроса
- Чтобы автоматически создать индекс
- Чтобы запретить соединение
! Имя делает результат подзапроса доступным для внешней части.

Q: Что произойдёт в SQLite, если скалярный подзапрос вернёт две строки?
+ База возьмёт первую строку без ошибки
- База вернёт ошибку
- База вернёт обе строки
- База вернёт NULL
! Это особенность SQLite, которую нельзя считать нормальным поведением.

Q: Почему `WHERE price > AVG(price)` не работает?
+ Агрегат нельзя применять в WHERE до группировки
- AVG не существует в SQLite
- price имеет текстовый тип
- Нужно использовать ORDER BY
! Для сравнения со средним нужен подзапрос или HAVING.

Q: Когда JOIN лучше подзапроса?
+ Когда нужны столбцы из обеих таблиц
+ Когда нужно соединить строки по ключу
- Когда нужен только признак наличия заказа
- Когда нужно сохранить одну строку на клиента при многих заказах
! JOIN добавляет столбцы второй таблицы, но может размножить строки.

Q: В каких случаях подзапрос в SELECT может быть дорогим?
+ Когда внешний запрос возвращает много строк
+ Когда подзапрос выполняется для каждой строки без индекса
- Когда подзапрос возвращает одно число
- Когда в подзапросе используется MAX
! Коррелированный подзапрос повторяется для каждой строки внешнего запроса.

Q: Что означает ошибка `sub-select returns 2 columns - expected 1`?
+ Подзапрос в IN вернул два столбца вместо одного
- В таблице две строки с одинаковым ключом
- В SELECT указано два псевдонима
- В WHERE использовано два условия
! Для IN и сравнения нужен ровно один столбец.

Q: Как называется подзапрос, который ссылается на столбец внешнего запроса?
= коррелированный
= коррелированный подзапрос
! Такой подзапрос зависит от текущей строки внешнего запроса.

Q: Какое ключевое слово начинает общее табличное выражение, похожее на именованный подзапрос?
= WITH

! WITH задаёт имя для временного результата в начале запроса.
