## Сводка, в которой не хватает названий

Менеджер просит сводку по заказу: номер заказа, название книги, количество и цена. В таблице `позиция_заказа` есть номер заказа, код книги, количество и цена, но нет самого названия. Название лежит в `книга`, автор в `автор` и `книга_автор`, а площадка в `площадка` и `сотрудник`. Читать сводку из кодов бессмысленно: `код_книги = 217` ничего не говорит продавцу.

Можно было бы выгрузить позиции, затем для каждой строки отдельно сходить в `книга`, потом в `автор`. На десяти строках это сработает, на тысяче превратится в тысячу лишних запросов. Реляционная модель предлагает другой способ: соединить таблицы по общему значению и получить один результат.

**Соединение сопоставляет строки двух таблиц по условию.** Условие чаще всего проверяет равенство внешнего ключа и первичного ключа: `книга.код_книги = позиция_заказа.код_книги`. Результат содержит столбцы обеих таблиц, а число строк зависит от того, сколько пар нашлось и какой вид соединения выбран.

## Как работает соединение

Начнём с крайнего случая. Если условие не задано, база составляет все возможные пары строк. Это декартово произведение.

```sql
SELECT п.название AS площадка, к.название AS категория
FROM площадка п
CROSS JOIN категория к
ORDER BY п.код_площадки, к.код_категории
LIMIT 6;
```

| `площадка` | `категория` |
|---|---|
| Страница Москва | Художественная литература |
| Страница Москва | Детская литература |
| Страница Москва | Учебная литература |
| Страница Москва | Справочная литература |
| Страница Москва | Компьютерная литература |
| Страница Москва | Деловая литература |

Четыре площадки и двенадцать категорий дают 48 строк. Каждая площадка соединена с каждой категорией, даже если книг этой категории на площадке нет. `CROSS JOIN` полезен для построения матрицы «площадка на категорию», но в обычной выборке почти всегда является ошибкой: забытое условие превращает десять строк в миллион.

`INNER JOIN` добавляет условие и оставляет только пары, которые ему удовлетворяют:

```sql
SELECT з.номер_заказа, к.название, п.количество, п.цена_коп
FROM позиция_заказа п
JOIN заказ з ON з.номер_заказа = п.номер_заказа
JOIN книга к ON к.код_книги = п.код_книги
WHERE з.номер_заказа = 1001
ORDER BY к.код_книги;
```

| `номер_заказа` | `название` | `количество` | `цена_коп` |
|---|---|---|---|
| 1001 | Издание 8 | 2 | 118300 |
| 1001 | Издание 103 | 2 | 30800 |
| 1001 | Издание 217 | 4 | 32900 |
| 1001 | Издание 253 | 2 | 68000 |

Слово `INNER` можно не писать: `JOIN` без уточнения означает внутреннее соединение. Условие после `ON` описывает, как строки соотносятся друг с другом. Условие после `WHERE` фильтрует уже готовый результат. Для внутреннего соединения эти два условия часто дают одно и то же, но для внешнего разница принципиальна.

Если соединяемые столбцы называются одинаково, вместо `ON` можно написать `USING`:

```sql
SELECT п.номер_заказа, s.номер_поставки, п.количество, s.количество
FROM позиция_заказа п
JOIN спецификация_поставки s USING (код_книги)
ORDER BY п.код_книги
LIMIT 5;
```

| `номер_заказа` | `номер_поставки` | `количество` | `количество` |
|---|---|---|---|
| 1001 | 3 | 2 | 90 |
| 1001 | 7 | 2 | 23 |
| 1038 | 14 | 4 | 45 |
| 1046 | 11 | 1 | 51 |
| 1035 | 8 | 1 | 59 |

`USING` требует, чтобы столбец с таким именем был в обеих таблицах, и выводит его один раз. В результате два столбца называются одинаково, и при чтении приходится различать их по позиции. Поэтому в отчётах всё равно пишут псевдонимы:

```sql
SELECT п.номер_заказа, s.номер_поставки,
       п.количество AS заказано,
       s.количество AS поставлено
FROM позиция_заказа п
JOIN спецификация_поставки s USING (код_книги)
ORDER BY п.код_книги
LIMIT 5;
```

## Внутреннее соединение и три таблицы

Соединение один-ко-многим размножает строки. Одна книга встречается в нескольких позициях заказов, поэтому при соединении `книга` с `позиция_заказа` книга появится столько раз, сколько раз её заказывали. Это не ошибка, а смысл соединения: каждая строка результата описывает одну пару.

Цепочка из трёх таблиц читается по шагам. Сначала `заказ` соединяется с `сотрудник` по табельному номеру, затем с `площадка` по коду площадки:

```sql
SELECT з.номер_заказа, с.фио AS продавец, п.название AS площадка
FROM заказ з
JOIN сотрудник с ON с.табельный_номер = з.табельный_номер
JOIN площадка п ON п.код_площадки = с.код_площадки
ORDER BY з.номер_заказа
LIMIT 6;
```

| `номер_заказа` | `продавец` | `площадка` |
|---|---|---|
| 1001 | Смирнова Анна Петровна | Страница Москва |
| 1002 | Кузнецов Игорь Львович | Страница Москва |
| 1003 | Петрова Мария Сергеевна | Страница Москва |
| 1004 | Волков Дмитрий Андреевич | Страница Тверь |
| 1005 | Соколова Ольга Ивановна | Страница Тверь |
| 1006 | Морозов Павел Юрьевич | Страница Тверь |

Каждая следующая таблица добавляет столбцы к уже найденным строкам. Заказ ссылается на одного сотрудника, сотрудник на одну площадку, поэтому число строк не меняется. Если бы сотрудник мог относиться к нескольким площадкам, строки размножились бы, и это было бы видно по числу заказов.

Книгу с автором и издательством собирают через таблицу связи:

```sql
SELECT к.название AS книга, а.фамилия AS автор, и.название AS издательство
FROM книга к
JOIN книга_автор ка ON ка.код_книги = к.код_книги
JOIN автор а ON а.код_автора = ка.код_автора
JOIN издательство и ON и.код_издательства = к.код_издательства
WHERE к.код_категории = 1
ORDER BY к.код_книги
LIMIT 8;
```

| `книга` | `автор` | `издательство` |
|---|---|---|
| Издание 12 | Достоевский | Эксмо |
| Издание 19 | Маркес | Питер |
| Издание 44 | Пушкин | Питер |
| Издание 54 | Пушкин | АСТ |
| Издание 76 | Стругацкий | Питер |
| Издание 90 | Харари | АСТ |
| Издание 97 | Кинг | МИФ |
| Издание 98 | Кристи | Дрофа |

Здесь четыре таблицы, потому что автор хранится не в книге, а в отдельной связи. Если у книги два автора, она появится две строки. Для отчёта «книга и её авторы» это правильно, для отчёта «число книг» потребуется `DISTINCT` или отдельный подсчёт.

Порядок таблиц в `FROM` не задаёт порядок вывода и не обязан совпадать с порядком соединения. База сама решает, с какой таблицы начать: обычно с той, которая сильнее сокращает результат. Для читателя важен смысл: каждая следующая таблица добавляет столбцы к уже найденным строкам.

Внутреннее соединение отбрасывает строки без пары. Если у книги не указан автор, `JOIN книга_автор` не найдёт соответствия, и книга исчезнет из результата. Если в позиции заказа стоит код удалённой книги, позиция тоже исчезнет. Иногда это именно то, что нужно, иногда потеря строк незаметна и портит отчёт.

Проверить потерю можно сравнением числа строк:

```sql
SELECT COUNT(*) FROM позиция_заказа п
JOIN книга к ON к.код_книги = п.код_книги;
```

```text
185
```

Все 185 позиций нашли книгу, потому что внешний ключ не позволяет ссылаться на несуществующую запись. Если бы ограничение было выключено, часть строк могла бы пропасть.

## Внешние соединения

`LEFT JOIN` сохраняет все строки левой таблицы, даже если пары справа нет. На месте недостающих столбцов появляется `NULL`.

```sql
SELECT к.код_книги, к.название, п.номер_заказа
FROM книга к
LEFT JOIN позиция_заказа п ON п.код_книги = к.код_книги
WHERE к.код_книги <= 3
ORDER BY к.код_книги, п.номер_заказа;
```

| `код_книги` | `название` | `номер_заказа` |
|---|---|---|
| 1 | Издание 1 |  |
| 2 | Издание 2 |  |
| 3 | Издание 3 | 1007 |

Первая и вторая книги не заказывались, но сохранились. Третья заказывалась, у неё есть номер заказа. Если бы стоял `JOIN`, в результате осталась бы только третья строка.

Число строк тоже показывает разницу:

```sql
SELECT COUNT(*) FROM книга к
LEFT JOIN позиция_заказа п ON п.код_книги = к.код_книги;
```

```text
4846
```

Внутреннее соединение дало бы 185 строк, по одной на позицию заказа. Левое сохранило все 4800 книг и добавило к ним 185 позиций, из которых 139 попали на существующие книги. Поэтому строк стало 4800 + 185 - 139 = 4846.

Обратная задача тоже решается левым соединением. Чтобы найти книги, которые ни разу не заказывали, ищут строки, где правая часть пуста:

```sql
SELECT к.код_книги, к.название
FROM книга к
LEFT JOIN позиция_заказа п ON п.код_книги = к.код_книги
WHERE п.код_книги IS NULL AND к.код_книги <= 300
ORDER BY к.код_книги
LIMIT 5;
```

Среди первых трёхсот книг таких 161. Приём называется антисоединением: левое соединение плюс проверка на `NULL` даёт то, чего нет в правой таблице.

`RIGHT JOIN` сохраняет все строки правой таблицы. В SQLite он появился в версии 3.39, до этого его приходилось переписывать перестановкой таблиц:

```sql
SELECT к.название, п.номер_заказа
FROM позиция_заказа п
RIGHT JOIN книга к ON к.код_книги = п.код_книги
WHERE к.код_категории = 1
ORDER BY к.код_книги
LIMIT 5;
```

| `название` | `номер_заказа` |
|---|---|
| Издание 12 | 1038 |
| Издание 19 | 1052 |
| Издание 44 |  |
| Издание 54 | 1053 |
| Издание 76 |  |

Результат совпадает с левым соединением, в котором таблицы поменяли местами. Это общее правило: `A RIGHT JOIN B` равно `B LEFT JOIN A`, если сохранить условие.

`FULL JOIN` сохраняет строки обеих таблиц. Он тоже появился в 3.39:

```sql
SELECT COUNT(*)
FROM позиция_заказа п
FULL JOIN книга к ON к.код_книги = п.код_книги;
```

```text
4846
```

В учебной базе все позиции имеют книгу, поэтому полное соединение дало столько же строк, сколько левое. Если бы существовали позиции с удалённой книгой, они добавились бы отдельными строками с пустыми столбцами каталога.

В старых сборках SQLite `RIGHT` и `FULL` могут быть недоступны. Полное соединение заменяют объединением:

```sql
SELECT к.название, п.номер_заказа
FROM книга к LEFT JOIN позиция_заказа п ON п.код_книги = к.код_книги
UNION ALL
SELECT NULL, п.номер_заказа
FROM позиция_заказа п
WHERE NOT EXISTS (SELECT 1 FROM книга к WHERE к.код_книги = п.код_книги);
```

`UNION ALL` склеивает два результата без удаления дублей. Вторая часть добавляет строки, для которых не нашлось книги. Такой запрос длиннее, но работает везде.

## Ловушки соединений

Первая ловушка связана с местом условия. Если фильтровать правую таблицу в `WHERE`, строки с `NULL` не пройдут проверку и левое соединение станет внутренним:

```sql
SELECT к.код_книги, к.название, п.номер_заказа
FROM книга к
LEFT JOIN позиция_заказа п ON п.код_книги = к.код_книги
WHERE п.количество > 2
ORDER BY к.код_книги
LIMIT 5;
```

В результат попадут только книги, у которых есть позиция с количеством больше двух. Книги без заказов исчезнут, хотя `LEFT JOIN` должен был их сохранить. Условие по правой таблице нужно переносить в `ON`:

```sql
SELECT к.код_книги, к.название, п.номер_заказа
FROM книга к
LEFT JOIN позиция_заказа п
  ON п.код_книги = к.код_книги AND п.количество > 2
ORDER BY к.код_книги
LIMIT 5;
```

Теперь сохраняются все книги, а количество больше двух влияет только на то, какая позиция подставится. У книг без подходящей позиции остаётся `NULL`. Строк в результате 4818: 4800 книг плюс дополнительные пары для книг, у которых несколько подходящих позиций.

Вторая ловушка это размножение строк при двух соединениях один-ко-многим. У книги 134 четыре заказа и две поставки. Соединим оба списка по коду книги:

```sql
SELECT п.номер_заказа, п.количество AS заказано,
       s.номер_поставки, s.количество AS поставлено
FROM позиция_заказа п
JOIN спецификация_поставки s ON s.код_книги = п.код_книги
WHERE п.код_книги = 134
ORDER BY п.номер_заказа, s.номер_поставки;
```

| `номер_заказа` | `заказано` | `номер_поставки` | `поставлено` |
|---|---|---|---|
| 1009 | 5 | 4 | 15 |
| 1009 | 5 | 13 | 72 |
| 1026 | 3 | 4 | 15 |
| 1026 | 3 | 13 | 72 |
| 1030 | 3 | 4 | 15 |
| 1030 | 3 | 13 | 72 |
| 1047 | 3 | 4 | 15 |
| 1047 | 3 | 13 | 72 |

Восемь строк вместо четырёх заказов и двух поставок. Каждый заказ соединён с каждой поставкой. Если просуммировать `заказано`, получится 28 вместо 14, а `поставлено` даст 348 вместо 87. Отчёт завышен в два и в четыре раза.

Правильный способ считать два независимых итога это отдельные запросы или подзапросы:

```sql
SELECT
  (SELECT SUM(количество) FROM позиция_заказа WHERE код_книги = 134) AS заказано,
  (SELECT SUM(количество) FROM спецификация_поставки WHERE код_книги = 134) AS поставлено;
```

Третья ловушка это `NULL` в столбце соединения. `NULL` не равен `NULL`, поэтому строка с пустым внешним ключом не найдёт пару даже сама с собой. Во внутреннем соединении она исчезнет, в левом останется с пустыми столбцами справа.

Четвёртая ловушка это `NATURAL JOIN`. Он соединяет по всем столбцам с одинаковыми именами, и после добавления нового общего столбца условие незаметно меняется. В учебной схеме `NATURAL JOIN` между `книга` и `категория` вообще не даёт строк, потому что общий столбец `название` сравнивает название книги с названием категории. Явный `ON` читается дольше, но не меняет смысл при изменении схемы.

## Самосоединение и чтение трёх таблиц

Самосоединение нужно, когда строка ссылается на другую строку той же таблицы. У категории есть родитель, и родитель хранится в той же `категория`:

```sql
SELECT к.название AS категория, р.название AS родитель
FROM категория к
LEFT JOIN категория р ON р.код_категории = к.код_родителя
ORDER BY к.код_категории;
```

| `категория` | `родитель` |
|---|---|
| Художественная литература |  |
| Детская литература |  |
| Учебная литература |  |
| Справочная литература |  |
| Компьютерная литература |  |
| Деловая литература |  |
| Психология |  |
| История |  |
| Научно-популярная литература |  |
| Поэзия |  |
| Иностранная литература |  |
| Подарочные издания | Художественная литература |

Одна и та же таблица указана дважды с разными псевдонимами. Без псевдонимов база не поймёт, к какому экземпляру относится `название`. Категории верхнего уровня сохранились благодаря `LEFT JOIN`; внутреннее соединение оставило бы только «Подарочные издания».

Три таблицы читаются по одной строке результата. Возьмём позицию заказа 1001:

```sql
SELECT з.номер_заказа, к.название, п.количество, п.цена_коп
FROM позиция_заказа п
JOIN заказ з ON з.номер_заказа = п.номер_заказа
JOIN книга к ON к.код_книги = п.код_книги
WHERE з.номер_заказа = 1001
ORDER BY к.код_книги;
```

Результат описывает одну позицию: номер заказа, книгу, количество и цену. Каждое следующее соединение добавляло столбцы, но не меняло число строк, потому что и заказ, и книга имеют по одной подходящей записи.

Если после соединения число строк выросло, значит, одна из таблиц относится к предыдущей как один-ко-многим. Это нормально для позиций заказа и ненормально, если ожидалась одна строка на заказ. Тогда либо добавляют `DISTINCT`, либо переносят расчёт в подзапрос.

## Соединение или подзапрос

Соединение нужно, когда в результате требуются столбцы обеих таблиц. Если нужен только факт наличия связи, соединение часто оказывается лишним.

Задача «показать книги, которые хотя бы раз заказывали» решается соединением с `DISTINCT`:

```sql
SELECT DISTINCT к.код_книги, к.название
FROM книга к
JOIN позиция_заказа п ON п.код_книги = к.код_книги
ORDER BY к.код_книги
LIMIT 5;
```

`DISTINCT` скрывает размножение: книга, заказанная пять раз, появляется один раз. Но база сначала строит все пары, а потом убирает дубли. На больших объёмах это лишняя работа.

Тот же результат даёт `EXISTS`:

```sql
SELECT к.код_книги, к.название
FROM книга к
WHERE EXISTS (
  SELECT 1 FROM позиция_заказа п WHERE п.код_книги = к.код_книги
)
ORDER BY к.код_книги
LIMIT 5;
```

`EXISTS` проверяет, есть ли хотя бы одна подходящая строка, и останавливается на первой. Список столбцов внутри подзапроса не важен, поэтому `SELECT 1` здесь нормален. Дубли не появляются, `DISTINCT` не нужен.

Правило выбора простое. Если нужны столбцы из обеих таблиц, берут `JOIN`. Если нужен только признак «связь есть» или «связи нет», берут `EXISTS` или `NOT EXISTS`. Если нужен список значений для сравнения, подходит `IN`, но с `NULL` он требует осторожности.

Обратная задача «книги без заказов» через `NOT EXISTS` выглядит так:

```sql
SELECT к.код_книги, к.название
FROM книга к
WHERE NOT EXISTS (
  SELECT 1 FROM позиция_заказа п WHERE п.код_книги = к.код_книги
)
ORDER BY к.код_книги
LIMIT 5;
```

Запрос читается как «выбрать книгу, для которой не существует ни одной позиции заказа». Он не размножает строки и не требует `DISTINCT`. Левое соединение с `IS NULL` даёт тот же результат, но `NOT EXISTS` яснее выражает намерение.

`EXPLAIN QUERY PLAN` показывает, как база собирается выполнять соединение:

```sql
EXPLAIN QUERY PLAN
SELECT з.номер_заказа, к.название
FROM позиция_заказа п
JOIN заказ з ON з.номер_заказа = п.номер_заказа
JOIN книга к ON к.код_книги = п.код_книги
WHERE з.статус = 'оплачен';
```

В плане будут шаги `SCAN` и `SEARCH`. `SCAN` означает перебор таблицы, `SEARCH` поиск по индексу. Если для соединения нет индекса, SQLite может построить автоматический индекс на время запроса; на маленькой таблице это быстрее, чем создавать постоянный. На рабочей базе индексы по внешним ключам создают заранее.

## Проверка соединения

Перед сдачей отчёта проверяют число строк и отсутствие размножения. Начните с вопроса: сколько строк должно быть в результате. Для сводки по одному заказу это число позиций заказа, для списка книг это число книг, для отчёта по категориям это число категорий.

Затем сравните с фактическим результатом:

```sql
SELECT COUNT(*) FROM позиция_заказа WHERE номер_заказа = 1001;
SELECT COUNT(*) FROM позиция_заказа п
JOIN книга к ON к.код_книги = п.код_книги
WHERE п.номер_заказа = 1001;
```

Если числа совпали, соединение не размножило строки. Если второе больше, у книги несколько подходящих записей в правой таблице, и это нужно объяснить.

Проверьте, не потерялись ли строки:

```sql
SELECT COUNT(*) FROM книга;
SELECT COUNT(*) FROM книга к
LEFT JOIN позиция_заказа п ON п.код_книги = к.код_книги;
```

Левое соединение не должно вернуть меньше строк, чем левая таблица. Если вернуло, значит, в `WHERE` попало условие по правой таблице.

Наконец, посмотрите несколько строк результата и назовите вслух, что означает каждая пара. Если строка читается как «заказ такой-то, книга такая-то, количество такое-то», соединение собрано верно. Если в строке смешаны два независимых факта, скорее всего, соединены два списка один-ко-многим и суммы будут неверными.

## Типичные ошибки

- **Забыть `ON`.** Получается декартово произведение, и строк становится во много раз больше.
- **Условие по правой таблице в `WHERE`.** Левое соединение превращается во внутреннее, строки без пары исчезают.
- **Соединить два списка один-ко-многим и суммировать.** Каждая строка левой таблицы умножается на строки правой, итог завышается.
- **Сравнивать `NULL` через `=`.** Пустой внешний ключ не найдёт пару; для проверки используют `IS NULL`.
- **`NATURAL JOIN` в рабочем запросе.** Условие зависит от совпадения имён и меняется после `ALTER TABLE`.
- **Одинаковые имена столбцов без псевдонимов.** В результате два столбца `количество`, и непонятно, какой откуда.
- **Ожидать порядок от соединения.** Без `ORDER BY` порядок строк не гарантирован.
- **Считать, что `RIGHT` и `FULL` есть везде.** В SQLite до 3.39 их не было, в других СУБД синтаксис тоже отличается.

## Проверьте себя

> [!CHECK] Почему `SELECT COUNT(*) FROM книга к LEFT JOIN позиция_заказа п ON п.код_книги = к.код_книги` даёт 4846, а не 4800?
> Левое соединение сохраняет все 4800 книг, а для 139 заказанных книг добавляет по строке на каждую позицию заказа. Всего позиций 185, поэтому 4800 + 185 - 139 = 4846. Если нужна одна строка на книгу, считают `COUNT(DISTINCT к.код_книги)` или сначала агрегируют позиции.

> [!CHECK] В запросе с `LEFT JOIN` поставили `WHERE п.количество > 2`. Почему пропали книги без заказов?
> У таких книг все столбцы правой таблицы равны `NULL`, а `NULL > 2` даёт неизвестность. Условие в `WHERE` отбрасывает эти строки, и левое соединение ведёт себя как внутреннее. Условие по правой таблице переносят в `ON`.

> [!CHECK] Книга 134 имеет четыре заказа и две поставки. Почему сумма заказов после соединения стала 28 вместо 14?
> Соединение по коду книги составило все пары: четыре заказа на две поставки дают восемь строк. Каждая строка заказа повторилась дважды, поэтому `SUM` удвоил количество. Независимые итоги считают отдельными запросами или подзапросами.

## Итоги

- `JOIN` сопоставляет строки по условию `ON`; без условия получается декартово произведение.
- `INNER JOIN` оставляет только пары, `LEFT` и `RIGHT` сохраняют строки одной стороны, `FULL` обеих.
- Левое соединение с проверкой `IS NULL` находит строки без пары.
- Условие по правой таблице в `WHERE` превращает внешнее соединение во внутреннее.
- Два соединения один-ко-многим размножают строки и завышают суммы.
- Самосоединение использует два псевдонима одной таблицы, а результат трёх таблиц читают по одной строке.
- `RIGHT` и `FULL` появились в SQLite 3.39, старые версии требуют переписывания через `LEFT` и `UNION ALL`.
- `CROSS JOIN` строит все пары строк и в обычной выборке почти всегда означает забытое условие.
- Для проверки наличия связи `EXISTS` дешевле соединения с `DISTINCT`, а столбцы обеих таблиц требует именно `JOIN` с условием `ON` и проверкой числа строк.

::quiz
Q: Что делает JOIN?
+ Сопоставляет строки двух таблиц по условию
- Копирует одну таблицу в другую
- Удаляет дубли из таблицы
- Создаёт внешний ключ
! JOIN формирует результат из пар строк, удовлетворяющих условию.

Q: Что получится, если выполнить JOIN без условия ON?
+ Декартово произведение строк
- Пустой результат
- Одна строка
- Ошибка синтаксиса
! Без условия каждая строка соединяется с каждой.

Q: Чем INNER JOIN отличается от LEFT JOIN?
+ LEFT JOIN сохраняет все строки левой таблицы
- INNER JOIN сохраняет все строки правой таблицы
- LEFT JOIN удаляет левую таблицу
- Между ними нет разницы
! LEFT JOIN добавляет строки без пары с NULL справа.

Q: Что стоит на месте отсутствующих столбцов правой таблицы при LEFT JOIN?
+ NULL
- Ноль
- Пустая строка
- Значение из первой строки
! Не найденная пара даёт NULL во всех столбцах правой таблицы.

Q: Как найти книги, которые ни разу не заказывали?
+ LEFT JOIN и WHERE правая таблица IS NULL
- INNER JOIN и WHERE
- CROSS JOIN
- RIGHT JOIN без условия
! Антисоединение оставляет строки без пары.

Q: Что делает RIGHT JOIN?
+ Сохраняет все строки правой таблицы
- Сохраняет все строки левой таблицы
- Удаляет правую таблицу
- Сортирует результат
! RIGHT JOIN противоположен LEFT JOIN по сохраняемой стороне.

Q: В какой версии SQLite появились RIGHT и FULL JOIN?
+ 3.39
- 3.20
- 3.35
- 3.50
! До 3.39 их заменяли переписыванием через LEFT JOIN.

Q: Почему условие по правой таблице в WHERE ломает LEFT JOIN?
+ Строки с NULL не проходят условие
- SQLite запрещает WHERE после JOIN
- Условие удаляет левую таблицу
- JOIN выполняется после WHERE
! NULL в сравнении даёт неизвестность, и строка отбрасывается.

Q: Что происходит при соединении двух списков один-ко-многим?
+ Число строк размножается
- Число строк всегда уменьшается
- Строки автоматически суммируются
- JOIN удаляет дубли
! Каждая строка одной стороны соединяется с несколькими строками другой.

Q: Какие виды соединений сохраняют строки без пары?
+ LEFT JOIN
+ RIGHT JOIN
+ FULL JOIN
+ LEFT JOIN с IS NULL
- INNER JOIN
- CROSS JOIN
! Внешние соединения сохраняют одну или обе стороны.

Q: Что нужно для соединения трёх таблиц?
+ Условие ON для каждой пары
+ Псевдонимы для различения таблиц
+ Понимание, какая связь один-ко-многим
+ Проверка числа строк после соединения
- Отказ от WHERE
- Обязательный CROSS JOIN
! Каждое соединение добавляет столбцы и может менять число строк.

Q: Какие ошибки встречаются при JOIN?

- Явный список столбцов

- Сколько столбцов в результате
