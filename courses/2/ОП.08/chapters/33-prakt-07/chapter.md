## Краткие теоретические сведения

Индекс это отдельная структура, в которой значения одного или нескольких столбцов упорядочены вместе со ссылками на строки таблицы. Чаще всего это B-дерево: сбалансированное дерево, где каждый узел хранит отсортированные ключи, а листья содержат ссылки на строки. Поиск по дереву спускается от корня к листу и делает число шагов, сравнимое с логарифмом от числа строк. Для 4800 строк это три-четыре шага вместо просмотра всех строк подряд.

План запроса показывает, как СУБД собирается выполнить запрос. Команда `EXPLAIN QUERY PLAN` печатает строки вида `SCAN book` или `SEARCH book USING INDEX idx_book_title (title=?)`. `SCAN` означает полный просмотр таблицы, `SEARCH` означает поиск по индексу. Если в плане появился `SEARCH` с именем вашего индекса, индекс используется. Если остался `SCAN`, индекс не подошёл: возможно, условие написано так, что применить его нельзя, например функция над столбцом.

Индекс ускоряет чтение и замедляет запись. При каждой вставке, обновлении и удалении строки СУБД обновляет все индексы таблицы. Три индекса означают три дополнительные структуры, которые нужно поправить. Индекс занимает место на диске и в памяти. Поэтому индекс ставят под конкретный запрос, а не «на всякий случай» на каждый столбец.

Индекс полезен, когда условие отбирает малую долю строк и когда столбец часто используется в соединении или сортировке. Индекс почти бесполезен на столбце с двумя значениями: половина строк всё равно подходит, и просмотр таблицы окажется не медленнее. На маленькой таблице из десятка строк индекс тоже не нужен: накладные расходы больше выигрыша.

Долю строк, которую отбирает условие, называют селективностью. Чем меньше строк подходит, тем полезнее индекс. Номер заказа или номер книги это хороший ключ поиска: подходящих строк единицы. Статус заказа или название площадки это плохой ключ: подходящих строк тысячи, и СУБД дешевле просмотреть таблицу целиком, чем читать индекс и потом обращаться к строкам.

Индекс может покрывать запрос. Если все столбцы, которые нужны запросу, уже лежат в индексе, СУБД читает только индекс и не обращается к таблице. В плане это выглядит как `USING COVERING INDEX`. Покрывающий индекс особенно полезен для отчётов, которые считают суммы по одному столбцу: дерево меньше таблицы, и чтение идёт быстрее.

Составной индекс строится по нескольким столбцам сразу, и порядок столбцов в нём важен. Индекс по паре `(category_id, title)` помогает запросу, который фильтрует по категории и сортирует по названию. Тот же индекс не поможет запросу, который фильтрует только по названию: поиск в дереве начинается с первого столбца. Поэтому индекс подбирают под конкретный запрос, а не под таблицу.

Транзакция это группа команд, которая выполняется как одно целое. Она начинается командой `BEGIN`, подтверждается командой `COMMIT` и отменяется командой `ROLLBACK`. Если между началом и подтверждением произошёл сбой, СУБД отменяет незавершённые изменения. Свойства транзакции описывают словом ACID: атомарность, согласованность, изолированность и долговечность. Для практики достаточно атомарности: либо все команды выполнены, либо ни одна.

В SQLite транзакция блокирует запись для других соединений. Пока один пользователь не выполнил `COMMIT` или `ROLLBACK`, второй писатель ждёт. Читатели при этом обычно продолжают работать. Это ещё одна причина держать транзакцию короткой: длинная транзакция останавливает оформление заказов на всей площадке.

Права в серверной СУБД выдают командой `GRANT` и отзывают командой `REVOKE`. Право привязано к объекту: таблице, столбцу или базе. Роль это именованный набор прав, который выдают пользователю. Принцип минимальных прав требует выдать ровно те операции, без которых работа не выполняется, и ни одной лишней.

SQLite не поддерживает учётные записи базы и команду `GRANT`, поэтому в учебной базе права проверяют иначе. Первый уровень это режим соединения `PRAGMA query_only = ON`, который запрещает запись. Второй уровень это представление, которое показывает только часть столбцов. Третий уровень это триггер, который отменяет операцию через `RAISE(ABORT, ...)`. Настоящая граница в SQLite проходит по файлу базы: кто открыл файл на запись, тот может изменить всё.

Время запроса измеряют несколько раз и берут наименьшее или медиану. Один замер ничего не значит: браузер в этот момент может быть занят другой вкладкой. На небольших таблицах разница во времени мала, поэтому главным доказательством остаётся план запроса, а время служит дополнением. Перед замерами закройте лишние вкладки и не запускайте тяжёлые запросы параллельно.

В sqliteonline время выполнения показывается в окне сообщений под редактором. Оно округлено до миллисекунд, поэтому значение 0 не означает «мгновенно», оно означает «меньше миллисекунды». Для отчёта так и пишите: меньше 1 мс, а не ноль.

## Ход работы

### Шаг 1. Соберите учебную базу

Выполните подготовительный скрипт. Он создаёт справочники, каталог, остатки, заказы и журнал движений товара. Объём журнала около 200 000 строк за год, это пример объёма, а не точное число из учёта магазина.

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE category (
  category_id INTEGER PRIMARY KEY,
  name        TEXT NOT NULL UNIQUE
);
INSERT INTO category (category_id, name) VALUES
 (1,'Современная проза'),(2,'Классика'),(3,'Фантастика'),
 (4,'Детективы'),(5,'Детские книги'),(6,'Учебники'),
 (7,'Научная литература'),(8,'Психология'),(9,'Бизнес'),
 (10,'Кулинария'),(11,'Искусство'),(12,'Путеводители');

CREATE TABLE site (
  site_id INTEGER PRIMARY KEY,
  name    TEXT NOT NULL UNIQUE
);
INSERT INTO site (site_id, name) VALUES (1,'Москва'),(2,'Тверь'),(3,'Тула'),(4,'Калуга');

CREATE TABLE book (
  book_id     INTEGER PRIMARY KEY,
  title       TEXT NOT NULL,
  category_id INTEGER NOT NULL REFERENCES category(category_id),
  price       REAL NOT NULL CHECK (price > 0)
);

WITH RECURSIVE n(i) AS (SELECT 1 UNION ALL SELECT i + 1 FROM n WHERE i < 4800)
INSERT INTO book (book_id, title, category_id, price)
SELECT i, 'Книга ' || printf('%04d', i), (i % 12) + 1, 250 + (i % 40) * 25 FROM n;

CREATE TABLE stock (
  site_id INTEGER NOT NULL REFERENCES site(site_id),
  book_id INTEGER NOT NULL REFERENCES book(book_id),
  qty     INTEGER NOT NULL DEFAULT 0 CHECK (qty >= 0),
  PRIMARY KEY (site_id, book_id)
);
INSERT INTO stock (site_id, book_id, qty)
SELECT s.site_id, b.book_id, 5 + (b.book_id % 7)
FROM site s CROSS JOIN book b WHERE b.book_id <= 100;

CREATE TABLE orders (
  order_id    INTEGER PRIMARY KEY,
  customer_id INTEGER NOT NULL,
  site_id     INTEGER NOT NULL REFERENCES site(site_id),
  order_date  TEXT NOT NULL,
  status      TEXT NOT NULL DEFAULT 'новый'
              CHECK (status IN ('новый','оплачен','отменён'))
);
WITH RECURSIVE n(i) AS (SELECT 1 UNION ALL SELECT i + 1 FROM n WHERE i < 20)
INSERT INTO orders (order_id, customer_id, site_id, order_date, status)
SELECT i, 500 + i, (i % 4) + 1, date('2026-03-01', '+' || (i % 30) || ' days'), 'оплачен' FROM n;

CREATE TABLE order_line (
  order_id INTEGER NOT NULL REFERENCES orders(order_id),
  book_id  INTEGER NOT NULL REFERENCES book(book_id),
  qty      INTEGER NOT NULL CHECK (qty > 0),
  price    REAL NOT NULL CHECK (price > 0),
  PRIMARY KEY (order_id, book_id)
);
INSERT INTO order_line (order_id, book_id, qty, price)
SELECT o.order_id, b.book_id, 1 + (o.order_id % 3), b.price
FROM orders o JOIN book b ON b.book_id BETWEEN o.order_id AND o.order_id + 2;

CREATE TABLE stock_movement (
  movement_id INTEGER PRIMARY KEY,
  site_id     INTEGER NOT NULL,
  book_id     INTEGER NOT NULL,
  qty         INTEGER NOT NULL,
  moved_at    TEXT NOT NULL
);
WITH RECURSIVE n(i) AS (SELECT 1 UNION ALL SELECT i + 1 FROM n WHERE i < 200000)
INSERT INTO stock_movement (movement_id, site_id, book_id, qty, moved_at)
SELECT i, (i % 4) + 1, (i % 4800) + 1, (i % 3) + 1,
       date('2026-01-01', '+' || (i % 365) || ' days') FROM n;
```

Проверьте число строк в каждой таблице и запишите его в отчёт. Конструкция `WITH RECURSIVE` строит последовательность чисел и работает как генератор строк: она нужна, чтобы не вводить тысячи строк вручную.

### Шаг 3. Создайте индекс и сравните план и время

|---|---|---|---|---|---|

Если время не изменилось, а план изменился, не считайте опыт неудачным. На таблице в несколько тысяч строк выигрыш может быть меньше точности измерения в браузере. План остаётся доказательством того, что индекс применяется.

### Шаг 4. Проверьте цену индекса при вставке

Индекс ускоряет чтение, но каждая вставка обновляет и его. Сравните две таблицы: одну без индексов, вторую с тремя индексами.

| Таблица | Число строк | Индексы | Время вставки | Вывод |
|---|---|---|---|---|
| `book_plain` | 20 000 | нет |  |  |
| `book_indexed` | 20 000 | три |  |  |

Вывод делайте по запросам, а не по числу индексов. Индекс на `title` нужен для поиска книги по названию, индекс на `category_id` нужен для отчётов по категориям. ### Шаг 5. Проведите транзакцию с откатом

Кладовщик перевозит три экземпляра книги с площадки в Москве на площадку в Туле. Операция состоит из двух обновлений, и между ними может произойти сбой.

```sql
SELECT site_id, qty FROM stock WHERE book_id = 50 ORDER BY site_id;

BEGIN;
UPDATE stock SET qty = qty - 3 WHERE site_id = 1 AND book_id = 50;
UPDATE stock SET qty = qty + 3 WHERE site_id = 3 AND book_id = 50;

SELECT site_id, qty FROM stock WHERE book_id = 50 ORDER BY site_id;

ROLLBACK;

SELECT site_id, qty FROM stock WHERE book_id = 50 ORDER BY site_id;
```

Запишите три результата: до транзакции, внутри транзакции и после отката. Первый и третий обязаны совпасть. Это и есть доказательство атомарности: база не осталась в состоянии, где товар списан, но не зачислен.

Если SQLite сообщает `cannot start a transaction within a transaction`, значит, предыдущая транзакция не закрыта. Выполните `ROLLBACK` и начните заново. Незакрытая транзакция держит блокировку записи и мешает другим соединениям.

### Шаг 6. Повторите транзакцию с подтверждением

Теперь выполните ту же операцию с `COMMIT`.

```sql
BEGIN;
UPDATE stock SET qty = qty - 3 WHERE site_id = 1 AND book_id = 50;
UPDATE stock SET qty = qty + 3 WHERE site_id = 3 AND book_id = 50;
COMMIT;

SELECT site_id, qty FROM stock WHERE book_id = 50 ORDER BY site_id;
```

Сравните с результатом шага 5. В Москве стало на три меньше, в Туле на три больше, сумма по площадкам не изменилась. Проверьте это отдельным запросом с `SUM(qty)` по книге 50.

Отдельно проверьте, что транзакция не спасает от логической ошибки. Выполните `BEGIN`, затем `UPDATE stock SET qty = qty - 1000 WHERE site_id = 2 AND book_id = 50` и посмотрите на результат. Ограничение `CHECK (qty >= 0)` отклонит команду, и транзакцию нужно завершить откатом. Запишите, что произошло.

Напишите скрипт выдачи прав для серверной СУБД. За основу возьмите синтаксис MySQL 8 и создайте три роли, кроме администратора. Скрипт сохраните отдельным файлом и приложите к отчёту.

Не выполняйте этот скрипт в SQLite: он завершится синтаксической ошибкой, потому что учётных записей базы там нет. В отчёте укажите эту причину и объясните, где скрипт будет работать.

### Шаг 8. Ограничьте запись в SQLite и проверьте отказ

Проверьте три уровня ограничения, доступные в SQLite. Первый уровень это режим соединения. Включите режим отдельным запуском, затем попробуйте запись, а после неё выключите режим ещё одним запуском: если клиент останавливает пакет на ошибке, команда выключения не выполнится.

```sql
PRAGMA query_only = ON;
UPDATE book SET price = 1 WHERE book_id = 1;
PRAGMA query_only = OFF;
```

Запишите текст отказа. Второй уровень это представление, которое скрывает лишние столбцы.

```sql
CREATE VIEW v_book_seller AS
SELECT book_id, title, price FROM book;

SELECT * FROM v_book_seller LIMIT 3;
```

Третий уровень это триггер, который запрещает удаление заказов.

```sql
CREATE TRIGGER orders_no_delete
BEFORE DELETE ON orders
BEGIN
  SELECT RAISE(ABORT, 'удаление заказов запрещено');
END;

DELETE FROM orders WHERE order_id = 1;
```

Заполните таблицу проверок. В последнем столбце объясните, от чего защищает именно этот уровень и чего он не защищает.

| Проверка | Команда | Текст отказа | Что доказано |
|---|---|---|---|
| Запись в режиме только для чтения | `UPDATE book ...` |  |  |
| Удаление заказа | `DELETE FROM orders ...` |  |  |
| Чтение через представление | `SELECT * FROM v_book_seller` |  |  |

Три уровня отличаются силой. `query_only` защищает от случайной записи в текущем соединении, но другое соединение с тем же файлом продолжит писать. Представление скрывает столбцы от того, кто работает через него, но не запрещает обратиться к исходной таблице. Триггер отменяет конкретную операцию и переживает перезапуск, но его может удалить тот, у кого есть право менять структуру. Вместе они закрывают типовые ошибки приложения, а настоящую границу даёт серверная СУБД с `GRANT`.
