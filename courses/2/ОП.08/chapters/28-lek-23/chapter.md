## Поиск по оглавлению

В каталоге «Страницы» 4800 книг. Продавец ищет «SQL за 30 дней». Без индекса база читает первую строку таблицы, сравнивает название, переходит ко второй и так до конца. В худшем случае она просмотрит все 4800 строк, даже если нужная книга стоит последней. Такой способ называют полным просмотром, или сканированием таблицы.

На бумажной книге у этой задачи есть готовое решение: оглавление. Оно не содержит весь текст, но содержит названия глав и номера страниц, расположенные по порядку. Чтобы найти главу, не нужно листать всю книгу: достаточно открыть оглавление и перейти по номеру.

**Индекс это отдельная структура, которая хранит значения выбранного столбца в отсортированном виде и ссылки на строки таблицы.** База ищет значение в индексе, получает ссылку и читает нужную строку. Чем больше таблица, тем заметнее выигрыш.

Проверим на учебном наборе из 4800 книг. Запрос `SELECT id, title FROM books WHERE title = 'Книга номер 3187'` без индекса выполняется примерно 0,15 мс. После создания индекса по `title` тот же запрос занимает около 0,002 мс. Числа зависят от компьютера и настроек, важнее отношение: поиск перестал зависеть от размера таблицы.

На тестовой таблице позиций заказов из 120 000 строк разница ещё заметнее. Сумма по одной книге без индекса занимает около 2,6 мс, с индексом около 0,01 мс. При одном запросе это незаметно. В отчёте, который выполняется для каждой из 4800 книг, разница превращается в минуты.

Индекс не является копией таблицы. Он содержит только ключ поиска и ссылку на строку. Если индекс построен по названию, в нём нет цены, года и издательства. Чтобы получить остальные столбцы, база обращается к таблице. Исключение составляют покрывающие индексы, о них ниже.

## Что именно создаёт индекс

Команда создания выглядит просто.

```sql
CREATE INDEX idx_books_title ON books(title);
```

После выполнения в базе появляется объект `idx_books_title`. Он поддерживается автоматически: при вставке, обновлении и удалении строки база обновляет и таблицу, и все её индексы. Программисту не нужно ничего делать вручную, но и отменить эту работу для отдельной операции нельзя.

У индекса есть имя, таблица, список столбцов и порядок сортировки. По умолчанию сортировка возрастающая. Для поиска это обычно не важно, но для запросов с `ORDER BY` направление может иметь значение.

```sql
CREATE INDEX idx_books_title_desc ON books(title DESC);
```

Индекс может быть уникальным. Тогда база не позволит вставить две строки с одинаковым значением ключа. Об этом отдельный раздел.

| Что хранит индекс | Что не хранит |
|---|---|
| значение ключевого столбца | остальные столбцы таблицы |
| ссылку на строку (в SQLite rowid) | текст запроса, который его использует |
| служебные узлы дерева | копию всей таблицы |

Индекс занимает место на диске. Для небольшой таблицы это килобайты, для таблицы на миллионы строк это гигабайты. Поэтому индексы создают под конкретные запросы, а не «на всякий случай» для каждого столбца.

В SQLite индекс автоматически создаётся для первичного ключа и для ограничения `UNIQUE`. Если объявлен составной первичный ключ, автоматический индекс строится по всем его столбцам в указанном порядке. Эти индексы видны в `sqlite_master` и в плане запроса под именами вида `sqlite_autoindex_...`.

## Как устроено B-дерево

В SQLite и большинстве реляционных СУБД обычный индекс построен как B-дерево. Это сбалансированное дерево, в котором все листья находятся на одной глубине. Внутренние узлы хранят разделительные ключи, листья содержат ключи и ссылки на строки.

Представим индекс по названию книги. В корневом узле записаны несколько названий, которые делят алфавит на диапазоны. База сравнивает искомое название с разделителем и уходит в нужную ветвь. На следующем уровне диапазон сужается ещё раз. Через три или четыре шага она попадает в лист с нужным значением.

| Уровень | Что происходит | Сколько вариантов остаётся |
|---|---|---|
| корень | сравнение с разделителями | примерно 1 из 200 |
| средний узел | сужение диапазона | примерно 1 из 40000 |
| лист | точное значение и ссылка | одна строка |

Числа условные и зависят от размера страницы и длины ключа. Смысл в том, что глубина растёт логарифмически. Для миллиона строк обычно достаточно трёх-четырёх уровней. Поэтому время поиска по индексу почти не меняется при росте таблицы с тысячи до миллиона строк, если не растёт глубина дерева.

B-дерево поддерживает не только точное равенство, но и диапазоны. Запрос `WHERE title BETWEEN 'А' AND 'К'` находит начальную точку диапазона и читает листья по порядку до конечной. Сортировка `ORDER BY title` тоже может использовать индекс: листья уже лежат в нужном порядке, и базе не нужно строить временную сортировку.

Если индекса для сортировки нет, план содержит строку `USE TEMP B-TREE FOR ORDER BY`. Это означает, что база сначала прочитала строки, а затем построила временную структуру для их упорядочивания. На маленькой таблице такая сортировка незаметна, на большой она требует памяти и времени. Индекс по столбцу сортировки убирает этот шаг, если порядок строк в индексе совпадает с порядком в `ORDER BY`.

Листья индекса связаны между собой. Это позволяет читать диапазон последовательно, не возвращаясь каждый раз к корню. Именно поэтому индекс хорошо работает для `BETWEEN`, `>`, `<` и для сортировки, а не только для `=`.

Есть важное ограничение. Индекс хранит ключ и ссылку, но не сами строки. Если запросу нужны столбцы, которых нет в ключе, база для каждой найденной строки обращается к таблице. При большом числе совпадений это может быть медленнее, чем один последовательный просмотр. Планировщик учитывает это и иногда отказывается от индекса.

## План запроса

Прежде чем создавать индекс, полезно посмотреть, как база собирается выполнять запрос. В SQLite для этого есть `EXPLAIN QUERY PLAN`.

```sql
EXPLAIN QUERY PLAN
SELECT id, title
FROM books
WHERE title = 'SQL за 30 дней';
```

До создания индекса план содержит одну строку.

```text
SCAN books
```

`SCAN` означает последовательный просмотр таблицы. После создания индекса план меняется.

```sql
DROP INDEX IF EXISTS idx_books_title;
CREATE INDEX idx_books_title ON books(title);

EXPLAIN QUERY PLAN
SELECT id, title
FROM books
WHERE title = 'SQL за 30 дней';
```

```text
SEARCH books USING COVERING INDEX idx_books_title (title=?)
```

`SEARCH` означает поиск по индексу. `COVERING INDEX` говорит, что все нужные запросу столбцы (`id` и `title`) есть в индексе, поэтому обращаться к таблице не нужно. В SQLite индекс по `title` автоматически содержит `rowid`, а `id` в этой таблице является псевдонимом `rowid`. Поэтому индекс оказался покрывающим.

Если запросить столбец, которого в индексе нет, план изменится.

```sql
EXPLAIN QUERY PLAN
SELECT title, price
FROM books
WHERE title = 'SQL за 30 дней';
```

```text
SEARCH books USING INDEX idx_books_title (title=?)
```

Появилось `USING INDEX` без слова `COVERING`. База найдёт строку по индексу, а затем обратится к таблице за ценой. Это нормально: одно обращение по ссылке дешевле, чем чтение всей таблицы.

План это не обещание, а решение планировщика на текущих данных. Он оценивает число строк, стоимость чтения и наличие индексов. Оценки берутся из статистики, которую собирает команда `ANALYZE`. Без статистики планировщик может ошибиться, особенно на таблицах со сложным распределением значений.

```sql
ANALYZE;
SELECT tbl, idx, stat
FROM sqlite_stat1
WHERE tbl = 'orders';
```

Для составного индекса по `store_id, order_date` статистика выглядит как `20 5 1`: всего 20 строк, 5 различных значений `store_id`, 1 различная пара. Эти числа помогают планировщику понять, насколько условие избирательно.

План нужно проверять после каждого изменения: добавили индекс, изменили запрос, выросли данные. То, что работало на 20 строках, может перестать работать на миллионе.

Посмотреть, какие индексы уже есть у таблицы, можно командами `PRAGMA index_list` и `PRAGMA index_info`.

```sql
PRAGMA index_list('orders');
PRAGMA index_info('idx_orders_store_date');
```

Первая команда показывает имя, уникальность и происхождение каждого индекса. Вторая перечисляет столбцы в порядке ключа. Это быстрее, чем искать определение в `sqlite_master`, и помогает заметить дубли: два индекса с одинаковым набором столбцов почти всегда лишние.

Не путайте `EXPLAIN QUERY PLAN` и `EXPLAIN`. Первая команда показывает шаги выполнения человеческим языком: `SCAN`, `SEARCH`, `USE TEMP B-TREE FOR ORDER BY`. Вторая выдаёт низкоуровневые инструкции виртуальной машины SQLite, в которых легко утонуть. Для выбора индекса достаточно `EXPLAIN QUERY PLAN`.

## Когда индекс работает

Индекс ускоряет поиск, когда условие позволяет сузить диапазон. Проще всего это видно по типу условия.

| Условие | Использует индекс | Причина |
|---|---|---|
| `title = 'SQL за 30 дней'` | да | точное значение |
| `title BETWEEN 'А' AND 'К'` | да | диапазон |
| `title GLOB 'SQL*'` | да, в SQLite | поиск по префиксу |
| `title LIKE '%SQL%'` | нет | образец начинается с шаблона |
| `LOWER(title) = 'sql за 30 дней'` | нет | функция скрывает столбец |
| `price + 100 > 1000` | нет | выражение скрывает столбец |
| `store_id = 1 OR order_date = '2026-09-02'` | обычно нет | два разных условия |

Причина запрета на функцию и выражение одна: индекс построен по значению столбца, а не по результату `LOWER(title)`. Чтобы найти по функции, базе пришлось бы вычислить её для каждой строки. В некоторых СУБД можно создать индекс по выражению, и тогда запрос с этой же функцией сможет им воспользоваться. В SQLite выражение в индексе тоже поддерживается.

```sql
CREATE INDEX idx_books_title_lower ON books(LOWER(title));
```

Такой индекс поможет запросу `WHERE LOWER(title) = 'sql за 30 дней'`, но не запросу `WHERE title = 'SQL за 30 дней'`. Индекс и условие должны совпадать по выражению.

С `LIKE` есть тонкость. В SQLite `LIKE` по умолчанию не учитывает регистр, поэтому индекс с обычным сравнением не подходит. `GLOB` учитывает регистр и может использовать индекс для префикса. Если нужен именно `LIKE`, создают индекс с подходящей сортировкой или включают настройку `PRAGMA case_sensitive_like = ON`. В MySQL и PostgreSQL поведение зависит от collation. Поэтому утверждение «индекс ускоряет LIKE» верно только для шаблона, который начинается с известного префикса.

Соединение таблиц тоже выигрывает от индекса. Если запрос соединяет заказы и позиции по `order_items.order_id`, индексу по этому столбцу есть что делать: для каждого заказа база быстро находит его позиции. Без индекса она будет просматривать всю таблицу позиций для каждого заказа.

```sql
EXPLAIN QUERY PLAN
SELECT o.id, i.book_id
FROM orders o
JOIN order_items i ON i.order_id = o.id
WHERE o.customer_id = 5;
```

```text
SCAN o
SEARCH i USING COVERING INDEX sqlite_autoindex_order_items_1 (order_id=?)
```

Автоматический индекс составного первичного ключа `(order_id, book_id)` уже покрывает условие по `order_id`. Поэтому отдельный индекс по `order_id` здесь не нужен: он будет дублировать существующий.

## Составной индекс и левый префикс

Индекс может строиться по нескольким столбцам.

```sql
CREATE INDEX idx_orders_store_date ON orders(store_id, order_date);
```

Порядок столбцов в определении важен. Индекс сначала сортирует строки по `store_id`, а внутри одинаковых `store_id` по `order_date`. Поэтому он помогает запросу, который фильтрует по `store_id`, и запросу, который фильтрует по обоим столбцам. Запросу только по `order_date` он помогает гораздо меньше.

Проверим на планах.

```sql
EXPLAIN QUERY PLAN
SELECT id FROM orders WHERE store_id = 1;
```

```text
SEARCH orders USING COVERING INDEX idx_orders_store_date (store_id=?)
```

```sql
EXPLAIN QUERY PLAN
SELECT id FROM orders WHERE order_date = '2026-09-02';
```

```text
SCAN orders USING COVERING INDEX idx_orders_store_date
```

Во втором случае база читает весь индекс, потому что начало ключа ей неизвестно. Это не полный просмотр таблицы, а просмотр индекса, но выигрыша от сортировки по `order_date` нет.

```sql
EXPLAIN QUERY PLAN
SELECT id FROM orders
WHERE store_id = 1 AND order_date = '2026-09-02';
```

```text
SEARCH orders USING COVERING INDEX idx_orders_store_date (store_id=? AND order_date=?)
```

Оба условия использованы. Это и есть правило левого префикса: индекс работает по непрерывной начальной части своего ключа. Если ключ `(A, B, C)`, то запросы по `A`, по `A и B`, по `A, B и C` используют индекс, а запрос только по `B` или только по `C` не использует.

Правило не означает, что столбцы нужно ставить в порядке убывания важности. Порядок выбирают по запросам. Если чаще всего ищут по площадке и дате, ключ `(store_id, order_date)` подходит. Если чаще ищут по дате и площадке, а площадка почти всегда указана, тот же ключ всё равно работает, потому что оба столбца есть в условии. Если же частый запрос фильтрует только по дате, нужен отдельный индекс по `order_date`.

Есть ещё покрывающий индекс. Если все столбцы запроса входят в индекс, база не обращается к таблице. Например, индекс `(store_id, order_date)` покрывает запрос `SELECT store_id, order_date FROM orders WHERE store_id = 1`. Это экономит чтение, но увеличивает размер индекса. Покрывающий индекс оправдан для частого отчёта, а не для каждого запроса.

## Уникальный индекс

Уникальный индекс запрещает повторение ключа.

```sql
CREATE UNIQUE INDEX idx_customers_email ON customers(email);
```

После этого вставка второго клиента с тем же адресом электронной почты завершится ошибкой.

```text
UNIQUE constraint failed: customers.email
```

Уникальность это бизнес-правило, а не только скорость поиска. Если два клиента не могут иметь один адрес, правило должно жить в базе, а не в приложении. Приложение можно обойти, ручной скрипт тоже, а ограничение базы действует всегда.

В SQLite уникальный индекс допускает несколько значений `NULL`. `NULL` означает «значение неизвестно», и два неизвестных значения не считаются равными. Поэтому два клиента без email могут существовать, а два клиента с одинаковым реальным адресом нет. Это поведение отличается от `NOT NULL`, которое запрещает пустое значение вообще.

| Ограничение | Что запрещает | Несколько NULL |
|---|---|---|
| `PRIMARY KEY` | повтор ключа и обычно NULL | зависит от СУБД |
| `UNIQUE` | повтор значения | разрешены в SQLite |
| `NOT NULL` | отсутствие значения | не применимо |
| `CHECK` | значение по условию | зависит от условия |

Первичный ключ в SQLite тоже создаёт уникальный индекс. Для целочисленного первичного ключа это псевдоним `rowid`, и отдельный индекс может не создаваться. Для составного или текстового ключа индекс строится.

## Цена индекса

Индекс ускоряет чтение, но замедляет запись. Каждая вставка строки требует вставить ключ в каждое дерево индекса. Обновление ключевого столбца требует удалить старый ключ и вставить новый. Удаление строки требует удалить ключи из всех индексов.

Замер на 50 000 строках позиций заказа: без индексов вставка занимает около 32 мс, с двумя индексами около 70 мс. Разница более чем в два раза. На одной строке это микросекунды, на массовом импорте это секунды и минуты.

| Операция | Без индекса | С двумя индексами |
|---|---|---|
| вставка 50 000 строк | около 32 мс | около 70 мс |
| поиск по книге | просмотр 50 000 строк | поиск по дереву |
| обновление названия | обновление строки | плюс обновление индекса |

Числа получены на учебном наборе в памяти и приведены как пример. На реальном диске абсолютные значения будут другими, но направление сохранится: индексы увеличивают стоимость записи.

Есть и менее очевидная цена. Планировщик может выбрать неправильный индекс и сделать запрос медленнее, чем без индекса. Чем больше индексов, тем больше вариантов ему нужно оценить. Обычно это не проблема, но на сложных запросах с десятком индексов план может удивить.

Индекс занимает диск и память. Чем больше ключей и чем длиннее текст, тем больше размер. Индекс по названию книги на 4800 строк небольшой, индекс по описанию на миллион строк может весить больше самой таблицы. Поэтому индексируют то, по чему действительно ищут, а не всё подряд.

При массовой загрузке данных иногда сначала загружают строки, а потом создают индексы. Так быстрее, потому что дерево строится один раз, а не обновляется на каждой вставке. Но это допустимо только в окно загрузки, когда таблица не используется. В обычной работе индексы должны существовать постоянно.

## Как выбрать индекс

Выбор начинается не со столбца, а с запроса. Сначала выписывают запросы, которые выполняются часто и занимают заметное время. Для каждого смотрят план и ищут шаги `SCAN` по большой таблице.

Дальше оценивают избирательность. Избирательность показывает, какую долю строк оставляет условие. Если столбец `status` имеет пять значений, условие `status = 'выдан'` оставит примерно пятую часть таблицы. Индекс по такому столбцу редко помогает: базе проще прочитать всю таблицу, чем прыгать по индексу и возвращаться к строкам. Если столбец `email` почти уникален, условие оставит одну строку, и индекс будет очень полезен.

| Столбец | Различных значений | Избирательность | Польза индекса |
|---|---|---|---|
| email клиента | почти столько же, сколько строк | высокая | большая |
| номер заказа | равен числу заказов | высокая | большая |
| дата заказа | сотни | средняя | для диапазона |
| status | 5 | низкая | небольшая |
| пол | 2 | очень низкая | почти нет |

Для составного индекса порядок столбцов выбирают по условиям. Сначала ставят столбец, который используется в равенстве и имеет высокую избирательность, затем столбец диапазона или сортировки. Например, для запроса `WHERE store_id = 1 AND order_date BETWEEN ... ORDER BY order_date` подходит `(store_id, order_date)`: площадка сужает диапазон, дата задаёт порядок.

Полезно проверить индекс до и после. Записывают время выполнения, план и число строк. Если план не изменился, индекс, скорее всего, не нужен. Если изменился, но время выросло, возможно, индекс не подходит или статистика устарела. После изменений выполняют `ANALYZE`.

В SQLite есть частичные индексы. Они строятся не по всем строкам, а по условию.

```sql
CREATE INDEX idx_orders_new ON orders(order_date)
WHERE status = 'новый';
```

Такой индекс меньше и обслуживается только для новых заказов. Запрос должен содержать то же условие `WHERE status = 'новый'`, иначе индекс не применится. Частичный индекс хорош, когда интересна небольшая часть таблицы.

Есть индексы по выражению, например `LOWER(email)`. Они помогают запросам, которые сравнивают именно это выражение. Обычный индекс по `email` для такого запроса бесполезен.

Наконец, индексы нужно удалять. Если запрос исчез или индекс дублирует другой, его удаляют командой `DROP INDEX`. Лишний индекс замедляет запись и занимает место, не принося пользы. Периодическая ревизия индексов так же важна, как их создание. Практический приём: выписать все индексы таблицы, рядом указать запросы, которые их используют, и удалить те, для которых запроса не нашлось.

## Типичные ошибки

**Индекс по столбцу с малым числом значений.** Индекс по `status` или `city` на большой таблице часто не используется. База решает, что проще просканировать таблицу. Исключение составляют случаи, когда одно значение встречается очень редко.

**Неверный порядок столбцов в составном индексе.** Индекс `(order_date, store_id)` не поможет запросу только по `store_id`, а `(store_id, order_date)` поможет. Порядок определяется запросами, а не привычкой.

**Функция вокруг столбца.** `WHERE LOWER(title) = ...` отключает обычный индекс по `title`. Нужен индекс по выражению или изменение условия.

**Шаблон с ведущим процентом.** `LIKE '%SQL%'` не может использовать обычный индекс, потому что неизвестно, с чего начинается значение. Для полнотекстового поиска нужен отдельный механизм.

**Дублирующие индексы.** Индекс по `(order_id)` и автоматический индекс по `(order_id, book_id)` частично дублируются. Первый может быть лишним. Дубли увеличивают стоимость записи.

**Индекс на маленькой таблице.** Таблица на 20 строк читается быстрее, чем дерево индекса. Планировщик это понимает и может игнорировать индекс, но место он всё равно занимает.

**Ожидание, что индекс ускорит всё.** Индекс помогает поиску и соединению, но не ускоряет полный просмотр отчёта, который читает все строки. Если запрос всё равно читает всю таблицу, индекс не нужен.

**Отсутствие индекса на внешнем ключе.** Соединение `orders` и `order_items` по `order_id` без индекса на `order_items.order_id` заставляет базу просматривать позиции для каждого заказа. Это одна из самых частых причин медленных отчётов. Проверить легко: план соединения покажет `SCAN` по таблице позиций вместо `SEARCH`.

## Итоги

- Индекс это отдельная отсортированная структура с ключом и ссылкой на строку, а не копия таблицы.
- B-дерево обеспечивает логарифмическую глубину и поддерживает равенство, диапазоны и сортировку.
- `EXPLAIN QUERY PLAN` показывает `SCAN` или `SEARCH` и помогает проверить, используется ли индекс.
- Индекс работает по левому префиксу составного ключа и не работает, если столбец обёрнут функцией.
- Уникальный индекс защищает бизнес-правило, а не только ускоряет поиск.
- Каждый индекс замедляет вставку, обновление и удаление, поэтому лишние индексы удаляют.
- Индекс выбирают под конкретный частый запрос, проверяют планом и замером, а не создают на все столбцы.
- Лишний индекс почти всегда хуже его отсутствия: он расходует место на диске и замедляет каждую запись в таблицу.

::quiz
Q: Что хранит обычный индекс?
+ Ключ поиска и ссылку на строку таблицы
- Полную копию всех строк таблицы
- Текст запросов, которые его используют
- Результат последнего выполнения SELECT
! Индекс хранит ключ и ссылку, а остальные столбцы читаются из таблицы.

Q: Какая структура чаще всего лежит в основе индекса в SQLite?
+ B-дерево
- Стек
- Очередь
- Хеш-таблица без упорядочения
! B-дерево поддерживает поиск, диапазоны и сортировку.

Q: Что означает SCAN в плане запроса?
+ Последовательный просмотр таблицы или индекса
- Поиск по индексу
- Создание нового индекса
- Сортировку результата
! SCAN читает строки подряд, SEARCH ищет по структуре.

Q: Что означает COVERING INDEX в плане?
+ Все нужные столбцы есть в индексе, к таблице обращаться не нужно
- Индекс покрывает всю таблицу целиком
- Индекс временно отключён
- Индекс создан автоматически
! Покрывающий индекс содержит все столбцы запроса.

Q: Почему `WHERE LOWER(title) = 'sql'` не использует обычный индекс по title?
+ Функция скрывает значение столбца от индекса
- LOWER не существует в SQLite
- Индекс хранит только числа
- Запрос возвращает слишком много строк
! Индекс построен по значению title, а не по результату LOWER.

Q: Какие условия могут использовать индекс?
+ `title = 'SQL за 30 дней'`
+ `title BETWEEN 'А' AND 'К'`
+ `title GLOB 'SQL*'`
- `title LIKE '%SQL%'`
- `LOWER(title) = 'sql за 30 дней'`
! Точное значение, диапазон и префикс сужают область поиска.

Q: Как работает правило левого префикса для индекса (store_id, order_date)?
+ Запрос по store_id использует индекс
+ Запрос по store_id и order_date использует индекс
- Запрос только по order_date использует индекс так же хорошо
- Запрос по order_date без store_id вообще невозможен
! Индекс применяется к непрерывной начальной части ключа.

Q: Зачем нужен уникальный индекс?
+ Чтобы запретить повтор значения в столбце
+ Чтобы ускорить поиск по этому столбцу
- Чтобы разрешить несколько одинаковых строк
- Чтобы автоматически удалять дубли
! Уникальность это ограничение, а индекс ускоряет проверку.

Q: Сколько значений NULL допускает уникальный индекс в SQLite?
+ Несколько
- Ровно одно
- Ни одного
- Столько же, сколько обычных значений
! SQLite считает NULL неизвестным и не сравнивает их как равные.

Q: Почему индексы замедляют вставку?
+ Каждая вставка обновляет все деревья индексов
- Индекс блокирует таблицу навсегда
- Индекс копирует всю таблицу при вставке
- Вставка требует перезапуска базы
! Чем больше индексов, тем больше работы при записи.

Q: Что делает команда ANALYZE?
+ Собирает статистику для планировщика
- Создаёт индекс по всем столбцам
- Удаляет неиспользуемые индексы
- Перестраивает таблицу
! Статистика помогает планировщику оценивать число строк.

Q: Какие индексы стоит создавать?
+ Под частые запросы с избирательным условием
+ По внешнему ключу, который используется в соединениях
- По каждому столбцу таблицы
- По столбцу с двумя значениями на всю таблицу
! Индекс оправдан, когда он помогает конкретному запросу.

Q: Что произойдёт, если создать индекс, который не использует ни один запрос?
+ Он будет замедлять запись и занимать место
- База удалит его автоматически
- Запросы начнут выполняться быстрее
- Он заменит первичный ключ
! Лишний индекс приносит только расходы.

Q: Как называется индекс, который содержит все столбцы запроса?
= покрывающий
= покрывающий индекс
! Покрывающий индекс позволяет не обращаться к таблице.

Q: Какая команда удаляет индекс?
= DROP INDEX
= drop index
! DROP INDEX удаляет индекс из схемы.
