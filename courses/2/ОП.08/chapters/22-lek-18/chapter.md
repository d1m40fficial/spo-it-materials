## Заказ, который потерялся в отчёте

В понедельник менеджер «Страницы» просит отчёт: оплаченные заказы за сентябрь, от самых дешёвых к самым дорогим. Через час он присылает скриншот: в списке пятьдесят девять заказов, среди них отменённые и августовские. Продавец, который готовил запрос, удивился: условие вроде было.

В запросе стояло три ошибки сразу. В `WHERE` вместо `AND` использовали `OR`, дату сравнили как строку без границ месяца, а `ORDER BY` поставили до `WHERE`, потому что так было записано в примере из интернета. Каждая ошибка по отдельности выглядит безобидно, вместе они дают отчёт, которому нельзя верить.

**WHERE выбирает строки, ORDER BY упорядочивает уже выбранные строки.** Это две разные операции, и выполняются они в разное время. Фильтр отбрасывает то, что не нужно, сортировка меняет только порядок оставшегося. Если перепутать их местами, база либо вернёт лишнее, либо выдаст ошибку синтаксиса.

## WHERE: сравнение и три значения истины

`WHERE` стоит после `FROM` и получает условие. Условие проверяется для каждой строки, и в результат попадают только те строки, для которых оно истинно.

```sql
SELECT номер_заказа, дата_заказа, статус
FROM заказ
WHERE статус = 'оплачен'
ORDER BY дата_заказа
LIMIT 5;
```

| `номер_заказа` | `дата_заказа` | `статус` |
|---|---|---|
| 1037 | 2026-08-01 | оплачен |
| 1022 | 2026-08-08 | оплачен |
| 1007 | 2026-08-15 | оплачен |
| 1052 | 2026-08-22 | оплачен |
| 1017 | 2026-09-01 | оплачен |

Доступны обычные сравнения: `=`, `<>` или `!=`, `<`, `>`, `<=`, `>=`. Для текста сравнение идёт по кодам символов, для чисел по величине, для дат в формате `ГГГГ-ММ-ДД` по календарю, потому что такой текст совпадает с порядком дат.

```sql
SELECT код_книги, название, цена_коп
FROM книга
WHERE цена_коп > 200000
ORDER BY цена_коп DESC;
```

Запрос вернёт книги дороже двух тысяч рублей. Граница не включается: `>` строгий, `>=` включает. Разница в одну копейку иногда решает, попадёт ли товар в отчёт.

С `NULL` сравнение ведёт себя не как с обычным значением. `NULL` означает «значение неизвестно», поэтому `цена_коп = NULL` не истинно и не ложно, а неизвестно. В результат попадают только истинные условия, и строка с `NULL` не проходит.

```sql
SELECT код_категории, название, код_родителя
FROM категория
WHERE код_родителя IS NULL;
```

| `код_категории` | `название` | `код_родителя` |
|---|---|---|
| 1 | Художественная литература |  |
| 2 | Детская литература |  |
| 3 | Учебная литература |  |
| 4 | Справочная литература |  |
| 5 | Компьютерная литература |  |

Так находятся категории верхнего уровня, у которых нет родителя. Запись `WHERE код_родителя = NULL` вернула бы ноль строк, потому что сравнение с `NULL` даёт неизвестность. Для проверки пустоты используют `IS NULL` и `IS NOT NULL`.

Условие может быть простым значением:

```sql
SELECT 1 AS x WHERE NULL;
SELECT 1 AS x WHERE NULL OR 1;
```

Первый запрос не вернёт строк: `NULL` не проходит фильтр. Второй вернёт единицу, потому что `NULL OR TRUE` даёт истину. Эти два примера показывают, что `WHERE` пропускает только истину, а не всё, что не является ложью.

| `A` | `B` | `A AND B` | `A OR B` |
|---|---|---|---|
| истина | истина | истина | истина |
| истина | ложь | ложь | истина |
| истина | неизвестно | неизвестно | истина |
| ложь | ложь | ложь | ложь |
| ложь | неизвестно | ложь | неизвестно |
| неизвестно | неизвестно | неизвестно | неизвестно |

Из таблицы видно главное: `FALSE AND NULL` даёт ложь, а `TRUE OR NULL` даёт истину. Поэтому порядок вычислений и скобки меняют результат не меньше, чем сами значения.

## AND, OR и NOT

Операторы имеют приоритет. `NOT` связывает сильнее `AND`, `AND` сильнее `OR`. Запись:

```text
WHERE код_категории = 1 OR код_категории = 2 AND цена_коп < 50000
```

читается как «категория 1 или (категория 2 и цена меньше 500 рублей)». В результат попадут все книги категории 1, даже дорогие, и только дешёвые книги категории 2. В учебной базе это 543 строки.

Если нужны дешёвые книги обеих категорий, скобки обязательны:

```sql
SELECT код_книги, название, код_категории, цена_коп
FROM книга
WHERE (код_категории = 1 OR код_категории = 2)
  AND цена_коп < 50000
ORDER BY код_книги
LIMIT 8;
```

Такое условие возвращает 264 строки. Разница в 279 строках это цена одного пропущенного скобочного выражения.

Правило простое: если в условии есть и `AND`, и `OR`, ставьте скобки вокруг каждой смысловой группы. Даже когда приоритет совпадает с замыслом, скобки объясняют его читателю.

`NOT` отрицает условие целиком:

```sql
SELECT код_книги, название, цена_коп
FROM книга
WHERE NOT цена_коп > 280000
ORDER BY цена_коп DESC
LIMIT 3;
```

Запрос вернёт три самые дорогие книги, которые не дороже 2800 рублей. `NOT` применяется к сравнению, а не только к следующему слову. Если нужно отрицание сложного условия, его заключают в скобки: `NOT (статус = 'выдан' OR статус = 'отменён')`.

`NOT` с `NULL` даёт `NULL`, а не истину. Поэтому `WHERE NOT код_родителя = 1` не вернёт категории с пустым родителем. Для отрицания с пустыми значениями пишут `WHERE код_родителя IS NULL OR код_родителя <> 1`.

Законы де Моргана помогают переписать условие без ошибок. `NOT (A AND B)` равносильно `NOT A OR NOT B`, а `NOT (A OR B)` равносильно `NOT A AND NOT B`. Проверять равносильность лучше на нескольких строках, а не в уме: `NULL` ломает интуицию.

## LIKE, BETWEEN и IN

`LIKE` сравнивает строку с шаблоном. Знак `%` заменяет любое число символов, включая ноль, а `_` заменяет ровно один символ.

```sql
SELECT название
FROM книга
WHERE название LIKE 'Война%';
```

| `название` |
|---|
| Война и мир. Том 1 |
| Война и мир. Том 2 |

Шаблон `%мир%` находит все названия, где встречается «мир», а `_ойна%` требует ровно один символ перед «ойна». Подчёркивание удобно, когда неизвестна первая буква, но легко ошибиться: `_` совпадает и с пробелом, и с цифрой.

```sql
SELECT название
FROM книга
WHERE название LIKE '%мир%'
ORDER BY название;
```

| `название` |
|---|
| Война и мир. Том 1 |
| Война и мир. Том 2 |
| Подарочный атлас мира |

Если в данных встречается сам знак `%`, его экранируют:

```sql
SELECT 'Скидка 10%' LIKE '%10\%%' ESCAPE '\' AS нашли;
```

```text
1
```

Без `ESCAPE` последний `%` считался бы шаблоном, и строка совпала бы с более широким набором.

Регистр зависит от алфавита. Для латиницы `LIKE` по умолчанию не различает регистр:

```sql
SELECT 'SQL' LIKE 'sql' AS латиница;
```

```text
1
```

Для кириллицы то же сравнение даёт ложь:

```sql
SELECT 'Война' LIKE 'война' AS кириллица;
```

```text
0
```

Это ограничение встроенного `LIKE`, а не ошибка данных. Чтобы искать без учёта регистра по-русски, хранят нормализованный столбец, например название в нижнем регистре, и ищут по нему. Преобразование `LOWER` в SQLite тоже работает только с латиницей, поэтому русский текст приводят к нижнему регистру в приложении или при загрузке.

`BETWEEN` проверяет попадание в диапазон и включает обе границы:

```sql
SELECT код_книги, название, цена_коп
FROM книга
WHERE цена_коп BETWEEN 60000 AND 100000
ORDER BY цена_коп, код_книги
LIMIT 5;
```

| `код_книги` | `название` | `цена_коп` |
|---|---|---|
| 124 | Издание 124 | 60000 |
| 311 | Издание 311 | 60000 |
| 638 | Издание 638 | 60000 |
| 1143 | Издание 1143 | 60000 |
| 1813 | Издание 1813 | 60000 |

`BETWEEN 60000 AND 100000` равносильно `>= 60000 AND <= 100000`. Для дат это удобно, если дата хранится как текст `ГГГГ-ММ-ДД`:

```sql
SELECT номер_заказа, дата_заказа, статус
FROM заказ
WHERE дата_заказа BETWEEN '2026-09-01' AND '2026-09-30'
ORDER BY дата_заказа, номер_заказа
LIMIT 5;
```

| `номер_заказа` | `дата_заказа` | `статус` |
|---|---|---|
| 1005 | 2026-09-01 | отменён |
| 1017 | 2026-09-01 | оплачен |
| 1029 | 2026-09-01 | выдан |
| 1041 | 2026-09-01 | новый |
| 1053 | 2026-09-01 | собран |

В сентябре 20 заказов. Но у `BETWEEN` с датой есть ловушка. Если в столбце хранится дата со временем, `2026-09-30 14:00` больше, чем `2026-09-30`, и в диапазон не попадёт. Надёжнее задавать полуоткрытый интервал:

```sql
SELECT номер_заказа, дата_заказа
FROM заказ
WHERE дата_заказа >= '2026-09-01'
  AND дата_заказа < '2026-10-01'
ORDER BY дата_заказа, номер_заказа
LIMIT 5;
```

Второй вариант включает весь последний день и не зависит от того, есть ли в значении время.

`IN` проверяет совпадение с одним из перечисленных значений:

```sql
SELECT номер_заказа, статус
FROM заказ
WHERE статус IN ('оплачен', 'собран')
ORDER BY номер_заказа
LIMIT 5;
```

| `номер_заказа` | `статус` |
|---|---|
| 1002 | оплачен |
| 1003 | собран |
| 1007 | оплачен |
| 1008 | собран |
| 1012 | оплачен |

Список может быть длинным, а вместо констант допустим подзапрос:

```sql
SELECT код_книги, название
FROM книга
WHERE код_категории IN (
  SELECT код_категории FROM категория WHERE название LIKE 'Учебная%'
);
```

`NOT IN` отрицает список, но с `NULL` ведёт себя опасно. Если в подзапросе есть хотя бы один `NULL`, сравнение с ним даёт неизвестность, и `NOT IN` не вернёт ни одной строки. Для отрицания надёжнее `NOT EXISTS` или явное `IS NOT NULL` в подзапросе.

## Сравнение значений разных типов

SQLite хранит тип вместе со значением, поэтому сравнение зависит не только от оператора, но и от того, что стоит слева и справа.

```sql
SELECT '10' < '9' AS текст, 10 < 9 AS число;
```

| `текст` | `число` |
|---|---|
| 1 | 0 |

Две текстовые строки сравниваются посимвольно: первый символ `1` меньше `9`, поэтому `'10'` считается меньше `'9'`. Числа сравниваются по величине, и десять больше девяти. Ошибка появляется, когда число случайно хранится текстом: сортировка и диапазон дают не тот порядок.

У столбца есть объявленный тип, который задаёт сходство (affinity). Если столбец объявлен как `INTEGER` или `REAL`, SQLite старается привести текстовый операнд к числу. Если столбец объявлен как `TEXT`, число приводится к тексту. Поэтому один и тот же запрос с одним и тем же литералом может вести себя по-разному в двух таблицах.

```sql
SELECT COUNT(*) FROM книга WHERE цена_коп > '100000';
```

В `книга` столбец `цена_коп` объявлен как `INTEGER`, поэтому строка `'100000'` приводится к числу, и запрос работает как числовое сравнение. Но полагаться на неявное приведение не стоит: явный `CAST` показывает намерение и не зависит от объявления столбца.

```sql
SELECT COUNT(*) FROM книга WHERE цена_коп > CAST('100000' AS INTEGER);
```

Для дат правило то же. Текст `2026-09-01` сравнивается посимвольно, но формат `ГГГГ-ММ-ДД` устроен так, что посимвольный порядок совпадает с календарным. Формат `ДД.ММ.ГГГГ` этим свойством не обладает: `01.10.2026` окажется меньше `02.09.2026`, хотя октябрь позже сентября. Поэтому даты в базе хранят в ISO-формате, а показывают пользователю в привычном виде через приложение.

## ORDER BY: порядок результата

`ORDER BY` ставится после `WHERE` и перечисляет столбцы сортировки:

```sql
SELECT название, цена_коп
FROM книга
WHERE код_категории = 1
ORDER BY цена_коп DESC, название ASC
LIMIT 10;
```

Первым идёт главный ключ: цена по убыванию. Если цены совпадают, вступает второй ключ: название по возрастанию. Без второго ключа две книги с одинаковой ценой могли бы меняться местами от запуска к запуску.

`ASC` означает возрастание и подразумевается по умолчанию. `DESC` означает убывание. Для текста возрастание это порядок кодов символов, а не алфавит языка.

Сортировать можно по выражению и по псевдониму:

```sql
SELECT название, цена_коп / 100.0 AS цена
FROM книга
ORDER BY цена DESC, название
LIMIT 5;
```

| `название` | `цена` |
|---|---|
| Подарочный атлас мира | 2890.0 |
| Алгоритмы. Построение и анализ | 2190.0 |
| Python. К вершинам мастерства | 1890.0 |
| SQL для профессионалов | 1750.0 |
| Кулинарная книга. Русская кухня | 1680.0 |

Псевдоним `цена` подошёл бы и в `ORDER BY` без кавычек. Сортировка по номеру столбца `ORDER BY 2` работает, но считается плохой практикой: после изменения списка `SELECT` номер укажет на другой столбец.

`NULL` в SQLite считается меньше любого значения. При сортировке по возрастанию пустые значения идут первыми, при сортировке по убыванию последними.

```sql
SELECT код_категории, название, код_родителя
FROM категория
ORDER BY код_родителя
LIMIT 5;
```

| `код_категории` | `название` | `код_родителя` |
|---|---|---|
| 1 | Художественная литература |  |
| 2 | Детская литература |  |
| 3 | Учебная литература |  |
| 4 | Справочная литература |  |
| 5 | Компьютерная литература |  |

Если пустые значения должны быть в конце, используют `NULLS LAST`:

```sql
SELECT код_категории, название, код_родителя
FROM категория
ORDER BY код_родителя NULLS LAST, название
LIMIT 5;
```

| `код_категории` | `название` | `код_родителя` |
|---|---|---|
| 12 | Подарочные издания | 1 |
| 6 | Деловая литература |  |
| 2 | Детская литература |  |
| 11 | Иностранная литература |  |
| 8 | История |  |

`NULLS FIRST` и `NULLS LAST` появились в SQLite 3.30. В более старых версиях порядок обходят выражением `ORDER BY код_родителя IS NULL, код_родителя`: сначала ложь, потом истина.

`ORDER BY` не меняет порядок строк в таблице. Он влияет только на результат запроса. Следующий `SELECT` без сортировки вернёт строки в другом порядке, и это нормально.

Сортировка стоит памяти и времени. SQLite собирает выбранные строки, упорядочивает их и только потом отдаёт клиенту. Если по столбцу сортировки есть индекс, база может прочитать строки уже в нужном порядке и обойтись без отдельной сортировки. Поэтому `ORDER BY` по индексированному столбцу дешевле, чем по выражению вроде `ROUND(цена_коп * 0.9 / 100.0, 2)`. Для учебных объёмов разница незаметна, для отчёта на миллион строк она решает, сработает запрос быстро или нет.

## Сортировка кириллицы и устойчивая пагинация

Русский алфавит и коды Unicode не совпадают. Буква «Ё» стоит в Unicode перед «Е», а не после, поэтому сравнение по коду даёт неожиданный результат:

```sql
SELECT 'Ёлка' < 'Ель' AS по_кодам, 'ёж' > 'яблоко' AS ё_после;
```

| `по_кодам` | `ё_после` |
|---|---|
| 1 | 1 |

По правилам русского алфавита «Ёлка» должна идти после «Ель», а «ёж» перед «яблоко». SQLite сравнивает коды символов и не знает языковых правил.

Встроенная сортировка `COLLATE NOCASE` тоже помогает только для латиницы. Для кириллицы она не меняет регистр и не задаёт алфавитный порядок. Если нужен настоящий русский алфавит, есть три пути: хранить дополнительный столбец с ключом сортировки, подготовленным приложением, сортировать результат в приложении или подключить расширение с нужной культурой. В учебной базе достаточно помнить ограничение и не обещать пользователю «алфавитный порядок», если его нет.

Для латиницы `COLLATE NOCASE` работает:

```sql
SELECT название
FROM книга
WHERE название LIKE 'sql%'
ORDER BY название COLLATE NOCASE;
```

| `название` |
|---|
| SQL для профессионалов |

Сортировка по нескольким столбцам и `LIMIT` вместе образуют пагинацию. Чтобы страницы не пересекались, последним ключом добавляют уникальный столбец:

```sql
SELECT код_книги, название, цена_коп
FROM книга
ORDER BY цена_коп DESC, код_книги
LIMIT 3 OFFSET 2;
```

| `код_книги` | `название` | `цена_коп` |
|---|---|---|
| 707 | Python. К вершинам мастерства | 189000 |
| 708 | SQL для профессионалов | 175000 |
| 716 | Кулинарная книга. Русская кухня | 168000 |

Без `код_книги` книги с одинаковой ценой могут попасть на две страницы сразу или не попасть ни на одну. Это не ошибка SQLite, а следствие неустойчивого порядка.

## Проверка фильтра и сортировки

Перед сдачей отчёта проверяют три вещи: сколько строк должно быть, те ли строки попали и в том ли они порядке.

Сначала считают строки без вывода:

```sql
SELECT COUNT(*) FROM заказ
WHERE статус IN ('оплачен', 'собран')
  AND дата_заказа >= '2026-09-01'
  AND дата_заказа < '2026-10-01';
```

Если число совпало с ожидаемым, смотрят образец:

```sql
SELECT номер_заказа, дата_заказа, статус
FROM заказ
WHERE статус IN ('оплачен', 'собран')
  AND дата_заказа >= '2026-09-01'
  AND дата_заказа < '2026-10-01'
ORDER BY дата_заказа, номер_заказа
LIMIT 10;
```

Образец показывает, что условие не захватило август и не потеряло последний день сентября. Сортировка по дате и номеру делает результат устойчивым: заказы одного дня идут в предсказуемом порядке.

Затем проверяют границы отдельно:

```sql
SELECT MIN(дата_заказа) AS первый, MAX(дата_заказа) AS последний
FROM заказ
WHERE статус IN ('оплачен', 'собран')
  AND дата_заказа >= '2026-09-01'
  AND дата_заказа < '2026-10-01';
```

Если минимум равен `2026-09-01`, а максимум `2026-09-30`, диапазон взят правильно. Если минимум оказался августовским, значит, одна из границ забыта или перепутана.

План запроса подсказывает, пользуется ли база индексом:

```sql
EXPLAIN QUERY PLAN
SELECT * FROM заказ WHERE статус = 'оплачен';
```

`SCAN заказ` означает полный перебор. Для 60 заказов это нормально, для миллионов строк требует индекса по `статус`. Но индекс не отменяет `LIKE '%слово%'`: ведущий процент заставляет перебирать значения.

Проверку повторяют на данных, которые лежат на границе условия. Если отчёт строится за сентябрь, в базе должен быть заказ от 31 августа и заказ от 1 октября. Тогда видно, что границы не захватывают лишний день и не теряют нужный. На пустой или однородной таблице любое условие выглядит правильным.

## Типичные ошибки

- **`= NULL` вместо `IS NULL`.** Сравнение с пустым значением не истинно, поэтому строки не находятся.
- **`OR` без скобок.** Приоритет `AND` выше, и условие читается не так, как задумано.
- **`NOT IN` с `NULL` в подзапросе.** Результат неожиданно пустой. Помогает `NOT EXISTS`.
- **`LIKE '%слово%'` на миллионе строк.** Ведущий процент не даёт использовать индекс, база перебирает всё.
- **`LIKE` по кириллице без учёта регистра.** Встроенный `LIKE` различает регистр русских букв.
- **`BETWEEN` с датой и временем.** Последний день может не попасть в диапазон. Надёжнее полуоткрытый интервал.
- **Сортировка по номеру столбца.** После правки `SELECT` номер указывает на другое поле.
- **`LIMIT` без уникального порядка.** Страницы пересекаются, отчёт меняется от запуска к запуску.
- **Сравнение чисел, хранящихся текстом.** `'10' < '9'` истинно, потому что сравниваются символы, а не величины.

## Проверьте себя

> [!CHECK] Почему `WHERE статус = 'оплачен' OR статус = 'собран' AND дата_заказа > '2026-09-01'` возвращает августовские оплаченные заказы?
> Приоритет `AND` выше `OR`, поэтому условие читается как «оплачен или (собран и после сентября)». Все оплаченные заказы проходят независимо от даты. Нужны скобки: `WHERE (статус = 'оплачен' OR статус = 'собран') AND дата_заказа > '2026-09-01'`.

> [!CHECK] Запрос `WHERE дата_заказа BETWEEN '2026-09-01' AND '2026-09-30'` вернул 20 строк, а в сентябре 21 заказ. В чём причина?
> Один заказ имеет дату `2026-09-30` со временем, например `2026-09-30 14:00`. Такая строка больше границы `2026-09-30` и не попадает в `BETWEEN`. Полуоткрытый интервал `>= '2026-09-01' AND < '2026-10-01'` включает весь последний день.

> [!CHECK] Почему сортировка `ORDER BY название` не даёт русский алфавитный порядок?
> SQLite сравнивает коды Unicode, а не порядок букв русского алфавита. «Ё» в Unicode стоит перед «Е», поэтому результат отличается от ожидаемого. Встроенный `NOCASE` помогает только для латиницы. Для русского порядка нужен отдельный ключ сортировки или сортировка в приложении.

## Итоги

- `WHERE` фильтрует строки, `ORDER BY` сортирует уже выбранный результат.
- Сравнение с `NULL` даёт неизвестность; пустоту проверяют через `IS NULL`.
- `AND` связывает сильнее `OR`, поэтому смысловые группы заключают в скобки.
- `LIKE` ищет по шаблону, `BETWEEN` задаёт включительный диапазон, `IN` проверяет список.
- Для даты надёжнее полуоткрытый интервал, чем `BETWEEN` по последнему дню.
- `ORDER BY` принимает несколько ключей; `NULL` по умолчанию идёт первым, `NULLS LAST` меняет это.
- Сортировка кириллицы по кодам не совпадает с алфавитом, а устойчивая пагинация требует уникального последнего ключа.
- `LIKE` с ведущим процентом не использует индекс, а `ORDER BY` по индексированному столбцу обходится без отдельной сортировки, если порядок строк совпадает с порядком индекса.

::quiz
Q: Что делает WHERE?
+ Отбирает строки по условию
- Сортирует строки результата
- Удаляет строки из таблицы
- Группирует строки
! WHERE проверяет условие для каждой строки и оставляет истинные.

Q: Какое сравнение находит пустое значение?
+ IS NULL
- = NULL
- == NULL
- <> NULL
! Сравнение с NULL даёт неизвестность, а IS NULL проверяет пустоту.

Q: Какой оператор имеет более высокий приоритет?
+ AND
- OR
- Оба равны
- NOT ниже обоих
! AND связывает сильнее OR, поэтому скобки обязательны.

Q: Что делает LIKE с шаблоном 'Война%'?
+ Ищет строки, начинающиеся с «Война»
- Ищет строки, заканчивающиеся на «Война»
- Ищет точное совпадение
- Ищет строки, где есть «Война» в любом месте
! Знак % в конце заменяет любое продолжение строки.

Q: Что означает BETWEEN 60000 AND 100000?
+ Значение от 60000 до 100000 включительно
- Значение строго больше 60000 и меньше 100000
- Значение от 60000 до 100000, не включая границы
- Любое значение больше 100000
! BETWEEN включает обе границы.

Q: Чем опасен NOT IN с подзапросом, где есть NULL?
+ Результат может оказаться пустым
- Запрос выполняется быстрее
- SQLite удаляет таблицу
- NOT IN игнорирует NULL и работает как обычно
! Сравнение с NULL даёт неизвестность, и условие не проходит.

Q: Что делает ORDER BY цена_коп DESC, название ASC?
+ Сортирует по цене по убыванию, затем по названию по возрастанию
- Сортирует по названию, затем по цене
- Сортирует только по цене
- Сортирует по цене по возрастанию
! Первый ключ главный, второй разрешает совпадения.

Q: Где по умолчанию стоят NULL при сортировке по возрастанию?
+ В начале
- В конце
- В середине
- Порядок случаен
! SQLite считает NULL меньшим любого значения.

Q: Что делает NULLS LAST?
+ Ставит пустые значения в конец
- Удаляет пустые значения
- Заменяет NULL на ноль
- Сортирует только непустые строки
! NULLS LAST меняет место NULL в порядке результата.

Q: Какие условия можно построить с AND, OR и NOT?
+ статус = 'оплачен' AND дата_заказа > '2026-09-01'
+ (код_категории = 1 OR код_категории = 2) AND цена_коп < 50000
+ NOT (статус = 'выдан' OR статус = 'отменён')
+ код_родителя IS NULL OR код_родителя <> 1
- WHERE COUNT(*) > 10
- ORDER BY цена_коп DESC
! Логические операторы соединяют условия, а не команды и не агрегаты.

Q: Какие операторы подходят для поиска по списку и диапазону?
+ IN
+ BETWEEN
+ LIKE
+ IS NULL
- ORDER BY
- GROUP BY
! IN проверяет список, BETWEEN диапазон, LIKE шаблон, IS NULL пустоту.

Q: Что нужно для устойчивой пагинации?
+ ORDER BY с уникальным последним ключом
+ LIMIT и OFFSET
+ Постоянный порядок строк
- Сортировка по номеру столбца
- Отсутствие ORDER BY
! Уникальный ключ не даёт страницам пересекаться.

Q: Какие ошибки приводят к неверной фильтрации?
+ = NULL вместо IS NULL
+ OR без скобок при наличии AND
+ NOT IN с NULL в подзапросе
+ BETWEEN по дате со временем
- Использование IS NOT NULL
- Скобки вокруг групп условий
! Каждая ошибка меняет набор строк или делает его пустым.

Q: Какой оператор заменяет один символ в шаблоне LIKE?
= _
