## Три потерянные строки

В книжном магазине «Страница» старая система учёта отдала справочник покупателей в CSV. В файле 4800 строк. После импорта в новую базу оказалось 4797. Три покупателя исчезли, и никто не заметил этого, пока один из них не попросил вернуть забытый заказ.

Разбор показал три разные причины. В названии одной организации была запятая, и строка развалилась на лишние столбцы. Вторая строка пришла в кодировке Windows-1251, а база ждала UTF-8, поэтому имя превратилось в набор символов и не прошло проверку. Третья строка была пустой в конце файла и не создала запись.

Ни одна из этих причин не связана с SQL. Все три относятся к формату файла и его сопоставлению с таблицей. **Импорт это перевод данных из формата файла в формат таблицы, и ошибка перевода почти всегда выглядит как «строки просто нет».** Поэтому перенос начинают со схемы, кодировки и проверки, а не с нажатия кнопки.

## Два формата

CSV хранит таблицу текстом. Каждая строка файла это строка таблицы, значения разделены запятыми или другим символом. Первая строка обычно содержит заголовки столбцов.

```text
id,name,city,email,registered
101,ООО «Читатель»,Москва,,2026-09-02
102,Петров Пётр,Тула,petrov@mail.ru,2026-09-03
103,"ООО «Книга, свет»",Калуга,info@kniga.ru,2026-09-04
```

Значение с запятой внутри взято в двойные кавычки. Если внутри значения есть кавычка, её удваивают. Строка может занимать несколько физических строк, если значение содержит перевод строки. Это описано в стандарте RFC 4180, но не все программы следуют ему одинаково.

JSON хранит данные как дерево. Массив объектов соответствует набору строк, ключи соответствуют столбцам.

```json
[
  {"id": 101, "name": "ООО «Читатель»", "city": "Москва", "email": null},
  {"id": 102, "name": "Петров Пётр", "city": "Тула", "email": "petrov@mail.ru"},
  {"id": 103, "name": "ООО «Книга, свет»", "city": "Калуга", "email": "info@kniga.ru"}
]
```

| Свойство | CSV | JSON |
|---|---|---|
| Форма | плоская таблица | дерево |
| Заголовки | первая строка или отдельная схема | ключи объектов |
| Вложенность | нет | есть |
| Типы | все значения текст | числа, строки, boolean, null |
| Читаемость | высокая для таблицы | высокая для структуры |
| Риск | разделитель, кавычки, кодировка | вложенность, типы, размер |

CSV удобен для выгрузки из Excel и для простых справочников. JSON удобен для обмена с приложением и для данных со вложенными объектами. Например, заказ с позициями в JSON выглядит как один объект с массивом `items`, а в CSV потребует отдельного файла позиций или повторения заказа в каждой строке.

Для учебной базы «Страницы» оба формата нужны. Справочники удобно грузить из CSV, а данные приложения, такие как заказы с позициями, приходят в JSON.

## Схема файла и схема таблицы

Перед импортом выписывают соответствие полей. Это таблица, в которой для каждого поля файла указано, куда оно попадает, какой тип ожидается и что делать с пустым значением.

| Поле файла | Столбец таблицы | Тип | Обязательное | Преобразование |
|---|---|---|---|---|
| id | customers.id | INTEGER | да | убрать пробелы, проверить число |
| name | customers.name | TEXT | да | обрезать пробелы |
| city | customers.city | TEXT | да | сверить со справочником городов |
| email | customers.email | TEXT | нет | пустое значение заменить на NULL |
| registered | customers.registered | TEXT даты | да | привести к ISO `ГГГГ-ММ-ДД` |

Такая таблица ловит большинство ошибок до импорта. Если в файле есть поле, которого нет в таблице, решают, игнорировать его или добавить столбец. Если в таблице есть обязательное поле, которого нет в файле, импорт не сможет заполнить его без значения по умолчанию.

Вложенный JSON требует разложения на несколько таблиц. Объект заказа с массивом позиций нельзя записать в одну строку `orders`, если схема нормализована. Сначала создают заказ в `orders`, затем каждую позицию в `order_items` с тем же `order_id`. Это тот же принцип, что при ручном вводе, только строк больше.

Полезно сразу определить, что считается пустым значением. В CSV пустая ячейка не отличает пустую строку от отсутствия значения. В JSON есть отдельный `null`. Если для столбца `email` пустая строка допустима, а `NULL` означает «не указан», правило нужно зафиксировать. Иначе после импорта часть клиентов получит пустые строки, а часть `NULL`, и запросы `WHERE email IS NULL` будут находить только половину.

## Кодировка

Текст в файле это последовательность байтов. Кодировка задаёт соответствие байтов символам. Если файл записан в UTF-8, а прочитан как Windows-1251, русские буквы превращаются в мусор. Если наоборот, мусор появится в другой стороне.

Самый частый случай связан с BOM. UTF-8 может начинаться с трёх байтов `EF BB BF`. Они не видны в редакторе, но становятся частью первого заголовка. Вместо столбца `id` база видит `﻿id` с невидимым символом в начале. Импорт создаёт столбец с другим именем, и запрос `SELECT id` не находит его.

Признаки проблемы:

- первый столбец в таблице называется `п»їid` или `ГївЂ№id`;
- русские буквы выглядят как `РџСЂРёРІРµС‚`;
- вместо букв стоят вопросительные знаки;
- часть строк читается нормально, часть нет.

Причина последнего варианта в смешанной кодировке: файл собирали из двух источников, один сохранил UTF-8, другой Windows-1251. Исправлять по одной строке бессмысленно, нужно перекодировать файл целиком или разделить его на части.

Как проверить кодировку:

1. Открыть файл в редакторе, который показывает кодировку, например в VS Code.
2. Посмотреть первые байты: BOM виден как `U+FEFF` или `EF BB BF`.
3. Попробовать открыть файл в UTF-8 и в Windows-1251, сравнить русский текст.
4. Для CSV из Excel выбрать сохранение «CSV UTF-8 (разделитель: запятая)», а не обычный CSV.

В SQLite текст хранится в том виде, в котором его передали. База не перекодирует строки автоматически. Если в таблицу попал мусор, он там и останется, пока его не исправят отдельным `UPDATE` или повторным импортом.

Перекодировать файл можно в текстовом редакторе или небольшим скриптом. В Python достаточно прочитать файл в исходной кодировке и записать в UTF-8.

```python
text = open("customers.csv", encoding="cp1251").read()
open("customers_utf8.csv", "w", encoding="utf-8", newline="").write(text)
```

Параметр `newline=""` не даёт Python удвоить переводы строк в CSV. После преобразования файл открывают заново и проверяют, что заголовок читается, а первая строка не начинается с BOM. Если BOM уже попал в заголовок, его удаляют вручную или при импорте указывают, что файл в UTF-8 с BOM.

Excel добавляет ещё одну сложность. При открытии CSV он пытается угадать типы: `007` превращается в `7`, длинный номер заказа может стать `1,23E+12`, дата `02.09.2026` может быть переставлена в американский формат. Поэтому CSV для импорта лучше не открывать в Excel «на посмотреть», а проверять текстовым редактором или отдельной копией.

## Разделитель и кавычки

В русской локали Excel часто использует точку с запятой как разделитель списка. Файл с точкой с запятой, открытый как CSV с запятой, попадёт целиком в один столбец. База увидит одну длинную строку вместо пяти полей.

| Разделитель | Где встречается | Как выглядит |
|---|---|---|
| запятая | RFC 4180, международный CSV | `101,Петров,Тула` |
| точка с запятой | Excel в русской локали | `101;Петров;Тула` |
| табуляция | TSV, выгрузки из таблиц | `101[таб]Петров[таб]Тула` |
| вертикальная черта | самодельные выгрузки | `101|Петров|Тула` |

Перед импортом смотрят на несколько первых строк и считают число полей. Если в заголовке пять полей, а в строке данных шесть, значит разделитель или кавычки обработаны неверно.

Кавычки нужны, когда значение содержит разделитель, перевод строки или саму кавычку. Правило удвоения кавычек важно соблюдать при экспорте. Если название `ООО "Книга, свет"` записать без экранирования, запятая внутри кавычек может быть принята за разделитель, а кавычки потеряются.

При экспорте из Excel в CSV он сам ставит кавычки вокруг таких значений. Но при ручной сборке файла в блокноте это легко пропустить. Поэтому выгрузку лучше делать программой, а не руками.

Есть ещё завершающая пустая строка. Многие редакторы добавляют перевод строки в конец файла. Одни импортёры игнорируют её, другие создают пустую запись. Если после импорта число строк на единицу больше, проверяют конец файла.

Заголовок тоже бывает разным. Вместо `id,name,city` файл может содержать `ID;Наименование;Город` или `id;name;city;`. Импортёр должен знать, есть ли заголовок, как называется каждый столбец и что делать с лишним пустым. В sqliteonline параметры импорта задаются в диалоге, и их нужно проверить до нажатия кнопки.

## Типы и пустые значения

CSV не хранит типы. Все значения в нём текст, даже если выглядят как число или дата. Если импортировать файл сразу в таблицу с типом `INTEGER`, база попытается преобразовать текст и в случае неудачи подставит `0` или `NULL`. Лучше сначала загрузить всё в промежуточную таблицу, где все столбцы `TEXT`, проверить значения, а затем перенести в целевую таблицу с преобразованием.

```sql
CREATE TABLE customers_import (
  id TEXT,
  name TEXT,
  city TEXT,
  email TEXT,
  registered TEXT
);
INSERT INTO customers_import VALUES
('101','ООО «Читатель»','Москва','','2026-09-02'),
('102','Петров Пётр','Тула','petrov@mail.ru','02.09.2026'),
('103','ООО «Книга, свет»','Калуга','info@kniga.ru','2026-09-03'),
('104','Сидорова Ольга','Тверь','sidorova@mail.ru','2026-09-04 '),
('101','ООО «Читатель»','Москва','sales@chitay.ru','2026-09-02');
```

После загрузки проверяют даты. В базе удобен формат `ГГГГ-ММ-ДД`, потому что он сравнивается как строка и не зависит от локали. Проверка через `GLOB` находит строки, которые не соответствуют шаблону.

```sql
SELECT id, registered
FROM customers_import
WHERE registered NOT GLOB '????-??-??';
```

Для учебного файла результат: строки `102` с датой `02.09.2026` и `104` с датой `2026-09-04 ` (пробел в конце). Обе выглядят почти правильными, но база не сможет сравнить их с датой в формате ISO.

Числа с десятичной запятой тоже требуют преобразования. В CSV из русской локали цена может быть записана как `620,50`. Функция `CAST('620,50' AS REAL)` вернёт `620.0`, потому что запятая не является десятичным разделителем для SQLite. Нужно сначала заменить запятую на точку, затем преобразовать.

Логические значения приходят в разных видах. В JSON это `true` и `false`, в CSV часто `да` и `нет`, `1` и `0`, `Y` и `N`. В SQLite нет отдельного логического типа, поэтому выбирают представление `0` и `1` с ограничением `CHECK (flag IN (0, 1))`. Преобразование `да` в `1` и `нет` в `0` делают явно, иначе база сохранит текст и запрос `WHERE flag = 1` не найдёт строки.

```sql
SELECT CAST('42,5' AS REAL) AS bad, CAST(REPLACE('42,5', ',', '.') AS REAL) AS good;
```

| bad | good |
|---|---|
| 42.0 | 42.5 |

Ещё опаснее `CAST('abc' AS INTEGER)`. Он возвращает `0`, а не ошибку. Строка с испорченным идентификатором молча станет нулём и может совпасть с другой записью. Поэтому перед преобразованием проверяют, что значение действительно число.

```sql
SELECT id
FROM customers_import
WHERE id NOT GLOB '[0-9]*' OR TRIM(id) = '';
```

Пустые значения проверяют отдельно.

```sql
SELECT id, name
FROM customers_import
WHERE TRIM(COALESCE(email, '')) = '';
```

`COALESCE` нужен, потому что `TRIM(NULL)` возвращает `NULL`, а сравнение с пустой строкой не сработает. После проверки решают, заменить пустую строку на `NULL` или оставить. Для необязательного email логичнее `NULL`: он означает «не указан», а пустая строка выглядит как указанное, но пустое значение.

## Импорт в sqliteonline

В sqliteonline данные загружают через меню импорта. Порядок такой:

1. Создать промежуточную таблицу со всеми столбцами `TEXT`.
2. Открыть импорт и выбрать файл.
3. Указать разделитель, кодировку и наличие заголовка.
4. Проверить предварительный просмотр: число столбцов и первую строку.
5. Выполнить импорт и сразу посмотреть `SELECT * FROM customers_import LIMIT 5`.

JSON в sqliteonline можно разобрать функциями JSON. Если файл уже вставлен в текстовый столбец, `json_each` разворачивает массив в строки.

```sql
WITH data(doc) AS (
  VALUES ('[{"id":101,"name":"ООО Читатель","city":"Москва","email":null},
            {"id":102,"name":"Петров Пётр","city":"Тула","email":"petrov@mail.ru"}]')
)
SELECT json_extract(j.value, '$.id') AS id,
       json_extract(j.value, '$.name') AS name,
       json_extract(j.value, '$.email') AS email
FROM data, json_each(data.doc) AS j;
```

| id | name | email |
|---|---|---|
| 101 | ООО Читатель | NULL |
| 102 | Петров Пётр | petrov@mail.ru |

`json_each` возвращает по одной строке на элемент массива. `json_extract` вынимает значение по пути. Если email отсутствует или равен `null`, результат будет `NULL`, а не пустая строка.

Тип значения сохраняется. Если в JSON записать `"id": "103"`, `json_extract` вернёт текст, а не число. При вставке в целевую таблицу с `INTEGER` SQLite преобразует текст, но лучше проверить заранее.

```sql
SELECT json_extract('{"id": 101}', '$.id') AS number,
       json_extract('{"id": "101"}', '$.id') AS text;
```

```text
number = 101 (integer)
text = 101 (text)
```

Проверить корректность JSON целиком можно функцией `json_valid`. Она возвращает `1` для правильного документа и `0` для повреждённого.

```sql
SELECT json_valid('[{"id": 1}]') AS ok,
       json_valid('[{"id": 1},]') AS broken;
```

Импорт лучше выполнять в одной транзакции. Если на середине обнаружилась ошибка, `ROLLBACK` вернёт базу к состоянию до загрузки. Для большого файла транзакцию делят на пакеты, чтобы не держать блокировку слишком долго.

## Размер файла и пакеты

Учебный справочник на 4800 строк небольшой, но выгрузка заказов за несколько лет может содержать миллионы строк. Браузер и sqliteonline держат файл в памяти, поэтому огромный CSV лучше разделить на части по 50-100 тысяч строк. Каждую часть загружают отдельной транзакцией и после каждой сверяют число строк.

Пакетная загрузка даёт два преимущества. При ошибке теряется только последний пакет, а не весь файл. Блокировка не держится на всей загрузке, и другие пользователи могут работать с базой. Номер пакета и число загруженных строк записывают в журнал импорта, чтобы после сбоя продолжить с нужного места, а не начинать заново.

Если файл уже загружен частично, повторный импорт всего файла создаст дубли. Перед повторной попыткой проверяют, какие ключи уже есть, и пропускают их. Уникальный индекс по идентификатору превращает случайный дубль в ошибку, которую легче заметить.

## Заказ в JSON: разложение на две таблицы

Вложенный JSON нельзя записать в одну таблицу без потери структуры. Покажем на заказе с позициями.

```json
{
  "order_id": 501,
  "customer_id": 1,
  "order_date": "2026-10-01",
  "items": [
    {"book_id": 10, "quantity": 2, "price": 1400},
    {"book_id": 22, "quantity": 1, "price": 1190}
  ]
}
```

Заказ и его позиции это две таблицы. Сначала извлекают шапку заказа, затем разворачивают массив `items`.

```sql
WITH doc(d) AS (
  VALUES ('{"order_id":501,"customer_id":1,"order_date":"2026-10-01",
           "items":[{"book_id":10,"quantity":2,"price":1400},
                    {"book_id":22,"quantity":1,"price":1190}]}')
)
SELECT json_extract(j.value, '$.book_id') AS book_id,
       json_extract(j.value, '$.quantity') AS quantity,
       json_extract(j.value, '$.price') AS price
FROM doc, json_each(doc.d, '$.items') AS j;
```

| book_id | quantity | price |
|---|---|---|
| 10 | 2 | 1400 |
| 22 | 1 | 1190 |

`json_each` с путём `$.items` проходит по массиву и возвращает по строке на позицию. Шапка заказа при этом не повторяется: её вставляют в `orders` один раз, а `order_id` передают в каждую позицию. Если попытаться вставить заказ и позиции одной командой без транзакции, при ошибке в позиции заказ останется без строк, а при повторной попытке появится дубль.

Порядок такой: вставить заказ, получить его идентификатор, вставить позиции, проверить, что число позиций совпало с длиной массива. Всё это в одной транзакции. Для нескольких заказов внешний `json_each` идёт по массиву заказов, а внутренний по `$.items` каждого заказа.

## Проверка после импорта

После импорта недостаточно увидеть несколько строк. Нужна сверка, которая отвечает на три вопроса: все ли строки дошли, не появились ли лишние, совпадают ли значения.

| Проверка | Что сравнить | Признак ошибки |
|---|---|---|
| Количество | строки файла и строки таблицы | числа расходятся |
| Уникальность | число строк и число уникальных ключей | ключей меньше |
| Ссылки | внешние ключи и справочник | есть строки без пары |
| Даты | шаблон ISO | есть точки или пробелы |
| Суммы | итог файла и итог таблицы | расхождение на копейки |
| Типы | `typeof` столбца | число стало текстом |

Начнём с числа строк.

```sql
SELECT COUNT(*) AS rows_total,
       COUNT(DISTINCT id) AS ids_unique
FROM customers_import;
```

Для учебного файла результат: `5` строк и `4` уникальных идентификатора. Пятая строка дублирует `101`. Дубли надо найти и решить, какая запись правильная.

```sql
SELECT id, COUNT(*) AS copies
FROM customers_import
GROUP BY id
HAVING COUNT(*) > 1;
```

| id | copies |
|---|---|
| 101 | 2 |

Сравнить источник и приёмник можно через `EXCEPT`. Он возвращает строки, которые есть в первом результате, но отсутствуют во втором.

```sql
CREATE TEMP TABLE source_ids (id INTEGER);
INSERT INTO source_ids VALUES (1), (2), (3), (4), (5);
CREATE TEMP TABLE target_ids (id INTEGER);
INSERT INTO target_ids VALUES (1), (2), (4), (5);

SELECT id FROM source_ids
EXCEPT
SELECT id FROM target_ids;
```

| id |
|---|
| 3 |

Если таких строк нет, множества совпадают. `EXCEPT` не показывает, сколько раз значение встречалось, поэтому для проверки дублей он не заменяет `GROUP BY`.

Проверка ссылочной целостности ищет строки, которые ссылаются на несуществующий справочник.

```sql
SELECT i.id
FROM customers_import i
LEFT JOIN stores s ON s.city = i.city
WHERE s.id IS NULL;
```

Если город в файле написан иначе, чем в справочнике, соединение не найдёт пару. Это не всегда ошибка: возможно, город действительно новый. Но решение должно быть явным, а не случайным.

Суммовая сверка полезна для денежных данных. Сумма по файлу и сумма по таблице должны совпадать с точностью до копейки. Если они расходятся, ищут строку с потерянной позицией или неверным количеством.

```sql
CREATE TEMP TABLE order_items_import (
  order_id INTEGER, book_id INTEGER, quantity INTEGER, price REAL
);
INSERT INTO order_items_import VALUES (1, 10, 1, 1400), (1, 22, 2, 1190);

SELECT SUM(quantity * price) AS total_source FROM order_items_import;
SELECT SUM(quantity * unit_price) AS total_target FROM order_items;
```

Наконец, смотрят на типы.

```sql
SELECT typeof(id), typeof(email), COUNT(*)
FROM customers
GROUP BY typeof(id), typeof(email);
```

Если идентификатор оказался текстом, а должен быть числом, это проявится при сортировке и соединении. `typeof` показывает фактический тип значения, а не объявленный в схеме.

::/gate

## Экспорт

Экспорт кажется простой операцией: выбрать данные и сохранить в CSV. Ошибки здесь те же, что при импорте, только меняется направление.

Перед выгрузкой выбирают только нужные столбцы. Если в таблице есть персональные данные, паспортные номера или внутренние комментарии, они не должны попасть в файл для внешнего получателя. Представление или отдельный `SELECT` помогают ограничить набор.

Разделитель выбирают под получателя. Для Excel в русской локали удобна точка с запятой, для международного обмена запятая. Если файл откроют в другой стране, запятая может быть десятичным разделителем, и числа сломаются. Поэтому в сопроводительном сообщении указывают формат и кодировку.

Даты выгружают в ISO, числа с точкой, идентификаторы как текст, если в них есть ведущие нули. Длинные номера телефонов и карт тоже лучше оставить текстом, иначе Excel превратит их в число и потеряет формат.

Отдельная проблема это формулы. Если значение начинается с `=`, `+`, `-` или `@`, Excel может воспринять его как формулу при открытии файла. Пользовательские данные, например название организации `=ООО`, способны выполнить нежелательное действие. При экспорте такие значения экранируют апострофом или заключают в кавычки по правилам получателя.

После выгрузки файл открывают заново и проверяют: число строк, заголовки, кодировку, разделитель, отсутствие обрезанных значений. Экспорт без проверки это тот же импорт с потерянными строками, только ошибка обнаружится у получателя.

## Типичные ошибки

**BOM в первом заголовке.** Столбец `id` превращается в `﻿id`, и запросы не находят его. Лечение: сохранять UTF-8 без BOM или удалять BOM при импорте.

**Неверный разделитель.** Весь файл попадает в один столбец. Лечение: посчитать поля в первых строках и выбрать правильный разделитель.

**Потеря ведущих нулей.** `007` становится `7`. Лечение: импортировать идентификаторы как текст и преобразовывать только после проверки.

**Дата в локальном формате.** `02.09.2026` не сравнивается с `2026-09-02`. Лечение: приводить к ISO на этапе загрузки.

**Пустая строка и NULL смешаны.** Запрос `IS NULL` находит не всех. Лечение: зафиксировать правило и привести значения к одному виду.

**Дубли после повторного импорта.** Файл загрузили дважды, строки удвоились. Лечение: уникальный ключ, проверка существования или очистка промежуточной таблицы перед загрузкой.

**Обрезанное значение с запятой.** Название `ООО «Книга, свет»` развалилось на два столбца. Лечение: кавычки и проверка числа полей.

**Молчаливое преобразование типа.** `CAST('abc' AS INTEGER)` даёт `0`. Лечение: проверять значения до преобразования, а не после.

**Экспорт формул и персональных данных.** Файл открывается в Excel и выполняет формулу или раскрывает лишние столбцы. Лечение: ограничить набор полей и экранировать опасные значения.

## Итоги

- Импорт это перевод формата файла в формат таблицы, и ошибки перевода теряют строки незаметно.
- CSV хранит плоскую таблицу, JSON хранит дерево; для JSON заранее планируют разложение на несколько таблиц.
- Схема соответствия полей, типов и обязательности ловит большинство ошибок до загрузки.
- Кодировку, BOM и разделитель проверяют до импорта, а не после.
- Промежуточная таблица со всеми столбцами `TEXT` позволяет проверить данные и преобразовать их осознанно.
- После импорта сверяют число строк, уникальность, ссылки, суммы и типы; потерянные строки находят через `EXCEPT` или `NOT EXISTS`.
- При экспорте ограничивают столбцы, выбирают разделитель и кодировку, проверяют файл повторным открытием.
- Сверка до и после импорта экономит часы разбирательства, а потерянная строка может обнаружиться слишком поздно.

::quiz
Q: Чем CSV отличается от JSON?
+ CSV хранит плоскую таблицу, JSON хранит дерево
- CSV хранит типы, JSON только текст
- JSON не поддерживает массивы
- CSV всегда использует точку с запятой
! CSV это строки и разделители, JSON это вложенные объекты и массивы.

Q: Что такое BOM в начале файла?
+ Служебные байты, которые могут попасть в имя первого столбца
- Первая строка с заголовками
- Команда импорта
- Признак конца файла
! BOM не виден в редакторе, но становится частью первого значения.

Q: Почему файл с точкой с запятой может попасть в один столбец?
+ Импорт ожидает другой разделитель
- База не поддерживает текст
- В файле нет заголовка
- Строки слишком длинные
! Разделитель должен совпадать с настройкой импорта.

Q: Зачем загружать CSV сначала в таблицу со столбцами TEXT?
+ Чтобы проверить и преобразовать значения до записи в целевые типы
- Чтобы ускорить импорт в два раза
- Чтобы автоматически создать индексы
- Чтобы база сама удалила дубли
! Промежуточная таблица сохраняет исходные значения без молчаливого преобразования.

Q: Какие утверждения о `CAST('42,5' AS REAL)` верны?
+ Результат равен 42.0
+ Запятая не является десятичным разделителем для SQLite
- Результат равен 42.5
- Запрос завершится ошибкой
! SQLite отбрасывает дробную часть после запятой, поэтому нужна замена запятой на точку.

Q: Какие значения проверяет `GLOB '????-??-??'`?
+ Дату в формате ГГГГ-ММ-ДД
- Телефон в формате +7
- Число с запятой
- Email с собакой
! Шаблон из четырёх цифр, дефиса, двух цифр, дефиса и двух цифр.

Q: Что делает `json_each`?
+ Разворачивает массив JSON в строки
- Создаёт таблицу в схеме
- Проверяет права доступа
- Преобразует JSON в CSV
! Функция возвращает по строке на каждый элемент массива.

Q: Как проверить, что JSON синтаксически корректен?
+ `json_valid(doc)`
- `json_extract(doc, '$')`
- `json_each(doc)`
- `typeof(doc)`
! json_valid возвращает 1 для правильного документа и 0 для повреждённого.

Q: Зачем после импорта сравнивать число строк источника и приёмника?
+ Чтобы найти потерянные или лишние строки
- Чтобы автоматически создать индекс
- Чтобы ускорить запросы
- Чтобы изменить кодировку
! Расхождение говорит о проблеме импорта.

Q: Что вернёт `EXCEPT`?
+ Строки первого результата, которых нет во втором
- Строки, которые есть в обоих результатах
- Все строки обоих результатов
- Только повторяющиеся строки
! EXCEPT показывает разницу множеств.

Q: Какие проблемы бывают при экспорте в CSV?
+ Потеря ведущих нулей
+ Формулы в ячейках
+ Неверная кодировка
- Автоматическое создание резервной копии
- Удаление всех индексов
! Excel может менять формат значений и выполнять формулы.

Q: Какие правила помогают сохранить данные при импорте?
+ Загружать в промежуточную таблицу TEXT
+ Проверять кодировку и разделитель
+ Сверять число строк после импорта
- Доверять автоматическому определению типов
- Открывать CSV в Excel перед импортом
! Проверка и промежуточная таблица снижают риск потери.

Q: Почему пустую строку и NULL нужно различать?
+ Запросы `IS NULL` находят только NULL
- NULL хранится как ноль
- Пустая строка не может быть в TEXT
- База удаляет пустые строки
! Разные значения требуют разных условий и дают разные отчёты.

Q: Какая функция SQLite проверяет корректность JSON?
= json_valid
= JSON_VALID
! json_valid возвращает 1 для правильного документа и 0 для повреждённого.

Q: Какой оператор SQL возвращает строки одного запроса, которых нет в другом?
= EXCEPT
= except
! EXCEPT сравнивает два набора строк и оставляет разницу.
