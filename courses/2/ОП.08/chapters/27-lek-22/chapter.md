## Пять отчётов и один запрос

В книжном магазине «Страница» есть отчёт по заказам. Он соединяет четыре таблицы: заказы, площадки, позиции заказа и книги, отбрасывает отменённые заказы и считает сумму каждой строки. Запрос занимает двадцать строк. Сначала его пишут для одного отчёта. Потом тот же расчёт нужен в отчёте по площадкам, в карточке клиента, в выгрузке для бухгалтерии и на дашборде руководителя.

Запрос копируют пять раз. Через месяц выясняется, что отменённые заказы нужно считать иначе: не исключать, а показывать отдельной строкой. Правку вносят в четыре копии, пятую забывают. Бухгалтерский отчёт расходится с дашбордом на сумму отменённых заказов, и никто не может объяснить, какая версия правильная.

**Представление это запрос, сохранённый в базе под именем.** Вместо пяти копий текста создают один объект `v_order_totals`, и все отчёты обращаются к нему как к таблице. Когда правило расчёта меняется, правят одно определение. Все, кто использует представление, получают новую версию автоматически.

Представление не хранит строки. Оно хранит только текст `SELECT` в системном каталоге. Это не копия данных, а правило их чтения. Каждый раз, когда к нему обращаются, база выполняет этот `SELECT` заново по текущим данным. Поэтому представление всегда показывает актуальное состояние таблиц, но не ускоряет тяжёлый запрос само по себе.

## Что именно сохраняется

Синтаксис создания простой.

```sql
CREATE VIEW v_order_totals AS
SELECT o.id AS order_id,
       o.order_date,
       s.name AS store_name,
       SUM(i.quantity * i.unit_price) AS total
FROM orders o
JOIN stores s ON s.id = o.store_id
JOIN order_items i ON i.order_id = o.id
WHERE o.status <> 'отменён'
GROUP BY o.id, o.order_date, s.name;
```

После выполнения в базе появляется объект с именем `v_order_totals`. Его можно использовать в `SELECT`, в `JOIN`, в `WHERE`, в других представлениях. С точки зрения внешнего запроса это таблица с четырьмя столбцами: `order_id`, `order_date`, `store_name`, `total`.

Проверим содержимое.

```sql
SELECT *
FROM v_order_totals
ORDER BY total DESC
LIMIT 3;
```

| order_id | order_date | store_name | total |
|---|---|---|---|
| 8 | 2026-09-10 | Страница на Арбате | 7530 |
| 5 | 2026-09-06 | Страница в Туле | 7120 |
| 19 | 2026-09-23 | Страница на Арбате | 5690 |

Представление вернуло три строки, но в базе нет таблицы с таким содержимым. Запрос к представлению был переписан в исходный `SELECT` с соединениями и группировкой. Строки вычислились в момент обращения.

Имена столбцов представления берутся из списка `SELECT`. Если столбец имеет псевдоним `total`, снаружи он тоже называется `total`. Можно задать имена явно:

```sql
DROP VIEW IF EXISTS v_order_totals;

CREATE VIEW v_order_totals (order_id, order_date, store_name, total) AS
SELECT o.id, o.order_date, s.name, SUM(i.quantity * i.unit_price)
FROM orders o
JOIN stores s ON s.id = o.store_id
JOIN order_items i ON i.order_id = o.id
WHERE o.status <> 'отменён'
GROUP BY o.id, o.order_date, s.name;
```

Явный список полезен, когда внутри запроса есть вычисляемые выражения без псевдонимов. Без него SQLite подставит текст выражения, и обращаться к такому столбцу снаружи будет неудобно.

Определение хранится в системном каталоге. Его можно увидеть запросом к `sqlite_master`.

```sql
SELECT name, type, sql
FROM sqlite_master
WHERE name = 'v_order_totals';
```

| name | type | sql |
|---|---|---|
| v_order_totals | view | CREATE VIEW v_order_totals AS SELECT ... |

В столбце `sql` лежит тот самый текст, который был выполнен. База не хранит отдельно список столбцов или план: при обращении она разбирает определение заново. Если определение ссылается на несуществующую таблицу, ошибка появится только в момент запроса, а не при создании представления. Это ещё одна причина проверять представление сразу после изменения схемы.

Представление можно создать заново только после удаления. Команда `CREATE VIEW` с существующим именем выдаст ошибку. Для замены используют `DROP VIEW v_order_totals;` и создают объект снова. В SQLite есть `CREATE VIEW IF NOT EXISTS`, но она не обновляет существующее определение, а просто ничего не делает. Поэтому в учебных скриптах чаще пишут `DROP VIEW IF EXISTS` перед созданием.

## Как выполняется запрос к представлению

База не хранит результат. При обращении к представлению планировщик разворачивает его определение и работает с базовыми таблицами. Это видно по плану запроса.

```sql
EXPLAIN QUERY PLAN
SELECT *
FROM v_order_totals
WHERE store_name = 'Страница в Туле';
```

Фрагмент плана:

```text
CO-ROUTINE v_order_totals
SCAN o
SEARCH s USING INTEGER PRIMARY KEY (rowid=?)
SEARCH i USING INDEX sqlite_autoindex_order_items_1 (order_id=?)
SCAN v_order_totals
```

В плане нет таблицы `v_order_totals` с данными. Есть шаг `CO-ROUTINE`, который выполняет внутренний запрос, и обращения к `orders`, `stores`, `order_items`. Представление исчезло, остались базовые таблицы.

Из этого следуют три практических вывода. Первый: представление не занимает места на диске, кроме текста определения. Второй: оно не кэширует результат, поэтому каждый запрос считает заново. Третий: условия внешнего запроса могут быть переданы внутрь, и база не обязана сначала строить все строки представления, а потом фильтровать. В примере выше условие по `store_name` попало в план, хотя оно написано снаружи.

Представление может ссылаться на другое представление.

```sql
CREATE VIEW v_store_revenue AS
SELECT store_name,
       SUM(total) AS revenue
FROM v_order_totals
GROUP BY store_name;
```

```sql
SELECT *
FROM v_store_revenue
ORDER BY revenue DESC;
```

| store_name | revenue |
|---|---|
| Страница на Арбате | 27680 |
| Страница в Туле | 18090 |
| Страница в Твери | 14170 |
| Страница в Калуге | 8420 |

Внешний запрос обращается к `v_store_revenue`, тот обращается к `v_order_totals`, а тот к трём таблицам. Цепочка работает, но каждый уровень добавляет сложность плану и человеку, который будет её читать. Два уровня представлений обычно достаточно. Пять уровней означают, что схему пора упрощать.

## Зачем нужны представления

Причины не сводятся к «короче писать». Представление решает пять разных задач, и полезно понимать, какую из них вы решаете.

| Задача | Что даёт представление |
|---|---|
| Скрыть сложность | отчёт пишет `SELECT * FROM v_order_totals`, а не четыре соединения |
| Собрать расчёт в одном месте | изменение правила происходит в одном объекте |
| Ограничить набор столбцов | снаружи видны только нужные поля |
| Дать стабильный интерфейс | приложение не зависит от переименования таблиц |
| Ограничить доступ | пользователю дают право на представление, а не на таблицу |

Первая причина экономит время чтения. Второй причиной пользуются, когда один и тот же расчёт повторяется в отчётах. Третья и пятая связаны с безопасностью: представление может показать только часть столбцов или только строки, относящиеся к площадке. Четвёртая помогает при изменении схемы: если таблицу разбили на две, представление может сохранить прежние имена и приложение продолжит работать.

Есть и причина, которой представления не служат. Это не средство ускорения. Если запрос внутри представления медленный, представление останется медленным. Иногда планировщик оптимизирует внешний запрос вместе с внутренним лучше, чем два отдельных запроса, но это побочный эффект, а не гарантия. Для ускорения нужны индексы, о них на следующем занятии.

Представление также не заменяет резервную копию и не фиксирует данные на момент создания. Оно всегда показывает текущие строки. Если нужен снимок состояния на первое число, создают отдельную таблицу и заполняют её, а не представление.

## Представление как договор с приложением

Приложение обращается к базе не ради красоты схемы. Ему нужны стабильные имена столбцов и понятный смысл значений. Пока приложение пишет `SELECT id, title, price FROM books`, любое переименование таблицы или разбиение её на две ломает код. Представление позволяет сохранить старый интерфейс, даже если внутри схема изменилась.

Предположим, таблицу `books` разделили на `books` и `book_prices`: название и автор остались в первой, цена переехала во вторую. Приложение по-прежнему хочет видеть столбцы `id`, `title`, `price`. Создаём представление с прежним именем.

```sql
CREATE VIEW v_books_catalog AS
SELECT b.id,
       b.title,
       p.price
FROM books b
JOIN book_prices p ON p.book_id = b.id;
```

Приложение меняет в запросе только имя таблицы на `v_books_catalog`, а остальной код остаётся прежним. Через полгода, когда все отчёты перейдут на новую схему, представление можно удалить. Так представление работает как переходный слой при миграции.

У этого договора есть цена. Представление становится частью интерфейса, и его изменение тоже ломает приложение. Нельзя молча переименовать столбец `price` в `retail_price`: снаружи это выглядит как исчезновение столбца. Если смысл значения меняется, лучше создать новое представление с новым именем, а старое оставить на время перехода.

Полезно фиксировать договор в документации: имя представления, назначение, список столбцов, единицы измерения, правила фильтрации. Тогда новый разработчик не будет гадать, входит ли отменённый заказ в `v_order_totals`. Ответ должен быть в описании, а не только в тексте `WHERE`.

## Обновляемость: главное ограничение

Представление выглядит как таблица, но изменять его можно не всегда. В SQLite представление по умолчанию доступно только для чтения. Попытка обновить его заканчивается ошибкой.

```sql
UPDATE v_order_totals
SET total = 0
WHERE order_id = 1;
```

```text
Error: cannot modify v_order_totals because it is a view
```

Причина в том, что представление содержит соединение и группировку. База не может однозначно определить, какую строку базовой таблицы нужно изменить. Сумма `total` вообще не хранится ни в одной таблице: она вычисляется из количества и цены. Записать новое значение суммы некуда.

В стандартном SQL представление считается обновляемым, если оно построено на одной таблице, не содержит `DISTINCT`, `GROUP BY`, `HAVING`, `UNION` и агрегатов, а ключ строки сохраняется. Даже при этих условиях разные СУБД ведут себя по-разному. MySQL разрешает обновлять простые представления, PostgreSQL тоже, а SQLite требует отдельного механизма.

Механизм называется `INSTEAD OF` триггер. Он срабатывает вместо операции над представлением и переводит её в операции над базовыми таблицами.

```sql
CREATE TRIGGER v_order_totals_update
INSTEAD OF UPDATE ON v_order_totals
BEGIN
  UPDATE orders
  SET order_date = NEW.order_date
  WHERE id = OLD.order_id;
END;
```

Теперь обновление проходит.

```sql
UPDATE v_order_totals
SET order_date = '2026-09-25'
WHERE order_id = 1;

SELECT id, order_date FROM orders WHERE id = 1;
```

| id | order_date |
|---|---|
| 1 | 2026-09-25 |

Триггер получил старую строку `OLD` и новую `NEW`, взял из них идентификатор заказа и дату, а затем обновил настоящую таблицу `orders`. Представление по-прежнему не хранит данные, но операция стала возможной.

Триггер не делает представление полностью обновляемым. В нём нужно явно описать каждую операцию: `INSERT`, `UPDATE`, `DELETE`. Если представление соединено из нескольких таблиц, придётся решать, в какую таблицу писать каждое поле. Для отчёта с суммой это обычно невозможно или бессмысленно. Поэтому правило простое: представления для чтения создают свободно, а представления для записи проектируют отдельно и осторожно.

Для `INSERT` триггер получает строку `NEW` и должен создать запись в базовой таблице. Для `DELETE` он получает `OLD` и удаляет соответствующую строку. Если представление объединяет заказ и позиции, одна вставка через представление может означать вставку в две таблицы, и триггер обязан выполнить обе операции. Ошибка в одной из них должна отменить всю операцию, поэтому триггер пишут так, чтобы он работал в одной транзакции.

В MySQL и PostgreSQL у обновляемых представлений есть `WITH CHECK OPTION`. Он запрещает вставлять строку, которая не попадёт в представление по условию `WHERE`. В SQLite этой опции нет. Если представление фильтрует строки, проверку приходится повторять в триггере или в приложении.

## Представления и права доступа

В MySQL и PostgreSQL представление может быть инструментом разграничения доступа. Пользователю дают право `SELECT` на представление и не дают прав на базовые таблицы. Тогда он видит только те столбцы и строки, которые описаны в представлении.

Например, представление для продавца может показывать книги без закупочной цены.

```sql
CREATE VIEW v_books_for_seller AS
SELECT id, title, price
FROM books;
```

Если у роли продавца есть право только на `v_books_for_seller`, закупочные столбцы ей недоступны. Представление с условием `WHERE store_id = 2` ограничивает продавца Тверью: он видит заказы своей площадки и не видит чужие.

У этого приёма есть граница. Представление не защищает данные, если у пользователя остаётся прямой доступ к таблице. Оно также не скрывает строки от того, кто может выполнить произвольный запрос к базовой таблице. Права на представление и права на таблицу настраивают вместе, а не вместо.

В SQLite полноценных `GRANT` и `REVOKE` нет. Доступ к базе определяется правами на файл, а внутри файла все подключившиеся видят все объекты. Поэтому в учебной работе представление служит удобством и единым расчётом, но не средством безопасности. Разграничение доступа подробно разберём в отдельном занятии.

В MySQL выдача права выглядит так.

```sql
CREATE USER 'seller'@'localhost' IDENTIFIED BY 'change_me';
GRANT SELECT ON shop.v_books_for_seller TO 'seller'@'localhost';
```

Права на таблицу `books` при этом не выдаются. Пользователь `seller` может читать представление, но не может обратиться к базовой таблице напрямую. Если представление построено с `SQL SECURITY DEFINER`, оно выполняется с правами создателя и может читать таблицу, к которой у продавца нет доступа. Это удобно, но требует аккуратности: ошибка в условии представления может открыть лишние строки.

Представление с фильтром по площадке ограничивает не столбцы, а строки.

```sql
CREATE VIEW v_orders_tula AS
SELECT o.id, o.order_date, o.status, c.name AS customer
FROM orders o
JOIN stores s ON s.id = o.store_id
JOIN customers c ON c.id = o.customer_id
WHERE s.city = 'Тула';
```

Продавец Тулы видит только заказы своей площадки. Но если у него есть прямой `SELECT` на `orders`, ограничение обходится одним запросом. Поэтому права выдают на представление, а прямой доступ к таблице закрывают.

Есть ещё одна тонкость. Представление не проверяет, что пользователь не может вывести скрытые данные через соединение. Если представление показывает имя клиента и сумму заказа, а базовая таблица клиентов доступна, пользователь соединит их сам. Защита строится на наборе прав, а не на одном объекте.

## Материализованные представления

Обычное представление вычисляется при каждом обращении. Если запрос тяжёлый, а данные меняются редко, возникает желание сохранить результат. Для этого в некоторых СУБД есть материализованное представление.

Оно хранит вычисленные строки на диске и обновляется по команде или по расписанию. PostgreSQL использует `REFRESH MATERIALIZED VIEW`, Oracle обновляет по расписанию, SQL Server поддерживает индексированные представления. В SQLite материализованных представлений нет. В MySQL их тоже нет встроенно: результат сохраняют в обычную таблицу и заполняют по расписанию или через триггеры.

| Свойство | Обычное представление | Материализованное |
|---|---|---|
| Хранит данные | нет | да |
| Актуальность | всегда текущие данные | на момент обновления |
| Скорость чтения | зависит от запроса | высокая |
| Стоимость записи | нет | нужно обновление |
| Поддержка в SQLite | да | нет |

Материализация это компромисс между свежестью и скоростью. Если отчёт строится раз в день, снимок на утро подходит. Если нужны данные за последнюю минуту, снимок врёт. В учебной базе «Страницы» объёмы небольшие, и обычного представления достаточно.

## Представление или общее табличное выражение

У представления есть близкий родственник: общее табличное выражение `WITH`. Оно тоже даёт имя запросу, но живёт только внутри одного выполнения.

```sql
WITH store_revenue AS (
  SELECT o.store_id, SUM(i.quantity * i.unit_price) AS revenue
  FROM orders o
  JOIN order_items i ON i.order_id = o.id
  WHERE o.status <> 'отменён'
  GROUP BY o.store_id
)
SELECT s.name, r.revenue
FROM stores s
JOIN store_revenue r ON r.store_id = s.id
ORDER BY r.revenue DESC;
```

Результат тот же, что у представления, но `store_revenue` существует только на время этого запроса. Другой запрос его не увидит, и в схеме базы он не появится.

| Признак | Представление | WITH |
|---|---|---|
| Живёт после запроса | да | нет |
| Видно другим пользователям | да | нет |
| Требует прав на создание | да | нет |
| Подходит для повторяющегося расчёта | да | нет |
| Подходит для одноразового отчёта | избыточно | да |

Выбор простой. Если расчёт нужен в нескольких отчётах и должен быть одинаковым, создают представление. Если расчёт нужен один раз внутри сложного запроса, используют `WITH`. Если нужен временный объект только для текущего подключения, в SQLite есть `CREATE TEMP VIEW`, но в учебных отчётах он почти не нужен.

`WITH` удобен и для проверки перед созданием представления. Сначала пишут запрос с `WITH`, смотрят результат и план, затем убирают обёртку и сохраняют внутренний запрос как представление. Так определение появляется уже проверенным.

## Типичные ошибки

**`SELECT *` внутри представления.** Представление фиксирует набор столбцов на момент создания. Если в базовую таблицу добавили столбец, снаружи он не появится. Если столбец переименовали или удалили, представление может сломаться. Лучше перечислять столбцы явно.

**`ORDER BY` внутри представления.** Порядок строк в представлении не гарантирован. База может переставить строки при соединении или группировке. Сортировку пишут во внешнем запросе, где она действительно нужна.

**Ожидание, что представление ускорит запрос.** Представление хранит текст, а не результат. Для скорости нужны индексы и продуманный запрос.

**Обновление представления без триггера.** В SQLite это ошибка `cannot modify ... because it is a view`. В MySQL простые представления обновляются, но соединение или агрегат делают их доступными только для чтения.

**Удаление базовой таблицы.** Представление остаётся в схеме, но при обращении выдаёт ошибку `no such table`. Перед изменением схемы проверяют зависимости.

**Одинаковое имя с таблицей.** В одной схеме не может быть таблицы и представления с одним именем. При миграции сначала удаляют старое представление, потом создают таблицу, иначе `CREATE TABLE` завершится ошибкой.

**Слишком длинная цепочка представлений.** Пять уровней вложенности усложняют план и затрудняют поиск ошибки. Если цепочка выросла, её упрощают или заменяют одним представлением с общим табличным выражением.

**Представление как замена правам.** Если пользователь может читать базовую таблицу, представление не скроет от него данные. Права настраивают на обоих уровнях.

**Удаление представления, от которого зависят другие.** Если `v_store_revenue` построено на `v_order_totals`, удаление нижнего представления ломает верхнее. SQLite не проверяет зависимости при `DROP VIEW`. Перед удалением находят все объекты, которые ссылаются на представление, и либо пересоздают их, либо сначала удаляют верхние уровни.

**Путаница между представлением и таблицей.** Новичок видит `SELECT * FROM v_order_totals` и считает, что это таблица с четырьмя столбцами. Он пытается добавить в неё индекс, изменить тип столбца или посмотреть размер на диске. Ничего из этого не работает: представление не имеет собственных строк и файлов. Индекс создают на базовой таблице, а размер смотрят у неё.

**Ожидание, что представление скроет медленный запрос.** Если внутри представления соединение без индекса, снаружи оно останется медленным. Более того, внешний фильтр не всегда передаётся внутрь так, как ожидает автор. Проверка плана обязательна.

**Неправильная единица измерения в столбце.** Представление может переименовать `price` в `total`, хотя внутри это цена за один экземпляр, а не сумма строки. Смысл столбца фиксируют в документации, иначе отчёт умножит цену на количество второй раз.

## Проверка перед публикацией

Представление кажется простым объектом, но ошибка в нём расходится по всем отчётам сразу. Перед тем как отдать его приложению, полезно пройти короткий список проверок.

1. Выполнить `SELECT * FROM v_order_totals LIMIT 5` и убедиться, что столбцы называются так, как ожидает отчёт.
2. Сравнить число строк представления с числом строк исходного запроса. Расхождение означает, что условие или соединение написано иначе.
3. Проверить дубли по ключу. Если представление должно возвращать одну строку на заказ, запрос `SELECT order_id, COUNT(*) ... GROUP BY order_id HAVING COUNT(*) > 1` должен вернуть пустой результат.
4. Посмотреть `EXPLAIN QUERY PLAN` и убедиться, что план обращается к нужным таблицам и индексам, а не сканирует всё подряд.
5. Попробовать обновить представление и убедиться, что поведение ожидаемое: либо ошибка, либо срабатывание триггера.
6. Проверить зависимости перед удалением или переименованием базовой таблицы.

Эти проверки ловят большинство ошибок, которые иначе всплывут в отчёте у директора. Представление это не «просто ещё один SELECT», а объект, от которого зависят другие запросы. Чем раньше проверено его поведение, тем дешевле исправление.

## Итоги

- Представление это именованный запрос в базе; строки он не хранит и вычисляется при обращении.
- `CREATE VIEW` сохраняет определение, `DROP VIEW` удаляет его, а для замены объект создают заново.
- Представление скрывает сложность, собирает расчёт в одном месте, ограничивает столбцы и даёт стабильный интерфейс.
- В SQLite представление по умолчанию только для чтения; запись возможна через `INSTEAD OF` триггер.
- Обновляемость в стандартном SQL ограничена одной таблицей и отсутствием агрегатов, `DISTINCT` и `GROUP BY`.
- Материализованное представление хранит результат, но требует обновления; в SQLite его нет.
- Представление не ускоряет запрос и не заменяет разграничение прав.
- Повторяющийся расчёт выносят в представление, одноразовый удобнее оформить через WITH.
