## Отчёт, который нельзя посчитать в уме

К концу месяца управляющая «Страницы» просит четыре числа. Сколько заказов приняла каждая площадка. Какую выручку она принесла. Каков средний чек. Какие категории дали больше всего продаж. В базе 60 заказов, 185 позиций и 4800 книг, и считать это вручную бессмысленно.

Предыдущие запросы возвращали по строке на каждую найденную запись. Для отчёта нужен другой результат: одна строка на площадку или на категорию, а внутри неё итог. Такую работу выполняют агрегатные функции вместе с группировкой.

**Агрегатная функция получает много значений и возвращает одно.** `COUNT` считает строки, `SUM` складывает, `AVG` находит среднее, `MIN` и `MAX` выбирают крайние значения. Без группировки агрегат сворачивает весь результат в одну строку. С `GROUP BY` он считает отдельно для каждой группы.

## Агрегатные функции

Начнём с самых простых вопросов. Сколько всего книг в каталоге:

```sql
SELECT COUNT(*) AS всего FROM книга;
```

```text
4800
```

`COUNT(*)` считает строки результата, независимо от того, что в них записано. Звёздочка здесь означает «строка целиком», а не «все столбцы».

`SUM` складывает числовой столбец. Цена хранится в копейках, поэтому выручку удобно сразу перевести в рубли:

```sql
SELECT ROUND(SUM(количество * цена_коп) / 100.0, 2) AS выручка
FROM позиция_заказа;
```

```text
412828.0
```

Выражение `количество * цена_коп` вычисляется для каждой позиции, затем значения складываются. Это и есть выручка по всем заказам в учебной базе: 412 828 рублей.

`AVG`, `MIN` и `MAX` работают по тому же принципу:

```sql
SELECT
  ROUND(AVG(цена_коп) / 100.0, 2) AS средняя,
  MIN(цена_коп) / 100.0 AS минимальная,
  MAX(цена_коп) / 100.0 AS максимальная
FROM книга;
```

| `средняя` | `минимальная` | `максимальная` |
|---|---|---|
| 690.07 | 180.0 | 2890.0 |

Средняя цена книги около 690 рублей, самая дешёвая стоит 180 рублей, самая дорогая 2890 рублей. `ROUND` не меняет значение в базе, а только формат вывода.

`COUNT`, `SUM`, `AVG`, `MIN` и `MAX` можно применять к выражению, а не только к столбцу. Например, средняя стоимость позиции заказа:

```sql
SELECT ROUND(AVG(количество * цена_коп) / 100.0, 2) AS средняя_позиция
FROM позиция_заказа;
```

Агрегат без `GROUP BY` всегда возвращает ровно одну строку. Даже если исходная таблица пуста, строка будет: `COUNT(*)` вернёт 0, а `SUM`, `AVG`, `MIN` и `MAX` вернут `NULL`. Это важно для отчётов: пустой месяц должен показать ноль, а не исчезнуть из результата.

```sql
SELECT
  COUNT(*) AS строк,
  SUM(цена_коп) AS сумма,
  TOTAL(цена_коп) AS итого,
  AVG(цена_коп) AS среднее
FROM книга
WHERE код_книги = -1;
```

| `строк` | `сумма` | `итого` | `среднее` |
|---|---|---|---|
| 0 |  | 0.0 |  |

`TOTAL` это вариант `SUM`, который возвращает 0.0 вместо `NULL` на пустом наборе. Он удобен, когда результат сразу попадает в расчёт или в отчёт, где пустая ячейка недопустима.

## COUNT и пустые значения

`COUNT(*)` считает все строки, а `COUNT(столбец)` считает только строки, где столбец не равен `NULL`.

```sql
SELECT
  COUNT(*) AS всего,
  COUNT(код_родителя) AS с_родителем
FROM категория;
```

| `всего` | `с_родителем` |
|---|---|
| 12 | 1 |

В справочнике двенадцать категорий, но только у одной указан родитель: «Подарочные издания» входит в художественную литературу. Разница в одиннадцать строк кажется мелочью, пока она не превращается в неверную иерархию каталога.

`COUNT(DISTINCT столбец)` считает уникальные непустые значения:

```sql
SELECT
  COUNT(*) AS всего,
  COUNT(DISTINCT код_категории) AS категорий
FROM книга;
```

| `всего` | `категорий` |
|---|---|
| 4800 | 12 |

`SUM` и `AVG` тоже игнорируют `NULL`. `AVG` делит сумму на число непустых значений, а не на общее число строк. Поэтому средняя цена книги считается по книгам с известной ценой, а не по всем строкам таблицы.

| Функция | Что делает с `NULL` | Пустой набор |
|---|---|---|
| `COUNT(*)` | считает строку | 0 |
| `COUNT(col)` | пропускает | 0 |
| `COUNT(DISTINCT col)` | пропускает | 0 |
| `SUM(col)` | пропускает | `NULL` |
| `TOTAL(col)` | пропускает | 0.0 |
| `AVG(col)` | пропускает | `NULL` |
| `MIN`, `MAX` | пропускают | `NULL` |

`SUM(DISTINCT col)` складывает уникальные значения. На количестве это даёт странный результат:

```sql
SELECT
  SUM(количество) AS всего,
  SUM(DISTINCT количество) AS только_разные
FROM позиция_заказа;
```

| `всего` | `только_разные` |
|---|---|
| 582 | 15 |

Первое число это сумма всех количеств, второе сумма чисел от 1 до 5, каждое по одному разу. `SUM(DISTINCT)` нужен редко, и применять его без понимания данных опасно.

### Агрегаты и типы

Тип результата зависит от типа аргумента. `SUM` над целым столбцом возвращает целое, `SUM` над вещественным возвращает вещественное. `AVG` всегда возвращает вещественное, даже если среднее оказалось целым.

```sql
SELECT
  SUM(количество) AS сумма_штук,
  AVG(количество) AS среднее,
  ROUND(AVG(количество), 2) AS округлённое
FROM позиция_заказа;
```

| `сумма_штук` | `среднее` | `округлённое` |
|---|---|---|
| 582 | 3.145945945945946 | 3.15 |

`SUM` вернул целое 582, `AVG` вернул длинную дробь. `ROUND` только меняет вывод, но не тип: значение остаётся вещественным.

Целочисленное деление может испортить процент. Если разделить сумму штук на число позиций, результат будет целым:

```sql
SELECT SUM(количество) / COUNT(*) AS среднее_нацело,
       SUM(количество) * 1.0 / COUNT(*) AS среднее_точно
FROM позиция_заказа;
```

| `среднее_нацело` | `среднее_точно` |
|---|---|
| 3 | 3.145945945945946 |

Умножение на `1.0` превращает числитель в вещественное число и заставляет SQLite выполнить деление точно. Тот же эффект даёт `CAST(SUM(количество) AS REAL)`. Ошибка особенно заметна при расчёте процентов: `20 / 60 * 100` даёт 0, а `20.0 / 60 * 100` даёт 33.33.

`SUM` больших целых может переполниться, если значения близки к пределу 64-битного целого. Для денег и количеств учебной базы это не проблема, но в реальных системах суммы хранят в целых копейках, чтобы избежать округления. При выводе в рублях делят на `100.0` и округляют: без этого в отчёте появятся значения вроде `412828.00000000006`.

## GROUP BY: итоги по группам

`GROUP BY` делит строки на группы по значению одного или нескольких столбцов и применяет агрегат к каждой группе.

У заказа нет прямого кода площадки: площадка определяется через сотрудника, который принял заказ. Поэтому группировка опирается на соединение:

```sql
SELECT п.название AS площадка, COUNT(*) AS заказов
FROM заказ з
JOIN сотрудник с ON с.табельный_номер = з.табельный_номер
JOIN площадка п ON п.код_площадки = с.код_площадки
GROUP BY п.код_площадки, п.название
ORDER BY п.код_площадки;
```

| `площадка` | `заказов` |
|---|---|
| Страница Москва | 15 |
| Страница Тверь | 15 |
| Страница Тула | 15 |
| Страница Калуга | 15 |

В учебной базе 60 заказов распределены по четырём площадкам поровну. В `GROUP BY` указаны и код, и название. Формально достаточно кода, потому что название зависит от него. Но явный список делает запрос понятным и совместимым с СУБД, которые требуют все неагрегированные столбцы в группировке.

Группировать можно по нескольким столбцам:

```sql
SELECT с.код_площадки, з.статус, COUNT(*) AS заказов
FROM заказ з
JOIN сотрудник с ON с.табельный_номер = з.табельный_номер
GROUP BY с.код_площадки, з.статус
ORDER BY с.код_площадки, з.статус
LIMIT 10;
```

| `код_площадки` | `статус` | `заказов` |
|---|---|---|
| 1 | выдан | 2 |
| 1 | новый | 4 |
| 1 | оплачен | 3 |
| 1 | отменён | 3 |
| 1 | собран | 3 |
| 2 | выдан | 3 |
| 2 | новый | 3 |
| 2 | оплачен | 3 |
| 2 | отменён | 3 |
| 2 | собран | 3 |

Каждая пара «площадка и статус» образует отдельную группу. Порядок столбцов в `GROUP BY` не влияет на результат, но влияет на читаемость.

Группировать можно по выражению. Месяц из даты извлекают через `substr` или `strftime`:

```sql
SELECT substr(дата_заказа, 1, 7) AS месяц, COUNT(*) AS заказов
FROM заказ
GROUP BY месяц
ORDER BY месяц;
```

| `месяц` | `заказов` |
|---|---|
| 2026-08 | 20 |
| 2026-09 | 20 |
| 2026-10 | 20 |

`strftime('%Y-%m', дата_заказа)` даёт тот же результат. `substr` работает с текстом и не проверяет формат даты, `strftime` понимает дату и вернёт `NULL`, если строка не похожа на дату. Для учебной базы с форматом `ГГГГ-ММ-ДД` подходят оба варианта.

`CASE` делит строки на сегменты по условию:

```sql
SELECT
  CASE
    WHEN цена_коп < 50000 THEN 'до 500'
    WHEN цена_коп < 100000 THEN '500-999'
    ELSE 'от 1000'
  END AS сегмент,
  COUNT(*) AS книг
FROM книга
GROUP BY сегмент
ORDER BY сегмент;
```

| `сегмент` | `книг` |
|---|---|
| 500-999 | 2370 |
| до 500 | 1495 |
| от 1000 | 935 |

Сегменты отсортированы по коду символов, а не по смыслу, поэтому «500-999» оказался первым. Если нужен порядок «до 500», «500-999», «от 1000», добавляют числовой ключ сортировки или сортируют по минимальной цене сегмента.

Главная ловушка `GROUP BY` это неагрегированный столбец, которого нет в группировке:

```sql
SELECT с.код_площадки, з.статус, COUNT(*) AS заказов
FROM заказ з
JOIN сотрудник с ON с.табельный_номер = з.табельный_номер
GROUP BY с.код_площадки;
```

SQLite вернёт по одной строке на площадку и подставит какой-то статус из группы:

| `код_площадки` | `статус` | `заказов` |
|---|---|---|
| 1 | новый | 15 |
| 2 | выдан | 15 |
| 3 | оплачен | 15 |
| 4 | отменён | 15 |

Статус выбран произвольно, потому что в группе их несколько. Стандарт SQL такой запрос запрещает, а SQLite разрешает как расширение. Полагаться на это нельзя: результат может измениться после обновления версии или добавления индекса. Если столбец нужен в результате, его добавляют в `GROUP BY` или оборачивают в агрегат.

### Группировка не сортирует

`GROUP BY` не обещает порядок групп. SQLite часто возвращает их в порядке возрастания ключа, потому что так устроен алгоритм, но это следствие реализации, а не правило языка. Если порядок важен, его задают явно:

```sql
SELECT п.название AS площадка, COUNT(*) AS заказов
FROM заказ з
JOIN сотрудник с ON с.табельный_номер = з.табельный_номер
JOIN площадка п ON п.код_площадки = с.код_площадки
GROUP BY п.код_площадки, п.название
ORDER BY заказов DESC, п.название;
```

Сортировка по агрегату ставит на первое место площадку с наибольшим числом заказов. Без `ORDER BY` тот же запрос может вернуть площадки в другом порядке после изменения плана.

`NULL` образует отдельную группу. Если в столбце группировки есть пустые значения, все они попадут в одну строку с `NULL`, а не исчезнут. Это отличается от `WHERE column = 'значение'`, который пустые значения отбрасывает. Для отчёта «сколько записей без категории» это как раз нужно, для отчёта «сколько записей по категориям» пустую группу иногда исключают условием `WHERE column IS NOT NULL`.

::gate Чем HAVING отличается от WHERE?

## HAVING: фильтр групп

`WHERE` фильтрует строки до группировки. `HAVING` фильтрует уже собранные группы после агрегатов.

```sql
SELECT
  к.код_категории,
  COUNT(*) AS книг,
  ROUND(AVG(к.цена_коп) / 100.0, 2) AS средняя
FROM книга к
GROUP BY к.код_категории
HAVING AVG(к.цена_коп) > 69000
ORDER BY средняя DESC;
```

| `код_категории` | `книг` | `средняя` |
|---|---|---|
| 11 | 386 | 701.45 |
| 10 | 407 | 698.37 |
| 4 | 403 | 696.39 |
| 7 | 401 | 696.01 |
| 12 | 375 | 694.34 |

В результат попали только те категории, где средняя цена выше 690 рублей. Условие применяется к каждой группе целиком, а не к отдельной книге. Если бы то же условие стояло в `WHERE`, база попыталась бы вычислить среднее для каждой строки и выдала ошибку `misuse of aggregate`.

| Вопрос | `WHERE` | `HAVING` |
|---|---|---|
| Что фильтрует | строки | группы |
| Когда выполняется | до `GROUP BY` | после `GROUP BY` |
| Какие условия допустимы | по столбцам и выражениям строки | по агрегатам и столбцам группировки |
| Пример | `WHERE статус = 'выдан'` | `HAVING COUNT(*) >= 3` |

Оба фильтра можно использовать в одном запросе:

```sql
SELECT п.название AS площадка, COUNT(*) AS выдано
FROM заказ з
JOIN сотрудник с ON с.табельный_номер = з.табельный_номер
JOIN площадка п ON п.код_площадки = с.код_площадки
WHERE з.статус = 'выдан'
GROUP BY п.код_площадки, п.название
HAVING COUNT(*) >= 3
ORDER BY выдано DESC;
```

`WHERE` оставляет только выданные заказы, `GROUP BY` собирает их по площадкам, `HAVING` убирает площадки, где выданных заказов меньше трёх. В учебной базе в результат попадают три площадки.

SQLite разрешает ссылаться на псевдоним агрегата в `HAVING`:

```sql
SELECT с.код_площадки, COUNT(*) AS n
FROM заказ з
JOIN сотрудник с ON с.табельный_номер = з.табельный_номер
GROUP BY с.код_площадки
HAVING n >= 15
ORDER BY n DESC;
```

Это удобно, но тоже расширение. В стандартном SQL псевдоним в `HAVING` недоступен, поэтому в переносимом запросе повторяют `COUNT(*)`.

`HAVING` без `GROUP BY` применяется ко всему результату как к одной группе:

```sql
SELECT COUNT(*) AS всего
FROM заказ
HAVING COUNT(*) > 100;
```

Запрос вернёт пустой результат, потому что 60 не больше 100. Это допустимый способ проверить условие на итог, но читается он хуже, чем `WHERE` с подзапросом.

::gate Почему сумма выручки после соединения может оказаться больше настоящей?

## Итоги по группам с соединением

Выручка по площадкам требует соединить заказы, их позиции, сотрудников и справочник площадок:

```sql
SELECT
  п.название AS площадка,
  COUNT(DISTINCT з.номер_заказа) AS заказов,
  ROUND(SUM(поз.количество * поз.цена_коп) / 100.0, 2) AS выручка
FROM заказ з
JOIN сотрудник с ON с.табельный_номер = з.табельный_номер
JOIN площадка п ON п.код_площадки = с.код_площадки
JOIN позиция_заказа поз ON поз.номер_заказа = з.номер_заказа
GROUP BY п.код_площадки, п.название
ORDER BY выручка DESC;
```

| `площадка` | `заказов` | `выручка` |
|---|---|---|
| Страница Калуга | 15 | 125435.0 |
| Страница Тула | 15 | 104580.0 |
| Страница Москва | 15 | 97142.0 |
| Страница Тверь | 15 | 85671.0 |

`COUNT(DISTINCT з.номер_заказа)` считает заказы, а не строки соединения. Без `DISTINCT` каждый заказ посчитался бы столько раз, сколько у него позиций, и число заказов выросло бы до 185. `SUM` при этом считает по строкам позиций, и размножения здесь нет, потому что каждая позиция соединяется с одним заказом и одной площадкой.

Если добавить второе соединение один-ко-многим, например со спецификацией поставки, строки размножатся и `SUM` завысится. Правило простое: в одном запросе не суммируют два независимых списка. Для двух итогов делают два запроса или два подзапроса.

Список площадок с числом заказов можно получить через левое соединение, чтобы сохранить площадку без заказов:

```sql
SELECT п.название AS площадка, COUNT(з.номер_заказа) AS заказов
FROM площадка п
LEFT JOIN сотрудник с ON с.код_площадки = п.код_площадки
LEFT JOIN заказ з ON з.табельный_номер = с.табельный_номер
GROUP BY п.код_площадки, п.название
ORDER BY заказов, п.код_площадки;
```

`COUNT(з.номер_заказа)` считает только непустые номера, поэтому площадка без заказов получит 0, а не 1. Если написать `COUNT(*)`, она получит 1, потому что левое соединение всё равно вернуло строку с `NULL`.

`FILTER` позволяет посчитать несколько итогов в одной строке:

```sql
SELECT
  п.название AS площадка,
  COUNT(*) AS всего,
  COUNT(*) FILTER (WHERE з.статус = 'выдан') AS выдано,
  COUNT(*) FILTER (WHERE з.статус = 'отменён') AS отменено
FROM заказ з
JOIN сотрудник с ON с.табельный_номер = з.табельный_номер
JOIN площадка п ON п.код_площадки = с.код_площадки
GROUP BY п.код_площадки, п.название
ORDER BY п.код_площадки;
```

| `площадка` | `всего` | `выдано` | `отменено` |
|---|---|---|---|
| Страница Москва | 15 | 2 | 3 |
| Страница Тверь | 15 | 3 | 3 |
| Страница Тула | 15 | 4 | 2 |
| Страница Калуга | 15 | 3 | 4 |

`FILTER` появился в SQLite 3.30. В более старых версиях то же самое записывают через `SUM(CASE WHEN ... THEN 1 ELSE 0 END)`. Оба варианта считают строки, удовлетворяющие условию, не выполняя отдельный запрос.

Сортировать результат можно по агрегату:

```sql
SELECT
  п.название AS площадка,
  SUM(поз.количество) AS экземпляров
FROM заказ з
JOIN сотрудник с ON с.табельный_номер = з.табельный_номер
JOIN площадка п ON п.код_площадки = с.код_площадки
JOIN позиция_заказа поз ON поз.номер_заказа = з.номер_заказа
GROUP BY п.код_площадки, п.название
ORDER BY экземпляров DESC
LIMIT 3;
```

| `площадка` | `экземпляров` |
|---|---|
| Страница Калуга | 171 |
| Страница Тула | 155 |
| Страница Москва | 137 |

Псевдоним агрегата в `ORDER BY` работает и в SQLite, и в большинстве СУБД. Сортировка по номеру столбца тоже возможна, но хуже читается.

## Проверка итогов

Итог по группам проверяют сложением. Сумма выручки по площадкам должна совпасть с общей выручкой по всем заказам:

```sql
SELECT ROUND(SUM(v) / 100.0, 2) AS итого_по_группам
FROM (
  SELECT SUM(поз.количество * поз.цена_коп) AS v
  FROM заказ з
  JOIN сотрудник с ON с.табельный_номер = з.табельный_номер
  JOIN позиция_заказа поз ON поз.номер_заказа = з.номер_заказа
  GROUP BY с.код_площадки
);
```

```text
412828.0
```

Если сумма по группам больше общего итога, где-то размножились строки. Если меньше, часть строк потерялась из-за внутреннего соединения или слишком узкого `WHERE`. Расхождение в копейках допустимо из-за округления, расхождение в рублях означает ошибку.

Число заказов проверяют независимым запросом:

```sql
SELECT COUNT(*) FROM заказ;
SELECT COUNT(DISTINCT номер_заказа) FROM позиция_заказа;
```

Первое число это все заказы, второе только те, у которых есть хотя бы одна позиция. Оба равны 60. Если второе меньше, существуют пустые заказы. Если в отчёте по площадкам сумма заказов не равна 60, значит, соединение или фильтр изменили набор.

Проверка занимает немного времени и спасает от отчёта, который выглядит правдоподобно, но завышен вдвое. Особенно внимательно смотрят на запросы, где рядом стоят `JOIN`, `GROUP BY` и `SUM`.

## Типичные ошибки

- **Агрегат в `WHERE`.** `WHERE COUNT(*) > 10` даёт ошибку. Для групп нужен `HAVING`.
- **`HAVING` вместо `WHERE`.** Условие по отдельной строке работает, но фильтрация идёт позже и медленнее.
- **Неагрегированный столбец вне `GROUP BY`.** SQLite подставит произвольное значение, стандарт SQL выдаст ошибку.
- **`COUNT(*)` вместо `COUNT(column)` после левого соединения.** Площадка без заказов получит 1 вместо 0.
- **`SUM` после двух соединений один-ко-многим.** Строки размножаются, итог завышается.
- **`AVG` по строкам с `NULL`.** Среднее считается по непустым значениям, и знаменатель может оказаться меньше ожидаемого.
- **Целочисленное деление при расчёте процентов.** `SUM(количество) / COUNT(*)` даст целое, если оба аргумента целые. Для дробного результата умножают на `1.0` или приводят к `REAL`.
- **Забытое деление на 100.0.** Цена в копейках попадает в отчёт как рубли, и сумма вырастает в сто раз.
- **Группировка по псевдониму в переносимом запросе.** SQLite разрешает, другие СУБД не всегда.
- **Пустой результат без агрегата.** Запрос без `GROUP BY` всегда возвращает строку, а с `GROUP BY` на пустом наборе не возвращает ничего. Для отчёта это разные вещи.

## Проверьте себя

> [!CHECK] Почему `SELECT с.код_площадки, з.статус, COUNT(*) FROM заказ з JOIN сотрудник с ON с.табельный_номер = з.табельный_номер GROUP BY с.код_площадки` показывает только один статус на площадку?
> В группе несколько статусов, и SQLite выбирает значение из произвольной строки. Это расширение SQLite, а не правило SQL. Чтобы увидеть все статусы, нужно `GROUP BY с.код_площадки, з.статус`; чтобы получить один итог по статусу, нужен агрегат вроде `MIN(з.статус)`.

> [!CHECK] В отчёте по площадкам `COUNT(*)` после левого соединения показал 16 заказов вместо 15. Что произошло?
> Левое соединение сохранило все строки левой таблицы. Если у площадки нет заказов, оно вернёт одну строку с `NULL`, и `COUNT(*)` посчитает её. Для подсчёта связанных записей используют `COUNT(з.номер_заказа)`, который пропускает `NULL`.

> [!CHECK] Почему выручка по площадкам выросла после добавления соединения с поставками?
> Заказы и поставки относятся к книгам как два независимых списка один-ко-многим. Соединение составило все пары, и каждая позиция заказа повторилась столько раз, сколько поставок у книги. Для двух итогов нужны отдельные запросы или подзапросы.

## Итоги

- Агрегатные функции сворачивают много строк в одно значение: `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`, `TOTAL`.
- `COUNT(*)` считает строки, `COUNT(column)` пропускает `NULL`, `COUNT(DISTINCT column)` считает уникальные значения.
- На пустом наборе `COUNT` даёт 0, `SUM` и `AVG` дают `NULL`, `TOTAL` даёт 0.0.
- `GROUP BY` задаёт группы, внутри которых считается агрегат.
- `WHERE` фильтрует строки до группировки, `HAVING` фильтрует готовые группы.
- После соединения проверяют число строк: размножение завышает `SUM` и искажает `COUNT`.
- `COUNT(DISTINCT)` и `COUNT(column)` защищают итог от размножения и пустых строк.
- Итог по группам сверяют с общим итогом и независимым подсчётом строк, иначе ошибка соединения останется незамеченной до публикации отчёта.

## Тест по лекции

::quiz
Q: Что делает агрегатная функция?
+ Сворачивает много значений в одно
- Возвращает одну строку таблицы
- Удаляет дубли
- Создаёт новую таблицу
! COUNT, SUM, AVG, MIN и MAX возвращают итог по набору строк.

Q: Что считает COUNT(*)?
+ Все строки результата
- Только строки без NULL
- Уникальные значения
- Число столбцов
! Звёздочка означает строку целиком, поэтому NULL не мешает.

Q: Чем COUNT(column) отличается от COUNT(*)?
+ Пропускает строки, где column равен NULL
- Считает только уникальные значения
- Работает быстрее любого другого COUNT
- Считает столбцы таблицы
! COUNT(column) учитывает только непустые значения.

Q: Что вернёт SUM на пустом наборе?
+ NULL
- 0
- 0.0
- Ошибку
! SUM возвращает NULL, а TOTAL возвращает 0.0.

Q: Что задаёт GROUP BY?
+ Группы, по которым считаются агрегаты
- Порядок строк результата
- Условие фильтрации строк
- Список столбцов результата
! GROUP BY делит строки на группы до вычисления агрегатов.

Q: Чем HAVING отличается от WHERE?
+ HAVING фильтрует группы после агрегатов
- HAVING фильтрует строки до группировки
- WHERE фильтрует группы
- Между ними нет разницы
! WHERE работает со строками, HAVING с готовыми группами.

Q: Где агрегатная функция запрещена?
+ В WHERE
- В списке SELECT
- В HAVING
- В ORDER BY
! В WHERE агрегат запрещён, потому что строки ещё не собраны в группы.

Q: Что произойдёт, если выбрать столбец, которого нет в GROUP BY?
+ SQLite подставит произвольное значение из группы
- SQLite всегда вернёт NULL
- Запрос всегда завершится ошибкой
- Столбец будет удалён
! Это расширение SQLite, стандарт SQL такой запрос запрещает.

Q: Почему после LEFT JOIN COUNT(*) может дать 1 вместо 0?
+ Левое соединение возвращает строку с NULL
- COUNT(*) не работает с NULL
- Заказ удаляется
- GROUP BY считает неправильно
! Строка с NULL существует, поэтому COUNT(*) её учитывает.

Q: Какие функции относятся к агрегатным?
+ COUNT
+ SUM
+ AVG
+ MAX
- ROUND
- COALESCE
! ROUND и COALESCE обрабатывают отдельные значения, а не набор строк.

Q: Что нужно проверить в отчёте с GROUP BY?
+ Все неагрегированные столбцы входят в GROUP BY
+ Условие по строкам стоит в WHERE
+ Условие по группам стоит в HAVING
+ Число строк после соединения не размножилось
- Агрегат стоит в WHERE
- Псевдоним используется вместо GROUP BY
! Эти проверки защищают от произвольных значений и завышенных итогов.

Q: Какие функции игнорируют NULL?
+ SUM
+ AVG
+ MIN
+ MAX
- COUNT(*)
- TOTAL
! COUNT(*) считает строки, а остальные работают с непустыми значениями.

Q: Что произойдёт при соединении двух списков один-ко-многим и SUM?
+ Строки размножатся
+ Итог завысится
+ Каждая позиция повторится несколько раз
+ Число заказов может вырасти
- SUM автоматически уберёт дубли
- JOIN запрещает агрегаты
! Каждая строка одной стороны соединяется с несколькими строками другой.

Q: Какая функция считает уникальные непустые значения?
= COUNT(DISTINCT)
= COUNT DISTINCT
! COUNT(DISTINCT column) пропускает NULL и повторяющиеся значения.

Q: Какое ключевое слово фильтрует группы после GROUP BY?
= HAVING
= having
! HAVING применяется к готовым группам и агрегатам.
::/gate
