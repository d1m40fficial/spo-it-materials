## Цель работы

Научиться переносить данные из файла обмена в таблицу базы так, чтобы после импорта можно было доказать: ни одна строка не потерялась, лишние не появились, а значения попали в столбцы нужного типа. Работа идёт на выгрузке заказчиков книжного магазина «Страница». Старая касса отдала файл JSON, в котором часть записей оформлена не так, как ждёт новая схема.

Итог работы это не только заполненная таблица. Нужен воспроизводимый скрипт загрузки и отчёт о сверке: сколько записей было в файле, сколько попало в промежуточную таблицу, сколько принято в основную, какие строки отклонены и почему.

## Краткие теоретические сведения

JSON хранит данные как вложенные объекты и массивы. Объект это набор пар «имя поля» и «значение» в фигурных скобках, массив это список значений в квадратных скобках. В выгрузке кассы верхний уровень это массив объектов: каждый объект описывает одного заказчика, а поля внутри имеют свои типы: число, строка, пустое значение `null`.

При переносе в таблицу сначала строят соответствие: поле JSON становится столбцом, объект становится строкой. Простое соответствие работает, пока файл плоский. Если внутри объекта лежит вложенный массив, например список телефонов, понадобится вторая таблица и связь один ко многим.

Промежуточная таблица снимает главную опасность импорта. Сырой текст файла сначала кладут в таблицу как есть, в один столбец, и только потом разбирают его запросами. Если разбор ошибочен, исходные данные остаются на месте, и загрузку можно повторить. Прямая вставка из файла в рабочую таблицу такой возможности не даёт: ошибка в одной строке отменяет всю команду, и по сообщению не видно, какая именно строка виновата.

Функция `json_each` разворачивает массив JSON в набор строк. Для массива объектов она возвращает по строке на объект, а сам объект доступен в служебном столбце `value`. Функция `json_extract` достаёт значение по пути вида `$.phone`. Путь начинается с `$`, точкой отделяется имя поля, а для вложенных объектов путь продолжается: `$.address.city`.

SQLite хранит значения в одном из пяти классов: `NULL`, `INTEGER`, `REAL`, `TEXT`, `BLOB`. Тип столбца задаёт не жёсткий запрет, а предпочтение, которое называется сродством типов. Число, вставленное в столбец `TEXT`, превратится в текст, а строка `'42'` в столбце `INTEGER` станет числом. Поэтому проверять типы нужно не по объявлению столбца, а функцией `typeof` после загрузки.

Пустая строка и `NULL` это разные вещи. Пустая строка занимает место и участвует в сравнениях, `NULL` означает отсутствие значения. При импорте пустые строки часто превращают в `NULL` функцией `nullif(trim(x), '')`, иначе условие `IS NULL` не найдёт ни одной записи.

Дата в SQLite хранится как текст в формате `ГГГГ-ММ-ДД`. Такой формат сравнивается и сортируется как строка, поэтому проверка шаблоном работает надёжно. Оператор `GLOB` сравнивает строку с шаблоном, где `[0-9]` означает одну цифру. Запись `'2025-03-05' GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'` даёт 1, а запись `'14.02.2025'` даёт 0.

Повторный запуск скрипта не должен ломать базу. Загрузка, которую можно выполнить дважды с тем же результатом, называется идемпотентной; в SQLite её дают условие `WHERE NOT EXISTS` или добавка `INSERT OR IGNORE`.

### Шаг 2. Создайте справочник площадок и таблицу заказчиков

Площадки ведутся отдельным справочником, иначе название города придётся повторять в каждой строке и однажды написать его иначе. Ниже требования к двум таблицам. Типы и ограничения выберите сами, имена столбцов возьмите из таблицы соответствия.

| Таблица | Столбец | Смысл | Обязательность |
|---|---|---|---|
| `site` | `site_id` | номер площадки | первичный ключ |
| `site` | `name` | название площадки | обязательно, без повторов |
| `customer` | `customer_id` | номер заказчика из файла | первичный ключ |
| `customer` | `full_name` | название или имя заказчика | обязательно |
| `customer` | `email` | почта | необязательно |
| `customer` | `phone` | телефон | необязательно |
| `customer` | `site_id` | ссылка на площадку | обязательно, внешний ключ |
| `customer` | `registered_at` | дата регистрации | обязательно |
| `customer` | `level` | уровень лояльности | обязательно, одно из трёх значений |
| `customer` | `source_row` | номер строки в файле | необязательно, для сверки |

Уровней три: `обычный`, `серебряный`, `золотой`. Ограничение `CHECK` должно отклонить любое другое значение. Не забудьте выполнить `PRAGMA foreign_keys = ON`, иначе SQLite не станет проверять внешний ключ, и ссылка на несуществующую площадку пройдёт молча.

Если таблица `customer` уже создана на прошлом занятии, не пересоздавайте её: добавьте недостающий столбец `source_row` через `ALTER TABLE customer ADD COLUMN source_row INTEGER` и переходите к следующему шагу.

### Шаг 3. Загрузите JSON в промежуточную таблицу

Создайте таблицу для сырого текста и положите в неё весь массив. Ниже пример на двух записях, чтобы увидеть механизм; затем выполните то же с полной выгрузкой из шага 1.

```sql
CREATE TABLE stage_customer (
  row_no  INTEGER PRIMARY KEY,
  payload TEXT NOT NULL
);

INSERT INTO stage_customer (payload)
SELECT value
FROM json_each('[{"id":1,"name":"ООО «Читатель»","site":"Москва"},{"id":2,"name":"ИП Соколова","site":"Тверь"}]');

SELECT row_no, payload FROM stage_customer;
```

Функция `json_each` вернула по строке на каждый объект, а `value` содержит объект целиком. Проверьте число строк промежуточной таблицы запросом `SELECT COUNT(*) FROM stage_customer` и сравните с числом объектов в файле. Если числа разошлись, массив разобран не полностью: скорее всего, при копировании потерялась квадратная скобка.

Строка JSON заключена в одинарные кавычки SQL, внутри неё стоят двойные кавычки JSON; апостроф в данных удваивают.

### Шаг 4. Разберите поля через json_extract

Посмотрите на сырые значения трёх первых строк.

```sql
SELECT row_no,
       json_extract(payload, '$.id')         AS customer_id,
       json_extract(payload, '$.name')       AS full_name,
       json_extract(payload, '$.site')       AS site_name,
       json_extract(payload, '$.registered') AS registered_at
FROM stage_customer
WHERE row_no <= 3;
```

Теперь постройте представление `stage_customer_flat`, в котором каждое поле станет отдельным столбцом. Приведение делайте сразу: `CAST(... AS INTEGER)` для номера, `trim(...)` для текста, `nullif(trim(...), '')` для почты. Так вы не перенесёте в рабочую таблицу лишние пробелы и пустые строки.

| Столбец представления | Откуда берётся | Приведение |
|---|---|---|
| `row_no` | номер строки промежуточной таблицы | без изменений |
| `customer_id` | `$.id` | `CAST(... AS INTEGER)` |
| `full_name` | `$.name` | `trim` |
| `email` | `$.email` | `trim`, затем `nullif` с пустой строкой |
| `phone` | `$.phone` | без `trim`, чтобы тип остался виден |
| `site_name` | `$.site` | без `trim`, чтобы увидеть лишний пробел |
| `registered_at` | `$.registered` | без изменений |
| `level` | `$.level` | `trim` |

Проверьте себя на двух записях: у заказчика с номером 5 в поле `site` есть лишний пробел, у заказчика с номером 3 почта пустая. После приведения первое значение должно совпасть с названием площадки, а второе стать `NULL`.

### Шаг 5. Найдите проблемные строки

До загрузки в рабочую таблицу выясните, какие строки нельзя принять без решения. Ниже заготовки запросов, допишите условия сами.

```sql
-- повторы номера заказчика
SELECT customer_id, COUNT(*) AS copies, MIN(row_no) AS first_row
FROM stage_customer_flat
GROUP BY customer_id
HAVING COUNT(*) > 1;

-- дата не в формате ГГГГ-ММ-ДД
SELECT row_no, customer_id, registered_at
FROM stage_customer_flat
WHERE registered_at NOT GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]';

-- площадка, которой нет в справочнике
SELECT f.row_no, f.customer_id, f.site_name

LEFT JOIN site s ON s.name = trim(f.site_name)

SELECT row_no, '[' || site_name || ']' AS site_name
```

### Шаг 6. Загрузите очищенные строки

Загрузка идёт из плоского представления в рабочую таблицу. Ниже скелет с рабочим примером соединения; условия отбора допишите по находкам шага 5.

```sql
INSERT INTO customer (customer_id, full_name, email, phone, site_id, registered_at, level, source_row)
SELECT f.customer_id,
       f.full_name,
       f.email,
       f.phone,
       s.site_id,
       f.registered_at,
       trim(f.level),
       f.row_no
FROM stage_customer_flat f
JOIN site s ON s.name = trim(f.site_name)
WHERE 1 = 1
  -- здесь условие корректной даты
  -- здесь условие выбора одной строки из повторов
ORDER BY f.row_no;
```

Поясним два места. Соединение с `site` заодно отбрасывает площадки, которых нет в справочнике: без пары строка не попадёт в результат. Условие выбора одной строки из повторов удобно записать подзапросом с `MIN(row_no)`: остаётся первая по порядку запись, а поздняя копия считается отклонённой.

Значение уровня приведите к нижнему регистру. Встроенная функция `lower` в SQLite работает только с латинскими буквами, поэтому для русского текста она бесполезна: `lower('Золотой')` вернёт `'Золотой'`. Используйте `CASE` или явную замену, иначе ограничение `CHECK` отклонит корректную по смыслу строку.

### Шаг 7. Сверьте число строк до и после

Соберите три числа одним запросом и запишите их в отчёт.

```sql
SELECT (SELECT COUNT(*) FROM stage_customer)      AS in_file,
       (SELECT COUNT(*) FROM customer)             AS in_table,
       (SELECT COUNT(*) FROM stage_customer)
     - (SELECT COUNT(*) FROM customer)             AS rejected;
```

Третье число само по себе ничего не доказывает. Нужен список отклонённых строк с причиной. Такой запрос находит строки файла, которые не попали в таблицу, по служебному столбцу `source_row`.

```sql
SELECT f.row_no, f.customer_id, f.full_name, f.site_name, f.registered_at
FROM stage_customer_flat f
WHERE f.row_no NOT IN (SELECT source_row FROM customer WHERE source_row IS NOT NULL);
```

Проверьте, что каждая строка из этого списка объяснена в таблице находок. Если в списке оказалась строка, которую вы не собирались отклонять, ошибка в условии загрузки, а не в данных.

### Шаг 8. Проверьте типы и ограничения

Убедитесь, что значения попали в столбцы нужного класса, а ограничения работают.

```sql
SELECT typeof(customer_id)   AS id_type,
       typeof(full_name)     AS name_type,
       typeof(email)         AS email_type,
       typeof(phone)         AS phone_type,
       typeof(registered_at) AS date_type
FROM customer
LIMIT 1;
```

Затем попробуйте нарушить каждое ограничение отдельной командой и запишите текст отказа: уровень вне списка, ссылка на несуществующую площадку, повтор номера заказчика. Отказ это доказательство, что ограничение включено. Если команда прошла, ограничение не создано или внешние ключи выключены.

### Шаг 9. Повторите загрузку без дублей

Выполните скрипт загрузки второй раз. Первичный ключ не даст вставить те же номера, и появится ошибка `UNIQUE constraint failed`. Это ожидаемое поведение, но скрипт должен быть пригоден для повторного запуска.

Перепишите вставку так, чтобы повтор не вызывал ошибку и не менял результат. Достаточно добавить условие, которое пропускает уже загруженные номера. После правки выполните скрипт дважды и покажите, что число строк не изменилось.

Скрипт загрузки приводится в отчёте полностью, с комментариями к каждому этапу. Таблицы нумеруются, название ставится под таблицей.

## Что сдать

- заполненную таблицу соответствия полей JSON и столбцов;
- SQL-скрипт создания таблиц, разбора и загрузки, который выполняется без ошибок при повторном запуске;
- список находок с решением по каждой проблемной строке;
- таблицу сверки с числом строк в файле, промежуточной и рабочей таблице;
- отчёт Word с текстами отказов ограничений и выводом.

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

- **5**: соответствие полей заполнено полностью, таблицы созданы со всеми ограничениями, загрузка идёт через промежуточную таблицу, все проблемные строки найдены и объяснены, числа сверки сходятся, повторный запуск не меняет результат, отчёт оформлен по шаблону.
- **4**: работа выполнена, но одна проблемная строка пропущена или повторный запуск приводит к ошибке, хотя данные не портятся.
- **3**: загрузка выполнена, однако промежуточная таблица не использована, сверка ограничена подсчётом строк без списка отклонённых, типы проверены только по объявлению столбцов.
- **2**: работа не выполнена.
- **1**: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
