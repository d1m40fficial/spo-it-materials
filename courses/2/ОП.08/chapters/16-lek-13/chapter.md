## Чек, который не сходится на копейку

В «Странице» три книги стоят 19,99, 5,01 и 0,10 рубля. Кассир складывает их в уме и получает 25,10. База складывает те же числа и выдаёт 25,099999999999998. Разница в две тысячные копейки выглядит смешной, но в отчёте за месяц она превращается в расхождение, которое бухгалтер не примет.

Причина не в ошибке запроса. Числа с плавающей точкой хранят приближение, а не точное десятичное значение. Двоичная дробь не может точно представить 0,1 так же, как десятичная не может точно представить одну треть. Поэтому `0.1 + 0.2` в SQLite не равно `0.3`, и это не дефект конкретной СУБД.

**Тип данных это обещание, какие значения столбец принимает и как СУБД будет их сравнивать, складывать и хранить.** Обещание влияет не только на размер файла. Оно определяет, найдёт ли запрос строку, получится ли сумма, сохранится ли ведущий ноль в артикуле и можно ли сравнить две даты.

SQLite отличается от многих СУБД тем, что проверяет типы мягко. В столбец, объявленный целым, можно вставить текст, и ошибки не будет. Это удобно для обучения и опасно для рабочей базы: часть ошибок видна только в результате запроса. Поэтому тип выбирают осознанно, а не «на глаз».

## Пять классов хранения

В SQLite есть пять классов хранения: `NULL`, `INTEGER`, `REAL`, `TEXT` и `BLOB`. Класс хранения это то, как значение реально лежит в файле. Объявленный тип столбца задаёт не класс, а сродство, по-английски affinity: правило, к какому классу приводить вставленное значение.

| Объявленный тип | Сродство | Что происходит при вставке |
|---|---|---|
| `INTEGER`, `INT`, `BIGINT` | INTEGER | текст, похожий на целое, становится целым |
| `REAL`, `DOUBLE`, `FLOAT` | REAL | целое превращается в вещественное |
| `TEXT`, `VARCHAR(50)`, `CHAR` | TEXT | число превращается в текст |
| `NUMERIC`, `DECIMAL`, `DATE`, `BOOLEAN` | NUMERIC | числовой текст становится числом, если это возможно |
| `BLOB` или тип не указан | BLOB | значение хранится как есть |

Проверим на практике. Создадим таблицу с четырьмя разными объявлениями и вставим в неё текстовые значения.

```sql
CREATE TABLE проба (
  a INTEGER,
  b TEXT,
  c REAL,
  d NUMERIC
);
INSERT INTO проба VALUES ('10', 10, '3.5', '007');
SELECT a, typeof(a), b, typeof(b), c, typeof(c), d, typeof(d) FROM проба;
```

Результат в SQLite:

```text
10 | integer | 10 | text | 3.5 | real | 7 | integer
```

Столбец `a` получил целое 10, потому что сродство INTEGER распознало числовой текст. Столбец `b` сохранил текст, потому что у него сродство TEXT. Столбец `c` стал вещественным. Столбец `d` с сродством NUMERIC превратил `'007'` в целое 7 и потерял ведущие нули.

Этот пример объясняет половину ошибок начинающих. Объявили `VARCHAR(20)` для артикула, вставили `007`, а потом удивляются, что поиск по `'007'` ничего не находит. Хорошо, что здесь сродство TEXT и нули сохранились. А если бы столбец был `NUMERIC`, артикул превратился бы в 7.

Класс хранения можно узнать функцией `typeof()`. Она возвращает строку `null`, `integer`, `real`, `text` или `blob`. Это первый инструмент проверки после загрузки данных: пройдите по столбцам и посмотрите, совпадает ли фактический класс с ожидаемым.

Начиная с версии 3.37 SQLite поддерживает строгие таблицы. Команда `CREATE TABLE ... STRICT` запрещает хранить значение неподходящего класса: в целый столбец нельзя вставить текст, а в текстовый число. Для рабочей базы это полезная защита, но в учебных заданиях обычная таблица удобнее, потому что не мешает показать приведение типов. Если база создаётся надолго, строгий режим стоит рассмотреть отдельно.

## Целые числа

`INTEGER` подходит для идентификаторов, количества, года издания и денег в минимальных единицах. Целое занимает от 1 до 8 байт в зависимости от величины: число 1 хранится одним байтом, миллион семью. Для учебной базы с 4800 книгами и 120 сотрудниками это не имеет решающего значения, но для миллионов строк экономия заметна.

Первичный ключ удобно объявлять как `INTEGER PRIMARY KEY`. В SQLite такой столбец становится псевдонимом встроенного номера строки и заполняется автоматически, если не указан. Это не то же самое, что `AUTOINCREMENT`: автоматическое заполнение работает и без ключевого слова, а `AUTOINCREMENT` лишь запрещает повторно использовать удалённые номера. Для учебных таблиц достаточно `INTEGER PRIMARY KEY`.

Деньги в целом виде хранят в копейках. Цена 1540 рублей записывается как 154000. Сумма трёх позиций считается точно, без двоичных дробей. При выводе значение делят на 100 и форматируют.

```sql
CREATE TABLE позиция (
  номер_заказа INTEGER NOT NULL,
  код_книги INTEGER NOT NULL,
  количество INTEGER NOT NULL,
  цена_коп INTEGER NOT NULL
);
INSERT INTO позиция VALUES (1001, 204, 2, 154000), (1001, 318, 1, 98000);
SELECT номер_заказа, SUM(количество * цена_коп) AS сумма_коп
FROM позиция
GROUP BY номер_заказа;
```

Результат: `1001 | 406000`. Это ровно 4060 рублей, без приближения. Такой подход принят в платёжных системах и в бухгалтерском учёте, где копейка должна сходиться.

Количество тоже целое. Дробное количество книг не имеет смысла, а ограничение `CHECK (количество > 0)` защищает от нуля и минуса. Год издания можно хранить целым, но для арифметики дат лучше подходит дата, об этом ниже.

## Вещественные числа и их предел

`REAL` хранит число с плавающей точкой двойной точности, 8 байт. Он подходит для измерений, где важна скорость и не нужна абсолютная точность: вес посылки, расстояние, коэффициент скидки, средняя оценка. Он не подходит для денег и для любых величин, которые должны совпасть при сравнении.

```sql
SELECT 0.1 + 0.2, 0.1 + 0.2 = 0.3;
```

Результат: `0.30000000000000004 | 0`. Сумма не равна ожидаемому значению, и условие `= 0.3` не найдёт строку. Если сравнивать вещественные числа, сравнивают с допуском: `ABS(x - 0.3) < 0.000001`, а не на равенство.

Сумма текстовых значений, похожих на числа, тоже даёт приближение:

```sql
CREATE TABLE цена (p TEXT);
INSERT INTO цена VALUES ('19.99'), ('5.01'), ('0.10');
SELECT SUM(p), typeof(SUM(p)) FROM цена;
```

Результат: `25.099999999999998 | real`. SQLite применил числовое преобразование, но точность уже потеряна. Именно этот случай открывает лекцию.

Есть ещё одна тонкость. `REAL` не хранит десятичную дробь, а хранит ближайшую двоичную. При выводе SQLite показывает кратчайшее представление, которое восстанавливает то же двоичное значение, поэтому 0,1 выглядит как 0.1, хотя внутри это не ровно 0,1. Сравнение с литералом 0.1 работает, потому что литерал получает то же приближение, а вот арифметика накапливает расхождение.

| Величина | Тип | Почему |
|---|---|---|
| Цена книги | INTEGER в копейках | нужна точная сумма |
| Скидка 5 процентов | INTEGER или REAL | хранится как процент, не как деньги |
| Вес посылки | REAL | измерение, точность до грамма |
| Средний чек | REAL при выводе | вычисляемое значение, не хранится |
| Количество экземпляров | INTEGER | целое по смыслу |

Правило простое: если значение когда-нибудь сравнивают на равенство или суммируют как деньги, используют целое. Если это измерение с допуском, используют вещественное. Для процентов скидки хватает целого числа от 0 до 100, а для коэффициента 0,125 уже нужен `REAL` или хранение в тысячных долях целым.

Объявление `DECIMAL(10, 2)` не спасает от приближения. В SQLite такой столбец получает сродство NUMERIC и хранит значение как целое или вещественное, но не как точную десятичную дробь с фиксированной запятой. Поэтому `DECIMAL` удобен для чтения схемы, но не гарантирует бухгалтерскую точность. Если точность важна, используют целые копейки, а формат с двумя знаками задают при выводе.

::gate Какой тип выбрать для ISBN, телефона и даты?

## Текст

`TEXT` хранит строку в кодировке базы, обычно UTF-8. В SQLite объявление `VARCHAR(50)` не ограничивает длину: это сродство TEXT, а число в скобках игнорируется. Ограничение длины задают через `CHECK (length(поле) <= 50)`, если оно действительно нужно.

Текст выбирают для названий, имён, адресов, телефонов, ISBN, артикулов и любых кодов, у которых есть ведущие нули или буквы. ISBN это текст, хотя выглядит как число: дефисы, контрольная цифра X и ведущие нули входят в значение. Телефон тоже текст: плюс, пробелы и скобки являются частью формата.

```sql
CREATE TABLE книга (
  код_книги INTEGER PRIMARY KEY,
  isbn TEXT NOT NULL UNIQUE,
  название TEXT NOT NULL,
  год_издания INTEGER
);
INSERT INTO книга VALUES (204, '978-5-17-118245-7', 'Тихий Дон', 1928);
SELECT isbn, typeof(isbn), length(isbn) FROM книга;
```

Результат: `978-5-17-118245-7 | text | 17`. Длина считается в символах, а не в байтах, поэтому кириллица не удваивает значение.

Для поиска без учёта регистра в SQLite применяют `COLLATE NOCASE`, но она работает только для латиницы. Русские буквы `NOCASE` не складывает, поэтому регистр приводят функцией `LOWER()` или хранят отдельное поле для поиска. Это ограничение SQLite, а не SQL вообще.

## Дата и время

В SQLite нет отдельного класса хранения для даты. Дату хранят одним из трёх способов: текстом в формате ISO 8601, целым числом секунд или миллисекунд с начала эпохи, либо числом дней по юлианскому календарю. Для учебных баз удобнее текст `YYYY-MM-DD`: он читается глазами и правильно сравнивается как строка.

```sql
CREATE TABLE поставка (
  номер_поставки INTEGER PRIMARY KEY,
  дата_поставки TEXT NOT NULL
);
INSERT INTO поставка VALUES (1, '2026-11-05'), (2, '05.11.2026'), (3, '2026-03-09');
SELECT дата_поставки FROM поставка
WHERE дата_поставки >= '2026-01-01'
ORDER BY дата_поставки;
```

Результат: `2026-03-09` и `2026-11-05`. Строка `05.11.2026` в выборку не попала, потому что начинается с нуля и при сравнении строк оказалась меньше `2026-01-01`. Формат `ДД.ММ.ГГГГ` удобен человеку, но ломает сортировку и сравнение.

С форматом ISO работают встроенные функции. `date('2026-11-05', '+1 month')` вернёт `2026-12-05`, а разница в днях считается через `julianday`.

```sql
SELECT date('2026-11-05', '+1 month') AS через_месяц,
       julianday('2026-11-05') - julianday('2026-10-05') AS дней;
```

Результат: `2026-12-05 | 31.0`. Обратите внимание на округление календаря: `date('2026-01-31', '+1 month')` возвращает `2026-03-03`, потому что 31 февраля не существует. Арифметика месяцев в SQLite не переносит дату на последний день месяца автоматически.

Дату и время лучше хранить с указанием часового пояса, если система работает в нескольких городах. У «Страницы» четыре площадки в одном часовом поясе, поэтому достаточно `YYYY-MM-DD` и `YYYY-MM-DD HH:MM:SS` без смещения. Для учебной базы этого хватает.

Если нужен момент создания записи, используют `DEFAULT CURRENT_TIMESTAMP`. SQLite подставляет время в UTC, а не в местное. Для журнала операций это правильный выбор: часовой пояс сервера может измениться, а UTC остаётся точкой отсчёта. Для отчёта по площадке время переводят в местное уже при выводе, а не при хранении. Время с точностью до минуты записывают как `YYYY-MM-DD HH:MM`, и такой текст тоже сравнивается правильно.

## Логические значения и двоичные данные

Отдельного логического типа в SQLite нет. `TRUE` и `FALSE` это псевдонимы чисел 1 и 0, а `typeof(TRUE)` возвращает `integer`. Логическое поле объявляют как `INTEGER` с ограничением `CHECK (поле IN (0, 1))`, а не как `BOOLEAN`, чтобы сродство было предсказуемым. Если вставить в такое поле строку `'да'`, ограничение не пропустит значение, и это лучше, чем молчаливое приведение.

```sql
CREATE TABLE книга (
  код_книги INTEGER PRIMARY KEY,
  в_продаже INTEGER NOT NULL DEFAULT 1 CHECK (в_продаже IN (0, 1))
);
```

`BLOB` хранит произвольные байты: изображения, архивы, PDF. В учебной базе он не нужен: обложки и сканы лучше хранить файлами, а в таблице держать путь или имя файла. Большой `BLOB` замедляет выборку и резервное копирование, а работать с ним в sqliteonline неудобно.

`NULL` означает отсутствие значения, а не ноль и не пустую строку. `NULL` не равен сам себе, поэтому проверка пишется через `IS NULL`, а не `= NULL`. Для внешнего ключа `NULL` означает необязательную связь, и это допустимо, если по смыслу сотрудник может быть не распределён на площадку.

::gate Как тип столбца влияет на сравнение и сумму?

## Типы для учебной «Страницы»

Соберём решения в таблицу. Она пригодится на практике, когда будем писать `CREATE TABLE`.

| Столбец | Тип | Ограничение | Почему |
|---|---|---|---|
| код книги | INTEGER | PRIMARY KEY | суррогатный ключ |
| ISBN | TEXT | UNIQUE, NOT NULL | дефисы и ведущие нули |
| название | TEXT | NOT NULL | строка |
| год издания | INTEGER | CHECK между 1500 и 2100 | целый год |
| цена | INTEGER | CHECK > 0 | копейки, точная сумма |
| количество | INTEGER | CHECK > 0 | целое по смыслу |
| дата заказа | TEXT | NOT NULL | ISO 8601 |
| телефон | TEXT | NOT NULL | формат с плюсом |
| в продаже | INTEGER | DEFAULT 1, CHECK 0 или 1 | логическое значение |
| комментарий | TEXT | без ограничения | может отсутствовать |

Для 4800 книг разница в размере между `INTEGER` и `TEXT` для цены составляет десятки килобайт, то есть ничто. Выбор делается не ради экономии места, а ради правильной арифметики. Это важный поворот мысли: тип выбирают по операциям, которые будут выполняться, а не по внешнему виду значения.

Оценим порядок величин. Одна строка каталога с целым кодом, ISBN из 17 символов, названием из 40 символов и несколькими числами занимает около 150 байт. Умножим на 4800 и получим примерно 720 килобайт без учёта индексов. База из десятков тысяч строк всё ещё помещается в несколько мегабайт и свободно открывается в браузере. Поэтому на учебных объёмах экономить байты бессмысленно, а вот точность суммы и правильная сортировка важны каждый день.

## Приведение типов и сравнение

Приведение бывает явным и неявным. Явное выполняет функция `CAST`, неявное СУБД делает сама при сравнении или арифметике. `CAST('12abc' AS INTEGER)` вернёт 12: SQLite читает числовой префикс и останавливается на первой букве. `CAST('abc' AS INTEGER)` вернёт 0. `CAST(12.9 AS INTEGER)` вернёт 12, то есть отбрасывает дробную часть, а не округляет.

```sql
SELECT CAST('12abc' AS INTEGER), CAST('abc' AS INTEGER), CAST(12.9 AS INTEGER);
```

Результат: `12 | 0 | 12`. Молчаливое превращение текста в ноль опасно: опечатка в номере заказа не вызовет ошибку, а создаст строку с нулевым ключом. Поэтому в рабочей базе типы проверяют до вставки, а не после.

При выводе денег из копеек делят на 100 и форматируют. `printf('%.2f', сумма_коп / 100.0)` вернёт строку с двумя знаками после точки, а не `25.1`. Для отчёта это удобнее, чем ручное округление, потому что формат задаётся один раз в запросе.

Сравнение значений разных классов подчиняется порядку: `NULL` меньше чисел, числа меньше текста, текст меньше `BLOB`. Поэтому `'10' = 10` возвращает 0, если оба значения литералы без сродства столбца. Но в столбце с INTEGER сродством сравнение с `'10'` уже сработает, потому что СУБД приведёт текст к числу.

```sql
CREATE TABLE т (a INTEGER, b TEXT);
INSERT INTO т VALUES ('10', '10');
SELECT a = '10', b = 10, a = 10, b = '10' FROM т;
```

Результат: `1 | 1 | 1 | 1`. Все четыре сравнения истинны, потому что сродство столбца приводит операнд к своему классу. Без сродства, на литералах, результат был бы другим. Это и есть главная ловушка: одно и то же выражение ведёт себя по-разному в зависимости от объявления столбца.

Сортировка смешанного столбца тоже выдаёт странный порядок. Если в одном столбце лежат числа и текст, сначала идут числа по возрастанию, затем текст по алфавиту. Число 10 окажется раньше текста `'9'`, потому что число как класс меньше текста, а не потому, что 10 меньше 9.

## Типичные ошибки

**Цена в REAL.** Сумма из сотни чеков даёт хвост из цифр, а сравнение с эталоном не срабатывает. Лечится хранением в копейках и делением на 100 только при выводе. Проверить себя просто: если в отчёте появилось число с длинной дробной частью, где ожидались деньги, тип выбран неверно.

**Артикул в INTEGER.** Ведущие нули исчезают, а артикул `0012` превращается в 12. Если код состоит из цифр, это не значит, что он числовой.

**Дата в формате ДД.ММ.ГГГГ.** Сортировка ставит май раньше января, а условие «после 1 марта» отбрасывает часть строк. Лечится форматом ISO 8601.

**Телефон в INTEGER.** Плюс и ведущий ноль не помещаются в число, а длина номера превышает точное представление. Телефон это всегда текст.

**Надежда на VARCHAR(50).** SQLite не ограничивает длину по объявлению. Нужно ограничение `CHECK (length(поле) <= 50)`.

**Сравнение NULL через равенство.** `WHERE телефон = NULL` не находит ничего, потому что сравнение с NULL даёт неизвестность. Нужно `IS NULL`.

**Неявное приведение вместо проверки.** Текст, попавший в числовой столбец, может стать нулём без ошибки. После загрузки данных проверяют `typeof()` по каждому столбцу и сверяют диапазоны.

**Хранение файлов в BLOB без необходимости.** База растёт, копирование замедляется, а sqliteonline неудобно показывает такие значения. Для учебного проекта достаточно пути к файлу.

## Итоги

- В SQLite пять классов хранения: `NULL`, `INTEGER`, `REAL`, `TEXT`, `BLOB`, а объявленный тип задаёт сродство столбца.
- `INTEGER` подходит для ключей, количества и денег в копейках, `REAL` для измерений с допуском.
- `TEXT` хранит ISBN, телефоны, артикулы и названия; длина в `VARCHAR(n)` не проверяется.
- Дату хранят текстом ISO 8601 или числом, но не в формате `ДД.ММ.ГГГГ`, если нужна сортировка.
- Логическое значение это `INTEGER` 0 или 1 с ограничением `CHECK`.
- Неявное приведение может превратить текст в ноль без ошибки, поэтому фактические классы проверяют через `typeof()`.
- Тип выбирают по операциям: точная сумма требует целого, а не «красивого» вещественного.
