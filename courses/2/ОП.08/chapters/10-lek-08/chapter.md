## Заказ, в котором пять книг

В «Странице» продавец оформляет заказ и записывает состав в одно поле: «Чистый код x1; Алгоритмы x1». Так проще набирать, и в отчёте заказ выглядит компактно. Пока заказов десятки, всё работает. Когда их становятся тысячи, отдел аналитики просит посчитать, сколько экземпляров «Чистого кода» продано за сентябрь, и выясняется, что ответить нечем: количество спрятано внутри текста, а не лежит в отдельном столбце.

Первая нормальная форма начинается с простого требования: **в каждой ячейке должно быть одно значение**. Не «одна книга», не «один смысл», а именно одно значение, с которым можно сравнить, сложить или соединить.

Звучит почти банально, но нарушение встречается постоянно. Список телефонов в одной ячейке, теги через запятую, авторы книги в одной строке, диапазон дат «с 1 по 15 сентября», JSON с произвольной структурой. Всё это компактно выглядит и плохо работает в запросах.

## Что требует первая нормальная форма

Отношение находится в первой нормальной форме, если выполнены три условия.

| Условие | Что проверяют | Пример нарушения |
|---|---|---|
| Атомарность | в ячейке одно значение | «Чистый код x1; Алгоритмы x1» |
| Нет повторяющихся групп | нет набора однотипных столбцов | `kniga1`, `kniga2`, `kniga3` |
| Строки различимы | есть первичный ключ | две строки без идентификатора |

Первое условие самое известное, но не единственное. Таблица с тремя столбцами «книга 1», «книга 2», «книга 3» формально содержит по одному значению в ячейке, однако в ней есть повторяющаяся группа. Четвёртую книгу добавить некуда, а запрос «найти все заказы с книгой 5» превращается в три условия через `OR`. Это тоже нарушение 1НФ, только записанное столбцами, а не строкой.

Третье условие часто забывают. Если в таблице нет ключа, две одинаковые строки неотличимы, и непонятно, дубль это или две разные продажи. Первичный ключ делает строку объектом, а не набором совпавших значений.

**Атомарность относительна задачи, а не абсолютна.** Название «Чистый код» это одно значение, хотя состоит из двух слов. Адрес «Москва, Тверская, 12» для доставки может быть одним значением, а для отчёта по городам его придётся разделить. Вопрос не в том, сколько частей в тексте, а в том, будет ли запрос обращаться к части отдельно.

## Как выглядит нарушение

Соберём заказы за 3 сентября в таблицу, где состав записан текстом.

```sql
CREATE TABLE zakaz (
  zakaz_id INTEGER PRIMARY KEY,
  data TEXT,
  pokupatel TEXT,
  sostav TEXT
);

INSERT INTO zakaz VALUES
  (1001, '2026-09-03', 'Иванова', 'Чистый код x1; Алгоритмы x1'),
  (1002, '2026-09-03', 'Петров', 'Чистый код x2'),
  (1003, '2026-09-04', 'Смирнов', 'Чистый код на Python x1; SQL для простых смертных x1');
```

Первый запрос кажется очевидным: найти заказы, где есть «Чистый код».

```sql
SELECT zakaz_id, sostav
FROM zakaz
WHERE sostav LIKE '%Чистый код%';
```

```text
1001|Чистый код x1; Алгоритмы x1
1002|Чистый код x2
1003|Чистый код на Python x1; SQL для простых смертных x1
```

Три строки, хотя книга «Чистый код» есть только в двух заказах. Третья строка попала в результат потому, что «Чистый код на Python» содержит те же слова в начале. `LIKE` ищет подстроку, а не книгу. Отличить одно издание от другого внутри текста можно только новыми условиями, и каждая новая книга будет добавлять новую ловушку.

Второй запрос не работает вовсе. Нужно посчитать, сколько экземпляров продано:

```sql
SELECT sum(kolichestvo) FROM zakaz;
```

```text
no such column: kolichestvo
```

Столбца нет, потому что количество записано словами внутри `sostav`. Его можно вытащить регулярным выражением или разбором строки, но это уже не работа с базой, а программирование парсера поверх неё. Для каждой новой формы записи парсер придётся менять.

Третья проблема касается соединения. Нужно соединить заказ с таблицей книг, чтобы получить цену. В этой схеме запрос даже не выполнится: таблицы книг ещё нет. Если её создать, соединение по названию не найдёт ни одной строки, потому что в `sostav` лежит «Чистый код x1; Алгоритмы x1», а в `nazvanie` лежит «Чистый код». Даже если очистить текст, одна ячейка содержит две книги, и одна строка заказа должна была бы дать две строки результата. Реляционная модель так не умеет: соединение работает между строками, а не внутри строки.

Отсюда главный вывод: **список в ячейке прячет строки.** Каждый элемент списка по смыслу является отдельной строкой дочерней таблицы, но записан как часть текста. Пока он там, база не может ни посчитать, ни соединить, ни проверить его существование.

::/gate

## Чем плоха повторяющаяся группа

Нарушение 1НФ бьёт по трём операциям сразу. Их называют аномалиями, потому что данные выглядят целыми, а операции дают неверный результат.

**Аномалия вставки.** Нельзя добавить книгу в заказ, не переписав всю строку текста. Нельзя добавить новую книгу в справочник, если она ещё ни разу не продавалась: справочника книг просто нет, есть только текст заказов. Приходится придумывать фиктивную продажу, чтобы завести позицию.

**Аномалия обновления.** Переименовали книгу, и нужно найти все заказы, где встречается старое название. Часть строк обновят, часть пропустят, потому что где-то написано «Чистый код», а где-то «Чистый код (2-е изд.)». В базе окажутся два названия одной книги.

**Аномалия удаления.** Удалили последний заказ с книгой, и информация о ней исчезла полностью: название, автор, цена. Справочник не должен зависеть от продаж.

Отдельная цена такой записи это невозможность проверки. В тексте легко опечататься: «Алгоритмы x1» и «Алгоритмы х1» с русской буквой «х» выглядят одинаково, а база считает их разными. Ограничение `CHECK` не поможет, потому что не знает, где в строке книга, а где количество.

Таблица с повторяющимися столбцами страдает иначе. `kniga1`, `kniga2`, `kniga3` позволяют хранить не больше трёх книг, а четвёртую приходится либо терять, либо добавлять новый столбец и переписывать все запросы. Пустые ячейки в такой таблице означают не «нет значения», а «книг меньше трёх», и отличить одно от другого невозможно.

::/gate

## Приведение к 1НФ

Разложение делают в два шага: отделяют шапку документа от строк и каждой строке дают своё место.

Шапка заказа содержит то, что относится к заказу целиком: номер, дату, покупателя.

```sql
CREATE TABLE zakaz (
  zakaz_id INTEGER PRIMARY KEY,
  data TEXT NOT NULL,
  pokupatel TEXT NOT NULL
);
```

Строка заказа содержит одну книгу и количество.

```sql
CREATE TABLE zakaz_stroka (
  zakaz_id INTEGER NOT NULL REFERENCES zakaz(zakaz_id),
  kniga_id INTEGER NOT NULL,
  kolichestvo INTEGER NOT NULL CHECK (kolichestvo > 0),
  cena INTEGER NOT NULL CHECK (cena > 0),
  PRIMARY KEY (zakaz_id, kniga_id)
);
```

Первичный ключ строки составной: номер заказа плюс код книги. Один заказ может содержать много книг, одна книга может быть во многих заказах, а пара «заказ плюс книга» встречается один раз. Это ровно та уникальность, которую раньше прятал текст.

Заполним таблицы теми же данными.

```sql
INSERT INTO zakaz VALUES
  (1001, '2026-09-03', 'Иванова'),
  (1002, '2026-09-03', 'Петров'),
  (1003, '2026-09-04', 'Смирнов');

INSERT INTO zakaz_stroka VALUES
  (1001, 5, 1, 1890),
  (1001, 7, 1, 1590),
  (1002, 5, 2, 1890),
  (1003, 8, 1, 1790),
  (1003, 9, 1, 2190);
```

Теперь считаются и экземпляры, и суммы:

```sql
SELECT sum(kolichestvo) AS ekzemplyarov FROM zakaz_stroka;
SELECT zakaz_id, sum(kolichestvo * cena) AS itogo
FROM zakaz_stroka
GROUP BY zakaz_id
ORDER BY zakaz_id;
```

```text
6
1001|3480
1002|3780
1003|3980
```

Поиск конкретной книги тоже стал точным. В широкой таблице запрос по `LIKE` вернул три заказа, включая лишний. В новой схеме книга имеет код, и сравнение идёт по коду, а не по подстроке:

```sql
SELECT count(*) AS zakazov, sum(kolichestvo) AS ekzemplyarov
FROM zakaz_stroka
WHERE kniga_id = 5;
```

```text
2|3
```

Два заказа, три экземпляра. Именно это число раньше приходилось угадывать по тексту.

Разложение на две таблицы не увеличило объём данных, а изменило их форму. Каждая книга заказа стала отдельной строкой, поэтому агрегаты и соединения работают без разбора текста. Шапка заказа хранится один раз, а не повторяется в каждой позиции, и дата с покупателем не могут разойтись между строками одного документа.

Обратите внимание: количество и цена переехали в строку заказа, хотя в исходной таблице их не было отдельными столбцами. При разборе текста «x1» и «x2» становятся значениями `kolichestvo`, а цена берётся из справочника книг или фиксируется в момент продажи. Цена в строке заказа хранится отдельно от текущей цены книги, потому что продажа должна помнить цену на дату покупки. Это не дублирование, а историческая фиксация.

## Атомарность не означает «одно слово»

Самая частая ошибка при освоении 1НФ это стремление раздробить всё. ФИО превращают в три столбца, адрес в шесть, телефон в код страны, код города и номер. Иногда это оправдано, иногда создаёт новые проблемы.

Правило простое: **дробите только то, к чему будете обращаться отдельно.** Если приложение ищет сотрудника по фамилии и сортирует по ней, фамилия нужна отдельным столбцом. Если отчество нужно только для печати пропуска, хранить его вместе с именем нормально. Если отчёты строятся по городам, город в адресе нужен отдельно. Если адрес печатается одной строкой на конверте, разбивать его на части без необходимости вредно: соберёте обратно с ошибками.

С датой похожая история. `2026-09-03` это одно значение типа даты, хотя внутри есть год, месяц и день. Функции `strftime` извлекают части без разбора строки. Разбивать дату на три числовых столбца стоит только тогда, когда база не поддерживает тип даты, а запросы постоянно фильтруют по месяцу. В SQLite дата хранится текстом в формате ISO, и это нормально.

Многозначный атрибут отличается от составного. Составной атрибут можно разложить на части внутри той же строки: адрес на город и улицу. Многозначный атрибут даёт несколько значений для одной строки: у книги несколько авторов, у заказа несколько книг. Именно многозначный атрибут требует отдельной таблицы, потому что число значений заранее неизвестно. Составной атрибут отдельной таблицы не требует, его достаточно разделить на столбцы.

Телефон сотрудника это классический многозначный атрибут. Один телефон можно оставить в таблице сотрудника, два уже требуют решения: либо отдельная таблица `telefon`, либо ограничение «не больше двух» и два столбца. Первое честнее, потому что не ставит предел, который завтра придётся поднимать.

## Многозначный атрибут на примере авторов

У книги бывает несколько авторов. Если хранить их в одном столбце «Мартин, Коплиен», получится та же беда, что со списком книг: нельзя найти все книги автора, нельзя посчитать соавторство, нельзя проверить, что фамилия написана одинаково. Два столбца `avtor1` и `avtor2` тоже не решают задачу: у учебника может быть три автора, а у сборника десять.

Правильное решение это таблица связи. Авторы живут в своём справочнике, книги в своём, а факт авторства хранится парой.

```sql
CREATE TABLE kniga (
  id INTEGER PRIMARY KEY,
  nazvanie TEXT NOT NULL
);

INSERT INTO kniga VALUES
  (5, 'Чистый код'),
  (7, 'Алгоритмы'),
  (8, 'Чистый код на Python');

CREATE TABLE avtor (
  id INTEGER PRIMARY KEY,
  familiya TEXT NOT NULL,
  imya TEXT NOT NULL
);

CREATE TABLE kniga_avtor (
  kniga_id INTEGER NOT NULL REFERENCES kniga(id),
  avtor_id INTEGER NOT NULL REFERENCES avtor(id),
  PRIMARY KEY (kniga_id, avtor_id)
);
```

Заполним фрагмент каталога.

```sql
INSERT INTO avtor VALUES
  (1, 'Мартин', 'Роберт'),
  (2, 'Персиваль', 'Гарри'),
  (3, 'Бхаргава', 'Адитья');

INSERT INTO kniga_avtor VALUES (5, 1), (8, 2), (7, 3);
```

Теперь авторы книги находятся одним соединением:

```sql
SELECT k.nazvanie, a.familiya, a.imya
FROM kniga k
JOIN kniga_avtor ka ON ka.kniga_id = k.id
JOIN avtor a ON a.id = ka.avtor_id
WHERE k.id = 5;
```

```text
Чистый код|Мартин|Роберт
```

Обратный запрос, все книги автора, устроен так же, только условие ставится на `avtor_id`. Число авторов у книги ничем не ограничено: достаточно добавить ещё одну строку в `kniga_avtor`. Именно этого не хватало столбцу со списком.

Таблица связи может иметь собственные атрибуты. Для перевода нужно знать не только кто перевёл, но и какую книгу, а роль человека отличается от авторства. Тогда в `kniga_uchastnik` появляется столбец `rol` со значениями «автор», «переводчик», «иллюстратор», и первичный ключ расширяется до тройки. Это уже не нарушение 1НФ, а нормальная детализация связи: каждая ячейка по-прежнему содержит одно значение.

Связь книги и автора относится к типу многие ко многим: одна книга может иметь нескольких авторов, один автор может написать несколько книг. В реляционной базе такая связь всегда раскладывается на две связи один ко многим через таблицу связи. Строка заказа устроена похоже, но у неё есть количество и цена, поэтому таблица связи несёт данные, а не только пару ключей.

::/gate

::gate Когда разбиение на две таблицы сохраняет все данные, а когда теряет?

## Проверка результата

Разложение должно быть обратимым: из новых таблиц можно собрать исходные данные без потерь и без выдуманных строк. Проверяют это тремя запросами.

Первый считает строки в исходной широкой таблице.

```sql
SELECT count(*) AS zakazov FROM zakaz;
```

```text
3
```

Второй проверяет, что после разложения заказов столько же и ни один не потерян.

```sql
SELECT count(DISTINCT zakaz_id) AS zakazov FROM zakaz_stroka;
```

```text
3
```

Третий собирает строки обратно и сравнивает количество экземпляров.

```sql
SELECT sum(kolichestvo) AS vsego FROM zakaz_stroka;
```

```text
6
```

Шесть экземпляров это сумма всех количеств: 1 + 1 + 2 + 1 + 1. Если бы при переносе потерялась одна позиция, число уменьшилось бы, и это сразу видно. Тот же контроль применяют к сумме заказа: итог по строкам должен совпасть с итогом, который был в документе.

Отдельно проверяют сирот. Строка заказа без заказа невозможна, и внешний ключ это гарантирует. Если проверка внешних ключей была выключена, сироты ищут соединением:

```sql
SELECT count(*) AS sirot
FROM zakaz_stroka s
LEFT JOIN zakaz z ON z.zakaz_id = s.zakaz_id
WHERE z.zakaz_id IS NULL;
```

Ноль означает, что каждая строка нашла свой заказ. Это и есть проверка сохранения связей: разложение не должно отрывать дочерние строки от родительских.

Потеря связи возникает, когда в новую таблицу забыли перенести ключ. Например, вынесли книги в справочник, но не сохранили `kniga_id` в строке заказа, а оставили только название. Формально данные на месте, а соединить строку с книгой нечем: название может измениться или повториться. Ключ переносят всегда, даже если рядом лежит текст для удобства чтения.

## Типичные ошибки

**Список через запятую считают допустимым.** «Одно поле, зато гибко» заканчивается парсером, который ломается на названии с запятой. Запятая внутри значения и запятая-разделитель неразличимы без экранирования, а экранирование это уже формат, а не значение.

**Путают 1НФ с отсутствием NULL.** NULL это отсутствие значения, а не нарушение формы. Таблица с NULL может быть в 1НФ, если значения атомарны и есть ключ. И наоборот, таблица без NULL может нарушать 1НФ списком в ячейке.

**Делают `kniga1`, `kniga2`, `kniga3`.** Повторяющаяся группа переехала из строки в столбцы, но осталась повторяющейся. Четвёртая книга по-прежнему не помещается.

**Хранят JSON в реляционной таблице без причины.** JSON удобен для обмена, но запросы к нему в SQLite и MySQL сложнее, а ограничения целостности почти не работают. Если поля нужны для поиска и соединений, их место в столбцах.

**Разбивают всё подряд.** Шесть столбцов адреса, три столбца ФИО и отдельный столбец для каждой цифры телефона усложняют вставку и не помогают запросам. Атомарность определяют по использованию, а не по желанию раздробить.

**Забывают первичный ключ после разложения.** Две таблицы без ключей не дают гарантии, что строки не повторятся. Строка заказа получает составной ключ, справочник книг получает свой.

## Итоги

- 1НФ требует атомарных значений, отсутствия повторяющихся групп и различимых строк.
- Список в ячейке прячет строки: по нему нельзя точно искать, считать и соединять таблицы.
- Многозначный атрибут выносят в отдельную таблицу, составной достаточно разделить на столбцы.
- Шапка документа и его строки разводятся по двум таблицам, строка получает составной ключ.
- Атомарность определяют по тому, как данные используются в запросах, а не по числу слов в значении.
- После разложения проверяют число строк, суммы и отсутствие сирот.

Q: Что требует первая нормальная форма?
+ Атомарные значения, отсутствие повторяющихся групп и различимые строки
- Только отсутствие NULL во всех столбцах
- Наличие внешнего ключа в каждой таблице
- Разделение каждого текста на отдельные слова
! 1НФ это три условия, а не только атомарность.

Q: Почему список книг в одной ячейке мешает запросам?
+ База не может сравнить, посчитать и соединить отдельные элементы списка
- Список занимает слишком много места на диске
- SQLite не поддерживает текстовые столбцы
- Список нельзя вывести в отчёт
! Элементы списка не являются отдельными строками.

Q: Чем плохи столбцы kniga1, kniga2, kniga3?
+ Это повторяющаяся группа, число книг ограничено тремя
- Они всегда содержат NULL
- Они не могут быть текстовыми
- Они требуют внешнего ключа
! Однотипные столбцы повторяют структуру и ограничивают количество.

Q: Что происходит с заказом 1003 при поиске LIKE '%Чистый код%'?
+ Он попадает в результат, хотя содержит другую книгу
- Он теряется из результата
- Он дублируется дважды
- Запрос завершается ошибкой
! LIKE ищет подстроку и не различает «Чистый код» и «Чистый код на Python».

Q: Какой ключ получает таблица строк заказа после разложения?
+ Составной из номера заказа и кода книги
- Только номер заказа
- Только код книги
- Суррогатный номер без ограничений
! Пара «заказ плюс книга» уникальна, каждый столбец по отдельности нет.

Q: Куда переносят количество и цену из текста «Чистый код x2»?
+ В отдельные столбцы строки заказа
- В название книги
- В таблицу покупателей
- В первичный ключ заказа
! Количество и цена относятся к конкретной строке заказа.

Q: Что означает атомарное значение?
+ Значение, к которому запрос обращается как к целому
- Значение, состоящее из одного слова
- Значение, не содержащее цифр
- Значение, которое нельзя изменить
! Атомарность зависит от использования в запросах.

Q: Какой атрибут обязательно требует отдельной таблицы?
+ Многозначный, например несколько авторов книги
- Составной, например адрес из города и улицы
- Любой текстовый атрибут
- Любой атрибут с NULL
! Число значений многозначного атрибута заранее неизвестно.

Q: Зачем после разложения сравнивают сумму количеств?
+ Чтобы убедиться, что ни одна позиция не потеряна
- Чтобы ускорить запросы
- Чтобы проверить тип данных
- Чтобы удалить дубликаты
! Сумма до и после должна совпадать.

Q: Какие признаки указывают на нарушение 1НФ?
+ Телефоны через запятую в одной ячейке
+ Столбцы kniga1, kniga2, kniga3
+ Таблица без первичного ключа
- Столбец с типом TEXT
- Столбец, содержащий NULL
! Список, повторяющаяся группа и отсутствие ключа нарушают форму.

Q: Какие данные допустимо хранить в одной ячейке?
+ Название книги «Чистый код»
+ Дату в формате 2026-09-03
+ Адрес, который всегда печатается одной строкой
- Список из пяти книг заказа
- Три телефона сотрудника через точку с запятой
! Атомарность определяется тем, нужны ли части значения отдельно.

+ Проверить отсутствие строк без родителя
- Сравнить размер файла базы
- Проверить, что все столбцы имеют тип TEXT
! Обратимость проверяют счётом строк, сумм и ссылок.
