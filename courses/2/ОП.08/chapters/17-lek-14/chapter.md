## Ошибка, которая появляется через час

Скрипт базы учебной «Страницы» выглядел почти готовым. Первой шла таблица заказов, за ней позиции, книги, площадки. Скрипт выполнялся без единой ошибки. Через час, когда попробовали вставить первый заказ, sqliteonline ответил: `FOREIGN KEY constraint failed`. Площадки, на которую ссылается заказ, ещё не было, потому что её таблицу создали последней.

SQLite разрешил создать таблицу с внешним ключом на несуществующую таблицу. Проверка откладывается до первой вставки. Другая СУБД отказала бы сразу, но и там порядок команд важен: родительская таблица должна существовать раньше дочерней, иначе ссылка не на что.

**CREATE TABLE описывает структуру таблицы: столбцы, их типы и ограничения, которые СУБД проверяет при каждой операции с данными.** Ограничение это не украшение схемы. Это правило, которое нельзя обойти через приложение, потому что оно живёт в самой базе.

В этой лекции собирается рабочий скрипт для восьми таблиц «Страницы». Каждая команда проверена в SQLite, а ошибки показаны такими, какими их увидит человек в sqliteonline.com.

## Анатомия команды

У команды есть имя таблицы, список определений в скобках и необязательные уточнения. Каждое определение это либо столбец, либо ограничение уровня таблицы. Определения разделяются запятыми, после последнего запятая не ставится.

```sql
CREATE TABLE IF NOT EXISTS площадка (
  код_площадки INTEGER PRIMARY KEY,
  название TEXT NOT NULL UNIQUE,
  город TEXT NOT NULL,
  адрес TEXT
);
```

`IF NOT EXISTS` делает команду безопасной для повторного запуска: если таблица уже есть, SQLite ничего не делает и не выдаёт ошибку. В учебном скрипте это удобно, в рабочем изменении схемы опаснее, потому что можно не заметить, что старая таблица осталась с другой структурой.

Имя таблицы и столбцов пишут латиницей или кириллицей. SQLite понимает кириллические имена без кавычек, но в переносимом SQL их заключают в двойные кавычки. В учебной базе кириллица допустима: она делает схему читаемой, а sqliteonline корректно показывает такие имена. Главное, соблюдать единый стиль и не смешивать `код_книги` с `book_id` в одной таблице.

Тип столбца указывается после имени. В SQLite он задаёт сродство, а не жёсткий класс хранения, поэтому `INTEGER`, `TEXT` и `REAL` покрывают почти все учебные случаи. Ограничения пишутся после типа в любом порядке, но читать удобнее в одном: сначала `NOT NULL`, затем `DEFAULT`, затем `UNIQUE`, затем `CHECK`, затем `REFERENCES`.

Команда заканчивается точкой с запятой. Комментарии начинаются с двух дефисов и продолжаются до конца строки. В скрипте базы комментарии ставят перед каждой группой таблиц: так видно, где справочники, где документы, а где строки документов.

```sql
CREATE TABLE издательство (
  код_издательства INTEGER PRIMARY KEY,
  название TEXT NOT NULL UNIQUE,
  город TEXT
);
```

Здесь `PRIMARY KEY` объявлен у столбца, потому что ключ один. `NOT NULL` запрещает пустое название, `UNIQUE` запрещает два одинаковых издательства. Город может отсутствовать, поэтому ограничения у него нет.

## Ограничения столбца

`NOT NULL` запрещает значение `NULL`. Это не то же самое, что запрет пустой строки: пустая строка `''` является значением и проходит проверку. Если пустая строка недопустима, добавляют `CHECK (length(поле) > 0)`.

`DEFAULT` подставляет значение, когда столбец не указан в `INSERT`. Значение по умолчанию может быть числом, строкой, выражением или функцией. `DEFAULT 0` удобен для счётчиков, `DEFAULT 'новый'` для статуса, `DEFAULT CURRENT_TIMESTAMP` для даты создания записи.

```sql
CREATE TABLE сотрудник (
  табельный_номер INTEGER PRIMARY KEY,
  фио TEXT NOT NULL,
  код_площадки INTEGER NOT NULL REFERENCES площадка(код_площадки),
  роль TEXT NOT NULL DEFAULT 'продавец',
  CONSTRAINT chk_роль CHECK (роль IN ('продавец', 'кладовщик', 'менеджер', 'администратор'))
);
```

Вставка без указания роли подставит `продавец`. Если указать `NULL`, сработает `NOT NULL` и команда завершится ошибкой. `DEFAULT` не спасает от явного `NULL`: он работает только при отсутствии столбца в команде.

Поэтому в `INSERT` перечисляют только те столбцы, которые действительно известны. Команда `INSERT INTO сотрудник (табельный_номер, фио, код_площадки) VALUES (101, 'Иванова А. П.', 1);` оставит роль по умолчанию. Если же перечислить все четыре столбца и передать `NULL` в роли, сработает `NOT NULL`, а не `DEFAULT`. Явный список столбцов ещё и защищает команду от поломки при добавлении нового столбца в таблицу.

`PRIMARY KEY` объявляет первичный ключ. У столбца типа `INTEGER` он становится псевдонимом номера строки и заполняется автоматически, если значение не указано. Для строковых ключей автоматического заполнения нет, значение нужно передавать явно.

`UNIQUE` запрещает повторение значения, но в SQLite допускает несколько `NULL`: два сотрудника без email пройдут проверку, а два одинаковых email нет. Если нужен ровно один `NULL`, это выражают через частичный индекс, но в учебной схеме достаточно обычного `UNIQUE`.

`CHECK` задаёт условие, которое должно быть истинным. Важная тонкость: если условие даёт `NULL`, проверка считается пройденной. Поэтому `CHECK (цена > 0)` пропустит строку с `NULL` в цене. Запретить `NULL` может только `NOT NULL`, и эти два ограничения работают в паре.

```sql
CREATE TABLE книга (
  код_книги INTEGER PRIMARY KEY,
  isbn TEXT NOT NULL UNIQUE,
  название TEXT NOT NULL,
  код_издательства INTEGER NOT NULL REFERENCES издательство(код_издательства),
  код_категории INTEGER NOT NULL REFERENCES категория(код_категории),
  год_издания INTEGER,
  цена_коп INTEGER NOT NULL DEFAULT 0,
  CONSTRAINT chk_цена CHECK (цена_коп >= 0),
  CONSTRAINT chk_год CHECK (год_издания BETWEEN 1500 AND 2100)
);
```

Имена ограничений (`chk_цена`, `chk_год`) полезны в сообщениях об ошибке. SQLite покажет `CHECK constraint failed: chk_цена`, и сразу понятно, какое правило нарушено. Без имени он выведет само выражение, что тоже читаемо, но менее удобно в большой схеме.

## Ограничения уровня таблицы

Составной первичный ключ нельзя объявить у одного столбца. Его выносят в конец списка и перечисляют столбцы через запятую. Так же поступают с составным внешним ключом и составным `UNIQUE`.

```sql
CREATE TABLE позиция_заказа (
  номер_заказа INTEGER NOT NULL REFERENCES заказ(номер_заказа) ON DELETE CASCADE,
  код_книги INTEGER NOT NULL REFERENCES книга(код_книги),
  количество INTEGER NOT NULL,
  цена_коп INTEGER NOT NULL,
  CONSTRAINT pk_позиция PRIMARY KEY (номер_заказа, код_книги),
  CONSTRAINT chk_количество CHECK (количество > 0),
  CONSTRAINT chk_цена_позиции CHECK (цена_коп >= 0)
);
```

Ограничение уровня таблицы виднее в конце и не привязано к одному столбцу. Для составного ключа это единственный допустимый способ. Для внешнего ключа из двух столбцов тоже: `FOREIGN KEY (а, б) REFERENCES родитель(в, г)`.

Составной внешний ключ нужен, когда родительский ключ сам состоит из двух столбцов. Пусть таблица `спецификация_поставки` имеет ключ «номер поставки, код книги», а таблица `приёмка` фиксирует фактически принятые позиции. Тогда ссылка из приёмки на спецификацию записывается парой столбцов.

```sql
CREATE TABLE приёмка (
  номер_поставки INTEGER NOT NULL,
  код_книги INTEGER NOT NULL,
  дата_приёмки TEXT NOT NULL,
  CONSTRAINT pk_приёмка PRIMARY KEY (номер_поставки, код_книги),
  CONSTRAINT fk_приёмка_спецификация
    FOREIGN KEY (номер_поставки, код_книги)
    REFERENCES спецификация_поставки(номер_поставки, код_книги)
);
```

Пара столбцов должна совпадать по составу и порядку с ключом родителя. Если переставить столбцы местами, SQLite выдаст `foreign key mismatch`, даже когда типы подходят.

`UNIQUE` на паре столбцов запрещает повторение пары, но разрешает повторять каждый столбец по отдельности. Это часто путают с двумя отдельными `UNIQUE`. В таблице `позиция_заказа` пара «заказ, книга» уникальна, а книга может встречаться в разных заказах.

## Внешние ключи и порядок создания

Внешний ключ объявляют через `REFERENCES` после столбца или через `FOREIGN KEY` в конце таблицы. Родительский столбец должен быть первичным ключом или иметь ограничение `UNIQUE`, иначе SQLite выдаст `foreign key mismatch` при первой операции.

```sql
CREATE TABLE заказ (
  номер_заказа INTEGER PRIMARY KEY,
  дата_заказа TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  код_покупателя INTEGER NOT NULL REFERENCES покупатель(код_покупателя),
  табельный_номер INTEGER NOT NULL REFERENCES сотрудник(табельный_номер),
  статус TEXT NOT NULL DEFAULT 'новый',
  CONSTRAINT chk_статус CHECK (статус IN ('новый', 'оплачен', 'собран', 'выдан', 'отменён'))
);
```

В SQLite внешние ключи по умолчанию выключены. Это отличие от многих СУБД, и его забывают чаще всего. Без команды `PRAGMA foreign_keys = ON;` можно вставить заказ на несуществующего покупателя, и база не возразит. Команду выполняют в каждом соединении, перед работой со схемой.

```sql
PRAGMA foreign_keys = ON;
```

Проверить режим можно запросом `PRAGMA foreign_keys;`. Значение 1 означает, что проверка включена, 0 что выключена. В sqliteonline команду нужно выполнить в том же окне, где выполняются остальные команды. Режим не сохраняется в файле базы: при следующем подключении его включают заново.

Действие при удалении и обновлении задают через `ON DELETE` и `ON UPDATE`. `RESTRICT` запрещает удалять родителя, пока на него ссылаются. `CASCADE` удаляет или обновляет дочерние строки вместе с родителем. `SET NULL` обнуляет ссылку, но требует, чтобы столбец допускал `NULL`. `NO ACTION` откладывает проверку до конца команды и по поведению близок к `RESTRICT`.

| Действие | Что происходит с дочерними строками | Когда выбирать |
|---|---|---|
| `RESTRICT` | удаление родителя запрещено | справочники, которые нельзя терять |
| `CASCADE` | дочерние строки удаляются | позиции заказа вместе с заказом |
| `SET NULL` | внешний ключ становится `NULL` | необязательная связь |
| `NO ACTION` | проверка в конце команды | поведение по умолчанию |

Для «Страницы» удобно так: площадку с сотрудниками удалять нельзя (`RESTRICT`), позиции заказа уходят вместе с заказом (`CASCADE`), а категорию с книгами лучше не удалять вовсе. Эти решения принимают по смыслу данных, а не по удобству.

Порядок создания вытекает из ссылок. Сначала создают таблицы, на которые никто не ссылается: площадка, издательство, категория, покупатель. Затем книги и сотрудников, которые ссылаются на справочники. Затем заказы, которые ссылаются на покупателя и сотрудника. Последними идут позиции, поставки и спецификации.

```text
1. площадка
2. издательство
3. категория
4. покупатель
5. книга
6. сотрудник
7. заказ
8. позиция_заказа
```

Категория ссылается сама на себя. Это допустимо в одной команде: SQLite сначала создаёт таблицу, затем проверяет ссылку. При вставке родительская категория должна уже существовать, поэтому сначала добавляют категории верхнего уровня, потом подкатегории.

Самоссылка создаёт цикл только на уровне данных, но не на уровне создания таблицы. Если же две таблицы ссылаются друг на друга, порядок создания становится невозможным без дополнительной команды. В SQLite на время загрузки можно отложить проверку: `PRAGMA defer_foreign_keys = ON;` внутри транзакции. После завершения транзакции ссылки проверяются снова. Пользоваться этим стоит только при импорте подготовленного набора, а не при обычной работе.

При удалении порядок обратный: сначала дочерние таблицы, потом родительские. Если удалить родителя первым, сработает `RESTRICT` или `CASCADE`, и часть данных исчезнет раньше, чем вы этого ожидали.

## Полный скрипт для «Страницы»

Соберём восемь таблиц в одном скрипте. Он выполняется сверху вниз и не требует ручной правки порядка.

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE площадка (
  код_площадки INTEGER PRIMARY KEY,
  название TEXT NOT NULL UNIQUE,
  город TEXT NOT NULL,
  адрес TEXT
);

CREATE TABLE издательство (
  код_издательства INTEGER PRIMARY KEY,
  название TEXT NOT NULL UNIQUE,
  город TEXT
);

CREATE TABLE категория (
  код_категории INTEGER PRIMARY KEY,
  название TEXT NOT NULL UNIQUE,
  код_родителя INTEGER REFERENCES категория(код_категории)
);

CREATE TABLE покупатель (
  код_покупателя INTEGER PRIMARY KEY,
  фио TEXT NOT NULL,
  телефон TEXT,
  email TEXT UNIQUE
);

CREATE TABLE книга (
  код_книги INTEGER PRIMARY KEY,
  isbn TEXT NOT NULL UNIQUE,
  название TEXT NOT NULL,
  код_издательства INTEGER NOT NULL REFERENCES издательство(код_издательства),
  код_категории INTEGER NOT NULL REFERENCES категория(код_категории),
  год_издания INTEGER,
  цена_коп INTEGER NOT NULL DEFAULT 0,
  CONSTRAINT chk_цена CHECK (цена_коп >= 0),
  CONSTRAINT chk_год CHECK (год_издания BETWEEN 1500 AND 2100)
);

CREATE TABLE сотрудник (
  табельный_номер INTEGER PRIMARY KEY,
  фио TEXT NOT NULL,
  код_площадки INTEGER NOT NULL REFERENCES площадка(код_площадки) ON DELETE RESTRICT,
  роль TEXT NOT NULL DEFAULT 'продавец',
  CONSTRAINT chk_роль CHECK (роль IN ('продавец', 'кладовщик', 'менеджер', 'администратор'))
);

CREATE TABLE заказ (
  номер_заказа INTEGER PRIMARY KEY,
  дата_заказа TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  код_покупателя INTEGER NOT NULL REFERENCES покупатель(код_покупателя),
  табельный_номер INTEGER NOT NULL REFERENCES сотрудник(табельный_номер),
  статус TEXT NOT NULL DEFAULT 'новый',
  CONSTRAINT chk_статус CHECK (статус IN ('новый', 'оплачен', 'собран', 'выдан', 'отменён'))
);

CREATE TABLE позиция_заказа (
  номер_заказа INTEGER NOT NULL REFERENCES заказ(номер_заказа) ON DELETE CASCADE,
  код_книги INTEGER NOT NULL REFERENCES книга(код_книги),
  количество INTEGER NOT NULL,
  цена_коп INTEGER NOT NULL,
  CONSTRAINT pk_позиция PRIMARY KEY (номер_заказа, код_книги),
  CONSTRAINT chk_количество CHECK (количество > 0),
  CONSTRAINT chk_цена_позиции CHECK (цена_коп >= 0)
);
```

В скрипте есть всё, что понадобится на практике: первичные ключи, внешние ключи, `NOT NULL`, `DEFAULT`, `UNIQUE`, `CHECK` и порядок создания. Обратите внимание на `цена_коп`: деньги хранятся целым числом, как разбиралось в предыдущей лекции.

Здесь восемь таблиц, потому что лекция показывает приёмы на ядре схемы. На практике к ним добавятся автор, связь книги с авторами, поставщик, поставка и спецификация поставки. Приёмы те же: справочник, зависимая таблица, таблица связи. Порядок создания расширяется по тому же правилу: сначала родители, затем строки документов.

::/gate

::gate Как убедиться, что ограничения действительно работают?

## Проверка схемы и отказов

После создания таблиц полезно посмотреть, что именно записалось. `PRAGMA table_info` показывает столбцы, типы, признак `NOT NULL` и значение по умолчанию. `PRAGMA foreign_key_list` показывает внешние ключи и действия при удалении. Запрос к `sqlite_master` возвращает исходный текст команд.

В выводе `table_info` шесть столбцов: номер, имя, объявленный тип, признак `NOT NULL`, значение по умолчанию и номер в первичном ключе. Признак `notnull` равен 1 у обязательного столбца и 0 у необязательного. Если у поля, которое должно быть обязательным, стоит 0, ограничение забыто. Значение по умолчанию показывается в кавычках так, как оно записано в схеме.

```sql
PRAGMA table_info('сотрудник');
PRAGMA foreign_key_list('сотрудник');
SELECT name, sql FROM sqlite_master WHERE type = 'table' ORDER BY name;
```

Ограничения проверяются не чтением схемы, а попыткой нарушить каждое правило. Ниже пять команд, которые обязаны завершиться ошибкой. Если хоть одна проходит, ограничение не работает.

```sql
INSERT INTO площадка VALUES (1, 'Страница Москва', 'Москва', 'Ленина, 10');
INSERT INTO площадка VALUES (2, 'Страница Москва', 'Москва', 'Ленина, 10');
INSERT INTO сотрудник (табельный_номер, фио, код_площадки, роль)
VALUES (101, 'Иванова А. П.', 1, 'кассир');
INSERT INTO сотрудник (табельный_номер, фио, код_площадки)
VALUES (102, NULL, 1);
INSERT INTO заказ (номер_заказа, код_покупателя, табельный_номер)
VALUES (1001, 999, 101);
```

Первая команда проходит, вторая падает с `UNIQUE constraint failed: площадка.название`. Третья даёт `CHECK constraint failed: chk_роль`, четвёртая `NOT NULL constraint failed: сотрудник.фио`, пятая `FOREIGN KEY constraint failed`. Если пятая команда прошла, значит `PRAGMA foreign_keys = ON;` не выполнен.

Отдельно проверяют каскад. Заказ 1001 с позициями удаляется, и позиции должны исчезнуть вместе с ним. Площадка с сотрудниками, наоборот, не удаляется, пока сотрудники не переведены или не удалены.

```sql
DELETE FROM заказ WHERE номер_заказа = 1001;
SELECT COUNT(*) FROM позиция_заказа WHERE номер_заказа = 1001;
```

Второй запрос вернёт 0, если каскад сработал. Для площадки запрос `DELETE FROM площадка WHERE код_площадки = 1;` вернёт ошибку `FOREIGN KEY constraint failed`, пока в таблице сотрудников есть ссылки на неё. После проверки верните удалённые строки обратно или выполните скрипт заново, чтобы схема осталась в исходном состоянии.

## Типичные ошибки

**Забытый `PRAGMA foreign_keys = ON;`.** Схема выглядит правильной, внешние ключи объявлены, но не проверяются. Ссылки на несуществующие строки появляются молча.

**Неправильный порядок создания.** Дочерняя таблица создаётся раньше родительской. SQLite может пропустить `CREATE`, но первая вставка упадёт. В других СУБД упадёт уже создание.

**Опора на `DEFAULT` вместо `NOT NULL`.** Думают, что значение по умолчанию защищает от пустоты. На самом деле явный `NULL` проходит, если нет `NOT NULL`.

**`CHECK` без `NOT NULL`.** Условие `цена > 0` пропускает `NULL`, потому что сравнение с `NULL` даёт неизвестность, а неизвестность не является нарушением. Ограничения работают в паре.

**Внешний ключ на неуникальный столбец.** Родительский столбец не объявлен ключом или `UNIQUE`, и SQLite выдаёт `foreign key mismatch` при вставке. Ссылаться можно только на уникальный набор.

**Составной ключ объявлен у одного столбца.** `PRIMARY KEY (а, б)` нельзя заменить двумя `PRIMARY KEY`. Второй вызовет ошибку `table has more than one primary key`.

**Забытое имя ограничения.** В большой схеме сообщение `CHECK constraint failed` без имени заставляет искать виновника по всей таблице. Имена `chk_цена`, `chk_роль` экономят время.

**Удаление родителя раньше дочерних строк.** При `RESTRICT` команда падает, при `CASCADE` исчезают данные, которые собирались сохранить. Порядок удаления обратен порядку создания.

**Смешение стилей имён.** В одной схеме `код_книги`, в другой `book_id`. Соединения приходится писать с оглядкой на регистр и раскладку, а ошибки `no such column` учащаются.

**Ограничение объявлено после данных.** Добавить `CHECK` в готовую таблицу командой `ALTER TABLE` в SQLite нельзя. Схему продумывают до загрузки, иначе ограничение придётся переносить в приложение, где его легко обойти.

**Проверка только на одной строке.** Ограничение может сработать на дубле, но пропустить `NULL` или отрицательное значение. Каждое правило проверяют отдельной командой, а не одной общей вставкой. В таблице проверок должно быть столько строк, сколько ограничений вы объявили.

## Итоги

- `CREATE TABLE` задаёт столбцы, типы и ограничения, которые проверяет сама СУБД.
- `NOT NULL` запрещает `NULL`, `DEFAULT` подставляет значение при отсутствии столбца, `CHECK` проверяет условие.
- `CHECK` пропускает `NULL`, поэтому для обязательных числовых полей нужны оба ограничения.
- Составной первичный ключ и составной внешний ключ объявляются на уровне таблицы.
- Внешние ключи в SQLite включаются командой `PRAGMA foreign_keys = ON;` в каждом соединении.
- Родительские таблицы создаются раньше дочерних, удаляются позже.
- `RESTRICT` защищает справочник от удаления, `CASCADE` убирает зависимые строки вместе с родителем.
- Схема проверяется через `PRAGMA table_info`, `PRAGMA foreign_key_list` и намеренными нарушениями ограничений, а не только чтением текста команд.
- Ограничение, объявленное после загрузки данных, уже не защищает старые строки: схему продумывают до первой вставки.

::quiz
Q: Что делает ограничение NOT NULL?
+ Запрещает хранить в столбце значение NULL
- Запрещает пустую строку
- Подставляет значение по умолчанию
- Проверяет уникальность значения
! NOT NULL запрещает отсутствие значения, но пустая строка остаётся допустимой.

Q: Когда срабатывает значение DEFAULT?
+ Когда столбец не указан в команде INSERT
- Когда в столбец передан NULL
- При каждом обновлении строки
- При создании таблицы
! DEFAULT подставляет значение только при отсутствии столбца в команде.

Q: Где объявляется составной первичный ключ?
+ На уровне таблицы, после списка столбцов
- У первого столбца ключа
- У каждого столбца отдельно
- В отдельной команде CREATE KEY
! Составной ключ перечисляет несколько столбцов в одном ограничении таблицы.

Q: Почему родительская таблица создаётся раньше дочерней?
+ Внешний ключ ссылается на уже существующую таблицу и её ключ
- Так требует синтаксис CREATE TABLE
- Иначе дочерняя таблица получит другой тип
- Иначе не сработает DEFAULT
! Ссылка должна указывать на существующий уникальный ключ родителя.

Q: Что делает команда PRAGMA foreign_keys = ON в SQLite?
+ Включает проверку внешних ключей в текущем соединении
- Создаёт внешние ключи заново
- Удаляет все внешние ключи
- Включает автонумерацию строк
! По умолчанию проверка внешних ключей в SQLite выключена.

Q: Что означает действие ON DELETE RESTRICT?
+ Запрещает удалять родительскую строку, пока на неё ссылаются дочерние
- Удаляет дочерние строки вместе с родительской
- Обнуляет внешний ключ в дочерних строках
- Игнорирует ссылки при удалении
! RESTRICT защищает справочник от потери связанных данных.

Q: Что проверяет ограничение CHECK?
+ Условие, которое должно быть истинным для значения
- Уникальность значения в столбце
- Наличие значения в столбце
- Тип значения при вставке
! CHECK задаёт логическое условие на значение.

Q: Какая команда показывает столбцы таблицы и их ограничения?
+ PRAGMA table_info('сотрудник')
- SELECT * FROM сотрудник
- PRAGMA foreign_keys
- DROP TABLE сотрудник
! table_info возвращает имя, тип, NOT NULL и значение по умолчанию.

Q: Какие ограничения можно объявить на уровне столбца?
+ NOT NULL
+ DEFAULT
+ CHECK
- Составной внешний ключ
- Составной первичный ключ
! Составные ключи объявляются только на уровне таблицы.

Q: Какие команды помогают проверить схему после создания?
+ PRAGMA table_info('заказ')
+ PRAGMA foreign_key_list('заказ')
+ SELECT sql FROM sqlite_master WHERE name = 'заказ'
- DELETE FROM заказ
- INSERT INTO заказ VALUES (1)
! Схему читают через служебные команды и sqlite_master.

Q: Что верно про ограничение UNIQUE в SQLite?
+ Оно разрешает несколько значений NULL
+ Оно может охватывать несколько столбцов
+ Оно запрещает повторение указанного значения или набора
- Оно автоматически делает столбец первичным ключом
- Оно запрещает любые значения NULL
! UNIQUE не запрещает NULL, а составное UNIQUE проверяет набор целиком.

Q: В каком порядке создаются таблицы учебной схемы?
+ площадка раньше сотрудника
+ издательство раньше книги
+ заказ раньше позиции заказа
- позиция заказа раньше заказа
- книга раньше издательства
! Сначала справочники, затем зависимые таблицы, затем документы и их строки.

Q: Какое ограничение задаёт значение по умолчанию?
= DEFAULT
! Например, DEFAULT 'новый' подставит статус, если столбец не указан.

Q: Какое ограничение проверяет условие на значение столбца?
= CHECK
! CHECK (цена >= 0) запрещает отрицательные значения.

Q: Какая команда включает проверку внешних ключей в SQLite?
= PRAGMA foreign_keys = ON
= PRAGMA foreign_keys=ON
! Команда выполняется в каждом соединении перед работой с данными.
