## Требование, которое приходит после сдачи схемы

Схема книжного магазина «Страница» собрана и проверена: четырнадцать таблиц, ключи, ограничения, четыре площадки и 4800 книг. Числа относятся к учебному набору после загрузки каталога; на маленькой копии из практики они меньше, схема от этого не меняется. Через неделю приходит заведующая складом. Ей нужно видеть вес книги, чтобы считать доставку, формат издания, чтобы понимать, поместится ли книга в ячейку, и число страниц для карточки товара. Бухгалтер просит убрать служебный столбец `код_1с`, если он остался от переноса данных. А цена должна стать строго положительной: сейчас ограничение `chk_цена` разрешает ноль, и кто-то уже пытался сохранить книгу с нулевой ценой.

Пересоздавать базу нельзя. В `книга` лежат 4800 строк, на неё ссылаются 185 позиций заказов, 76 строк спецификаций поставок и 4801 связь с авторами. Если выполнить `DROP TABLE` и собрать таблицу заново, придётся выгружать данные, а любая ошибка в выгрузке останется незамеченной до первого отчёта. Для изменения готовой структуры есть команда `ALTER TABLE`.

**ALTER TABLE меняет описание таблицы, не создавая её заново.** В SQLite у команды четыре операции: добавить столбец, переименовать таблицу, переименовать столбец и удалить столбец. Всё остальное, а именно смену типа, добавление или удаление ограничения, смену первичного ключа, приходится делать через пересборку: новая таблица, перенос строк, удаление старой, переименование новой.

Ниже перечислены таблицы учебной базы. К этому списку мы будем возвращаться в следующих занятиях, поэтому имена и связи стоит запомнить.

## Добавление столбца

Синтаксис добавления простой:

```sql
ALTER TABLE книга ADD COLUMN вес_грамм INTEGER NOT NULL DEFAULT 0;
```

Команда дописывает описание столбца в схему. Существующие строки при этом не переписываются: SQLite хранит значение по умолчанию в описании таблицы и подставляет его при чтении старых строк. Поэтому операция занимает доли секунды даже на большой таблице.

Проверим результат:

```sql
SELECT код_книги, isbn, название, цена_коп, вес_грамм
FROM книга
ORDER BY код_книги
LIMIT 3;
```

| `код_книги` | `isbn` | `название` | `цена_коп` | `вес_грамм` |
|---|---|---|---|---|
| 204 | 978-5-17-118245-7 | Война и мир. Том 1 | 129000 | 0 |
| 205 | 978-5-17-118246-4 | Война и мир. Том 2 | 129000 | 0 |
| 318 | 978-5-17-087512-1 | Преступление и наказание | 89000 | 0 |

Второй столбец добавляют с текстовым значением по умолчанию:

```sql
ALTER TABLE книга ADD COLUMN формат TEXT DEFAULT '70x100/16';
```

У старых строк появится формат `70x100/16`, у новых он будет подставляться, пока его не укажут явно. Это удобный способ ввести поле, которое заполнят позже: `NULL` в нём означает «ещё не указано», а значение по умолчанию задаёт разумную заготовку. Третий столбец, `страницы`, добавляют без значения по умолчанию, потому что для разных книг оно разное:

```sql
ALTER TABLE книга ADD COLUMN страницы INTEGER;
```

Ограничения добавления столбца перечислены в документации SQLite и проверяются до изменения схемы.

| Что добавляют | Результат | Причина |
|---|---|---|
| `NOT NULL DEFAULT 0` | работает | у старых строк есть значение |
| `NOT NULL` без `DEFAULT` | ошибка `Cannot add a NOT NULL column with default value NULL` | старым строкам нечего подставить |
| `UNIQUE` | ошибка `Cannot add a UNIQUE column` | уникальность нужно проверять по всем строкам |
| `PRIMARY KEY` | ошибка `Cannot add a PRIMARY KEY column` | первичный ключ задаётся при создании |
| `DEFAULT CURRENT_TIMESTAMP` | ошибка `Cannot add a column with non-constant default` | значение по умолчанию должно быть постоянным |
| `REFERENCES` с `NOT NULL` и ненулевым `DEFAULT` | ошибка при включённых внешних ключах | значение по умолчанию должно быть `NULL` |

Последнее правило легко пропустить. Если столбец ссылается на другую таблицу, SQLite не может проверить, что значение по умолчанию существует в родительской таблице, поэтому требует `NULL`. Сначала добавляют `NULL`-столбец, потом заполняют его допустимыми значениями, и только затем, при пересборке, ставят `NOT NULL`.

Есть и ограничение на выражение по умолчанию. До версии 3.31 в `DEFAULT` разрешались только константы, позже появились выражения в скобках, но `CURRENT_TIMESTAMP` в `ADD COLUMN` всё равно не проходит: время добавления столбца не имеет смысла для старых строк.

## Переименование таблицы и столбца

Переименование таблицы выглядит так:

```sql
ALTER TABLE книга RENAME TO каталог;
```

SQLite не только меняет имя, но и обновляет ссылки на таблицу в определениях внешних ключей, представлений и триггеров. Если представление `v_книга` выбирало из `книга`, после переименования оно будет выбирать из `каталог`. Это отличает SQLite от некоторых СУБД, где представление пришлось бы пересоздавать.

Если таблица названа неудачно, переименование возвращает прежнее имя:

```sql
ALTER TABLE каталог RENAME TO книга;
```

Переименование столбца появилось в SQLite 3.25 и работает по той же логике:

```sql
ALTER TABLE книга RENAME COLUMN цена_коп TO цена_продажи_коп;
```

После команды меняется имя в схеме, а значения остаются на месте. Ссылки на столбец в ограничениях внешних ключей, триггерах и представлениях обновляются автоматически. Проверить результат можно уже знакомой командой:

```sql
PRAGMA table_info(книга);
```

В выводе вместо `цена_коп` появится `цена_продажи_коп`, а позиция, тип и признаки ограничений сохранятся.

```sql
SELECT код_книги, название, цена_продажи_коп
FROM книга
ORDER BY код_книги
LIMIT 3;
```

| `код_книги` | `название` | `цена_продажи_коп` |
|---|---|---|
| 204 | Война и мир. Том 1 | 129000 |
| 205 | Война и мир. Том 2 | 129000 |
| 318 | Преступление и наказание | 89000 |

В учебной базе оставим прежнее имя, чтобы не ломать запросы следующих занятий:

```sql
ALTER TABLE книга RENAME COLUMN цена_продажи_коп TO цена_коп;
```

Главная ловушка переименования не в базе, а вне её. Приложение, отчёты и чужие запросы обращаются к старому имени и падают с ошибкой `no such column`. Поэтому переименование делают в три шага: находят все места, где встречается старое имя, договариваются о сроке перехода и только потом меняют схему. В учебной базе удобно держать файл с запросами и просматривать его перед изменением.

Если переименовывают таблицу, на которую ссылаются внешние ключи, полезно проверить их после команды:

```sql
PRAGMA foreign_key_list(позиция_заказа);
```

Команда покажет, на какую таблицу и столбцы ссылается дочерняя таблица. Если в выводе осталось старое имя, значит ссылка не обновилась, и её нужно исправить пересборкой.

::/gate

## Удаление столбца

Удаление столбца появилось в SQLite 3.35:

```sql
ALTER TABLE книга ADD COLUMN код_1с TEXT;
ALTER TABLE книга DROP COLUMN код_1с;
```

Первая команда создаёт служебный столбец, вторая убирает его. В учебной копии `код_1с` нет, поэтому сначала создадим его, чтобы увидеть обе операции. В рабочей базе он мог остаться от переноса из старой программы; тогда первая команда вернёт ошибку `duplicate column name`, и её пропускают. В отличие от добавления, удаление это настоящая работа с данными: SQLite читает каждую строку и собирает её заново без удалённого столбца. На 4800 строках операция пройдёт быстро, на миллионах строк её планируют отдельно.

Не каждый столбец разрешено удалять. Ограничения связаны с тем, что SQLite не хочет оставлять схему в противоречивом состоянии.

| Нельзя удалить | Пример | Почему |
|---|---|---|
| столбец первичного ключа | `код_книги` | исчезнет уникальность строк |
| столбец с `UNIQUE` | `isbn` | пропадёт ограничение уникальности |
| столбец, входящий в индекс | `название` при индексе `idx_книга_название` | индекс станет ссылаться на несуществующий столбец |
| столбец в `CHECK` | `цена_коп` с проверкой `> 0` | проверка перестанет разбираться |
| столбец внешнего ключа | `код_издательства` в `книга` | нарушится ссылочная целостность |
| столбец в выражении индекса или представления | вычисляемый индекс, `v_книга` | выражение станет неполным |
| последний столбец таблицы | единственный `название` | таблица без столбцов невозможна |

Проверим на практике. Попытка удалить `код_книги` даёт ошибку:

```text
Error: cannot drop PRIMARY KEY column: "код_книги"
```

Попытка удалить `название`, по которому построен индекс, даёт другую ошибку:

```sql
CREATE INDEX idx_книга_название ON книга (название);
ALTER TABLE книга DROP COLUMN название;
```

```text
Error: error in index idx_книга_название after drop column: no such column: название
```

Порядок действий в таком случае обратный: сначала удаляют индекс, потом столбец.

```sql
DROP INDEX idx_книга_название;
```

Но удалять название книги почти никогда не нужно. Пример с `название` показывает механизм, а не рекомендацию. После проверки индекс создают заново, потому что он нужен для поиска по названию.

Перед удалением полезно посмотреть индексы таблицы:

```sql
PRAGMA index_list(книга);
```

Если в списке есть индекс, который использует столбец, его удаляют первым. После удаления столбца стоит пересобрать статистику запросов, но об этом речь пойдёт в занятии про индексы.

::gate ALTER TABLE не умеет добавлять CHECK. Как поставить проверку на готовую таблицу?

## Пересборка таблицы

Смена ограничения это создание таблицы с новым описанием и перенос данных. В документации SQLite этот приём называют пересборкой (table rebuild). Он состоит из фиксированной последовательности шагов, и каждый шаг закрывает конкретный риск.

1. **Сохранить копию и пересчитать строки.** `CREATE TABLE книга_backup AS SELECT * FROM книга;` даёт копию данных, но без ограничений. Число строк до и после пересборки должно совпасть.
2. **Выключить внешние ключи.** `PRAGMA foreign_keys = OFF;` обязателен до начала транзакции. С включёнными ключами `DROP TABLE` выполняет неявное удаление строк и может отказать или запустить каскад.
3. **Открыть транзакцию.** `BEGIN;` гарантирует, что при ошибке база вернётся к исходному состоянию.
4. **Создать новую таблицу с нужным описанием.** Имя временное, например `книга_new`.
5. **Перенести строки с явным списком столбцов.** `INSERT INTO книга_new (код_книги, isbn, ...) SELECT код_книги, isbn, ... FROM книга;`
6. **Удалить старую таблицу.** `DROP TABLE книга;`
7. **Переименовать новую.** `ALTER TABLE книга_new RENAME TO книга;`
8. **Пересоздать индексы, триггеры и представления.** При удалении старой таблицы они исчезли вместе с ней. Представления могли остаться, но их нужно проверить.
9. **Проверить ссылки.** `PRAGMA foreign_key_check;` возвращает строки, которые ссылаются на несуществующие родительские записи. Пустой результат означает, что ссылочная целостность не нарушена.
10. **Зафиксировать транзакцию.** `COMMIT;`
11. **Включить внешние ключи.** `PRAGMA foreign_keys = ON;` Возвращать их нужно в той же сессии, иначе проверка ссылок останется выключенной до переподключения.
12. **Сверить данные.** Сравнить число строк, суммы, несколько конкретных записей и попробовать нарушить новое ограничение.

Соберём скрипт для `книга`: усилим проверку цены, сохраним страницы, вес и формат, не потеряем ключи и данные.

```sql
PRAGMA foreign_keys = OFF;
BEGIN;

CREATE TABLE книга_new (
  код_книги INTEGER PRIMARY KEY,
  isbn TEXT NOT NULL UNIQUE,
  название TEXT NOT NULL,
  код_издательства INTEGER NOT NULL REFERENCES издательство(код_издательства),
  код_категории INTEGER NOT NULL REFERENCES категория(код_категории),
  год_издания INTEGER,
  цена_коп INTEGER NOT NULL DEFAULT 0,
  страницы INTEGER,
  вес_грамм INTEGER NOT NULL DEFAULT 0,
  формат TEXT DEFAULT '70x100/16',
  CONSTRAINT chk_цена CHECK (цена_коп > 0),
  CONSTRAINT chk_год CHECK (год_издания BETWEEN 1500 AND 2100)
);

INSERT INTO книга_new (код_книги, isbn, название, код_издательства, код_категории,
                      год_издания, цена_коп, страницы, вес_грамм, формат)
SELECT код_книги, isbn, название, код_издательства, код_категории,
       год_издания, цена_коп, страницы, вес_грамм, формат
FROM книга;

DROP TABLE книга;
ALTER TABLE книга_new RENAME TO книга;
CREATE INDEX idx_книга_название ON книга (название);

PRAGMA foreign_key_check;
COMMIT;
PRAGMA foreign_keys = ON;
```

После выполнения число строк остаётся 4800:

```sql
SELECT COUNT(*) FROM книга;
```

```text
4800
```

Новое ограничение работает. Попытка сохранить нулевую цену даёт ошибку:

```sql
INSERT INTO книга (isbn, название, код_издательства, код_категории, цена_коп)
VALUES ('978-5-0000-99999', 'Тест', 1, 1, 0);
```

```text
Error: CHECK constraint failed: chk_цена
```

Ссылочная целостность тоже на месте: `PRAGMA foreign_key_check` вернул пустой результат. Если бы перенос потерял строки, счётчик это показал. Если бы в `код_издательства` попало значение, которого нет в `издательство`, проверка нашла бы его до фиксации транзакции.

Почему нельзя обойтись `DROP TABLE` без выключения внешних ключей? Потому что `DROP TABLE` при включённых ключах выполняет неявное удаление всех строк. В нашей базе на `книга` ссылаются 185 позиций заказов, 76 строк спецификаций поставок и 4801 связь с авторами, поэтому команда завершается ошибкой:

```text
Error: FOREIGN KEY constraint failed
```

Выключение ключей на время пересборки это не отключение целостности навсегда, а разрешение временно разобрать таблицу. Проверка `foreign_key_check` и включение ключей обратно обязательны.

Отдельно про `SELECT *` в переносе. Если написать `INSERT INTO книга_new SELECT * FROM книга`, порядок столбцов возьмётся из старой таблицы, а новый список может не совпасть. При добавленном столбце данные молча сдвинутся: цена попадёт в страницы, страницы в вес. Явный список столбцов стоит нескольких строк и спасает от самой неприятной ошибки пересборки.

Представления и триггеры после пересборки проверяют отдельно. Представление, которое ссылалось на старую таблицу, после `DROP TABLE` может остаться в схеме, но при обращении выдаст ошибку. Триггеры удаляются вместе с таблицей, их нужно создать заново. Поэтому перед пересборкой выписывают всё, что было построено вокруг таблицы:

```sql
SELECT name, type, sql
FROM sqlite_master
WHERE type IN ('index', 'trigger', 'view');
```

## Как планировать изменение

Изменение структуры редко бывает одной командой. Сначала выясняют, что именно меняется и кто зависит от старой схемы. Для каждого требования выбирают способ и записывают риск.

| Требование | Способ | Главный риск |
|---|---|---|
| добавить необязательное поле | `ADD COLUMN` | старые запросы не знают о поле |
| добавить обязательное поле | `ADD COLUMN` с `DEFAULT`, затем заполнение | неверное значение по умолчанию |
| переименовать поле | `RENAME COLUMN` | внешний код со старым именем |
| убрать служебное поле | `DROP COLUMN` | индекс или ограничение на поле |
| поставить `CHECK` | пересборка | потеря строк при переносе |
| сменить тип | пересборка с преобразованием | несовместимые значения |

Работу выполняют на копии. В sqliteonline.com удобно сделать две вкладки: в одной исходная база, в другой копия, собранная скриптом. Скрипт изменения прогоняют на копии, сверяют число строк и несколько контрольных сумм, и только потом повторяют на рабочей базе. Если база живёт на сервере, выбирают окно обслуживания: пересборка `книга` на 4800 строках занимает секунды, но на таблице заказов за год может занять заметное время и заблокировать запись.

План отката пишут до начала работы. Для учебной базы достаточно копии таблицы и скрипта, который возвращает прежнее описание. Для рабочей базы нужен либо экспорт, либо резервная копия, снятая перед окном обслуживания. Фраза «если что, восстановим» без проверенного способа восстановления планом не считается.

Схему и код меняют вместе. Если приложение уже обращается к `цена_коп`, переименование в `цена_продажи_коп` выпускают одной поставкой с правкой запросов. Пока схема и код расходятся, часть функций работает, часть падает, и найти причину становится труднее, чем при полной остановке.

## Типичные ошибки

- **Менять таблицу без копии.** Ошибка в переносе столбцов обнаруживается после `DROP TABLE`, когда откатить уже нечего. Копия и транзакция дают два независимых способа вернуться.
- **Забыть `PRAGMA foreign_keys = OFF`.** `DROP TABLE` падает с ошибкой внешнего ключа или запускает каскад, который удаляет дочерние строки.
- **Оставить ключи выключенными.** После пересборки `PRAGMA foreign_keys = ON` возвращает проверку. Без неё база принимает битые ссылки до перезапуска.
- **Переносить через `SELECT *`.** Порядок столбцов меняется, и данные сдвигаются без единого сообщения об ошибке.
- **Удалять столбец с индексом.** SQLite отказывает, но новичок начинает искать ошибку в данных, а не в индексе.
- **Переименовать столбец и не обновить запросы.** База работает, приложение падает. Старое имя нужно искать во всём проекте, а не только в схеме.
- **Добавлять `NOT NULL` без значения по умолчанию.** На пустой таблице команда пройдёт, на рабочей с 4800 строками откажет.
- **Считать, что `ALTER TABLE` одинаков во всех СУБД.** В MySQL есть `MODIFY COLUMN` и `ADD CONSTRAINT`, в SQLite их нет. Скрипт переносится между СУБД только после проверки.

> [!PITFALL] Пересборка и внешние ключи
> Выключение `foreign_keys` действует на соединение, а не на базу. Если после пересборки закрыть вкладку и открыть её снова, SQLite снова включит проверку по настройке соединения. Внутри одной сессии `PRAGMA foreign_keys = ON` нужно выполнить явно. В sqliteonline.com каждый запуск скрипта может начинаться с нового соединения, поэтому команду ставят в начало скрипта.

## Проверьте себя

> [!CHECK] В таблице `заказ` нужно заменить `CHECK (статус IN (...))` на более широкий список. Какие шаги обязательны?
> Пересборка: выключить внешние ключи, открыть транзакцию, создать `заказ_new` с новым `CHECK`, перенести строки с явным списком столбцов, удалить старую таблицу, переименовать новую, пересоздать индексы, выполнить `PRAGMA foreign_key_check`, зафиксировать транзакцию и включить ключи. Дочерние `позиция_заказа` должны сохранить свои 185 строк.

> [!CHECK] Почему `ALTER TABLE книга RENAME COLUMN цена_коп TO цена_продажи_коп` безопаснее, чем пересборка?
> Команда меняет только имя в схеме и обновляет ссылки, не переписывая строки. Пересборка нужна там, где меняется тип или ограничение. Но переименование ломает внешний код, который обращается к старому имени, поэтому перед ним ищут все использования.

> [!CHECK] Можно ли добавить столбец `код_поставщика INTEGER NOT NULL REFERENCES поставщик(код_поставщика) DEFAULT 1`?
> Нет. При включённых внешних ключах SQLite не разрешает ненулевое значение по умолчанию для ссылающегося столбца, потому что не может гарантировать существование записи с кодом 1. Сначала добавляют столбец с `NULL`, заполняют допустимыми значениями, затем при пересборке ставят `NOT NULL`.

## Итоги

- `ALTER TABLE` меняет структуру готовой таблицы, не пересоздавая её.
- SQLite поддерживает `ADD COLUMN`, `RENAME TO`, `RENAME COLUMN` и `DROP COLUMN`; смена типа и ограничений требует пересборки.
- Новый столбец с `NOT NULL` требует постоянного значения по умолчанию, а `UNIQUE` и `PRIMARY KEY` добавить нельзя.
- Переименование обновляет ссылки в схеме, но не в приложении, поэтому старые имена ищут по всему проекту.
- Удалить нельзя столбец ключа, индекса, ограничения или последний столбец таблицы.
- Пересборка идёт в транзакции с выключенными внешними ключами, явным списком столбцов, проверкой `foreign_key_check` и включением ключей обратно.

+ Изменяет структуру уже существующей таблицы
- Удаляет все строки таблицы
- Создаёт копию базы данных
- Меняет права пользователя на таблицу
! ALTER TABLE работает со схемой, а не с содержимым таблицы.

- Добавление столбца
- Переименование столбца
- Удаление столбца
! Для смены типа и ограничений таблицу пересобирают.

Q: Что получают существующие строки при добавлении столбца с DEFAULT 0?
+ Значение 0
- Значение NULL
- Ошибку выполнения
- Случайное значение
! Значение по умолчанию подставляется при чтении старых строк.

Q: Почему нельзя добавить NOT NULL без DEFAULT?
+ Старым строкам нечего подставить
- SQLite не поддерживает NOT NULL
- Таблица становится пустой
- Ограничение конфликтует с внешним ключом
! Обязательный столбец требует значения для каждой существующей строки.

Q: Что произойдёт при попытке добавить столбец с UNIQUE?
+ SQLite вернёт ошибку
- Столбец добавится без проверки
- Все значения станут NULL
- Таблица пересоберётся автоматически
! Уникальность нельзя проверить без пересборки и проверки всех строк.

Q: Что обновляет RENAME COLUMN кроме имени в схеме?
+ Ссылки в ограничениях, триггерах и представлениях
- Все запросы в приложении
- Значения столбца
- Индексы других таблиц
! Внешний код база не видит, его обновляют отдельно.

Q: Какой столбец нельзя удалить командой DROP COLUMN?
+ Столбец первичного ключа
- Столбец с типом TEXT
- Столбец, который не используется
- Столбец со значением NULL
! Первичный ключ обеспечивает уникальность строк.

Q: Зачем перед пересборкой выключают внешние ключи?
+ Чтобы DROP TABLE не проверял и не каскадировал дочерние строки
- Чтобы ускорить создание таблицы
- Чтобы отключить проверку типов
- Чтобы сохранить индексы
! Неявное удаление строк при DROP TABLE иначе упрётся в ссылки.

Q: Что показывает PRAGMA foreign_key_check после пересборки?
+ Строки со ссылками на несуществующие родительские записи
- Список всех внешних ключей
- Число строк в таблице
- Значения по умолчанию
! Пустой результат означает, что ссылочная целостность не нарушена.

Q: Какие операции поддерживает ALTER TABLE в SQLite?
+ ADD COLUMN
+ RENAME TO
+ RENAME COLUMN
+ DROP COLUMN
- MODIFY COLUMN
- ADD CONSTRAINT
! Смена типа и добавление ограничения выполняются пересборкой.

Q: Что обязательно сделать при пересборке таблицы?
+ Перечислить столбцы в INSERT явно
+ Пересоздать индексы и триггеры
+ Выполнить PRAGMA foreign_key_check
+ Зафиксировать изменения через COMMIT
- Использовать SELECT * для переноса
- Оставить внешние ключи выключенными
! Явный список и проверка ссылок защищают от сдвига данных и битых связей.

Q: Какие столбцы нельзя удалять?
+ Входящие в индекс
+ Входящие в ограничение CHECK
+ Являющиеся внешним ключом
+ Последний столбец таблицы
- Содержащие только NULL
- Имеющие тип REAL
! Схема не должна остаться со ссылкой на несуществующий столбец.

Q: Что нужно проверить после изменения структуры?
+ Число строк до и после

+ Запросы приложения со старыми именами
+ Сохранность внешних ключей
- Цвет интерфейса sqliteonline
- Количество таблиц в других базах
! Изменение схемы затрагивает данные, ограничения и внешний код.

! PRAGMA table_info возвращает позицию, имя, тип и признаки ограничений.
