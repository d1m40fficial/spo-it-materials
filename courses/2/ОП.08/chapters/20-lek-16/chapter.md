## Приёмка, которая не помещается в одну строку

Четырнадцатого октября на площадку в Твери пришла поставка от ООО «Книжный дом»: двенадцать новых книг, среди них учебник по SQL и два подарочных альбома. В этот же день открылось издательство «Лань», с которым магазин начал работать, а менеджер принял три заказа от школы. Всё это нужно внести в базу до конца смены.

Схема уже готова, ограничения стоят. Не хватает только данных. Для них есть три команды: `INSERT` добавляет строки, `UPDATE` меняет значения в существующих строках, `DELETE` удаляет строки. Вместе их называют языком манипулирования данными, а коротко DML.

**DML меняет содержимое, а не описание таблицы.** Ошибка в `ALTER TABLE` ломает структуру, ошибка в `UPDATE` портит данные, которые потом трудно восстановить. Поэтому каждая команда изменения данных выполняется по одному порядку: сначала `SELECT` с тем же условием, потом изменение, потом проверка числа затронутых строк.

В таблице `книга` цена хранится в копейках целым числом `цена_коп`. В примерах ниже используется это имя. Если в вашей копии столбец назван иначе, замените его во всех запросах, иначе база ответит `no such column`.

## INSERT: как добавить строку

У команды две формы записи. Первая перечисляет столбцы и значения:

```sql
INSERT INTO издательство (название, город)
VALUES ('Лань', 'Санкт-Петербург');
```

Столбец `код_издательства` не указан. Он объявлен как `INTEGER PRIMARY KEY`, поэтому SQLite сам выбирает следующее свободное число. В учебном наборе с восемью издательствами код равен 9. В вашей копии число может отличаться: важен не конкретный код, а то, что база выбрала следующий свободный.

```sql
SELECT код_издательства, название, город
FROM издательство
WHERE название = 'Лань';
```

| `код_издательства` | `название` | `город` |
|---|---|---|
| 9 | Лань | Санкт-Петербург |

Узнать выбранный идентификатор можно сразу после вставки:

```sql
SELECT last_insert_rowid();
```

```text
9
```

`last_insert_rowid()` возвращает идентификатор последней вставки в текущем соединении. Это важно: функция не смотрит на другие соединения и не работает как глобальный счётчик. Если между `INSERT` и проверкой выполнить другую вставку, вернётся уже её номер.

Вторая форма перечисляет значения без имён столбцов:

```sql
INSERT INTO издательство
VALUES (10, 'ОГИЗ', 'Москва');
```

Такой запрос короче, но опаснее. Он требует ровно столько значений, сколько столбцов в таблице, и в том же порядке. После `ALTER TABLE ADD COLUMN` число столбцов меняется, и запрос начинает падать или, что хуже, записывать город в новый столбец. Поэтому в учебных скриптах и в рабочем коде список столбцов указывают всегда.

Несколько строк добавляют одним запросом:

```sql
INSERT INTO поставщик (название, ИНН, город) VALUES
  ('Книжный поток', '7709999999', 'Москва'),
  ('ИП Белова', '4009999999', 'Калуга');
```

Одна команда добавляет две строки, и обе получают свои коды. Такой вариант быстрее серии одиночных вставок: SQLite разбирает запрос один раз и выполняет вставки в одной транзакции.

Столбцы, которых нет в списке, получают значение по умолчанию. Если значения по умолчанию нет, получают `NULL`. Разница между «не указал» и «указал `NULL`» существенна: `DEFAULT` подставит заготовку, а явный `NULL` запишет пустое значение, если ограничение `NOT NULL` это разрешает.

```sql
INSERT INTO книга (isbn, название, код_издательства, код_категории,
                   год_издания, цена_коп)
VALUES ('978-5-0000-99998', 'SQL. Практическое руководство', 9, 5, 2026, 189000);
```

В ответ SQLite сообщает только число добавленных строк, а не их идентификаторы. Если идентификатор нужен приложению, используют `RETURNING`:

```sql
INSERT INTO книга (isbn, название, код_издательства, код_категории,
                   год_издания, цена_коп)
VALUES ('978-5-0000-99997', 'Python. Сборник рецептов', 9, 5, 2026, 175000)
RETURNING код_книги, название, цена_коп;
```

```text
4802|Python. Сборник рецептов|175000
```

`RETURNING` появился в SQLite 3.35 и работает для `INSERT`, `UPDATE` и `DELETE`. В sqliteonline.com он доступен, но в старых учебных сборках SQLite его может не быть. Тогда идентификатор берут через `last_insert_rowid()`.

Данные можно перенести из одной таблицы в другую:

```sql
CREATE TABLE архив_заказа AS
SELECT * FROM заказ WHERE 0;

INSERT INTO архив_заказа
SELECT * FROM заказ WHERE статус = 'отменён';

SELECT COUNT(*) FROM архив_заказа;
```

```text
12
```

Первая команда создаёт пустую копию структуры, вторая переносит двенадцать отменённых заказов. `CREATE TABLE AS SELECT` не копирует ограничения и ключи, поэтому для архива это допустимо, а для рабочей таблицы нет.

Если строка с таким уникальным значением уже есть, обычный `INSERT` завершается ошибкой:

```text
Error: UNIQUE constraint failed: заказ.номер_заказа
```

Для повторного запуска скрипта используют `INSERT OR IGNORE`, который пропускает конфликтующую строку, или `INSERT OR REPLACE`, который заменяет её. У третьего варианта есть точная форма:

```sql
INSERT INTO спецификация_поставки (номер_поставки, код_книги, количество, закупочная_цена)
VALUES (1, 1, 5, 10000)
ON CONFLICT (номер_поставки, код_книги)
DO UPDATE SET количество = количество + excluded.количество;
```

`excluded` это строка, которую пытались вставить. Если строка для книги 1 в поставке 1 уже была, количество увеличится на 5; если нет, появится новая строка. Такой запрос называют UPSERT, то есть update или insert.

У вставки есть режимы конфликта. Они указываются сразу после `INSERT` и решают, что делать при нарушении ограничения.

| Режим | Поведение | Когда подходит |
|---|---|---|
| `OR ABORT` | отменяет команду, изменения в транзакции остаются | поведение по умолчанию |
| `OR FAIL` | отменяет команду, но не откатывает уже вставленные строки | пакетная загрузка с разбором |
| `OR IGNORE` | пропускает конфликтующую строку | повторный запуск скрипта |
| `OR REPLACE` | удаляет старую строку и вставляет новую | обновление справочника |
| `OR ROLLBACK` | откатывает всю транзакцию | строгая загрузка |

`OR REPLACE` легко принять за безопасное обновление. На самом деле он удаляет старую строку, а вместе с ней могут сработать каскады внешних ключей. Если на книгу ссылаются позиции заказа, замена записи в `книга` способна удалить эти позиции. Для обновления лучше явный `UPDATE` или `ON CONFLICT DO UPDATE`.

## UPDATE: изменить существующие строки

`UPDATE` получает имя таблицы, список присваиваний и условие:

```sql
UPDATE книга
SET цена_коп = CAST(ROUND(цена_коп * 1.10) AS INTEGER)
WHERE код_категории = 5;
```

Команда повышает цену на десять процентов для компьютерной литературы. В этой сессии под условие попадает 406 строк: 404 книги категории и две книги, добавленные выше. Проверить число можно функцией `changes()`:

```sql
SELECT changes();
```

```text
406
```

`changes()` возвращает число строк, изменённых последней командой в текущем соединении. Для `UPDATE` это не число просмотренных строк, а число строк, где значение действительно изменилось. Если записать то же самое значение, строка не считается изменённой.

Перед выполнением `UPDATE` полезно выполнить `SELECT` с тем же условием:

```sql
SELECT COUNT(*) FROM книга WHERE код_категории = 5;
SELECT код_книги, название, цена_коп
FROM книга
WHERE код_категории = 5
ORDER BY код_книги
LIMIT 5;
```

Первый запрос показывает, сколько строк будет затронуто, второй позволяет увидеть конкретные записи. Если число неожиданно большое или маленькое, условие проверяют до изменения, а не после.

Условия может не быть:

```sql
UPDATE книга SET формат = '84x108/32';
```

Такая команда меняет все строки таблицы. Иногда это нужно, например при массовом заполнении нового столбца. Но в девяти случаях из десяти забытое `WHERE` это ошибка, которая обнаруживается по жалобе пользователя. SQLite не спрашивает подтверждения и не запоминает, какими были прежние значения.

Вернуть конкретную строку можно через `RETURNING`:

```sql
UPDATE книга
SET цена_коп = 199000
WHERE код_книги = 707
RETURNING код_книги, название, цена_коп;
```

```text
707|Python. К вершинам мастерства|199000
```

Присваивания в одном `SET` вычисляются по старым значениям строки. Если написать `SET цена_коп = цена_коп * 1.1, старая_цена = цена_коп`, во втором присваивании окажется старая цена, а не новая. Это отличается от последовательного выполнения операторов в программе.

Проверка `CHECK` действует и на `UPDATE`:

```sql
UPDATE книга SET цена_коп = -1 WHERE код_книги = 707;
```

```text
Error: CHECK constraint failed: chk_цена
```

Строка остаётся прежней, команда отменяется. Если в одном `UPDATE` несколько строк и одна нарушает ограничение, поведение зависит от режима конфликта. По умолчанию `ABORT` отменяет текущую команду, но не трогает изменения, сделанные ранее в транзакции. Поэтому массовые правки выполняют в транзакции и проверяют результат до `COMMIT`.

Если правил несколько, удобно записать их в `CASE`. Например, поднять цену на десять процентов для учебной литературы, на пять для детской и оставить остальные без изменений:

```sql
UPDATE книга
SET цена_коп = CAST(ROUND(цена_коп * CASE код_категории
    WHEN 3 THEN 1.10
    WHEN 2 THEN 1.05
    ELSE 1.00
  END) AS INTEGER)
WHERE код_категории IN (2, 3);
```

`CASE` возвращает множитель для каждой строки, а `WHERE` ограничивает набор. Такой запрос меняет 842 строки, то есть все книги двух категорий. Если бы `WHERE` не было, цена остальных книг умножилась бы на 1.00 и формально не изменилась, но SQLite всё равно прошёл бы по всем 4800 строкам.

`UPDATE` может опираться на агрегат другой таблицы. Например, поднять цену книг, которые заказывали чаще пяти раз:

```sql
UPDATE книга
SET цена_коп = CAST(ROUND(цена_коп * 1.03) AS INTEGER)
WHERE код_книги IN (
  SELECT код_книги
  FROM позиция_заказа
  GROUP BY код_книги
  HAVING SUM(количество) > 5
);
```

Подзапрос сначала считает итоги по книгам, затем `IN` оставляет только те, чей суммарный заказ больше пяти экземпляров. Агрегаты подробно разберём в отдельной лекции, а здесь важно, что `UPDATE` умеет брать условие из результата другого запроса.

## DELETE: удалить строки

`DELETE` удаляет строки, а не столбцы и не таблицу:

```sql
DELETE FROM позиция_заказа WHERE номер_заказа = 1001;
DELETE FROM заказ WHERE номер_заказа = 1001;
```

Первая команда убирает спецификацию заказа, вторая сам заказ. В учебной схеме у позиций заказа объявлено каскадное удаление, поэтому достаточно второй команды. Но полезно понимать, что происходит с дочерними строками и почему порядок иногда важен.

Проверим удаление книги, на которую ссылаются позиции:

```sql
DELETE FROM книга WHERE код_книги = 204;
```

```text
Error: FOREIGN KEY constraint failed
```

SQLite проверяет внешний ключ только тогда, когда он включён:

```sql
PRAGMA foreign_keys = ON;
```

По умолчанию в SQLite внешние ключи выключены для каждого нового соединения. Это историческая особенность, а не ошибка настройки. Если `PRAGMA foreign_keys` возвращает 0, ограничения не работают, и удалить родительскую строку можно, оставив детей сиротами. В sqliteonline.com команду ставят в начало скрипта, потому что каждый запуск может открывать новое соединение.

Поведение при удалении родителя задаётся в описании внешнего ключа:

| Действие | Что происходит с дочерними строками | Когда выбирают |
|---|---|---|
| `ON DELETE RESTRICT` | удаление запрещено, пока есть дети | справочники, которые нельзя терять |
| `ON DELETE NO ACTION` | то же, но проверка откладывается до конца команды | поведение по умолчанию |
| `ON DELETE CASCADE` | дочерние строки удаляются вместе с родителем | спецификация заказа |
| `ON DELETE SET NULL` | внешний ключ становится `NULL` | необязательная связь |

Для спецификации заказа подходит каскад:

```sql
CREATE TABLE позиция_заказа (
  номер_заказа INTEGER NOT NULL REFERENCES заказ(номер_заказа) ON DELETE CASCADE,
  код_книги INTEGER NOT NULL REFERENCES книга(код_книги),
  количество INTEGER NOT NULL,
  цена_коп INTEGER NOT NULL,
  CONSTRAINT pk_позиция PRIMARY KEY (номер_заказа, код_книги),
  CONSTRAINT chk_количество CHECK (количество > 0),
  CONSTRAINT chk_цена_позиции CHECK (цена_коп >= 0)
);
```

С таким описанием `DELETE FROM заказ WHERE номер_заказа = 1001` удалит заказ и все его позиции одной командой. Проверим:

```sql
DELETE FROM заказ WHERE номер_заказа = 1001;
SELECT COUNT(*) FROM позиция_заказа WHERE номер_заказа = 1001;
```

```text
0
```

Но каскад это не способ скрыть ошибку проектирования. Если удаление заказа не должно уничтожать историю продаж, заказ не удаляют, а переводят в статус `отменён`. Мягкое удаление сохраняет отчётность.

Мягкое удаление требует трёх договорённостей. Во-первых, в таблице появляется признак состояния: `статус`, `удалён_в` или отдельный флаг. Во-вторых, все запросы приложения добавляют условие `WHERE удалён_в IS NULL`, иначе удалённые записи снова попадут в отчёты. В-третьих, удаление перестаёт быть физическим: команда `DELETE` заменяется на `UPDATE`.

```sql
UPDATE заказ
SET статус = 'отменён'
WHERE номер_заказа = 1007 AND статус <> 'выдан';
```

Условие `статус <> 'выдан'` защищает от отмены уже выданного заказа. Число изменённых строк подскажет, сработала ли защита: 0 означает, что заказ не найден или уже выдан. Такой подход удобен для документов, но плох для справочников, где запись действительно нужно убрать.

| Способ | Команда | Плюс | Минус |
|---|---|---|---|
| физическое удаление | `DELETE` | таблица не растёт | история теряется |
| мягкое удаление | `UPDATE` признака | история сохраняется | все запросы усложняются |
| архив | `INSERT` в другую таблицу, затем `DELETE` | рабочая таблица лёгкая | нужна синхронизация |

Удалить все строки тоже можно:

```sql
CREATE TABLE корзина (код INTEGER PRIMARY KEY, номер TEXT);
INSERT INTO корзина (номер) VALUES ('a'), ('b'), ('c');
DELETE FROM корзина;
```

Таблица остаётся, ограничения и индексы остаются, исчезают только строки. Команды `TRUNCATE`, привычной по MySQL, в SQLite нет. `DROP TABLE` удаляет таблицу целиком вместе со структурой, и путать его с `DELETE` нельзя.

`DELETE` тоже поддерживает `RETURNING`:

```sql
DELETE FROM заказ
WHERE статус = 'отменён'
RETURNING номер_заказа;
```

Команда вернёт двенадцать удалённых заказов и благодаря каскаду уберёт их позиции. Перед массовым удалением полезно посчитать строки:

```sql
SELECT COUNT(*) FROM заказ WHERE статус = 'отменён';
```

::gate Как отменить несколько изменений, если третья строка оказалась ошибочной?

## Транзакция: пачка изменений как одно целое

Три команды `DELETE`, `UPDATE` и `INSERT` можно выполнить как одну транзакцию:

```sql
BEGIN;
DELETE FROM позиция_заказа WHERE номер_заказа = 1002;
SELECT COUNT(*) FROM позиция_заказа WHERE номер_заказа = 1002;
ROLLBACK;
```

Внутри транзакции после удаления счётчик показывает 0. После `ROLLBACK` строки возвращаются, и тот же запрос снова показывает 3. База вернулась к состоянию до `BEGIN`.

`COMMIT` фиксирует изменения:

```sql
BEGIN;
UPDATE книга
SET цена_коп = CAST(ROUND(цена_коп * 1.10) AS INTEGER)
WHERE код_категории = 5;
SELECT changes();
COMMIT;
```

Если между `BEGIN` и `COMMIT` произошла ошибка, транзакция остаётся открытой. Ошибка отменяет неудачную команду, но не всю транзакцию. Решение принимает человек или программа: выполнить `ROLLBACK` и повторить всё заново либо исправить ошибку и продолжить. Закрыть вкладку в этот момент нельзя: SQLite откатит незафиксированные изменения, и результат окажется не тем, который ожидали.

Для частичного отката есть `SAVEPOINT`:

```sql
BEGIN;
SAVEPOINT pered_tsenami;
UPDATE книга SET цена_коп = цена_коп * 2;
ROLLBACK TO pered_tsenami;
COMMIT;
```

`ROLLBACK TO` возвращает состояние на момент точки сохранения, не закрывая транзакцию. Так удобно пробовать рискованную правку внутри большой операции. Точка сохранения действует до `COMMIT` или полного `ROLLBACK`; после завершения транзакции её имя исчезает, и повторный откат к ней невозможен. Если точек сохранения несколько, `ROLLBACK TO` возвращает к указанной, а не обязательно к самой последней.

В sqliteonline.com каждый запуск скрипта обычно выполняется в режиме автозафиксации: без `BEGIN` каждая команда фиксируется сразу. Явная транзакция нужна там, где несколько команд должны пройти вместе. Проверить режим можно по поведению: если после ошибки предыдущие изменения остались, значит, каждая команда фиксировалась отдельно.

> [!PITFALL] Транзакция и внешние ключи
> Выключение внешних ключей через `PRAGMA foreign_keys = OFF` нельзя делать внутри транзакции: команда молча не сработает. Сначала выключают ключи, потом открывают транзакцию. После `COMMIT` ключи включают обратно. Это правило понадобится при пересборке таблиц и при массовой загрузке данных.

## Безопасный порядок изменения данных

Опытный администратор не начинает с `DELETE`. Он начинает с вопроса, сколько строк должно измениться и как это проверить.

1. **Сформулировать условие.** Записать его словами: «все отменённые заказы старше января», «книги категории 5», «поставки поставщика 3».
2. **Посчитать строки.** Выполнить `SELECT COUNT(*)` с тем же `WHERE`. Число должно быть ожидаемым.
3. **Посмотреть образец.** Выполнить `SELECT` с `LIMIT 10`. Так видны конкретные записи и возможные сюрпризы.
4. **Открыть транзакцию.** `BEGIN;` даёт возможность отменить всё одной командой.
5. **Выполнить изменение.** `UPDATE` или `DELETE` с тем же условием.
6. **Проверить `changes()`.** Число изменённых строк должно совпасть с числом из шага 2.
7. **Проверить данные.** Повторить `SELECT`: строки должны исчезнуть или получить новые значения.
8. **Зафиксировать.** `COMMIT;` только после проверки.
9. **Сохранить скрипт.** Изменение должно воспроизводиться на копии базы, а не существовать только в истории вкладки.

| Операция | Чем проверить | Что может пойти не так |
|---|---|---|
| `INSERT` | `last_insert_rowid()`, `RETURNING` | пропущен обязательный столбец |
| `UPDATE` | `SELECT` до и после, `changes()` | забытое `WHERE` |
| `DELETE` | `SELECT COUNT(*)`, `changes()` | дочерние строки блокируют удаление |
| `UPSERT` | `RETURNING`, повторный запуск | неверный конфликтный ключ |
| транзакция | `ROLLBACK` на копии | забытый `COMMIT` |

Проверку удобно записывать прямо в скрипт, чтобы она выполнялась вместе с изменением:

```sql
BEGIN;
UPDATE книга
SET цена_коп = CAST(ROUND(цена_коп * 1.10) AS INTEGER)
WHERE код_категории = 5;
SELECT changes() AS изменено;
SELECT код_книги, название, цена_коп
FROM книга WHERE код_категории = 5
ORDER BY код_книги LIMIT 5;
COMMIT;
```

Скрипт выполняет изменение и сразу показывает число строк и образец результата. Если число не совпало с ожидаемым, `COMMIT` заменяют на `ROLLBACK` и разбираются в условии. Такой скрипт удобно хранить рядом с базой: он документирует не только команду, но и способ проверки.

## Типичные ошибки

- **`UPDATE` или `DELETE` без `WHERE`.** Команда затрагивает все строки. Лекарство одно: сначала `SELECT` с тем же условием.
- **`INSERT` без списка столбцов.** После изменения схемы значения попадают не в те поля. Список столбцов пишут всегда.
- **Удаление книги или площадки, на которую ссылаются.** Внешний ключ отказывает. Сначала удаляют дочерние строки или выбирают другое действие при удалении.
- **Выключенные внешние ключи.** `PRAGMA foreign_keys` по умолчанию равен 0. Без явного включения база принимает битые ссылки.
- **Массовая правка без транзакции.** Ошибка на середине оставляет половину строк изменённой, а вторую половину нет.
- **`DELETE` вместо `DROP`.** Первая команда очищает строки, вторая удаляет таблицу. Восстановить структуру после `DROP` сложнее.
- **Опора на порядок строк.** Без `ORDER BY` база не обещает порядок. `LIMIT 10` в `DELETE` без сортировки удаляет произвольные строки.
- **Забытый `COMMIT`.** Изменения видны в текущей вкладке, но после переподключения исчезают.

## Проверьте себя

> [!CHECK] Нужно удалить все заказы со статусом «отменён». Почему перед `DELETE` стоит посчитать строки?
> У заказов есть позиции, и каскад удалит их вместе с заказом. Если условие окажется шире задуманного, исчезнут не только отменённые заказы. `SELECT COUNT(*)` с тем же `WHERE` показывает объём работы до изменения, а `changes()` после подтверждает, что удалено столько же строк.

> [!CHECK] `UPDATE книга SET цена_коп = цена_коп * 1.1` выполнен без `WHERE`. Что произошло и как это исправить?
> Цена выросла у всех 4800 книг. Если транзакция ещё открыта, помогает `ROLLBACK`. Если уже зафиксирована, нужно восстановить прежние значения из копии или разделить текущую цену на 1.1, помня о погрешности округления. Профилактика: `SELECT` с тем же условием и `changes()` до `COMMIT`.

> [!CHECK] Почему `INSERT INTO книга VALUES (...)` может сломаться после добавления столбца?
> Форма без списка столбцов требует значения для каждого столбца в порядке схемы. После `ADD COLUMN` число и порядок меняются, и запрос либо падает, либо записывает данные не в те поля. Явный список столбцов делает запрос устойчивым к изменению схемы.

## Итоги

- `INSERT` добавляет строки; список столбцов защищает от изменения порядка и состава полей.
- `UPDATE` и `DELETE` без `WHERE` затрагивают всю таблицу, поэтому условие проверяют через `SELECT` и `changes()`.
- Внешний ключ запрещает удалять родителя с дочерними строками; каскад или порядок удаления решают задачу.
- `PRAGMA foreign_keys = ON` включает проверку ссылок в текущем соединении.
- Транзакция `BEGIN`, `COMMIT`, `ROLLBACK` делает пачку изменений единым целым, а `SAVEPOINT` позволяет откатить часть.
- Безопасный порядок: посчитать, посмотреть, изменить в транзакции, проверить, зафиксировать.

## Тест по лекции

::quiz
Q: Зачем в INSERT перечисляют столбцы?
+ Чтобы порядок и состав столбцов в таблице не влияли на запрос
- Чтобы ускорить вставку в два раза
- Чтобы отключить проверку ограничений
- Чтобы автоматически создать индексы
! Явный список привязывает значения к именам, а не к позициям.

Q: Что получит столбец, не указанный в INSERT, если у него есть DEFAULT?
+ Значение по умолчанию
- Всегда NULL
- Ошибку выполнения
- Значение из предыдущей строки
! DEFAULT подставляется, когда столбец не указан явно.

Q: Что возвращает last_insert_rowid()?
+ Идентификатор последней вставки в текущем соединении
- Число строк в таблице
- Максимальный идентификатор базы
- Имя последней таблицы
! Функция работает в пределах соединения и не является глобальным счётчиком.

Q: Чем опасен UPDATE без WHERE?
+ Он изменяет все строки таблицы
- Он удаляет таблицу
- Он не выполняет проверку CHECK
- Он требует подтверждения
! Без условия под изменение попадает каждая строка.

Q: Как узнать число строк, изменённых последней командой?
+ SELECT changes()
- SELECT COUNT(*)
- SELECT last_insert_rowid()
- PRAGMA table_info
! changes() возвращает число затронутых строк в текущем соединении.

Q: Что произойдёт при удалении книги, на которую ссылаются позиции заказа?
+ SQLite вернёт ошибку внешнего ключа
- Позиции удалятся автоматически
- Книга удалится, позиции останутся
- Удалятся все книги
! Без каскада родительскую строку нельзя удалить, пока есть дети.

Q: Какое действие внешнего ключа удаляет дочерние строки вместе с родителем?
+ ON DELETE CASCADE
- ON DELETE RESTRICT
- ON DELETE SET NULL
- ON DELETE NO ACTION
! CASCADE передаёт удаление дочерним таблицам.

Q: Что делает ROLLBACK?
+ Отменяет изменения текущей транзакции
- Удаляет все таблицы
- Фиксирует изменения навсегда
- Создаёт резервную копию
! ROLLBACK возвращает состояние на момент BEGIN или SAVEPOINT.

Q: Почему нужно выполнять PRAGMA foreign_keys = ON?
+ По умолчанию SQLite не проверяет внешние ключи
- Это ускоряет все запросы
- Это создаёт первичные ключи
- Это включает автоинкремент
! Проверка ссылок включается для каждого соединения отдельно.

Q: Какие команды изменяют данные в таблицах?
+ INSERT
+ UPDATE
+ DELETE
+ REPLACE
- SELECT
- CREATE TABLE
! SELECT читает данные, а CREATE TABLE меняет схему.

Q: Что входит в безопасный порядок изменения данных?
+ Посчитать строки через SELECT COUNT(*)
+ Посмотреть образец через SELECT с LIMIT
+ Выполнить изменение в транзакции
+ Сверить changes() с ожидаемым числом
- Сразу выполнить DELETE без условия
- Оставить транзакцию открытой
! Проверка до и после защищает от массовой ошибки.

Q: По каким причинам INSERT может завершиться ошибкой?
+ Нарушение NOT NULL
+ Нарушение UNIQUE
+ Нарушение CHECK
+ Ссылка на несуществующего родителя
- Указание списка столбцов
- Использование RETURNING
! Ограничения проверяются при вставке каждой строки.

Q: Что умеет DELETE?
+ Удалить строки по условию WHERE
+ Удалить все строки таблицы
+ Вернуть удалённые строки через RETURNING
+ Завершиться ошибкой при нарушении внешнего ключа
- Удалить таблицу вместе со структурой
- Сбросить автоинкремент без дополнительных команд
! DROP TABLE удаляет структуру, DELETE работает только со строками.

Q: Какое ключевое слово ограничивает строки в UPDATE и DELETE?
= WHERE
= where
! WHERE задаёт условие, без него команда затрагивает все строки.

Q: Какая команда отменяет незафиксированную транзакцию?
= ROLLBACK
= rollback
! ROLLBACK возвращает базу к состоянию до начала транзакции.
