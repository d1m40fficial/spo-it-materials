## Две книги с одним названием

В книжном магазине «Страница» 4800 позиций, и среди них легко найти пару, которую продавец назовёт одинаково. «Чистый код» Роберта Мартина и «Чистый код на Python» Персиваля это разные книги, разные авторы и разные цены, но в разговоре покупатель часто сокращает название до двух слов. Если база хранит книги и ищет их по названию, запрос вернёт две строки там, где нужна одна, а заказ уйдёт не на ту полку.

Проблема не в том, что продавец неточен. Проблема в том, что название не даёт гарантии. Одно и то же название могут иметь переиздание, сокращённый перевод и книга другого автора. Значение, которое должно указывать на строку, обязано быть уникальным не «в среднем», а всегда, при любом пополнении базы.

**Ключ это столбец или набор столбцов, значение которого однозначно определяет строку таблицы.** Не «помогает найти», не «обычно уникально», а именно определяет: одно значение, одна строка. Всё остальное в теме ключей выводится из этого обещания.

У ключа есть ещё второе требование, менее очевидное: минимальность. Если набор из трёх столбцов уникален, но уже первые два дают уникальность, третий в ключе лишний. Ключ должен быть наименьшим набором, который ещё работает. Набор без лишних столбцов называют потенциальным ключом, или ключом-кандидатом.

У одной таблицы потенциальных ключей может быть несколько. У книги это номер ISBN, внутренний артикул магазина и, возможно, пара «издательство плюс номер в каталоге издательства». Все они обещают уникальность. Но **первичный ключ у таблицы только один**: тот потенциальный ключ, который назначен главным. Остальные становятся альтернативными.

## Первичный ключ

Первичный ключ выбирают, когда создают таблицу, и дальше на него опираются все связи. В SQLite объявление выглядит так:

```sql
CREATE TABLE kniga (
  isbn TEXT PRIMARY KEY,
  nazvanie TEXT NOT NULL,
  cena INTEGER NOT NULL
);

INSERT INTO kniga VALUES ('978-5-4461-0990-6', 'Чистый код', 1890);
INSERT INTO kniga VALUES ('978-5-4461-0990-6', 'Чистый код. Второе издание', 2190);
```

Вторая вставка завершится ошибкой:

```text
UNIQUE constraint failed: kniga.isbn
```

СУБД не спрашивает, какое из двух значений правильное. Она отказывает целиком, потому что обещание ключа нарушено. Это и есть главная польза ограничения: ошибку видит тот, кто вводит данные, а не покупатель через месяц.

У первичного ключа четыре свойства, которые полезно держать в голове.

| Свойство | Что означает | Что ломается без него |
|---|---|---|
| Уникальность | двух строк с одним значением нет | запрос возвращает несколько строк |
| Обязательность | значение есть у каждой строки | строку нельзя найти по ключу |
| Неизменность | значение не меняют после вставки | связи указывают в пустоту |
| Минимальность | лишних столбцов в ключе нет | ключ сложнее и тяжелее, чем нужно |

Обязательность в SQLite требует отдельной оговорки. Исторически SQLite разрешает NULL в столбце `TEXT PRIMARY KEY`, если явно не указан `NOT NULL` и таблица не объявлена `WITHOUT ROWID`. Проверим:

```sql
CREATE TABLE t (kod TEXT PRIMARY KEY, nazvanie TEXT);
INSERT INTO t VALUES (NULL, 'первая');
INSERT INTO t VALUES (NULL, 'вторая');
SELECT count(*) FROM t WHERE kod IS NULL;
```

```text
2
```

Две строки без ключа, и СУБД не возражает. В MySQL или PostgreSQL такая вставка была бы отклонена, а в SQLite правило мягче. Поэтому в учебной базе пишите `TEXT PRIMARY KEY NOT NULL` или используйте `INTEGER PRIMARY KEY`, где NULL автоматически заменяется на новый номер. Это не формальность: пустой ключ нельзя связать с другой таблицей, и строка выпадает из всех соединений.

::gate Чем альтернативный ключ отличается от просто ещё одного столбца?

## Альтернативный ключ

Вернёмся к книге. ISBN уникален, но у магазина есть своя жизнь: поставщик присылает накладные с внутренним артикулом, а склад печатает ценники по номеру позиции. Если сделать ISBN первичным ключом, каждая накладная должна нести ISBN, а поставщик может его не знать. Тогда удобнее числовой номер:

```sql
CREATE TABLE kniga (
  id INTEGER PRIMARY KEY,
  isbn TEXT NOT NULL UNIQUE,
  nazvanie TEXT NOT NULL,
  cena INTEGER NOT NULL
);

INSERT INTO kniga (isbn, nazvanie, cena)
VALUES ('978-5-4461-0990-6', 'Чистый код', 1890);

INSERT INTO kniga (isbn, nazvanie, cena)
VALUES ('978-5-4461-0990-6', 'Чистый код. Второе издание', 2190);
```

Ошибка та же, но теперь она относится к альтернативному ключу:

```text
UNIQUE constraint failed: kniga.isbn
```

**Альтернативный ключ это потенциальный ключ, который не выбран первичным, но продолжает быть уникальным.** Его объявляют через `UNIQUE`. Строку можно найти и по `id`, и по `isbn`, и оба запроса вернут одну и ту же запись:

```sql
SELECT * FROM kniga WHERE isbn = '978-5-4461-0990-6';
SELECT * FROM kniga WHERE id = 1;
```

```text
1|978-5-4461-0990-6|Чистый код|1890
```

Зачем держать два ключа, если хватает одного? Причины практические. Первичный ключ обслуживает связи между таблицами, поэтому он должен быть коротким и неизменным. Альтернативный ключ обслуживает поиск и импорт: по ISBN книгу находят в каталоге, по артикулу сверяют накладную. Кроме того, альтернативный ключ защищает от дублей, даже если кто-то вставит строку в обход приложения.

У `UNIQUE` в SQLite есть особенность: несколько значений NULL допускаются, потому что NULL не равен сам себе. Для обязательного альтернативного ключа добавляйте `NOT NULL`. Для необязательного, например ИНН контрагента, пустое значение допустимо, и тогда `UNIQUE` защищает только заполненные строки.

Таблица `sotrudnik` показывает другой случай. Табельный номер уникален и удобен, но 120 сотрудников приходят и уходят, а номера иногда переиспользуют. Если табельный номер сделать первичным ключом, а потом номер старого сотрудника отдадут новому, старые заказы и накладные начнут указывать на другого человека. Числовой `id`, который никогда не переиспользуется, такой ошибки не допускает.

## Составной ключ

До сих пор ключом был один столбец. Но в заказе покупателя одна и та же книга может встретиться только один раз, а разные книги встречаются сколько угодно. Ни номер заказа, ни код книги по отдельности строку не определяют: по номеру заказа найдётся несколько строк, по коду книги тоже. Зато пара значений уникальна.

```sql
CREATE TABLE zakaz_stroka (
  zakaz_id INTEGER NOT NULL,
  kniga_id INTEGER NOT NULL,
  kolichestvo INTEGER NOT NULL,
  cena INTEGER NOT NULL,
  PRIMARY KEY (zakaz_id, kniga_id)
);

INSERT INTO zakaz_stroka VALUES (1001, 5, 2, 1890);
INSERT INTO zakaz_stroka VALUES (1001, 5, 1, 1890);
```

Повтор пары отклоняется:

```text
UNIQUE constraint failed: zakaz_stroka.zakaz_id, zakaz_stroka.kniga_id
```

А одинаковые книги в разных заказах проходят спокойно:

```sql
INSERT INTO zakaz_stroka VALUES (1002, 5, 1, 1890);
SELECT * FROM zakaz_stroka ORDER BY zakaz_id, kniga_id;
```

```text
1001|5|2|1890
1002|5|1|1890
```

**Составной ключ это ключ из двух и более столбцов, уникальный только вместе.** Он нужен там, где сама сущность возникает из пары: строка заказа, спецификация поставки, оценка за курс, назначение сотрудника на площадку.

С составным ключом легко ошибиться в сторону лишнего столбца. Если объявить `PRIMARY KEY (zakaz_id, kniga_id, cena)`, уникальность сохранится, но ключ перестанет быть минимальным: цена не нужна, чтобы отличить строки. Последствия практические. Во-первых, в связях придётся таскать лишний столбец. Во-вторых, изменение цены станет изменением ключа, а ключи менять нельзя. Минимальность не украшение, она защищает от такой ловушки.

Второй соблазн это добавить в таблицу суррогатный `id` и оставить составной ключ без внимания. Если у строки заказа есть `id`, а пара `(zakaz_id, kniga_id)` не объявлена уникальной, в заказ можно дважды добавить одну книгу. Тогда итоговая сумма посчитается дважды, а склад спишет не то количество. Суррогатный ключ не отменяет естественную уникальность, он лишь заменяет её в роли главного идентификатора.

::gate Почему внешний ключ не делает строку дочерней таблицы уникальной?

## Внешний ключ

Первичный и альтернативный ключи отвечают на вопрос «как найти строку в этой таблице». Внешний ключ отвечает на другой вопрос: «на какую строку в другой таблице ссылается эта запись». У книги есть издательство, и в таблице книги хранится номер издательства:

```sql
CREATE TABLE izdatelstvo (
  id INTEGER PRIMARY KEY,
  nazvanie TEXT NOT NULL
);

CREATE TABLE kniga (
  id INTEGER PRIMARY KEY,
  nazvanie TEXT NOT NULL,
  izdatelstvo_id INTEGER NOT NULL REFERENCES izdatelstvo(id)
);
```

`izdatelstvo_id` это внешний ключ. Он не уникален: у «Питера» тысячи книг, и тысячи строк будут содержать одно и то же значение. Он не обязан быть уникальным, потому что ссылка работает в обратную сторону: много книг ссылаются на одно издательство.

**Внешний ключ это столбец, значение которого должно совпадать со значением ключа в другой таблице.** Ссылаться можно на первичный ключ или на альтернативный, то есть на любой объявленный уникальный набор. Ссылаться на обычный столбец нельзя: СУБД не сможет гарантировать, что цель существует и единственна.

Главная тонкость SQLite: внешние ключи по умолчанию выключены. Проверим:

```sql
PRAGMA foreign_keys;
```

```text
0
```

При нуле СУБД принимает ссылку на несуществующее издательство:

```sql
INSERT INTO kniga (nazvanie, izdatelstvo_id) VALUES ('Чистый код', 99);
SELECT * FROM kniga;
```

```text
1|Чистый код|99
```

Строка появилась, хотя издательства с номером 99 нет. Включим проверку и повторим:

```sql
PRAGMA foreign_keys = ON;
INSERT INTO kniga (nazvanie, izdatelstvo_id) VALUES ('Алгоритмы', 99);
```

```text
FOREIGN KEY constraint failed
```

Теперь ссылка проверяется. Заодно меняется поведение удаления: если удалить издательство, у которого есть книги, СУБД откажет. Добавим издательство и книгу, которая на него ссылается:

```sql
INSERT INTO izdatelstvo (id, nazvanie) VALUES (1, 'Питер');
INSERT INTO kniga (nazvanie, izdatelstvo_id) VALUES ('Алгоритмы', 1);

DELETE FROM izdatelstvo WHERE id = 1;
```

```text
FOREIGN KEY constraint failed
```

Это поведение по умолчанию, `ON DELETE RESTRICT`. Его можно заменить на каскад или на обнуление ссылки, но это уже тема целостности. Здесь важно запомнить: **внешний ключ защищает только тогда, когда проверка включена**. В sqliteonline.com включайте `PRAGMA foreign_keys = ON;` в начале сеанса и повторяйте после переподключения.

Внешний ключ бывает составным. В строке поставки ссылка на спецификацию может состоять из пары столбцов, если ключ спецификации составной. Тогда объявление занимает отдельную строку таблицы:

```sql
FOREIGN KEY (postavka_id, kniga_id) REFERENCES postavka_stroka(postavka_id, kniga_id)
```

Смысл тот же: набор значений дочерней строки должен существовать в родительской таблице целиком, а не по частям.

::gate Когда номер строки лучше ISBN, а когда наоборот?

## Естественный и суррогатный ключ

Все ключи делятся на две породы. **Естественный ключ берут из предметной области**: ISBN, ИНН, табельный номер, код площадки, серия и номер паспорта. **Суррогатный ключ придумывает сама база**: целое число, которое не значит ничего, кроме «это строка номер 42».

Соблазн естественного ключа в том, что он уже есть. Не нужно ничего добавлять, а значение что-то говорит человеку: по ISBN видно издание, по коду `MSK` видно Москву. Соблазн суррогатного ключа в том, что он стабилен: номер не меняется, когда меняется название издательства или город площадки.

| Признак | Естественный ключ | Суррогатный ключ |
|---|---|---|
| Источник | предметная область | генерация базой |
| Смысл | несёт информацию | не несёт информации |
| Длина | часто длинный, текстовый | короткое целое |
| Изменчивость | может измениться по внешним правилам | не меняется никогда |
| Проверка | нужна на реальных данных | уникальность гарантирует СУБД |
| Риск | переиспользование и смена формата | лишний столбец и необходимость `UNIQUE` |

Практическое правило для учебной базы такое: **суррогатный первичный ключ плюс `UNIQUE` на естественном**. Это даёт устойчивые связи и одновременно запрещает дубли. Именно так устроена таблица книги: `id` для связей, `isbn` для поиска и защиты от повторов.

Бывают случаи, когда естественный ключ лучше. Справочник площадок мал и стабилен: четыре строки, коды `MSK`, `TVR`, `TUL`, `KLG` понятны и человеку, и программе. Но и здесь есть ловушка: если завтра площадку в Твери переименуют в «Тверь-Центр», код `TVR` останется верным, а вот код, собранный из первых букв названия, придётся менять. Поэтому естественный ключ выбирают, когда он не зависит от того, что можно переписать.

Отдельно стоит сказать про составной естественный ключ. Пара «номер заказа плюс код книги» выглядит естественной, но у неё есть цена: в каждой дочерней таблице придётся хранить оба столбца. Для строки заказа это нормально, потому что сама сущность и есть пара. Для книги это плохо: тащить ISBN и артикул во все накладные тяжело. Поэтому составной ключ оставляют там, где он описывает саму связь, а не там, где он просто удобен.

## Как проверить ключ на своих данных

Ключ проверяют не рассуждением, а запросом. Первый шаг: найти повторы среди кандидатов.

```sql
SELECT isbn, count(*) AS strok
FROM kniga
GROUP BY isbn
HAVING count(*) > 1;
```

Если запрос вернул пустой результат, уникальность на текущих данных есть. Но это ещё не доказательство: завтра придут две книги с одинаковым ISBN из разных источников, и ограничение придётся вводить вместе с очисткой дублей.

Второй шаг: проверить минимальность. Уберите из ключа по одному столбцу и посмотрите, останется ли уникальность. Если пара `(zakaz_id, kniga_id)` уникальна, а `zakaz_id` сам по себе нет, ключ минимален. Если уникален и один столбец, второй лишний.

Третий шаг: проверить неизменность. Задайте вопрос, что произойдёт, если значение изменится. ISBN может измениться при исправлении ошибки в каталоге. Табельный номер меняется при переводе. Название площадки меняется при ребрендинге. Ключ, который меняется, требует каскадного обновления всех ссылок, а это лишняя работа и риск.

Четвёртый шаг: проверить обязательность. В ключе не должно быть NULL. В SQLite для текстового ключа это нужно писать явно, иначе появятся строки, которые невозможно связать.

Пятый шаг: оценить размер. Ключ из длинной строки повторяется в каждой дочерней таблице и в каждом индексе. Целое число в 4 байта дешевле ISBN из 17 символов, особенно когда строк сотни тысяч. На учебных 4800 книгах разница незаметна, но привычка выбирать короткий ключ полезна.

Отдельно проверяют ссылки. Запрос ниже ищет книги, которые ссылаются на несуществующее издательство:

```sql
SELECT count(*) AS sirot
FROM kniga k
LEFT JOIN izdatelstvo i ON i.id = k.izdatelstvo_id
WHERE i.id IS NULL;
```

Ноль означает, что битых ссылок нет. Такой запрос полезен при импорте: внешний ключ проверяет только новые вставки, а старые данные могли попасть в базу до включения `PRAGMA foreign_keys`.

Ещё одна практическая деталь: SQLite не создаёт индекс на столбец внешнего ключа автоматически. Для поиска книг по издательству индекс полезен, а для проверки удаления издательства он ускоряет поиск дочерних строк. На четырёх тысячах книг разница мала, на миллионе становится заметной. Это тема индексов, но связь с ключами прямая: внешний ключ описывает логику, индекс обслуживает скорость.

## Типичные ошибки

**Ключом назначают название.** Названия повторяются, переиздания меняют подзаголовок, а сокращения совпадают. Название годится для поиска, но не для идентификации.

**В таблице два первичных ключа.** Так не бывает: `PRIMARY KEY` объявляют один раз. Если хочется объявить второй уникальный столбец, это `UNIQUE`, то есть альтернативный ключ. Некоторые СУБД позволяют несколько `UNIQUE`, но не несколько `PRIMARY KEY`.

**Внешний ключ путают с первичным.** Внешний ключ не обязан быть уникальным и часто повторяется. Его задача указывать на родителя, а не отличать строки дочерней таблицы.

**Забывают `PRAGMA foreign_keys = ON`.** База принимает битые ссылки, а ошибка всплывает позже, когда удаляют издательство или строят отчёт. Проверка должна быть включена с первого дня.

**Суррогатный ключ считают заменой естественному.** Если у книги есть `id`, но нет `UNIQUE` на ISBN, дубликаты всё равно появятся. Суррогатный ключ различает строки, но не запрещает двум строкам описывать одну и ту же книгу.

**Ключ строят из изменчивых частей.** Код площадки из первых букв города, номер договора с датой, артикул с годом выпуска: всё это меняется при переименовании или продлении. Связи при этом рвутся.

## Итоги

- Ключ однозначно определяет строку и не содержит лишних столбцов.
- Потенциальных ключей может быть несколько, первичный назначают один.
- Альтернативный ключ объявляют через `UNIQUE` и используют для поиска и защиты от дублей.
- Составной ключ нужен там, где сущность задаётся парой значений, например строкой заказа.
- Внешний ключ ссылается на первичный или альтернативный ключ и проверяется только при `PRAGMA foreign_keys = ON`.
- Для связей удобнее суррогатный ключ, а естественную уникальность сохраняют отдельным `UNIQUE`.

::quiz
Q: Что такое ключ таблицы?
+ Столбец или набор столбцов, значение которого однозначно определяет строку
- Любой столбец с уникальными значениями в текущих данных
- Столбец, который чаще всего используют в запросах
- Номер строки, выданный при вставке
! Ключ это обещание уникальности и обязательности, а не удобство запроса.

Q: Сколько первичных ключей может быть у одной таблицы?
+ Один
- Столько, сколько уникальных столбцов
- Два: числовой и текстовый
- Ни одного, если есть внешний ключ
! Первичный ключ один, остальные потенциальные ключи становятся альтернативными.

Q: Чем альтернативный ключ отличается от первичного?
+ Он тоже уникален, но не выбран главным идентификатором строки
- Он не уникален и служит только для поиска
- Он всегда состоит из двух столбцов
- Он ссылается на другую таблицу
! Альтернативный ключ это потенциальный ключ, не назначенный первичным.

Q: Какой столбец в таблице книги объявлен альтернативным ключом в примере занятия?
+ isbn
- nazvanie
- cena
- izdatelstvo_id
! ISBN уникален, но главным ключом выбран числовой id.

Q: Что произойдёт при вставке книги с уже существующим ISBN, если на столбце есть UNIQUE?
+ СУБД отклонит вставку с ошибкой ограничения
- СУБД заменит старое название новым
- СУБД создаст вторую строку с тем же ISBN
- СУБД удалит старую строку
! UNIQUE запрещает повтор значения, а не исправляет данные.

Q: Зачем в строке заказа составной ключ (zakaz_id, kniga_id)?
+ Пара значений уникальна, а каждый столбец по отдельности нет
- Потому что в заказе не может быть двух книг
- Потому что номер заказа меняется при каждой вставке
- Потому что книга не имеет собственного ключа
! Одна книга может быть в разных заказах, а в одном заказе встречается один раз.

Q: Что означает минимальность ключа?
+ В ключе нет столбца, без которого уникальность сохраняется
- Ключ состоит ровно из одного столбца
- Ключ занимает не больше четырёх байт
- Ключ нельзя изменить после создания таблицы
! Минимальный ключ нельзя сократить без потери уникальности.

Q: На какой ключ может ссылаться внешний ключ?
+ На первичный или на объявленный уникальный ключ
- На любой текстовый столбец таблицы
- Только на первичный ключ
- На столбец с наибольшим числом повторов
! Ссылка должна указывать на набор, который гарантированно уникален.

Q: Что произойдёт с внешним ключом в SQLite, если не включить PRAGMA foreign_keys?
+ Ссылки на несуществующие строки будут приниматься
- Все внешние ключи удалятся из схемы
- Внешний ключ станет первичным
- СУБД потребует пересоздать таблицу
! По умолчанию проверка внешних ключей в SQLite выключена.

Q: Какие утверждения о внешнем ключе верны?
+ Он может повторяться в разных строках дочерней таблицы
+ Он может быть необязательным и содержать NULL
+ Он ссылается на ключ родительской таблицы
- Он всегда уникален
- Он запрещает удаление дочерней строки
! Внешний ключ описывает ссылку, а не уникальность дочерней строки.

Q: Какие признаки говорят, что столбец плохо подходит на роль первичного ключа?
+ Значение может измениться после вставки
+ Значение может повторяться у разных объектов
+ Значение может быть пустым
- Значение короткое и целое
- Значение не несёт смысла
! Ключ должен быть уникальным, обязательным и неизменным.

Q: Какие меры защищают таблицу книги от дублей при суррогатном ключе?
+ Объявить UNIQUE на ISBN
+ Проверить повторы запросом GROUP BY с HAVING
+ Оставить NOT NULL на обязательных столбцах
- Отказаться от первичного ключа
- Разрешить NULL в ISBN
! Суррогатный ключ различает строки, но уникальность книги задаёт отдельное ограничение.

Q: Что означает аббревиатура ISBN в контексте ключей?
= международный стандартный номер книги
= уникальный номер издания
! ISBN уникален для издания и потому подходит на роль естественного ключа.

Q: Как называют ключ, придуманный базой и не несущий смысла предметной области?
= суррогатный
= суррогатный ключ
! Суррогатный ключ это число, которое только различает строки.

Q: Какой командой в SQLite включают проверку внешних ключей?
= PRAGMA foreign_keys = ON
= pragma foreign_keys=on
! Без этой команды ссылки на несуществующие строки принимаются.
