## Цель работы

Научиться читать список процессов, определять, какой ресурс занят, и завершать зависшую программу так, чтобы не потерять данные и не остановить лишнее. Работа выполняется на двух гостевых системах стенда: сначала в `ubuntu-lab`, затем в `win-lab`. Результат это отчёт с таблицами наблюдений и разбором трёх ситуаций.

Наблюдение отличается от «посмотреть в диспетчер задач». Нужно связать строку в списке с процессом, процесс с ресурсом, а ресурс с действием. Один и тот же высокий процент процессора может быть полезной работой, ошибкой программы или ожиданием диска, и действия в этих случаях разные.

## Краткие теоретические сведения

Процесс это выполняющаяся программа со своим адресным пространством, открытыми файлами и правами. Ядро хранит сведения о процессе в блоке управления и показывает их через команды и файловую систему `proc`. Поток это единица работы внутри процесса: у него свой стек и регистры, но общая с процессом память.

Состояние процесса в Linux кодируется буквой в колонке `STAT`. `R` означает, что процесс выполняется или готов выполняться. `S` означает прерываемый сон, обычно ожидание ввода или таймера. `D` означает непрерываемый сон, чаще всего ожидание диска, и такой процесс не реагирует на сигналы до завершения операции. `T` означает остановку, `Z` означает зомби, то есть завершившийся процесс, чей родитель ещё не забрал код возврата.

Основные ресурсы, за которые конкурируют процессы, это процессор, память, диск и файловые дескрипторы. Процессор показывает колонка `%CPU`, память колонки `%MEM` и `RSS`, диск косвенно виден по состоянию `D` и по времени ожидания. Число открытых файлов и сокетов показывает каталог `/proc/PID/fd`.

Завершение бывает штатным и принудительным. Сигнал `TERM` просит программу завершиться, и она может сохранить данные. Сигнал `KILL` завершает немедленно и не может быть перехвачен. В Windows `Stop-Process` завершает процесс, а ключ `-Force` действует жёстче. Принудительное завершение оправдано, когда программа не отвечает и данные уже не сохранить, но оно может оставить файлы в несогласованном состоянии.

## Ход работы

### Шаг 1. Зафиксируйте параметры стенда

Откройте терминал в `ubuntu-lab` и выполните команды:

```bash
uname -a
nproc
free -h
uptime
```

Запишите в таблицу версию ядра, число процессоров, общий объём памяти и среднюю загрузку. Эти значения понадобятся, чтобы понимать, на каком фоне идут наблюдения. Если загрузка уже высокая, часть измерений будет искажена.

| Параметр | Значение | Команда |
|---|---|---|
| Версия ядра |  | `uname -a` |
| Число процессоров |  | `nproc` |
| Общая память |  | `free -h` |
| Средняя загрузка |  | `uptime` |

Повторите те же измерения в `win-lab` средствами PowerShell: `Get-ComputerInfo | Select-Object OsName, OsVersion, CsNumberOfLogicalProcessors, CsTotalPhysicalMemory` и `Get-CimInstance Win32_OperatingSystem | Select-Object FreePhysicalMemory, TotalVisibleMemorySize`.

### Шаг 2. Прочитайте дерево процессов

В `ubuntu-lab` выполните:

```bash
ps -ef --forest
ps -eo pid,ppid,stat,pcpu,pmem,etime,comm --sort=-pcpu | head -n 12
```

Первая команда показывает дерево: процесс, его родителя и команду. Вторая сортирует процессы по загрузке процессора и добавляет состояние, время работы и имя программы. Колонка `PPID` показывает родителя, `ETIME` время с момента запуска, `COMM` имя исполняемого файла.

Ниже пример одной строки, разобранной по полям:

```text
  PID  PPID STAT %CPU %MEM     ELAPSED COMMAND
 2143  2101 S     0.0  0.1       03:12 bash
```

Строка означает, что процесс `bash` с идентификатором 2143 запущен процессом 2101, находится в прерываемом сне, почти не использует процессор и память и работает три минуты двенадцать секунд.

Найдите в дереве свою оболочку и терминал, который её запустил. Заполните таблицу для пяти процессов: возьмите два процесса из верхней части списка по процессору, саму оболочку, процесс службы и один фоновый процесс.

| PID | PPID | STAT | %CPU | %MEM | ETIME | Команда | Роль |
|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |  |

Запишите, у каких процессов родитель равен 1. Объясните одной строкой, почему они потеряли исходного родителя.

### Шаг 3. Найдите процесс по имени и определите родителя

Запустите долгую команду в фоне и запомните её идентификатор:

```bash
sleep 600 &
echo $!
```

Команда `echo $!` печатает PID последнего фонового процесса. Найдите его тремя способами: `pgrep -a sleep`, `pidof sleep` и `ps -o pid,ppid,stat,comm -p PID`, подставив полученный номер вместо `PID`.

Сравните ответы. `pgrep` и `pidof` ищут по имени, а `ps -p` показывает конкретный процесс. Если запущено несколько команд `sleep`, по имени найдётся несколько строк, и для точной работы нужен PID.

Заполните карточку процесса:

| Поле | Значение |
|---|---|
| PID |  |
| PPID |  |
| Состояние |  |
| Команда |  |
| Время запуска |  |

Остановите процесс командой `kill PID` и проверьте, что он исчез из списка. Если процесс не найден, команда `kill` вернёт ошибку, и это нормальный результат проверки.

### Шаг 4. Измерьте ресурсы процесса

Запустите процесс, который займёт процессор:

```bash
python3 -c "while True: pass" &
```

Запомните PID из `echo $!`. Затем выполните:

```bash
top -b -n 1 -p PID
cat /proc/PID/status | grep -E "State|VmRSS|VmSize|Threads"
ls /proc/PID/fd | wc -l
```

Первая команда покажет срез по конкретному процессу: процент процессора, память, время. Вторая даст состояние, размер виртуальной и резидентной памяти, число потоков. Третья покажет, сколько файловых дескрипторов открыто.

Повторите измерение через десять секунд. Заполните таблицу и объясните, какие значения изменились.

| Момент | %CPU | VmRSS | Threads | Дескрипторы | Состояние |
|---|---|---|---|---|---|
| Первое измерение |  |  |  |  |  |
| Второе измерение |  |  |  |  |  |

Завершите процесс командой `kill PID`. Убедитесь, что загрузка вернулась к прежнему уровню. Если процесс не завершился, проверьте состояние и только потом применяйте `kill -9`.

### Шаг 5. Понаблюдайте состояния процесса

Запустите `sleep 300 &` и выполните `ps -o pid,stat,wchan:24,comm -p PID`. Процесс будет в состоянии `S`, потому что ждёт таймер. Затем отправьте `kill -STOP PID` и снова посмотрите состояние: появится `T`. Верните работу командой `kill -CONT PID` и завершите процесс.

Отдельно понаблюдайте зомби. Создайте файл `zombie.py` с текстом:

```python
import os, time

pid = os.fork()
if pid == 0:
    os._exit(0)
time.sleep(60)
```

Запустите его в фоне командой `python3 zombie.py &`, запомните PID родителя и посмотрите дочерние процессы:

```bash
ps -o pid,ppid,stat,comm --ppid PID
```

В списке появится строка с состоянием `Z`. Заполните таблицу состояний и укажите причину каждого перехода.

| Состояние | Как получено | Что означает | Почему не занимает процессор |
|---|---|---|---|
| `R` |  |  |  |
| `S` |  |  |  |
| `T` |  |  |  |
| `Z` |  |  |  |

Через минуту родитель завершится, и зомби исчезнет. Если нужно убрать его раньше, завершите родителя.

### Шаг 6. Повторите наблюдение в Windows 10

Перейдите в `win-lab`. Откройте диспетчер задач, вкладку «Подробности», и добавьте столбцы «PID», «Состояние», «Потоки», «Память». Запустите Блокнот и найдите его в списке. Затем выполните в PowerShell:

### Шаг 7. Разберите три ситуации и выберите действие

Ниже журнал наблюдений, снятый на стенде. Значения условные, но набор полей такой же, как в реальной диагностике.

```text
PID  COMMAND   %CPU  %MEM  STAT  WCHAN            Примечание
2311 python3    99.3   1.2  R     -                запущен вручную, растёт CPU
2450 dd          0.0   0.1  D     blkdev_issue_flush  копирует образ на диск
2501 firefox     42.0  18.4  S     futex_wait       открыто 12 вкладок
2555 bash         0.0   0.3  S     wait_woken       ожидает команду

```

Для каждой строки определите ресурс, причину состояния и действие. Первая строка дана как образец.

| PID | Ресурс | Причина | Действие | Обоснование |
|---|---|---|---|---|
| 2311 | процессор | бесконечный цикл в Python | завершить по PID после проверки | процесс не ждёт ввода и не сохраняет данные |
| 2450 |  |  |  |  |
| 2501 |  |  |  |  |
| 2602 |  |  |  |  |

Проверьте на реальном процессе из шага 4, что мягкое завершение через `TERM` срабатывает, а на учебном процессе в состоянии `S` не требует принудительных мер. Для строки 2450 объясните, почему сигнал `TERM` не сработает, пока не завершится операция ввода-вывода, и чем это опасно при выключении питания. Для строки 2602 объясните, почему зомби нельзя убить сигналом и кто его уберёт.

### Шаг 8. Сведите наблюдения в отчёт

Соберите результаты шагов в один документ. В таблице «симптом, процесс, ресурс, команда, действие» должно быть не меньше пяти строк. Отдельно запишите три вывода: какой ресурс оказался самым нагруженным, какие средства диагностики дали ответ быстрее всего и в каком случае принудительное завершение было бы опасным.

## Требования к отчёту

Отчёт оформляется в DOCX и содержит титульный лист с названием работы и фамилией исполнителя, цель работы, параметры стенда, таблицы наблюдений, разбор трёх ситуаций, снимки экрана и выводы.

В отчёте должны быть:

- таблица параметров `ubuntu-lab` и `win-lab`;
- таблица пяти процессов с полями PID, PPID, STAT, CPU, память, время, команда;
- таблица ресурсов процесса с двумя измерениями;
- таблица состояний `R`, `S`, `T`, `Z`;
- таблица соответствия средств Ubuntu и Windows;
- разбор ситуаций с обоснованием действия;
- пять-семь предложений вывода.

Снимки экрана должны показывать команду и её вывод целиком, а не только фрагмент. На снимке диспетчера задач должны быть видны столбцы PID, состояние и потребление памяти. Под каждым снимком укажите, что на нём проверяется.

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

- **5**: заполнены все таблицы, состояния объяснены верно, ресурс определён по данным, действия обоснованы, снимки показывают команды и результат, вывод опирается на наблюдения.
- **4**: работа выполнена полностью, но в одной таблице пропущены поля или объяснение состояния дано без причины, а вывод повторяет данные без обобщения.
- **3**: таблицы заполнены частично, состояние процесса указано без объяснения, ресурс определён только по проценту процессора, обоснование действия отсутствует.
- **2**: работа не выполнена или выполнена фрагментарно без наблюдений на стенде.
- **1**: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
