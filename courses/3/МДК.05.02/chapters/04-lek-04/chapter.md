## Ошибка на первой минуте

Новый разработчик открывает проект «Склад+» в VS Code, нажимает «Запустить» и получает `ModuleNotFoundError: No module named 'flask'`. Он устанавливает Flask командой `pip install flask`, повторяет запуск и видит ту же ошибку. На его компьютере два Python: один из Microsoft Store, другой из установщика с сайта python.org. VS Code запускает один, терминал вызывает другой, а `pip` ставит пакет в тот, который нашёл первым, не обязательно в тот, которым выполняется код.

Полчаса уходит на переустановку библиотеки, которая уже установлена. Причина не в коде и не в библиотеке. Причина в том, что никто не сказал, какой интерпретатор является интерпретатором проекта.

**Интерпретатор это конкретный файл программы, который выполняет код, и проект должен запускаться тем файлом, для которого установлены зависимости.** Пока это не зафиксировано, каждая команда может попасть в другое окружение, а ошибка будет выглядеть как дефект программы.

Хуже всего то, что ошибка воспроизводится не у всех. У одного разработчика запуск работает, у другого падает, и оба уверены, что дело в коде. На самом деле у них разные файлы `python.exe`, разные наборы библиотек и разные переменные среды. Поэтому первое, что проверяют при такой жалобе, это версию и путь интерпретатора, а не исходники.

Проверка быстрая и состоит из двух команд: `where python` в терминале и запуск скрипта с `sys.executable`. Если пути не совпадают с папкой `.venv`, дальше искать ошибку в коде бессмысленно. Сначала приводят окружение к одному интерпретатору, потом повторяют сценарий. В половине случаев ошибка исчезает вместе с неправильным окружением.

У этой истории есть неприятное продолжение. Если поставить библиотеку в глобальный Python, она может понадобиться другому проекту в другой версии. Обновление для одной задачи ломает вторую, и обе команды начинают спорить о том, чей пакет правильный. Поэтому проблема окружения решается не дисциплиной отдельного разработчика, а устройством проекта: у каждого проекта должно быть своё место для зависимостей.

## Интерпретатор: что запускается на самом деле

Команда `python` не является программой. Это имя, которое оболочка ищет в переменной `PATH` и превращает в путь к исполняемому файлу. Если в `PATH` первым стоит Python из Microsoft Store, запустится он, даже если рядом установлен другой. Поэтому вопрос «какая у меня версия Python» имеет смысл только вместе с вопросом «какой файл запустился».

Оболочка перебирает каталоги из `PATH` слева направо и останавливается на первом файле с подходящим именем. На Windows к имени добавляются расширения из `PATHEXT`, обычно `.COM`, `.EXE`, `.BAT`, `.CMD`. На Linux и macOS разделитель другой, но правило то же: побеждает первый найденный файл. Команда `where python` в Windows и `which -a python` в Linux показывают все найденные варианты по порядку, а не только выбранный.

Порядок в `PATH` объясняет половину странных ошибок. Установщик может добавить новую версию, но старая останется выше в списке. Тогда `python --version` показывает 3.11, хотя в проекте уже создано окружение с 3.13, а `pip` ставит пакеты в 3.11. Команда `python -c "import sys; print(sys.executable)"` показывает, какой файл реально работает, и это надёжнее, чем гадать по версии.

| Откуда берётся python | Как проверить | Чем опасен |
|---|---|---|
| установщик с python.org | `python --version`, `where python` | несколько версий в PATH |
| Microsoft Store | `where python` показывает пакет WindowsApps | права на установку пакетов ограничены |
| виртуальное окружение | третья строка скрипта даёт True | нужно активировать или указать путь |
| VS Code выбрал сам | строка состояния или палитра команд | не совпадает с терминалом |

На Windows есть ещё один слой, о котором забывают. Пакет Python из Microsoft Store создаёт в каталоге `WindowsApps` небольшой файл `python.exe`, который является не интерпретатором, а точкой запуска приложения. Такой файл может открыть магазин или выдать сообщение вместо выполнения кода. Официальная документация Python рекомендует отключать такие псевдонимы в параметрах Windows, если установлен обычный интерпретатор. Это не ошибка Python, а особенность платформы, и она тоже выглядит как «Python не работает».

Для выбора версии на Windows существует отдельная программа `py`. Она читает установленные версии, умеет запускать нужную через ключ `py -3.13` и учитывает строку `#!` в начале файла. Лончер удобен, когда на машине несколько версий и нужно явно назвать одну. Но он не решает главную задачу проекта: он выбирает версию Python, а не набор библиотек. Зависимости всё равно должны жить в окружении проекта.

### Что происходит после запуска файла

CPython, самая распространённая реализация Python, не выполняет текст построчно напрямую. Сначала он разбирает исходник в дерево разбора, затем превращает его в байт-код, компактные инструкции для виртуальной машины, и только потом исполняет этот байт-код в цикле вычислений. Байт-код сохраняется рядом с исходником в каталоге `__pycache__` с расширением `.pyc`. При следующем запуске интерпретатор проверяет, не изменился ли исходный файл, и при совпадении берёт готовый байт-код.

Кэш объясняет две вещи. Во-первых, первый запуск большого проекта чуть медленнее последующих. Во-вторых, удаление `__pycache__` безопасно: это не исходники и не библиотеки, а производные файлы, которые создаются заново. Если программа ведёт себя странно после правки, кэш почти никогда не виноват, потому что интерпретатор сверяет время и размер файла. Виноват обычно другой файл, который импортируется вместо исправленного.

Куда интерпретатор смотрит при импорте, описывает список `sys.path`. В начале списка стоит каталог запущенного скрипта, затем пути из переменной `PYTHONPATH`, затем стандартная библиотека и каталоги с пакетами. Если запустить `python src/sklad/__main__.py`, первым в поиске окажется `src/sklad`, а не корень проекта, и пакет `sklad` может не найтись. Запуск `python -m sklad` добавляет текущий каталог и находит пакет правильно. Это ещё один довод в пользу единой команды запуска.

У списка поиска есть обратная сторона. Файл с именем `random.py` в рабочем каталоге перекроет стандартный модуль `random`, потому что локальный каталог стоит раньше библиотеки. Программа начнёт падать в неожиданном месте, а трассировка будет указывать на чужой код. Поэтому имена файлов проекта пишут по правилам [PEP 8](https://peps.python.org/pep-0008/), не повторяют имена стандартных модулей, а запуск выполняют из предсказуемого каталога.

Проверить окружение можно из самого кода. Скрипт печатает версию, имя исполняемого файла и признак того, работает ли он внутри виртуального окружения.

```python
import os
import sys

print(sys.version.split()[0])
print(os.path.basename(sys.executable))
print(sys.prefix != sys.base_prefix)
```

Запуск на учебной машине даёт такой результат.

```text
3.13.14
python.exe
False
```

Третья строка `False` означает, что интерпретатор глобальный: его библиотеки лежат в общей папке системы, а не в проекте. Именно так выглядит окружение, в котором `pip install` может поставить пакет для одного проекта и сломать другой.

::figure python-path | Как оболочка выбирает файл python и чем отличаются sys.executable, sys.prefix и sys.base_prefix. Слева порядок поиска в PATH, справа три адреса, которые полезно сверить перед разбором ошибки импорта.

Версия важна не сама по себе, а вместе с зависимостями. Код, написанный для Python 3.12, обычно работает на 3.13, но библиотека может требовать конкретную версию. Если на учебной машине 3.13, а на стенде 3.11, расхождение лучше обнаружить до выпуска. Ещё важнее то, что разные версии Python не разделяют установленные пакеты: окружение, созданное для 3.13, не годится для 3.11, даже если папка называется одинаково.

::gate Что произойдёт, если активировать окружение, но запустить файл чужим интерпретатором?

## Виртуальное окружение

Виртуальное окружение это отдельная папка с копией интерпретатора и своим набором библиотек. Проект получает собственные зависимости, а глобальный Python остаётся нетронутым. Для «Склад+» окружение создают в папке `.venv` внутри проекта.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python l4_env.py
```

После активации приглашение терминала начинается с имени окружения, а третья строка скрипта меняется на `True`.

```text
3.13.14
python.exe
True
```

Теперь `python` указывает на файл внутри `.venv`, а `pip` ставит пакеты туда же. Проверить состав установленного можно командой `python -m pip list`: она покажет только библиотеки проекта, а не весь набор системы.

Устройство окружения простое. В папке появляется свой `python.exe`, файл `pyvenv.cfg` с путём к базовому интерпретатору и каталог `Lib/site-packages` для библиотек. В `pyvenv.cfg` есть строки `home` и `include-system-site-packages`; вторая почти всегда равна `false`, и это значит, что глобальные пакеты проекту не видны. Пакеты, установленные в окружение, не видны глобальному Python, а глобальные пакеты не видны проекту, если их специально не добавить. Такая изоляция и есть смысл venv: обновление библиотеки для одного проекта не ломает другой.

Механизм активации часто понимают неверно. Скрипт `Activate.ps1` не меняет файлы проекта и не переключает VS Code. Он меняет переменные текущей оболочки: добавляет каталог `Scripts` в начало `PATH`, запоминает путь в `VIRTUAL_ENV` и подменяет приглашение. Команда `deactivate` возвращает прежние значения. Поэтому активация действует только в том окне терминала, где она выполнена, и исчезает при закрытии окна.

| Действие | Команда | Результат |
|---|---|---|
| создать окружение | `python -m venv .venv` | папка `.venv` с интерпретатором |
| активировать в PowerShell | `.\.venv\Scripts\Activate.ps1` | `python` указывает в `.venv` |
| запустить без активации | `.\.venv\Scripts\python.exe файл.py` | тот же интерпретатор |
| посмотреть пакеты | `python -m pip list` | список библиотек окружения |
| зафиксировать зависимости | `python -m pip freeze` | строки для файла зависимостей |

В PowerShell активация может быть запрещена политикой выполнения сценариев. Тогда есть два выхода: разрешить сценарии для текущего пользователя командой `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` или не активировать окружение вовсе, а вызывать интерпретатор напрямую.

```powershell
.\.venv\Scripts\python.exe l4_env.py
```

Прямой вызов даже надёжнее: он не зависит от того, что сейчас активировано в терминале. Активация удобна для интерактивной работы, а в скриптах сборки и в задачах VS Code путь к интерпретатору указывают явно.

### pip и его ловушки

Команда `pip` это отдельная программа, а не часть интерпретатора. У неё есть собственный путь запуска, и в окружении она тоже своя. Запись `python -m pip install` надёжнее, потому что сначала выбирается интерпретатор, а затем внутри него запускается модуль pip. Запись `pip install` полагается на то, что первая найденная команда pip принадлежит нужному Python. На машине с несколькими версиями это не гарантировано.

Список зависимостей получают командой `python -m pip freeze`. Она печатает установленные пакеты с точными версиями, и этот список сохраняют в файле проекта. На другой машине окружение создают заново и ставят пакеты из списка. Так повторяют не папку `.venv`, а состав библиотек, что надёжнее и переносимо между системами.

```powershell
python -m pip freeze > requirements.txt
python -m pip install -r requirements.txt
```

У этого способа есть границы. `pip freeze` перечисляет всё, что установлено, включая транзитивные зависимости, и не различает прямые и косвенные. Файл получается точным, но не объясняет, зачем нужен каждый пакет. Кроме того, колёса пакетов зависят от платформы и версии Python: список, собранный на Windows, не гарантирует ту же сборку на Linux, если для пакета нет бинарного колеса. Поэтому в больших проектах рядом с `requirements.txt` появляются файлы блокировки с хешами и отдельные наборы для разработки и эксплуатации.

Папку `.venv` не хранят в Git. Она большая, зависит от операционной системы и легко создаётся заново из списка зависимостей. В репозитории лежит файл с версиями, а окружение каждый раз разворачивает у себя. Каталог `.venv` добавляют в `.gitignore` вместе с `__pycache__` и файлами секретов.

### Когда глобальная установка запрещена

Долгое время `pip install` в системный Python был обычной практикой, и именно из-за неё возникали конфликты с пакетным менеджером операционной системы. Системный пакет и пакет из pip могли претендовать на один файл, а обновление одного ломало другой. В 2023 году эту проблему оформили в PEP 668: интерпретатор может быть помечен как externally managed, то есть управляемый извне.

Практический результат выглядит так. На дистрибутиве, который помечает системный Python как externally managed, команда `pip install flask` вне окружения завершается ошибкой с текстом `error: externally-managed-environment` и предложением создать venv. Это не поломка, а защита: система сообщает, что глобальные пакеты принадлежат дистрибутиву. Правильное решение состоит из двух шагов: создать окружение и поставить библиотеку в него. Ключ `--break-system-packages` существует, но его использование возвращает ту самую проблему, от которой защищает маркер.

| Инструмент | Что даёт | Чем платим |
|---|---|---|
| `venv` из стандартной библиотеки | ничего не нужно устанавливать | только Python, без системных библиотек |
| `virtualenv` | быстрее создаёт, поддерживает старые версии | отдельная зависимость |
| `conda` | ставит не только Python-пакеты | тяжёлый дистрибутив и свой формат окружений |
| `uv` | очень быстрое разрешение зависимостей | новый инструмент в учебном процессе |

Для учебного проекта достаточно `venv`: он входит в Python, не требует установки и ведёт себя одинаково на всех учебных машинах. Остальные инструменты стоит знать, но выбирать их нужно под задачу, а не потому, что они быстрее в демонстрации.

::figure venv-switch | Переключите «Глобальный Python» и «Проект .venv»: сравните sys.prefix, каталог site-packages и адрес, куда ставит пакеты pip. Активация меняет только текущую оболочку, поэтому в другом окне терминала картина может быть прежней.

## VS Code: папка, интерпретатор, терминал

VS Code не является средой выполнения Python. Он редактор, который запускает выбранный интерпретатор и показывает результат. Расширение Python добавляет к редактору запуск, отладку, подсказки и просмотр тестов, но само выполнение остаётся задачей интерпретатора.

Полезны и аннотации типов. [PEP 484](https://peps.python.org/pep-0484/) описывает запись `def available(positions: int, reserved: int) -> int`. Интерпретатор такую аннотацию не проверяет, но Pylance в VS Code читает её и предупреждает о несовпадении. Это подсказка разработчику, а не замена проверки во время выполнения.

Первое действие в новом проекте это открыть папку проекта целиком, а не отдельный файл. От корня папки зависят поиск настроек, терминал и запуск тестов. Если открыть только `main.py`, VS Code считает рабочей папкой каталог этого файла, и относительные пути вроде `data/demo.sqlite` начнут вести не туда.

Второе действие: выбрать интерпретатор. Это делают через палитру команд: `Python: Select Interpreter`, затем пункт с путём внутри `.venv`. Выбор сохраняется в служебном хранилище рабочей папки, а строка состояния показывает версию и имя окружения. После выбора стоит открыть новый терминал: старый мог быть создан до переключения и сохранить прежний `PATH`.

| Элемент | Файл | Зачем |
|---|---|---|
| выбранный интерпретатор | `.vscode/settings.json` | запуск и подсказки используют `.venv` |
| конфигурация запуска | `.vscode/launch.json` | аргументы, рабочая папка, режим отладки |
| терминал | вкладка Terminal | команды выполняются в окружении проекта |
| задачи | `.vscode/tasks.json` | повторяемые команды сборки и тестов |

Настройку интерпретатора можно записать в `.vscode/settings.json`, чтобы она применялась у всех, кто открыл проект.

```json
{
  "python.defaultInterpreterPath": "${workspaceFolder}/.venv/Scripts/python.exe"
}
```

Путь относительный: `${workspaceFolder}` подставляет корень открытой папки. На Linux и macOS путь к интерпретатору другой, поэтому в общем проекте такие настройки дополняют или описывают в README. Для учебной машины с Windows указанного пути достаточно. Важно понимать, что `defaultInterpreterPath` задаёт путь по умолчанию, пока интерпретатор не выбран вручную; ручной выбор может иметь приоритет, поэтому фактический путь всегда проверяют в строке состояния.

Настройки VS Code бывают пользовательскими и на уровне рабочей папки. Пользовательские действуют во всех проектах, настройки папки лежат в `.vscode/settings.json` и применяются только здесь. Чем больше уровней, тем выше приоритет у более конкретного: настройка папки перекрывает настройку пользователя. Если интерпретатор выбран в пользовательских настройках, он может перебить настройку проекта. Поэтому выбор `.venv` сохраняют именно на уровне папки, а не глобально.

Файл `.vscode/launch.json` описывает запуск для отладчика. В нём указывают тип `python`, модуль или путь к программе, рабочую папку и аргументы командной строки.

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Склад+: запуск",
      "type": "python",
      "request": "launch",
      "module": "sklad",
      "cwd": "${workspaceFolder}",
      "console": "integratedTerminal",
      "env": { "SKLAD_ENV": "dev" }
    }
  ]
}
```

Рабочая папка важна для относительных путей: если она равна корню проекта, база `data/demo.sqlite` находится, а если указана папка `src/`, тот же путь ведёт в другое место. Конфигурацию хранят в репозитории, чтобы у всей команды запуск был одинаковым. Секреты в `launch.json` не пишут: файл попадает в Git, а переменные окружения с паролями задают отдельно.

Похожий файл `.vscode/tasks.json` хранит повторяемые команды: прогон тестов, проверку стиля, сборку. Задача запускается из меню и не требует помнить длинную строку. Для проекта «Склад+» достаточно двух задач: `python -m pytest` и `python -m sklad`. Обе выполняются выбранным интерпретатором, поэтому задача и терминал дают одинаковый результат.

```json
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "тесты",
      "type": "shell",
      "command": "${workspaceFolder}/.venv/Scripts/python.exe",
      "args": ["-m", "pytest", "-q"],
      "group": { "kind": "test", "isDefault": true }
    }
  ]
}
```

Терминал VS Code наследует окружение, но не всегда переключается на новый интерпретатор сам. Если после выбора `.venv` в терминале всё ещё работает глобальный Python, терминал нужно открыть заново. Проверка та же: запустить скрипт и посмотреть третью строку. Настройка `python.terminal.activateEnvironment` включает автоматическую активацию в новых терминалах, но она не отменяет проверку.

Есть компромисс между общей и личной настройкой. Если хранить в репозитории всё, включая пути и вкусы, проект становится неудобным для коллег с другой системой. Если не хранить ничего, каждый новый участник проходит те же полчаса с `ModuleNotFoundError`. Рабочее правило простое: в репозитории лежит то, что нужно для воспроизводимого запуска, а личные темы, шрифты и сочетания клавиш остаются в пользовательских настройках.

## Отладка: точка останова и шаги

Отладчик останавливает программу в выбранном месте и показывает состояние. Точка останова ставится щелчком слева от номера строки. Запуск через `F5` начинает отладку, запуск через кнопку треугольника выполняет программу без остановок.

Внутри связь устроена через протокол отладки. Редактор не умеет управлять Python напрямую: он отправляет команды адаптеру отладки, а тот уже общается с процессом Python. В расширении Python эту роль выполняет `debugpy`. Протокол DAP задаёт общий язык команд: поставить точку, продолжить, получить стек, прочитать переменную. Благодаря этому один и тот же интерфейс VS Code работает с Python, C#, JavaScript и другими языками, хотя адаптеры у них разные.

Когда программа остановилась, доступны несколько действий. Шаг с заходом (`F11`) входит внутрь вызываемой функции. Шаг через (`F10`) выполняет строку целиком и остаётся в текущей функции. Шаг с выходом (`Shift+F11`) доходит до конца текущей функции и возвращается к вызывающему коду. Продолжить (`F5`) идёт до следующей точки останова.

| Действие | Клавиша | Когда нужно |
|---|---|---|
| продолжить | F5 | до следующей точки останова |
| шаг через | F10 | выполнить строку, не заходя в функцию |
| шаг с заходом | F11 | проверить, что происходит внутри функции |
| шаг с выходом | Shift+F11 | вернуться к вызывающему коду |
| остановить | Shift+F5 | прервать отладку |

В панели переменных видно текущие значения, в панели стека вызовов цепочку функций, которые привели к этой строке. Стек читают сверху вниз: верхняя строка это место, где программа стоит сейчас, нижние показывают, кто её вызвал. В панели `Watch` можно добавить выражение и следить за ним, а в консоли отладки вычислить значение, не меняя код.

У точек останова есть полезные варианты. Условная точка срабатывает только при выполнении выражения, например `site == "Тверь"`. Точка по счётчику останавливает программу на пятом проходе цикла. Точка журнала печатает сообщение и не останавливает выполнение. Всё это экономит время, когда дефект проявляется только на одном наборе данных.

Отладчик полезен, когда непонятно, почему значение стало не тем. Он показывает факт, а не догадку. Печать через `print` тоже работает, но требует правок в коде и не даёт посмотреть стек. Для одной переменной хватит печати, для разбора цепочки вызовов нужен отладчик.

Разберём сценарий. В отчёте по Туле вместо 1110 появляется 1150. Точку останова ставят на строку `return positions - reserved` в функции `available`. После запуска отладчик останавливается, и в панели переменных видно: `positions` равно 1150, `reserved` равно 0. Значит, значение резерва не дошло до функции. Шаг с выходом возвращает в `report`, где видно, что из строки базы взяты только позиции, а резерв потерян при разборе. Причина найдена по значениям, а не по догадке.

У отладки есть ограничения. Она меняет timing: остановка в неудачном месте скрывает гонку потоков или превращает её в другую ошибку. Она не входит в код, написанный на C, если для расширения нет отладочных символов. Она не видит дочерние процессы, пока не включена соответствующая настройка. И она объясняет только один запуск. Поэтому после находки добавляют проверку `available(1150, 40) == 1110`, и в следующий раз дефект ловил бы тест, а не человек с точкой останова.

Отладка не заменяет тест. Она объясняет один конкретный запуск, а тест закрепляет правило для всех запусков. Хорошая последовательность такая: воспроизвести дефект, остановиться в месте, где значение уже неверно, подняться по стеку к месту, где оно стало неверным, сформулировать причину и закрыть её тестом.

## Как читать трассировку

Трассировка это отчёт интерпретатора о том, где и почему программа остановилась. Она выглядит пугающе, но читается по правилам. Ниже скрипт, который должен показать остаток по площадке, но обращается к площадке, которой нет в словаре.

```python
def available(positions, reserved):
    return positions - reserved


def report(site):
    data = {"Тула": (1150, 40), "Калуга": (570, 15)}
    positions, reserved = data[site]
    return available(positions, reserved)


print(report("Тверь"))
```

Запуск завершается ошибкой.

```text
Traceback (most recent call last):
  File "l4_bug.py", line 11, in <module>
    print(report("Тверь"))
          ~~~~~~^^^^^^^^^
  File "l4_bug.py", line 7, in report
    positions, reserved = data[site]
                          ~~~~^^^^^^
KeyError: 'Тверь'
```

Читать нужно снизу. Последняя строка `KeyError: 'Тверь'` называет тип ошибки и значение, которого не хватило. Выше два кадра: первый показывает строку 11, где вызван `report`, второй строку 7, где произошёл сбой. Порядок кадров обратный порядку выполнения: сверху то, что было раньше, снизу то, что случилось последним.

Номер строки в нижнем кадре указывает на `data[site]`. Значение `site` равно `"Тверь"`, а в словаре есть только Тула и Калуга. Причина не в функции `available`, до неё управление не дошло. Причина в том, что код не проверил наличие площадки.

Под строкой кода в трассировке стоят знаки `^^^^`. Они подчёркивают выражение, на котором произошёл сбой, и помогают не гадать, что именно вычислялось. В примере каретка стоит под `data[site]`, а не под всем присваиванием. Это ускоряет чтение длинной строки с несколькими вызовами.

Верхние кадры нужны, чтобы понять путь. По ним видно, из какого обработчика вызвана функция и какие аргументы переданы. Но искать правку всегда начинают с нижнего кадра: именно там программа столкнулась с реальностью. Если нижний кадр находится в чужой библиотеке, смотрят кадр выше него, то есть последний свой вызов.

::figure traceback-reader | Нажимайте кадры трассировки снизу вверх: подсветится строка и появится объяснение, что из неё следует. Схема показывает, почему тип ошибки читают в последней строке, а причину ищут в нижнем кадре.

Бывает, что ошибка вызвана другой ошибкой. Тогда интерпретатор показывает две трассировки подряд, соединённые строкой `The above exception was the direct cause of the following exception`. Читают их так же снизу: нижняя часть говорит, что произошло в итоге, верхняя показывает исходную причину. При обработке исключений связь сохраняют через `raise ... from ...`, иначе причина теряется и остаётся только внешнее сообщение.

```python
try:
    count = int(text)
except ValueError as error:
    raise ValueError(f"Количество должно быть числом: {text!r}") from error
```

Конструкция `from None` делает обратное: она скрывает исходную ошибку, когда она не нужна пользователю. Это допустимо на границе программы, но опасно внутри модуля, потому что расследование теряет первую улику.

В Python 3.11 появились две возможности, которые меняют чтение отчётов. Исключения можно объединять в группу через `ExceptionGroup`, а перехватывать по частям конструкцией `except*`; тогда в трассировке видно несколько независимых ошибок, а не одна. Второе новшество это `add_note`: к исключению можно добавить пояснение, которое появится в отчёте, не меняя тип ошибки.

```python
try:
    report("Тверь")
except KeyError as error:
    error.add_note("Проверьте справочник площадок перед отчётом")
    raise
```

Путь к файлу в сообщении сокращён до имени, чтобы не загромождать запись. В реальном окне терминала перед именем стоит полный путь, и по нему видно, какой файл запущен. Если путей два и они разные, это признак того, что запускается копия из другого каталога.

Исправление добавляет проверку и понятное сообщение.

```python
def available(positions, reserved):
    return positions - reserved


def report(site):
    data = {"Тула": (1150, 40), "Калуга": (570, 15)}
    if site not in data:
        return f"Площадка {site} не найдена"
    positions, reserved = data[site]
    return f"{site}: {available(positions, reserved)} позиций"


print(report("Тула"))
print(report("Тверь"))
```

```text
Тула: 1110 позиций
Площадка Тверь не найдена
```

Такая проверка не делает программу правильной, но делает отказ понятным. Пользователь видит, что площадки нет, а не стек вызовов на пол-экрана. Для учебного проекта этого достаточно, для боевой системы сообщение дополнительно пишут в журнал.

| Симптом в трассировке | Что проверить | Частая причина |
|---|---|---|
| `ModuleNotFoundError` | `sys.executable`, установлен ли пакет | запуск не тем интерпретатором |
| `ImportError` с именем своего модуля | `sys.path`, имя файла | локальный файл перекрыл модуль |
| `KeyError` | значение ключа в нижнем кадре | нет проверки наличия |
| `TypeError` | типы операндов | строка вместо числа |
| `FileNotFoundError` | рабочая папка `cwd` | запуск из другого каталога |

Трассировка отвечает на вопрос «где», но не всегда на вопрос «почему». Если ошибка возникает в чужой библиотеке, причина часто в данных, которые ей передали. Поэтому сначала смотрят последний свой кадр, затем значения аргументов, и только потом лезут в исходники библиотеки.

## Реальные случаи: цена неверного окружения

### Переход с Python 2 на Python 3

Python 3.0 вышел в декабре 2008 года, но совместимость с ним не была полной. В Python 3 изменились строки, деление, печать и обработка исключений. Код с `print "Остаток"` в Python 3 не разбирается и даёт `SyntaxError`, а деление целых чисел стало возвращать дробный результат. Долгое время две ветки существовали параллельно: Python 2.7 оставался удобным для старых библиотек, а Python 3 требовал переписывания.

PEP 373 зафиксировал график поддержки Python 2.7 и прямо указал, что Python 2.8 не будет. [PEP 404](https://peps.python.org/pep-0404/) оформил это как «un-release schedule», чтобы прекратить ожидание. Поддержка 2.7 официально завершилась 1 января 2020 года, через одиннадцать лет после выхода Python 3.0. Официальная страница python.org называет эту дату концом эпохи и объясняет, что обновления безопасности для 2.7 больше не выпускаются.

Для темы занятия важна не история языка, а следствие для окружения. В системе могли одновременно стоять `python` версии 2.7 и `python3` версии 3.x, а команда `pip` могла ставить пакеты в первую. Проект запускался одним файлом, а зависимости оказывались в другом. Ошибка выглядела как несовместимость библиотеки, хотя причиной был выбор интерпретатора. Именно после этого перехода в документации закрепилось правило: версия Python указывается явно, а зависимости ставятся через `python -m pip` внутри окружения.

Урок для проекта «Склад+» простой: версия интерпретатора должна быть записана в README и в файле зависимостей, а не подразумеваться. Если завтра на учебной машине появится Python 3.14, проект не должен молча перейти на него.

### Запрет глобальной установки

В 2023 году дистрибутивы Linux начали помечать системный Python как externally managed. Поводом стали конфликты между пакетным менеджером дистрибутива и pip: обе системы устанавливали файлы в одни каталоги и считали их своими. Обновление системного пакета могло удалить библиотеку, от которой зависел проект, а установка из pip могла сломать служебные программы дистрибутива.

PEP 668 описал маркер и поведение инструментов: при наличии маркера pip не должен по умолчанию ставить пакеты в глобальный контекст, а должен предложить виртуальное окружение. Для пользователя это выглядит как внезапная ошибка на команде, которая работала годами. Старые инструкции из интернета перестали работать, и это хороший пример того, почему проверяют документацию, а не копируют команду из поста пятилетней давности.

| Что произошло | Что показала ошибка | Чему учит |
|---|---|---|
| Python 2.7 перестал обновляться | поддержка закончилась, но код остался | версия это часть контракта проекта |
| системный pip запретил установку | `externally-managed-environment` | зависимости живут в окружении |
| два Python в PATH | пакет есть, импорт не работает | проверяют `sys.executable`, а не версию |

Общий вывод из обоих случаев один: окружение это не удобство для аккуратных разработчиков, а способ сделать результат воспроизводимым. Пока окружение не зафиксировано, любая ошибка может оказаться не ошибкой кода.

## Типичные ошибки

**Не тот интерпретатор.** Симптом: пакет установлен, но `ModuleNotFoundError` остаётся. Причина: установка и запуск попали в разные Python. Лечение: выбрать `.venv` и проверить третью строку скрипта.

**Окружение не активировано.** Симптом: в терминале работает глобальный Python. Причина: активация выполнена в другом окне. Лечение: новый терминал или прямой путь к интерпретатору.

**Запуск из чужого каталога.** Симптом: файл не найден или база открылась пустая. Причина: относительный путь считается от текущей папки. Лечение: запускать из корня проекта или задавать рабочую папку в `launch.json`.

**Локальный файл перекрыл модуль.** Симптом: библиотека ведёт себя странно, трассировка указывает на неожиданный файл. Причина: файл проекта называется как стандартный модуль. Лечение: переименовать файл и проверить `sys.path`.

**Пробелы и кириллица в пути.** Симптом: команда разваливается на части. Причина: путь не взят в кавычки. Лечение: кавычки вокруг пути и латинские имена каталогов для кода.

**Читают только первую строку.** Симптом: правят не тот файл. Причина: причина указана в последней строке, а не в первой. Лечение: читать снизу вверх и смотреть нижний кадр.

**Отладка вместо теста.** Симптом: дефект найден, но завтра возвращается. Причина: проверка осталась в голове. Лечение: после отладки добавить тест на найденный случай.

**Правка установленной библиотеки.** Симптом: исправление работает на одной машине и исчезает после переустановки. Причина: файл пакета изменён прямо в `site-packages`. Лечение: не трогать чужой код, оформлять обход в своём модуле или обновлять библиотеку.

**Несколько открытых терминалов.** Симптом: в одном окне окружение активно, в другом нет. Причина: активация действует только на текущую оболочку. Лечение: проверять интерпретатор в каждом окне или вызывать его по пути.

**Запуск через стороннюю кнопку.** Симптом: в терминале всё работает, а при запуске кнопкой расширения ошибка возвращается. Причина: расширение запускает свой интерпретатор. Лечение: запускать через конфигурацию отладки или терминал.

## Практический вывод

Откройте проект «Склад+» и выполните три проверки. Запустите скрипт с версией и убедитесь, что третья строка даёт `True`. Выберите тот же интерпретатор в VS Code и перезапустите терминал. Поставьте точку останова в функции расчёта и пройдите её по шагам, записав значения переменных.

Затем намеренно сломайте код: обратитесь к несуществующей площадке и прочитайте трассировку снизу вверх. Найдите тип ошибки, нижний кадр и строку. Исправьте код проверкой и повторите запуск. Такое упражнение снимает страх перед красным текстом в терминале.

Третья проверка касается воспроизводимости. Создайте окружение заново в отдельной папке, установите зависимости из сохранённого списка и запустите тот же скрипт. Если результат совпал, проект готов к передаче. Если нет, сравнивайте не код, а версии Python и пути `sys.executable`.

## Итоги

- `python` это имя в PATH, поэтому важно знать, какой файл запускается.
- Виртуальное окружение даёт проекту собственный интерпретатор и набор библиотек.
- Активация меняет только текущую оболочку, а не настройки проекта.
- `.venv` не хранят в Git, зависимости фиксируют в файле проекта.
- VS Code запускает выбранный интерпретатор, и его выбор должен совпадать с терминалом.
- Точка останова, шаги и стек вызовов показывают состояние программы без правок кода.
- Трассировку читают снизу: тип ошибки, затем нижний кадр с нужной строкой.
- Рабочая папка запуска влияет на относительные пути к базе и файлам.
- Окружение проекта воспроизводят из списка зависимостей, а не копированием папки.
