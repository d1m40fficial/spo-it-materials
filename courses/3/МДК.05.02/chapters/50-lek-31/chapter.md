## Проект, который работал только у автора

На консультации перед защитой приложение открывается с полпинка. Автор показывает вход, добавляет товар, строит отчёт и уверенно говорит, что всё готово. Через день тот же проект запускают на учебной машине, и он не стартует. База лежит в папке автора и в репозиторий не попала. Пароль записан прямо в коде и меняется только в одном месте, о котором знает один человек. README отсутствует, поэтому непонятно, какую команду выполнять первой. Вход работает с тестовой учётной записью, которую автор добавил вручную месяц назад.

Проект был почти готов. Не хватило нескольких вещей, каждая из которых кажется мелочью, пока не попробуешь повторить работу на другом компьютере. Именно эту проверку и проходит итоговый проект: не «получилось ли у автора», а «получится ли у другого человека по инструкции и без вопросов».

**Итоговый проект это работающая система с проверяемыми артефактами, а не самый большой файл за семестр.** Артефакт это то, что можно открыть, запустить, выполнить или сравнить: скрипт схемы, файл базы, набор тестов, коллекция запросов, README, описание API. Чем больше решений подтверждено артефактами, тем меньше остаётся места для рассказа вместо доказательства.

В курсе есть сквозной пример «Склад+»: 120 сотрудников, четыре площадки, 12 товарных категорий и 4800 позиций на складе. Он показывает масштаб и связи, но итоговый проект каждый выбирает сам. Предметная область может быть другой: прокат инструмента, заявки на ремонт, запись на приём, учёт оборудования в мастерской. Требования к устройству системы остаются теми же.

## Что считается итоговым проектом

Итоговый проект это небольшая информационная система, которую можно целиком объяснить коротко. В ней есть данные, правила работы с ними, пользователи с разными правами, программный интерфейс и способ запуска. Всё остальное считается расширением и добавляется только после того, как обязательная часть работает.

Границы задаются числами, а не ощущением «пока не надоест». Минимум нужен, чтобы проверить все изученные темы: базу, доступ к данным, бизнес-логику, вход, API, тесты и документацию. Максимум нужен, чтобы проект остался обозримым и его можно было закончить.

| Признак | Минимум | Что проверяют |
|---|---|---|
| Предметная область | одна, понятная без длинного пояснения | тему можно назвать одним предложением |
| Сущности | 4-6 таблиц со связями | ключи, внешние ключи, справочники |
| Роли | 3 роли с разными правами | запрет настраивается на сервере, а не в интерфейсе |
| Сценарии | 5-7 законченных действий | каждый сценарий имеет начало, результат и проверку |
| Маршруты API | 6-8 маршрутов | чтение, создание, изменение, удаление и вход |
| Тесты | не меньше 10 модульных и 3 интеграционных | проверяются и успешные, и ошибочные случаи |
| Документы | README и описание API | по ним проект поднимает другой человек |

Числа не случайны. Четыре таблицы уже дают главную сущность, справочник, таблицу пользователей и связь между ними. Шесть таблиц позволяют показать связь «многие ко многим» и историю операций. Три роли дают разные права: администратор управляет справочниками, менеджер оформляет операции, обычный пользователь видит только свои записи. Пять сценариев покрывают вход, чтение, создание, изменение и отчёт. Если сценариев меньше, часть модулей останется без применения и её невозможно проверить.

Копировать «Склад+» целиком не нужно и вредно. В нём 4800 позиций, четыре площадки и десяток отчётов, потому что это пример промышленной системы. Для итогового проекта достаточно одной площадки и одного склада, но схема, вход и API должны быть устроены так же честно, как в большом примере.

Есть три признака, по которым тему стоит отклонить или сузить. Первый: нет данных, которые нужно хранить. Система «умный дом» без датчиков и журнала событий превращается в одну кнопку. Второй: у всех пользователей одинаковые права, и тогда нечего проверять в авторизации. Третий: готовое решение скачивается из интернета целиком, и проект не показывает работу автора, даже если запускается.

### Минимальный жизнеспособный продукт

Минимальный жизнеспособный продукт, или MVP, это не «половина всего», а один законченный сценарий, который проходит через все слои системы. Пользователь входит, выполняет главное действие, получает результат и видит его в интерфейсе. За этим сценарием стоят таблицы, ограничения, правила, маршрут API и хотя бы один тест.

Срез строят вертикально. Горизонтальный подход сначала делает все таблицы, потом все запросы, потом все маршруты, и до первой проверки проходит несколько недель. Вертикальный срез соединяет тонкую полоску каждого слоя и уже на второй неделе показывает, что слои стыкуются. Ошибка в модели данных обнаруживается до того, как на неё написан интерфейс.

::figure scope-slice | Пять слоёв и пять колонок. Срез 1 проходит все слои для входа и выдачи, срез 2 добавляет возврат и отчёт, экспорт остаётся за границами.

У вертикального среза есть цена. Он не показывает полную картину: часть сущностей ещё не используется, часть отчётов не считается. Зато он рано отвечает на главный вопрос, работает ли связка целиком. Горизонтальный подход даёт красивую схему и много кода, но откладывает этот ответ до конца.

В MVP входят вход, одна главная операция, её отказ и просмотр результата. Не входят экспорт, уведомления, вторая площадка и интеграции. Список «не входит» записывают рядом с планом и не трогают до защиты. Он защищает не от интересных идей, а от незакрытых обязательных модулей: каждая новая функция отнимает время у проверки.

> [!TRADEOFF] Ширина или глубина
> Можно сначала собрать все модули в минимальном виде, а потом углублять. Можно довести до блеска один модуль и не успеть закрыть остальные. Для учебного проекта выгоднее ширина: проверяющий должен увидеть все обязательные модули, а глубина одного из них не компенсирует отсутствие входа или тестов.

## Обязательные модули

Модуль это часть системы с понятной ответственностью и проверяемым результатом. Список ниже не является меню, из которого выбирают половину. Каждый модуль закрывает отдельный риск: без него проект либо не запускается, либо не доказывает, что автор умеет работать с соответствующей темой.

| Модуль | Артефакт | Критерий готовности |
|---|---|---|
| Репозиторий и каркас | каталоги `src`, `tests`, `docs`, `db`, файлы `README.md`, `requirements.txt`, `.gitignore` | проект клонируется, структура видна без пояснений |
| База данных | `db/schema.sql` и файл базы | схема создаётся с нуля одной командой, внешние ключи включены |
| Доступ к данным | модуль с запросами и соединением | значения передаются параметрами, соединение закрывается |
| Бизнес-логика | функции проверки и операции | правила не размазаны по обработчикам маршрутов |
| Вход и роли | таблица пользователей и модуль проверки пароля | пароль хранится хешем, роли проверяются на сервере |
| API | 6-8 маршрутов и единый формат ошибки | успех и отказ различаются кодом состояния |
| Интерфейс | командная строка или веб-страница | главный сценарий проходится без правки кода |
| Тесты | набор модульных и интеграционных проверок | прогон зелёный на чистой копии проекта |
| Документация и запуск | README, описание API, пример настроек | другой человек повторяет запуск по инструкции |

Репозиторий и каркас задают место каждому файлу. Если код, тесты и скрипты базы лежат в корне вперемешку, проверяющий тратит время на поиск точки входа, а автор путается в собственных файлах. Каркас нужен не для красоты: он показывает, что разработчик умеет отделять исходный код от данных, тестов и документации.

База данных хранит не только строки, но и правила. Первичный ключ не даёт создать дубль, внешний ключ не даёт сослаться на несуществующую запись, `CHECK` не даёт записать отрицательный остаток. Если все ограничения проверяются только в Python, база постепенно накопит мусор: достаточно одной программы, которая пишет в неё напрямую.

Доступ к данным отделяют от бизнес-логики, чтобы запросы не повторялись в каждом обработчике. Один модуль знает, как открыть соединение, выполнить параметризованный запрос и превратить строку в объект. Обработчик маршрута вызывает функцию и не занимается SQL. Такое разделение упрощает тесты: функцию доступа можно проверить на учебной базе, не поднимая веб-сервер.

Бизнес-логика отвечает на вопросы предметной области. Можно ли вернуть инструмент после срока? Какие поля обязательны при создании заявки? Кто имеет право отменить операцию? Если ответы записаны в одном месте, их можно проверить тестами. Если они разбросаны по кнопкам интерфейса, при появлении второго клиента (командной строки или API) правила придётся писать заново.

Вход и роли закрывают доступ. Пароль хранится не в открытом виде, а в виде хеша с солью. Роль и признак блокировки проверяются на сервере перед каждым действием. Интерфейс может скрыть кнопку, но запрос всё равно можно отправить из Postman, поэтому запрет должен жить в коде, который обрабатывает запрос.

API делает функции системы доступными извне. Шесть-восемь маршрутов достаточно, чтобы показать чтение списка, чтение одной записи, создание, изменение, удаление, вход и один отчёт. У каждого ответа есть код состояния, а у ошибки единый формат с полем `error` и, где нужно, списком проблемных полей.

Интерфейс нужен не для украшения. Он показывает, что систему можно использовать, не зная внутреннего устройства. Командная строка подходит, если сценарий понятен и выполняется последовательностью команд. Веб-страница подходит, если важны формы и таблицы. В любом случае главный сценарий должен проходиться без правки исходного кода.

Тесты подтверждают, что правила работают после изменений. Модульные проверяют отдельные функции: расчёт стоимости, проверку даты, разбор строки. Интеграционные проверяют связку: маршрут, база и ответ. Отрицательные случаи обязательны, потому что именно они показывают, что система умеет отказывать.

Документация и запуск завершают проект. README отвечает на вопросы «что это», «как установить», «как запустить», «как проверить». Описание API перечисляет маршруты, параметры, ответы и ошибки. Пример настроек показывает, какие переменные окружения нужны, не раскрывая секретов. Если инструкция проверена на чистой машине, проект перестаёт зависеть от памяти автора.

## Готовность как пропускная способность

Считать готовность процентом удобно для планирования и опасно для решения. Семь закрытых модулей из десяти дают 70 процентов, и число выглядит солидным. Но если среди трёх незакрытых оказался вход в систему, показать главный сценарий всё равно нельзя: без входа нет ролей, без ролей нет проверки прав, а без проверки прав API открыт всем.

Ниже небольшой скрипт, который считает готовность по списку модулей. У каждого модуля есть код, название, признак обязательности и признак выполнения. Скрипт печатает таблицу, находит блокирующие пункты и возвращает код завершения: ноль, если проект готов, и единицу, если нет.

```python
import sys

MODULES = [
    {"code": "repo", "title": "Репозиторий и каркас", "required": True, "done": True},
    {"code": "db", "title": "Схема базы и справочники", "required": True, "done": True},
    {"code": "data", "title": "Доступ к данным", "required": True, "done": True},
    {"code": "logic", "title": "Бизнес-логика и CRUD", "required": True, "done": True},
    {"code": "auth", "title": "Вход и роли", "required": True, "done": True},
    {"code": "api", "title": "Маршруты API и ошибки", "required": True, "done": True},
    {"code": "ui", "title": "Интерфейс", "required": True, "done": True},
    {"code": "tests", "title": "Тесты", "required": True, "done": False},
    {"code": "docs", "title": "Документация и запуск", "required": True, "done": False},
    {"code": "report", "title": "Дополнительный отчёт", "required": False, "done": False},
]


def report(modules):
    total = len(modules)
    done = sum(1 for m in modules if m["done"])
    percent = round(100 * done / total)
    print(f"Модулей: {total}, закрыто: {done}, готовность: {percent}%")
    for m in modules:
        mark = "готово" if m["done"] else "нет"
        print(f"{m['code']:<8}{m['title']:<32}{mark}")
    blocking = [m["title"] for m in modules if m["required"] and not m["done"]]
    if blocking:
        print("Блокирующие пункты: " + ", ".join(blocking))
        print("Вердикт: проект не готов к защите")
        return 1
    print("Вердикт: проект готов к защите")
    return 0


if __name__ == "__main__":
    sys.exit(report(MODULES))
```

Вывод на учебном наборе выглядит так:

```text
Модулей: 10, закрыто: 7, готовность: 70%
repo    Репозиторий и каркас            готово
db      Схема базы и справочники        готово
data    Доступ к данным                 готово
logic   Бизнес-логика и CRUD            готово
auth    Вход и роли                     готово
api     Маршруты API и ошибки           готово
ui      Интерфейс                       готово
tests   Тесты                           нет
docs    Документация и запуск           нет
report  Дополнительный отчёт            нет
Блокирующие пункты: Тесты, Документация и запуск
Вердикт: проект не готов к защите
```

Семь модулей из десяти закрыты, но вердикт отрицательный. Скрипт не пытается усреднить качество: он отделяет сведения от решения. Процент отвечает на вопрос «сколько сделано», список блокирующих пунктов на вопрос «что именно мешает показать проект». Для плана работ полезны оба ответа, для допуска к защите только второй.

Проверка списка не заменяет проверку кода. Скрипт читает признаки, которые заполнил автор, и не знает, действительно ли тесты проходят, а README описывает текущие маршруты. Поэтому каждый признак должен опираться на артефакт: тесты на зелёный прогон, README на запуск с чистой копии, API на коллекцию запросов. Самопроверка без артефакта превращается в оптимистичный список.

| Ситуация | Процент | Вердикт |
|---|---|---|
| все десять модулей закрыты | 100 | готов |
| не закрыт дополнительный отчёт | 90 | готов |
| не закрыт вход | 90 | не готов |
| не закрыты тесты и документация | 80 | не готов |
| не закрыты база и API | 80 | не готов |

Разница между второй и третьей строкой показывает, зачем нужен признак обязательности. Необязательным может быть дополнительный отчёт или экспорт, без которого главный сценарий работает. Вход, база и API необязательными не бывают: без них система не выполняет обещанное.

## План работ по этапам

План строят от результата, а не от списка тем. У каждого этапа есть законченный результат, который можно показать, и критерий, по которому видно, что этап закрыт. Пока результата нет, следующий этап не начинают: иначе схема базы пишется под функции, которых ещё нет, а тесты проверяют код, который скоро перепишут.

| Этап | Результат | Критерий готовности | Неделя |
|---|---|---|---|
| 1. Заявка и каркас | заявка на проект и репозиторий с каталогами | 11 обязательных путей на месте, первый коммит отправлен | 1 |
| 2. Схема и вход | `schema.sql` и модуль проверки пароля | 4-6 таблиц, четыре сценария входа проверены | 1-2 |
| 3. Срез MVP | вход и главный сценарий через все слои | сценарий проходит без правок, данные видны в интерфейсе | 2-3 |
| 4. Операции и отказы | создание, чтение, изменение и удаление записи | четыре операции и пять отказов на неверных данных | 3-4 |
| 5. Тесты | модульные и интеграционные тесты, отчёт о прогоне | прогон зелёный на чистой копии | 4-5 |
| 6. Запуск и секреты | настройки вне кода, README и пример окружения | клон и запуск по шагам, секретов в истории нет | 5 |
| 7. Документы и слайды | README, описание API, презентация | документы совпадают с текущими маршрутами | 5-6 |
| 8. Защита | сценарий показа и запасной план | пять частей без правок, время уложилось | 6 |

Первый этап кажется подготовительным, но он задаёт границы. В заявке написано, какие сущности входят в систему, кто ею пользуется и какие сценарии считаются главными. Без заявки проект растёт в стороны: сначала добавляется экспорт в Excel, потом уведомления, потом вторая площадка, и к защите не закрыт даже вход.

Второй этап соединяет данные и доступ. Схема создаётся скриптом, а не в графическом редакторе по памяти. Модуль входа проверяется на четырёх случаях: верный пароль, неверный пароль, неизвестный логин и заблокированная запись. Если все четыре дают одинаковый отказ, пользователь не понимает, что исправлять, а проверяющий не видит разницы между ошибкой ввода и запретом.

Третий этап собирает срез MVP. Это самый важный этап для проверки архитектуры: если данные из формы доходят до базы и возвращаются в интерфейс, значит, слои соединены. Ошибки в этот момент дешевле всего исправить, потому что кода ещё мало и он не размазан по десятку отчётов.

Четвёртый этап добавляет операции. Для каждой операции заранее выписывают, какие поля обязательны, какие значения допустимы и что происходит при нарушении. Пять отказов это минимум: пустое обязательное поле, слишком длинная строка, неверный формат даты, отрицательное число, ссылка на несуществующую запись. Проверки пишут в бизнес-логике, а не в интерфейсе, иначе API обойдёт их.

Пятый этап закрепляет поведение тестами. Сначала проверяют функции, которые легко изолировать, затем связку маршрута с базой. Тест на успешный сценарий обязателен, но недостаточен: если нет теста на отказ, ошибка в проверке полей останется незамеченной. Отчёт о прогоне сохраняют, потому что зелёный экран через неделю уже не докажет, что тесты проходили.

Шестой этап выносит секреты и проверяет запуск. Пароль базы, ключ подписи и адрес сервера берутся из переменных окружения, а в репозитории лежит только пример настроек. Запуск повторяют на чистой копии: клонируют репозиторий в новый каталог, создают окружение, устанавливают зависимости, создают базу, запускают приложение. Всё, что при этом пришлось доделывать вручную, дописывают в README.

Седьмой этап приводит документы в соответствие с кодом. README и описание API пишут не по памяти, а по фактическим маршрутам и ответам. Презентация содержит не скриншоты всех файлов, а схему, главный сценарий и одно трудное решение. Слайды нужны для рассказа, а не для замены работающего приложения. Подробнее о том, как писать инструкцию, которая выполняется без автора, сказано в лекции 30.

Восьмой этап это репетиция. Сценарий показа прогоняют целиком на чистой базе, засекают места, где приложение ведёт себя не так, как ожидалось, и исправляют их до защиты. Вопросы задают заранее: почему выбрана такая схема, где проверяется роль, что будет при неверном пароле, какой тест ловит ошибку. Репетиция показывает не пробелы в знаниях, а пробелы в подготовке.

### Как оценить срок

Оценка по этапам опирается на артефакты, а не на ощущение занятости. Если этап заканчивается таблицей, функцией или тестом, можно посчитать, сколько таких единиц осталось. Оценка «неделя на этап» почти всегда ошибочна: этапы различаются в два-три раза, а интеграция занимает время, которого в плане обычно нет.

Рабочее правило для учебного проекта: 60 процентов времени на сборку обязательных модулей, 20 на интеграцию и исправление связок, 20 на проверку, документы и репетицию. Это не закон, а способ не отдать все шесть недель первой половине списка. Последняя неделя не должна содержать новых функций: в ней закрываются проверки, документы и показ.

В план закладывают буфер на интеграцию. Два модуля, написанные отдельно, почти никогда не соединяются с первого раза: не совпадают имена полей, форматы даты, коды ошибок. Чем позже начинается соединение, тем больше несовпадений накопилось. Поэтому интеграционный прогон ставят в конце каждой недели, а не в последний день.

Если срок подходит к концу, сокращают объём, а не проверки. Убирают экспорт, уведомления, вторую площадку и дополнительные отчёты. Оставляют вход, главный сценарий, отказ, тесты и README. Проект с четырьмя сценариями и доказательствами сильнее проекта с двенадцатью сценариями и обещанием «потом проверю».

## Интеграция модулей

Собрать модули в конце это самый дорогой способ. Каждый модуль по отдельности работает, а вместе они не запускаются: один ждёт поле `user_id`, другой присылает `userId`, третий возвращает дату строкой, четвёртый объектом. Чем больше модулей соединяется за один раз, тем труднее понять, какая пара не сходится.

Интеграцию начинают с контракта. Контракт это описание того, что модуль принимает и что возвращает: имя маршрута, параметры, поля ответа, коды ошибок. Для HTTP API контракт удобно держать в файле OpenAPI: по нему видно, какие поля обязательны, какие типы допустимы и какие ответы возможны [OpenAPI Specification](https://spec.openapis.org/oas/latest.html). Контракт пишут до реализации, а не после, иначе он описывает случайное состояние кода.

Порядок соединения повторяет поток данных: база, доступ к данным, бизнес-логика, API, интерфейс. На каждом шаге предыдущий слой уже проверен. Если слой базы ещё меняется, нет смысла писать к нему три обработчика: они устареют вместе со схемой. Если API ещё не готов, интерфейс можно проверить на заглушке, но заглушка должна возвращать те же поля, что и настоящий маршрут.

Заглушка полезна как временная замена, но опасна как постоянная. Пока интерфейс работает с заглушкой, он не проверяет ни базу, ни права, ни ошибки. Поэтому у каждой заглушки есть срок: до интеграционного прогона недели. Если заглушка дожила до защиты, значит, часть системы так и не была соединена.

Сквозной прогон делают по одному сценарию, но через все слои. Проверяют не «работает ли функция», а «что видит пользователь»: форма отправляет данные, сервер проверяет роль, логика применяет правило, база сохраняет строку, ответ возвращает результат, страница показывает его. Такой прогон ловит несовпадения, которые модульные тесты не видят.

Полезно иметь одну команду запуска и один скрипт наполнения базы. Если для проверки нужно вручную создать таблицы, добавить пользователя и вспомнить пароль, интеграция будет проверяться редко. Команда вида «создать базу, заполнить справочники, запустить сервис» экономит время на каждом прогоне и делает проверку повторяемой.

Ветки и слияния тоже часть интеграции. Долгая ветка с десятью файлами превращается в конфликт, который страшно разрешать. Небольшие изменения, ежедневное слияние и прогон тестов после каждого слияния стоят дешевле, чем одна героическая попытка соединить всё за день до защиты. Если тесты запускаются автоматически при отправке изменений, поломка видна сразу, а не через неделю.

## Проверки перед защитой

Проверка отвечает на вопрос, а не создаёт видимость работы. «Тесты есть» это утверждение. «Тесты проходят на чистой копии, отчёт сохранён» это доказательство. Разница между ними определяет, что увидит проверяющий: обещание или результат. Стандарты жизненного цикла описывают верификацию и передачу как отдельные процессы, у которых есть входы, выходы и ответственные [ISO/IEC/IEEE 12207:2017](https://www.iso.org/standard/63712.html).

| Уровень | Что проверяет | Сколько достаточно | Пример |
|---|---|---|---|
| модульный | одна функция или правило | 10 и больше | расчёт срока возврата |
| интеграционный | маршрут, логика и база вместе | 3 и больше | выдача инструмента через API |
| контрактный | поля и коды ответа | по одному на маршрут | ошибка 400 с полем `error` |
| дымовой | запуск и главный путь после сборки | 1 | вход и список записей |

Модульные тесты дешёвые и быстрые, но они не доказывают, что слои соединены. Интеграционные тесты дороже, потому что поднимают базу и приложение, зато ловят несовпадения контрактов. Дымовой тест не проверяет бизнес-правила, он отвечает на вопрос, жива ли система после сборки. Все четыре уровня нужны вместе, потому что каждый закрывает свой тип ошибки. SWEBOK относит тестирование и качество к отдельным областям знания и подчёркивает, что проверки планируют вместе с разработкой, а не добавляют в конце [SWEBOK v4.0a](https://www.computer.org/education/bodies-of-knowledge/software-engineering).

Отрицательные случаи важнее успешных. Успешный сценарий показывает, что система работает при правильных данных. Отказ показывает, что она защищена: неверный пароль не пускает, чужая роль не меняет запись, пустое поле не сохраняется, повторный логин не создаётся. Если тесты проверяют только успех, проверяющий видит парадную сторону и не видит границ.

Покрытие это мера, а не цель. Можно покрыть половину строк и не проверить ни одного отказа, а можно покрыть меньше строк и поймать все важные ветки. Серия ISO/IEC/IEEE 29119 описывает процессы тестирования, документы и техники, но не назначает универсальную долю покрытия для любого проекта [ISO/IEC/IEEE 29119-1:2022](https://www.iso.org/standard/81291.html). Поэтому в отчёте указывают, какие риски покрыты, а не только процент строк.

Трассировка связывает требование, сценарий, тест и артефакт. В таблице на каждое требование видно, каким сценарием оно проверяется и какой тест это подтверждает. Если у требования нет теста, оно не проверено. Если у теста нет требования, возможно, он проверяет то, чего в проекте нет. ISO/IEC/IEEE 29148:2018 требует, чтобы отдельное требование было необходимо, однозначно, выполнимо и проверяемо [ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html). Требование «система должна быть удобной» проверить нельзя, а «форма входа отклоняет пустой пароль с кодом 400» можно.

| Требование | Сценарий | Тест | Артефакт |
|---|---|---|---|
| выдача только при остатке больше нуля | выдача последнего инструмента | `test_issue_when_stock_zero` | отчёт прогона |
| менеджер не удаляет справочник | удаление категории под менеджером | `test_delete_forbidden_for_manager` | ответ 403 |
| пароль не хранится открытым | создание пользователя | `test_password_is_hashed` | строка в базе |

Качество проекта удобно описывать не словами «хорошо» или «плохо», а характеристиками. ISO/IEC 25010:2023 задаёт модель качества продукта, в которой есть функциональная пригодность, надёжность, защищённость, удобство взаимодействия и сопровождаемость [ISO/IEC 25010:2023](https://www.iso.org/standard/78176.html). Для учебного проекта не нужно доказывать все характеристики. Достаточно выбрать три, которые важны для темы, и показать, чем они подтверждены.

| Характеристика | Как подтвердить | Что честно сказать |
|---|---|---|
| функциональная пригодность | сценарии и приёмочные проверки | какие сценарии не входят |
| защищённость | хеш пароля, роли, проверка на сервере | какие угрозы не рассматривались |
| надёжность | обработка ошибок, журнал, повторный запуск | что будет при падении базы |
| сопровождаемость | структура каталогов, README, тесты | где код связан сильнее всего |

Документация проверяется действием, а не наличием файла. README читает человек, который не видел проект, и повторяет запуск. Описание API сверяют с фактическими маршрутами: если в документе `/api/items`, а в коде `/api/tools`, читатель получит 404. Документация делится по задаче читателя: учебный пример, инструкция по шагам, справочник и объяснение решений [Diátaxis](https://diataxis.fr/). Смешивать всё в одном файле значит написать текст, который не помогает ни одной из этих задач.

README это витрина и точка входа. Документация GitHub перечисляет его обычные разделы: что делает проект, зачем он нужен, как начать, где получить помощь и кто поддерживает [GitHub Docs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes). Для учебного проекта к этому добавляют команды установки, создания базы, запуска и проверки. README не пересказывает код, он ведёт к работающей системе.

Приёмку проводят на чистой копии. Клонируют репозиторий в новый каталог, создают окружение, устанавливают зависимости, создают базу, запускают приложение, проходят главный сценарий и три отказа. Всё, что пришлось исправлять вручную, записывают в список исправлений. Чистая копия это единственная честная проверка того, что проект не зависит от машины автора.

## Реальные случаи

### Healthcare.gov, 2013

Федеральную площадку медицинского страхования запустили 1 октября 2013 года. Проверку готовности перенесли с марта на сентябрь, за несколько недель до запуска, и часть согласований не получили. Счётная палата США установила, что система была запущена без подтверждения соответствия требованиям по производительности [GAO, 2014](https://www.gao.gov/products/gao-14-694).

Обязательства по основной системе выросли с 56 млн долларов до более 209 млн, по хабу данных с 30 млн почти до 85 млн. Контракт с первым подрядчиком закрывали с удержанием около 267 тысяч долларов из 12,5 млн уплаченных сборов. Новый контракт на 91 млн долларов к июню 2014 года вырос более чем до 175 млн.

Для итогового проекта здесь три урока. Проверка готовности не переносится ради даты: если её сдвинули, дату сдвигают тоже. Интеграция многих компонентов требует сквозного прогона, а не проверки каждого по отдельности. Обязательство подрядчика формулируют как проверяемый результат, а не как процесс.

### NHS NPfIT, 2002-2011

Британская программа должна была дать каждому пациенту электронную карту к 2010 году. К маю 2011 года на системы медицинских записей потратили 2,7 млрд фунтов. Национальное аудиторское управление заключило, что эти деньги не дали соотношения цены и качества, и не нашло оснований верить, что оставшиеся 4,3 млрд дадут другой результат.

Из 97 систем для крупных больниц за семь лет внедрили четыре. Даже там, где системы работали, они давали в основном административные выгоды, а не клинические. Подключение существующих систем оценили ещё минимум в 220 млн фунтов [NAO, 2011](https://www.nao.org.uk/reports/the-national-programme-for-it-in-the-nhs-an-update-on-the-delivery-of-detailed-care-records-systems/).

Урок для границ проекта простой. Большой объём не делает проект сильнее, если интеграция не проверена. Срез, который доходит до пользователя, ценнее плана на десятки систем. Число внедрённых систем и подтверждённая выгода это разные показатели, и на защите нужны оба.

### TSB, 2018

В апреле 2018 года банк TSB перенёс данные клиентов на новую платформу. Данные мигрировали успешно, но платформа сразу дала технические сбои. Пострадали все отделения и значительная часть 5,2 млн клиентов, банк вернулся к обычной работе только в декабре 2018 года. Компенсации клиентам составили 32,7 млн фунтов.

В декабре 2022 года FCA и PRA оштрафовали банк на 48,65 млн фунтов за недостатки управления операционным риском и подрядчиками [FCA, 2022](https://www.fca.org.uk/news/press-releases/tsb-fined-48m-operational-resilience-failings). Регуляторы отметили, что банк плохо спланировал миграцию и недостаточно контролировал программу.

Для проекта это урок о проверке сквозных сценариев. Успешный перенос данных не означает, что система работает: важны вход, выдача, отказ и восстановление после сбоя. Запасной план и проверка на копии данных готовятся до запуска, а не после первой ошибки.

| Случай | Что выглядело готовым | Что не проверили | Вывод |
|---|---|---|---|
| Healthcare.gov | контракты и отдельные компоненты | готовность и сквозную работу | проверка не переносится ради даты |
| NHS NPfIT | план и число систем | интеграцию и выгоду | объём не заменяет срез |
| TSB | перенос данных | сценарии и восстановление | успешная миграция не равна работе |

## Демонстрация и защита

Защита это не пересказ кода. Это короткий показ того, что система решает задачу, и ответы, которые подтверждают понимание. Хороший показ идёт по сценарию пользователя, а не по каталогам проекта. Проверяющий должен увидеть вход, главное действие, отказ и результат, а не двадцать открытых файлов.

::figure defense-route | Десять минут показа: задача, сценарий, решения, доказательства и границы. Ниже запасной план на случай сбоя.

Сценарий показа готовят заранее и репетируют на чистой базе. Сначала называют задачу и пользователя: кто и зачем открывает систему. Потом проходят главный сценарий целиком, включая один отказ: неверный пароль, чужая роль или пустое поле. Затем показывают одно трудное решение: почему таблица выделена, почему ключ составной, где проверяется право. В конце называют границы и то, что сделали бы дальше.

Слайды поддерживают показ, а не заменяют его. На слайде достаточно схемы, главного сценария, двух решений и таблицы доказательств. Скриншоты всех экранов не нужны: они занимают время и ничего не доказывают. Если приложение работает, показывают приложение. Если не работает, показывают запись прогона и объясняют, что именно сломалось.

| Вопрос | Где искать ответ |
|---|---|
| почему эта таблица выделена отдельно | схема и связи |
| почему ключ составной | ограничение и данные |
| что будет при неверном пароле | модуль входа и тест |
| где хранится секрет | пример настроек и `.gitignore` |
| какой тест поймает ошибку | файл теста и отчёт |
| что сломается при удалении роли | проверка прав и сценарий |

Ответ на защите строят по формуле: решение, причина, альтернатива, цена, артефакт. «Сделал отдельную таблицу истории, потому что нужна дата каждой выдачи. Альтернатива хранить только текущую выдачу проще, но тогда нельзя построить отчёт по просрочкам. Цена вторая таблица и запрос с соединением. Вот схема и тест на отчёт». Такой ответ показывает не заученный текст, а понимание.

Если во время показа что-то падает, не отлаживают на сцене. Переходят к запасному доказательству: записи прогона, коллекции Postman, отчёту тестов. После показа называют причину сбоя, если она известна, и что сделано, чтобы её найти. Честное «здесь падает, потому что база не создана, я покажу запись рабочего прогона» лучше десяти минут молчаливой правки кода.

Запасной план готовят до защиты. В него входят чистая база и скрипт наполнения, запись главного сценария, коллекция запросов с сохранёнными ответами, отчёт о прогоне тестов и известные ограничения. Проверяют запасной план заранее: запись должна открываться, коллекция запускаться, база создаваться. Иначе запасной план существует только в рассказе.

## Разбор ошибок

Ошибки перед защитой повторяются. Их полезно знать не для того, чтобы испугаться, а для того, чтобы проверить свой проект за один вечер.

| Ошибка | Признак | Лечение |
|---|---|---|
| проект живёт на одной машине | на учебной машине падает при старте | относительные пути, скрипт базы, README |
| секреты в репозитории | пароль виден в истории | переменные окружения, `.env.example`, замена секрета |
| база создаётся вручную | на другой машине нет таблиц | `schema.sql` и скрипт справочников |
| вход для одного пользователя | нет второй роли | три учётные записи и проверка роли |
| API возвращает 200 на ошибку | клиент не видит отказа | коды 400, 401, 403, 404, 409 |
| тесты проверяют только успех | неверная запись сохраняется | по тесту на каждый отказ |
| документация отстала | запрос из README даёт 404 | сверка маршрутов перед защитой |
| объём растёт быстрее модулей | много кода и нет сценария | список «не входит» и заморозка |
| показ на грязной базе | на сцене чужие данные | чистая база и seed-скрипт |
| монолог без доказательств | слайды вместо системы | сценарий и таблица артефактов |

Отдельно стоит ошибка «почти готово». Она выглядит как список из десяти пунктов, где восемь закрыты, а два «доделаю за выходные». Обычно именно эти два пункта и проверяет комиссия: вход, тесты или запуск. Поэтому «почти» считают как «нет» и закрывают пункт до защиты, а не после.

Ещё одна ошибка это подмена результата процессом. «Я писал проект каждый день», «я посмотрел пять туториалов», «я почти разобрался с миграциями» не являются артефактами. Артефакт отвечает на вопрос «что можно проверить». Если ответа нет, работа ещё не стала результатом.

## Оценка результата

Результат оценивают по трём группам: работает ли система, доказано ли это, понимает ли автор свои решения. Первая группа проверяется запуском, вторая артефактами, третья вопросами. Ни одна из групп не заменяет другую: работающее приложение без доказательств похоже на случайную удачу, а доказательства без понимания рассыпаются на первом вопросе.

| Уровень | Что видно |
|---|---|
| не зачтено | главный сценарий не проходит, обязательный модуль не закрыт |
| базовый | сценарий проходит, есть вход, база, API, тесты и README |
| уверенный | добавлены отказы, трассировка, чистый запуск и запасной план |
| сильный | автор объясняет альтернативы, цену решений и границы проекта |

Оценка не требует большого проекта. Маленькая система с честными границами и доказательствами сильнее большой системы с обещаниями. Проверяющий смотрит на соотношение заявленного и подтверждённого: если в README написано «поддерживает три роли», он проверит три роли, а не поверит строчке.

Перед защитой полезно пройти короткий список. Главный сценарий проходит на чистой копии. Тесты зелёные, отчёт сохранён. В репозитории нет секретов и файла базы. README повторяется другим человеком. Описание API совпадает с маршрутами. Пять частей показа укладываются во время. На каждый вопрос из таблицы выше есть артефакт. Если хотя бы один пункт не выполняется, его закрывают или честно называют ограничением.

Ограничение это не провал. Провал это скрытое ограничение, которое обнаруживается на защите. «Экспорт в Excel не входит в проект, потому что приоритет был у проверки ролей и тестов» звучит профессионально. «Всё работает» с последующим падением на первом запросе звучит плохо, даже если код написан неплохо.

## Итоги

- Итоговый проект оценивают по проверяемым артефактам, а не по объёму кода.
- Обязательные модули: репозиторий, база, доступ к данным, логика, вход, API, интерфейс, тесты, документация и запуск.
- Готовность считают по блокирующим пунктам, а не по среднему проценту.
- План строят от результата этапа, а последнюю неделю отдают проверке и репетиции.
- MVP это один сквозной срез через все слои, а не половина каждого модуля.
- Интеграцию начинают с контракта и повторяют каждую неделю, а не в последний день.
- Перед защитой проект проверяют на чистой копии и показывают не только успех, но и отказ.
- Оценка складывается из работающей системы, доказательств и понимания решений.

::quiz
Q: Что делает итоговый проект готовым к защите?
+ Набор работающих модулей, подтверждённых артефактами
- Количество строк кода в проекте
- Число использованных библиотек
- Объём презентации
! Готовность подтверждается запуском, тестами и документами, а не размером кода.

Q: Что такое минимальный жизнеспособный продукт в учебном проекте?
+ Один законченный сценарий, проходящий через все слои
- Первая половина каждого модуля
- Пустой каркас репозитория
- Презентация без приложения
! MVP проверяет связку слоёв на одном сценарии, а не половину каждого слоя.

Q: Зачем начинать с вертикального среза?
+ Он рано показывает, что слои соединяются
- Он уменьшает число таблиц до одной
- Он заменяет тесты
- Он убирает необходимость в README
! Ошибку в модели данных дешевле найти до того, как на неё написан интерфейс.

Q: Что означает блокирующий пункт в отчёте о готовности?
+ Обязательный модуль, без которого проект нельзя показать
- Любой незакрытый модуль, включая дополнительный отчёт
- Ошибку в оформлении презентации
- Замечание рецензента по стилю кода
! Блокирующий пункт отменяет вердикт независимо от процента готовности.

Q: Почему процент готовности не заменяет список блокирующих пунктов?
+ Среднее число скрывает отсутствие входа или базы
- Процент всегда больше ста
- Процент нельзя посчитать
- Список нужен только для отчёта
! Семь модулей из десяти выглядят солидно, но без входа проект не работает.

Q: С чего начинается план работ по проекту?
+ С заявки и каркаса репозитория
- С презентации для защиты
- С экспорта в Excel
- С покупки сервера
! Заявка задаёт границы, каркас задаёт места для файлов.

Q: Что проверяет интеграционный тест?
+ Связку маршрута, бизнес-логики и базы
- Только синтаксис одного файла
- Скорость набора текста
- Оформление README
! Интеграционный тест ловит несовпадения контрактов между слоями.

Q: Что делать, если во время показа приложение упало?
+ Перейти к запасному доказательству и назвать причину сбоя
- Отлаживать код перед комиссией
- Молча перезапускать приложение
- Закончить показ без объяснений
! Запись прогона и коллекция запросов подтверждают работу, а отладка на сцене отнимает время.

Q: Что установила Счётная палата США по запуску Healthcare.gov?
+ Система была запущена без подтверждения соответствия требованиям
- Все требования были проверены до запуска
- Затраты не изменились
- Подрядчик отказался от контракта до запуска
! Проверку готовности перенесли на сентябрь 2013 года.

Q: Какие артефакты подтверждают готовность проекта?
+ Скрипт схемы базы и файл базы
+ Набор тестов и отчёт о прогоне
+ README и описание API
- Количество скачанных библиотек
- Список просмотренных видео
! Артефакт можно открыть и проверить, он не зависит от памяти автора.

Q: Какие признаки говорят, что объём проекта пора сузить?
+ Нет данных, которые нужно хранить
+ У всех пользователей одинаковые права
+ Готовое решение скачивается целиком
- В системе есть справочник
- Пользователи делятся на роли
! Без данных, прав и собственной работы проект нечего проверять.

Q: Что подтверждает проверку на чистой копии?
+ Клон репозитория и запуск по шагам README
+ Создание базы одной командой
+ Зелёный прогон тестов и сохранённый отчёт
- Открытие проекта в редакторе автора
- Показ презентации комиссии
! Чистая копия показывает, что проект не зависит от машины автора.

Q: Как называется документ, по которому другой человек устанавливает и запускает проект?
= README
= readme
! README содержит установку, запуск и проверку работы.

Q: Как называется минимальный продукт с одним сквозным сценарием?
= MVP
= минимальный жизнеспособный продукт
! MVP проверяет все слои на одном законченном сценарии.

Q: Как называется тест, который проверяет связку модулей и базы?
= интеграционный
= интеграционный тест
! Интеграционный тест проверяет совместную работу нескольких частей системы.
