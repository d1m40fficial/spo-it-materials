## Одна кавычка в поиске

Кладовщик на площадке в Калуге ищет товар и вводит в строку поиска `' OR 1=1 --`. Приложение показывает не одну позицию, а все 4800. Ещё через минуту он открывает карточку с чужим кодом и получает остатки московского склада. Ни пароль, ни роль он не подбирал: он воспользовался тем, что введённый текст попал прямо в SQL-запрос и стал его частью.

Такая ошибка встречается в учебных проектах постоянно, потому что на маленькой базе она незаметна. Запрос с подстановкой работает, поиск находит товар, отчёт строится. Проблема проявляется только тогда, когда кто-то вводит кавычку, дефис или слово `UNION`.

**Безопасность приложения с базой держится на трёх правилах: данные не становятся кодом, секреты не лежат в репозитории, права проверяются на сервере для каждой записи.** Нарушение любого из них открывает путь к остальным: через инъекцию можно прочитать таблицу пользователей, через украденный ключ подключиться к базе напрямую, через слабую проверку прав забрать чужие документы.

У «Северного склада» 4800 позиций, 120 учётных записей и четыре площадки. Потеря базы остатков остановит отгрузку, а утечка накладных раскроет условия работы с поставщиками. Поэтому защита здесь не абстрактное требование, а условие ежедневной работы.

## Угрозы и поверхность атаки

Уязвимость это не обязательно ошибка в одной строке. Чаще это сочетание: открытый маршрут, лишняя роль, старая библиотека и отсутствие журнала. Чтобы не проверять наугад, используют список типовых классов угроз. OWASP Top 10:2025 собирает десять категорий по данным о реальных инцидентах [OWASP Top 10:2025](https://owasp.org/Top10/2025/).

| Категория | Как выглядит в «Склад+» | Первый контроль |
|---|---|---|
| A01 Нарушение контроля доступа | кладовщик открывает чужую накладную | проверка записи на сервере |
| A02 Ошибка конфигурации | отладочный режим на рабочем сервере | минимальная конфигурация |
| A03 Сбой цепочки поставки | уязвимая библиотека в сборке | фиксация версий и обновление |
| A04 Криптографические ошибки | пароль под быстрым хешем, HTTP | медленный KDF, TLS |
| A05 Инъекция | кавычка в поиске меняет запрос | параметры и белый список |
| A06 Небезопасное проектирование | нет лимита на импорт файла | модель угроз и лимиты |
| A07 Ошибки аутентификации | подбор пароля без ограничений | MFA и ограничение попыток |
| A08 Нарушение целостности | обновление без проверки подписи | подпись и контроль хеша |
| A09 Ошибки журналирования | инцидент не виден в журнале | события и оповещения |
| A10 Ошибки обработки исключений | в ответ уходит стек вызовов | общий ответ, подробности в журнал |

Список полезен как карта, но не заменяет модель угроз. Атаку удобно раскладывать на шаги, потому что защита почти никогда не стоит на одном шаге. Сначала злоумышленник собирает сведения: открытые порты, версии библиотек, адреса документации, имена сотрудников. Затем ищет вход: слабый пароль, старую версию пакета, страницу без проверки. После входа закрепляется: создаёт учётную запись, кладёт файл, подключает внешний сервис. Дальше повышает права и забирает данные. Каждый шаг даёт защите шанс остановить атаку, если на этом шаге есть контроль и он кому-то виден.

Модель угроз отвечает на три вопроса: что защищаем, от кого и каким путём злоумышленник может подойти. Для «Северного склада» активы это остатки, накладные, учётные записи и ключи. Противники делятся на внешнего сканера, сотрудника с лишними правами и автоматический червь, который ищет известную уязвимость. Пути входа это HTTP-маршруты, база, файлы конфигурации, зависимости и журналы.

Поверхность атаки растёт с каждой возможностью. Новый маршрут добавляет точку входа, новый пакет добавляет чужой код, новый файл резервной копии добавляет копию данных. Поэтому защита строится слоями: проверка входа, параметры запроса, права учётной записи базы, шифрование канала, журнал и обновления. Один слой может отказать, но следующий ограничит ущерб.

::figure attack-surface | Пять поверхностей приложения и первый контроль на каждой. Схема показывает, что защита это не один барьер, а набор слоёв: данные, конфигурация, зависимости и журналы.

У защиты есть цена. Каждый слой добавляет работу: параметры требуют дисциплины, шифрование требует управления ключами, журнал требует места и разбора. Поэтому слои выбирают по риску, а не по принципу «чем больше, тем лучше». Пароль администратора защищают вторым фактором, а общедоступный справочник городов не требует того же уровня.

Есть и обратная ошибка: считать безопасность отдельным этапом перед сдачей. Проверка, сделанная один раз, устаревает при первом новом маршруте. Безопасность это свойство процесса: как пишут запросы, где хранят настройки, как обновляют зависимости и что записывают в журнал.

## Инъекция: когда данные становятся кодом

SQL-запрос это строка. Если приложение склеивает команду и пользовательский ввод в одну строку, база получает единый текст и не различает, где закончилась команда и начались данные. Кавычка во вводе закрывает строковый литерал, а всё после неё база читает как продолжение команды.

Проверим это на учебной таблице остатков:

```python
import sqlite3

connection = sqlite3.connect(":memory:")
connection.execute(
    "CREATE TABLE stock (id INTEGER PRIMARY KEY, item TEXT, site TEXT, qty INTEGER)"
)
connection.executemany(
    "INSERT INTO stock VALUES (?, ?, ?, ?)",
    [
        (1, "Кабель UTP", "Москва", 120),
        (2, "Коробка 400", "Тверь", 80),
        (3, "Стрейч-плёнка", "Тула", 240),
        (4, "Паллета", "Калуга", 60),
    ],
)

user_input = "' OR 1=1 --"
query = f"SELECT id, item, site FROM stock WHERE item = '{user_input}'"

print("запрос:", query)
print("склейка:", connection.execute(query).fetchall())

safe = connection.execute(
    "SELECT id, item, site FROM stock WHERE item = ?", (user_input,)
).fetchall()
print("параметр:", safe)

count = connection.execute("SELECT COUNT(*) FROM stock").fetchone()[0]
print("всего строк в таблице:", count)
```

Вывод:

```text
запрос: SELECT id, item, site FROM stock WHERE item = '' OR 1=1 --'
склейка: [(1, 'Кабель UTP', 'Москва'), (2, 'Коробка 400', 'Тверь'), (3, 'Стрейч-плёнка', 'Тула'), (4, 'Паллета', 'Калуга')]
параметр: []
всего строк в таблице: 4
```

Склейка вернула все четыре строки. Условие `item = ''` ложно, но `OR 1=1` истинно всегда, а два дефиса превращают остаток строки в комментарий. Параметризованный запрос вернул пустой список: значение `' OR 1=1 --` сравнивалось с названием товара как обычный текст и ни с чем не совпало.

Причина в том, что параметр передаётся отдельно от текста команды. База сначала разбирает запрос с местом для значения, а потом подставляет значение в это место. Кавычки внутри значения остаются данными и не могут изменить структуру команды.

::figure injection-flow | Один ввод и два пути. Выберите полезную нагрузку и режим: схема покажет итоговый запрос, число строк и объяснение. Сравните, как одна и та же строка остаётся текстом при параметре.

Инъекция не ограничивается обходом условия. Через `UNION` злоумышленник дописывает второй запрос и читает другую таблицу, через сообщение об ошибке узнаёт имена колонок, через точку с запятой пытается выполнить отдельную команду. Драйверы часто запрещают несколько команд в одном вызове, но чтение чужой таблицы через `UNION` от этого не исчезает. Поэтому защита не сводится к запрету кавычек: запрет обходят кодировкой и другими символами, а параметр убирает саму возможность изменить структуру запроса.

Есть вариант, который сложнее заметить. При первом запросе значение сохраняется в базе как обычный текст, без вреда. Через неделю другой отчёт читает это значение и снова подставляет его в текст запроса. Это инъекция второго порядка: проверка на входе была, а на выходе из базы её не повторили. Поэтому параметры нужны в каждом месте, где значение становится частью команды, а не только в обработчике формы.

Проверка ввода остаётся полезной, но как второй слой. Она отсекает заведомо неверные значения, ограничивает длину и формат, помогает вернуть понятную ошибку. Заменить параметры проверкой она не может: любая проверка опирается на список запрещённых символов, а список всегда неполон.

Ущерб от неудачной инъекции ограничивают права учётной записи базы. Если приложение подключается пользователем с правом читать только свои таблицы, `UNION` не откроет таблицу пользователей. Если у него права администратора, одна ошибка в запросе открывает всю базу. Поэтому минимальные права это не формальность, а последний рубеж.

В C# опасный вариант выглядит так же, как в Python, только с интерполяцией строки:

```csharp
var search = Console.ReadLine() ?? "";
var sql = $"SELECT id, item, site FROM stock WHERE item = '{search}'";
using var bad = new SqliteCommand(sql, connection);
```

Исправленный вариант использует параметр:

```csharp
var sql = "SELECT id, item, site FROM stock WHERE item = $search";
using var command = new SqliteCommand(sql, connection);
command.Parameters.AddWithValue("$search", search);
```

Правило простое: **любое значение, пришедшее от клиента, передаётся параметром, а не вставляется в текст запроса.** Это касается не только поиска, но и фильтров, сортировки, имени таблицы и номера страницы.

| Место в коде | Опасный вариант | Безопасный вариант |
|---|---|---|
| Поиск по названию | `WHERE item = '{text}'` | `WHERE item = ?` и кортеж значений |
| Фильтр по площадке | `WHERE site = '{site}'` | `WHERE site = ?` |
| Сортировка | `ORDER BY {column}` | выбор из белого списка колонок |
| Ограничение строк | `LIMIT {count}` | приведение к числу и проверка диапазона |

Сортировка и имя таблицы параметром не передаются: база подставляет параметры только вместо значений. Для них заранее задают допустимый список: если клиент просит сортировку по `quantity`, приложение подставляет строку `quantity` из списка, а любой другой ввод заменяет на сортировку по умолчанию. Белый список работает потому, что он перечисляет разрешённое, а не запрещённое.

ORM снижает риск, но не отменяет его. Обычные запросы EF Core параметризуются автоматически. Опасность появляется там, где в ORM передают готовую строку: методы вида `FromSqlRaw` с интерполяцией снова склеивают текст. Для параметров есть `FromSql` с интерполяцией, которая создаёт параметры, а не строку.

Этот класс ошибок описан в каталоге CWE как CWE-89, неправильная нейтрализация специальных элементов в SQL-команде [CWE-89](https://cwe.mitre.org/data/definitions/89.html). Инъекция бывает не только в SQL. Командная строка собирается из аргументов и ввода, шаблон страницы подставляет текст без экранирования, LDAP-фильтр склеивает условие с логином. Во всех случаях механизм один: данные попадают в язык, который разбирает команды. Защита тоже одна: разделять код и данные, использовать готовые API с параметрами и проверять допустимые значения.

### Инъекция в чужой библиотеке

В мае 2023 года злоумышленники начали использовать уязвимость CVE-2023-34362 в продукте MOVEit Transfer, который компании ставят для обмена файлами. CISA и ФБР описали схему: SQL-инъекция позволяла установить веб-оболочку, а через неё выкачать данные из базы приложения. Атака шла по интернет-доступным установкам, то есть по тем, которые организация считала внутренним сервисом [CISA AA23-158A](https://www.cisa.gov/news-events/cybersecurity-advisories/aa23-158a).

Для темы это важно по двум причинам. Во-первых, инъекция может жить не в вашем коде, а в продукте, который вы установили. Во-вторых, наличие уязвимости не означает мгновенной атаки: между публикацией исправления и массовым использованием проходит время, и именно в этот промежуток решает скорость обновления. CISA ведёт каталог известных эксплуатируемых уязвимостей, где такие случаи помечены как приоритетные для исправления [CISA KEV](https://www.cisa.gov/known-exploited-vulnerabilities-catalog).

## Секреты: строка подключения, ключи, пароли

Секрет это значение, которое даёт доступ к системе: пароль базы, ключ подписи токенов, ключ внешнего сервиса, пароль администратора. Пароль, вписанный прямо в исходный код, называют жёстко закодированными учётными данными; в каталоге CWE это отдельный класс CWE-798 [CWE-798](https://cwe.mitre.org/data/definitions/798.html). У секрета есть особенность: он ценен только пока неизвестен. Поэтому задача не в том, чтобы спрятать файл, а в том, чтобы секрет не попал туда, откуда его можно прочитать.

Каналов утечки несколько. Секрет попадает в репозиторий вместе с `appsettings.json`, в историю Git после удаления строки, в журнал приложения при отладке, в текст ошибки на странице, в снимок экрана на совещании, в архив с резервной копией и в переписку с коллегой. Один и тот же пароль часто используют на учебном стенде и на рабочем сервере, поэтому утечка учебного файла открывает боевую базу.

Правильное хранение выглядит скучно. В коде остаётся имя настройки, значение приходит извне. Для разработки используют хранилище секретов, для сервера переменные окружения или отдельное хранилище, для всех сред разные значения.

```text
ConnectionStrings__Sklad=Data Source=sklad.db;Password=...
Jwt__Key=...
```

В Python тот же принцип:

```python
import os

dsn = os.environ.get("SKLAD_DSN")
if not dsn:
    raise SystemExit("Не задана переменная SKLAD_DSN")

print("строка подключения получена, длина:", len(dsn))
```

Приложение не печатает саму строку, а сообщает только, что настройка есть. Если переменная не задана, оно останавливается с понятным сообщением, а не подставляет пароль по умолчанию.

| Где хранить | Что можно | Что нельзя |
|---|---|---|
| `appsettings.json` | адрес сервера, размер страницы, уровень журнала | пароль, ключ подписи |
| `appsettings.Development.json` | локальный адрес базы | пароль от рабочей базы |
| секреты разработчика | пароль учебной базы | общий пароль для всех разработчиков |
| переменные окружения сервера | пароль и ключи стенда | значения, которые попадут в журнал |
| хранилище секретов | все боевые секреты | открытая выдача всем сотрудникам |

Если секрет уже попал в репозиторий, удалить строку недостаточно. История Git сохраняет старую версию, а копии могли разойтись по форкам и архивам. Секрет считают скомпрометированным, меняют на новый и только потом чистят историю. Смена важнее чистки: старый пароль уже нельзя считать тайной.

::figure secret-channels | Шесть каналов утечки секрета. Нажмите канал: схема покажет, как значение уходит наружу и какой контроль его закрывает. Обратите внимание, что часть каналов не связана с кодом приложения.

Учётная запись базы тоже подчиняется правилу наименьших привилегий. Приложению «Склад+» нужны чтение и запись в свои таблицы, но не удаление базы и не управление пользователями. Отдельная учётная запись для приложения, отдельная для миграций и отдельная для администратора сокращают ущерб от ошибки.

Журнал и страница ошибки это отдельный канал. Когда база недоступна, драйвер часто пишет в текст исключения всю строку подключения вместе с паролем. Если приложение показывает такую ошибку клиенту, секрет уходит в браузер и в системы сбора ошибок. Поэтому клиенту возвращают короткое сообщение с идентификатором запроса, а подробности пишут в журнал, где строка подключения уже вырезана.

Снимок экрана и переписка кажутся безобидными, но на учебных и рабочих совещаниях в кадр попадают окна с настройками, вкладки с токенами и файлы конфигурации. Правило простое: секрет не показывают на экране и не пересылают в чате. Для передачи используют хранилище секретов с ограниченным доступом и сроком действия.

Отдельная история это конвейер сборки. Пароль к базе, ключ публикации и токен реестра пакетов часто лежат в настройках сборочной системы, откуда попадают в журнал сборки и в артефакт. Секреты конвейера выдают на одну задачу и на короткий срок, маскируют в выводе и не передают в контейнер, которому они не нужны. Если пароль всё же попал в лог, его меняют так же, как любой другой.

Поиск секретов полезно автоматизировать. Инструменты вроде `gitleaks` и `trufflehog` просматривают историю коммитов и находят строки, похожие на ключи и пароли. Они не заменяют дисциплину, но ловят случайную вставку до того, как репозиторий станет публичным.

Среды разделяют не только адресами, но и секретами. Учебная база не должна открываться паролем рабочей, а ключ подписи учебных токенов не должен приниматься боевым сервисом. Иначе ошибка на стенде превращается в инцидент на проде, а разработчик получает доступ, который ему не положен.

У секрета есть срок жизни. Ключ подписи меняют по расписанию и при подозрении на утечку. Пароль базы меняют при смене сотрудника, у которого был доступ. Токен доступа живёт минуты. Чем дольше секрет действует, тем больше времени у злоумышленника, который получил его копию.

## Доступ: проверка на сервере

Нарушение контроля доступа стоит первым в списке OWASP Top 10:2025. Причина в том, что проверку легко поставить не там: спрятать кнопку, отфильтровать список на клиенте, доверить полю из тела запроса.

Есть три частых сценария. Первый: пользователь открывает адрес `/api/admin/users` напрямую, хотя ссылки в интерфейсе нет. Если маршрут не защищён ролью, страница откроется. Второй: кладовщик меняет в адресе номер записи и получает чужую накладную. Третий: клиент отправляет в теле запроса лишнее поле `role` или `site`, и модель принимает его целиком.

Третий сценарий называют массовым назначением полей. Приложение ждёт название и количество, а получает ещё и роль. Если модель совпадает с сущностью базы, лишнее поле запишется. Защита простая: для входящих данных описывают отдельную модель, где перечислены только разрешённые поля, а остальные игнорируются.

| Угроза | Как выглядит | Защита |
|---|---|---|
| Обход маршрута | прямой запрос к административному адресу | `[Authorize(Roles = "admin")]` на контроллере |
| Чужая запись | подмена идентификатора в адресе | сравнение площадки записи с площадкой пользователя |
| Лишнее поле | в теле запроса пришла роль | отдельная модель запроса без служебных полей |
| Скрытая кнопка | запрет только в интерфейсе | проверка на сервере для каждого запроса |

Проверку прав проектируют от запрета: по умолчанию закрыто всё, а открывается только то, что нужно. Новый контроллер без атрибута не должен становиться общедоступным. Для этого в приложении включают глобальную политику, которая требует вход для всех маршрутов, а исключения помечают явно.

Политику удобно описать в одном месте, а не повторять условие в каждом действии. В ASP.NET Core для этого служит требование к утверждению:

```csharp
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("StockEditor", policy => policy
        .RequireRole("storekeeper", "manager")
        .RequireClaim("site"));
});
```

Политика отвечает на вопрос «может ли эта роль вообще менять остатки». К какой площадке относится запись, она не знает, поэтому в действии остаётся сравнение площадки пользователя с площадкой строки. Две проверки дополняют друг друга, и убирать вторую нельзя.

Проверять защиту нужно двумя учётными записями. Одна с ролью кладовщика своей площадки, вторая с ролью менеджера. Запросы повторяют с обеими: кладовщик не должен получить чужую запись, менеджер должен. Проверка только «своим» пользователем ничего не доказывает: она показывает, что доступ есть, но не показывает, что чужой его не получит.

Административные маршруты выносят в отдельный префикс и закрывают отдельной политикой. Это упрощает проверку: все адреса, начинающиеся с `api/admin`, требуют роль администратора, и новый контроллер в этой папке получает защиту по общему правилу. Ссылки в интерфейсе при этом остаются удобством, а не защитой.

Отдельно проверяют прямые адреса. Список маршрутов можно получить из документации API, из журнала или перебором. Если административная страница существует, но не защищена, отсутствие ссылки в меню ничего не меняет.

Права дублируют на уровне базы. Приложению не нужен доступ к таблице пользователей, если оно только читает остатки. Ограничения внешних ключей и проверки значений не дают записать бессмысленные данные даже при ошибке в коде. Защита на нескольких уровнях не лишняя: каждый уровень закрывает свой способ обхода.

## Шифрование, хеширование и кодирование

Эти три операции часто путают, а разница определяет, от чего каждая защищает.

Кодирование переводит данные в другой вид без секрета. Base64 превращает байты в текст и легко раскрывается обратно. Это удобно для передачи, но совершенно не защищает: строка `U2tsYWQr` читается любой библиотекой за одну команду и даёт «Sklad+».

Хеширование необратимо. Из пароля получают хеш, из хеша пароль не восстанавливают. Хеш подходит для проверки пароля и для контроля целостности файла. Для паролей нужен медленный алгоритм с солью, а не быстрый SHA-256.

Шифрование обратимо, но только с ключом. Оно защищает данные, которые нужно прочитать позже: файл базы, резервную копию, номер договора. Ключ хранится отдельно от данных, иначе шифрование защищает только от потери диска.

| Операция | Обратима | Секрет | Для чего |
|---|---|---|---|
| Кодирование | да, без ключа | нет | передача и хранение текста |
| Хеширование | нет | соль | пароли, контроль целостности |
| Шифрование | да, с ключом | ключ | данные при хранении и передаче |

Данные в пути защищает TLS. Без него пароль и токен идут открытым текстом, и любой узел в сети может их прочитать. HTTPS обязателен не только для внешнего сайта, но и для обмена между сервисами внутри сети: внутренняя сеть не делает трафик безопасным.

Клиент проверяет сертификат сервера по цепочке доверия и сроку действия. Если проверку отключить ради удобства, соединение останется зашифрованным, но собеседник не будет проверен, и данные уйдут тому, кто выдаёт себя за сервер. Отключение проверки допустимо только на изолированном учебном стенде и только на время отладки.

Данные при хранении защищают шифрованием диска, файла базы или резервных копий. Отдельно решают, что делать с ключом: он не должен лежать в том же архиве, что и зашифрованная копия. Резервная копия без ключа бесполезна при восстановлении и опасна при утечке.

Собственные алгоритмы шифрования не пишут. Для стандартных задач берут библиотеку: TLS для канала, проверенный алгоритм для паролей, штатное шифрование для файлов. Самодельная схема почти всегда содержит ошибку, которую автор не видит.

Ключ живёт отдельно от данных и меняется по расписанию. Если ключ лежит рядом с зашифрованной резервной копией, кража архива даёт и замок, и ключ. При смене ключа старые копии перешифровывают или хранят вместе с идентификатором ключа, чтобы при восстановлении было понятно, чем их открывать. Потерянный ключ означает потерянные данные, поэтому копия ключа хранится в другом месте и с другим доступом.

Шифрование не заменяет права доступа. Расшифрованную базу может прочитать любой, у кого есть учётная запись приложения. Поэтому права на таблицы, проверка роли и журнал действий остаются обязательными даже при шифровании диска.

## Зависимости и обновления

Каждая библиотека в проекте выполняется с правами приложения. Уязвимость в пакете не менее опасна, чем уязвимость в собственном коде, а заметить её сложнее: исходный текст пакета никто не читает.

Работа с зависимостями состоит из трёх шагов. Первый: зафиксировать версии, чтобы сборка была воспроизводимой. Второй: проверять известные уязвимости по базе. В C# для этого служит `dotnet list package --vulnerable`, в Python сканер вроде `pip-audit` сверяет установленные версии с базой PyPA. Третий: обновлять в срок, который зависит от того, эксплуатируется ли уязвимость.

Каталог известных эксплуатируемых уязвимостей CISA полезен тем, что отделяет теоретические проблемы от тех, которые уже используют. Уязвимость из каталога исправляют в первую очередь, даже если её оценка кажется невысокой. Уязвимость без известных атак можно планировать в обычное обновление.

Проверять нужно и транзитивные зависимости, которые пришли вместе с прямыми. Пакет может не содержать уязвимости сам, но тянуть старую библиотеку с известной проблемой. Сканер показывает цепочку, поэтому обновление иногда начинается не с того пакета, который указан в проекте, а с его зависимости.

Полезен и перечень компонентов сборки. Список пакетов с версиями и лицензиями позволяет быстро ответить на вопрос «используем ли мы эту библиотеку» в день, когда о её уязвимости узнали все. Без такого списка поиск идёт по файлам проекта, а часть зависимостей приходит неявно.

Обновление это компромисс. Новая версия закрывает старую дыру, но может сломать совместимость. Поэтому обновляются небольшими шагами, с прогоном тестов и возможностью откатиться. Обновление раз в год крупным прыжком почти всегда заканчивается долгим разбором несовместимостей.

## Журнал и обнаружение

Защита без наблюдения отвечает только на попытки, которые уже случились, и молчит, когда атака идёт. Журнал нужен не для отчёта, а для ответа на три вопроса: что произошло, с какой учётной записью и что делать дальше.

Полезные события для «Склад+» это вход и выход, неудачные попытки, изменение прав, отказ в доступе, изменение остатка, экспорт данных и обращение к административным маршрутам. Для каждого события фиксируют время, идентификатор пользователя, действие, результат и идентификатор запроса. Пароль, токен и тело запроса в журнал не попадают.

Записывать всё подряд бесполезно: в большом журнале инцидент тонет. Поэтому задают пороги. Пять отказов по разным записям за минуту, вход из новой страны, серия ошибок на одном маршруте и обращение к административному адресу без роли это поводы для оповещения. Порог может быть грубым, но он должен быть, иначе журнал читают только после утечки.

Журнал тоже защищают. Злоумышленник, получивший доступ, старается стереть записи, поэтому журнал пишут на отдельный узел или в хранилище с ограниченным правом удаления. Срок хранения выбирают по требованиям, а не по размеру диска.

## Реальный случай: Equifax, 2017

Equifax, крупное бюро кредитных историй, обрабатывала данные сотен миллионов человек. В марте 2017 года была опубликована критическая уязвимость Apache Struts, и на следующий день уведомление пришло в компанию. Внутреннее письмо требовало установить исправление в течение 48 часов, но на одном из старых приложений патч не применили [House Oversight, 2018](https://oversight.house.gov/wp-content/uploads/2018/12/Equifax-Report.pdf).

В мае злоумышленники вошли через эту уязвимость и оставались в сети 76 дней. Они нашли файл с логинами и паролями в открытом виде, получили доступ к 48 базам и отправили около девяти тысяч запросов. Утечку не замечали потому, что устройство мониторинга трафика не работало: его сертификат истёк 19 месяцев назад. Всего пострадали 148 миллионов человек. В 2019 году компания согласилась выплатить не менее 575 миллионов долларов в рамках урегулирования с FTC, CFPB и штатами [FTC, 2019](https://www.ftc.gov/news-events/news/press-releases/2019/07/equifax-pay-575-million-part-settlement-ftc-cfpb-states-related-2017-data-breach).

В этом случае сработали сразу три правила из начала лекции. Устаревшая зависимость дала вход. Секреты в открытом виде дали доступ к другим базам. Отсутствие мониторинга дало время. Ни одна из трёх ошибок по отдельности не привела бы к такому масштабу.

| Ошибка | Что показала | Что проверять |
|---|---|---|
| Неустановленный патч | уведомление было, применения не было | срок исправления и учёт исключений |
| Секреты в файле | один файл открыл 48 баз | поиск паролей в репозитории и на дисках |
| Истёкший сертификат | мониторинг молчал 19 месяцев | срок действия и оповещения |

## Типичные ошибки

**Склейка SQL.** Строка `WHERE item = '{text}'` пропускает кавычку и комментарий. Симптом: поиск с апострофом возвращает весь список или ошибку синтаксиса. Лечится параметром, а не экранированием вручную.

**Секрет в репозитории.** Пароль в `appsettings.json` остаётся в истории Git. Симптом: секрет находят в старом коммите после удаления строки. Лечится сменой пароля и хранением вне репозитория.

**Проверка только в интерфейсе.** Кнопка скрыта, маршрут открыт. Симптом: запрос из Postman с обычным токеном выполняет запрещённое действие. Лечится атрибутом и политикой на сервере.

**Доверие полям из тела запроса.** Клиент присылает `role` вместе с названием товара, и модель записывает роль. Симптом: пользователь повышает себе права одним запросом. Лечится отдельной моделью с разрешёнными полями.

**Подробная ошибка на клиенте.** В ответ попадает текст SQL, имя таблицы и стек вызовов. Симптом: страница 500 рассказывает, как устроена база. Лечится общим сообщением клиенту и подробной записью в журнал.

**Кодирование вместо шифрования.** Base64 считают защитой и хранят в нём пароли. Симптом: строка легко раскрывается. Лечится хешированием паролей и настоящим шифрованием данных.

**Полные права у приложения.** Сервис подключается к базе как администратор. Симптом: ошибка в коде позволяет удалить таблицу. Лечится отдельной учётной записью с минимальными правами.

**Устаревшая зависимость.** В библиотеке есть известная уязвимость, а версия не обновлялась. Симптом: сканер находит проблему в пакете. Лечится обновлением и проверкой `dotnet list package --vulnerable`.

**Отключённая проверка сертификата.** Ради удобства в коде появился обход проверки TLS. Симптом: приложение соединяется с любым сервером, который выдаёт себя за нужный. Лечится возвратом проверки и настройкой доверенного сертификата.

## Проверка перед выпуском

| Проверка | Вопрос | Признак проблемы |
|---|---|---|
| Запросы | все значения переданы параметрами | в коде есть интерполяция в SQL |
| Секреты | в репозитории нет паролей и ключей | поиск по слову `password` находит значение |
| Доступ | каждый маршрут защищён | новый контроллер открыт без атрибута |
| Записи | проверяется владелец | действие доверяет номеру из адреса |
| Ошибки | клиент не видит внутренностей | в ответе есть текст SQL |
| Канал | HTTPS обязателен | пароль идёт по HTTP |
| Зависимости | нет известных уязвимостей | сканер пакетов выдаёт предупреждение |
| Журнал | события и отказы записываются | инцидент нельзя восстановить по записям |

Полноту проверки удобно сверять с ASVS 5.0: стандарт перечисляет требования к проверке ввода, управлению секретами, контролю доступа и обработке ошибок, и каждое требование можно проверить в коде или запросе [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/).

Проверку повторяют не один раз перед сдачей, а при каждом изменении, которое касается входа, запросов и настроек. Новый маршрут, новая таблица и новый внешний сервис добавляют путь, которого раньше не было. Список проверок короткий, поэтому его можно пройти за несколько минут и не полагаться на память.

Отдельно проверяют поведение при ошибке. Отключают базу, вводят неверный пароль, отправляют чужой идентификатор и смотрят, что видит клиент. Если в ответе есть текст SQL, имя таблицы или стек вызовов, защита настроена неверно, даже когда обычные запросы работают.

## Итоги

- Инъекция возникает там, где ввод склеивают с текстом команды, и лечится параметрами.
- Секреты хранят вне репозитория, а попавший в историю секрет считают скомпрометированным и меняют.
- Доступ проверяют на сервере для маршрута, роли, конкретной записи и допустимых полей.
- Кодирование не защищает, хеширование необратимо, шифрование требует ключа.
- TLS защищает данные в пути, шифрование и права доступа защищают данные при хранении.
- Зависимость это часть поверхности атаки, поэтому версии фиксируют и проверяют по каталогу уязвимостей.
- Инъекцию, утечку секретов и слабые права объединяет одно: приложение доверяет данным, которые пришли извне.
- Перед выпуском проверяют запросы, секреты, маршруты, ошибки, зависимости и журнал.

Q: Как называется атака, при которой введённый текст становится частью SQL-запроса?
+ SQL-инъекция
- Межсайтовый скриптинг
- Подбор пароля
- Отказ в обслуживании
! Ввод не отделяется от команды, поэтому база исполняет его как код.

Q: Почему параметризованный запрос защищает от инъекции?
+ Значение передаётся отдельно и не разбирается как часть команды
- Значение шифруется перед отправкой
- Значение удаляется из запроса
- Запрос выполняется только для администратора
! База сначала разбирает структуру запроса, а затем подставляет значение.

Q: Что делать с секретом, который попал в историю Git?
+ Считать скомпрометированным и сменить
- Удалить строку и считать вопрос закрытым
- Переименовать файл
- Добавить файл в gitignore
! Старая версия остаётся в истории, поэтому секрет меняют.

Q: Где хранить пароль базы на сервере?
+ В переменной окружения или хранилище секретов
- В коде приложения
- В appsettings.json в репозитории
- В комментарии к контроллеру
! Секрет не должен попадать в репозиторий и в образ приложения.

Q: Что такое Base64?
+ Кодирование без секрета, которое легко раскрывается
- Шифрование с ключом
- Необратимый хеш
- Алгоритм подписи токена
! Base64 меняет форму данных, но не скрывает их.

Q: Что защищает данные при передаче между клиентом и сервером?
+ TLS
- Base64
- Соль
- Имя пользователя в адресе
! TLS шифрует канал и проверяет сертификат сервера.

Q: Что такое массовое назначение полей?
+ Лишние поля из тела запроса попадают в модель и сохраняются
- Массовое создание пользователей администратором
- Пакетная вставка строк в таблицу
- Одновременная работа нескольких складов
! Клиент присылает больше полей, чем разрешено, и меняет служебные значения.

Q: Что делает команда dotnet list package --vulnerable?
+ Показывает пакеты с известными уязвимостями
- Обновляет все пакеты до последней версии
- Удаляет неиспользуемые зависимости
- Публикует проект на сервере
! Команда сверяет версии пакетов с базой уязвимостей.

Q: Что делать с подробным текстом ошибки в рабочей среде?
+ Показать клиенту общее сообщение, а подробности записать в журнал
- Показать клиенту текст SQL для диагностики
- Отключить журналирование
- Вернуть код 200
! Подробности помогают атакующему понять устройство базы.

Q: Какие меры защищают от SQL-инъекции?
+ Параметризованные запросы
+ ORM с параметрами вместо готовой строки
+ Белый список для сортировки и имён колонок
- Экранирование кавычек вручную во всех местах
- Хранение пароля базы в коде
! Параметры и белый список убирают возможность изменить структуру команды.

Q: Какие каналы могут выдать секрет?
+ История Git
+ Журнал приложения
+ Снимок экрана и переписка
- Файл стилей
- Список маршрутов API
! Секрет утекает везде, где его значение сохраняется или отображается.

Q: Что показал случай Equifax?
+ Устаревшая зависимость, открытые секреты и молчащий мониторинг усилили друг друга
+ Патч был доступен, но его не применили к старому приложению
+ Истёкший сертификат скрывал утечку 19 месяцев
- Одной ошибки в SQL-запросе хватило для всей утечки
- Компания не использовала Apache Struts
! Масштаб дала комбинация трёх ошибок, а не одна строка кода.

Q: Что нужно сделать с секретом после утечки?
= сменить

= отозвать
