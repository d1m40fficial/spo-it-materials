## Накладная, которая пришла двумя файлами

В понедельник 5 октября 2026 года в ООО «Северный склад» приходят два файла. Поставщик «ТрансЛогистика» присылает `supplies.json` с тремя поставками. Бухгалтерия выгружает `stock.csv` со справочником товаров. В справочнике 4800 позиций, 12 товарных категорий и четыре площадки: Москва, Тверь, Тула и Калуга. Кладовщик открывает оба файла и ищет товар `SKU-1042`.

В JSON количество записано как `"qty": 48`, в CSV та же величина стоит в ячейке `48`. На экране это одно и то же число. После разбора выясняется, что в первом случае программа получила целое число `48`, а во втором строку `"48"`. Пока значение только печатают, разницы не видно. Как только его складывают с другим количеством или сравнивают с порогом, строка ведёт себя иначе: `"48" + "12"` даёт `"4812"`, а `"48" > "100"` возвращает `True`, потому что строки сравниваются посимвольно.

**Формат обмена это договор о структуре данных, а не о внешнем виде файла.** Договор отвечает на вопросы: где лежит заголовок, чем разделены поля, какие значения считаются числом, что означает пустая ячейка и можно ли вкладывать один объект в другой. Если договор не описан, каждая сторона понимает его по-своему, и ошибка проявляется уже в базе склада.

Дальше разберём два формата, которые чаще всего встречаются в учебном проекте `sklad-plus`: JSON для обмена с сервисами и CSV для обмена с таблицами и бухгалтерией. Главный вопрос занятия простой: что именно формат сообщает о данных и что приходится восстанавливать вручную.

## Что на самом деле хранит JSON

JSON строится из шести видов значений: объект, массив, строка, число, логическое значение и `null`. Объект это набор пар «ключ и значение» в фигурных скобках. Массив это упорядоченный список в квадратных скобках. Всё остальное это скалярные значения.

```json
{
  "number": "НК-2026-0417",
  "warehouse": "Москва",
  "date": "2026-10-05",
  "items": [
    {"sku": "SKU-1042", "title": "Перчатки нитриловые", "qty": 48, "price": 312.50},
    {"sku": "SKU-2210", "title": "Стрейч-плёнка", "qty": 12, "price": 890.00}
  ],
  "closed": false
}
```

Разберём этот документ в Python и посмотрим на типы.

```python
import json

raw = """{
  "number": "НК-2026-0417",
  "warehouse": "Москва",
  "date": "2026-10-05",
  "items": [
    {"sku": "SKU-1042", "title": "Перчатки нитриловые", "qty": 48, "price": 312.50},
    {"sku": "SKU-2210", "title": "Стрейч-плёнка", "qty": 12, "price": 890.00}
  ],
  "closed": false
}"""

doc = json.loads(raw)
print(type(doc).__name__, list(doc))
print(doc["items"][0]["qty"], type(doc["items"][0]["qty"]).__name__)
print(doc["date"], type(doc["date"]).__name__)
print(doc["closed"], type(doc["closed"]).__name__)
print(sum(item["qty"] * item["price"] for item in doc["items"]))
```

Вывод:

```text
dict ['number', 'warehouse', 'date', 'items', 'closed']
48 int
2026-10-05 str
False bool
25680.0
```

Четыре наблюдения по этому выводу.

Первое: объект стал словарём `dict`, массив стал списком `list`, строка осталась строкой, число стало `int` или `float`, логическое значение стало `bool`. Соответствие предсказуемое, и на нём строится вся работа с JSON в Python.

Второе: дата `2026-10-05` осталась строкой. В JSON нет типа «дата». Для дат договариваются об ISO 8601, потому что такая строка сортируется как текст и однозначно читается, но проверять её всё равно должна программа. Если поставщик пришлёт `05.10.2026`, разбор не упадёт: он просто вернёт другую строку, и ошибка всплывёт позже, при сравнении или записи в базу.

Третье: `false` стало `False`. Это уже логическое значение, а не строка `"false"`. Разница существенна: `if doc["closed"]` работает, а `if doc["closed"] == "false"` никогда не выполнится.

Четвёртое: сумма `25680.0` получилась вещественной, потому что цена задана как `312.50`. Для учебного примера это нормально. Для денег в рабочей системе так поступать не стоит: двоичное представление дроби накапливает погрешность. Ниже разберём, чем заменить `float`.

Отдельно стоит сказать про порядок ключей. В спецификации JSON объект это неупорядоченный набор пар. Python сохраняет порядок вставки при разборе, и на этом удобно строить вывод, но полагаться на порядок ключей в чужом документе нельзя. Если порядок важен, используйте массив, а не объект.

## Вложенность: сила и цена

Главное преимущество JSON в том, что он хранит структуру, а не только значения. Накладная содержит список строк, и этот список лежит внутри объекта накладной. Никакой отдельной таблицы связей для этого не нужно.

К вложенному значению ведёт путь из ключей и индексов.

```python
print(doc["items"][1]["sku"])
print(doc["warehouse"])
```

```text
SKU-2210
Москва
```

Путь читается слева направо: взять ключ `items`, затем второй элемент списка, затем ключ `sku`. Если на любом шаге ключа нет, Python выбросит `KeyError`, а если индекс вышел за границы списка, то `IndexError`. Это не недостаток формата, а сигнал, что документ не соответствует договору.

Для необязательных полей используют `get`.

```python
discount = doc.get("discount", 0)
print(discount)
```

```text
0
```

Вложенность удобна, но у неё есть цена. Чем глубже структура, тем больше кода проверяет наличие промежуточных уровней. Если документ приходит от внешней системы, каждое обязательное поле стоит проверить явно и вернуть понятную ошибку с именем поля, а не молча получить `KeyError` в середине импорта.

Типичная ошибка новичка выглядит так: программа обращается к `doc["shipments"][0]["items"][0]["qty"]`, а поставщик присылает пустой список поставок. Индекс `0` падает, импорт останавливается, и в журнале остаётся только трассировка. Правильнее сначала проверить, что список не пуст, и обработать пустой документ как отдельный случай.

У вложенности есть и обратная сторона для базы данных. Накладная в JSON это один объект, а в реляционной базе это две таблицы: заголовок и строки. При импорте нужно разложить дерево на строки, сохранить связь по идентификатору и позаботиться о том, чтобы повторный импорт не создал дубли. Формат обмена не решает эту задачу за вас: он только доносит структуру.

После разбора документ стоит превратить в объекты программы, а не передавать словарь через все функции. Словарь не подсказывает, какие поля обязательны, и не проверяет типы. Класс или `dataclass` с явными полями делает контракт видимым: у накладной есть номер, склад, дата и список строк, у строки есть артикул, количество и цена. Преобразование выполняет отдельная функция, которая либо возвращает объект, либо поднимает ошибку с именем поля. Дальше бизнес-логика работает с объектами и не знает, пришли данные из JSON, из CSV или из базы.

Такое разделение полезно и при тестировании. Проверку разбора можно сделать на небольшом документе, не поднимая базу и не обращаясь к сети. Проверку правил можно сделать на объектах, не создавая файлы. Если же словарь гуляет по всему коду, тест на одну функцию требует собрать весь документ целиком, а изменение поля ломает сразу несколько слоёв.

## Что JSON не гарантирует

У JSON есть ограничения, о которых забывают, потому что формат выглядит простым.

**Нет комментариев.** Строка `//` или `/* */` делает документ недопустимым. Конфигурацию с комментариями хранят в другом формате, а в JSON оставляют пояснения в отдельном поле или в документации.

**Нет типа «дата» и «деньги».** Дата остаётся строкой, деньги остаются числом или строкой. И то, и другое проверяет принимающая сторона. Для денег в Python удобно разбирать число сразу в `Decimal`, а не в `float`.

**Нет обязательных полей.** Спецификация не говорит, какие ключи должны присутствовать. Два документа с одинаковой структурой могут отличаться набором полей. Обязательность описывают отдельно, например схемой JSON Schema [JSON Schema](https://json-schema.org/draft/2020-12/json-schema-core).

**Ключи должны быть уникальны, но это не гарантировано.** RFC 8259 говорит, что имена в объекте должны быть уникальны, однако при дублях поведение программ непредсказуемо: одни оставляют последнее значение, другие первое, третьи сообщают об ошибке [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259.html). Python по умолчанию оставляет последнее. Если поставщик присылает два ключа `qty`, результат зависит от парсера, и спор о том, «какое число правильное», не имеет технического ответа.

**Числа ограничены точностью.** RFC 8259 рекомендует считать interoperable только целые в диапазоне от минус 2 в 53-й степени плюс один до 2 в 53-й степени минус один. Более длинные целые и очень точные дроби могут потерять точность при разборе в `double`. Для идентификаторов, которые выглядят как число, безопаснее строка.

**У разбора есть ресурсные пределы.** Слишком глубокая вложенность упирается в предел рекурсии или в настройку парсера, огромная строка занимает память, а документ на гигабайт не помещается в процесс. Это не ошибка формата, а ограничение реализации, и его нужно знать до того, как принимать файл от внешней системы. В C# `JsonDocument` имеет настройку максимальной глубины, в Python глубина ограничена рекурсией интерпретатора. Если файл приходит извне, размер, глубину и количество элементов проверяют до разбора, а не после.

**Сжатые данные требуют отдельного лимита.** Архив может распаковаться в сотни раз больше исходного размера и исчерпать диск или память. Если обмен идёт через архив, ограничивают размер распакованного содержимого и число файлов, а не только размер принятого архива.

**BOM в JSON не нужен.** RFC 8259 требует, чтобы JSON в открытом обмене был в UTF-8, и запрещает добавлять BOM в начало сетевого документа. Парсер может BOM игнорировать, но не обязан. Практический вывод: JSON пишут в UTF-8 без BOM, а при чтении чужих файлов проверяют первые байты.

**Порядок ключей не гарантирован.** Даже если Python сохраняет порядок вставки, другой язык или другая версия библиотеки может его изменить. Если порядок важен, используют массив.

Эти ограничения не делают JSON плохим. Они означают, что формат отвечает за синтаксис, а за смысл отвечает договор и проверка. JSON Schema как раз описывает смысл: типы полей, обязательность, допустимые значения и вложенные структуры. Проверка по схеме до импорта дешевле, чем разбор последствий в базе.

```json
{
  "type": "object",
  "required": ["number", "warehouse", "items"],
  "properties": {
    "number": {"type": "string", "minLength": 1},
    "warehouse": {"type": "string"},
    "date": {"type": "string", "format": "date"},
    "items": {
      "type": "array",
      "minItems": 1,
      "items": {
        "type": "object",
        "required": ["sku", "qty", "price"],
        "properties": {
          "sku": {"type": "string"},
          "qty": {"type": "integer", "minimum": 1},
          "price": {"type": "number", "minimum": 0}
        }
      }
    }
  }
}
```

Схема не заменяет бизнес-правила. Она не знает, что артикул должен существовать в справочнике или что остаток не может стать отрицательным. Но она отсекает структурные ошибки до того, как они попадут в код, и делает сообщение об ошибке точным: не «неверный JSON», а «поле items[0].qty должно быть целым числом».

У схемы есть версия, и это не формальность. Если поставщик добавляет поле, старый клиент не должен падать. Если поле становится обязательным, это новая версия договора, и старые файлы перестают проходить проверку. Практическое правило: новые необязательные поля добавляют без смены версии, удаление и переименование полей требуют новой версии и переходного периода. Политика для неизвестных полей тоже входит в договор: их можно игнорировать, сохранять или отклонять. Молчаливое игнорирование удобно для совместимости, но может скрыть опечатку в имени поля.

JSON Schema поддерживает это через `required`, `properties` и `additionalProperties`. Если `additionalProperties` равно `false`, лишнее поле становится ошибкой. Если схема не задаёт его, лишние поля обычно разрешены. Выбор зависит от того, хотите ли вы ловить опечатки строго или принимать расширения от новых версий поставщика. Записать это решение в договор дешевле, чем выяснять его при первом конфликте.

## CSV: таблица, у которой всё строки

CSV это текст, в котором строки файла соответствуют строкам таблицы, а поля разделены одним символом. Обычно это запятая, точка с запятой или табуляция. Первая строка часто содержит заголовок с именами столбцов.

```csv
sku;title;qty;price
SKU-1042;Перчатки нитриловые;48;312,50
SKU-2210;Стрейч-плёнка;12;890,00
```

Формат кажется простым, но у него нет единого стандарта, который соблюдали бы все программы. RFC 4180 описывает распространённое соглашение: разделитель запятая, строки разделены CRLF, поля с разделителем или переводом строки заключаются в двойные кавычки, кавычка внутри поля удваивается [RFC 4180](https://www.rfc-editor.org/rfc/rfc4180.html). Excel и русская локаль часто используют точку с запятой, потому что запятая занята десятичным разделителем. Поэтому первое, что нужно сделать при чтении CSV, это выяснить разделитель и кодировку.

У RFC 4180 есть важная оговорка: это информационный документ, а не строгий стандарт. Он сам признаёт, что реализации различаются, и советует быть консервативным в том, что создаёшь, и либеральным в том, что принимаешь. На практике это означает, что «CSV» может означать десяток несовместимых диалектов. Договор обмена должен фиксировать не слово CSV, а конкретные параметры: кодировку, разделитель, кавычки, перевод строки и десятичный разделитель.

Прочитаем тот же файл модулем `csv`.

```python
import csv
import io

text = (
    "sku;title;qty;price\n"
    "SKU-1042;Перчатки нитриловые;48;312,50\n"
    "SKU-2210;Стрейч-плёнка;12;890,00\n"
)

rows = list(csv.DictReader(io.StringIO(text), delimiter=";"))
print(rows[0])
print(type(rows[0]["qty"]).__name__)
print(type(rows[0]["price"]).__name__)
```

```text
{'sku': 'SKU-1042', 'title': 'Перчатки нитриловые', 'qty': '48', 'price': '312,50'}
str
str
```

`DictReader` берёт первую строку как имена полей и возвращает словари. Удобно, что порядок столбцов можно менять, а код обращается к значениям по имени. Но все значения остаются строками, включая количество и цену. Модуль `csv` не знает, что `48` это число: он видит только текст между разделителями.

Вторая особенность касается десятичной запятой. Строка `312,50` не преобразуется в число функцией `float` напрямую. Нужно заменить запятую на точку или использовать локаль. В учебном проекте выбирают один способ и фиксируют его в договоре обмена.

Третья особенность это BOM. Excel при сохранении в UTF-8 может поставить в начало файла невидимый символ `\ufeff`. Если открыть файл с кодировкой `utf-8`, этот символ попадёт в имя первого столбца.

```python
from pathlib import Path

path = Path("bom.csv")
path.write_text("\ufeffsku;qty\nSKU-1042;48\n", encoding="utf-8")

with path.open(encoding="utf-8", newline="") as file:
    reader = csv.DictReader(file, delimiter=";")
    print("поля:", reader.fieldnames)

with path.open(encoding="utf-8-sig", newline="") as file:
    reader = csv.DictReader(file, delimiter=";")
    print("поля с sig:", reader.fieldnames)
```

```text
поля: ['\ufeffsku', 'qty']
поля с sig: ['sku', 'qty']
```

Кодировка `utf-8-sig` читает BOM и отбрасывает его. Если этого не сделать, код `row["sku"]` выбросит `KeyError`, хотя столбец `sku` в файле есть. Симптом коварный: глазами файл выглядит правильным.

Четвёртая особенность это кавычки. Поле `"Перчатки, нитриловые"` содержит запятую, поэтому должно быть в кавычках. Если разделитель точка с запятой, запятая внутри поля безопасна, а точка с запятой требует кавычек. Кавычка внутри поля удваивается: `"ООО ""Северный склад"""`. Разбор вручную через `line.split(";")` ломается на первом же таком поле, поэтому для CSV используют модуль, а не деление строки.

| Поле | JSON | CSV | Что сделать |
|---|---|---|---|
| Количество | `48` (число) | `48` (строка) | `int(row["qty"])` |
| Цена | `312.5` (число) | `312,50` (строка) | заменить запятую, затем `Decimal` |
| Дата | `2026-10-05` (строка) | `05.10.2026` (строка) | разобрать `datetime.strptime` |
| Артикул | `SKU-1042` (строка) | `SKU-1042` (строка) | оставить строкой |
| Признак | `false` (логическое) | `0` или `нет` (строка) | сопоставить с таблицей значений |
| Пустая ячейка | `null` | пустая строка | решить, это ноль или отсутствие |

Начнём с количества. В JSON число приходит числом, потому что формат различает строку и число синтаксически: `48` без кавычек это число, `"48"` в кавычках это строка. В CSV кавычки означают только экранирование разделителя, а не тип. Поэтому `48` и `"48"` в CSV это одна и та же строка.

Цена сложнее. Даже если заменить запятую на точку и вызвать `float`, для денег получится неточное значение. Проверка `0.1 + 0.2 == 0.3` возвращает `False`, потому что двоичная дробь не представляет десятичные доли точно. В учебном проекте для цен и сумм используют `Decimal`, а в базу записывают целое число копеек или тип `NUMERIC` с фиксированной точностью.

```python
from decimal import Decimal

price = Decimal("312.50")
qty = 48
print(price * qty)
print(Decimal("0.1") + Decimal("0.2") == Decimal("0.3"))
```

```text
15000.00
True
```

У `Decimal` есть цена: он медленнее `float` и требует явного контекста округления. Для 4800 позиций это незаметно, для миллионов строк разница станет ощутимой. Выбор зависит от задачи. Деньги, налоги и остатки в бухгалтерии требуют точности. Научные расчёты и графики часто допускают `float`.

Дата требует явного формата. Строка `05.10.2026` не разбирается функцией `datetime.fromisoformat`. Нужен `strptime` с шаблоном `%d.%m.%Y`. Если формат в файле может измениться, его указывают в договоре обмена и проверяют при импорте. Молчаливая попытка угадать формат приводит к тому, что часть дат читается как май, а часть как декабрь.

Артикул наоборот нельзя превращать в число. `SKU-1042` содержит буквы, поэтому остаётся строкой. Но и чисто цифровые артикулы вроде `007` опасно пропускать через `int`: ведущий ноль исчезнет, и товар перестанет находиться. Правило простое: идентификатор всегда строка, даже если выглядит числом.

Логический признак в CSV не имеет стандарта. Встречаются `true` и `false`, `1` и `0`, `да` и `нет`, `Y` и `N`. Программа должна привести их к одному типу явной таблицей соответствия, а не полагаться на `bool("false")`, который вернёт `True`, потому что непустая строка истинна. Это одна из самых частых ошибок при импорте.

Пустая ячейка тоже требует решения. В JSON есть `null`, и он отличается от нуля и от пустой строки. В CSV пустая ячейка неотличима от отсутствующего значения, если договор не задаёт правило. Для количества пустая ячейка обычно означает ноль, для цены отсутствие данных, для даты «ещё не выполнено». Одно и то же пустое место в разных столбцах означает разное, и это нужно прописать.

Есть ещё одна потеря, которую замечают не сразу: масштаб десятичной дроби. JSON число `312.50` после разбора в `float` становится `312.5`, и информация о двух знаках после запятой исчезает. Для цены это обычно неважно, для бухгалтерского документа важно. `Decimal("312.50")` сохраняет масштаб, а `float` нет. Поэтому в договоре обмена фиксируют не только формат, но и правило округления.

## Сравнение форматов

Теперь можно сравнить форматы по признакам, которые важны при обмене.

| Признак | JSON | CSV |
|---|---|---|
| Структура | дерево с вложенностью | плоская таблица |
| Типы значений | различает число, строку, логическое значение, null | все значения строки |
| Заголовок | ключи объекта | первая строка, часто обязательна |
| Повторяющиеся группы | массив внутри объекта | отдельная таблица или повторение строк |
| Читаемость для человека | средняя, много скобок | высокая, похоже на таблицу |
| Открытие в Excel | требует преобразования | открывается напрямую |
| Размер | больше из-за ключей | меньше при том же наборе полей |
| Обмен с API | естественный формат | редкий, требует описания |
| Потоковая обработка | возможна построчно, но сложнее | удобна построчно |
| Риск потери типов | низкий | высокий |

Из таблицы видно, что форматы решают разные задачи. JSON выигрывает там, где данные имеют структуру: накладная со строками, заказ с позициями, ответ сервиса с вложенными объектами. CSV выигрывает там, где данные плоские и их много: справочник товаров, остатки по складам, выгрузка для бухгалтерии.

Есть и промежуточный случай. Иногда одну и ту же информацию отдают в двух форматах: JSON для программы и CSV для человека. Это нормальная практика, если оба файла строятся из одного источника и проходят проверку. Плохо, когда два формата живут отдельно и расходятся по составу полей.

У JSON есть ограничения, о которых забывают. В нём нет комментариев, нет ссылок между объектами, нет типа «дата» и нет обязательных полей. Два документа с одинаковой структурой могут отличаться набором ключей. Поэтому JSON-схему описывают отдельно, например через JSON Schema, и проверяют документ перед импортом.

У CSV тоже есть скрытые сложности. Разделитель зависит от локали, кодировка от программы, десятичный разделитель от настроек Windows, а кавычки внутри поля требуют удвоения. Файл, который открывается в Excel, не обязательно правильно прочитается модулем `csv` с настройками по умолчанию.

## Чтение и запись в Python

Начнём с JSON. Чтение из файла выполняет `json.load`, разбор строки выполняет `json.loads`. Запись в файл выполняет `json.dump`, преобразование в строку выполняет `json.dumps`.

```python
import json

record = {"sku": "SKU-1042", "title": "Перчатки нитриловые"}

print(json.dumps(record, ensure_ascii=False, indent=2))
print(json.dumps(record))
```

```text
{
  "sku": "SKU-1042",
  "title": "Перчатки нитриловые"
}
{"sku": "SKU-1042", "title": "\u041f\u0435\u0440\u0447\u0430\u0442\u043a\u0438 \u043d\u0438\u0442\u0440\u0438\u043b\u043e\u0432\u044b\u0435"}
```

Параметр `ensure_ascii=False` оставляет кириллицу читаемой. Без него каждый русский символ превращается в последовательность `\uXXXX`. Оба варианта корректны с точки зрения JSON, но первый удобнее для чтения и меньше по размеру. Параметр `indent=2` добавляет отступы: файл становится длиннее, зато его можно сравнивать глазами и в системе контроля версий.

Для записи в файл удобно использовать контекстный менеджер.

```python
from pathlib import Path

path = Path("supplies.json")
with path.open("w", encoding="utf-8") as file:
    json.dump(record, file, ensure_ascii=False, indent=2)
```

Теперь CSV. Чтение через `DictReader` мы уже видели. Запись выполняет `DictWriter`.

```python
import csv

rows = [
    {"sku": "SKU-1042", "qty": 48},
    {"sku": "SKU-2210", "qty": 12},
]

with open("stock.csv", "w", encoding="utf-8-sig", newline="") as file:
    writer = csv.DictWriter(file, fieldnames=["sku", "qty"], delimiter=";")
    writer.writeheader()
    writer.writerows(rows)
```

Здесь важны три параметра. `encoding="utf-8-sig"` добавляет BOM, чтобы Excel правильно показал кириллицу. `newline=""` отключает преобразование переводов строк: без него на Windows каждая запись получит лишний `\r`, и в файле появятся пустые строки между данными. `delimiter=";"` задаёт разделитель, совпадающий с настройками русской локали.

Проверить результат можно повторным чтением и сравнением количества строк. Это дешевле, чем открывать файл вручную, и хорошо ложится в автоматическую проверку.

У чтения JSON есть настройки, которые полезны для денег и дублей. `parse_float=Decimal` разбирает дробные числа сразу в `Decimal`, не проходя через `float`. `object_pairs_hook` получает все пары ключей и значений, включая дубли, и позволяет проверить их до того, как словарь оставит последнее значение. `parse_constant` управляет обработкой `NaN` и `Infinity`, которые Python принимает по умолчанию, хотя RFC 8259 их запрещает.

```python
import json
from decimal import Decimal

text = '{"qty": 48, "price": 312.50, "qty": 50}'

def no_duplicates(pairs):
    keys = [key for key, value in pairs]
    if len(keys) != len(set(keys)):
        raise ValueError("в объекте повторяется ключ")
    return dict(pairs)

doc = json.loads('{"qty": 48, "price": 312.50}', parse_float=Decimal)
print(doc["price"], type(doc["price"]).__name__)

try:
    json.loads(text, object_pairs_hook=no_duplicates)
except ValueError as err:
    print("дубль:", err)
```

Для документа с дублем `qty` этот код поднимет `ValueError`, а не молча оставит 50. Для документа без дубля цена станет `Decimal`. Такой разбор строже стандартного и лучше подходит для импорта из внешней системы.

Запись тоже требует настроек. `allow_nan=False` запрещает записывать `NaN` и `Infinity`, которые не являются допустимым JSON. `sort_keys=True` делает порядок ключей предсказуемым, если файл сравнивают в системе контроля версий. `ensure_ascii=False` сохраняет кириллицу. Вместе это даёт файл, который одинаково читается человеком и программой.

## Тот же обмен на C#

В C# для JSON есть `System.Text.Json`. Код читает документ и обходит вложенные массивы.

```csharp
using System;
using System.IO;
using System.Text.Json;

string path = Path.Combine("data", "supplies.json");
string json = File.ReadAllText(path);
using JsonDocument doc = JsonDocument.Parse(json);

JsonElement root = doc.RootElement;
Console.WriteLine(root.GetProperty("supplier").GetString());

foreach (JsonElement shipment in root.GetProperty("shipments").EnumerateArray())
{
    string number = shipment.GetProperty("number").GetString()!;
    foreach (JsonElement item in shipment.GetProperty("items").EnumerateArray())
    {
        int qty = item.GetProperty("qty").GetInt32();
        decimal price = item.GetProperty("price").GetDecimal();
        Console.WriteLine($"{number} {item.GetProperty("sku").GetString()} {qty * price}");
    }
}
```

Разница с Python видна сразу: C# требует указывать тип при чтении. `GetInt32` упадёт, если в документе окажется строка `"48"`. Это не придирка языка, а полезная проверка договора: документ, который не соответствует схеме, не пройдёт дальше. В Python такая же проверка выполняется вручную или через библиотеку валидации.

`JsonDocument` держит весь документ в памяти и даёт доступ к любому элементу. Для больших файлов есть `Utf8JsonReader`, который читает поток токенов без построения дерева, и `JsonSerializer`, который переводит документ в классы. Выбор такой же, как в Python между `json.load` и построчным разбором: дерево удобнее, поток экономнее.

Для CSV в .NET нет встроенного разборщика, который понимал бы все правила RFC 4180. Простой `line.Split(';')` ломается на поле с точкой с запятой внутри кавычек и на переводе строки внутри значения. В учебном проекте CSV читают на Python, а на C# обрабатывают JSON, либо подключают отдельную библиотеку и фиксируют её версию в файле зависимостей. В составе .NET есть `TextFieldParser` из пространства `Microsoft.VisualBasic.FileIO`, который умеет кавычки и разделители, но его поведение и доступность зависят от платформы, поэтому его тоже проверяют на учебных данных.

## Проверка перед записью

Импорт редко заканчивается разбором. Данные нужно проверить, преобразовать и записать. Порядок шагов влияет на то, какие ошибки дойдут до базы.

Сначала проверяется структура: документ разбирается, обязательные поля присутствуют, типы совпадают. Затем проверяются значения: количество положительное, цена не отрицательная, дата в допустимом диапазоне, артикул существует в справочнике. Только после этого данные преобразуются в объекты программы и записываются одной транзакцией.

Если проверять по одной записи и сразу писать, ошибка на середине оставит половину импорта. Если сначала собрать все ошибки, можно показать поставщику список проблем и не менять базу вовсе. Для накладной лучше второй вариант. Для справочника из 4800 позиций иногда разумнее загрузить корректные строки, а ошибочные вернуть отдельным файлом, но это решение должно быть записано в договоре.

Проверка по схеме и проверка бизнес-правил это разные уровни. Схема отвечает, что `qty` это целое число. Бизнес-правило отвечает, что товара с таким артикулом хватает на складе. Смешивать их в одном обработчике не стоит: схема применяется до преобразования, бизнес-правило после, и сообщения об ошибке у них разные.

Отдельный случай это большой поток однотипных записей. Массив из миллиона объектов плохо ложится в память и неудобен для дописывания. Для журналов и пакетной выгрузки используют JSON Lines: один объект на строку, каждая строка самостоятельна. Такой файл читают построчно, не загружая целиком, и дописывают новой строкой без переписывания предыдущих.

У JSON Lines есть свои границы. Это не отдельный стандарт, а соглашение, поэтому договор обмена должен запрещать переводы строк внутри объекта. Если процесс упал на середине записи, последняя строка может оказаться неполной, и её нужно отбрасывать или проверять. При дописывании из нескольких процессов строки могут перемешаться, поэтому нужен один писатель или блокировка. Для журнала событий эти компромиссы приемлемы, для накладной лучше один цельный JSON, который либо принят, либо отклонён целиком.

## Реальные сбои

### Формулы в CSV

CSV открывают в Excel, а Excel интерпретирует ячейку, которая начинается с `=`, как формулу. Если выгрузка содержит имя поставщика, комментарий или название товара из внешнего источника, злоумышленник может записать туда формулу. При открытии файла она выполнится на компьютере бухгалтера. Это называется CSV injection, или formula injection [OWASP](https://community.owasp.org/attacks/CSV_Injection).

Опасны не только `=`, но и `+`, `-`, `@`, табуляция, перевод строки, а также полноширинные варианты этих знаков. Формула может обратиться к внешнему ресурсу, собрать данные из соседних ячеек или использовать уязвимость самой программы. В 2014 году в Apache OpenOffice была исправлена уязвимость CVE-2014-3524, связанная с выполнением команд через специально сформированную электронную таблицу [CVE-2014-3524](https://www.cve.org/CVERecord?id=CVE-2014-3524). Это показывает, что угроза не теоретическая.

Защита зависит от того, кто читает файл. Если CSV предназначен для программы, достаточно экранировать кавычки по RFC 4180: формула останется текстом. Если файл открывают в Excel, одного экранирования мало: Excel может снять кавычки при сохранении и повторном открытии, и формула снова станет активной. OWASP рекомендует ставить перед опасным значением апостроф или табуляцию, но предупреждает, что табуляция остаётся в данных и мешает программному импорту. Универсального решения нет: нужно выбирать между безопасностью для человека и чистотой данных для программы.

В учебном проекте достаточно правила: при выгрузке проверять начало каждого текстового поля и либо запрещать опасные символы, либо добавлять апостроф, а в договоре писать, что файл предназначен для Excel. Молча выгружать пользовательские строки в CSV и надеяться, что никто не откроет файл, нельзя.

::figure csv-injection | Как формула попадает из текстового поля в ячейку Excel. Слева исходная строка поставщика, справа результат открытия файла. Внизу перечислены опасные начала ячеек и цена двух способов защиты.

### BOM и кодировка в JSON

Второй случай выглядит безобидно. Программа на Windows сохраняет JSON в UTF-8 с BOM, потому что так делает редактор или библиотека. Формально файл читается, но `json.loads` в Python получает строку, которая начинается с невидимого `\ufeff`, и выдаёт `JSONDecodeError: Unexpected UTF-8 BOM`. RFC 8259 прямо говорит, что генератор не должен добавлять BOM в JSON, а парсер может его игнорировать, но не обязан.

Лечение простое: читать файл с `encoding="utf-8-sig"` или убрать BOM при записи. Сложность в том, что ошибка проявляется не на вашей машине, а на стороне принимающей системы, и сообщение указывает на позицию 0, где визуально ничего нет. Поэтому BOM проверяют в тестах обмена, а не после жалобы.

Третий случай связан с дублями ключей. Поставщик присылает объект, в котором `qty` указан дважды: сначала 48, потом 50. Python оставит 50, другая библиотека может оставить 48 или выбросить ошибку. RFC 8259 называет поведение непредсказуемым. Если сумма в накладной не сходится, причиной может быть не арифметика, а дубль ключа, который никто не заметил.

| Случай | Что сломалось | Что показывает |
|---|---|---|
| Формула в CSV | текст из внешнего источника стал формулой | выгрузка это граница безопасности |
| BOM в JSON | невидимый символ в начале документа | кодировка входит в договор обмена |
| Дубль ключа | парсеры выбрали разные значения | уникальность ключей проверяют явно |

## Как выбрать формат и зафиксировать договор

Выбор формата сводится к трём вопросам. Есть ли вложенность? Кто будет открывать файл? Какие типы нужно сохранить?

| Задача | Формат | Причина |
|---|---|---|
| Ответ API с накладной и строками | JSON | вложенность и типы |
| Справочник товаров для Excel | CSV | плоская таблица, открывается напрямую |
| Обмен с бухгалтерией | CSV | привычный инструмент и простая сверка |
| Конфигурация приложения | JSON | структура и явные типы |
| Выгрузка 4800 позиций для сверки | CSV | компактность и построчная обработка |
| Журнал событий для другой системы | JSON Lines | по одному объекту на строку |

Если данные нужны и человеку, и программе, делают две выгрузки из одного источника. Это лучше, чем один файл, который каждая сторона трактует по-своему.

Договор обмена удобно оформить коротким списком. В нём указывают кодировку, разделитель, десятичный разделитель, формат даты, наличие заголовка, правило для пустых значений, способ экранирования кавычек, максимальный размер файла и версию схемы. Для CSV добавляют строку о том, что делать с BOM, а для JSON о том, какие поля обязательны.

Пример договора для файла остатков.

```text
Файл: stock.csv
Кодировка: UTF-8 с BOM
Разделитель: точка с запятой
Заголовок: обязателен, первая строка
Десятичный разделитель: запятая
Дата: ДД.ММ.ГГГГ
Пустое количество: 0
Пустая цена: ошибка импорта
Артикул: строка, ведущие нули сохраняются
Опасные начала ячеек: апостроф при выгрузке
Версия схемы: 2
```

Такой договор занимает полстраницы, но снимает большинство споров при импорте. Если поставщик меняет формат, он меняет версию схемы, и программа может отклонить незнакомый файл с понятным сообщением, а не испортить данные.

В договоре стоит указать и предел размера. Файл на 4800 строк и файл на десять миллионов строк требуют разной обработки: первый можно прочитать целиком, второй только потоком. Если предел не задан, поставщик однажды пришлёт выгрузку, которая положит процесс, а принимающая сторона будет выяснять, кто виноват. Предел превращает этот спор в заранее известное правило.

Для JSON договор дополняют ссылкой на схему и правилом для чисел. Например: целые до 2 в 53-й степени, деньги в виде строки с двумя знаками или числа с `Decimal`, даты в ISO 8601, дубли ключей запрещены, BOM запрещён. Эти пункты выглядят техническими, но именно они отделяют обмен, который работает годами, от обмена, который ломается при первом нестандартном поставщике.

### Как проверять обмен

Обмен проверяют на наборе небольших файлов, каждый из которых представляет один риск. Минимальный корректный документ доказывает, что разбор вообще работает. Документ без обязательного поля проверяет сообщение об ошибке. Документ с числом в кавычках проверяет, что тип не подменяется молча. Документ с дублем ключа проверяет решение из договора. Отдельные файлы нужны для BOM, переводов строк CRLF, точки с запятой внутри кавычек и неверной кодировки.

Сравнивать результаты лучше по разобранным данным, а не по байтам файла. Байтовое сравнение ломается от порядка ключей и отступов, хотя данные те же. Если договор фиксирует точный формат, например для подписи или контрольной суммы, байтовое сравнение как раз уместно. В остальных случаях сравнивают объекты: номер накладной, список строк, количество и сумму.

Проверять стоит и сообщения об ошибке. Хорошее сообщение называет поле и позицию: `items[2].qty`, строка 17, столбец `price`. Если тест ожидает только слово «ошибка», он пропустит регрессию, после которой пользователь снова не поймёт, что исправлять. Для внешнего API полезно проверить, что внутренние имена таблиц и пути не попадают в ответ. Это одновременно тест качества и тест безопасности.

## Типичные ошибки

**Лишний символ в имени столбца.** Симптом: `KeyError: 'sku'`, хотя столбец есть. Причина: BOM в начале файла, чтение с `encoding="utf-8"`. Лечение: `utf-8-sig`.

**Пустые строки при записи.** Симптом: между строками CSV появился пустой ряд. Причина: открытие файла без `newline=""` на Windows. Лечение: добавить параметр и перезаписать файл.

**Цена не преобразуется.** Симптом: `ValueError: could not convert string to float: '312,50'`. Причина: десятичная запятая. Лечение: заменить запятую или разбирать с учётом локали, для денег использовать `Decimal`.

**Дата читается неверно.** Симптом: месяц и день поменялись местами. Причина: формат `%d.%m.%Y` и `%m.%d.%Y` похожи, а даты вроде `05.10.2026` и `10.05.2026` обе допустимы. Лечение: фиксировать формат в договоре и проверять диапазон.

**JSON не разбирается.** Симптом: `json.decoder.JSONDecodeError` с указанием позиции. Частые причины: комментарий `//`, лишняя запятая после последнего элемента, одинарные кавычки вместо двойных, `NaN` вместо числа. JSON не допускает ничего из этого.

**Дубли ключей.** Симптом: значение поля не то, что ожидалось. Причина: в объекте два одинаковых ключа, парсер оставил последний. Спецификация не запрещает дубли, но и не определяет, какой ключ главный. Лечение: проверять документ на дубли до разбора.

**Файл не помещается в память.** Симптом: программа падает или начинает использовать гигабайты. Причина: `json.load` читает весь документ целиком. Лечение: потоковый разбор для больших файлов или разбиение выгрузки на части.

**Опасная формула в CSV.** Симптом: Excel выполняет содержимое ячейки. Причина: значение начинается с `=`, `+`, `-` или `@`. Лечение: экранировать такие значения при выгрузке и не открывать чужие CSV без проверки.

**Не тот разделитель.** Симптом: весь файл попал в один столбец. Причина: ожидалась запятая, а файл сохранён с точкой с запятой. Лечение: определять разделитель по заголовку и фиксировать его в договоре.

**Слишком большое целое.** Симптом: идентификатор в базе не совпадает с исходным. Причина: число больше 2 в 53-й степени прошло через `float` или `double`. Лечение: хранить идентификатор строкой.

**`NaN` в JSON.** Симптом: файл читается Python, но не читается другой системой. Причина: `json.dumps` по умолчанию разрешает `NaN` и `Infinity`. Лечение: `allow_nan=False` и проверка данных до записи.

| Ошибка | Симптом | Лечение |
|---|---|---|
| BOM в заголовке | `KeyError` по имени столбца | `utf-8-sig` |
| нет `newline` | пустые строки CSV | `newline=""` |
| десятичная запятая | `ValueError` при разборе цены | заменить запятую, `Decimal` |
| дубль ключа | разные значения у сторон | проверка пар ключей |
| формула в ячейке | Excel выполняет текст | экранировать начало поля |
| большое целое | идентификатор искажён | хранить строкой |

## Итоги

- JSON хранит дерево и различает число, строку, логическое значение и `null`, поэтому вложенные документы описываются естественно.
- CSV хранит плоскую таблицу, где все ячейки строки, а типы восстанавливает программа.
- Потеря типов проявляется в количестве, цене, дате, артикуле и логическом признаке, и каждое поле требует своего правила.
- BOM, десятичная запятая и `newline=""` это три причины большинства ошибок при работе с CSV на Windows.
- JSON не гарантирует уникальность ключей, точность больших чисел и наличие обязательных полей, поэтому документ проверяют по схеме.
- Формат выбирают по структуре данных и по тому, кто будет файл открывать, а не по привычке.
- Договор обмена фиксирует кодировку, разделитель, формат даты, правило для пустых значений и защиту от формул.
