## Ветка, которая потеряла скидку

В четверг два разработчика получили задачи по одному файлу `pricing.py`. Первый поднял скидку с 5 до 10 процентов, второй изменил ту же строку до 7. Оба отправили изменения в общий репозиторий. Первый слил свою ветку без замечаний, второй получил конфликт и решил его быстро: оставил свою строку, удалил чужую и нажал «завершить слияние».

Через день отдел продаж обнаружил, что скидка снова 7 процентов. Задача первого разработчика была закрыта, тесты проходили, история выглядела нормально. Пропала не строка кода, а результат работы человека. Восстановили его только по переписке и старой ветке.

**Ветка это отдельная линия работы, которая позволяет менять код, не затрагивая общую версию.** Слияние возвращает изменения в общую линию. Конфликт это место, где Git не может решить за людей, какую правку оставить. Если разрешать конфликт удалением чужой строки, Git не ошибётся: он сделает ровно то, что попросили, и потеряет работу.

Ветки нужны не для красоты истории. Они дают возможность проверить изменение до того, как оно попадёт к остальным, и вернуться к рабочей версии, если проверка не прошла. В проекте `sklad-plus` над кодом работают несколько человек, и без веток каждая незаконченная правка сразу оказывалась бы в общей версии.

Потерянная работа обходится дороже конфликта. Конфликт занимает минуты и заканчивается понятным решением. Потерянный коммит обнаруживают через день, когда по нему уже отчитались перед заказчиком. Восстанавливать приходится по журналам, переписке и резервным копиям, а иногда и переписывать заново. Поэтому правила работы с ветками защищают не удобство разработчика, а результат команды.

У этой истории есть менее заметный слой. Второй разработчик не был злоумышленником. Он видел конфликт, видел две версии строки и принял решение «моя версия новее». В его картине мира скидка 7 процентов была последней согласованной. В картине мира первого разработчика последней была 10. Git не хранит картину мира: он хранит коммиты и их родителей. Поэтому вопрос «кто прав» решается не в момент конфликта, а в требованиях, в задаче и в разговоре. Инструмент лишь показывает, что два изменения встретились в одном месте.

Дальше разберём, как устроена история внутри, почему слияние иногда обходится без нового коммита, чем перебазирование отличается от слияния по последствиям и какие правила не дают общей ветке потерять чужую работу.

## Коммит, дерево и указатель

Чтобы уверенно работать с ветками, нужно представить четыре вещи: объект, коммит, ссылку и индекс. **Объект** это единица хранения внутри репозитория. Файл хранится как объект типа blob, каталог как объект типа tree, а коммит как объект, который ссылается на корневое дерево и на родителей. У каждого объекта есть имя, вычисленное из его содержимого. Поэтому одинаковое содержимое в двух местах репозитория хранится один раз, а любое изменение даёт новое имя.

**Коммит** это снимок всего проекта, а не только изменённых файлов. Внутри коммита лежат ссылка на дерево, имя автора, дата, сообщение и ссылки на родителей. Первый коммит родителей не имеет, обычный коммит имеет одного, коммит слияния двух и более. Цепочка родителей и образует историю, которую рисует `git log --graph`.

| Понятие | Что это | Что происходит при коммите |
|---|---|---|
| Объект | blob, tree, commit или tag внутри репозитория | создаются новые объекты |
| Коммит | снимок дерева и ссылка на родителя | появляется новый коммит |
| Ветка | подвижная ссылка на коммит | ссылка сдвигается на новый коммит |
| `HEAD` | ссылка на текущую ветку или коммит | остаётся на той же ветке |
| Индекс | подготовленные к коммиту изменения | очищается после коммита |
| Рабочий каталог | файлы на диске | не меняется сам по себе |

Имя объекта вычисляется хеш-функцией. Долгое время в Git использовался SHA-1, который даёт 40 шестнадцатеричных символов. В 2017 году исследователи показали практическую коллизию SHA-1 на двух разных PDF-файлах, после чего Git добавил защиту от подмены объектов и поддержку SHA-256 в новых репозиториях. Для повседневной работы важно другое: имя коммита зависит от содержимого, родителей, автора, даты и сообщения. Изменили сообщение, получили другое имя. Именно поэтому перебазирование, которое меняет родителя, всегда меняет имена коммитов.

**Ветка** это не копия проекта. Это файл в служебном каталоге `.git`, в котором записан хеш одного коммита, то есть примерно 41 байт. Когда вы делаете коммит в ветке `main`, Git создаёт новый коммит и переписывает файл ветки так, чтобы он указывал на новинку. Создание ветки поэтому почти ничего не стоит: это запись одного имени. Переключение ветки меняет файлы рабочего каталога под выбранный снимок, но второй проект на диске не появляется.

`HEAD` это отдельная ссылка, которая показывает, где вы находитесь. Обычно она указывает на ветку, а ветка на коммит. Если открыть `.git/HEAD`, можно увидеть строку вида `ref: refs/heads/main`. Когда `HEAD` указывает прямо на коммит, состояние называют отсоединённым. В нём удобно смотреть старую версию, но новые коммиты не принадлежат ветке и после переключения могут остаться без имени. Спасает журнал ссылок `git reflog`, который хранит перемещения `HEAD` и веток.

**Индекс** это третий слой между рабочим каталогом и историей. Он хранит не файлы, а снимок того, что войдёт в следующий коммит. Поэтому `git add` важен отдельно от `git commit`: можно изменить десять файлов, добавить в индекс два и закоммитить только их. При конфликте индекс временно хранит три версии файла: общую, свою и чужую. Эти версии называют стадиями, и по ним Git понимает, что именно не сходится.

```text
git status
git log --oneline --graph --all
git reflog
```

`git status` показывает ветку, изменения и конфликты. `git log` показывает историю, флаг `--graph` рисует ветвление, `--oneline` сокращает запись, `--all` добавляет все ветки. `git reflog` показывает, куда перемещались указатели, и часто это единственный способ найти коммит, потерянный после неудачного перебазирования.

::figure git-graph | Граф из пяти коммитов: общий предок, две ветки, коммит слияния и подписи ссылок. Нажмите на коммит, чтобы увидеть его родителей и объяснение. Сравните положение `main`, `feature/discount` и `HEAD`.

История в Git не является одной прямой линией. Каждый коммит знает своего родителя, а ветки это ярлыки на разные концы цепочки. Слияние создаёт коммит с двумя родителями, поэтому граф разветвляется и сходится. Понимание графа избавляет от страха перед конфликтами: конфликт это не поломка, а развилка, которую нужно свести вручную.

Отсоединённый указатель полезен и опасен одновременно. Полезен, потому что позволяет проверить старую версию, не трогая ветки. Опасен, потому что человек может сделать несколько коммитов, переключиться на `main` и решить, что работа пропала. На самом деле коммиты живы, пока на них ссылается `HEAD`, ветка, тег или журнал ссылок. `git switch -c experiment` из отсоединённого состояния даёт этим коммитам имя и снимает риск.

Отдельно стоит запомнить, что тег это тоже ссылка, но обычно неподвижная. Лёгкий тег просто указывает на коммит, аннотированный хранит автора, дату и сообщение. Тегом отмечают релиз, потому что номер версии должен указывать на конкретный снимок, а не на «примерно ту неделю».

Сообщение коммита это часть интерфейса истории. Через месяц по нему ищут причину изменения, а не пересказ файлов. В командах часто принимают соглашение **Conventional Commits**: тип изменения (`feat`, `fix`, `docs`, `refactor`, `test`), необязательная область и краткое описание в повелительном наклонении. Например, `fix(stock): учитывать резерв при проверке остатка` говорит и что изменилось, и где. Соглашение описано на отдельном сайте [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/). Оно не заменяет содержательное сообщение, но делает историю предсказуемой и позволяет автоматически собирать список изменений релиза.

## Слияние: три версии и один коммит

Слияние вливает изменения одной ветки в другую. Git не сравнивает два файла целиком и не выбирает «более новый». Он находит **общий предок** двух веток, то есть последний коммит, который был в обеих историях. Этот предок называется базой слияния. Затем Git сравнивает с ним каждую сторону и применяет изменения, которые не пересекаются.

Такое сравнение называют трёхсторонним: база, ваша версия, их версия. Если в базе строка была `DISCOUNT = 5`, у вас стала `DISCOUNT = 10`, а у коллеги `DISCOUNT = 7`, обе стороны изменили одно место по-разному. Git не знает, какое значение правильное, и оставляет конфликт. Если же вы изменили скидку, а коллега добавил функцию в другой конец файла, изменения не пересекаются и Git применяет оба.

| Ситуация | Что сделает `git merge` |
|---|---|
| целевая ветка не менялась после отделения | fast-forward, новый коммит не нужен |
| обе ветки менялись, файлы не пересекаются | коммит слияния без конфликта |
| обе ветки изменили одну строку | конфликт, нужна ручная правка |
| одна ветка переименовала файл, другая изменила его | Git попробует связать переименование, иначе конфликт |
| целевая ветка уже содержит рабочую | сообщение «Already up to date» |

Если целевая ветка не получала новых коммитов с момента создания рабочей, Git может просто передвинуть указатель вперёд. Это называют **fast-forward**, то есть перемоткой. Нового коммита не появляется, история остаётся линейной, а факт слияния в ней не виден.

```text
git switch main
git merge feature/report
```

```text
Updating cbc67fe..4ac50e2
Fast-forward
 report.py | 4 ++++
 1 file changed, 4 insertions(+)
 create mode 100644 report.py
```

Коммит слияния нужен, когда обе ветки разошлись. У него два родителя, и он фиксирует точку, где работа отделилась и вернулась. Именно в этом коммите разрешается конфликт, если он был.

```text
git log --graph --oneline --all
```

```text
*   5773655 Свести скидку к согласованному значению
|\
| * 0fa9a5f Поднять скидку до 10 процентов
* | 6eeb16b Установить скидку 7 процентов
|/
* 2867907 Добавить расчёт стоимости со скидкой
```

Читать граф нужно сверху вниз: верхний коммит самый новый, ниже его родители. Символы `|\` и `|/` показывают, где ветка отделилась и где соединилась. Коммит `5773655` имеет двух родителей: `0fa9a5f` из рабочей ветки и `6eeb16b` из `main`. Хэши в вашем репозитории будут другими: они зависят от содержимого, автора и времени коммита.

Иногда команда хочет сохранить коммит слияния даже при возможности fast-forward. Тогда используют `git merge --no-ff имя`. Это делает историю чуть длиннее, но оставляет видимую границу задачи. Обратный выбор, `--ff-only`, запрещает создавать коммит слияния и завершается ошибкой, если перемотка невозможна. Это полезная защита от неожиданной развилки.

Есть и третий вариант, `git merge --squash`. Он собирает все изменения ветки в один набор и кладёт его в индекс, но коммит слияния не создаёт и связь с веткой не сохраняет. Так делают, когда хотят один аккуратный коммит вместо десяти черновых. Цена в том, что Git больше не знает, что ветка уже влита: повторное слияние может снова принести те же изменения. Поэтому squash применяют осознанно, а не как замену обычному слиянию.

Слияние не проверяет код и не запускает тесты. Оно только соединяет истории. Если в ветке был дефект, после слияния он окажется в главной ветке. Поэтому перед слиянием прогоняют тесты на рабочей ветке, а после слияния повторяют их на главной: объединение двух правильных изменений иногда даёт неправильный результат. Классический пример: одна ветка переименовала функцию, другая добавила её вызов. По отдельности обе ветки работают, вместе получается ошибка.

Перед слиянием полезно посмотреть, что именно придёт из ветки:

```text
git log main..feature/discount --oneline
git diff main...feature/discount --stat
```

Первая команда показывает коммиты, которых нет в `main`. Вторая показывает файлы и число изменённых строк относительно общего предка. Три точки здесь означают сравнение с базой слияния, а не с текущим концом `main`. Это дешевле, чем сливать вслепую и разбираться потом.

### Конфликт и его разрешение

Конфликт возникает, когда обе ветки изменили одну и ту же строку, удалили файл, который другая ветка правила, или по-разному переименовали один путь. Git останавливает слияние и оставляет в файле маркеры.

```text
git merge feature/discount
```

```text
Auto-merging pricing.py
CONFLICT (content): Merge conflict in pricing.py
Automatic merge failed; fix conflicts and then commit the result.
```

```text
git status --short
```

```text
UU pricing.py
```

Две буквы `U` означают, что файл изменён обеими сторонами и конфликт ещё не разрешён. Другие сочетания, например `AA` или `DU`, говорят о добавлении или удалении с двух сторон. Внутри файла Git оставляет обе версии:

```text
<<<<<<< HEAD
DISCOUNT = 7
=======
DISCOUNT = 10
>>>>>>> feature/discount
```

Верхняя часть относится к текущей ветке, в которую сливают, нижняя к вливаемой. Разрешение конфликта это не выбор одной из строк наугад, а решение, какое поведение должно остаться. В примере отдел продаж согласовал 10 процентов, поэтому правильная строка одна, а не обе.

```text
DISCOUNT = 10  # согласовано с отделом продаж
```

После правки файл сохраняют, добавляют в индекс и завершают слияние:

```text
git add pricing.py
git commit -m "Свести скидку к согласованному значению"
```

`git add` сообщает Git, что конфликт в этом файле разрешён. `git commit` создаёт коммит слияния. Если в процессе поняли, что слияние начали зря, его отменяют командой `git merge --abort`: рабочее состояние вернётся к тому, что было до слияния.

| Шаг | Команда | Что проверяют |
|---|---|---|
| 1 | `git status` | какие файлы конфликтуют |
| 2 | открыть файл | обе версии и маркеры |
| 3 | исправить | итоговое поведение, а не механический выбор |
| 4 | `git add файл` | конфликт отмечен разрешённым |
| 5 | `git commit` | сообщение объясняет решение |
| 6 | прогнать тесты | слияние не сломало поведение |

Конфликт может быть не только в одной строке. Если один разработчик переименовал файл, а другой изменил его содержимое, Git может предложить новое имя и спросить, что делать. Если один удалил функцию, а другой её вызывал, конфликт проявится как ошибка сборки уже после слияния. Поэтому после разрешения конфликта запускают тесты, а не только смотрят на исчезнувшие маркеры.

В спорной ситуации помогает разговор с автором второй ветки. Git показывает, кто и когда изменил строку, но не объясняет причину. Сообщение коммита и обсуждение задачи дают контекст: одно изменение могло быть временным обходом, а другое окончательным решением. Если договориться не удаётся, решение фиксируют в сообщении коммита слияния, чтобы через месяц было понятно, почему оставили именно эту версию.

Для повторяющихся конфликтов есть механизм `git rerere`, название которого расшифровывается как reuse recorded resolution. Git запоминает, как вы разрешили конфликт, и при следующей встрече тех же сторон предлагает готовое решение. Это полезно при длинной ветке, которую регулярно обновляют от главной: один и тот же конфликт не приходится разрешать заново. Но запоминание не отменяет проверку: автоматически применённое решение тоже нужно прочитать.

> [!PITFALL] «Моя версия правильная»
> Кнопка «оставить моё» или «оставить чужое» разрешает конфликт механически. Если вторая сторона добавила проверку или исправление, оно исчезнет. Перед выбором нужно прочитать обе версии и понять, зачем каждая появилась.

::gate Почему перебазирование меняет хэши коммитов и когда это допустимо?

## Перебазирование и цена линейной истории

Перебазирование берёт коммиты рабочей ветки и заново применяет их поверх другой ветки. История становится линейной, как будто работу начали позже. Хэши коммитов меняются, потому что у них появляется другой родитель, а имя коммита зависит от родителя.

```text
git switch feature/report
git rebase main
```

```text
Successfully rebased and updated refs/heads/feature/report.
```

После перебазирования граф выглядит так:

```text
* 4ac50e2 Добавить строку отчёта по остаткам
* cbc67fe Описать запуск проекта
*   5773655 Свести скидку к согласованному значению
|\
| * 0fa9a5f Поднять скидку до 10 процентов
* | 6eeb16b Установить скидку 7 процентов
|/
* 2867907 Добавить расчёт стоимости со скидкой
```

Коммит `4ac50e2` стоит прямо над `cbc67fe`, без боковой ветки. Читать такую историю проще: изменения идут друг за другом. Но у перебазирования есть цена: если ветку уже отправили в общий репозиторий и коллеги на неё опираются, их история разойдётся с новой. Поэтому перебазируют только личные ветки, которые ещё не стали общими.

Внутри перебазирование работает не как слияние. Git не создаёт один общий коммит, а по очереди применяет каждый коммит ветки к новой базе. Если конфликт возникает на втором коммите, его разрешают, добавляют файл в индекс и выполняют `git rebase --continue`. Потом Git применяет третий коммит, и конфликт может повториться. Отсюда практическое следствие: при перебазировании конфликты решаются несколько раз, при слиянии один раз.

```text
git add pricing.py
git rebase --continue
```

Если стало сложно, перебазирование отменяют командой `git rebase --abort`. Прерывать и продолжать можно несколько раз, пока все коммиты не перенесутся. Если конфликт уже разрешён, но вы не хотите продолжать, `git rebase --skip` пропускает текущий коммит. Пропуск это опасная операция: вместе с коммитом исчезнет и его изменение, поэтому применять её стоит только к явно лишнему коммиту.

| Признак | Слияние | Перебазирование |
|---|---|---|
| История | сохраняет ветвление и коммит слияния | делает линию линейной |
| Хэши коммитов | не меняются | меняются |
| Конфликты | решаются один раз при слиянии | могут повторяться на каждом коммите |
| Общая ветка | безопасно | опасно, если ветку уже используют |
| Читаемость | видно, где была задача | выглядит как последовательная работа |
| Восстановление | проще, история не переписана | нужен `reflog`, если что-то пошло не так |

::figure merge-rebase | Два варианта одной и той же работы: слияние с коммитом-развилкой и перебазирование в линию. Переключите режим кнопкой и посмотрите, что происходит с хэшами, общими ветками и конфликтами.

Есть правило, которое стоит запомнить: **перебазируют то, что ещё не отправили другим, сливают то, что уже общее.** Если ветка существует только на вашей машине, перебазирование безопасно. Если её уже скачали коллеги, перебазирование перепишет историю и создаст им лишнюю работу.

В повседневной работе перебазирование часто применяют при получении чужих изменений: `git pull --rebase` переносит ваши локальные коммиты поверх свежей главной ветки. Это избавляет от лишнего коммита слияния в личной работе. Но если в локальной ветке уже есть общие коммиты, лучше использовать обычный `git pull` с слиянием, чтобы не менять историю, которую видят другие.

Интерактивное перебазирование `git rebase -i` позволяет привести черновую ветку в порядок до отправки. В открывшемся списке коммитов можно оставить коммит как есть, переименовать сообщение, объединить несколько коммитов в один или удалить лишний. Это удобно, когда в ветке остались коммиты «поправил опечатку» и «ещё раз поправил». Но переписывать можно только личную ветку: после отправки коллегам такой список превращается в изменение общей истории.

Флаг `--onto` переносит не всю ветку, а выбранный диапазон коммитов на другую базу. Он нужен, когда ветку случайно создали от чужой рабочей ветки, а не от `main`. Вместо ручного копирования коммитов достаточно указать, что переносить и куда. Синтаксис легко перепутать, поэтому перед выполнением смотрят `git log --oneline --graph` и проверяют диапазон.

У перебазирования есть ещё один компромисс. Линейная история выглядит аккуратно, но скрывает, что задача разрабатывалась параллельно с другими. Коммит слияния, наоборот, показывает реальную развилку и точку интеграции. Для небольшой команды и коротких веток разница невелика. Для большой истории с релизными ветками коммиты слияния помогают восстановить, когда именно изменение попало в основную линию.

Поэтому спор «merge или rebase» не имеет одного правильного ответа. Правило, которое работает в учебном проекте, звучит так: личную ветку можно перебазировать до отправки, общую ветку сливают. Внутри команды это правило фиксируют в документе, чтобы каждый новый участник не выяснял его в первом конфликте.

::/gate

::gate Что происходит, когда двое отправили изменения в одну ветку?

## Удалённый репозиторий и общая ветка

Удалённый репозиторий хранит общую копию истории. Локальная ветка и её удалённая копия это два указателя, которые синхронизируют командами `git push` и `git pull`. `push` отправляет ваши коммиты на сервер, `pull` забирает чужие и сливает их с вашими. Если сервер отклонил отправку, значит, на нём появились новые коммиты: сначала забирают их, затем повторяют отправку.

| Команда | Направление | Что делает |
|---|---|---|
| `git push` | от вас на сервер | отправляет коммиты ветки |
| `git pull` | с сервера к вам | забирает и сливает изменения |
| `git fetch` | с сервера к вам | забирает, но не сливает |
| `git push -u origin ветка` | от вас на сервер | связывает ветки при первой отправке |

`git fetch` полезен, когда нужно посмотреть чужие изменения до слияния. Он обновляет удалённые ветки, но не трогает рабочий каталог. После него можно сравнить свою ветку с серверной и решить, сливать сразу или сначала разобраться. `git pull` делает то же самое и сразу добавляет слияние или перебазирование, поэтому в незнакомой ситуации безопаснее начать с `fetch`.

Важно понимать, что `origin/main` это не ветка на сервере в момент просмотра, а локальная запись о том, где сервер был в последний раз. Пока вы не выполнили `fetch`, эта запись устаревает. Отсюда странные ситуации: «на сервере уже исправили, а у меня старое». Исправили, но локальная копия знаний о сервере ещё не обновилась.

Запрос на слияние это не формальность. В нём видно, какие файлы изменились, кто автор и какие проверки прошли. Рецензент читает diff и оставляет замечания до слияния, а не после. Если в проекте нет отдельного рецензента, роль проверяющего берёт второй разработчик или преподаватель, но проверка всё равно должна быть.

Главную ветку защищают настройками репозитория: запрещают прямую отправку и требуют пройти проверку. Тогда даже опытный разработчик не сможет случайно отправить незаконченную правку. Защита не заменяет дисциплину, но делает ошибку заметной до того, как она попадёт к остальным. Дополнительно можно потребовать рецензию от владельца участка кода и запретить слияние, пока не закрыты блокирующие замечания.

| Ветка | Назначение | Время жизни | Кто сливает |
|---|---|---|---|
| `main` | рабочая версия проекта | постоянно | ответственный за слияние |
| `feature/...` | новая функция | до завершения задачи | автор после проверки |
| `fix/...` | исправление дефекта | до проверки | автор после проверки |
| `docs/...` | документация | до слияния | автор |
| `release/...` | подготовка версии | до выпуска | ответственный за релиз |

Для `sklad-plus` достаточно трёх уровней: главная ветка, рабочие ветки задач и короткие ветки исправлений. Главная ветка всегда должна собираться и проходить тесты. Рабочая ветка живёт до слияния задачи. Ветка исправления создаётся от главной и возвращается в неё после проверки. Релизная ветка нужна, только если версию готовят отдельно и в неё больше не попадают новые функции.

Рабочий цикл выглядит так. Сначала забирают свежую главную ветку, затем создают рабочую, делают коммиты, отправляют ветку в общий репозиторий, открывают запрос на слияние, проходят проверку и только потом сливают. После слияния рабочую ветку удаляют, чтобы не плодить устаревшие указатели.

```text
git switch main
git pull
git switch -c feature/stock-report
git push -u origin feature/stock-report
```

Флаг `-u` связывает локальную ветку с удалённой, чтобы следующие `git push` и `git pull` работали без указания имени. После этого в интерфейсе репозитория можно открыть запрос на слияние и попросить рецензию.

::figure branch-flow | Схема ветвления учебного проекта: главная ветка, задача, исправление и релиз. Переключите сценарий, чтобы увидеть, от какой ветки создаётся следующая и где стоит защита.

Перед отправкой полезно проверить, что в коммит не попали лишние файлы. `git status` показывает неотслеживаемые файлы, `git diff --cached` показывает то, что уже подготовлено. Если в списке оказались база, журнал или файл с паролем, их убирают из индекса и добавляют шаблон в `.gitignore`.

| Проверка перед отправкой | Команда |
|---|---|
| текущая ветка и изменения | `git status` |
| что войдёт в коммит | `git diff --cached` |
| история ветки | `git log --oneline main..HEAD` |
| тесты | `python -m pytest` |
| отсутствие секретов | просмотр `git diff --cached` |

История и удалённый репозиторий решают разные задачи. История позволяет понять, кто и зачем менял код. Удалённый репозиторий позволяет обмениваться работой. Ни то, ни другое не является резервной копией по умолчанию: сервер может потерять данные, а локальная копия может быть уничтожена вместе с ноутбуком. Поэтому в проекте нужны и история, и регулярные копии, и проверка восстановления.

## Когда история спасает, а когда нет

Три случая показывают, что ветки и удалённый репозиторий это инструменты с ограничениями. В каждом случае проблема была не в команде `merge`, а в процессе вокруг неё.

### BitKeeper и появление Git

До 2005 года ядро Linux разрабатывалось с использованием проприетарной системы BitKeeper, которую её создатель разрешал использовать сообществу бесплатно. В 2005 году сотрудничество прекратилось, и бесплатная лицензия была отозвана. Сообщество осталось без инструмента, который выдерживал бы десятки тысяч файлов и постоянные слияния.

Линус Торвальдс начал писать замену в апреле 2005 года. Уже через несколько дней прототип мог хранить историю, а вскоре Git стал использоваться для слияния изменений самого ядра. История этого перехода описана в книге Pro Git [Pro Git, история Git](https://git-scm.com/book/en/v2/Getting-Started-A-Short-History-of-Git). Урок для темы: инструмент и принятый в команде процесс связаны. Когда инструмент исчезает, исчезает и возможность сливать работу привычным способом. Распределённая модель, в которой у каждого есть полная история, снижает зависимость от одного сервера, но не отменяет договорённостей о ветках.

### GitLab.com, 31 января 2017 года

В этот день инженер GitLab.com работал с репликой базы и по ошибке удалил каталог данных на основном сервере вместо вторичного. Было удалено около 300 ГБ данных. Восстановление заняло около 18 часов, а данные, созданные примерно за шесть часов, спасти не удалось. По оценке компании, пострадали около 5000 проектов, 5000 комментариев и 700 новых учётных записей.

Самое важное в отчёте: несколько механизмов резервного копирования не сработали одновременно. Ежедневный дамп базы не создавался из-за несовпадения версий `pg_dump` и сервера, а сообщения об ошибке не доходили. Снимки диска не были включены для серверов базы. Реплика использовалась для отказоустойчивости, а не для восстановления. Оставался снимок шестичасовой давности. При этом Git-репозитории не пострадали, потому что хранились отдельно от базы [GitLab, 2017](https://about.gitlab.com/blog/postmortem-of-database-outage-of-january-31/).

Урок для темы: удалённый репозиторий не становится резервной копией от того, что он удалённый. Если восстановление ни разу не проверяли, нельзя утверждать, что оно работает. Для учебного проекта это означает простое правило: перед сдачей работы убедитесь, что репозиторий существует не только на вашей машине, а архив сданной версии лежит отдельно.

### CVE-2024-32002: клонирование как выполнение чужого кода

В 2024 году в Git нашли уязвимость, которая позволяла выполнить код при клонировании специально подготовленного репозитория с подмодулями. На файловых системах, где имена не различают регистр, например в Windows и macOS, подмодуль мог подменить путь и записать hook в служебный каталог. При рекурсивном клонировании hook выполнялся до того, как пользователь открывал проект.

Уязвимость затронула версии до 2.45.1, 2.44.1, 2.43.4, 2.42.2, 2.41.1, 2.40.2 и 2.39.4. Исправление описано в базе уязвимостей [NVD, CVE-2024-32002](https://nvd.nist.gov/vuln/detail/CVE-2024-32002). Урок для темы: `git clone --recursive` по ссылке из письма или задачи это не безобидное чтение. Подмодули, hooks и настройки репозитория относятся к недоверенному вводу. Перед клонированием незнакомого проекта стоит понять, откуда он, а рекурсивные подмодули включать осознанно.

| Случай | Что сломалось | Вывод |
|---|---|---|
| BitKeeper, 2005 | исчез инструмент, а вместе с ним привычный процесс | история и процесс должны опираться на несколько механизмов |
| GitLab, 2017 | резервные копии не проверяли, реплика не заменяла восстановление | удалённый репозиторий не равен резервной копии |
| Git, 2024 | рекурсивное клонирование выполнило код из подмодуля | репозиторий и его настройки это недоверенный ввод |

::/gate

## Проверка перед слиянием и типичные ошибки

Слияние это точка, где работа одного человека становится работой всех. Поэтому проверка перед слиянием важнее скорости. Минимальный набор такой: ветка собрана, тесты проходят, diff прочитан, в нём нет секретов и случайных файлов, описание объясняет изменение.

| Что проверить | Зачем | Как |
|---|---|---|
| ветка создана от свежей главной | меньше конфликтов | `git log --oneline main..HEAD` |
| тесты проходят | изменение не ломает поведение | запуск набора тестов |
| diff прочитан целиком | автор видит свои случайные правки | `git diff main...HEAD` |
| нет секретов и мусора | данные не утекают в историю | `git diff --cached`, `.gitignore` |
| описание понятно | рецензент знает, что проверять | заголовок и описание запроса |

После слияния работу не заканчивают. Нужно удалить рабочую ветку, обновить локальную главную, прогнать тесты на объединённом коде и убедиться, что CI собрал именно тот коммит, который попал в `main`. Если после слияния обнаружен дефект, исправление делают отдельной веткой от свежей главной, а не правкой поверх старой.

**Коммиты прямо в главную ветку.** Несколько человек пишут в `main`, и незаконченная правка ломает сборку у всех. Симптом: тесты падают, хотя никто не завершал задачу. Лечение: работать в отдельной ветке и сливать только проверенное.

**Слияние без проверки.** Ветку сливают, не запустив тесты и не прочитав diff. Конфликт разрешён, маркеры удалены, но поведение сломано. Симптом: после слияния отчёт пустой. Лечение: прогон тестов до и после слияния.

**Разрешение конфликта удалением чужой строки.** Самая дорогая ошибка в примере с начала лекции. Симптом: задача закрыта, а изменение исчезло. Лечение: читать обе версии и фиксировать решение в сообщении коммита.

**Долгоживущая ветка.** Ветка живёт месяц и расходится с главной на сотни строк. Конфликты накапливаются, слияние превращается в отдельный проект. Симптом: «сначала надо ещё раз переписать всё». Лечение: небольшие задачи и регулярное обновление от главной ветки.

**Перебазирование общей ветки.** Автор перебазирует ветку, которую уже скачали коллеги, и меняет все хэши. Симптом: у коллег расходятся истории и появляются дубли коммитов. Лечение: перебазировать только личные ветки, общие сливать.

**Принудительная отправка без предупреждения.** `git push --force` затирает удалённую ветку. Если кто-то успел отправить свои коммиты, они пропадут. Симптом: «вчера мой коммит был, сегодня его нет». Лечение: не использовать силу на общих ветках, а если она действительно нужна, применять `--force-with-lease` и предупреждать команду.

**Забытый `.gitignore`.** В репозиторий попадают база, журнал, виртуальное окружение и файл с паролем. Симптом: репозиторий растёт, а секрет виден в истории. Лечение: настроить игнор до первого коммита, а секрет при попадании заменить и удалить из истории.

**Переключение с незакоммиченными изменениями.** Файлы переносятся в другую ветку или мешают переключению. Симптом: правка оказалась не там, где планировалась. Лечение: перед сменой ветки проверять `git status` и либо коммитить, либо временно откладывать изменения через `git stash`.

**Слияние ветки в саму себя.** Автор путает ветки и выполняет `git merge` на той же ветке, где стоит. Симптом: сообщение «Already up to date», а изменения не появились в главной. Лечение: перед слиянием проверить `git branch --show-current` и явно указать целевую ветку.

**Потеря коммита после перебазирования.** Автор отменяет перебазирование, не сохранив ветку, и не знает, где искать старые коммиты. Симптом: «всё пропало». Лечение: `git reflog` показывает перемещения указателя, по нему можно вернуться и создать ветку заново.

> [!KEY] Ветка это не копия проекта
> Ветка это указатель на коммит. Переключение меняет файлы в рабочем каталоге, но не создаёт второй проект. Поэтому ветки дешёвые, а коммиты общие для всего репозитория.

## Итоги

- Коммит это снимок проекта, ветка это указатель на коммит, `HEAD` показывает текущую позицию.
- Ветку создают под одну задачу и дают ей имя, по которому понятно назначение.
- Fast-forward просто передвигает указатель, слияние разошедшихся веток создаёт коммит с двумя родителями.
- Конфликт разрешают вручную: прочитать обе версии, выбрать поведение, добавить файл и завершить слияние.
- Перебазирование делает историю линейной, меняет хэши и подходит только для личных веток.
- Главная ветка всегда собирается и проходит тесты, а рабочая ветка живёт до слияния задачи.
- Удалённый репозиторий и резервная копия это разные вещи, а клонирование незнакомого проекта требует осторожности.

Q: Что такое ветка в Git?
+ Указатель на коммит, который двигается при новых коммитах
- Полная копия проекта на диске
- Файл с настройками репозитория
- Список изменённых строк
! Ветка это ярлык на коммит, а не отдельная копия файлов.

Q: Что делает команда `git switch -c feature/discount`?
+ Создаёт ветку `feature/discount` и переключается на неё
- Удаляет ветку `feature/discount`
- Сливает ветку в `main`
- Отправляет ветку в удалённый репозиторий
! Флаг `-c` означает создание новой ветки.

Q: Что такое fast-forward при слиянии?
+ Перемещение указателя целевой ветки без создания коммита слияния
- Принудительная отправка ветки в удалённый репозиторий
- Удаление всех коммитов рабочей ветки
- Разрешение конфликта выбором первой версии
! Перемотка возможна, когда целевая ветка не получала новых коммитов.

Q: Когда при слиянии возникает конфликт?
+ Когда обе ветки изменили одну и ту же строку или файл
- Когда в ветке больше одного коммита
- Когда ветка отправлена в удалённый репозиторий
- Когда в проекте есть файл `.gitignore`
! Git не может выбрать между двумя изменениями одного места.

Q: Почему перебазирование меняет хэши коммитов?
+ Потому что у коммитов появляется другой родитель
- Потому что Git удаляет сообщения коммитов
- Потому что меняется имя удалённого репозитория
- Потому что перебазирование создаёт новый тег
! Имя коммита зависит от содержимого и родителя, поэтому перенос на новую базу даёт новые имена.

Q: Что делает `git fetch`?
+ Забирает изменения с сервера, но не сливает их с рабочей веткой
- Сливает удалённую ветку в текущую
- Отправляет локальные коммиты на сервер
- Удаляет удалённые ветки
! Fetch обновляет сведения о сервере, а слияние выполняют отдельно.

Q: Что означает отклонённая отправка `git push`?
+ На сервере появились коммиты, которых нет локально
- Локальная ветка удалена
- В репозитории закончилось место
- Пользователь не имеет прав на чтение
! Сначала забирают чужие коммиты, затем повторяют отправку.

Q: Что произошло в GitLab.com в 2017 году?
+ Основной сервер базы потерял данные, а резервные копии не сработали
- Все Git-репозитории были удалены вместе с базой
- Компания потеряла лицензию на Git
- Ветки перестали сливаться из-за ошибки в Git
! Git-репозитории хранились отдельно, но данные базы восстановить полностью не удалось.

Q: Чем опасно рекурсивное клонирование незнакомого репозитория?
+ Подмодуль может выполнить код через hook при клонировании
- Клонирование всегда удаляет локальные ветки
- Git запрещает клонировать репозитории с подмодулями
- После клонирования нельзя сделать коммит
! Уязвимость CVE-2024-32002 показала, что подмодули и hooks относятся к недоверенному вводу.

Q: Какие команды создают новую ветку?
+ `git branch feature/report`
+ `git switch -c feature/report`
+ `git checkout -b feature/report`
- `git merge feature/report`
- `git push feature/report`
! Все три команды создают ветку, но переключаются на неё не все.

Q: Какие правила защищают общую ветку?
+ Работать в отдельной ветке под задачу
+ Запускать тесты перед слиянием
+ Читать обе стороны конфликта
- Коммитить напрямую в `main` без проверки
- Разрешать конфликт удалением чужой строки
! Ветка, тесты и внимательное разрешение конфликта сохраняют чужую работу.

Q: Что проверяют перед отправкой ветки в общий репозиторий?
+ Что в diff нет секретов и случайных файлов
+ Что тесты проходят на рабочей ветке
+ Что описание объясняет цель изменения
- Что в ветке как можно больше коммитов
- Что история переписана после отправки
! Перед отправкой проверяют состав изменения, тесты и понятность описания.

Q: Как называется слияние, при котором указатель просто перемещается вперёд?
= fast-forward
= перемотка
! При перемотке новый коммит слияния не создаётся.

Q: Как называется перенос коммитов ветки на новую базу?
= rebase
= перебазирование
! Перебазирование применяет коммиты заново поверх другой ветки.

Q: Какая команда показывает состояние рабочего каталога и индекс?
= git status
= status
! `git status` показывает ветку, изменения и конфликты.
