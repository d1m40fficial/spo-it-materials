## Отчёт, в котором 480 012 коробок

Менеджер «Северного склада» выгружает остатки и видит странное число: 480 012 коробок вместо 4 812. Ошибка появилась после того, как к количеству из файла прибавили двенадцать коробок, поступивших утром. В файле количество хранилось текстом, и программа сложила текст с числом: `"4800" + 12` дала `"480012"`.

На Python тот же код упал бы с ошибкой: строка и число не складываются. В C# операция прошла молча, потому что язык разрешает прибавить число к строке и получить строку. Оба языка что-то сделали с типами, но по разным правилам, и менеджер увидел результат этих правил, а не свой отчёт.

**Тип это договор о том, какие значения хранит переменная и какие операции с ними допустимы.** Пока договор соблюдается, программа считает. Как только значение одного типа попадает туда, где ожидали другой, результат зависит от языка: Python чаще останавливает программу, C# чаще молча приводит значение к нужному виду.

У этой истории есть второй слой. Даже если бы программа сложила числа правильно, она могла бы ошибиться в другом. Количество коробок помещается в целое, а цена с копейками в двоичной дроби может дать хвост. Ошибка типа видна сразу, ошибка точности накапливается месяцами. Поэтому разговор о типах начинается не с синтаксиса объявления, а с вопроса: что именно означает значение и какие операции с ним имеют смысл.

## Тип как договор

У типа три части. Первая это множество значений: целое число не может быть равно 4,75, а строка не может быть истиной. Вторая это набор операций: числа складывают, строки соединяют, логические значения объединяют через «и» и «или». Третья это способ хранения в памяти: целое занимает фиксированное число байт, строка хранится отдельно от переменной.

Из этих трёх частей следуют три практические функции типа. Тип **защищает** от бессмысленных операций: не даёт умножить название товара на цену. Тип **подсказывает** инструменту, как оптимизировать код и сколько памяти выделить. Тип **документирует** намерение: если функция принимает `decimal`, это сигнал, что речь о деньгах, а не об измерении объёма.

В Python тип привязан к значению, а не к имени. Переменная это ссылка на объект, и один и тот же объект несёт свой тип. Поэтому имя можно переприсвоить:

```python
value = 4800
value = "4800"
```

Вторая строка не ошибка: имя теперь указывает на строку. Тип проверяется в момент операции, когда программа до неё дошла.

В C# тип привязан к переменной и известен компилятору заранее:

```csharp
int value = 4800;
value = "4800";
```

Вторая строка не соберётся: компилятор сообщит `CS0029`, потому что переменная объявлена целой. Проверка происходит до запуска, и программа с такой ошибкой не попадёт к пользователю.

| Свойство | Python | C# |
|---|---|---|
| Когда известен тип | во время выполнения | при сборке |
| Где хранится | в объекте значения | в объявлении переменной |
| Можно ли сменить тип | да, переприсвоив имя | нет, только объявить новую |
| Когда видна ошибка | при выполнении операции | при компиляции |
| Объявление | `value = 4800` | `int value = 4800;` |

Динамическая типизация удобна для коротких скриптов и неудобна для больших программ: ошибку в имени или типе можно найти только на том пути, который выполнился. Статическая типизация требует больше букв, но проверяет все ветки сразу.

У динамической типизации есть смягчение, о котором стоит знать. В Python можно писать аннотации типов, описанные в PEP 484: `def available(positions: int, reserved: int) -> int:`. Интерпретатор их не проверяет и не мешает передать строку. Проверкой занимаются отдельные инструменты, например mypy или pyright. Аннотации полезны как документация и как раннее предупреждение, но они не превращают Python в статически типизированный язык.

У статической типизации тоже есть исключения. Ключевое слово `dynamic` в C# откладывает проверку до выполнения, а приведение через `object` может обойти часть проверок. Это инструменты для узких задач: взаимодействия с внешними библиотеками, динамических сценариев. В обычном коде проекта их избегают, потому что они возвращают ту самую ошибку, от которой защищает компилятор.

Есть ещё различие между значимыми и ссылочными типами. `int`, `double`, `bool` и `decimal` являются значимыми: значение хранится прямо в переменной или в поле объекта. `string` и классы являются ссылочными: переменная хранит ссылку на объект в куче. Для темы занятия важно одно следствие: значимый тип не может быть `null`, если он не объявлен как `int?`, а строка может быть `null`, если не включена проверка `Nullable`.

::figure type-contract | Сравните две модели: в Python тип принадлежит объекту, а имя можно переприсвоить; в C# тип записан в объявлении и проверяется при сборке. Обратите внимание, где появляется ошибка в каждом случае.

## Четыре семейства типов

Почти любое значение в учебном проекте относится к одному из четырёх семейств: целые числа, вещественные числа, строки и логические значения.

| Семейство | Python | C# | Пример из «Склад+» |
|---|---|---|---|
| Целые | `int` | `int`, `long`, `byte` | количество коробок, номер ячейки |
| Вещественные | `float`, `Decimal` | `double`, `decimal` | объём груза, цена |
| Строки | `str` | `string` | название товара, код накладной |
| Логические | `bool` | `bool` | признак переполнения ячейки |

В Python целое число не ограничено по размеру: `int` хранит сколько угодно цифр, пока хватает памяти. В C# у каждого целого типа есть жёсткий диапазон.

| Тип C# | Размер | Диапазон |
|---|---|---|
| `byte` | 1 байт | от 0 до 255 |
| `short` | 2 байта | от -32 768 до 32 767 |
| `int` | 4 байта | от -2 147 483 648 до 2 147 483 647 |
| `long` | 8 байт | от -9 223 372 036 854 775 808 до 9 223 372 036 854 775 807 |

Для количества коробок и номеров хватает `int`. Стоимость запаса из 4800 позиций по 129,90 рубля даёт 623 520 рублей, это 62 352 000 копеек, и такое число в `int` помещается. Годовой оборот склада больше, для него может понадобиться `long`.

Фиксированная ширина целых типов не случайна. Процессор работает с машинными словами, а библиотеки и форматы файлов ожидают конкретное число байт. Фиксированный размер позволяет заранее посчитать память, быстро выполнять арифметику и обмениваться данными с другими системами. Цена такой предсказуемости в том, что диапазон конечен. Если значение выходит за границу, программа должна это заметить. По умолчанию C# не проверяет каждую операцию, потому что проверка стоит времени, и выбирает быстрое, но опасное поведение.

Вещественные числа хранят дробную часть, но по-разному. `double` использует двоичное представление и жертвует точностью ради диапазона. `decimal` хранит десятичные цифры и подходит для денег. В Python обычный `float` это двойная точность, а для денег применяют модуль `decimal`.

Строка это последовательность символов. В обоих языках строка неизменяема: методы возвращают новую строку, а исходная остаётся прежней. Логический тип принимает два значения: истину и ложь.

У выбора семейства есть цена. Целые числа быстрые и точные, но ограничены диапазоном. Двоичные дроби быстрые и с огромным диапазоном, но не представляют десятичные копейки точно. Десятичные дроби точны для денег, но медленнее и имеют меньший диапазон. Строки универсальны, но любая арифметика требует разбора. Логический тип прост, но в Python он связан с целыми, а в C# требует явного сравнения.

## Объявление переменных

В Python переменная создаётся присваиванием. Имя пишут строчными буквами с подчёркиваниями:

```python
positions = 4800
volume_m3 = 3.852
category = "Электроинструмент"
is_full = volume_m3 > 3.5
```

В C# переменную объявляют с типом. Локальные имена пишут с маленькой буквы в стиле camelCase, типы и методы с большой:

```csharp
int positions = 4800;
double volumeM3 = 3.852;
string category = "Электроинструмент";
bool isFull = volumeM3 > 3.5;
```

Ключевое слово `var` позволяет не писать тип явно, но не отменяет его: компилятор выводит тип из правой части и дальше считает переменную этим типом.

```csharp
var positions = 4800;      // int
var volumeM3 = 3.852;      // double
```

Если позже присвоить переменной `positions` строку, компилятор всё равно ошибётся. `var` экономит буквы, но не делает язык динамическим. Это важно понимать при переводе кода с Python: замена `x = 1` на `var x = 1` не сохраняет свободу переприсваивания.

Константу объявляют словом `const`, и её значение должно быть известно при сборке:

```csharp
const double PalletVolumeM3 = 1.44;
```

В Python константу пишут заглавными буквами, но язык не запрещает её изменить. Это соглашение, а не правило, которое проверяет интерпретатор.

У переменных C# есть ещё одно отличие: локальная переменная должна быть присвоена до первого использования, иначе сборка остановится с ошибкой `CS0165`. Значения по умолчанию существуют у полей класса, но не у локальных переменных. Отдельно стоит помнить про `null`: строка может не содержать значения, и компилятор с включённой проверкой `Nullable` предупреждает, предлагая писать `string?`, если отсутствие значения допустимо. Для чисел используют `int?`:

```csharp
int? freeCells = null;
string? note = null;
```

В Python `None` может оказаться в любом имени без объявления, и ошибка проявится только при обращении к нему. В C# такой риск виден по типу и предупреждению компилятора.

У области видимости тоже есть различия. В Python переменная, созданная в функции, видна до конца функции, а переменная модуля видна всем функциям модуля. В C# локальная переменная видна только внутри блока, где объявлена. Поэтому одинаковое имя в двух ветках `if` может означать две разные переменные, и это не ошибка, а разные области видимости.

## Целые числа, деление и переполнение

Самая частая ошибка новичка связана с делением. В Python оператор `/` всегда возвращает вещественное число, а `//` отбрасывает дробную часть:

```python
print(7 / 2)
print(7 // 2)
```

```text
3.5
3
```

В C# оба операнда целые, поэтому `/` выполняет целочисленное деление:

```csharp
Console.WriteLine(7 / 2);
Console.WriteLine(7.0 / 2);
```

```text
3
3,5
```

Если нужен дробный результат, хотя бы один операнд должен быть вещественным. Запись `(double)boxes / perPallet` приводит к вещественному типу только числитель, и деление становится дробным. Остаток от деления даёт оператор `%`: 4817 коробок по 40 штук на паллету дают 120 полных паллет и 17 коробок в остатке.

Для положительных чисел разница между `/` и `//` незаметна. Для отрицательных она становится важной. В Python `-7 // 2` даёт `-4`, потому что деление с остатком округляет вниз, к меньшему целому. В C# `-7 / 2` даёт `-3`, потому что целочисленное деление отбрасывает дробную часть к нулю. Тот же оператор `%` тоже ведёт себя по-разному: в Python остаток имеет знак делителя, в C# знак делимого.

| Выражение | Python | C# |
|---|---|---|
| `7 / 2` | `3.5` | `3` |
| `7 // 2` | `3` | `3` |
| `-7 // 2` | `-4` | `-3` |
| `-7 % 2` | `1` | `-1` |
| `7.0 / 2` | `3.5` | `3.5` |

Эта таблица объясняет, почему перенос алгоритма с одного языка на другой требует не только замены синтаксиса. Если алгоритм разбивает позиции на паллеты и где-то появляется отрицательное значение, знак результата может измениться. Для количества остатков лучше использовать положительные значения или явно описать правило округления.

Переполнение в Python невозможно: число растёт, пока хватает памяти. В C# диапазон `int` конечен. По умолчанию арифметика не проверяется, и при выходе за границу значение переходит на противоположный конец диапазона:

```csharp
int max = int.MaxValue;
Console.WriteLine(max + 1);
```

```text
-2147483648
```

Причина в двоичном представлении. Целое хранится в дополнительном коде: старший бит означает знак, а сложение выполняется по модулю разрядной сетки. Когда к максимальному положительному числу прибавляется единица, все биты переходят в состояние, которое читается как минимальное отрицательное. Это не случайная порча памяти, а предсказуемое следствие ограниченной ширины.

Если такая ошибка недопустима, блок `checked` превращает переполнение в исключение `OverflowException`:

```csharp
checked
{
    int max = int.MaxValue;
    int next = max + 1;
}
```

Константное выражение `int.MaxValue + 1` компилятор отвергает сразу, а переменная проверяется только в момент выполнения. Поэтому одинаковое на вид выражение ведёт себя по-разному в зависимости от того, известно ли значение при сборке.

| Способ | Что происходит при выходе за диапазон | Когда выбирать |
|---|---|---|
| обычная арифметика | значение переходит через границу | счётчики, где переполнение невозможно |
| `checked` | исключение `OverflowException` | суммы, остатки, денежные расчёты |
| `long` | диапазон шире, но тоже конечен | большие суммы и счётчики |
| `BigInteger` | диапазон ограничен памятью | точные большие вычисления |

Для денег в копейках лучше сразу брать `long` или `decimal`, а не надеяться, что сумма не превысит два миллиарда. Годовой оборот склада из 4800 позиций может вырасти, и однажды обычный `int` молча перейдёт в отрицательное значение. Проверка `checked` в месте расчёта стоит недорого и превращает незаметную ошибку в понятное исключение.

::figure int-overflow | Выберите тип и нажмите «максимум плюс один»: схема покажет границу диапазона и переход значения на противоположный конец. Внизу отмечено, что меняет блок checked.

::/gate

## Вещественные числа и decimal

Двоичная дробь не может точно представить 0,1: в памяти это бесконечная дробь, обрезанная до 53 бит. Поэтому сумма двух десятых не равна трём десятым:

```python
print(0.1 + 0.2)
print(0.1 + 0.2 == 0.3)
```

```text
0.30000000000000004
False
```

В C# с типом `double` картина та же:

```csharp
double a = 0.1;
double b = 0.2;
Console.WriteLine(a + b == 0.3);
```

```text
False
```

Чтобы понять причину, полезно посмотреть на устройство числа. Стандарт [IEEE 754](https://standards.ieee.org/ieee/754/6210/) описывает двоичное число с плавающей точкой как три поля: знак, экспоненту и дробную часть. У `double` это 1 бит знака, 11 бит экспоненты и 52 бита дробной части. Вместе с неявной ведущей единицей точность составляет 53 бита, что даёт примерно 15-17 значащих десятичных цифр.

Число 0,1 в двоичной системе является периодической дробью, как 1/3 в десятичной. При сохранении она обрезается, и в памяти оказывается ближайшее представимое значение, немного большее или меньшее. Сложение двух таких приближений даёт результат, который не равен ближайшему представлению 0,3. Ошибка крошечная, но сравнение на равенство видит её сразу.

| Свойство | double | decimal |
|---|---|---|
| Основание | двоичное | десятичное |
| Точность | около 15-17 значащих цифр | 28-29 значащих цифр |
| Диапазон | примерно до 1,7 × 10 в 308 степени | примерно до 7,9 × 10 в 28 степени |
| Скорость | быстрее | медленнее |
| Для чего | измерения, графики, объёмы | деньги, тарифы, суммы |

Тип `decimal` хранит значение как целое с десятичным масштабом, поэтому десятые складываются точно:

```csharp
decimal a = 0.1m;
decimal b = 0.2m;
Console.WriteLine(a + b == 0.3m);
```

```text
True
```

Суффикс `m` обязателен: без него литерал считается `double`. В Python аналогичную роль играет `Decimal`:

```python
from decimal import Decimal

print(Decimal("0.1") + Decimal("0.2"))
```

```text
0.3
```

`Decimal` создают из строки, а не из `float`: `Decimal(0.1)` уже содержит двоичную ошибку, которую переносит в десятичное значение. Это одна из самых коварных ловушек: код выглядит правильным, а число внутри уже неточное.

Выбор между `double` и `decimal` зависит от того, что означает число. Объём груза 3,852 кубического метра измерен с точностью до тысячных, и ошибка в шестнадцатом знаке после запятой на результат не влияет. Цена и сумма копеек требуют точного десятичного представления, потому что расхождение в одну копейку видно в отчёте и вызывает вопросы. Поэтому объёмы считают в `double`, а деньги в `decimal`.

У `decimal` есть ограничения, о которых забывают. Диапазон меньше, чем у `double`, поэтому очень большие суммы могут не поместиться. Операции медленнее, потому что выполняются программно, а не аппаратно. При переполнении `decimal` выбрасывает `OverflowException` всегда, а не только в блоке `checked`. И `decimal` не хранит бесконечность и «не число»: для особых состояний нужен отдельный признак.

Округление тоже требует внимания. И Python, и C# по умолчанию округляют половину к чётному: 2,5 даёт 2, а 3,5 даёт 4. Это правило снижает накопление ошибки, но удивляет бухгалтера, который ждёт 2,5 → 3. Если нужен другой способ, его указывают явно: в Python через модуль `decimal` с режимом `ROUND_HALF_UP`, в C# через `MidpointRounding.AwayFromZero`.

```csharp
Console.WriteLine(Math.Round(2.5));
Console.WriteLine(Math.Round(2.5, MidpointRounding.AwayFromZero));
```

```text
2
3
```

Сравнивать вещественные числа на равенство почти всегда ошибка. Правильнее сравнивать разницу с допуском: `Math.Abs(a - b) < 0.000001`. Допуск выбирают по смыслу задачи, а не по принципу «чем меньше, тем лучше»: слишком маленький допуск снова поймает шум, слишком большой пропустит реальное расхождение.

У двоичных чисел есть ещё особые значения: положительная и отрицательная бесконечность, а также NaN, «не число». Они появляются при делении на ноль в вещественной арифметике и при недопустимых операциях. Сравнение с NaN всегда ложно, даже `NaN == NaN`, поэтому для проверки используют `double.IsNaN`. В `decimal` таких значений нет, и деление на ноль даёт исключение.

## Строки

Строка хранит текст и не меняется после создания. Метод `ToUpper` в C# и `upper` в Python возвращают новую строку, а исходная остаётся прежней:

```csharp
string code = "sklad-4800";
string upper = code.ToUpper();
Console.WriteLine(code);
Console.WriteLine(upper);
```

```text
sklad-4800
SKLAD-4800
```

Соединение строк выполняют оператором `+`, но в C# он же соединяет строку с любым другим значением. Именно поэтому `"4800" + 12` даёт `"480012"`, а не ошибку. Python так не делает и сообщает `TypeError`.

У такого поведения есть неочевидное следствие: порядок операндов не важен. `"4800" + 12` и `12 + "4800"` в C# дают строку, потому что перегрузка оператора выбирается по наличию строки. В Python оба варианта завершаются ошибкой. Это ещё один пример того, что одинаковое выражение может означать разное в двух языках.

Для вставки значений в текст удобнее интерполяция. В Python это `f`-строка, в C# строка с префиксом `$`:

```python
positions = 4800
print(f"Позиций: {positions}")
```

```csharp
int positions = 4800;
Console.WriteLine($"Позиций: {positions}");
```

Обе строки печатают одно и то же. Формат можно задать после двоеточия: `{volume:0.###}` оставляет до трёх знаков после запятой, `{price:0.00}` всегда показывает две цифры. В Python похожий результат даёт `f"{volume:.3f}"`, но там количество знаков фиксировано, а не максимально.

Главное различие строк глубже синтаксиса. В Python строка это последовательность кодовых точек Unicode, а в C# последовательность кодовых единиц UTF-16. Для латиницы и кириллицы разницы не видно, для эмодзи и редких символов она появляется.

```python
print(len("😀"))
print(len("é"))
print(len("e\u0301"))
```

```text
1
1
2
```

В C# `"😀".Length` равно 2, потому что символ занимает две кодовые единицы UTF-16, суррогатную пару. `"é".Length` равно 1, а `"e\u0301".Length` равно 2. Визуально две последние строки выглядят одинаково, но сравниваются как разные.

| Строка | Python `len` | C# `Length` | Причина |
|---|---|---|---|
| `"склад"` | 5 | 5 | по одной единице на символ |
| `"😀"` | 1 | 2 | суррогатная пара в UTF-16 |
| `"é"` | 1 | 1 | одна кодовая точка |
| `"e"` + combining acute | 2 | 2 | две кодовые точки |

Отсюда практическое правило: длина строки не равна числу видимых символов. Для ограничения поля ввода по количеству знаков нужно считать текстовые элементы, а не кодовые единицы. В .NET для этого есть `StringInfo`, в Python для сложных случаев используют библиотеки сегментации текста.

Вторая ловушка связана с нормализацией Unicode. Один и тот же символ можно записать одной кодовой точкой или базовой буквой с комбинирующим знаком. Стандарт Unicode описывает формы NFC и NFD, которые приводят запись к единому виду, а подробные правила собраны в [UAX 15](https://www.unicode.org/reports/tr15/). Если данные приходят из разных источников, одно и то же название товара может не совпасть при сравнении.

```python
import unicodedata

a = "é"
b = "e\u0301"
print(a == b)
print(unicodedata.normalize("NFC", a) == unicodedata.normalize("NFC", b))
```

```text
False
True
```

В C# аналогично работает `Normalize(NormalizationForm.FormC)`. Нормализацию выполняют на входе, когда данные попадают в систему, а не при каждом сравнении. Иначе одна и та же строка будет проходить разные проверки в разных местах.

Сравнение строк зависит от культуры. В C# оператор `==` сравнивает строки порядково, по кодовым единицам, а методы сортировки могут учитывать язык. Для идентификаторов, кодов и имён файлов нужен `StringComparison.Ordinal`, для отображения пользователю `CurrentCulture`; правила разобраны в документации [о сравнении строк](https://learn.microsoft.com/en-us/dotnet/standard/base-types/best-practices-strings). Если перепутать, программа на турецкой локали может не найти файл с буквой `i`, потому что правила регистра там другие.

Python сравнивает строки по кодовым точкам и не учитывает локаль неявно. Для регистронезависимого сравнения используют `casefold`, а для сортировки с учётом языка отдельные функции. Это проще предсказать, но требует явного решения там, где текст предназначен человеку.

## Логический тип

Логическое значение получается из сравнения: `volumeM3 > 3.5` даёт истину или ложь. В C# тип `bool` принимает только `true` и `false`, и число вместо него не подставишь:

```csharp
bool isFull = volumeM3 > 3.5;
Console.WriteLine(isFull);
```

```text
True
```

В Python `bool` это подвид целого: `True` равен 1, `False` равен 0, а `True + True` даёт 2. В C# такая арифметика не компилируется. Зато Python считает ложными пустую строку, ноль и пустой список, а C# требует явного сравнения:

```python
if volume_m3:
    print("Объём известен")
```

В C# аналогичная запись `if (volumeM3)` не соберётся, потому что `double` не преобразуется в `bool` неявно. Нужно написать `if (volumeM3 > 0)`. Явность защищает от ошибки, когда ноль означает допустимое значение, а не отсутствие данных.

У логических операторов тоже есть разница. В Python `and` и `or` возвращают не обязательно `bool`, а один из операндов: `0 or "склад"` даёт строку. В C# `&&` и `||` всегда дают `bool` и вычисляют второй операнд только при необходимости. Для проверки `if (user != null && user.IsActive)` это важно: второй операнд не будет вычислен, если первый ложен.

В C# есть nullable-логика: `bool?` может быть `true`, `false` или `null`. Операторы `&` и `|` для такого типа возвращают `null`, если результат неизвестен, а `== true` отсекает `null`. Это удобно для трёх состояний, но требует явного решения, что означает отсутствие ответа.

## Преобразование типов

Преобразование бывает неявным и явным. Неявное выполняет компилятор без подсказки, если преобразование разрешено языком: `int` помещается в `long` без потерь, а `long` преобразуется в `double` неявно, хотя очень большие значения при этом теряют точность. Явное пишет программист и берёт ответственность за потерю данных.

```csharp
int boxes = 4817;
long total = boxes;          // неявно, без потерь
double average = boxes / 3.0; // неявно при смешивании с double
int truncated = (int)3.9;     // явно, дробная часть отбрасывается
```

Приведение `(int)3.9` даёт 3, потому что дробная часть отбрасывается, а не округляется. Функция `Convert.ToInt32(3.9)` округляет по правилу половины к чётному и даёт 4. Эти два способа легко перепутать, и разница в единицу портит итог.

| Задача | Python | C# |
|---|---|---|
| Строка в целое | `int("4800")` | `int.Parse("4800")` |
| Безопасный разбор | `try` и `except ValueError` | `int.TryParse` |
| Дробное в целое | `int(3.9)` даёт 3 | `(int)3.9` даёт 3, `Convert.ToInt32(3.9)` даёт 4 |
| Число в строку | `str(4800)` | `4800.ToString()` |
| Целое в дробное | `float(4800)` | `(double)4800` |

Разбор строки может закончиться ошибкой. Пробел внутри числа, запятая вместо точки и лишний символ приводят к исключению:

```csharp
int count = int.Parse("4 800");
```

```text
FormatException
```

Проверить строку заранее позволяет `TryParse`. Он не выбрасывает исключение, а возвращает признак успеха и записывает результат в переменную:

```csharp
int count;
bool ok = int.TryParse("4 800", out count);
Console.WriteLine($"{ok} {count}");
```

```text
False 0
```

В Python аналог это `try` и `except`, потому что отдельной функции с признаком успеха для `int` нет. В учебном проекте `TryParse` пригодится при чтении количества из файла: одна плохая строка не должна останавливать весь импорт.

```python
raw = "4 800"
try:
    count = int(raw)
except ValueError:
    count = 0
```

Отдельная ловушка связана с культурой. На русской локали разделитель дробной части это запятая, поэтому `double.Parse("4.75")` завершится ошибкой, а `double.Parse("4,75")` вернёт 4,75. При обмене данными с внешними системами число всегда разбирают с явно указанной культурой или в инвариантном формате, иначе на другом компьютере тот же файл прочитается иначе.

```csharp
using System.Globalization;

double a = double.Parse("4.75", CultureInfo.InvariantCulture);
double b = double.Parse("4,75", new CultureInfo("ru-RU"));
```

Обратное преобразование, из числа в строку, подчиняется тем же правилам. Формат задают явно, а культуру указывают, если строка уходит в файл или в другую систему:

```csharp
using System.Globalization;

decimal price = 623520.00m;
Console.WriteLine(price.ToString("0.00", CultureInfo.InvariantCulture));
Console.WriteLine(price.ToString("0.00"));
```

```text
623520.00
623520,00
```

Первая строка одинакова на любой машине, вторая зависит от локали. В файлах обмена и в API используют первый вариант, а человекочитаемый отчёт может позволить себе второй.

Есть ещё одна ошибка, которая выглядит безобидно. В Python `bool("False")` равно `True`, потому что непустая строка истинна. В C# `bool.Parse("False")` даёт `false`, а `bool.Parse("0")` выбрасывает исключение. Если значение приходит из формы или файла, его нужно разбирать по правилам формата, а не полагаться на интуицию.

| Преобразование | Опасность | Правило |
|---|---|---|
| `long` в `int` | потеря старших разрядов | проверять диапазон |
| `double` в `int` | потеря дробной части | решить, нужно ли округление |
| `decimal` в `double` | потеря точности | не использовать для денег |
| строка в число | исключение или ноль | `TryParse` или `try` |
| число в строку | зависимость от локали | `InvariantCulture` для обмена |

## Реальные случаи: цена одного преобразования

### Ariane 5, полёт 501

4 июня 1996 года европейская ракета Ariane 5 стартовала с космодрома Куру и через 37 секунд после зажигания двигателей была разрушена. Ракета отклонилась от траектории, и система самоликвидации сработала по команде. На борту находились четыре научных спутника Cluster, они были потеряны.

Отчёт комиссии по расследованию под руководством ESA установил цепочку причин. В инерциальной системе навигации выполнялось преобразование 64-битного вещественного числа в 16-битное целое. Значение переменной, описывающей горизонтальную составляющую, вышло за диапазон 16-битного целого и вызвало ошибку операнда. Программа обработки не была защищена от этой ошибки, хотя соседние преобразования защиту имели.

Дальше сработала цепочка отказов. Основная и резервная инерциальные системы отказали с разницей в один цикл, 72 миллисекунды. Бортовой компьютер получил диагностический код, принял его за данные о положении и отклонил сопла. Комиссия отметила, что функция выравнивания платформы нужна только до старта, но продолжала работать примерно 40 секунд после отрыва. Кроме того, программное обеспечение и траектория были перенесены с Ariane 4, а новая ракета имела другие характеристики разгона.

Урок для темы занятия прямой: преобразование обязано проверять диапазон. Если значение приходит из внешнего источника или зависит от режима, который изменился, нельзя полагаться на то, что оно поместится. В C# для этого есть `checked`, `TryParse` и явная проверка границ; в Python целые не переполняются, но преобразование в ограниченный формат всё равно требует контроля.

### Patriot в Дахране

25 февраля 1991 года батарея Patriot в Дахране, Саудовская Аравия, не смогла перехватить баллистическую ракету. Погибли 28 военнослужащих, 98 получили ранения. Отчёт GAO, опубликованный в 1992 году, назвал причиной программную ошибку в расчёте времени.

Система обновляла внутренние часы каждые 0,1 секунды, но представляла время в 24-битном регистре с усечением. Каждое обновление теряло около 0,000000095 секунды. Ошибка казалась ничтожной, однако батарея работала непрерывно более 100 часов. За это время расхождение накопилось примерно до 0,34 секунды, а положение стробирующего импульса сместилось примерно на 687 метров. Цель оказалась вне ожидаемого окна, и перехват не состоялся.

Здесь важны два механизма. Первый: двоичное представление 0,1 неточно, и усечение при каждом шаге добавляет маленькую ошибку. Второй: ошибка накапливается, потому что система работает долго без перезапуска. Для темы типов это пример того, что `double` и `float` не предназначены для точного учёта времени и денег без специальных правил.

### Два одинаковых названия товара

Третий случай не связан с катастрофой, но встречается в учебных проектах постоянно. В справочник товаров попадают две записи: «Кафе» с буквой `é`, записанной одной кодовой точкой, и «Кафе» с той же буквой, записанной как `e` плюс комбинирующий знак. На экране строки выглядят одинаково, но сравнение даёт ложь. Импорт создаёт дубль, отчёт раздваивает остатки, а поиск не находит товар по одному из написаний.

Причина в нормализации Unicode. Стандарт допускает несколько способов записать один и тот же символ, и приложение должно привести данные к одной форме, обычно NFC, на входе. В Python для этого есть `unicodedata.normalize`, в C# метод `Normalize`. Без этого правила любое сравнение текста зависит от того, какой редактор и какая система создали файл.

| Случай | Механизм | Урок |
|---|---|---|
| Ariane 5 | 64-битное число не поместилось в 16-битное | проверять диапазон преобразования |
| Patriot | ошибка 0,1 секунды накапливалась 100 часов | не хранить точное время в двоичной дроби |
| дубли товаров | разные формы Unicode | нормализовать текст на входе |

## Типичные ошибки

1. Целочисленное деление вместо дробного. `4800 / 1000` в C# даёт 4, а не 4,8. Лечится приведением одного операнда к `double`.
2. Переполнение `int` при умножении. 4800 × 129,90 в копейках помещается, а годовой оборот склада может выйти за 2,1 миллиарда. Проверяют диапазон или берут `long`.
3. Деньги в `double`. При сложении и умножении появляются хвосты в дробной части, и отчёт не сходится на копейки. Для денег берут `decimal`.
4. Строка вместо числа. `"4800" + 12` в C# даёт текст, а не сумму. Значение разбирают до арифметики.
5. Разбор без проверки. `int.Parse` на пустой строке или на тексте с пробелом выбрасывает исключение. Для пользовательского ввода берут `TryParse`.
6. Неявное приведение с потерей. `(int)3.9` отбрасывает дробь, `Convert.ToInt32` округляет. Выбор зависит от задачи, и его фиксируют в коде явно.
7. Сравнение строк без учёта культуры. `==` в C# сравнивает значения порядково, но для сортировки нужен `StringComparison`.
8. Логическое значение из числа. В Python `if count:` сработает при любом ненулевом числе, в C# такая запись не соберётся. Условие формулируют явно.
9. Сравнение `double` на равенство. `0.1 + 0.2 == 0.3` даёт ложь. Сравнивают разницу с допуском.
10. Длина строки вместо числа символов. Эмодзи занимает две кодовые единицы UTF-16, а комбинированный символ может занимать две кодовые точки. Для ограничения ввода считают текстовые элементы.

Разбор ошибок типа удобно начинать с сообщения компилятора. Код `CS0029` говорит о несовпадении типов при присваивании, `CS0165` об использовании локальной переменной без значения, `CS0266` о неявном преобразовании, которое требует явного. В Python имя ошибки `TypeError` указывает на недопустимую операцию, а текст сообщения называет типы, которые не подошли. Чтение сообщения целиком экономит больше времени, чем повторный запуск наугад.

## Итоги

- Тип задаёт множество значений, допустимые операции и способ хранения.
- В Python тип принадлежит значению и проверяется при выполнении, в C# тип принадлежит переменной и проверяется при сборке.
- Целые типы C# имеют конечный диапазон, переполнение по умолчанию не проверяется.
- Деньги хранят в `decimal`, а не в `double`, потому что двоичная дробь не представляет копейки точно.
- Строка неизменяема, а `+` в C# соединяет строку с любым значением, поэтому число разбирают до сложения.
- Длина строки в C# считается в кодовых единицах UTF-16, а в Python в кодовых точках.
- Явное преобразование выбирают, когда возможна потеря данных, и проверяют результат разбора через `TryParse`.
- Реальные случаи показывают, что непроверенное преобразование и накопленная ошибка точности стоят дороже, чем несколько строк проверки.
