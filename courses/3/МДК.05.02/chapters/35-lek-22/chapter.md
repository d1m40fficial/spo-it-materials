## Отгрузка, о которой известно одно слово

В 03:40 кладовщик из Калуги нажимает «Отгрузить» и получает сообщение об ошибке. Через десять минут звонит менеджер: машина стоит, накладная не закрыта. Инженер открывает журнал приложения и видит одну строку:

```text
ERROR: failed
```

В ней нет времени, имени пользователя, номера накладной и идентификатора запроса. Непонятно, это та самая отгрузка или ошибка недельной давности. Инженер начинает искать причину наугад: проверяет базу, свободное место, сеть до Калуги. На это уходит два часа, а причина оказывается в заблокированной записи товара, которую приложение не смогло прочитать.

Через сутки выясняется ещё одна подробность. Строка `failed` встречается в журнале 412 раз за неделю. Она появляется при таймауте, при отказе прав, при нарушении ограничения базы и при сетевой ошибке. Все четыре ситуации выглядят одинаково, поэтому поиск превращается в перебор. Инженер не может отличить редкий сбой от привычного фона, а поддержка не может ответить менеджеру, когда проблема повторится.

**Журнал это последовательность записей о том, что приложение пыталось сделать и чем это закончилось.** Он нужен не для того, чтобы любоваться выводом, а чтобы после сбоя восстановить ход событий: кто пришёл, что запросил, к какому объекту обратился, сколько ждал и что получил в ответ.

Хороший журнал отвечает на вопросы через месяц, на другой машине и без разработчика, который писал код. Именно это отличает его от отладочной печати, которая помогает здесь и сейчас, а после перезапуска терминала исчезает.

## Журнал это след решений, а не вывод отладки

Разница между журналом и отладочным выводом видна на вопросе, который задают к записи. Отладочный `print("тут")` отвечает на вопрос «дошла ли программа до этой строки». Запись журнала отвечает на вопрос «что произошло с этим запросом и этим пользователем». Первое нужно разработчику на своей машине, второе нужно инженеру через месяц после сбоя.

Хорошая запись отвечает на пять вопросов: когда, кто, что делал, с каким объектом, чем закончилось. Если хотя бы один ответ отсутствует, запись приходится дополнять догадками. В строке `ERROR: failed` нет ни одного ответа, поэтому она бесполезна, хотя формально это журнал.

У журнала три адресата. Разработчик ищет по нему причину дефекта, инженер поддержки восстанавливает картину сбоя, а служба безопасности проверяет доступ к данным. У каждого адресата свои вопросы, и один и тот же журнал должен на них отвечать. Поэтому запись делают структурой с постоянными полями, а не свободным текстом.

| Вопрос | Поле записи | Пример |
|---|---|---|
| Когда | `time` | `2026-10-12T09:16:41+03:00` |
| Кто | `user` | `kladovshchik_2` |
| Что делал | `action` | `stock_list` |
| С каким объектом | `site`, `supply_id`, `sku` | `site=Тула` |
| Чем закончилось | `result`, `error`, `duration_ms` | `reason=timeout` |
| В рамках чего | `request_id` | `8f23` |

Поле `request_id` связывает записи одного запроса. Без него шесть строк от одного действия выглядят как шесть независимых событий, и восстановить порядок можно только по времени, а при расхождении часов это ненадёжно.

Есть ещё одно различие, которое редко проговаривают. Журнал приложения описывает работу программы, а журнал аудита описывает действия людей с данными. Аудит нужен для доказательства факта доступа и хранится по правилам, которые задаёт служба безопасности. Приложение может писать оба потока, но смешивать их в одном файле не стоит: у них разные сроки хранения, разные права на чтение и разные требования к неизменности.

## Уровни: не важность текста, а цена события

Уровень показывает, насколько событие важно и кто должен на него реагировать. Уровни нужны не для красоты: по ним настраивают фильтр, и в рабочей среде обычно оставляют INFO и выше, а DEBUG включают только на время разбора.

| Уровень | Что означает | Пример из «Склад+» | Реакция |
|---|---|---|---|
| DEBUG | подробность для разработки | значение параметров запроса | никто, включают вручную |
| INFO | штатное событие завершено | вход выполнен, приёмка создана | не требует действий |
| WARNING | отклонение, работа продолжается | таймаут с повторной попыткой | проверить, если повторяется |
| ERROR | операция не выполнена | отчёт не выгружен, отгрузка не закрыта | разобрать в течение дня |
| CRITICAL | система или площадка недоступна | не открывается база, упал сервис | немедленно |

Граница между WARNING и ERROR проходит по результату операции. Если запрос к базе не удался, но приложение повторило его и получило данные, это WARNING: пользователь получил результат. Если после повтора операция всё равно не выполнена, это ERROR. Один и тот же сбой может дать обе записи, и это нормально, если у них разные `result`.

Ошибка валидации не является ERROR. Кладовщик ввёл количество 0, сервер вернул 400 и список полей. Это ожидаемое событие, о котором достаточно записи INFO или WARNING с кодом `validation_failed`. Если каждую опечатку писать как ERROR, журнал ошибок перестанет быть списком проблем, которые действительно нужно разбирать.

Уровень назначают по последствиям, а не по типу исключения. `PermissionError` при выгрузке отчёта это ERROR для менеджера, который ждёт файл, и WARNING, если приложение само запросило доступ и получило отказ в рамках проверки. Контекст важнее имени класса ошибки.

Полезно помнить, что имена уровней в разных библиотеках совпадают не полностью. В Python есть пять основных уровней и числовые значения: DEBUG 10, INFO 20, WARNING 30, ERROR 40, CRITICAL 50. В .NET к ним добавляется Trace ниже Debug и None для полного отключения. OpenTelemetry использует TRACE, DEBUG, INFO, WARN, ERROR, FATAL. Смысл один, но при переходе между библиотеками настройки переносят по смыслу, а не по числу.

| Событие | Python | .NET | OpenTelemetry |
|---|---|---|---|
| подробная трассировка | DEBUG | Trace | TRACE |
| отладочные значения | DEBUG | Debug | DEBUG |
| штатное событие | INFO | Information | INFO |
| отклонение с продолжением | WARNING | Warning | WARN |
| операция не выполнена | ERROR | Error | ERROR |
| отказ сервиса | CRITICAL | Critical | FATAL |

Фильтр по уровню это не то же самое, что фильтр по важности для бизнеса. Запись INFO о том, что пользователь вошёл, может быть критичной для аудита, а запись DEBUG с суммой заказа может содержать персональные данные. Уровень отвечает на вопрос «кого будить», а не на вопрос «что хранить». Эти решения принимают отдельно.

::figure log-level-filter | Нажмите кнопку уровня под схемой. В таблице останутся только записи, которые попадут в журнал при таком пороге, пересчитается их число и появится пояснение. Обратите внимание: при пороге INFO исчезает DEBUG, но остаётся WARNING, а при пороге ERROR пропадает причина ошибки.

## Формат записи: от строки к событию

Запись состоит из постоянных полей и сообщения. Постоянные поля пишут в одном порядке, чтобы журнал читался глазами и разбирался программой. Самый распространённый формат в учебных и рабочих системах это пары `ключ=значение`, разделённые пробелом.

```text
2026-10-12 09:16:41 WARN request_id=8f23 user=kladovshchik_2 action=stock_list site=Тула rows=0 reason=timeout
2026-10-12 09:17:10 ERROR request_id=8f23 user=kladovshchik_2 action=stock_list error=TimeoutError
```

Формат `ключ=значение` удобен для чтения и поиска: строку можно найти по `request_id=8f23` или отфильтровать по `action=stock_list`. Если значение содержит пробел, его заключают в кавычки или заменяют пробел подчёркиванием. Иначе разбор ломается на первом же названии площадки из двух слов.

Второй формат это JSON, по одной записи на строку. Он лучше подходит для централизованного сбора, когда журналы с четырёх площадок отправляют в одно хранилище и разбирают автоматически. JSON терпит вложенность и любые символы, но хуже читается человеком в терминале.

| Признак | `ключ=значение` | JSON |
|---|---|---|
| Чтение глазами | удобно | требует форматирования |
| Поиск по полю | простой шаблон | разбор или поисковый движок |
| Вложенные данные | плохо | хорошо |
| Размер записи | меньше | больше |
| Сбор с нескольких машин | вручную | стандартный формат |

Выбор формата не так важен, как постоянство. Если половина записей в JSON, а половина в свободном тексте, автоматический разбор невозможен. Договоритесь о формате один раз и проверьте его на нескольких событиях.

Структурированная запись начинается с отказа от склейки сообщения заранее. В Python принято передавать параметры отдельно, чтобы библиотека подставила их по шаблону:

```python
import logging

log = logging.getLogger("sklad.shipment")

log.info(
    "shipment_created request_id=%s user=%s supply_id=%s lines=%d duration_ms=%d",
    request_id, user, supply_id, len(lines), elapsed_ms,
)
```

В .NET та же идея выражается шаблоном сообщения. Фигурные скобки задают имена полей, которые провайдер журналирования сохраняет отдельно от текста:

```csharp
public sealed class ShipmentService(ILogger<ShipmentService> log)
{
    public void Create(string requestId, string user, int supplyId)
    {
        log.LogInformation(
            "shipment_created request_id={RequestId} user={User} supply_id={SupplyId}",
            requestId, user, supplyId);
    }
}
```

Разница между `$"supply_id={supplyId}"` и шаблоном `"supply_id={SupplyId}"` не косметическая. В первом случае строка уже склеена, и провайдер видит только текст. Во втором он получает имя поля и значение, поэтому может записать JSON, отфильтровать по `SupplyId` и построить график. Это и называют структурированным журналированием.

## Время, длительность и порядок

Время пишут в формате ISO 8601 с часовым поясом: `2026-10-12T09:16:41+03:00`. Локальное время без пояса опасно при сборе с нескольких площадок и при переходе на летнее время. Даже если все четыре склада находятся в одной зоне, запись с поясом однозначна, а без пояса требует догадки.

Часы на серверах синхронизируют. Если часы приложения в Москве отстают на две минуты, а часы базы в Туле спешат, порядок записей одного запроса нарушится: ответ окажется раньше запроса. Служба точного времени и единый часовой пояс в настройках снимают эту проблему. В учебном стенде достаточно одного сервера, но правило стоит запомнить для рабочей системы с четырьмя площадками.

Порядок внутри одного запроса лучше не выводить из времени. Две записи могут получить одинаковую метку с точностью до миллисекунды, а перестановка при сортировке сделает историю неверной. Надёжнее добавить порядковый номер события или писать идентификатор шага: `step=2`, `attempt=1`. Тогда последовательность сохраняется даже при расхождении часов.

Длительность операции пишут числом в миллисекундах. `duration_ms=1840` сразу показывает, что запрос шёл почти две секунды, а `duration_ms=12` что он быстрый. Без этого поля невозможно отличить медленную базу от сетевого таймаута, не открывая другие журналы. Измерять длительность лучше по монотонным часам, которые не зависят от перевода времени: в Python это `time.perf_counter`, в .NET `Stopwatch`.

Для распределённой системы одного `duration_ms` мало. Нужно понимать, где именно прошло время: в приложении, в базе или в очереди. Поэтому в запись добавляют `db_ms`, `queue_ms`, `http_ms`. Сумма частей не всегда равна общему времени, и расхождение само по себе является полезным наблюдением.

## Идентификатор запроса и контекст

Идентификатор запроса выдаётся на входе и передаётся во все записи, которые относятся к этому запросу. Его можно взять из заголовка `X-Request-ID`, если клиент его прислал, или сгенерировать на сервере. В ответ клиенту возвращают тот же идентификатор, чтобы пользователь мог назвать его в обращении в поддержку.

Ниже пример на Flask: идентификатор создаётся до обработчика, попадает в журнал и возвращается в заголовке ответа.

```python
import logging
import sys
import uuid

from flask import Flask, g, jsonify, request

app = Flask(__name__)
logger = logging.getLogger("sklad.api")
logger.setLevel(logging.INFO)
logger.propagate = False
handler = logging.StreamHandler(sys.stdout)
handler.setFormatter(logging.Formatter(
    "%(asctime)s %(levelname)s %(message)s", datefmt="%Y-%m-%d %H:%M:%S"
))
logger.addHandler(handler)


@app.before_request
def assign_request_id():
    g.request_id = request.headers.get("X-Request-ID") or uuid.uuid4().hex[:8]
    logger.info("request_start request_id=%s method=%s path=%s",
                g.request_id, request.method, request.path)


@app.after_request
def add_request_id(response):
    response.headers["X-Request-ID"] = g.request_id
    return response


@app.get("/api/stock")
def stock():
    logger.info("stock_list request_id=%s rows=%s", g.request_id, 4800)
    return jsonify({"rows": 4800}), 200


client = app.test_client()
response = client.get("/api/stock", headers={"X-Request-ID": "8f23"})
print("HTTP", response.status_code)
print("X-Request-ID:", response.headers.get("X-Request-ID"))
```

Запуск показывает, что один идентификатор связал начало запроса, работу обработчика и заголовок ответа:

```text
2026-10-31 11:26:18 INFO request_start request_id=8f23 method=GET path=/api/stock
2026-10-31 11:26:18 INFO stock_list request_id=8f23 rows=4800
HTTP 200
X-Request-ID: 8f23
```

В рабочем сервисе идентификатор передают и дальше: в вызовы базы, в очередь, в фоновую задачу. Если фоновая задача обрабатывает заявку через минуту после запроса, она сохраняет тот же `request_id`, и цепочка не рвётся. Для этого идентификатор передают явным параметром или кладут в контекст выполнения, а не надеются, что он сам появится в новом потоке.

В C# ту же роль играет область журналирования: `ILogger` с `BeginScope` добавляет идентификатор ко всем записям внутри блока, а провайдер выводит его в составе сообщения.

```csharp
using (log.BeginScope(new Dictionary<string, object> { ["request_id"] = requestId }))
{
    log.LogInformation("stock_list rows={Rows}", rows);
    ReserveStock(supplyId, requestId);
}
```

Смысл не меняется: один запрос, один идентификатор, все записи с ним. В распределённой системе к нему добавляют `trace_id` и `span_id` из W3C Trace Context. Журнал, метрики и трассировка тогда ссылаются друг на друга, и переход от медленного графика к конкретной записи занимает секунды.

Заголовок от клиента принимают с осторожностью. Слишком длинное значение или перевод строки внутри него ломают формат журнала и позволяют подделать запись. Перед использованием проверяют длину и набор символов: например, разрешают от 8 до 32 символов латиницы и цифр, а всё остальное заменяют сгенерированным значением. Тогда внешний клиент не сможет вставить в журнал чужую строку.

Отдельная проблема это очередь. Если приложение пишет журнал синхронно на диск, медленный диск останавливает обработку запроса. Если пишет в очередь, очередь может переполниться, и записи начнут теряться. Обычно выбирают компромисс: в очередь кладут всё, а при переполнении сохраняют WARNING и ERROR, отбрасывая DEBUG. Потерю части DEBUG фиксируют отдельным счётчиком, чтобы она не осталась незамеченной.

## Секреты, персональные данные и подделка записи

Журнал читают люди с разными правами, и он хранится дольше, чем живёт запрос. Поэтому в него не попадают секреты и лишние персональные данные. Пароль, токен, ключ API и строка подключения с паролем не должны появляться ни в одной записи, даже на уровне DEBUG.

| Нельзя писать | Почему | Что писать вместо |
|---|---|---|
| Пароль | даёт прямой доступ к учётной записи | `user=kladovshchik_2`, `result=denied` |
| Токен целиком | позволяет выдать себя за пользователя | `token_id=...`, `result=expired` |
| Номер карты | персональные данные | последние четыре цифры |
| Полное имя и адрес | избыточные персональные данные | идентификатор пользователя |
| Текст SQL с параметрами | раскрывает схему и данные | имя запроса, `duration_ms` |
| Стек вызовов клиенту | раскрывает устройство сервиса | короткий код ошибки |

Правило простое: в журнал пишут идентификаторы, а не содержимое. Идентификатор пользователя позволяет найти запись в справочнике, но сам по себе не раскрывает пароль. Номер накладной позволяет найти документ, но не показывает суммы и контрагентов.

Отдельно решают, что делать с адресом электронной почты и телефоном. Иногда без них невозможно разобрать обращение, но хранить их в общем журнале на всех уровнях не нужно. Если поле действительно важно, его маскируют: `user=kladovshchik_2`, `phone=***-***-12-34`.

Ошибки с секретами возникают из привычки писать в журнал весь объект запроса. `logger.info("request=%s", data)` выглядит удобно, пока в `data` не окажется пароль или токен. Пишите поля явно: `logger.info("login user=%s result=%s", login_name, result)`. Тогда лишнее не попадёт в запись случайно.

Маскирование должно происходить до записи, а не при чтении. Если пароль попал в файл, он останется в копиях, архивах и резервных копиях. Удаление строки из текущего файла не убирает её из старого сегмента. Поэтому фильтр ставят на входе в обработчик и проверяют тестом: подставить объект с полем `password` и убедиться, что в выводе его нет.

Вторая угроза это подделка записи через пользовательские данные. Если имя файла или значение поля содержит перевод строки, злоумышленник может добавить в журнал строку, которой не было. Такой приём называют log injection. Лечение простое: экранировать управляющие символы, ограничивать длину пользовательских полей и не собирать запись конкатенацией.

```python
def clean(value: str, limit: int = 120) -> str:
    value = value.replace("\r", "\\r").replace("\n", "\\n")
    return value[:limit]
```

OWASP рекомендует записывать события аутентификации, отказы в доступе и ошибки проверки ввода, но не секреты и не полные персональные данные [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html). Там же сказано, что журналы нужно защищать от изменения и хранить столько, сколько требует политика. Эти правила полезно прочитать целиком: они короткие и хорошо переводятся в чек-лист.

Третья угроза это чтение журнала не тем человеком. Каталог с журналами не должен быть доступен всем пользователям сервера. Права на запись есть у приложения, права на чтение у дежурной смены, а на удаление у отдельной процедуры ротации. Если журнал лежит рядом с исходным кодом и открыт веб-серверу, он становится способом утечки.

## Объём, ротация и стоимость

Журнал растёт с каждой операцией. В «Склад+» 120 сотрудников, в среднем 35 действий за рабочий день, это около 4200 записей. При средней длине 250 байт получается примерно 1 МБ в рабочий день и 23 МБ в месяц. За год без ротации накопится около 277 МБ, а поиск по одному файлу станет медленным.

Числа кажутся небольшими, пока не добавить DEBUG и JSON. Подробная запись параметров запроса весит 400-600 байт, а при включённом DEBUG число строк вырастает в пять раз. Тот же поток превращается в 5 МБ в день и 150 МБ в месяц. На четырёх площадках это уже 600 МБ, а с трассировкой и вовсе несколько гигабайт.

Ротация делит журнал на файлы по размеру или по дате. Настройка `RotatingFileHandler` с пределом 10 МБ и пятью копиями держит на диске около 50 МБ и создаёт новый файл, когда старый заполнен. Старые копии удаляются по кругу, поэтому место не растёт бесконечно.

```python
from logging.handlers import RotatingFileHandler

handler = RotatingFileHandler(
    "logs/app.log", maxBytes=10 * 1024 * 1024, backupCount=5, encoding="utf-8"
)
```

| Параметр | Значение для учебного стенда | Что означает |
|---|---|---|
| Размер файла | 10 МБ | после заполнения создаётся новый |
| Число копий | 5 | хранятся последние пять файлов |
| Срок хранения | 90 дней | требование службы безопасности |
| Уровень в работе | INFO | DEBUG включают на время разбора |
| Место | отдельный каталог вне репозитория | журнал не коммитят |

Срок хранения задают не по размеру диска, а по требованиям: сколько времени нужно, чтобы разобрать инцидент и доказать факт доступа. Девяносто дней это типичный учебный ориентир, в реальной системе срок может быть больше. Если журнал нужен дольше, его отправляют в центральное хранилище, а на сервере оставляют только последние дни.

Отдельно настраивают журнал ошибок. Удобно держать два потока: общий с уровнем INFO и отдельный с уровнем ERROR, чтобы дежурный не искал ошибки среди тысяч штатных записей. Оба потока пишут в разные файлы, но используют один формат и один идентификатор запроса.

Стоимость журнала складывается не только из диска. Централизованное хранилище берёт деньги за приём, индексацию и запросы. Высокая кардинальность поля, например `user_id` или `request_id` в качестве метки, делает индекс огромным. Поэтому идентификаторы ищут полнотекстовым поиском, а графики строят по ограниченному набору полей: `action`, `site`, `result`.

Сэмплирование снижает объём, но требует осторожности. Можно сохранять все ERROR и WARNING и каждый десятый INFO. Тогда редкая ошибка не потеряется, а фон станет меньше. Нельзя сэмплировать аудит и события безопасности: пропущенная запись о входе может оказаться единственным доказательством.

Журнал не заменяет метрики. Метрика это число, посчитанное по событиям: сколько запросов в секунду, какая доля завершилась ошибкой, сколько длится девяносто пятый процентиль. Метрики дешевы в хранении и хорошо показывают тренд, но не объясняют причину отдельного отказа. Журнал объясняет причину, но по нему дорого строить график за год. Поэтому в рабочей системе смотрят на график, а затем открывают записи того периода, где график изменился.

Трассировка добавляет третий взгляд. Она показывает путь одного запроса через несколько сервисов и время каждого шага. Журнал и трассировка связаны через `trace_id`: по нему можно перейти от медленного участка к записям с подробностями. Если в проекте уже есть трассировка, дублировать её шаги в журнале не нужно, достаточно ссылки.

Аудит отличается от журнала приложения не форматом, а обязательствами. Запись аудита должна быть неизменяемой, доступной только уполномоченным людям и храниться столько, сколько требует политика. Журнал приложения можно сэмплировать и чистить, аудит нельзя. Если смешать их в одном файле, ротация однажды удалит доказательство доступа, а служба безопасности узнает об этом после проверки.

::figure log-pipeline | Путь записи от вызова в коде до центрального хранилища. На каждом шаге справа указано, что может потеряться: структура, уровень, секрет, буфер, срок хранения или сеть. Используйте схему как порядок проверки при настройке нового сервиса.

::/gate

## Три аварии, в которых журнал оказался не тем, чем казался

Разборы ниже следуют правилу послеаварийного анализа без обвинений: ищут условие, которое позволило ошибке пройти, а не виноватого [Postmortem Culture](https://sre.google/sre-book/postmortem-culture/).

### GitLab, 2017: журнал был, а сигнала не было

31 января 2017 года инженер GitLab настраивал репликацию PostgreSQL и по ошибке удалил каталог данных на основном сервере вместо вторичного. Удаление остановили через секунду или две, но около 300 ГБ уже было потеряно. Сервис GitLab.com не работал примерно 18 часов, а восстановление шло из снимка шестичасовой давности. По оценке компании, пропали данные примерно 5000 проектов, 5000 комментариев и 700 учётных записей, созданных между 17:20 и 23:30 UTC [GitLab, 2017](https://about.gitlab.com/blog/postmortem-of-database-outage-of-january-31/).

Самое важное в этом разборе не команда удаления. Резервное копирование через `pg_dump` не работало: версия утилиты не совпадала с версией сервера, и процесс завершался ошибкой. Уведомления об ошибке отправлялись по электронной почте, но почтовый сервер отвергал их из-за настроек DMARC. Другого канала не было. В результате сбой резервного копирования не видел никто, пока не понадобилось восстановление.

Урок для журналирования прямой. Запись об ошибке, которую никто не получает, не является сигналом. Нужен отдельный канал доставки, проверка, что он работает, и мониторинг самого процесса резервного копирования. GitLab после разбора добавил панель состояния резервных копий и назначил владельца процедуры. Журнал стал частью контура наблюдения, а не файлом, который пишется сам по себе.

### Knight Capital, 2012: развёртывание без следа версий

1 августа 2012 года брокерская фирма Knight Capital включила новую версию торговой системы. Обновление должны были установить на восемь серверов, но на одном из них остался старый код. Этот код содержал функцию `Power Peg`, которая раньше использовалась для тестовых сценариев и не должна была работать с реальными заявками. После открытия рынка система начала отправлять заявки, которых никто не заказывал. За 45 минут фирма потеряла более 460 млн долларов, а Комиссия по ценным бумагам США позже установила, что у фирмы не было надлежащего контроля за развёртыванием и обработкой заявок [SEC, 2013](https://www.sec.gov/litigation/admin/2013/34-70694.pdf).

В этой истории нет одной строки журнала, которая спасла бы фирму. Но есть вопрос, на который журнал обязан отвечать: какая версия кода работает на каждой машине и когда она туда попала. Если развёртывание не оставляет следа, расхождение версий обнаруживается только по последствиям. Запись `deploy version=2.7 host=app-07 result=ok` кажется скучной, пока не выясняется, что на `app-08` такой записи нет.

Урок для темы: журнал нужен не только приложению, но и процессу доставки. Версия, время, хеш коммита и список машин должны попадать в отдельный поток, который не смешивается с бизнес-событиями. Тогда вопрос «что именно работало в момент сбоя» имеет ответ.

### TSB, 2018: миллионы клиентов и месяц разбора

22 апреля 2018 года британский банк TSB перевёл клиентов на новую банковскую платформу. Миграция прошла не полностью: часть клиентов не могла войти в приложение, операции не проходили, а разбор последствий растянулся на месяцы. В 2022 году Управление финансового надзора Великобритании оштрафовало банк на 29,1 млн фунтов за недостаточное управление операционной устойчивостью, а Банк Англии добавил отдельный штраф [FCA, 2022](https://www.fca.org.uk/publication/final-notices/tsb-bank-plc-2022.pdf).

Для журналирования здесь важны два обстоятельства. Первое: при массовом сбое поток записей резко вырастает, и хранилище должно выдержать не средний, а пиковый объём. Второе: поддержке нужно быстро отвечать на вопрос «что произошло с конкретным клиентом», а для этого записи должны быть связаны с идентификатором клиента и операции, а не только с номером сервера.

Урок для темы: журнал проектируют под худший день, а не под обычный. Проверка нагрузки на журнал входит в проверку готовности к запуску. Если при десятикратном росте записей приложение начинает тормозить или терять записи, журнал становится участником аварии, а не инструментом её разбора.

| Случай | Что отказало | Роль журнала | Вывод |
|---|---|---|---|
| GitLab, 2017 | резервное копирование и доставка уведомлений | ошибки писались, но сигнал не доходил | журнал без получателя не работает |
| Knight Capital, 2012 | контроль версий при развёртывании | не было следа, какая версия где работает | журнал доставки так же важен, как журнал приложения |
| TSB, 2018 | устойчивость при массовой миграции | объём и связь с клиентом | журнал проверяют на пиковой нагрузке |

::/gate

## Как читать журнал

Читать журнал значит восстанавливать историю по идентификатору. Ниже фрагмент утреннего журнала «Склад+». В нём перемешаны события разных пользователей, поэтому сначала выбирают нужный `request_id`.

```text
2026-10-12 09:14:22 INFO request_id=8f21 user=kladovshchik_1 action=login result=ok
2026-10-12 09:15:03 INFO request_id=8f22 user=kladovshchik_1 action=stock_list site=Москва rows=4800
2026-10-12 09:16:41 WARN request_id=8f23 user=kladovshchik_2 action=stock_list site=Тула rows=0 reason=timeout
2026-10-12 09:17:10 ERROR request_id=8f23 user=kladovshchik_2 action=stock_list error=TimeoutError
2026-10-12 09:20:55 INFO request_id=8f24 user=manager_1 action=report_export rows=312
2026-10-12 09:24:18 WARN request_id=8f25 user=admin action=user_block target=kladovshchik_3 reason=three_failed_logins
2026-10-12 09:25:02 INFO request_id=8f26 user=kladovshchik_3 action=login result=denied reason=blocked
2026-10-12 09:31:44 ERROR request_id=8f27 user=manager_1 action=report_export error=PermissionError
```

По `request_id=8f23` видно, что кладовщик из Тулы запросил остатки, получил таймаут и повтор не удался. По `8f25` и `8f26` видно, что администратор заблокировал учётную запись после трёх неудачных входов, а следующая попытка входа получила отказ. Эти две истории не связаны между собой, хотя стоят рядом.

| Идентификатор | Кто | Что произошло | Чем закончилось |
|---|---|---|---|
| `8f21` | `kladovshchik_1` | вход | успешно |
| `8f22` | `kladovshchik_1` | список остатков по Москве | 4800 строк |
| `8f23` | `kladovshchik_2` | список остатков по Туле | таймаут, затем ошибка |
| `8f25` | `admin` | блокировка `kladovshchik_3` | три неудачных входа |
| `8f26` | `kladovshchik_3` | вход | отказ, запись заблокирована |
| `8f27` | `manager_1` | выгрузка отчёта | нет прав |

Порядок записей внутри одного идентификатора тоже важен. Сначала WARNING о таймауте, потом ERROR о том, что повтор не помог. Если бы приложение писало только итоговую ошибку, причина осталась бы неизвестной. Если бы писало только таймаут, было бы непонятно, чем закончилось дело.

По журналу можно ответить и на вопрос, которого не было в запросе. Например, `rows=0` при `reason=timeout` показывает, что пустой список остатков не означает пустой склад: данные не пришли. Без этого поля поддержка могла бы сообщить менеджеру неверную причину.

При разборе полезно идти от общего к частному. Сначала выбрать временное окно и площадку, затем найти аномалию по частоте или длительности, затем взять один `request_id` и прочитать его целиком. Обратный порядок, когда сразу открывают первую ошибку, часто уводит в сторону: первая ошибка может быть следствием, а не причиной.

## Чек-лист перед запуском

| Пункт | Что проверить | Признак готовности |
|---|---|---|
| Поля | время, уровень, `request_id`, действие, результат | запись отвечает на пять вопросов |
| Уровни | INFO в работе, DEBUG по требованию | фильтр меняется без правки кода |
| Секреты | пароли, токены, карты | тест с объектом-ловушкой не находит секрет |
| Подделка | перевод строки в пользовательском поле | строка остаётся одной записью |
| Ротация | размер, число копий, срок | диск не растёт бесконечно |
| Доставка | ошибки журнала видны дежурному | тестовая ошибка доходит до получателя |
| Нагрузка | пиковый поток записей | приложение не теряет ERROR |
| Хранение | срок и права | журнал недоступен лишним людям |

Этот список проверяют до запуска, а не во время первого разбора. Каждый пункт можно проверить на учебном стенде: отправить запрос с паролем в поле, вставить перевод строки в имя пользователя, временно заполнить диск, отключить почтовый сервер. Дешевле найти проблему на стенде, чем объяснять её заказчику.

## Типичные ошибки

**Вывод через `print`.** `print` не знает уровней, не пишет время и не умеет отправлять записи в файл. В консоли разработчика он выглядит нормально, в рабочей среде теряется среди вывода сервера. Для журнала используют `logging` или его аналог в другом языке.

**Запись без контекста.** `ERROR: failed` не отвечает ни на один вопрос. Запись `ERROR request_id=8f23 user=kladovshchik_2 action=shipment_create supply_id=505 error=LockedError` позволяет найти документ и причину за минуту.

**Секрет в сообщении.** `logger.info("login=%s password=%s", login, password)` навсегда оставляет пароль в файле, копиях и резервных архивах. Даже удаление строки из текущего файла не убирает её из старых копий.

**Ошибка записана дважды.** Обработчик пишет ERROR, пробрасывает исключение, промежуточный слой пишет ERROR снова, и в журнале появляются две одинаковые записи с разным текстом. Пользователь видит один отказ, дежурный ищет две причины. Пишите один раз на границе, где решение принято.

**Уровень не по смыслу.** Каждая опечатка в форме пишется как ERROR, и журнал ошибок превращается в список нормальной работы. Настоящая авария теряется среди сотен записей о неверном количестве.

**Нет идентификатора.** Шесть строк одного запроса выглядят как шесть событий. Связать их можно только по времени, а при параллельных запросах это не работает.

**Журнал без ротации.** Файл растёт, пока не закончится место на диске. Сервер падает не из-за бизнес-ошибки, а из-за собственного журнала. Предел размера и число копий задают до запуска в работу.

**Журнал в репозитории.** Файл с идентификаторами пользователей попадает в Git и остаётся в истории даже после удаления. Каталог журналов добавляют в `.gitignore`, а конфигурацию хранят отдельно.

**Склейка вместо шаблона.** `logger.info("user=" + name)` теряет структуру и позволяет подставить перевод строки. Передавайте значения параметрами, а имена полей держите в шаблоне.

## Итоги

- Журнал восстанавливает ход запроса: когда, кто, что делал, с каким объектом и чем закончилось.
- Уровень выбирают по последствиям: INFO для штатных событий, WARNING для отклонений, ERROR для неудачных операций.
- `request_id` связывает записи одного запроса и возвращается клиенту в заголовке.
- В журнал пишут идентификаторы, а не пароли, токены и лишние персональные данные.
- Ротация и срок хранения защищают диск от переполнения, а журнал от бесконечного роста.
- Журнал без доставки, проверки и владельца не является сигналом, что показывают разборы GitLab, Knight Capital и TSB.

Q: Зачем нужен журнал приложения?
+ Чтобы восстановить ход запроса и причину сбоя
- Чтобы заменить резервное копирование базы
- Чтобы ускорить выполнение SQL-запросов
- Чтобы хранить пароли пользователей
! Журнал фиксирует события и результаты, по нему разбирают инцидент.

Q: Какой уровень подходит для штатного успешного входа?
+ INFO
- ERROR
- CRITICAL
- DEBUG
! Успешный вход это нормальное событие, для него достаточно INFO.

Q: Что означает уровень WARNING?
+ Отклонение, при котором работа продолжается
- Полная остановка сервиса
- Подробность только для разработчика
- Штатное завершение операции
! WARNING сообщает о проблеме, которую удалось обойти или повторить.

Q: Что связывает записи одного запроса?
+ `request_id`
- Имя пользователя
- Номер версии приложения
- Уровень сообщения
! Один идентификатор запроса позволяет собрать все его записи в одну историю.

Q: Что должно быть в записи журнала?
+ Время события
+ Пользователь и действие
+ Результат операции
- Пароль пользователя
- Полный текст токена
! Запись описывает событие и результат, но не раскрывает секреты.

Q: Почему пароль нельзя писать в журнал?
+ Он остаётся в файлах и копиях и даёт доступ к учётной записи
- Он увеличивает размер строки
- Он мешает ротации файла
- Он меняет уровень сообщения
! Секрет в журнале переживает запрос и попадает в резервные копии.

Q: Что делать с журналом, который растёт каждый день?
+ Настроить ротацию по размеру или дате
- Удалять файл перед каждым запросом
- Писать только ошибки валидации
- Хранить журнал в репозитории
! Ротация ограничивает размер и сохраняет последние записи.

Q: Почему ошибку не стоит записывать дважды?
+ Пользователь получает один отказ, а дежурный ищет две причины
- Вторая запись всегда теряется
- Журнал перестаёт быть текстовым
- Уровень ERROR становится необязательным
! Дублирование запутывает разбор и раздувает журнал.

Q: Что означает поле `duration_ms=1840`?
+ Операция заняла около 1,8 секунды
- Операция началась в 18:40
- В запросе 1840 строк
- Пользователь ждал 1840 минут
! Длительность пишут в миллисекундах, чтобы видеть медленные операции.

Q: Какие данные допустимо писать в журнал?
+ Идентификатор пользователя
+ Номер накладной
+ Код ошибки
- Пароль в открытом виде
- Полный токен доступа
! Идентификаторы позволяют найти объект, не раскрывая секрет.

Q: Какие события относятся к уровню ERROR?
+ Отгрузка не закрыта после повторной попытки
+ Отчёт не выгружен из-за отсутствия прав
- Пользователь ввёл количество 0 и получил 400
- Вход выполнен успешно
! ERROR означает, что операция не выполнена после всех попыток.

Q: Почему журнал GitLab не помог предотвратить потерю данных?
+ Ошибки резервного копирования отправлялись почтой, которую отвергал сервер
- Журнал был отключён на всех серверах
- Записи хранились в базе данных вместо файла
- Уровень INFO был запрещён настройками
! Сигнал об ошибке существовал, но не доходил до людей.

Q: Как называют деление журнала на файлы по размеру или дате?
= ротация
= ротация журнала
! Ротация создаёт новые файлы и удаляет старые по заданному правилу.

Q: В каком заголовке клиент получает идентификатор запроса?
= X-Request-ID
= X-Request-Id
! Сервер возвращает тот же идентификатор, чтобы его можно было назвать в поддержке.

Q: Как называют подделку записи через перевод строки в пользовательском поле?
= log injection
= инъекция в журнал
! Управляющие символы экранируют, а длину поля ограничивают.
