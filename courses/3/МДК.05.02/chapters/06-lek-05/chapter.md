## Два способа получить один результат

В понедельник кладовщик калужской площадки просит посчитать, сколько паллет займёт отгрузка. Объём груза известен: 3,852 кубического метра, объём одной паллеты 1,44. Программист открывает Python, пишет две строки, нажимает запуск и через секунду видит ответ: три паллеты.

Во вторник тот же расчёт нужен внутри учётного приложения «Склад+», которое написано на C#. Программист копирует знакомые строки в файл `Program.cs`, нажимает F5 и получает сообщение об ошибке. Код правильный, но среда не понимает, что с ним делать: в C# нельзя запустить текст программы напрямую.

**Программа на C# проходит через сборку, и всё устройство проекта служит этой сборке.** Python читает и выполняет файл строка за строкой. C# сначала превращает все файлы проекта в один готовый модуль, сборку, и только потом запускает её. Пока это правило не усвоено, папки `bin`, `obj` и файл проекта кажутся лишним мусором, а любая ошибка выглядит необъяснимой.

Разница видна не только в командах, но и в том, когда обнаруживается проблема. В Python опечатка в имени переменной проявляется, когда выполнение дойдёт до этой строки. В C# компилятор просматривает все файлы проекта и сообщает об опечатке до запуска. Это не делает программу правильной, но меняет момент, когда о ней узнаёт разработчик.

У сборки есть и вторая сторона. Готовая программа не требует исходного кода, компилятора и файла проекта. Достаточно сборки и среды исполнения. Поэтому один и тот же результат можно передать на сервер, на компьютер кладовщика и в тестовую среду, не объясняя, как настраивать проект. За это приходится платить шагом сборки между правкой и результатом.

## Идея: текст становится сборкой

Компилятор C# читает исходные файлы и проверяет их целиком, до запуска. Он строит дерево разбора, затем семантическую модель: какие имена существуют, совпадают ли типы, возвращает ли метод значение, существует ли указанный член класса. Если проверка прошла, компилятор записывает промежуточный код и метаданные в файл сборки.

Промежуточный код называют CIL, Common Intermediate Language, или просто IL. Это не машинные команды конкретного процессора, а инструкции виртуальной машины: загрузить значение, сложить, вызвать метод, вернуть результат. Рядом с кодом лежат метаданные: список типов, полей, методов и ссылок на другие сборки. Метаданные позволяют среде исполнения понять, что находится внутри, не читая исходники.

Благодаря общему IL среда исполнения не зависит от языка исходного кода. C# и F# компилируются в один и тот же промежуточный код, а библиотека, написанная на одном языке, вызывается из другого. Сборка получается самоописывающей: инструмент может прочитать список типов и методов без исходников, а среда при загрузке проверяет ссылки по именам и версиям. Если нужная сборка не найдена, ошибка возникает при загрузке, а не при компиляции, и сообщение называет отсутствующий файл.

У метаданных есть и обратная сторона. Сборка содержит имена типов и методов, поэтому она не является способом спрятать код. Обфускация меняет имена, но не делает сборку нечитаемой. Для учебного проекта это не проблема, для коммерческого продукта это отдельное решение, которое принимают осознанно.

Дальше работает общеязыковая среда исполнения, CLR. Она загружает сборку, проверяет IL на типобезопасность и передаёт код JIT-компилятору, который переводит инструкции в машинные команды по мере вызова методов. Первый вызов метода может быть медленнее, потому что код компилируется на ходу. Современная среда использует многоуровневую компиляцию: сначала быстрый вариант, затем более оптимизированный, если метод вызывается часто.

| Этап | Что происходит | Что получается |
|---|---|---|
| Восстановление | проверяются и скачиваются зависимости проекта | список пакетов в `obj` |
| Сборка | компилятор проверяет все файлы проекта | файл `.dll` в `bin` |
| Запуск | среда загружает сборку и вызывает точку входа | работающая программа |
| Публикация | сборка готовится для другой машины | папка `publish` |

Два шага вместо одного дают то, чего нет у интерпретатора. Ошибка типов видна до первого запуска, а не в момент, когда пользователь ввёл не то значение. Готовая сборка не требует исходного кода и компилятора на машине пользователя. Один и тот же файл `.dll` можно запустить на сервере, на компьютере кладовщика и в тестовой среде, если там есть подходящая версия среды исполнения.

Цена тоже понятна. Между правкой и результатом появляется шаг сборки. Для маленького проекта он занимает секунды, для большого решения минуты, и в это время программа не работает. Разработчик ждёт, пока компилятор проверит весь проект, даже если изменена одна строка. Компилятор умеет собирать только изменившиеся проекты, но внутри проекта проверка всё равно значительная.

Есть компромисс и внутри способа запуска. Обычная сборка оставляет IL и компилирует его при старте: программа дольше запускается, зато сборка меньше и лучше переносится. Публикация с готовым машинным кодом (ReadyToRun) сокращает время старта, но увеличивает размер. Нативная компиляция (Native AOT) даёт быстрый старт и небольшой набор файлов, однако ограничивает динамическую загрузку и часть возможностей отражения. Для учебного консольного приложения эти различия не критичны, но выбирать режим публикации нужно под задачу, а не по привычке.

::figure build-pipeline | Путь от файлов C# до работающей программы: компилятор, промежуточный код, загрузка сборки и JIT. Слева отмечено место, где появляется ошибка типов, справа граница между сборкой и запуском.

Полезно различать ошибку компиляции и ошибку выполнения. Компилятор ловит несуществующие имена, несовпадение типов и неправильные вызовы. Он не ловит деление на ноль, отсутствующий файл, неверный формат ввода и логические ошибки. Программа, которая собралась, ещё не доказала свою правильность, она лишь прошла проверку синтаксиса и типов.

## Решение, проект и сборка

Три слова, которые в разговоре заменяют друг друга, означают разные вещи.

**Проект** это единица сборки. Файл с расширением `.csproj` перечисляет настройки: целевую платформу, тип результата, зависимости, версию языка. Компилятор собирает один проект в одну сборку.

**Решение** это контейнер для нескольких проектов. Файл `.sln` хранит их список и связи между ними. Решение не компилируется само по себе, оно говорит инструменту, какие проекты собрать и в каком порядке.

**Сборка** это результат компиляции: файл `.dll` с кодом и, на Windows, небольшой `.exe`, который запускает этот код. Сборка это то, что реально исполняется.

Слово «сборка» уже встречалось в разговоре об архитектуре, где оно означало соединение объектов в точке входа. Здесь речь о другом: сборка это результат компиляции проекта. Контекст различает эти значения, но в разговоре о C# лучше уточнять, о какой сборке идёт речь.

| Понятие | Файл | Что описывает | Сколько в учебном проекте |
|---|---|---|---|
| Решение | `sklad-plus.sln` | набор проектов | одно |
| Проект | `SkladPlus.App.csproj` | одну сборку и её настройки | два |
| Сборка | `SkladPlus.App.dll` | готовый код для запуска | по одной на проект |

Файл проекта у консольного приложения выглядит так:

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>
</Project>
```

Строка `Sdk` подключает стандартный набор правил сборки, поэтому в файле нет списка исходников: компилятор сам берёт все файлы `.cs` из каталога проекта. `OutputType` со значением `Exe` означает консольное приложение, для библиотеки здесь стояло бы `Library` или строки не было бы вовсе. `TargetFramework` задаёт версию платформы, в учебном проекте это `net10.0`. `ImplicitUsings` добавляет частые пространства имён без отдельных строк `using`. `Nullable` включает проверку на возможное отсутствие значения.

Строка `TargetFramework` выглядит технической, но означает срок жизни проекта. Платформа .NET 10 вышла в ноябре 2025 года и относится к долгосрочной поддержке: обновления безопасности выходят три года, до ноября 2028. Платформы с короткой поддержкой живут два года. Если проект остаётся на версии, у которой закончилась поддержка, он продолжает собираться, но перестаёт получать исправления безопасности. Поэтому версию платформы выбирают не только по возможностям, но и по сроку сопровождения.

Зачем решению несколько проектов, если программа одна? Потому что части программы меняются с разной скоростью. Расчёты хранения нужны и консольному приложению, и будущему API, и проверкам. Их выносят в отдельный проект библиотеки, а приложение подключает его ссылкой после создания обоих проектов:

```bash
dotnet add src/SkladPlus.App reference src/SkladPlus.Storage
```

После этой команды приложение видит типы из библиотеки, а сама библиотека не знает, кто её использует. Такая связь в одну сторону позволяет заменить консольный интерфейс на веб-сервис, не переписывая расчёты. Если бы библиотека ссылалась на приложение, получилась бы циклическая зависимость, и собрать решение не удалось бы.

У ссылки на проект есть альтернатива: ссылка на пакет NuGet. Пакет удобен, когда библиотека версионируется отдельно и используется в нескольких решениях. Ссылка на проект удобна, когда код меняется вместе с приложением. Смешивать их без причины не стоит: пакет требует публикации и версии, проект требует, чтобы оба каталога были рядом при сборке.

### Восстановление зависимостей

Перед сборкой выполняется восстановление. Инструмент читает файл проекта, находит ссылки на пакеты, проверяет локальный кэш и при необходимости скачивает недостающее. Результат записывается в `obj/project.assets.json`: какие пакеты, каких версий и откуда взяты. Этот файл не редактируют руками, он производный.

Восстановление объясняет ошибку, знакомую новичкам: «проект не собирается, потому что не найден пакет». Причины бывают разные: нет доступа к сети, неверный источник пакетов, опечатка в имени, конфликт версий. Команда `dotnet restore` выполняет только этот этап и показывает, что именно не удалось. Иногда полезно очистить кэш, но чаще достаточно прочитать сообщение до конца.

Для повторяемости в проект добавляют файл блокировки `packages.lock.json`. Он фиксирует точное дерево зависимостей, включая транзитивные. Без него две машины могут получить разные версии косвенных пакетов и собрать разные программы из одного исходника. Для учебного проекта это необязательно, для промышленного обязательно.

## Что создаёт шаблон

Проект удобнее начать с шаблона, чем с пустого файла. Шаблон создаёт файл проекта, точку входа и служебные каталоги, которые нужны инструментам.

```bash
dotnet new sln -n sklad-plus
dotnet new console -o src/SkladPlus.App
dotnet new classlib -o src/SkladPlus.Storage
dotnet sln add src/SkladPlus.App src/SkladPlus.Storage
```

Первая команда создаёт файл решения `sklad-plus.sln`. Вторая создаёт консольный проект в каталоге `src/SkladPlus.App`. Третья создаёт проект библиотеки, четвёртая добавляет оба проекта в решение.

После этого структура выглядит так:

```text
sklad-plus/
  sklad-plus.sln
  src/
    SkladPlus.App/
      SkladPlus.App.csproj
      Program.cs
      bin/
      obj/
    SkladPlus.Storage/
      SkladPlus.Storage.csproj
      Class1.cs
      bin/
      obj/
```

Файл `Program.cs` после создания содержит строку вывода, а в некоторых версиях шаблона ещё и комментарий со ссылкой на справку:

```csharp
Console.WriteLine("Hello, World!");
```

Это не привычная программа с классом и методом. Начиная с C# 9 разрешены так называемые операторы верхнего уровня: компилятор сам заворачивает их в метод `Main` и создаёт класс. Такой файл короче, но у него есть ограничения: операторы верхнего уровня допустимы только в одном файле проекта, и объявления типов должны идти после них.

Каталог `obj` хранит промежуточные файлы: список восстановленных пакетов, сгенерированные файлы сборки, кеш компилятора. Каталог `bin` хранит готовый результат: сборку, файл запуска и копии зависимостей. Оба каталога создаются автоматически и не хранятся в Git. Править файлы внутри них бессмысленно: при следующей сборке они будут перезаписаны.

Первая сборка выполняется командой:

```bash
dotnet build
```

Она проходит по решению, собирает оба проекта и складывает результат в `src/SkladPlus.App/bin/Debug/net10.0/`. Там появляются `SkladPlus.App.dll` и файл запуска `SkladPlus.App.exe`. Запуск без сборки вручную делает другая команда:

```bash
dotnet run --project src/SkladPlus.App
```

Она сначала проверяет, изменились ли файлы, при необходимости собирает проект и только потом запускает сборку. Ключ `--project` обязателен, когда в решении несколько проектов: иначе инструмент не знает, какой из них запускать. Если сборка уже выполнена и нужно только запустить её, добавляют `--no-build`.

## Точка входа и пространство имён

У программы должен быть вход. В Python его роль играет условие `if __name__ == "__main__":`, в C# компилятор ищет метод `Main` с особой подписью. Тот же код можно записать явно, с классом и методом `Main`; так делают в старых проектах и когда точку входа нужно указать по имени класса.

```csharp
using System;

namespace SkladPlus.App
{
    class Program
    {
        static void Main(string[] args)
        {
            Console.WriteLine("Склад+ : проверка среды");
        }
    }
}
```

Метод `Main` объявлен статическим, потому что объект класса для запуска ещё не создан. Он может возвращать `void` или `int`, а параметр `string[] args` получает аргументы командной строки. Компилятор допускает ровно одну точку входа: два метода `Main` в разных классах дают ошибку `CS0017`, и тогда нужный класс указывают в параметре `StartupObject` файла проекта.

Пространство имён это адрес, по которому живут типы. Класс `Storage` из проекта библиотеки объявлен в пространстве `SkladPlus.Storage`, и приложение обращается к нему по полному имени или через `using`. Пространства имён не связаны с каталогами жёстко, но по соглашению совпадают с ними: так проще искать нужный файл.

В проекте библиотеки файл `Class1.cs` переименовывают в `Storage.cs` и заполняют расчётами:

```csharp
using System;

namespace SkladPlus.Storage
{
    public static class Storage
    {
        public const double PalletVolumeM3 = 1.44;

        public static double BoxVolume(double lengthCm, double widthCm, double heightCm)
        {
            return lengthCm * widthCm * heightCm / 1_000_000;
        }

        public static int PalletsNeeded(double totalVolumeM3)
        {
            return (int)Math.Ceiling(totalVolumeM3 / PalletVolumeM3);
        }
    }
}
```

Класс объявлен статическим, потому что ему не нужны объекты: методы принимают все данные параметрами и возвращают результат. Приложение обращается к ним по имени класса.

```csharp
using SkladPlus.Storage;

namespace SkladPlus.App
{
    class Program
    {
        static void Main(string[] args)
        {
            double volume = Storage.BoxVolume(40, 30, 25) * 24;
            Console.WriteLine($"Объём: {volume:0.###} м3");
            Console.WriteLine($"Паллет: {Storage.PalletsNeeded(volume)}");
        }
    }
}
```

Вывод на русской локали:

```text
Объём: 0,72 м3
Паллет: 1
```

Строка `using SkladPlus.Storage;` позволяет писать `Storage` вместо `SkladPlus.Storage.Storage`. Если убрать её, компилятор сообщит `CS0246`: тип не найден. Сама библиотека при этом собирается нормально, ошибка относится к приложению, которое не подключило ссылку или не импортировало пространство имён.

Есть ещё одна тонкость. Одинаковое короткое имя в двух пространствах имён приводит к неоднозначности. Компилятор не угадывает, какой тип имелся в виду, и требует полное имя или псевдоним `using`. Это не придирка: неоднозначность обнаруживается при сборке, а не в момент, когда пользователь нажал кнопку.

## Цикл работы в Visual Studio 2022

Visual Studio это не редактор с подсветкой, а среда сборки и отладки. Она показывает не только файлы, но и структуру решения, потому что именно эта структура определяет, что и как будет собрано.

При создании проекта выбирают шаблон `Console App`, версию платформы `net10.0`, имя проекта и расположение. Среда создаёт решение, проект и файл `Program.cs`, после чего проект можно запускать. Версия Visual Studio 2022, начиная с 17.0, является 64-битной. Это изменение сделано ради больших решений: 32-битный процесс ограничен адресным пространством, и на крупных проектах среда упиралась в память ещё до того, как заканчивала загрузку.

Окно `Solution Explorer` показывает решение, проекты, зависимости и файлы. Двойной щелчок по файлу открывает его в редакторе. Если проект не собирается, причина чаще всего видна в окне `Error List`: строка с номером ошибки и файлом, двойной щелчок ведёт к месту в коде. Полезно читать не только текст, но и код ошибки: по коду быстрее находится причина.

Запуск с отладкой выполняется клавишей F5, запуск без отладки сочетанием Ctrl+F5. Разница не только в скорости. С отладкой среда останавливается на точках останова, показывает значения переменных и позволяет выполнять код по шагам. Без отладки программа просто работает, а после завершения Visual Studio оставляет окно консоли открытым до нажатия клавиши, тогда как при запуске с отладкой оно закрывается сразу.

Точка останова ставится щелчком на левом поле строки или клавишей F9. Когда выполнение доходит до неё, программа приостанавливается. В окне `Locals` видны переменные текущего метода, в `Watch` можно добавить выражение и следить за ним, в `Call Stack` виден путь вызовов. Шаг с обходом выполняется клавишей F10, шаг с заходом в функцию клавишей F11.

| Действие | Клавиши | Что происходит |
|---|---|---|
| Собрать решение | Ctrl+Shift+B | компиляция без запуска |
| Запустить с отладкой | F5 | сборка, запуск, остановка на точках |
| Запустить без отладки | Ctrl+F5 | сборка и запуск |
| Поставить точку останова | F9 | остановка на выбранной строке |
| Шаг с обходом | F10 | следующая строка без захода в функцию |
| Шаг с заходом | F11 | переход внутрь вызываемой функции |

Сборка из меню `Build` собирает решение целиком. Внизу открывается окно `Output` с итогом: число проектов, предупреждения и ошибки. Предупреждения не мешают запуску, но показывают места, где компилятор сомневается: неиспользуемая переменная, возможное отсутствие значения, устаревший метод. Если предупреждений сотни, их перестают читать, поэтому в проекте полезно включать режим, при котором важные предупреждения становятся ошибками.

Команда `Rebuild` отличается от `Build`. `Build` выполняет инкрементальную сборку и пропускает проекты, которые не изменились. `Rebuild` сначала очищает результат, затем собирает заново. Если после правки кажется, что запускается старый код, помогает `Clean` и повторная сборка, но чаще причина в другом: запускается файл из `Debug`, а собран `Release`.

Инкрементальная сборка опирается на входы и выходы: исходные файлы, ссылки, настройки и время изменения. Если выходной файл новее входных, MSBuild считает проект актуальным и пропускает компиляцию. Иногда это правило ошибается: часы на машине переведены назад, файл восстановлен из архива с сохранением старой даты, генератор не обновил промежуточный файл. Тогда сборка честно сообщает, что всё готово, а программа остаётся прежней. Принудительная сборка выполняется ключом `--no-incremental` или командой `Rebuild`.

У сборки две конфигурации. `Debug` содержит отладочные символы и не оптимизирует код, поэтому в ней удобно искать ошибки. `Release` убирает отладочную информацию и включает оптимизации, её используют для передачи пользователю. Файлы двух конфигураций лежат в разных каталогах: `bin/Debug` и `bin/Release`.

Разница не только в размере. Оптимизация может переставить инструкции, встроить короткий метод в вызывающий код и убрать переменную, которая ни на что не влияет. Поэтому отладка в `Release` иногда показывает не те значения, которые ожидались: код делает то же самое, но не в том порядке, в котором написаны строки. Для поиска дефекта собирают `Debug`, а `Release` проверяют отдельно, ближе к выпуску.

::figure debug-release | Две конфигурации сборки: Debug и Release. Схема показывает, где лежат файлы, что происходит с символами и оптимизацией и почему отладка Release может вести себя иначе.

## Команды CLI

Visual Studio удобна, но не всегда доступна. На сервере, в контейнере и в сценарии сборки те же действия выполняет интерфейс командной строки `dotnet`. Он входит в состав SDK и работает одинаково на разных платформах.

| Команда | Что делает | Когда нужна |
|---|---|---|
| `dotnet --info` | показывает версии SDK и среды | проверить окружение |
| `dotnet new console` | создаёт проект из шаблона | начать новый проект |
| `dotnet build` | собирает решение или проект | проверить компиляцию |
| `dotnet run` | собирает и запускает | обычный запуск при разработке |
| `dotnet clean` | удаляет результат сборки | убрать старые файлы |
| `dotnet publish` | готовит сборку для передачи | выпуск на другой машине |

Команда `dotnet build` не запускает программу, а `dotnet run` запускает. Если нужно выполнить уже собранную сборку без исходного кода, её запускают через среду:

```bash
dotnet src/SkladPlus.App/bin/Release/net10.0/SkladPlus.App.dll
```

Публикация отличается от обычной сборки. `dotnet publish -c Release` собирает проект и складывает в отдельную папку всё, что нужно для запуска: сборку, зависимости, файл настроек. Для машины без установленного SDK этого достаточно, если среда исполнения на ней есть. Для машины без среды исполнения используют самодостаточную публикацию, а для быстрого старта и минимального набора файлов нативную компиляцию.

```bash
dotnet publish src/SkladPlus.App -c Release -o publish
dotnet publish src/SkladPlus.App -c Release -r win-x64 --self-contained true
```

Первый вариант требует установленной среды исполнения на целевой машине. Второй включает среду в папку публикации и поэтому весит больше. Третий вариант, нативная компиляция, убирает JIT и часть динамических возможностей, зато запускается быстрее и не требует отдельной среды. Выбор зависит от того, кто и как будет запускать программу.

В командах есть разделитель аргументов. Всё, что стоит после `--`, передаётся самой программе, а не инструменту:

```bash
dotnet run --project src/SkladPlus.App -- --site Тула
```

Без разделителя `--site` попытается разобрать `dotnet run` и завершится ошибкой. Это частая причина путаницы при запуске консольных программ с параметрами.

Версию SDK можно зафиксировать файлом `global.json`. Если на машине несколько SDK, файл говорит, какой выбрать, и не даёт сборке незаметно перейти на новую версию. Для учебного проекта это полезно, когда преподаватель и студент работают на разных машинах.

```bash
dotnet new globaljson --sdk-version 10.0.100 --roll-forward latestPatch
```

Ключ `roll-forward` разрешает взять более новый патч, но не меняет мажорную версию. Политика обновления это компромисс: строгая фиксация даёт воспроизводимость, но требует ручного обновления; свободная даёт свежие исправления, но может неожиданно сломать сборку.

Для сценариев сборки важен код возврата. Успешная команда завершается нулём, ошибка даёт ненулевой код. Конвейер непрерывной сборки смотрит именно на код, а не на текст в журнале: если `dotnet build` вернул ненулевое значение, следующие шаги останавливаются. В PowerShell код последней команды лежит в `$LASTEXITCODE`, и его полезно проверять в своих скриптах. Команда `dotnet test` тоже возвращает ненулевой код, если хотя бы один тест не прошёл, поэтому её можно ставить отдельным шагом без разбора вывода.

::gate Почему ошибка типов в C# видна до запуска, а в Python только во время выполнения?

## Одна задача на двух языках

Вернёмся к расчёту паллет. На Python программа выглядит так:

```python
import math

PALLET_VOLUME_M3 = 1.44
volume = 3.852
pallets = math.ceil(volume / PALLET_VOLUME_M3)

print(f"Объём: {volume} м3")
print(f"Паллет: {pallets}")
```

Вывод:

```text
Объём: 3.852 м3
Паллет: 3
```

Та же задача на C#:

```csharp
using System;

namespace SkladPlus.App
{
    class Program
    {
        static void Main(string[] args)
        {
            const double palletVolumeM3 = 1.44;
            double volume = 3.852;
            int pallets = (int)Math.Ceiling(volume / palletVolumeM3);

            Console.WriteLine($"Объём: {volume} м3");
            Console.WriteLine($"Паллет: {pallets}");
        }
    }
}
```

Вывод на русской локали:

```text
Объём: 3,852 м3
Паллет: 3
```

Число одно и то же, а разделитель дробной части при выводе разный. В исходном коде оба языка пишут дробную часть через точку, но C# при печати числа использует настройки системы: на русской локали это запятая, а Python всегда печатает точку. Для учебных примеров это мелочь, для обмена данными с внешними системами это причина ошибок, поэтому форматирование чисел разберут отдельно.

| Признак | Python | C# |
|---|---|---|
| Что запускается | файл `.py` | сборка `.dll` |
| Когда проверяются типы | во время выполнения | во время сборки |
| Точка входа | условие `if __name__ == "__main__"` | метод `Main` или операторы верхнего уровня |
| Зависимости | `pip` и виртуальное окружение | NuGet и файл проекта |
| Результат сборки | отсутствует | файл в `bin` |
| Инструмент | VS Code | Visual Studio 2022, CLI |
| Цена правки | сохранить и запустить | сохранить, собрать, запустить |

Разница в проверке типов объясняет, почему один и тот же код ведёт себя по-разному. В Python выражение с делением дойдёт до выполнения и упадёт с `TypeError` только тогда, когда очередь дойдёт до него. В C# компилятор увидит несовпадение типов заранее и не соберёт проект. Это не делает C# безопаснее во всём: ошибки логики и неверные данные он тоже не поймает. Он лишь переносит часть проверок из времени работы во время сборки.

У этого различия есть практическое следствие для перевода кода. Программа на Python может содержать функцию, которая никогда не вызывается с плохим аргументом, и ошибка в ней не проявится. При переводе на C# та же функция обязана иметь объявленные типы, и компилятор проверит все её ветки. Перевод становится не копированием строк, а уточнением контракта: что именно принимает функция и что возвращает.

## Реальные случаи: версия, зависимости, инструмент

### Проект, который остался на неподдерживаемой платформе

Платформа .NET развивается предсказуемым графиком. Версии с долгосрочной поддержкой получают исправления три года, версии со стандартной поддержкой два года. .NET Core 3.1 относилась к долгосрочной поддержке и завершила её 13 декабря 2022 года. После этой даты сборка продолжает работать, но обновления безопасности для неё не выпускаются.

Для проекта это означает не мгновенную поломку, а накопление риска. Библиотеки постепенно требуют более новую платформу, инструменты перестают поддерживать старую версию, а уязвимости остаются без исправлений. Компилятор предупреждает о неподдерживаемой целевой платформе кодом `NETSDK1138`, но предупреждение легко пропустить среди других.

Урок для «Склад+» простой: `TargetFramework` это не только техническая настройка, но и дата, до которой проект будет получать исправления. Версию платформы фиксируют осознанно и включают в план обновления, а не оставляют на последний день.

### Пакет, который исчез из неявных зависимостей

В .NET Core 2.x веб-проект мог подключить метапакет `Microsoft.AspNetCore.All`, который тянул за собой десятки библиотек. В .NET Core 3.0 этот метапакет перестали выпускать, а вместе с ним исчезли многие отдельные пакеты, которые входили в общий набор. Проекты, которые полагались на неявную зависимость, перестали собираться после обновления платформы.

Официальное руководство по переходу предлагает другое устройство: общая платформа ASP.NET Core содержит основные библиотеки, а всё, что выходит за её пределы, подключается явной ссылкой `PackageReference`. Явная ссылка длиннее, но она называет зависимость и её версию. При обновлении видно, что именно меняется, а не «магия, которая работала раньше».

Урок для темы: неявные зависимости удобны, пока платформа не изменит правило. Файл проекта должен честно перечислять то, что нужно программе. Тогда обновление становится работой с понятным списком, а не поиском исчезнувшего пакета.

### Среда, которая перестала помещаться в память

Visual Studio 2022 стала первой 64-битной версией среды. До этого 32-битный процесс был ограничен адресным пространством, и большие решения с сотнями проектов могли не загружаться полностью. Переход на 64 бита не ускорил каждую операцию, но снял потолок, из-за которого среда падала или работала нестабильно на крупных решениях.

Для учебного проекта это не критично: два проекта и десяток файлов помещаются в любую среду. Но случай показывает, что инструмент тоже имеет ограничения, и они проявляются на масштабе. Если среда ведёт себя странно на большом решении, полезно проверить не только код, но и версию инструмента, объём памяти и архитектуру процесса.

| Случай | Что сломалось | Чему учит |
|---|---|---|
| .NET Core 3.1 | закончилась поддержка | версия платформы имеет срок |
| метапакет ASP.NET Core | зависимость стала неявной | зависимости перечисляют явно |
| Visual Studio 2022 | 32-битный предел памяти | инструмент ограничен масштабом |

## Типичные ошибки

Ошибки сборки отличаются от ошибок выполнения тем, что программа ещё не запустилась. Ниже те, что встречаются чаще всего.

1. `CS0103: The name 'volume' does not exist in the current context`. Переменная объявлена в другом методе или написана с другой буквой. Область видимости ограничена блоком, поэтому значение из соседней функции недоступно.
2. `CS1002: ; expected`. Пропущена точка с запятой в конце оператора. Компилятор указывает на следующую строку, потому что замечает проблему только там.
3. `CS0029: Cannot implicitly convert type 'double' to 'int'`. Результат деления дробный, а переменная целая. Нужно явное приведение или другой тип.
4. `CS0017: Program has more than one entry point defined`. В проекте два метода `Main` или файл с операторами верхнего уровня соседствует с классом, у которого есть `Main`.
5. `NETSDK1045`: установленный SDK не поддерживает целевую платформу `net10.0`. Проект создан для более новой версии, чем та, что стоит на машине.
6. `NETSDK1138`: целевая платформа больше не поддерживается. Проект собирается, но обновления безопасности не получает.
7. `MSB1011`: в текущем каталоге несколько проектов или решений, и инструмент не знает, какой использовать. Помогает явно указать проект: `dotnet run --project ...` или путь к файлу проекта в `dotnet build`.
8. Запуск устаревшей сборки. Программа собрана в `Release`, а запускается файл из `bin/Debug`, или наоборот. Сначала смотрят путь, потом ищут ошибку в коде.
9. Правка файлов в `bin` или `obj`. Следующая сборка перезапишет изменения, и код снова станет прежним.
10. Запуск без аргумента `--`. Параметр программы пытается разобрать инструмент и завершается ошибкой.

Отдельная ошибка не в коде, а в привычке: искать причину в тексте программы, когда сообщение говорит о ссылке на проект или о версии SDK. Полезно читать не только текст ошибки, но и её код: по коду быстрее находится причина и решение.

## Цена и выгода

Сборка добавляет шаг и требует дисциплины: файлы должны лежать в проекте, ссылки должны быть объявлены, версия платформы должна совпадать. Взамен разработчик получает раннюю проверку типов, повторяемую сборку и возможность передать программу без исходного кода.

| Что даёт сборка | Чем приходится платить |
|---|---|
| Ошибки типов до запуска | время на компиляцию |
| Одинаковый результат на разных машинах | хранение и передача сборок |
| Явные зависимости проекта | ведение файла проекта |
| Отладка по исходному коду | размер инструментов |

Для учебного проекта выгода очевидна: расчёты отделяются от интерфейса, а будущий API сможет использовать ту же библиотеку. Для маленького скрипта на десять строк сборка избыточна, и Python здесь выигрывает. Выбор языка определяется задачей, а не привычкой.

## Итоги

- C# исполняет сборку, а не исходный файл, поэтому между правкой и запуском есть этап сборки.
- Проект это единица сборки, решение это контейнер проектов, сборка это готовый файл `.dll`.
- Файл `.csproj` задаёт тип результата, целевую платформу и зависимости.
- Шаблон `dotnet new console` создаёт проект, `dotnet build` собирает, `dotnet run` собирает и запускает.
- Точка входа это метод `Main` или операторы верхнего уровня, и она должна быть одна.
- Visual Studio показывает решение целиком, потому что от него зависит сборка, а не только редактирование файла.
- Debug и Release различаются символами и оптимизацией, поэтому отладку ведут в Debug.
- Целевая платформа и явные зависимости определяют срок жизни и воспроизводимость проекта.

- Решение и проект это одно и то же

- Список исходных файлов

- В папке docs

Q: Что означает ошибка CS0029?
+ Нельзя неявно преобразовать один тип в другой
- Пропущена точка с запятой
- В проекте две точки входа
- Не найдено пространство имён
! Компилятор требует явного преобразования, если типы несовместимы.

Q: Зачем в решении отдельный проект библиотеки?

- Чтобы заменить файл решения
- Чтобы хранить настройки Visual Studio

- С отладкой программа работает быстрее
- Без отладки нельзя собрать проект
- Без отладки программа не выводит текст в консоль

- Добавляет проект в решение
