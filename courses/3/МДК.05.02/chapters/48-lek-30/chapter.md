## Администратор, который не смог запустить сервис

В Калуге сменился администратор информационной системы. В первый день ему нужно было поднять «Склад+» на новой машине. В репозитории лежал README из трёх строк: «Установите зависимости. Запустите приложение. База создастся сама». Администратор установил зависимости, запустил команду и получил ошибку о том, что порт занят.

Он потратил три часа. Сначала искал, какой порт нужен: в коде было 8000, в старой инструкции 5000, в настройках сервера 8080. Потом выяснилось, что база не создаётся сама, а должна лежать в каталоге `data`. Потом не хватило прав на запись журнала. В итоге он позвонил в поддержку, и инженер за десять минут объяснил то, чего не было в документе.

В «Северном складе» 120 сотрудников на четырёх площадках. Служба поддержки принимает около 34 обращений в неделю, и часть из них начинается с вопроса «как запустить», «как обновить», «где взять адрес API». Каждый такой вопрос стоит времени и инженера, и пользователя. Документация сокращает эти обращения не потому, что она красивая, а потому, что человек находит ответ без звонка. Если ответ на частый вопрос есть в документе, инженер не повторяет его в двадцатый раз, а занимается сбоями. Это экономит часы поддержки каждую рабочую неделю.

**Документ это инструмент для конкретного читателя, который решает конкретную задачу.** У документа есть адресат, задача и признак успеха. Если после чтения читатель не смог выполнить действие, документ не выполнил работу, даже если в нём много страниц и красивых схем.

У этого определения есть неприятное следствие. Документ нельзя оценить по объёму, по числу разделов или по тому, что он «есть». Его оценивают по действию читателя: поднялся ли сервис, отправлен ли запрос, восстановлена ли база. Поэтому документацию проверяют так же, как код: запуском на чистом окружении и сравнением результата с ожидаемым.

Документ отличается от заметки и от пересказа кода. Заметка помогает автору вспомнить, что он делал. Документ помогает другому человеку сделать то, чего он не делал. Пересказ кода описывает, из каких функций состоит программа, но не отвечает, зачем она нужна и что делать, когда она не работает. Полезный документ всегда отвечает на вопрос читателя, а не на вопрос автора.

Есть ещё одна граница, которую стоит держать в голове. Документация не заменяет обучение, но и обучение не заменяет документацию. На занятии можно показать порядок действий, однако через месяц человек забудет половину. Документ остаётся, и к нему возвращаются в момент, когда нужно выполнить редкую операцию: восстановить базу, сменить ключ, подключить новую площадку.

## Кому и зачем нужен документ

Документация проекта не является одним файлом. Это набор документов, и у каждого свой читатель. Кладовщику нужно принять товар, менеджеру сформировать накладную, администратору запустить сервис, разработчику понять, как устроен модуль, а службе поддержки разобраться с ошибкой. Один текст не может ответить всем сразу.

| Документ | Читатель | Вопрос читателя | Признак успеха |
|---|---|---|---|
| README | разработчик, администратор | как установить и запустить | проект запущен по шагам |
| Руководство пользователя | кладовщик, менеджер | как выполнить операцию | операция выполнена |
| Руководство администратора | администратор ИС | как обновить и восстановить | сервис работает после обновления |
| Описание API | разработчик интеграции | как отправить запрос | получен ожидаемый ответ |
| Архитектурная записка | разработчик, аналитик | почему сделано так | решение понятно и проверяемо |
| Журнал изменений | заказчик, поддержка | что изменилось в версии | понятно, что проверять |

README отвечает на вопрос «как поднять проект с нуля». Руководство пользователя отвечает на вопрос «как выполнить рабочую операцию». Руководство администратора отвечает на вопрос «как обслуживать систему». Описание API отвечает на вопрос «как вызвать функцию из другой программы». Архитектурная записка объясняет решения, а журнал изменений сообщает, что поменялось между версиями.

Разделение нужно не для порядка в папках. У документов разный срок жизни и разный способ проверки. README проверяют запуском на чистой машине. Руководство пользователя проверяют, дав его человеку, который не знает систему. Описание API проверяют запросами из Postman. Архитектурную записку проверяют на соответствие коду и принятым решениям.

| Читатель | Что ему нужно | Что ему не нужно |
|---|---|---|
| Кладовщик | шаги приёмки, сообщения об ошибках | схема базы и код модуля |
| Менеджер | формирование накладной, отчёты | настройки сервера |
| Администратор | запуск, обновление, копии, права | внутреннее устройство классов |
| Разработчик | структура кода, API, тесты | инструкция по приёмке товара |
| Поддержка | коды ошибок, журналы, эскалация | маркетинговое описание продукта |

Попытка написать «общую документацию для всех» заканчивается текстом, который не помогает никому. Кладовщик тонет в терминах `SQLite` и `WSGI`, администратор ищет команду среди описания бизнес-процессов, разработчик не находит структуру модулей. Поэтому документы разделяют по читателю, а не по типам файлов.

Разделение не означает, что документы не связаны. README ссылается на руководство администратора, руководство пользователя ссылается на описание API, журнал изменений ссылается на версию. Ссылки должны работать, а версии совпадать. Если README описывает версию 1.0.0, а руководство 0.9, читатель не поймёт, какая команда правильная.

У каждого документа есть владелец. Обычно это роль, а не человек: README ведёт разработчик, руководство пользователя аналитик или методист, описание API разработчик вместе с интегратором. Владелец обновляет документ при изменении поведения и отвечает на замечания. Без владельца документ устаревает через месяц после выпуска.

Перед написанием полезно описать читателя конкретно, а не словами «пользователи системы». Помогают четыре вопроса. Что человек уже знает: видел ли он интерфейс, знаком ли с терминами. В какой ситуации читает: спокойно изучает систему или стоит у стеллажа с накладной в руках. Что ему нужно сделать сразу после чтения. Что будет, если он ошибётся. Ответы меняют тон и объём текста сильнее, чем любой шаблон.

Ситуация чтения влияет на форму. Инструкция для склада должна открываться на телефоне, иметь короткие шаги и не требовать прокрутки на два экрана. Руководство администратора читают за рабочим столом, и в нём уместны таблицы и длинные команды. Описание API читают в редакторе кода, поэтому примеры важнее абзацев. Один и тот же материал, свёрстанный без учёта ситуации, теряет половину пользы.

Документация входит в результат проекта, а не прикладывается к нему в конце. На приёмке заказчик проверяет не только работающее приложение, но и то, сможет ли сотрудник заказчика выполнить операцию без разработчика. Если руководство появилось за день до сдачи, его никто не проверял на чистом окружении, и первые вопросы пользователей станут первыми дефектами документа.

## Четыре вида документации

Форма документа следует из задачи читателя. Эту мысль подробно разбирает подход Diátaxis, который делит документацию на четыре вида: обучающие материалы, инструкции по задаче, справочник и объяснение [Diátaxis](https://diataxis.fr/). Деление полезно тем, что не даёт смешать в одном тексте обучение, команды и рассуждения.

| Вид | Задача читателя | Пример для «Склада+» | Проверка |
|---|---|---|---|
| Обучающий материал | освоить систему с нуля | первая приёмка товара по шагам | новичок прошёл сценарий |
| Инструкция | решить конкретную задачу | как восстановить базу из копии | задача выполнена по шагам |
| Справочник | найти точное значение | поля ответа API, коды ошибок | значение совпало с системой |
| Объяснение | понять причину решения | почему резерв хранится отдельно | читатель может объяснить выбор |

Обучающий материал ведёт за руку и не стыдится повторений. Инструкция предполагает, что читатель уже знает основы, и даёт короткий путь к цели. Справочник не учит и не объясняет, он перечисляет факты в предсказуемом порядке. Объяснение отвечает на «почему», а не на «как», и не содержит пошаговых команд.

Смешение видов создаёт знакомый дефект. В инструкцию по восстановлению базы вставляют три абзаца истории о том, почему выбрали PostgreSQL, и читатель в аварийной ситуации пролистывает их, теряя время. В справочник API добавляют учебный пример на полстраницы, и опытный интегратор не может быстро найти формат ошибки. В обучающий материал вставляют полный список параметров, и новичок пугается объёма.

Подход Diátaxis это карта, а не закон. В реальном проекте документы часто совмещают задачи: README содержит и обучение, и инструкцию, и короткий справочник настроек. Важно не то, сколько видов в одном файле, а то, что читатель понимает, в каком режиме он находится. Заголовок «Установка» обещает инструкцию, а не рассуждение о выборе библиотек.

::figure doc-quadrants | Четыре вида документации и их проверка. Нажмите квадрант: появится пример для «Склада+», признак хорошего текста и типичная ошибка смешения. Сравните задачу читателя с формой документа.

У каждого вида есть своя цена ошибки. Плохая инструкция останавливает работу, плохой справочник приводит к неверному запросу, плохое объяснение возвращает старый спор. Поэтому вид выбирают до написания, а не после: от него зависит, что считать полнотой.

## Инструкция, которую можно выполнить

Инструкция состоит из предусловий, шагов, ожидаемого результата каждого шага, раздела ошибок и проверки в конце. Предусловия сообщают, что должно быть готово до начала: версия Python, доступ к базе, свободный порт, права на каталог. Шаги описывают действие, а не намерение. Ожидаемый результат позволяет понять, что шаг выполнен, не заглядывая в следующий.

Плохой шаг звучит так: «Настройте базу данных». Что именно настроить, где, с какими правами и как понять, что получилось, неизвестно. Хороший шаг называет действие и результат: «Создайте каталог `data` командой `mkdir data`. Ожидаемый результат: каталог существует и доступен на запись пользователю службы».

| Признак плохого шага | Признак хорошего шага |
|---|---|
| «Настройте окружение» | «Создайте окружение командой `python -m venv .venv`» |
| «Запустите сервис» | «Выполните `.venv/bin/python -m sklad_plus.api`, дождитесь строки `Running on`» |
| «Проверьте работу» | «Отправьте запрос `/api/health`, ожидайте код 200 и `positions` 4800» |
| «При необходимости поправьте» | «Если порт занят, измените `SKLAD_API_PORT` и перезапустите службу» |

В инструкции не должно быть формулировок «интуитивно понятно», «как обычно», «по необходимости». Они перекладывают решение на читателя, а читатель пришёл за готовым порядком. Если выбор действительно нужен, опишите условие выбора и два варианта: «если база уже есть, перейдите к шагу 5; если нет, выполните шаг 4».

Команды должны быть готовы к копированию. Место, куда подставляют значение, обозначают явно: `python -m pip install dist/sklad_plus-1.0.0-py3-none-any.whl`. Если имя файла зависит от версии, скажите, где её взять. Не оставляйте в команде уголки и многоточия без пояснения: читатель скопирует их буквально.

Предупреждения ставят перед опасным шагом, а не после. Удаление базы, смена прав, остановка службы и миграция могут привести к потере данных. Перед таким шагом указывают, что будет потеряно, как сделать копию и как отменить действие. После шага пишут, как проверить результат.

Снимки экрана помогают, если на них видно то, о чём говорит текст. К снимку добавляют подпись: что именно смотреть. Снимок окна без адреса, команды и кода ответа не подтверждает проверку. Если интерфейс меняется, снимок устаревает быстрее текста, поэтому команды и текстовые шаги остаются основой.

::figure instruction-anatomy | Устройство инструкции: предусловия, шаги с ожидаемым результатом, ошибки, проверка и откат. Справа показан короткий пример для запуска «Склада+». Найдите место, где инструкция отвечает на вопрос «как понять, что шаг выполнен».

У инструкции должен быть конец. После последнего шага читатель проверяет, что задача решена: сервис отвечает, данные на месте, нужный сценарий проходит. Если инструкция обрывается на команде запуска, читатель не знает, что считать успехом, и либо звонит в поддержку, либо уходит с ощущением, что что-то не так.

Нумерация шагов кажется формальностью, пока инструкция не станет длиннее семи пунктов. Номер позволяет сослаться на конкретное место: «вы остановились на шаге 4». Ветвление оформляют явно: «если база уже есть, перейдите к шагу 5». Шаги, которые можно выполнить в любом порядке, лучше вынести в отдельный список, иначе читатель ищет скрытую зависимость.

Текст инструкции проверяют на длину предложений и на количество действий в одном шаге. Шаг «создайте каталог, скопируйте файл и перезапустите службу» содержит три действия и три способа ошибиться. Если одно из них не сработало, читатель не понимает, какое именно. Дробление на отдельные шаги с ожидаемым результатом стоит нескольких лишних строк и экономит часы разбора.

Откат в инструкции нужен не всегда, но для опасных операций он обязателен. Если шаг меняет структуру базы или удаляет файлы, рядом должно быть описано, как вернуть прежнее состояние. Откат пишут до шага, а не после: в момент ошибки читатель ищет его в панике и не находит.

## README проекта

README это первый документ, который открывает новый человек. Он отвечает на вопросы: что это за проект, на чём написан, что нужно установить, как настроить, как запустить, как проверить и где искать дальше. Хороший README занимает одну-две страницы и не пересказывает весь код.

| Раздел | Что содержит | Проверка |
|---|---|---|
| Название и назначение | что делает `sklad-plus` | понятно за одно предложение |
| Стек | Python, Flask, SQLite, версии | совпадает с проектом |
| Требования | Python 3.11+, свободный порт | перечислены все зависимости |
| Установка | создание окружения и установка | команды выполняются |
| Настройки | `.env.example`, переменные | нет настоящих секретов |
| Запуск | команда и ожидаемый вывод | сервис поднимается |
| Проверка | health check и тесты | код 200, тесты зелёные |
| Структура | каталоги `src`, `tests`, `docs` | совпадает с репозиторием |
| Ошибки | три частых случая | есть признак и действие |

README начинается с назначения, а не с истории компании. «`sklad-plus` это учебная ИС склада с API на Flask и базой SQLite» даёт больше, чем абзац о миссии. Затем идут требования и команды. Секреты в README не приводят: вместо них указывают `.env.example` и объясняют, какие значения заполнить.

Проверка README проста: возьмите чистую машину или новый каталог, выполните только то, что написано, и сравните результат. Если пришлось открывать исходники, чтобы понять команду, README неполон. Если команда работает только после устного пояснения, этого пояснения не хватает в тексте.

У README есть скрытая функция: он проверяет сам проект. Если для запуска нужно вручную создать три каталога и поправить два файла, README это покажет. Иногда после такой проверки исправляют не документ, а сборку: добавляют команду, которая создаёт каталоги, или значение по умолчанию, которое работает без правки. Документ и код исправляются вместе, и это нормальный результат проверки.

## Описание API

Описание API нужно разработчику, который вызывает сервис из другой программы. Ему нужны базовый адрес, способ авторизации, формат данных, список маршрутов, параметры, примеры запроса и ответа, коды ошибок и правила пагинации. Без этого он будет угадывать по коду и тратить время на пробы.

| Что описать | Пример для `sklad-plus` |
|---|---|
| Метод и путь | `GET /api/stock/{sku}` |
| Авторизация | заголовок `Authorization: Bearer <token>` |
| Параметры пути | `sku` это артикул вида `SKU-1042` |
| Параметры запроса | `limit` от 1 до 100, по умолчанию 20 |
| Успешный ответ | код 200, поля `sku`, `title`, `available` |
| Ошибки | 401 без токена, 404 неизвестный артикул, 500 сбой сервера |
| Формат ошибки | `{"error": "not found", "code": "SKU_NOT_FOUND"}` |

Пример запроса лучше давать в виде команды, которую можно скопировать. Пример ответа должен быть настоящим, а не придуманным. Если в описании указано поле `available`, а сервис возвращает `qty`, интеграция сломается на первом же запросе. Примеры проверяют запуском на тестовом стенде, а не переписывают из головы: только тогда описание и поведение совпадают.

Документация API бывает ручной и автоматической. Ручную таблицу пишут в Word или Markdown и проверяют запросами. Автоматическую получают из кода: FastAPI строит OpenAPI-схему по типам и маршрутам, ASP.NET Core показывает Swagger. Автоматическая схема не расходится с кодом, но её всё равно дополняют описаниями и примерами.

Формат OpenAPI описывает маршруты, операции, параметры, тела запросов, ответы, схемы данных и способы безопасности в одном документе [OpenAPI Specification 3.1](https://spec.openapis.org/oas/latest.html). Именно этот формат читают Postman, генераторы клиентов и порталы документации. Поэтому схема, построенная из кода, полезна не только людям: по ней можно сгенерировать коллекцию запросов и проверить, что описание не отстало от реализации.

Проверим, как FastAPI описывает ответы маршрута. В схеме видны коды 200, 404 и 422, а также ссылки на модели данных.

```python
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI(title="Склад+ API", version="1.0.0")

class StockItem(BaseModel):
    sku: str
    title: str
    available: int

@app.get("/api/stock/{sku}", response_model=StockItem, responses={404: {"description": "Товар не найден"}})
def get_stock(sku: str) -> StockItem:
    """Вернуть свободный остаток товара по артикулу."""
    if sku != "SKU-1042":
        raise HTTPException(status_code=404, detail="not found")
    return StockItem(sku=sku, title="Перфоратор", available=30)
```


Схема показывает, что маршрут возвращает модель `StockItem`, а для неизвестного артикула описан код 404. Код 422 появляется автоматически: FastAPI проверяет типы параметров и сообщает об ошибке валидации. Разработчику интеграции этого достаточно, чтобы понять формат и не гадать о кодах.

У описания API есть собственная версия, и она не всегда совпадает с версией приложения. Если маршрут меняет формат ответа, интеграторы должны узнать об этом до выпуска. Поэтому в описании фиксируют, какие поля устарели, до какой версии они поддерживаются и чем заменяются. Пометка «устарело» без даты удаления ничего не говорит: через год никто не помнит, можно ли ещё пользоваться старым полем.

Обратная совместимость в API стоит дороже, чем кажется. Каждое сохранённое старое поле нужно поддерживать, проверять и документировать, а новые клиенты видят два способа сделать одно и то же. Поэтому изменение формата планируют как отдельный выпуск: сначала добавляют новое поле и описывают его, затем переводят клиентов, затем помечают старое устаревшим и только потом удаляют. В описании отражают каждый шаг, иначе интегратор узнаёт об удалении из ошибки 400.

Документация в коде тоже полезна. Строка документации рядом с функцией объясняет смысл, а не пересказывает имя. Соглашения о строках документации в Python описаны в PEP 257: краткое описание в одну строку, затем пустая строка и подробности, если они нужны [PEP 257](https://peps.python.org/pep-0257/).

```python
def available_qty(stock: int, reserved: int) -> int:
    """Вернуть количество товара, доступное к отгрузке.

    :param stock: остаток на складе, не меньше нуля
    :param reserved: зарезервированное количество
    :return: stock - reserved, но не меньше нуля
    :raises ValueError: если stock или reserved отрицательны
    """
    if stock < 0 or reserved < 0:
        raise ValueError("количество не может быть отрицательным")
    return max(stock - reserved, 0)
```

```text
(stock: int, reserved: int) -> int
Вернуть количество товара, доступное к отгрузке.
```

В C# вместо строки документации используют XML-комментарии перед методом: `/// <summary>`, `/// <param>`, `/// <returns>`. При сборке из них получают XML-файл, который подключают к справке или Swagger [документация .NET, XML-комментарии](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/xmldoc/). Смысл тот же: описание стоит рядом с кодом и обновляется вместе с ним.

## Журнал изменений и версии

Журнал изменений ведут отдельно от README. В нём перечисляют версии, даты и изменения так, как их увидит пользователь: «добавлен экспорт накладной в CSV», «исправлена ошибка с занятой ячейкой». Внутренние переименования классов пользователю не нужны. По журналу поддержка понимает, что проверять после обновления, а заказчик видит, за что заплатил.

Формат журнала удобно вести по соглашению Keep a Changelog. Оно предлагает группировать записи по разделам «Добавлено», «Изменено», «Устарело», «Удалено», «Исправлено» и «Безопасность», а версии связывать с семантическим версионированием [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/). Соглашение не является стандартом, но делает журнал предсказуемым: читатель знает, где искать исправление, а где новую возможность.

Версия в журнале должна совпадать с версией артефакта. Если в журнале последняя запись 1.2.0, а на сервере работает 1.1.0, поддержка ищет причину не в той версии. Семантическое версионирование помогает удержать это соответствие: несовместимое изменение повышает старшую часть, новая возможность среднюю, исправление младшую [Semantic Versioning 2.0.0](https://semver.org/).

Журнал пишут для людей, а не для истории Git. Список коммитов содержит служебные сообщения вроде «fix», «wip» и «merge branch», и по нему нельзя понять, что проверить после обновления. Журнал собирают вручную или из размеченных сообщений, но в любом случае редактируют до выпуска: читатель не должен разбирать внутренний язык команды.

## Документация рядом с кодом

Документация живёт в репозитории рядом с кодом. Тогда изменение поведения и изменение описания попадают в один запрос на слияние, а рецензент видит расхождение. Если документация лежит в общем диске или в личной папке, она отстаёт от кода и никто не замечает, когда перестала быть верной.

| Что изменилось | Что обновить | Как проверить |
|---|---|---|
| Новый маршрут API | описание API и коллекцию Postman | запрос возвращает описанный ответ |
| Новый параметр настройки | README и `.env.example` | проект запускается по инструкции |
| Новая роль | руководство пользователя и права | сценарий роли проходит |
| Изменение шага | инструкция и снимок | шаг выполняется на чистой машине |
| Новая версия | журнал изменений | список изменений совпадает с тегами |

Автоматически проверяют то, что можно проверить. Ссылки в документе проверяет сборка сайта, примеры запросов запускают в Postman, команды из README выполняют в конвейере. Полностью автоматическая проверка невозможна: понятность текста оценивает человек. Но механические ошибки ловятся без чтения.

Ревью документа отличается от ревью кода. Рецензент не ищет стилистические придирки, он проверяет три вещи: адресат назван, шаги соответствуют коду, проверка действительно доказывает результат. Если в запросе на слияние изменился маршрут API, а описание осталось прежним, это замечание уровня ошибки, а не пожелание. Такой подход работает только при одном условии: рецензент знает, какой документ считается источником истины.

Единый стиль снижает стоимость правок. Короткий список правил полезнее толстого руководства: как называть команды, как оформлять пути, как писать сообщения об ошибках, где ставить предупреждение. Если правил нет, каждый автор придумывает свой формат, и читатель каждый раз заново привыкает к тексту. Стиль не делает документ правильным, но делает ошибки заметнее.

::figure doc-lifecycle | Круг жизни документа: изменение кода, правка текста, ревью, проверка примеров, выпуск и обращение поддержки. Стрелка возврата показывает, что обращение пользователя становится задачей на изменение. Найдите место, где документ снова становится частью кода.

У документации есть долг, как у кода. Каждый пропущенный шаг, устаревший снимок и неверный код ошибки накапливаются и возвращаются вопросами в поддержку. Долг закрывают небольшими правками при каждом изменении, а не генеральной переписью раз в год. Если документ переписывают целиком, его снова никто не проверяет, и старые ошибки возвращаются вместе с новыми. Владелец документа следит за этим долгом так же, как разработчик следит за дефектами в коде.

Долг удобно измерять по обращениям. Если за месяц 34 обращения повторяют одни и те же вопросы о приёмке, это не проблема пользователей, а пробел в руководстве. Вопросы формулируют словами пользователей, а ответы дают короткий порядок действий и ссылку на полный сценарий. Раздел частых вопросов пересматривают вместе с журналом обращений, иначе он превращается в свалку устаревших советов.

### NHS NPfIT, 2002-2011: требования и приёмка

В 2002 году в Англии начала работу Национальная программа ИТ для здравоохранения, цель которой была единая электронная медицинская карта для пациентов NHS. Программа должна была заменить множество локальных систем централизованными решениями. В 2011 году Национальное аудиторское управление Великобритании проверило результаты.

Вывод оказался жёстким. 2,7 млрд фунтов, потраченных на системы медицинских записей, не дали соразмерной отдачи, а в оставшиеся 4,3 млрд фунтов аудитор не нашёл оснований для уверенности. В северном, центральном и восточном регионах за семь лет в больницы поставили только четыре системы из 97 запланированных. В больницах системы давали в основном административный эффект, а не клинические возможности, ради которых программа начиналась [NAO, 2011](https://www.nao.org.uk/reports/the-national-programme-for-it-in-the-nhs-an-update-on-the-delivery-of-detailed-care-records-systems/).

Для темы документации важна деталь из отчёта. Прогресс оценивали не по исходным детальным требованиям контрактов, а по минимальному уровню функциональности, согласованному с клиницистами в 2008 году. Аудитор отметил, что оценка должна была бы опираться на требования контрактов с учётом клинической пользы и сложности, но такая оценка не проводилась. Иными словами, документ требований и документ приёмки разошлись, и измерить расхождение стало невозможно.

Урок для темы: **если критерий приёмки не записан рядом с требованием, прогресс можно измерить только по удобной шкале**. Минимальный набор функций выглядит успехом, пока никто не сравнил его с тем, что обещали. Документация требований нужна не для отчёта, а для того, чтобы приёмка отвечала на вопрос «сделано ли обещанное», а не «сделано ли хоть что-то».

### GitLab, 2017: разбор как документ

После аварии 31 января 2017 года GitLab опубликовала публичный разбор через десять дней. В нём были хронология событий, пять вопросов «почему» для каждой из двух проблем, список из пятнадцати задач по исправлению и отдельная задача на владельца данных. Компания также описала, что именно не сработало в резервном копировании, и признала, что процедура восстановления реплики не была ни автоматизирована, ни документирована [GitLab, Postmortem of database outage](https://about.gitlab.com/blog/2017/02/10/postmortem-of-database-outage-of-january-31/).

Этот текст интересен как документ, а не только как история. У него есть адресат: будущий инженер, который столкнётся с похожей ситуацией. У него есть задача: объяснить, почему пять механизмов страховки не сработали. У него есть проверяемый результат: задачи с номерами, которые можно закрыть. Разбор также содержит урок о границах публичности: в первом варианте осталось имя инженера, и компания решила в будущем имена скрывать.

Урок для темы: **разбор инцидента это технический документ с адресатом и задачами, а не отчёт о наказании**. Хороший разбор объясняет механизм, называет пробелы в процедурах и заканчивается списком изменений. Плохой ограничивается фразой «человеческий фактор» и не помогает следующему инженеру.

## Проверка документа

Перед публикацией документ проверяют по чек-листу. Главная проверка это прохождение на чистом окружении: читатель, который не участвовал в разработке, выполняет шаги и получает ожидаемый результат. Все места, где он остановился или спросил, становятся задачами на исправление.

| Проверка | Как выполнить | Признак ошибки |
|---|---|---|
| Адресат | назвать читателя и его задачу | документ написан «для всех» |
| Полнота | пройти шаги на чистой машине | нужен устный вопрос |
| Результат шага | сравнить с ожидаемым | непонятно, получилось или нет |
| Команды | скопировать и выполнить | команда не работает без правки |
| Ссылки | открыть каждую | ссылка ведёт на старую версию |
| Термины | сверить с интерфейсом | одно и то же названо по-разному |
| Ошибки | вызвать и описать | читатель не знает, что делать |
| Версия | сверить с релизом | документ от другой версии |

Проверка на чистой машине не требует второго человека, если есть снимок виртуальной машины. Достаточно откатить снимок, пройти инструкцию и записать каждое отклонение. Если инструкция ссылается на файл, которого нет в репозитории, это обнаружится сразу.

Отдельно проверяют примеры API. Их запускают на тестовом стенде и сравнивают коды ответов и поля с описанием. Пример, который когда-то работал, но перестал, хуже отсутствующего: читатель доверяет документу и ищет ошибку у себя. Поэтому примеры лучше держать в коллекции Postman или в тестах, которые выполняются вместе со сборкой.

Проверка терминов кажется мелочью, но именно она чаще всего ломает инструкцию. В системе написано «Ячейка хранения», в руководстве «место», в описании API «slot», а в разговоре поддержки «полка». Читатель ищет в интерфейсе слово, которого там нет. Единый словарь терминов на страницу дешевле, чем десять обращений в поддержку.

Полезно проверять документ на читателе, который не участвовал в разработке, и записывать не только ошибки, но и время. Если инструкция на десять шагов занимает сорок минут, возможно, часть шагов можно автоматизировать. Если читатель возвращается к одному и тому же абзацу дважды, абзац написан непонятно. Наблюдение за чтением даёт больше, чем опрос «всё ли понятно», на который обычно отвечают вежливым «да».

Отдельно проверяют, что документ не обещает больше, чем система делает. Фраза «поддерживаются все форматы» без списка форматов выглядит сильным преимуществом и становится первым дефектом при приёмке. Ограничения полезно писать прямо: какие версии поддерживаются, какие размеры файлов допустимы, что происходит при превышении. Честно описанное ограничение вызывает меньше вопросов, чем обнаруженное.

## Типичные ошибки

**Документ написан для автора.** Автор знает, где лежит база и какой порт свободен, поэтому пропускает важные шаги. Симптом: читатель останавливается на третьем шаге. Лечение: проверка человеком, который не участвовал в работе.

**Нет предусловий.** Инструкция начинается с команды, но не говорит, что нужен Python 3.11 и свободный порт. Симптом: команда не найдена или порт занят. Лечение: раздел требований и проверка окружения.

**Шаг без результата.** Написано «запустите сервис», но не сказано, какую строку ждать. Симптом: читатель не понимает, запустилось ли. Лечение: ожидаемый вывод и проверка здоровья.

**Устаревшие снимки.** Интерфейс изменился, кнопка называется иначе. Симптом: читатель ищет кнопку, которой нет. Лечение: проверять снимки при каждом изменении интерфейса.

**Секрет в примере.** В README или руководстве оставлен настоящий пароль. Симптом: секрет виден всем, у кого есть доступ к документу. Лечение: только условные значения и ссылка на `.env.example`.

**Описание API без ошибок.** Есть только успешный ответ. Симптом: интегратор не знает, что делать с 401 и 404. Лечение: таблица кодов и формат ошибки.

**Документ вне репозитория.** Файл лежит на общем диске и обновляется отдельно. Симптом: версия документа не совпадает с версией кода. Лечение: документация в репозитории и проверка в запросе на слияние.

**«Интуитивно понятно».** Текст перекладывает решение на читателя. Симптом: каждый делает по-своему. Лечение: конкретные шаги и условие выбора.

**Документ без владельца.** Все считают, что документ обновит кто-то другой. Симптом: через месяц инструкция описывает прошлую версию. Лечение: роль владельца и проверка при выпуске.

> [!KEY] Документ проверяют действием
> Красивый текст не доказывает полноту. Доказывает её читатель, который прошёл инструкцию на чистой машине и получил ожидаемый результат.

::/gate

## Что проверить в учебном проекте

В учебном проекте первым проверяют README, потому что от него зависит, сможет ли другой человек вообще увидеть приложение. Проверка идёт на чистой машине или на откаченном снимке: установка, настройки, запуск, health check. Каждое место, где пришлось открывать исходники или звонить автору, становится правкой.

Вторым проверяют описание API. Достаточно двух маршрутов: чтение остатка и создание накладной. Для каждого указывают метод, путь, параметры, успешный ответ, ошибки и пример запроса. Примеры запускают в Postman, а не переписывают из памяти. Если ответ не совпал с описанием, правят описание или код, но не оставляют расхождение.

Третьим проверяют журнал изменений. Он должен совпадать с версией артефакта и объяснять пользователю, что проверять после обновления. Записи вроде «исправлены ошибки» ничего не говорят: читатель не знает, какая ошибка была и как убедиться, что она исчезла.

Четвёртым проверяют владельца. У README, руководства и описания API должен быть человек или роль, которая отвечает за актуальность. Без владельца документы пройдут первую проверку и устареют к следующему выпуску.

## Итоги

- У документа есть адресат, задача и признак успеха; без них это пересказ, а не инструмент.
- Пользовательская и техническая документация различаются читателем и способом проверки.
- Форма документа следует из задачи: обучение, инструкция, справочник и объяснение не смешиваются в одном тексте.
- Инструкция состоит из предусловий, шагов с ожидаемым результатом, ошибок, проверки и отката.
- README отвечает за установку, настройки, запуск и проверку проекта на чистой машине.
- Описание API содержит метод, путь, параметры, успешный ответ, коды ошибок и примеры.
- Документацию держат в репозитории, обновляют вместе с кодом и проверяют прохождением на чистом окружении.
- Критерий приёмки должен быть записан рядом с требованием, иначе прогресс измеряют по удобной шкале.
