## Смена в Туле, 08:40

Кладовщик открывает «Склад+» и видит 4800 позиций на четырёх площадках: в Москве, Твери, Туле и Калуге. Товары разложены по 12 категориям, от крепежа до электрики. Задача на утро звучит просто: понять, что нужно заказать у поставщика, пока склад не встал.

Простота обманчива. Заказывать все 4800 позиций нельзя, это заморозит деньги и забьёт ячейки. Заказывать только те, где остаток равен нулю, тоже нельзя: товар кончится раньше, чем придёт поставка. Правило склада учитывает минимальный остаток и кратность упаковки: поставщик везёт крепёж коробками по 10 штук, электрику по 12, сантехнику по 4. Если остаток ниже минимума, нужно добрать разницу и округлить её вверх до целой коробки.

У правила есть цена. Одна лишняя коробка на 4800 позиций это десятки тысяч рублей в замороженном запасе, а одна пропущенная позиция это простой сборочной линии. Ошибка в условии и ошибка в границе цикла выглядят одинаково: программа работает, числа выходят правдоподобные, а заказ приходит неполный.

Такое правило нельзя применить одной формулой ко всей таблице. Сначала нужно решить, какие строки вообще участвуют в расчёте, потом пройти по ним и накопить итог. Эти два действия и есть управляющие конструкции: **ветвление выбирает, какие данные обрабатывать, а цикл повторяет обработку для каждой выбранной строки**.

Управляющая конструкция задаёт не только результат, но и порядок вычислений. Компьютер выполняет команды последовательно, а ветвление и цикл меняют эту последовательность: пропускают блок, повторяют его или выходят из него. Поэтому ошибка управления редко проявляется как исключение. Чаще она проявляется как правдоподобное число, которое не совпадает с ручным расчётом.

## Ветвление: какие позиции попадают в заказ

Начнём с одной строки. У позиции `SKU-1042` остаток 12 штук, минимум 40, упаковка 10. Остаток ниже минимума, значит позиция попадает в заказ. У позиции `SKU-2087` остаток 96 при минимуме 60, заказывать нечего.

На Python это записывается так:

```python
quantity = 12
min_quantity = 40
if quantity < min_quantity:
    print("заказать")
else:
    print("не заказывать")
```

На C# то же решение выглядит почти так же, но с фигурными скобками и обязательными круглыми скобками вокруг условия:

```csharp
int quantity = 12;
int minQuantity = 40;
if (quantity < minQuantity)
{
    Console.WriteLine("заказать");
}
else
{
    Console.WriteLine("не заказывать");
}
```

Разница в записи не меняет смысла. В обоих языках условие вычисляется один раз, приводится к логическому значению, и выполняется ровно одна ветка. Как только ветка выбрана, вторая не выполняется вообще, даже если её условие тоже оказалось бы истинным.

Внутри интерпретатора и компилятора это выглядит как переход. Python компилирует функцию в байт-код, где после проверки стоит команда условного перехода `POP_JUMP_FORWARD_IF_FALSE` или её аналог. Компилятор C# строит дерево выражений и генерирует инструкции ветвления для процессора. На уровне логики важно одно: проверка это точка, после которой управление уходит в одну сторону и уже не возвращается во вторую.

Условие в Python принимает любой объект, потому что у языка есть понятие истинности. Пустая строка, пустой список, число 0 и `None` считаются ложными, остальное истинным. Это удобно для проверки «список не пуст», но опасно, когда ноль является допустимым значением. Запись `if quantity:` пропустит позицию с нулевым остатком, хотя именно она требует заказа. В C# такого не произойдёт: `if (quantity)` не компилируется, потому что условие обязано иметь тип `bool`. Компилятор заставляет сформулировать проверку явно: `if (quantity > 0)`.

| Проверка | Python | C# | Что важно |
|---|---|---|---|
| Ноль это ложь | да | нет | `if quantity:` пропускает ноль |
| Пустой список это ложь | да | нет | в C# нужен `Count > 0` |
| Строка это ложь | пустая строка | нет | в C# нужен `Length > 0` |
| Значение `None` | ложь | `null` не приводится к `bool` | нужна проверка `is not None` или `!= null` |
| Сравнение с `None` | `is None` | `== null` или `is null` | `is` сравнивает ссылку, `==` может быть перегружен |

В Python условие может возвращать не только `True` и `False`. Операторы `and` и `or` возвращают один из операндов, а не логическое значение. Выражение `pack or 1` вернёт `pack`, если он не равен нулю, и `1` иначе. Это идиома для значения по умолчанию, но при переводе на C# её нельзя записать как `pack || 1`, потому что `||` возвращает `bool`. Там понадобится `pack != 0 ? pack : 1` или оператор `??` для ссылочных типов. Ошибка перевода здесь не ломает сборку, она меняет тип результата и смысл выражения.

Отдельно стоит запомнить цепочки сравнений. В Python можно написать `0 <= quantity < min_quantity`, и это означает два сравнения с одним вычислением `quantity`. В C# такое выражение не собирается: там пишут `quantity >= 0 && quantity < minQuantity`. Python-запись читается как математическое неравенство, но при переносе её нужно разложить на две проверки, не потеряв границу.

Когда условий несколько, порядок становится частью алгоритма. Для склада их три: позиция активна, остаток ниже минимума, категория не исключена из автозаказа. Запись с `elif` в Python и `else if` в C# читается сверху вниз, и первая истинная ветка забирает управление.

```python
if not position["active"]:
    decision = "архив"
elif position["category"] == "Спецтехника":
    decision = "заказ вручную"
elif position["qty"] < position["min_qty"]:
    decision = "в заказ"
else:
    decision = "достаточно"
```

Порядок здесь не случаен. Если поставить проверку остатка первой, архивная позиция с нулевым остатком попадёт в заказ, хотя её сняли с продажи. Проверка активности должна стоять раньше, потому что она отсекает строку независимо от чисел.

Тот же приём в C# называют защитным условием, или ранним выходом. Вместо вложенных `if` функция сначала отбрасывает невозможные случаи и возвращает результат:

```csharp
static int ReorderQuantity(int quantity, int minQuantity, int packSize)
{
    if (quantity >= minQuantity)
    {
        return 0;
    }
    int missing = minQuantity - quantity;
    int packs = (missing + packSize - 1) / packSize;
    return packs * packSize;
}
```

Проверка `quantity >= minQuantity` стоит первой и снимает главный вопрос: нужен ли заказ. Всё, что ниже, уже работает только с дефицитом. Такая запись короче вложенных веток и легче читается, потому что каждая строка имеет один смысл.

## Порядок условий, короткое замыкание и цена ветки

Цепочка `elif` и набор независимых `if` решают разные задачи. Цепочка выбирает ровно одно действие, даже если подходят несколько условий. Независимые проверки выполняют все подходящие действия, например записывают позицию в заказ и одновременно ставят пометку для снабженца. Путать эти формы опасно: замена цепочки на набор `if` может добавить строку в заказ дважды.

Логические операторы вычисляются слева направо и с коротким замыканием. В Python `and` и `or`, в C# `&&` и `||` прекращают вычисление, как только результат ясен. Если первый операнд `and` ложен, второй не вычисляется. Если первый операнд `or` истинен, второй тоже не вычисляется. Это не оптимизация, а часть семантики языка.

Короткое замыкание полезно, когда вторая проверка безопасна только после первой. Запись `row["pack"] != 0 and missing % row["pack"] == 0` не вызовет деления на ноль, потому что при нулевой упаковке вторая часть не выполнится. Но полагаться на это в сложных условиях рискованно: читателю приходится восстанавливать порядок вычислений, а любая перестановка операндов ломает защиту.

Побочные эффекты внутри условий делают порядок ещё опаснее. Если `check(row)` не только проверяет, но и пишет в журнал, то при коротком замыкании запись может не появиться. Условие должно отвечать на вопрос «истинно или ложно», а не выполнять работу. Это правило особенно важно при переводе: в C# методы в условии вызываются так же, но компилятор не подскажет, что вызов стал пропускаться.

Есть ещё различие между `&` и `&&` в C#. Оператор `&&` работает с логическими значениями и не вычисляет второй операнд без необходимости. Оператор `&` для `bool` вычисляет оба операнда, а для целых типов выполняет побитовое И. Python такого разделения не имеет: `and` всегда с коротким замыканием, а побитовое И записывается как `&` и имеет другой приоритет. Ошибка с приоритетом операторов встречается в условиях чаще, чем кажется: `a == 1 and b == 2` и `a == 1 & b == 2` выглядят похоже, но значат разное.

| Выражение | Python | C# | Совет |
|---|---|---|---|
| И с коротким замыканием | `a and b` | `a && b` | основной вариант для условий |
| Или с коротким замыканием | `a or b` | `a` или `b`, логическое ИЛИ | проверять порядок операндов |
| Отрицание | `not a` | `!a` | не путать с `!=` |
| Побитовое И | `a & b` | `a & b` | для флагов, не для условий |
| Значение по умолчанию | `a or b` | `a ?? b` | в Python работает и для чисел, и для объектов |
| Тернарное выражение | `x if cond else y` | `cond ? x : y` | скобки в C# обязательны при вложении |

Цена ветки измеряется не только строками кода. Каждое независимое условие добавляет путь выполнения, который нужно проверить. Метрика цикломатической сложности считает такие пути: функция без ветвлений имеет сложность 1, каждый `if` добавляет единицу, каждый цикл тоже. Число около 10 часто используют как эвристический порог, за которым функцию пора разделить. Это не закон природы и не требование стандарта, а ориентир для рецензии: чем больше путей, тем больше комбинаций для теста.

Сложные условия лечатся не сокращением строк, а именованием. Вместо `if qty < min and active and cat not in excluded` пишут функцию `needs_reorder(row)` и вызывают её. Имя переносит смысл в одно место, а условие становится коротким. Тот же приём работает в C#: локальная функция или отдельный метод с понятным именем читается лучше, чем пять связанных `&&`.

Для выбора одной ветки по значению служит `switch` в C# и `match` в Python начиная с версии 3.10. Классический `switch` требует `break` или `return` в каждой ветке, иначе управление провалится в следующую. Пустые метки можно объединять, но случайный пропуск `break` компилятор не всегда считает ошибкой. В C# 8 появилось выражение `switch`, где ветки возвращают значение и проваливание невозможно. В Python `match` сравнивает с образцом, поддерживает кортежи, словари и охранные условия `if`, а ветка `case _` играет роль `else`.

| Задача | Python | C# |
|---|---|---|
| Одна ветка по значению | `match value: case ...` | `switch (value) { case ...: break; }` |
| Выражение вместо оператора | `result = ... if ... else ...` | `result = value switch { ... }` |
| Несколько значений в одной ветке | `case 1:` и `case 2:` | `case 1: case 2:` |
| Ветка по умолчанию | `case _:` | `default:` |
| Проверка диапазона | `case x if x < 0:` | `case < 0:` в выражении или `when` |

`switch` и `match` не заменяют цепочку условий полностью. Они хороши, когда выбор идёт по значению или форме данных, а не по длинному составному условию. Если ветки проверяют разные поля и разные правила, цепочка `if` с ранними выходами остаётся понятнее.

## Цикл: обход коллекции и его механика

Одна строка обрабатывается ветвлением. 4800 строк обрабатываются циклом. В Python самый короткий способ пройти по списку словарей выглядит так:

```python
for row in positions:
    print(row["sku"])
```

Здесь нет счётчика и нет условия выхода: Python сам берёт следующий элемент, пока список не закончится. Если нужен номер строки, добавляют `enumerate`:

```python
for number, row in enumerate(positions, start=1):
    print(number, row["sku"])
```

В C# обход коллекции без счётчика делают через `foreach`:

```csharp
foreach (string sku in skus)
{
    Console.WriteLine(sku);
}
```

А обход по индексу через `for`:

```csharp
for (int i = 0; i < skus.Length; i++)
{
    Console.WriteLine(skus[i]);
}
```

Разница между двумя формами важна для перевода. `foreach` не даёт менять коллекцию во время обхода и не показывает индекс. `for` даёт индекс, но требует вручную задать начало, условие продолжения и шаг. В Python аналогичное деление выглядит как `for row in rows` и `for i in range(len(rows))`.

За этими формами стоит разная механика. Python-цикл `for` вызывает у объекта функцию `iter()`, получает итератор и на каждом шаге просит у него следующий элемент. Когда элементы заканчиваются, итератор возбуждает `StopIteration`, и цикл завершается. Поэтому `for` работает не только со списком, но и с файлом, словарём, генератором и любым объектом, у которого есть методы `__iter__` и `__next__`.

C#-цикл `foreach` требует, чтобы коллекция реализовала `IEnumerable<T>`. Компилятор превращает цикл в вызов `GetEnumerator()`, затем повторяет `MoveNext()` и читает `Current`, а в конце вызывает `Dispose()`. Для массива компилятор может сгенерировать более простой обход по индексу, но смысл тот же: перечислитель знает, где он остановился, и умеет сообщить об окончании.

| Что происходит | Python | C# |
|---|---|---|
| Получить перечислитель | `iter(rows)` | `rows.GetEnumerator()` |
| Проверить наличие элемента | исключение `StopIteration` | `MoveNext()` возвращает `false` |
| Прочитать элемент | `next(iterator)` | `iterator.Current` |
| Завершить обход | цикл ловит `StopIteration` | `Dispose()` |
| Изменить коллекцию в обходе | список можно, но элементы сдвигаются | `InvalidOperationException` |

Третья форма это цикл с условием. Он нужен, когда число повторений заранее неизвестно: например, читать строки из файла, пока не встретится пустая. В Python это `while condition:`, в C# `while (condition)`. У C# есть ещё `do { } while (condition);`, где тело выполняется хотя бы один раз, даже если условие ложно с самого начала. В Python встроенного `do-while` нет, его собирают из `while True` и `break`.

| Задача | Python | C# |
|---|---|---|
| Ветвление по условию | `if`, `elif`, `else` | `if`, `else if`, `else` |
| Обход коллекции | `for row in rows` | `foreach (var row in rows)` |
| Обход по индексу | `for i in range(len(rows))` | `for (int i = 0; i < rows.Length; i++)` |
| Повтор по условию | `while condition:` | `while (condition)` |
| Тело хотя бы один раз | `while True` и `break` | `do { } while (condition);` |
| Пропустить строку | `continue` | `continue` |
| Выйти из цикла | `break` | `break` |
| Граница диапазона | правый конец не входит | граница задаётся условием |

Последняя строка таблицы объясняет половину ошибок перевода. `range(0, 5)` в Python даёт 0, 1, 2, 3, 4, то есть пять значений без пятёрки. В C# условие `i < 5` даёт те же пять значений, а `i <= 5` уже шесть. При переносе кода нужно переводить не символы, а количество повторений.

У цикла есть инвариант, то есть утверждение, которое истинно перед каждой итерацией и после неё. Для расчёта заказа инвариант звучит так: `total` равен сумме заказов по всем уже обработанным строкам, а `count` равен числу этих строк. Инвариант объясняет, зачем накопители объявляют до цикла и почему их не обнуляют внутри тела. Если инвариант сформулирован, ошибку видно по коду, а не по результату.

Второе свойство правильного цикла это продвижение к завершению. Счётчик увеличивается, итератор движется, множество обработанных строк растёт. Цикл, который не приближается к концу, зависает. В Python это выглядит как `while i < len(rows)` без `i += 1`, в C# как `for` без шага. Компилятор такое не запрещает, потому что не знает, меняется ли переменная внутри тела.

Соберём рабочий расчёт для пяти позиций. В Python данные удобно держать списком словарей:

```python
positions = [
    {"sku": "SKU-1042", "category": "Крепёж", "qty": 12, "min_qty": 40, "pack": 10},
    {"sku": "SKU-2087", "category": "Электрика", "qty": 96, "min_qty": 60, "pack": 12},
    {"sku": "SKU-3310", "category": "Крепёж", "qty": 0, "min_qty": 25, "pack": 5},
    {"sku": "SKU-4155", "category": "Инструмент", "qty": 7, "min_qty": 7, "pack": 1},
    {"sku": "SKU-5201", "category": "Электрика", "qty": 3, "min_qty": 30, "pack": 6},
]

total = 0
count = 0
for row in positions:
    if row["qty"] >= row["min_qty"]:
        continue
    missing = row["min_qty"] - row["qty"]
    packs = (missing + row["pack"] - 1) // row["pack"]
    order = packs * row["pack"]
    total += order
    count += 1
    print(row["sku"], row["qty"], row["min_qty"], "->", order)

print("Позиций к заказу:", count)
print("Всего единиц:", total)
```

Запуск даёт:

```text
SKU-1042 12 40 -> 30
SKU-3310 0 25 -> 25
SKU-5201 3 30 -> 30
Позиций к заказу: 3
Всего единиц: 85
```

Обратите внимание на строку `packs = (missing + row["pack"] - 1) // row["pack"]`. Это округление вверх при целочисленном делении. Для `SKU-5201` дефицит равен 27, упаковка 6. Обычное деление `27 // 6` дало бы 4 коробки и 24 штуки, чего не хватает до минимума. Добавка `pack - 1` превращает 27 в 32, и `32 // 6` даёт 5 коробок, то есть 30 штук. Тот же приём работает в C#, где целочисленное деление отбрасывает дробную часть.

Проверим расчёт по строкам вручную. Для каждой позиции дефицит равен разнице между минимумом и остатком, число коробок округляется вверх, заказ равен числу коробок, умноженному на упаковку.

| Позиция | Остаток | Минимум | Дефицит | Коробок | Заказ |
|---|---|---|---|---|---|
| SKU-1042 | 12 | 40 | 28 | 3 | 30 |
| SKU-2087 | 96 | 60 | нет | 0 | 0 |
| SKU-3310 | 0 | 25 | 25 | 5 | 25 |
| SKU-4155 | 7 | 7 | нет | 0 | 0 |
| SKU-5201 | 3 | 30 | 27 | 5 | 30 |

Сумма заказов равна 85, и это число совпадает с выводом программы. Такая таблица полезна не только для проверки: она показывает, что формула работает на всех пяти строках, включая нулевой остаток и остаток ровно по минимуму.

Иногда цикл нужен не для полного обхода, а для поиска первой подходящей строки. Тогда после находки работу прекращают через `break`:

```python
for row in positions:
    if row["qty"] < row["min_qty"]:
        print("Первая позиция к заказу:", row["sku"])
        break
```

Программа печатает `Первая позиция к заказу: SKU-1042` и больше не перебирает список. В C# `break` работает так же и выходит только из ближайшего цикла. Если циклы вложены, `break` во внутреннем не остановит внешний: для этого нужен флаг или вынос поиска в отдельную функцию.

В Python у `for` есть необычная ветка `else`, которая выполняется, если цикл завершился без `break`. Она полезна для поиска: `else` означает «ничего не нашли». В C# такой конструкции нет, поэтому заводят переменную `found` и проверяют её после цикла. При переводе `for ... else` легко потерять эту ветку и получить молчаливое отсутствие сообщения.

Вложенные циклы нужны, когда обрабатывается пара множеств: например, для каждой позиции проверить все категории из списка исключений. Стоимость такого обхода равна произведению размеров: 4800 позиций на 12 категорий дают 57 600 сравнений. Для учебного проекта это немного, но привычка важна: если внутри цикла стоит поиск по списку, сложность растёт как квадрат. Словарь категорий или множество исключений превращает поиск в одну операцию и убирает внутренний цикл.

## Границы: где цикл ломается

Цикл, который правильно работает на пяти строках, может упасть на пустом списке или на последней строке. Граничный случай это вход, на котором условие цикла меняет смысл: ноль элементов, один элемент, последний элемент, значение ровно на пороге.

Первый случай: пустая коллекция. В Python `for row in []` не выполнится ни разу, и итог останется нулевым. В C# `for (int i = 0; i < skus.Length; i++)` при длине 0 тоже не выполнится. Это правильное поведение, но только если переменные `total` и `count` объявлены до цикла. Если объявить их внутри тела, после цикла их просто не будет, и программа не соберётся.

Второй случай: значение ровно на пороге. Позиция `SKU-4155` имеет остаток 7 при минимуме 7. Условие `qty < min_qty` ложно, заказ равен нулю. Если заменить его на `qty <= min_qty`, позиция попадёт в заказ и склад начнёт закупать товар, которого и так достаточно. Порог это самая частая причина лишних заказов.

Третий случай: последний элемент. Здесь появляется ошибка на единицу. Такой цикл в файле `offby.py`:

```python
positions = ["SKU-1042", "SKU-2087", "SKU-3310"]
for i in range(len(positions) + 1):
    print(positions[i])
```

печатает три строки, а затем падает:

```text
SKU-1042
SKU-2087
SKU-3310
Traceback (most recent call last):
  File "offby.py", line 3, in <module>
    print(positions[i])
IndexError: list index out of range
```

В C# та же ошибка выглядит как `IndexOutOfRangeException` и возникает при `i <= skus.Length`. Причина одна: условие продолжения пропускает индекс, которого в массиве нет. Лечение тоже одно: граница это длина, а не длина плюс один.

Четвёртый случай: изменение коллекции во время обхода. Кладовщик хочет убрать из списка позиции, которых достаточно. В Python такой код:

```python
skus = ["SKU-1", "SKU-2", "SKU-3", "SKU-4"]
for sku in skus:
    if sku in ("SKU-2", "SKU-3"):
        skus.remove(sku)
print(skus)
```

печатает `['SKU-1', 'SKU-3', 'SKU-4']`. Вторая позиция удалена, третья осталась, хотя её тоже собирались удалить. После удаления элементы сдвигаются влево, и цикл перескакивает через следующий. В C# `foreach` по списку при удалении внутри тела выбрасывает `InvalidOperationException` с сообщением «Коллекция была изменена; невозможно выполнить операцию перечисления». Правильное решение в обоих языках: собрать новый список или пройти по копии, а удалять после обхода.

Пятый случай: деление и кратность. Если `pack` равен нулю, формула округления делит на ноль: в Python будет `ZeroDivisionError`, в C# `DivideByZeroException`. Если остаток отрицательный, формула даст отрицательный заказ. Оба случая отсекаются проверкой входа до цикла, а не внутри него.

Шестой случай: переполнение. В Python целые числа не ограничены разрядностью, поэтому сумма миллиардов остатков останется точной, пока хватает памяти. В C# `int` занимает 32 бита и при переполнении по умолчанию заворачивается: `int.MaxValue + 1` даёт отрицательное число, и программа продолжает работу без ошибки. Для склада из 4800 позиций переполнение маловероятно, но в отчёте по всей сети или в счётчике времени оно реально. Проверяемое вычисление включают контекстом `checked`, а для больших сумм берут `long` или `decimal`.

Седьмой случай: целочисленное деление с отрицательными числами. В Python `//` округляет вниз, к минус бесконечности: `-7 // 2` равно `-4`. В C# деление целых отбрасывает дробную часть, то есть движется к нулю: `-7 / 2` равно `-3`. Для положительного дефицита разницы нет, а для отрицательного остатка результат расходится. Поэтому отрицательный вход отсекают проверкой, а не надеются, что формула «сама исправит».

Восьмой случай: сравнение вещественных чисел. Если остаток хранится как `double`, проверка `quantity == minQuantity` может не сработать из-за двоичного представления. Для количеств и денег используют целые единицы или `decimal`, а сравнение вещественных делают с допуском. В Python тип `float` тоже двоичный, поэтому правило одинаково.

| Случай | Вход | Ожидание | Что ломается |
|---|---|---|---|
| Пустая коллекция | нет строк | итог 0, счётчик 0 | переменные объявлены внутри цикла |
| Порог | остаток равен минимуму | заказ 0 | условие `<=` вместо `<` |
| Последний элемент | индекс равен длине | обход без падения | условие `<=` вместо `<` |
| Удаление в обходе | две позиции подряд | удалены обе | сдвиг элементов |
| Нулевая упаковка | `pack = 0` | понятная ошибка | деление на ноль |
| Отрицательный остаток | `qty = -3` | отказ | отрицательный заказ или разное деление |
| Переполнение | сумма больше `int.MaxValue` | ошибка или `long` | заворачивание `int` |
| Вещественный порог | `0.1 + 0.2` | сравнение с допуском | точное равенство |

Граничные случаи проверяют не после написания программы, а вместе с ней. Достаточно прогнать четыре набора: обычный, пустой, один элемент и значение на пороге. Если все четыре дают ожидаемый результат, цикл скорее всего устроен верно.

## Два разбора: как ошибка управления меняет результат

Управляющая конструкция кажется локальной деталью: одна строка, один `if`, один `goto`. Но именно она решает, попадёт ли проверка в выполнение. Ниже два случая, где стоимость ошибки измеряется не в рублях за коробку, а в безопасности и жизнях.

### Apple, 2014: лишний переход через проверку

В феврале 2014 года Apple выпустила обновления iOS и OS X, закрывающие уязвимость CVE-2014-1266. Национальная база уязвимостей США описывает её так: злоумышленник, занимающий позицию в сети, может перехватить или изменить данные в сеансе, защищённом SSL/TLS [NVD, CVE-2014-1266](https://nvd.nist.gov/vuln/detail/CVE-2014-1266). В сообщении Apple об обновлении указано, что исправление касается защищённого соединения SSL/TLS [Apple, 2014](https://support.apple.com/en-us/HT202358).

Причина стала видна в опубликованном исходном коде. В функции проверки подписи стояла конструкция с меткой `fail` для освобождения ресурсов. Ветка проверки `if` не имела фигурных скобок, а под ней оказался ещё один безусловный `goto fail`:

```c
if ((err = SSLHashSHA1.update(&hashCtx, &signedParams)) != 0)
    goto fail;
    goto fail;
if ((err = SSLHashSHA1.final(&hashCtx, &hashOut)) != 0)
    goto fail;
```

Отступы создают впечатление, что второй `goto` относится к тому же `if`. На самом деле без скобок к `if` относится только первая строка. Второй `goto` выполняется всегда и перепрыгивает вызов проверки подписи. Управление попадает на метку `fail`, код освобождает буферы и возвращает `err`, который к этому моменту равен нулю. Для вызывающего кода это выглядит как успешная проверка.

Ошибка не в криптографии и не в математике. Ошибка в том, что поток управления перестал соответствовать намерению автора. Компилятор не обязан считать это ошибкой: синтаксис корректен, а `goto` на существующую метку допустим. Предупреждение о недостижимом коде могло бы обратить внимание на следующий `if`, но для этого анализатор должен быть включён и его вывод не должен теряться среди тысяч других сообщений.

Урок для расчёта заказа простой. Фигурные скобки и ранний выход защищают не от «плохого стиля», а от неверного чтения структуры. Если ветка занимает больше одной строки, скобки обязательны. Если функция освобождает ресурсы через общую метку, переходы к ней должны быть видны и проверены отдельно. И главное: тест должен проверять не только успешный вход, но и отказ. Проверка подписи, которая не умеет отклонять плохой сертификат, проходит все счастливые сценарии.

### Patriot, 1991: цикл, который накапливал ошибку

25 февраля 1991 года батарея Patriot в Дахране, Саудовская Аравия, не перехватила иракскую ракету. Погибли 28 военнослужащих. Разбор американского контрольного управления показал, что причиной стала не одна неверная команда, а накопление ошибки в повторяющемся расчёте [GAO, IMTEC-92-26](https://www.gao.gov/products/imtec-92-26).

Система отслеживала время в десятых долях секунды и хранила значение в 24-битном регистре с фиксированной точкой. Число 0,1 в двоичной системе не представляется точно. Каждое обновление, которое происходило примерно каждые 0,1 секунды, теряло малую долю. Ошибка одного шага была ничтожной, но за 100 часов работы она накопилась примерно в 0,34 секунды. При скорости цели около 1,7 км/с это дало смещение области сопровождения примерно на 687 метров. Радар искал ракету не там, где она находилась.

У этой ошибки три управленческих урока. Первый: цикл накапливает не только полезный результат, но и погрешность. Если внутри повторяющегося расчёта есть округление, ошибка растёт с числом итераций, и проверка на одном шаге её не покажет. Второй: граница это не только индекс. Время работы, число итераций и диапазон значений тоже границы, и их нужно проверять. Третий: исправление должно доехать до всех экземпляров. Обновлённая версия существовала, но на позиции в Дахране работала старая, и это превратило известный дефект в катастрофу.

Для склада эти уроки переводятся в конкретные проверки. Сумма заказов за месяц не должна считаться в `float`, если важны копейки. Счётчик обработанных строк не должен переполняться на длинной выгрузке. Формула, которая вызывается 4800 раз, проверяется не только на одной строке, но и на полном наборе с ручной сверкой итога.

| Что проверять | Вопрос | Признак ошибки |
|---|---|---|
| Структура ветки | все ли строки входят в `if` по замыслу | проверка не выполняется, но результат успешный |
| Порядок условий | не перекрывает ли ранняя ветка позднюю | архивная строка попадает в заказ |
| Граница цикла | совпадает ли число итераций с длиной | падение на последнем элементе |
| Накопление | не растёт ли ошибка с каждой итерацией | итог расходится на длинной серии |
| Развёртывание | одинаков ли код на всех машинах | на тестовой машине верно, на рабочей нет |

## Перевод алгоритма с Python на C#

Перевод начинается не с кода, а с данных. В Python одна строка это словарь с ключами `sku`, `qty`, `min_qty`, `pack`. В C# до появления классов на этом курсе удобно держать те же значения в параллельных массивах: индекс `i` связывает `skus[i]`, `quantities[i]`, `minimums[i]` и `packs[i]`. Связь по номеру слабее связи по имени, но для перевода алгоритма её достаточно. На занятии про объекты эти массивы заменятся классом.

Второй шаг: переписать условие и тело цикла, сохранив порядок действий. Третий: проверить, что граница цикла даёт то же число повторений. Вот полная программа на C#:

```csharp
using System;
using System.Text;

class Program
{
    static void Main()
    {
        Console.OutputEncoding = Encoding.UTF8;
        string[] skus = { "SKU-1042", "SKU-2087", "SKU-3310", "SKU-4155", "SKU-5201" };
        int[] quantities = { 12, 96, 0, 7, 3 };
        int[] minimums = { 40, 60, 25, 7, 30 };
        int[] packs = { 10, 12, 5, 1, 6 };

        int total = 0;
        int count = 0;
        for (int i = 0; i < skus.Length; i++)
        {
            if (quantities[i] >= minimums[i])
            {
                continue;
            }
            int missing = minimums[i] - quantities[i];
            int packCount = (missing + packs[i] - 1) / packs[i];
            int order = packCount * packs[i];
            total += order;
            count++;
            Console.WriteLine(skus[i] + " " + quantities[i] + " " + minimums[i] + " -> " + order);
        }
        Console.WriteLine("Позиций к заказу: " + count);
        Console.WriteLine("Всего единиц: " + total);
    }
}
```

Вывод совпадает с Python строка в строку:

```text
SKU-1042 12 40 -> 30
SKU-3310 0 25 -> 25
SKU-5201 3 30 -> 30
Позиций к заказу: 3
Всего единиц: 85
```

Совпадение вывода это критерий правильного перевода. Если числа разошлись, ищите причину в трёх местах: в условии отбора, в округлении и в границе цикла. Синтаксис почти никогда не виноват, потому что программа с неверным синтаксисом просто не соберётся.

Есть и различия, которые нужно помнить при переносе.

| Что сравниваем | Python | C# |
|---|---|---|
| Длина коллекции | `len(rows)` | `rows.Length` для массива, `rows.Count` для списка |
| Целочисленное деление | `//`, округляет вниз | `/`, отбрасывает дробную часть |
| Остаток от деления | `%` | `%` |
| Логическое И и ИЛИ | `and`, `or`, `not` | `&&`, логическое ИЛИ, `!` |
| Истина и ложь | `True`, `False` | `true`, `false` |
| Вывод строки | `print(...)` | `Console.WriteLine(...)` |
| Сложение строки и числа | нужна f-строка или `str()` | `+` со строкой приводит число к строке |
| Условие | любой объект | только `bool` |
| Переполнение `int` | нет, целые произвольной длины | заворачивание, если не `checked` |

Последняя строка часто удивляет, но в обратную сторону. В Python выражение `"Всего: " + total` завершится ошибкой `TypeError: can only concatenate str (not "int") to str`, потому что `+` не смешивает строку и число. Нужна f-строка `f"Всего: {total}"` или явное `str(total)`. В C# то же выражение работает: если хотя бы один операнд строка, второй приводится к строке, и порядок операндов не важен.

Ещё одно различие касается `switch`. В C# классический `switch` выбирает ветку по точному значению и требует `break` в конце каждой ветки. В Python с версии 3.10 есть `match`, который умеет сравнивать с образцом и не требует `break`. Для склада это удобно при выборе кода площадки по названию, но обе конструкции решают одну задачу: выбрать одну ветку из нескольких по значению, а не по диапазону.

При переводе цикла проверяют не только границу, но и тип счётчика. В Python `range` может быть длиннее, чем помещается в `int` C#. В учебном проекте это не проблема, а в выгрузке за год может быть. Если число строк неизвестно заранее, в C# берут `long` или `checked`, а не надеются на молчаливое заворачивание.

## Какую конструкцию выбрать

Выбор конструкции это выбор формы данных и формы повторения. Если нужно отобрать строки, подходит ветвление внутри обхода. Если нужно посчитать итог по всем строкам, подходит цикл с накопителем. Если число повторений известно заранее, берите `for` по диапазону. Если неизвестно, берите `while`. Если нужно обойти коллекцию целиком и индекс не нужен, берите `foreach` или `for row in rows`.

| Ситуация | Конструкция | Почему |
|---|---|---|
| Отсеять архивные позиции | `if` с ранним `continue` | решение по одной строке |
| Посчитать итог по 4800 позициям | `for` с накопителем | число строк известно |
| Читать файл до пустой строки | `while` | число повторений неизвестно |
| Обойти все категории | `foreach` | индекс не нужен |
| Повторить попытку ввода | `do-while` в C#, `while True` в Python | тело нужно хотя бы раз |
| Найти первую позицию ниже минимума | `for` и `break` | дальше искать не нужно |
| Выбрать действие по коду площадки | `match` или `switch` | выбор по значению |
| Проверить пару условий | `and` или `&&` | короткое замыкание защищает вторую проверку |

Два правила помогают не усложнять. Первое: глубина вложенности не больше двух. Три уровня `if` внутри `for` внутри `if` читаются плохо, и почти всегда их можно разбить на отдельные функции. Второе: `break` и `continue` применяют только тогда, когда они сокращают код. Если после `continue` остаётся половина тела, проще переписать условие.

Полезно проверять не только правильность, но и объяснимость. Если коллеге нужно нарисовать схему вашего цикла, чтобы понять, почему итог равен 85, конструкция слишком сложная. Хороший признак: каждую ветку можно назвать одним предложением, а инвариант цикла формулируется без пересказа всего тела.

## Типичные ошибки

**Ошибка первая: граница цикла на единицу больше.** Симптом: программа падает на последней строке или, наоборот, не обрабатывает последний элемент. Причина в условии `i <= length` или `range(len(rows) + 1)`. Проверка: подставить длину 0 и длину 1.

**Ошибка вторая: округление вниз вместо вверх.** Симптом: заказ меньше минимума на несколько штук. Причина в `missing // pack` без добавки `pack - 1`. Проверка: взять дефицит, который не делится на упаковку нацело.

**Ошибка третья: изменение коллекции во время обхода.** Симптом: часть строк пропущена или возникает исключение. Причина в `remove` внутри `for` или `foreach`. Проверка: собрать новый список и сравнить длины.

**Ошибка четвёртая: условие на пороге.** Симптом: заказывается товар, которого достаточно. Причина в `<=` вместо `<`. Проверка: строка, где остаток равен минимуму, должна давать ноль.

**Ошибка пятая: счётчик объявлен внутри цикла.** Симптом: итог всегда равен последнему значению, а не сумме. Причина в `total = 0` внутри тела. Проверка: вывести итог после цикла и сравнить с ручной суммой.

**Ошибка шестая: скрытая работа в условии.** Симптом: журнал содержит не все проверки или, наоборот, лишние записи. Причина: функция в условии меняет состояние, а короткое замыкание пропускает вызов. Проверка: вынести побочный эффект из условия.

**Ошибка седьмая: неявное приведение к логическому значению.** Симптом: позиция с нулевым остатком пропущена. Причина: `if quantity:` вместо `if quantity < min_qty:`. Проверка: подставить ноль и пустую строку.

> [!PITFALL] Проверяйте не только середину списка
> Пять строк с разными остатками не показывают, что будет на пустом списке и на строке с остатком ровно по минимуму. Эти два входа ловят большинство ошибок границ.

## Итоги

- Ветвление выбирает, какие данные обрабатывать, цикл повторяет обработку для каждой выбранной строки.
- Порядок условий входит в алгоритм: проверка активности стоит раньше проверки остатка.
- Python принимает в условии любой объект, C# требует `bool`, и это различие ловит часть ошибок.
- Короткое замыкание защищает вторую проверку, но делает побочные эффекты в условии опасными.
- Python обходит коллекцию через `for row in rows`, C# через `foreach` или `for` по индексу.
- При переводе сохраняют число повторений, а не символы: `range(n)` и `i < n` дают одинаковый обход.
- Округление вверх при целочисленном делении делают добавкой `pack - 1` до деления.
- Граничные случаи проверяют на пустом списке, одном элементе, последнем элементе и значении на пороге.
- Ошибка управления может выглядеть как успешная проверка: случай Apple и случай Patriot показывают цену такого совпадения.

- Суммирует все остатки на складе
- Сортирует позиции по категории

- Чтобы избежать деления на ноль
- Чтобы перевести штуки в коробки без остатка
! Добавка перед целочисленным делением даёт округление вверх.

- Цикл пропустит последнюю строку
- Программа не соберётся

Q: Где нужно объявить накопитель итога?

- Внутри тела цикла, рядом с расчётом
- После цикла, перед выводом
- В условии цикла
! Переменная внутри тела создаётся заново на каждой итерации.

Q: Почему в C# запись `if (quantity)` не компилируется?

- Компилятор требует `switch`
- Переменная должна быть строкой

- Цикл завершится досрочно без сообщения
- Компилятор запретит сборку
! Перечислитель замечает изменение коллекции и выбрасывает исключение.

- Список пуст и не создан
- В условии использована строка вместо числа
! Ошибка возникает, когда запрашивают элемент с несуществующим индексом.
