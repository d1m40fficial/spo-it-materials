01Понедельник, 08:55

После выходных стенд запускают, и на хосте привычно вводится команда:

$ ssh -p 2222 student@127.0.0.1
ssh: connect to host 127.0.0.1 port 2222: Connection refused

При этом браузер в госте открывает сайты, ping 8.8.8.8 проходит, а сайт учебного колледжа загружается. Напрашивается вывод: «сеть работает, сломался SSH». Второй взгляд на ту же ошибку даёт другую версию: «пропал интернет». Оба вывода поспешны, потому что смотрят на разные слои и называют причиной тот, который заметили.

Сеть ломается послойно, и проверять её нужно в том же порядке, в каком собирается соединение. Сначала есть ли адрес у интерфейса, потом есть ли маршрут до сети, потом разрешается ли имя, потом слушает ли порт, потом отвечает ли служба. Каждый шаг отсекает часть причин. Прыжок через слой экономит минуту, но обычно уводит не туда.

В этой лекции пять инструментов: ip для адресов и маршрутов, ping для доступности, traceroute для пути, ss для портов и journalctl для служб. В Windows им соответствуют ipconfig, Test-NetConnection, tracert, netstat и журнал событий. Команды разные, логика одна.

02Свой адрес и интерфейс

Проверка начинается с собственного компьютера. Пока у интерфейса нет адреса, внешние команды бессмысленны: они не знают, откуда отправлять пакет.

$ ip -br a
lo               UNKNOWN        127.0.0.1/8 ::1/128
enp0s3           UP             10.0.2.15/24 fe80::a00:27ff:fe4e:66a1/64

Короткий формат -br показывает интерфейс, состояние и адреса. lo это петлевой интерфейс: через него программа обращается к самой машине по адресу 127.0.0.1. enp0s3 это сетевой адаптер VirtualBox, состояние UP означает, что кабель виртуально подключён. Если состояние DOWN, адреса может не быть вовсе.

Запись 10.0.2.15/24 содержит адрес и маску. Маска /24 означает 24 бита сети и 8 бит узла: сеть 10.0.2.0, широковещательный адрес 10.0.2.255, допустимые узлы от 10.0.2.1 до 10.0.2.254. Адрес 10.0.2.15 принадлежит диапазону частных сетей 10.0.0.0/8, который не маршрутизируется в интернете напрямую.

Диапазон Маска Назначение
10.0.0.0 /8 крупные частные сети
172.16.0.0 /12 частные сети среднего размера
192.168.0.0 /16 домашние и офисные сети
127.0.0.0 /8 петлевой интерфейс
169.254.0.0 /16 автоматические адреса при сбое DHCP

Адрес 169.254.x.x заслуживает отдельного внимания. Его система назначает сама, когда не получила ответ от DHCP. Такой адрес позволяет общаться только внутри одного сегмента и почти всегда означает, что проблема в DHCP или в кабеле, а не в DNS. Увидели 169.254 на интерфейсе, начинайте с режима сети и DHCP, а не с браузера.

Полную информацию об интерфейсе показывает ip addr show enp0s3. Там видны MAC-адрес, состояние state UP, флаг BROADCAST,MULTICAST, срок аренды адреса и статистика ошибок. Счётчики RX errors и TX dropped полезны, когда связь есть, но пакеты теряются.

В Windows ту же картину дают две команды.

> ipconfig /all
> Get-NetIPConfiguration

ipconfig /all показывает адаптеры, физические адреса, DHCP, шлюз и DNS. Get-NetIPConfiguration выдаёт те же сведения объектами PowerShell, с которыми удобно работать в сценариях. Для быстрой проверки адреса достаточно ipconfig.

Задача Linux Windows
Показать адреса ip -br a ipconfig
Подробно об адаптере ip addr show enp0s3 ipconfig /all
Включить интерфейс sudo ip link set enp0s3 up Enable-NetAdapter
Показать MAC ip link show enp0s3 Get-NetAdapter

03Маршрут по умолчанию

Адрес говорит, кто мы. Маршрут говорит, куда отправлять пакет. Если адрес есть, а маршрута нет, пакет не покинет машину.

$ ip route
default via 10.0.2.2 dev enp0s3 proto dhcp src 10.0.2.15 metric 100
10.0.2.0/24 dev enp0s3 proto kernel scope link src 10.0.2.15 metric 100

Первая строка это маршрут по умолчанию: всё, что не попало в известные сети, уходит через 10.0.2.2 на интерфейсе enp0s3. Вторая строка описывает локальную сеть 10.0.2.0/24: она подключена напрямую, шлюз для неё не нужен. Такую сеть называют connected, потому что маршрут к ней создаётся автоматически при назначении адреса.

Когда адресов и маршрутов несколько, система выбирает самый конкретный. Правило называется longest prefix match: из подходящих маршрутов побеждает тот, у которого длиннее маска. Поэтому маршрут /24 важнее маршрута /8, а маршрут по умолчанию с маской /0 применяется последним.

Проверить, какой маршрут будет выбран для конкретного адреса, можно командой ip route get.

$ ip route get 8.8.8.8
8.8.8.8 via 10.0.2.2 dev enp0s3 src 10.0.2.15 uid 1000
    cache

Команда не отправляет пакет. Она показывает решение маршрутизатора: адрес назначения, шлюз, интерфейс и источник. Если в ответе unreachable или Network is unreachable, маршрута нет, и ping не поможет.

В VirtualBox режим NAT устроен так: гость видит сеть 10.0.2.0/24, свой адрес 10.0.2.15, шлюз 10.0.2.2 и DNS 10.0.2.3. Шлюз 10.0.2.2 это виртуальный маршрутизатор, который выходит в сеть хоста. Хост для гостя тоже виден по адресу 10.0.2.2, но входящие соединения к гостю через этот адрес не проходят. Для них настроен проброс: хост слушает 127.0.0.1:2222 и передаёт соединение на 10.0.2.15:22.

Адрес Кто это Доступность
10.0.2.15 гость ubuntu-lab из гостя и через проброс
10.0.2.2 шлюз NAT и хост из гостя
10.0.2.3 DNS VirtualBox из гостя
127.0.0.1:2222 проброс на хосте только с хоста

В Windows таблицу маршрутов показывает route print или Get-NetRoute. Ищите строку с destination 0.0.0.0 и маской 0.0.0.0: это маршрут по умолчанию. Если таких строк две с одинаковой метрикой, пакеты могут уходить в неожиданную сторону. Метрика это цена маршрута: чем меньше число, тем он предпочтительнее.

04Имена и DNS

Человеку удобно помнить имя, компьютеру нужен адрес. Преобразование имени в адрес выполняет служба DNS. Запрос идёт к серверу, адрес которого система получила по DHCP или задал администратор.

В Ubuntu 22.04 разрешением имён управляет systemd-resolved. Файл /etc/resolv.conf обычно является ссылкой на заглушку и содержит адрес 127.0.0.53: это локальный сервер, который принимает запросы и передаёт их настоящему DNS.

$ resolvectl status
Global
       Protocols: -LLMNR -mDNS -DNSOverTLS DNSSEC=no/unsupported
resolv.conf mode: stub

Link 2 (enp0s3)
    Current Scopes: DNS
         Protocols: +DefaultRoute
Current DNS Server: 10.0.2.3
       DNS Servers: 10.0.2.3

Строка Current DNS Server показывает, куда уходят запросы. Если здесь пусто, имя не разрешится, даже когда ping по адресу работает. Проверить конкретное имя можно командой resolvectl query ubuntu.com или getent hosts ubuntu.com.

$ getent hosts ubuntu.com
185.125.190.36  ubuntu.com
185.125.190.37  ubuntu.com

Команда getent хороша тем, что использует те же источники, что и обычные программы: файл /etc/hosts, DNS и другие базы. Если getent имя находит, а браузер нет, проблема не в DNS, а в прокси или самом браузере. Если не находит, дальше проверяют сервер и зону.

Утилита dig показывает больше деталей: тип записи, время ответа, авторитетный сервер. Для краткого ответа достаточно dig +short ubuntu.com. В Ubuntu пакет dnsutils может быть не установлен, тогда dig и nslookup отсутствуют. Это не признак поломки сети, а отсутствие инструмента.

$ dig +short ubuntu.com
185.125.190.36
185.125.190.37

Файл /etc/hosts проверяется раньше DNS. Запись 127.0.0.1 localhost и 10.0.2.15 ubuntu-lab работают без сети. Если имя добавлено в /etc/hosts, DNS для него не запрашивается. Этим пользуются, когда нужно закрепить имя за адресом на одной машине.

В Windows имя разрешает Resolve-DnsName, а классическая команда nslookup показывает выбранный сервер. ipconfig /displaydns выводит кеш, ipconfig /flushdns его очищает. Кеш объясняет странный симптом: имя уже указывает на старый адрес, хотя запись в DNS изменена. Очистка кеша решает проблему без правки сети.

Ошибки DNS выглядят по-разному. NXDOMAIN означает, что имени не существует. Тайм-аут означает, что сервер не ответил. Отказ SERVFAIL означает, что сервер не смог обработать запрос. Лечение у них разное: в первом случае проверяют написание имени, во втором доступность сервера, в третьем зону и настройки сервера. Команда ping смешивает эти случаи в одно сообщение Name or service not known, поэтому для диагностики лучше getent или dig.

05Порты и сокеты

Адрес доставляет пакет на компьютер. Порт указывает, какой программе его отдать. Порт это число от 0 до 65535, которое вместе с адресом и протоколом образует сокет. Один компьютер может одновременно слушать десятки портов, и каждый принадлежит своей службе.

Диапазон Название Кто использует
0-1023 системные порты службы с повышенными правами
1024-49151 зарегистрированные приложения и серверы
49152-65535 динамические временные соединения клиентов

В Linux диапазон временных портов задан в /proc/sys/net/ipv4/ip_local_port_range, обычно от 32768 до 60999. В Windows динамический диапазон начинается с 49152. Когда браузер открывает сайт, он получает временный порт, а сервер отвечает с порта 443. Пара адресов и портов делает соединение уникальным.

Список слушающих сокетов показывает ss. Флаг -t оставляет TCP, -u добавляет UDP, -l показывает только слушающие, -p показывает процесс, -n запрещает преобразование портов в имена служб.

$ sudo ss -tulpn
Netid State  Recv-Q Send-Q Local Address:Port  Peer Address:Port Process
udp   UNCONN 0      0          127.0.0.53:53        0.0.0.0:*     users:(("systemd-resolve",pid=621,fd=13))
tcp   LISTEN 0      4096         0.0.0.0:22          0.0.0.0:*     users:(("sshd",pid=812,fd=3))
tcp   LISTEN 0      4096            [::]:22             [::]:*     users:(("sshd",pid=812,fd=3))

Строка 0.0.0.0:22 означает, что SSH слушает все адреса на машине. Строка 127.0.0.1:22 означала бы, что подключиться можно только с самой машины, и проброс порта с хоста не сработал бы. Это одна из самых частых причин «порт открыт, но снаружи недоступен».

Состояния сокетов помогают понять, что происходит. LISTEN ждёт входящее соединение. ESTAB означает установленное соединение. TIME-WAIT остаётся после закрытия и держится около минуты, чтобы поздние пакеты не попали в новое соединение. Много TIME-WAIT это нормально для нагруженного клиента, а не утечка.

$ ss -tan
State      Recv-Q Send-Q Local Address:Port   Peer Address:Port
LISTEN     0      4096       0.0.0.0:22          0.0.0.0:*
ESTAB      0      0      10.0.2.15:22        10.0.2.2:51432
TIME-WAIT  0      0      10.0.2.15:22        10.0.2.2:51430

В Windows аналог это netstat -ano. Флаг -a показывает все сокеты, -n числовые адреса, -o идентификатор процесса. В PowerShell удобнее Get-NetTCPConnection, который сразу отдаёт объекты с полями LocalAddress, LocalPort, State, OwningProcess.

> netstat -ano | findstr :22
  TCP    0.0.0.0:22             0.0.0.0:0              LISTENING       1420

> Get-NetTCPConnection -LocalPort 22 -State Listen
LocalAddress LocalPort State  OwningProcess
------------ --------- -----  -------------
0.0.0.0             22 Listen          1420

Имя процесса по идентификатору находит Get-Process -Id 1420. В Linux ту же роль играет lsof -i :22 или ss -p. Не путайте порт и службу: порт может быть открыт, а служба за ним зависшей. Тогда соединение устанавливается, но ответа нет.

06Проверка доступности узла

ping отправляет ICMP-запрос Echo Request и ждёт Echo Reply. Успешный ответ означает, что пакет дошёл до узла и вернулся. Это проверка сети, а не службы: веб-сервер может быть недоступен при работающем ping.

$ ping -c 4 10.0.2.2
PING 10.0.2.2 (10.0.2.2) 56(84) bytes of data.
64 bytes from 10.0.2.2: icmp_seq=1 ttl=64 time=0.31 ms
64 bytes from 10.0.2.2: icmp_seq=2 ttl=64 time=0.28 ms
64 bytes from 10.0.2.2: icmp_seq=3 ttl=64 time=0.30 ms
64 bytes from 10.0.2.2: icmp_seq=4 ttl=64 time=0.29 ms

--- 10.0.2.2 ping statistics ---
4 packets transmitted, 4 received, 0% packet loss, time 3004ms
rtt min/avg/max/mdev = 0.280/0.295/0.310/0.012 ms

Низкое время и отсутствие потерь говорят о хорошем канале. Высокое время или потери говорят о перегрузке, плохом канале или проблеме на стороне узла. Отсутствие ответа не всегда означает, что узел выключен: многие серверы и межсетевые экраны блокируют ICMP. Поэтому отрицательный ping это повод проверить порт, а не окончательный диагноз.

traceroute показывает путь до узла. Программа отправляет пакеты с увеличивающимся временем жизни и получает ответы от промежуточных маршрутизаторов. В Linux команда может отсутствовать, тогда её ставят пакетом traceroute; tracepath входит в базовые утилиты и работает без прав root.

$ traceroute 8.8.8.8
traceroute to 8.8.8.8 (8.8.8.8), 30 hops max, 60 byte packets
 1  10.0.2.2 (10.0.2.2)  0.301 ms  0.287 ms  0.275 ms
 2  * * *
 3  * * *

В NAT первый прыжок это шлюз 10.0.2.2. Звёздочки означают, что промежуточный узел не ответил на служебный пакет. Это не обязательно авария: многие маршрутизаторы не отвечают на такие запросы. Если при этом конечный узел доступен, путь считается рабочим.

Проверка порта отличается от проверки узла. Программа nc открывает TCP-соединение с указанным портом и сообщает, удалось ли оно. curl делает HTTP-запрос и показывает код ответа. ssh -v печатает этапы рукопожатия.

$ nc -zv 10.0.2.15 22
Connection to 10.0.2.15 22 port [tcp/ssh] succeeded!

$ curl -I http://example.com
HTTP/1.1 200 OK
Content-Type: text/html

Если порт закрыт, nc получает отказ Connection refused. Если порт фильтруется межсетевым экраном, соединение зависает до тайм-аута. Разница принципиальна: отказ означает, что пакет дошёл до узла и узел ответил сбросом; тайм-аут означает, что ответа нет и, возможно, пакет отброшен по пути.

В Windows Test-NetConnection объединяет проверку узла и порта.

> Test-NetConnection 127.0.0.1 -Port 2222
ComputerName           : 127.0.0.1
RemoteAddress          : 127.0.0.1
RemotePort             : 2222
TcpTestSucceeded       : True

TcpTestSucceeded : True означает, что TCP-соединение установлено. Если False, смотрят, слушает ли кто-то порт на другой стороне и не блокирует ли его межсетевой экран. Для проверки имени Test-NetConnection умеет разрешать имя и показывать адрес, но не заменяет Resolve-DnsName.

07Порядок диагностики

Диагностика идёт от ближнего слоя к дальнему. На каждом шаге записывается результат, чтобы не проверять одно и то же дважды.

Шаг Что проверяем Linux Windows Признак проблемы
1 Интерфейс ip -br a Get-NetAdapter состояние DOWN, нет адреса
2 Адрес и маска ip addr show ipconfig /all адрес 169.254, неверная маска
3 Шлюз ping -c 3 10.0.2.2 Test-Connection 10.0.2.2 шлюз не отвечает
4 Маршрут ip route get 8.8.8.8 Find-NetRoute 8.8.8.8 нет маршрута по умолчанию
5 DNS resolvectl query имя Resolve-DnsName имя имя не разрешается
6 Порт nc -zv узел порт Test-NetConnection -Port отказ или тайм-аут
7 Служба ss -tlnp, systemctl status Get-Service, Get-NetTCPConnection порт не слушается
8 Журнал journalctl -u служба Get-WinEvent ошибка запуска

Шаг 3 не обязателен, если шаг 4 уже показал маршрут, но он полезен для разделения «нет маршрута» и «маршрут есть, но шлюз не отвечает». Шаг 5 пропускают, когда проверяют соединение по адресу. Шаг 6 не поможет, если порт слушается только на петлевом интерфейсе: тогда проверять нужно адрес привязки, а не доступность.

Журнал службы отвечает на вопрос, почему порт не открылся. В Linux journalctl -u ssh -n 50 --no-pager показывает последние записи, systemctl status ssh состояние и код выхода. В Windows Get-WinEvent -LogName System -MaxEvents 50 показывает системные события, а оснастка «Просмотр событий» позволяет отфильтровать их по источнику и уровню.

Если служба запускается и сразу падает, причина обычно в конфигурации или занятом порту. Сообщение Address already in use означает, что порт уже слушает другой процесс. Его находят через ss -tlnp и завершают или перенастраивают. Сообщение Permission denied на порту ниже 1024 означает, что служба запущена без нужных прав.

08Разбор утреннего отказа

Вернёмся к началу лекции. Браузер в госте открывает сайты, ping 8.8.8.8 проходит, а SSH с хоста получает отказ. Значит, слои до порта включительно исправны: адрес есть, маршрут есть, DNS работает, внешняя сеть доступна. Отказ Connection refused говорит о том, что хост получил ответ от узла, но на порту 2222 никто не слушает.

Дальше проверяют две стороны проброса. На хосте Test-NetConnection 127.0.0.1 -Port 2222 показывает TcpTestSucceeded : False, если правило не создано или порт занят. В VirtualBox правило должно связывать 127.0.0.1:2222 с 10.0.2.15:22. Если адрес гостя в правиле устарел, VirtualBox передаёт соединение в никуда.

В госте проверяют службу и адрес привязки.

$ systemctl status ssh --no-pager
● ssh.service - OpenBSD Secure Shell server
     Loaded: loaded (/lib/systemd/system/ssh.service; enabled; vendor preset: enabled)
     Active: inactive (dead)

$ sudo systemctl start ssh
$ sudo ss -tlnp | grep :22
LISTEN 0 4096 0.0.0.0:22 0.0.0.0:* users:(("sshd",pid=812,fd=3))

Неактивная служба объясняет отказ полностью: порт закрыт, узел отвечает сбросом. После запуска службы соединение проходит. Если служба активна, а порт слушается только на 127.0.0.1, проброс не поможет: пакет приходит на адрес 10.0.2.15, а SSH его не принимает. В этом случае правят ListenAddress в конфигурации или проверяют, не переопределён ли адрес в дополнительном файле настроек.

Тайм-аут вместо отказа вёл бы к другой ветке. Он означал бы, что пакет не доходит: правило проброса не работает, адаптер выключен или межсетевой экран хоста блокирует порт. Разница между двумя сообщениями экономит полчаса поиска.

09Типичные ошибки

Ошибка Симптом Что проверить
Два DHCP-сервера адрес из чужой сети, нестабильная связь ip addr, журнал DHCP
Неверная маска сосед по сети не пингуется /24 вместо /16
Два маршрута по умолчанию часть сайтов открывается, часть нет ip route, метрики
DNS недоступен по адресу работает, по имени нет resolvectl status
Служба слушает 127.0.0.1 снаружи порт закрыт ss -tlnp
Порт занят другой программой служба не стартует Address already in use
Межсетевой экран блокирует соединение зависает ufw status, правила
ICMP заблокирован ping не проходит, сайт открывается проверить порт напрямую

Отдельная ошибка это путаница между NAT и локальной сетью. В NAT гость выходит наружу, но снаружи к нему не подключиться без проброса. Если ждать соединения с соседнего компьютера по адресу 10.0.2.15, ждать придётся напрасно: этот адрес существует только внутри NAT. Для входящих соединений нужен проброс, а для обмена файлами между машинами стенда проще использовать общую папку.

Ещё одна ошибка это вывод по одной команде. ping не прошёл, значит сеть мертва; сайт открылся, значит сеть здорова. Оба вывода поспешны. Одна команда проверяет один слой. Диагностика это последовательность проверок с записью результатов, а не поиск одной волшебной команды.

10Итоги

  • Проверка сети идёт по слоям: интерфейс, адрес, шлюз, маршрут, DNS, порт, служба, журнал.
  • ip -br a и ip route показывают адрес и маршрут, ip route get объясняет выбор пути.
  • Адрес 169.254.x.x указывает на сбой DHCP, а не на DNS.
  • getent и resolvectl проверяют имена теми же источниками, что и программы.
  • ss -tulpn показывает, кто слушает порт и на каком адресе.
  • Отказ в соединении и тайм-аут означают разные причины, и лечатся они по-разному.
  • Одна команда проверяет один слой; вывод делается по последовательности результатов.

Команда проверяет именно TCP-соединение с указанным портом.

Маска задаёт границу между сетью и узлом.

Сокет определяется адресом, портом и протоколом.
