01Накладная без поставщика

Кладовщик магазина «Страница» увольняется, а его учётную запись ещё не заблокировали. В пятницу он наводит порядок в справочнике и удаляет поставщика, с которым магазин больше не работает. В понедельник бухгалтер открывает накладные за август и видит странную картину: суммы на месте, книги на месте, а поле «поставщик» пустое у сорока документов. Восстановить, у кого закупали тираж, можно только по бумажным папкам.

Причина не в ошибке интерфейса. База разрешила удалить строку, на которую ссылались другие строки, потому что никто не запретил это делать. Данные остались синтаксически целыми, но потеряли смысл: накладная ссылается в пустоту.

Целостность данных это набор правил, при которых база не содержит противоречивых и неполных записей. Правила бывают трёх видов, и каждое отвечает на свой вопрос.

Вид целостности Вопрос, на который отвечает Что защищает
Сущностная существует ли сама строка как объект первичный ключ, обязательность
Ссылочная существует ли объект, на который ссылаются внешний ключ
Доменная допустимо ли значение в ячейке тип, CHECK, NOT NULL, DEFAULT

Разделение полезно не для экзамена, а для разбора сбоя. Когда в отчёте пустой поставщик, вы ищете нарушение ссылочной целостности. Когда в заказе отрицательная цена, вы ищете доменную. Когда в таблице две строки описывают одну и ту же книгу, вы ищете сущностную.

02Сущностная целостность

Сущностная целостность требует, чтобы каждую строку можно было отличить от любой другой и чтобы у строки был идентификатор. На практике это первичный ключ и запрет пустых значений в нём.

CREATE TABLE kniga (
  id INTEGER PRIMARY KEY,
  isbn TEXT NOT NULL UNIQUE,
  nazvanie TEXT NOT NULL
);

INSERT INTO kniga (isbn, nazvanie) VALUES ('978-5-4461-0990-6', 'Чистый код');
INSERT INTO kniga (isbn, nazvanie) VALUES ('978-5-4461-0990-6', 'Чистый код. Второе издание');

UNIQUE constraint failed: kniga.isbn

Вторая строка отклонена, и это правильно: две записи описывают одно издание. Но одной уникальности мало. Если разрешить NULL в ключе, появятся строки, которые нельзя найти и нельзя связать. В SQLite текстовый первичный ключ без NOT NULL пропускает пустые значения, поэтому обязательность задают явно:

CREATE TABLE ploshchadka (
  kod TEXT PRIMARY KEY NOT NULL,
  nazvanie TEXT NOT NULL,
  gorod TEXT NOT NULL
);

Проверка NOT NULL срабатывает и на обычных столбцах. Если у книги нет названия, строка бесполезна для продавца, поэтому nazvanie TEXT NOT NULL это тоже часть сущностной целостности: объект без имени не является полноценным объектом.

Есть тонкость с INTEGER PRIMARY KEY в SQLite. Такой столбец связан со скрытым номером строки, и при вставке NULL база сама подставляет следующий номер. Это удобно для суррогатных ключей, но означает, что проверить обязательность через NULL не получится: значение появится автоматически. Для текстовых ключей автоматической подстановки нет.

Сущностная целостность страдает не только от дублей. Она ломается, когда ключ переиспользуют: удалили сотрудника, а его табельный номер отдали новому. Старые накладные начинают указывать на другого человека, хотя формально ссылка существует. Ограничениями это не лечится, помогает только правило не переиспользовать ключи.

03Ссылочная целостность

Ссылочная целостность требует, чтобы внешний ключ указывал на существующую строку родительской таблицы. В накладной есть postavshchik_id, и значение обязано найтись в справочнике поставщиков.

PRAGMA foreign_keys = ON;

CREATE TABLE postavshchik (
  id INTEGER PRIMARY KEY,
  nazvanie TEXT NOT NULL
);

CREATE TABLE nakladnaya (
  id INTEGER PRIMARY KEY,
  nomer TEXT NOT NULL UNIQUE,
  data TEXT NOT NULL,
  postavshchik_id INTEGER NOT NULL REFERENCES postavshchik(id)
);

Если поставщика с номером 12 нет, вставка накладной отклоняется:

FOREIGN KEY constraint failed

Главная особенность SQLite: по умолчанию проверка выключена. PRAGMA foreign_keys возвращает 0, и база спокойно принимает ссылку на несуществующую строку. Включить проверку нужно в каждом сеансе:

PRAGMA foreign_keys = ON;

В sqliteonline.com это первая команда после открытия базы. Если её пропустить, все дальнейшие опыты с внешними ключами покажут не то поведение, которое задумано.

Что происходит при удалении родителя, зависит от действия, указанного в объявлении. По умолчанию действует NO ACTION, которое ведёт себя как запрет: пока есть дочерние строки, удалить поставщика нельзя.

DELETE FROM postavshchik WHERE id = 12;

FOREIGN KEY constraint failed

Это самый безопасный вариант. Он заставляет сначала разобраться с накладными: перенести их на другого поставщика, архивировать или удалить. Ошибка не даёт молча потерять связь.

Обратная ситуация тоже возможна: накладная ссылается на поставщика, которого нет, потому что данные импортировали до включения проверки. Тогда ссылочная целостность уже нарушена, и её ищут запросом:

SELECT count(*) AS sirot
FROM nakladnaya n
LEFT JOIN postavshchik p ON p.id = n.postavshchik_id
WHERE p.id IS NULL;

Ноль означает, что битых ссылок нет. Если число больше нуля, сначала исправляют данные, потом включают ограничение. Иначе PRAGMA foreign_keys = ON не изменит старые строки: он проверяет только новые операции.

Ссылка может быть необязательной. Книга без издательства это редкость, а сотрудник без площадки в момент перевода вполне возможен. Тогда в объявлении остаётся REFERENCES, но столбец допускает NULL:

ploshchadka_id INTEGER REFERENCES ploshchadka(id)

Пустое значение не нарушает ссылочную целостность, потому что ссылки просто нет. Нарушение начинается там, где стоит число, которому не соответствует ни одна строка.

04Каскады и их цена

ON DELETE CASCADE меняет правило: при удалении родителя СУБД сама удаляет дочерние строки. Для строк заказа это удобно. Удалили заказ, и его строки не остались сиротами.

PRAGMA foreign_keys = ON;

CREATE TABLE zakaz (
  id INTEGER PRIMARY KEY,
  data TEXT NOT NULL
);

CREATE TABLE zakaz_stroka (
  zakaz_id INTEGER NOT NULL REFERENCES zakaz(id) ON DELETE CASCADE,
  kniga_id INTEGER NOT NULL,
  kolichestvo INTEGER NOT NULL,
  PRIMARY KEY (zakaz_id, kniga_id)
);

INSERT INTO zakaz VALUES (1001, '2026-09-03'), (1002, '2026-09-03');
INSERT INTO zakaz_stroka VALUES (1001, 5, 2), (1001, 7, 1), (1002, 5, 1);

SELECT count(*) FROM zakaz_stroka;

3

Удалим заказ 1001:

DELETE FROM zakaz WHERE id = 1001;
SELECT count(*) FROM zakaz_stroka;

1

Осталась одна строка, относящаяся к заказу 1002. Каскад сработал молча, без отдельного запроса на удаление строк. В этом и сила, и опасность: одно неверное DELETE может унести больше данных, чем ожидалось. Поэтому каскад ставят там, где дочерняя строка не имеет смысла без родителя: строки заказа, строки накладной, спецификация поставки.

Для справочников чаще выбирают ON DELETE SET NULL. Если издательство ликвидировали, книги не обязаны исчезать, достаточно обнулить ссылку:

CREATE TABLE kniga (
  id INTEGER PRIMARY KEY,
  nazvanie TEXT NOT NULL,
  izdatelstvo_id INTEGER REFERENCES izdatelstvo(id) ON DELETE SET NULL
);

INSERT INTO izdatelstvo VALUES (1, 'Питер');
INSERT INTO kniga VALUES (10, 'Чистый код', 1);
DELETE FROM izdatelstvo WHERE id = 1;
SELECT * FROM kniga;

10|Чистый код|

Книга осталась, ссылка очистилась. Но у этого решения есть цена: отчёт «книги по издательствам» потеряет часть строк, а пользователь увидит пустое поле и не поймёт, почему. SET NULL подходит, когда отсутствие связи допустимо по смыслу, и плохо подходит, когда издательство обязательно.

Третье действие, ON UPDATE CASCADE, переносит изменение ключа на дочерние строки. Оно полезно, если ключ всё-таки меняется: изменили код площадки, и ссылки обновились сами.

PRAGMA foreign_keys = ON;
UPDATE izdatelstvo SET id = 77 WHERE id = 1;
SELECT * FROM kniga;

10|Чистый код|77

Соблазн включить каскад на всё велик, но это перекладывает решение на СУБД. Каскад не спрашивает, тот ли это заказ и та ли это книга. Если бизнес-правило требует сначала проверить остатки или сохранить историю, каскад мешает. Поэтому в учебной базе правило простое: каскад только для строк документа, которые без документа не существуют, а для справочников запрет или обнуление.

05Доменная целостность

Доменная целостность отвечает за значения в ячейках. У цены есть допустимый диапазон, у статуса заказа список значений, у даты формат, у названия ограничение длины. Всё это задаётся типом и ограничениями столбца.

CREATE TABLE zakaz (
  id INTEGER PRIMARY KEY,
  data TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'новый'
    CHECK (status IN ('новый', 'оплачен', 'выдан', 'отменён'))
);

INSERT INTO zakaz (id, data, status) VALUES (1001, '2026-09-03', 'доставлен');

CHECK constraint failed: status IN ('новый', 'оплачен', 'выдан', 'отменён')

Проверка CHECK это произвольное логическое условие. Оно может быть простым, как cena > 0, или составным, как data_okonchaniya >= data_nachala. Главное, чтобы условие было истинным для каждой допустимой строки и ложным хотя бы для одной недопустимой.

NOT NULL относится к доменной целостности, когда речь о значении столбца, и к сущностной, когда речь о ключе. Это не противоречие: одно ограничение может защищать два правила. Важно понимать, какое именно правило вы формулируете. «У заказа всегда есть дата» это доменное требование. «Строку заказа можно найти по паре» это сущностное.

DEFAULT не проверяет значение, а подставляет его, когда столбец не указан:

INSERT INTO zakaz (id, data) VALUES (1001, '2026-09-03');
SELECT id, status FROM zakaz;

1001|новый

Значение по умолчанию должно само проходить все проверки. Если DEFAULT 'ожидает', а CHECK разрешает только четыре статуса, вставка без статуса упадёт. Это частая ошибка при изменении справочника статусов: ограничение обновили, значение по умолчанию забыли.

С типами в SQLite отдельная история. Это динамическая СУБД: тип столбца скорее рекомендация, чем жёсткий запрет. В таблицу с cena INTEGER можно вставить строку 'дорого', и она сохранится как текст:

CREATE TABLE kniga (
  id INTEGER PRIMARY KEY,
  cena INTEGER NOT NULL CHECK (cena > 0)
);

INSERT INTO kniga (cena) VALUES ('дорого');
SELECT id, cena, typeof(cena) FROM kniga;

1|дорого|text

Проверка cena > 0 не сработала, потому что в SQLite текст при сравнении с числом считается больше любого числа. Формально условие истинно, фактически цена бессмысленна. Есть два способа закрыть дыру. Первый: объявить таблицу строгой.

CREATE TABLE kniga (
  id INTEGER PRIMARY KEY,
  cena INTEGER NOT NULL CHECK (cena > 0)
) STRICT;

INSERT INTO kniga (cena) VALUES ('дорого');

cannot store TEXT value in INTEGER column kniga.cena

Второй способ: проверять тип явно через typeof.

CREATE TABLE kniga (
  id INTEGER PRIMARY KEY,
  cena INTEGER NOT NULL
    CHECK (typeof(cena) = 'integer' AND cena > 0)
);

Оба варианта рабочие. В учебной базе достаточно STRICT для новых таблиц: он запрещает хранить текст в числовом столбце и не требует помнить про typeof в каждом CHECK.

06Где записывают ограничения

Ограничение можно объявить в строке столбца или отдельной строкой таблицы. Разница важна для составных правил.

CREATE TABLE zakaz_stroka (
  zakaz_id INTEGER NOT NULL REFERENCES zakaz(id) ON DELETE CASCADE,
  kniga_id INTEGER NOT NULL REFERENCES kniga(id),
  kolichestvo INTEGER NOT NULL CHECK (kolichestvo > 0),
  cena INTEGER NOT NULL CHECK (cena > 0),
  PRIMARY KEY (zakaz_id, kniga_id)
);

Здесь PRIMARY KEY и FOREIGN KEY занимают отдельные строки, потому что описывают набор столбцов. Ограничение столбца может ссылаться только на сам столбец, ограничение таблицы видит всю строку. Отсюда правило: если условие сравнивает два столбца, его место в конце таблицы.

CREATE TABLE postavka (
  id INTEGER PRIMARY KEY,
  data_nachala TEXT NOT NULL,
  data_okonchaniya TEXT NOT NULL,
  CHECK (data_okonchaniya >= data_nachala)
);

Порядок проверок при вставке тоже имеет значение. Сначала СУБД проверяет типы и NOT NULL, затем CHECK, затем уникальность и внешние ключи. Если строка нарушает несколько правил, вы увидите только первое сработавшее. Поэтому ошибку исправляют по одной, а не пытаются угадать все сразу.

Имена ограничений лучше задавать явно, особенно когда их много:

CONSTRAINT cena_polozhitelna CHECK (cena > 0)

Имя попадает в сообщение об ошибке и помогает найти виновника в большом скрипте. В SQLite имя можно указать и у UNIQUE, и у FOREIGN KEY.

07Что ограничения не ловят

Ограничения проверяют одну строку или ссылку между строками. Они не проверяют смысл операции целиком. Сумма строк заказа должна равняться итогу в заголовке, но CHECK не умеет считать по другой таблице. Сотрудник не может работать на двух площадках в один день, но это правило затрагивает несколько строк и время. Товар нельзя продать дешевле закупки, а цена закупки лежит в другой таблице.

Такие правила называют бизнес-правилами, и реализуют их в приложении, в триггерах или в транзакции с проверкой перед записью. Ограничения остаются фундаментом: они не дают появиться заведомо битой строке, а приложение отвечает за смысл. Если перенести всё в приложение, рано или поздно найдётся скрипт, который вставит данные в обход.

Есть и отложенная проверка. Внешний ключ можно объявить DEFERRABLE INITIALLY DEFERRED, тогда он проверяется в конце транзакции. Это нужно, когда две таблицы ссылаются друг на друга и вставить их можно только парой. В SQLite отложенные внешние ключи поддерживаются, но в учебных задачах почти не нужны: проще создать таблицы в правильном порядке.

Наконец, ограничения не спасают от ошибки проектирования. Если в таблице книги хранится название издательства текстом, NOT NULL и CHECK будут исправно работать, а название всё равно продублируется в тысяче строк и разойдётся при первом переименовании. Это уже не целостность отдельной строки, а нормализация, и ею мы займёмся дальше.

08Как проверить, что ограничения работают

Схему проверяют не чтением, а попыткой нарушить каждое правило. Для NOT NULL вставляют строку без обязательного столбца, для UNIQUE повторяют значение, для CHECK подставляют запрещённое. Каждая попытка должна завершиться ошибкой с именем ограничения. Если вставка прошла, значит правило не работает или написано не там.

Ссылки проверяют отдельно. PRAGMA foreign_key_check возвращает строки, которые ссылаются на несуществующих родителей:

PRAGMA foreign_key_check;

Пустой результат означает, что битых ссылок нет. Этот запрос полезен после импорта и перед сдачей работы: он видит старые нарушения, которые не ловятся при вставке новых строк. Полную проверку файла базы выполняет PRAGMA integrity_check, но она ищет повреждения страниц, а не смысловые ошибки.

09Типичные ошибки

Проверка внешних ключей выключена. Самая частая причина «странных» результатов в SQLite. PRAGMA foreign_keys = ON должен стоять в начале скрипта, а не в конце.

Каскад включён везде. Удаление одной книги уносит строки заказов, а удаление заказа уносит историю продаж. Каскад уместен для строк документа, но не для справочников и не для истории.

CHECK написан, но пропускает мусор. Условие cena > 0 не мешает тексту в динамической таблице. Проверяйте typeof или используйте STRICT.

DEFAULT противоречит CHECK. Значение по умолчанию добавлено раньше, чем расширили список статусов. Вставка без статуса начинает падать, хотя в схеме всё выглядит логично.

Ограничение объявлено не на том уровне. Условие, сравнивающее два столбца, записано в строке столбца и не видит второй. Его место в конце таблицы.

Дубликаты ищут только ограничением. UNIQUE не исправит уже существующие повторы. Сначала запрос с GROUP BY и HAVING, потом очистка, потом ограничение.

Проверка ограничений должна входить в приёмку схемы, а не выполняться один раз при разработке. Новый столбец, новое правило или импорт данных могут обойти старую проверку, и тогда ошибка вернётся через месяц.

10Итоги

  • Сущностная целостность даёт каждой строке уникальный и обязательный идентификатор.
  • Ссылочная целостность требует, чтобы внешний ключ указывал на существующую строку.
  • Доменная целостность ограничивает значения типом, NOT NULL, CHECK и DEFAULT.
  • В SQLite внешние ключи включают командой PRAGMA foreign_keys = ON, иначе проверка не работает.
  • Каскад удобен для строк документа и опасен для справочников и истории.
  • Ограничения защищают отдельную строку, а правила на несколько строк остаются за приложением и транзакциями.

01Почему CHECK (cena > 0) может пропустить текст в SQLite?
